# guides

`guides`는 모든 기술을 한 번씩 훑는 백과사전이 아니다. 개발자가 원하는 업무 분야의 프로젝트에 진입할 수 있도록 **선행 지식, 책임 경계, 실패 조건, 검증 방법과 다음 학습 경로**를 연결한 브랜치형 학습 저장소다. 동시에 `main`은 새 브랜치가 기존 브랜치와 같은 구조·품질·완성도를 갖추었는지 사람이 검토하는 기준점이다.

현재 카탈로그는 **26개 학습 브랜치와 16개 업무 트랙**으로 구성된다. 각 브랜치는 독립적인 학습 결과를 가지며, `main`은 브랜치 전체를 다음 관점으로 연결한다.

- 어떤 업무를 목표로 하는가
- 어떤 브랜치가 필수이고 무엇이 선택인가
- 각 브랜치가 무엇을 소유하고 무엇을 다른 브랜치에 맡기는가
- 완료 뒤 어떤 크기의 실제 변경에 참여할 수 있는가
- 가이드 이후 프로젝트·오픈소스·운영 경험으로 어떻게 이동하는가
- 새 브랜치를 어떤 공통 계약과 사람 검토로 `stable` 승인하는가

## 시작

1. [`guides 사용법`](docs/00-how-to-use-guides.md)에서 이 저장소의 종료 기준을 확인한다.
2. [`업무 트랙`](docs/03-career-tracks.md)에서 목표 분야를 선택한다.
3. [`브랜치 의존성 지도`](docs/04-dependency-map.md)에서 필수·권장·심화 관계를 확인한다.
4. 각 브랜치 README의 학습 순서와 검증 명령을 따른다.
5. 완료 뒤 [`가이드에서 실제 프로젝트로 이동하기`](docs/06-from-guide-to-project.md)를 따른다.

로컬에서 선택한 브랜치로 바로 전환할 수 있다.

```sh
git switch python
```

`main`의 로드맵을 그대로 열어 둔 채 학습하려면 별도 worktree를 만든다.

```sh
git worktree add ../guides-python python
cd ../guides-python
```

새 브랜치를 설계하거나 검토한다면 [`브랜치 품질 계약`](docs/09-branch-quality-contract.md)과 [`기여 안내`](CONTRIBUTING.md)에서 시작한다.

## 중요한 원칙

- **모든 브랜치를 완료하지 않는다.** 목표 업무의 필수 경로만 먼저 진행한다.
- **언어 개수가 실력을 의미하지 않는다.** 한 분야의 상태·실패·검증을 독립적으로 소유할 수 있어야 한다.
- **브랜치 완료는 전문가 인증이 아니다.** 트랙의 기본 목표는 기존 프로젝트에 합류해 작은 변경을 독립적으로 완성할 준비를 갖추는 것이다.
- **브랜치·트랙·프로젝트 완료는 서로 다르다.** 브랜치는 한 학습 범위, 트랙은 목표 업무의 필수 경로, 프로젝트는 실제 제약 속의 반복 기여로 판단한다.
- **전문성은 실제 프로젝트에서 형성된다.** 운영 장애, 성능 병목, 보안 문제, 마이그레이션과 반복 기여가 깊이를 만든다.
- **중복 설명보다 경계 연결을 우선한다.** 이미 다른 브랜치가 소유한 원리는 필요한 절을 참조한다.
- **`stable`은 사람이 승인한다.** 자동 검사는 기계적 무결성을 돕지만 교육적 품질과 실제 완성을 증명하지 않는다.

## 기계 판독 가능한 카탈로그

- [`catalog/branches.json`](catalog/branches.json): 브랜치 종류, 의존성, 소유·비소유 범위와 종료 능력
- [`catalog/tracks.json`](catalog/tracks.json): 업무 트랙별 공통·필수·권장·심화 브랜치

카탈로그와 문서의 기계적 무결성을 검사한다. 이 결과는 [`브랜치 품질 계약`](docs/09-branch-quality-contract.md)의 사람 검토를 대신하지 않는다.

```sh
./prepare.sh
./verify.sh
```
