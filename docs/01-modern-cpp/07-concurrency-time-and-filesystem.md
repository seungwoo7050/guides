# 동시성·시간·파일 시스템

## 목표

여러 실행 흐름이 같은 상태에 접근할 때 데이터 레이스를 제거하고 안전하게 종료할 수 있는 워커를 설계합니다. 시간과 파일 시스템은 단순한 값이 아니므로 각각의 실패와 변경 특성을 API에 반영합니다.

이 문서의 핵심은 스레드 수를 늘리는 것이 아니라 다음 규칙을 명확히 하는 것입니다.

- 공유 상태를 누가 소유하는가
- 어느 뮤텍스가 어떤 불변식을 보호하는가
- 대기 연산은 어떤 조건을 기다리는가
- 종료 요청은 어디까지 전달되는가
- 시간 제한에는 어떤 시계를 사용하는가
- 파일 변경이 중간에 실패하면 어떤 상태가 남는가

## 시작하기 전에

[알고리즘·ranges·templates·concepts](06-algorithms-ranges-templates-and-concepts.md)를 완료하고 컨테이너 변경과 반복자 무효화 규칙을 설명할 수 있어야 합니다.

## 1. 데이터 레이스와 논리적 경쟁 조건

데이터 레이스는 서로 다른 스레드의 동기화되지 않은 메모리 접근이 충돌하고, 그중 하나 이상이 쓰기이며 해당 접근이 원자적이지 않을 때 발생합니다. C++ 프로그램에 데이터 레이스가 있으면 동작은 정의되지 않습니다.

```cpp
int counter = 0;

// 여러 스레드에서 동기화 없이 실행
++counter;
```

`++counter`는 읽기, 증가, 쓰기가 합쳐진 연산이며 원자적으로 수행된다고 보장되지 않습니다.

데이터 레이스가 없어도 논리적인 경쟁 조건은 발생할 수 있습니다.

```text
스레드 A: 잔액 100 확인
스레드 B: 잔액 100 확인
스레드 A: 80 출금
스레드 B: 80 출금
```

각 읽기와 쓰기만 개별적으로 뮤텍스로 보호해도 “확인 후 변경” 전체가 하나의 임계 구역이 아니면 잔액 불변식이 깨집니다. 뮤텍스는 변수 하나가 아니라 **불변식을 검사하고 변경하는 연산 단위**를 보호해야 합니다.

## 2. 뮤텍스와 잠금 범위

```cpp
class Counter
{
public:
    void increment()
    {
        std::lock_guard lock{mutex_};
        ++value_;
    }

    [[nodiscard]] int value() const
    {
        std::lock_guard lock{mutex_};
        return value_;
    }

private:
    mutable std::mutex mutex_;
    int value_{0};
};
```

잠금을 보유한 상태에서는 다음과 같은 알 수 없거나 오래 걸리는 작업을 피합니다.

- 외부 콜백
- 느린 파일 시스템 I/O
- 네트워크 I/O
- 다른 컴포넌트의 실행 시간을 예측할 수 없는 함수

그러나 불변식 변경 중간에 잠금을 풀어서도 안 됩니다. 외부 작업이 필요한 경우 일반적으로 다음 구조를 검토합니다.

```text
lock
→ 공유 상태 검사·예약
→ 필요한 지역 복사 생성
→ unlock
→ 외부 작업 수행
→ lock
→ 결과 반영
→ unlock
```

잠금을 푼 동안 다른 스레드가 상태를 변경할 수 있으므로 예약 토큰, 버전 번호, 명시적인 중간 상태가 필요할 수 있습니다.

## 3. 여러 뮤텍스와 획득 순서

두 뮤텍스를 스레드마다 다른 순서로 획득하면 교착 상태가 발생할 수 있습니다.

```text
스레드 A: left 잠금 → right 대기
스레드 B: right 잠금 → left 대기
```

가능하면 하나의 불변식을 하나의 뮤텍스 아래에 둡니다. 여러 뮤텍스를 함께 획득해야 한다면 프로그램 전체의 일관된 순서를 정하거나 `std::scoped_lock`을 사용합니다.

```cpp
std::scoped_lock lock{left_mutex, right_mutex};
```

`std::scoped_lock`은 전달한 뮤텍스들을 교착 상태를 피하는 방식으로 획득하지만, 프로그램의 다른 경로에서 일부 뮤텍스를 다른 순서로 따로 잠그는 문제까지 해결하지는 않습니다. 잠금 관계가 복잡해지면 상태 소유 경계를 다시 검토합니다.

## 4. `atomic`이 적합한 범위

독립적인 카운터나 플래그 하나는 `std::atomic`으로 표현할 수 있습니다.

```cpp
std::atomic<bool> stopping{false};
```

하지만 서로 관계가 있는 여러 필드를 각각 atomic 변수로 나누면 일관된 스냅샷을 얻기 어렵습니다.

```text
status = succeeded
output = 아직 빈 문자열
```

두 필드가 함께 바뀌어야 한다면 같은 뮤텍스로 보호하는 편이 단순합니다. 메모리 순서를 직접 설계하는 락프리 구조는 측정된 필요와 충분한 검증 없이 기본 선택으로 삼지 않습니다.

## 5. 조건 변수는 조건식을 기다립니다

```cpp
std::unique_lock lock{mutex_};
changed_.wait(lock, [this] {
    return !queue_.empty() || stopping_;
});
```

조건 변수는 알림 하나를 저장했다가 소비하는 이벤트 객체가 아닙니다. 조건이 충족되지 않았는데도 깨어나는 현상(spurious wakeup)이 허용되고, 알림을 받기 전에 이미 상태가 바뀌었을 수도 있으므로 공유 상태의 조건식을 항상 다시 검사합니다.

다음 코드는 큐가 비어 있을 가능성을 처리하지 않습니다.

```cpp
changed_.wait(lock);
use(queue_.front());
```

확인해야 할 것은 “알림을 받았는가”가 아니라 “진행할 조건이 현재 참인가”입니다.

## 6. `jthread`와 스레드 수명

조인 가능한 `std::thread`가 소멸하면 `std::terminate`가 호출됩니다. 조인 가능한 `std::jthread`는 소멸 과정에서 중단을 요청하고 스레드가 끝날 때까지 조인합니다.

```cpp
class Worker
{
public:
    Worker()
        : thread_([this](std::stop_token token) { run(token); })
    {}

private:
    void run(std::stop_token token);
    std::jthread thread_;
};
```

`jthread`만 사용한다고 종료 문제가 모두 해결되지는 않습니다.

- 작업 코드가 중단 요청을 관찰해야 합니다.
- 호출 중인 블로킹 API가 `stop_token`을 지원하지 않을 수 있습니다.
- 공유 상태의 종료 순서를 정의해야 합니다.
- 워커가 접근하는 멤버는 스레드가 끝날 때까지 살아 있어야 합니다.

멤버는 선언의 역순으로 파괴됩니다. `jthread`를 자신이 접근하는 상태 멤버보다 뒤에 선언하면 스레드 객체가 먼저 파괴되어 조인된 뒤 나머지 상태가 파괴됩니다. 다만 워커가 조건 변수에서 대기한다면 소멸자에서 먼저 중단 요청과 알림을 수행하고 명시적으로 조인해야 할 수 있습니다.

## 7. `stop_token`은 협력적 취소를 제공합니다

```cpp
std::string work(std::stop_token token)
{
    while (!token.stop_requested())
    {
        if (one_step_completed())
            return "done";
    }
    return "cancelled";
}
```

취소 요청은 스레드를 강제로 중단하지 않습니다. 작업은 안전한 지점에서 요청을 확인하고 자신이 보유한 자원을 정리한 뒤 반환합니다.

중단 요청을 인식하는 대기 연산도 사용할 수 있습니다.

```cpp
std::condition_variable_any changed;
std::unique_lock lock{mutex};
changed.wait(lock, token, [&] { return ready; });
```

중단 시 별도 동작을 등록해야 한다면 `std::stop_callback`을 사용할 수 있습니다. 콜백이 등록된 즉시 실행될 가능성, 콜백 객체의 수명, 콜백 안에서 같은 잠금을 다시 획득하는 문제를 함께 검토합니다.

## 8. 용량 제한 큐와 백프레셔

무제한 큐는 생산 속도가 소비 속도보다 빠를 때 메모리 사용량과 지연을 계속 늘릴 수 있습니다. 큐가 한계에 도달하면 시스템이 어떻게 동작할지 정합니다.

- 즉시 거부
- 일정 시간 대기
- 오래된 항목 제거
- 우선순위별 제한
- 호출자에게 재시도 가능 시점 제공

```cpp
enum class SubmitError
{
    stopped,
    queue_full,
    empty_name,
    empty_work
};
```

용량이 무엇을 세는지도 명확히 해야 합니다.

```text
대기 중인 항목만 제한하는가
실행 중인 항목까지 포함하는가
항목 개수인가 총 바이트 수인가
```

실습의 `JobRunner`는 **대기 중인 작업 수**만 제한합니다. 용량이 1이고 작업 하나가 실행 중이며 다른 하나가 대기 중이라면 큐는 가득 찬 상태입니다.

## 9. 상태 전이와 종료 상태

동시 객체의 상태는 서로 관계가 불명확한 여러 `bool`보다 명시적인 상태 열거형으로 표현하는 편이 낫습니다.

```text
queued → running → succeeded
                 → failed
                 → cancelled
queued ─────────→ cancelled
```

종료 상태에 도달한 작업은 다시 `running`으로 돌아가서는 안 됩니다. 상태와 그 상태에 대응하는 출력·오류를 같은 뮤텍스 아래에서 함께 변경해 호출자가 모순된 스냅샷을 보지 않게 합니다.

## 10. `time_point`와 `duration`

시간 간격은 `std::chrono::duration`으로 표현합니다.

```cpp
using namespace std::chrono_literals;
auto timeout = 500ms;
```

단위가 타입에 포함되므로 초와 밀리초를 단순 정수로 섞는 실수를 줄일 수 있습니다.

### `steady_clock`

경과 시간과 시간 제한에 사용합니다. `steady_clock`의 시점은 시스템 시각 조정 때문에 역행하지 않습니다.

```cpp
const auto deadline = std::chrono::steady_clock::now() + 2s;
```

### `system_clock`

사용자에게 표시할 달력 시각과 외부 타임스탬프에 사용합니다. NTP 동기화나 관리자 변경으로 시각이 앞뒤로 조정될 수 있으므로 경과 시간 계산의 기본 시계로 사용하지 않습니다.

## 11. 시간 제한은 기한으로 전달합니다

각 하위 함수에 같은 시간 간격을 다시 전달하면 전체 수행 시간이 의도보다 길어질 수 있습니다.

```text
상위 시간 제한 2초
├─ 단계 A 최대 2초
├─ 단계 B 최대 2초
└─ 단계 C 최대 2초
```

전체 시간 예산을 지키려면 하나의 기한을 만들고 각 단계에서 남은 시간을 계산합니다.

```cpp
const auto remaining = deadline - std::chrono::steady_clock::now();
```

남은 시간이 0 이하라면 새로운 블로킹 작업을 시작하지 않습니다.

## 12. 파일 시스템 경로와 오류

문자열 연결로 경로를 조립하지 않습니다.

```cpp
std::filesystem::path root{"data"};
auto file = root / "jobs.tsv";
```

파일 시스템 연산은 다음과 같은 이유로 실패할 수 있습니다.

- 경로가 존재하지 않음
- 권한 부족
- 같은 이름에 예상과 다른 파일 종류가 존재함
- 저장 공간 부족
- 읽기 전용 파일 시스템
- 다른 프로세스가 동시에 경로를 변경함
- 심볼릭 링크와 경로 정규화에 따른 차이

예외 오버로드와 `error_code` 오버로드 중 하나를 의도적으로 선택합니다.

```cpp
std::error_code error;
std::filesystem::create_directories(root, error);
if (error)
{
    // 호출자가 실패를 값으로 처리
}
```

## 13. 파일 교체와 충돌·전원 손실 경계

설정이나 스냅샷 파일을 교체할 때 대상 파일을 먼저 `truncate`한 뒤 쓰면 중간 실패 시 빈 파일이나 일부만 기록된 파일이 남을 수 있습니다.

같은 파일 시스템 안에서 흔히 사용하는 전략은 다음과 같습니다.

```text
대상과 같은 디렉터리에 임시 파일 작성
→ flush와 close 결과 확인
→ 필요한 내구성 수준에 따라 fsync 수행
→ rename 또는 플랫폼별 교체 연산으로 대상 변경
```

`rename`의 원자적 교체 가능 여부와 전원 손실 후 내구성은 운영체제, 대상 존재 여부, 파일 시스템, 디렉터리 동기화 정책에 따라 달라집니다. 함수가 성공을 반환했다는 사실과 전원 손실 뒤에도 데이터가 남는다는 보장을 구분합니다.

실습의 저널은 추가 전용 관찰 기록이며 충돌 후 큐 복구를 보장하지 않습니다. 생성 이후 추가 기록이 실패해도 워커를 중단하지 않고 `journal_healthy()`만 `false`로 바꾸는 정책을 사용합니다. 제공하지 않는 내구성을 명확히 적는 편이 잘못된 보장을 제시하는 것보다 낫습니다.

## 14. 콜백과 잠금

사용자가 제공한 `Work` 콜백을 내부 뮤텍스를 보유한 상태에서 실행하지 않습니다.

```text
lock
→ 레코드를 running으로 전이
→ 콜백과 토큰을 지역 변수로 확보
→ unlock
→ 콜백 실행
→ lock
→ 종료 결과 반영
```

콜백이 오래 실행되거나 `JobRunner`를 다시 호출하더라도 내부 뮤텍스를 계속 점유하지 않습니다. 대신 콜백이 실행되는 동안 작업 레코드와 필요한 데이터의 수명이 유지되어야 합니다.

실습에서는 상태 전이와 저널 행 순서를 단순하게 맞추기 위해 짧은 추가 기록과 `flush`를 상태 뮤텍스 아래에서 수행합니다. 따라서 저장 장치가 느리면 `submit`과 `snapshot`도 지연될 수 있습니다. 실제 시스템에서 저널 쓰기를 전용 스레드와 별도 큐로 분리한다면 상태 반영과 기록 완료 사이의 일관성, 저널 큐 포화, 종료 순서를 새로운 요구사항으로 정의해야 합니다.

## 15. 종료 순서

서비스 객체는 종료 절차를 명확히 정의해야 합니다.

```text
새 제출 거부
→ 대기 작업 취소 또는 모두 처리
→ 실행 중인 작업에 중단 요청
→ 대기 중인 워커 깨우기
→ 워커 종료·조인
→ 저널과 상태 자원 파괴
```

`stop`은 여러 번 호출해도 같은 최종 상태로 수렴하도록 멱등하게 만듭니다. 여러 외부 호출자가 동시에 종료를 요청하더라도 실제 조인은 안전하게 한 번 수행되어야 합니다. `Work` 콜백 안에서 `stop`을 호출할 수 있다면 워커가 자기 자신을 조인하지 않도록 하고, 이후 외부 `stop`이나 소멸자가 조인을 완료하도록 설계합니다. 명시적 `stop`과 소멸자는 같은 상태 전이 규칙을 사용해야 합니다.

## 연결 실습

[로컬 작업 실행기](../../exercises/01-modern-cpp/04-local-job-runner/README.md)를 단계별로 구현합니다.

특히 다음 테스트는 임의의 `sleep` 대신 동기화 지점을 사용해 사건 순서를 제어합니다.

- 첫 번째 작업이 실제 `running` 상태에 들어감
- 두 번째 작업이 큐에서 대기함
- 세 번째 제출이 용량 제한 때문에 거부됨
- 중단 요청이 실행 중인 작업에 전달됨
- 외부 `stop`이 워커 종료를 기다림
- 콜백 내부의 `stop`이 자기 자신을 조인하지 않고 끝남
- 종료 상태가 조건 변수를 통해 관찰됨

## 실패 실험

- 조건식 없이 조건 변수를 기다립니다.
- 콜백을 뮤텍스를 보유한 상태에서 실행합니다.
- 큐를 무제한으로 바꾸고 생산자를 빠르게 반복합니다.
- 실행 중인 작업을 즉시 `cancelled`로 표시하면서 콜백은 계속 공유 상태를 변경하게 둡니다.
- 시간 제한에 `system_clock`을 사용하고 시스템 시각 변경의 영향을 확인합니다.
- 대상 파일을 먼저 `truncate`한 뒤 쓰기 중간에 예외를 발생시킵니다.

## 완료 기준

- 데이터 레이스와 논리적 경쟁 조건을 구분합니다.
- 각 뮤텍스가 보호하는 불변식을 문서화합니다.
- 조건 변수의 조건식과 중단 요청을 인식하는 대기를 구현합니다.
- 용량 제한 큐의 용량이 무엇을 의미하는지 설명합니다.
- `steady_clock`과 `system_clock`을 목적에 맞게 선택합니다.
- 파일 시스템 오류 처리와 충돌·전원 손실 내구성의 한계를 구분합니다.
- 종료 순서가 모든 스레드와 자원의 수명을 안전하게 끝냅니다.
