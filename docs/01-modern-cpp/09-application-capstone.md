## 1. 문제 범위

프로세스 안에서 작업 이름과 실행 함수를 제출하면 하나의 워커가 제출 순서대로 실행합니다. 호출자는 작업 ID를 받아 상태를 조회하거나 취소할 수 있습니다. 모든 상태 전이는 파일 저널에 기록을 추가하며, 기록 실패 여부는 별도의 저널 상태로 확인할 수 있습니다.

지원 범위:

```text
submit
snapshot
wait_for_terminal
cancel
stop
추가 전용 저널
```

지원하지 않는 범위:

```text
프로세스 비정상 종료 후 작업 재실행
여러 워커와 우선순위
분산 큐
프로세스 간 동기화
스레드 강제 종료
종료 레코드 자동 삭제·보존 기간 정책
JobId 오버플로 처리
fsync 기반 내구성 보장
```

지원하지 않는 범위를 명시해야 구현이 실제보다 강한 보장을 제공한다고 오해하지 않습니다.

## 2. 공개 모델

### `JobId`

일반 정수와 암묵적으로 섞이지 않는 값 타입입니다.

```cpp
class JobId
{
public:
    explicit JobId(std::uint64_t value);
    auto operator<=>(const JobId&) const = default;
};
```

### `JobStatus`

```text
queued
running
succeeded
failed
cancelled
```

`done`, `failed`, `cancelled` 같은 불리언 필드를 따로 두지 않습니다. 여러 필드가 서로 모순되는 조합을 만들 수 있기 때문입니다.

### `SubmitResult`

```text
성공: JobId
실패: empty_name | empty_work | queue_full | stopped
```

정상적인 백프레셔와 종료 후 거부는 예외가 아니라 오류값으로 반환합니다.

### `JobSnapshot`

호출자는 내부 `Record&`가 아니라 상태의 복사본을 받습니다. 따라서 잠금을 해제한 뒤에도 안전하게 읽을 수 있고 내부 객체의 수명이 외부에 노출되지 않습니다.

## 3. 상태와 소유권

| 상태·자원 | 소유자 | 보호·종료 규칙 |
|---|---|---|
| 워커 스레드 | `JobRunner` | `jthread`, 중단 요청 후 조인 |
| 큐 | `JobRunner` | `mutex_`를 보유한 상태에서 변경 |
| 레코드 맵 | `JobRunner` | 종료 후에도 조회할 수 있도록 유지하며 기본 과제에는 자동 정리 정책이 없음 |
| `Work` 호출 가능 객체 | 각 `Record` | 워커가 레코드 수명 안에서 호출 |
| 작업별 취소 상태 | 각 `Record` | `stop_source`가 `stop_token`을 발급 |
| 저널 경로 | `JobRunner` 값 | 생성 시 쓰기 가능 여부 확인 |
| 저널 스트림 | 각 추가 기록 호출의 지역 RAII 객체 | 상태 뮤텍스 아래에서 상태 전이 뒤 기록하고 `flush`한 후 소멸하며 느린 I/O가 상태 API를 지연시킬 수 있음 |
| 저널 상태 | `JobRunner` 불리언 값 | 실행 중 추가 기록 실패를 관찰 가능하게 유지 |

같은 자원에 소유자가 둘 이상 있는 것처럼 보인다면 곧바로 `shared_ptr`를 추가하기보다 소유 구조를 다시 검토합니다.

## 4. 상태 전이

```text
submit 성공
    ↓
 queued ───────────────→ cancelled
    ↓ 워커가 큐에서 꺼냄
 running ──────────────→ cancelled
    ├──────────────────→ succeeded
    └──────────────────→ failed
```

다음 규칙을 지킵니다.

- 종료 상태는 다시 바뀌지 않습니다.
- 대기 중인 작업을 취소하면 큐에서 제거하고 즉시 `cancelled`로 전이합니다.
- 실행 중인 작업을 취소하면 중단을 요청하며, 작업이 반환한 뒤 워커가 종료 상태를 확정합니다.
- `cancel`은 대기 상태를 실제로 취소했거나 실행 중인 작업에 최초 중단 요청을 발행했을 때만 `true`를 반환합니다.
- 정상 반환과 취소 요청이 경합하면 종료 상태를 반영하기 직전에 토큰을 다시 확인해 성공 상태가 취소 요청을 덮어쓰지 않게 합니다.
- 호출 가능 객체가 던진 예외는 워커 경계에서 `failed` 상태로 변환합니다.
- 스냅샷의 상태·출력·오류는 같은 잠금 아래에서 한 번에 반영합니다.
- `submit`은 레코드와 큐 등록이 모두 성공한 뒤 저널을 기록하며, 중간 할당 실패가 발생하면 이미 등록한 상태를 되돌립니다.

## 5. 잠금 경계

워커는 다음 순서로 동작합니다.

```text
lock
→ 조건식 대기
→ 큐에서 ID 제거
→ 레코드를 running으로 전이
→ 저널 기록
→ 수명이 보장된 레코드 포인터 확보
→ unlock

Work 실행

lock
→ succeeded | failed | cancelled 결과 반영
→ 저널 기록
→ unlock
→ 종료를 기다리는 호출자에게 알림
```

외부에서 전달된 `Work`를 내부 잠금 아래에서 호출하지 않습니다. 긴 작업이 `submit`, `snapshot`, `cancel`을 모두 막을 수 있고, 콜백이 `JobRunner`를 다시 호출하면 교착 상태가 발생할 수 있기 때문입니다.

## 6. 용량 제한 큐

`capacity`는 대기 중인 `queue_`의 크기만 제한합니다.

예:

```text
capacity = 1
running = 1
queued = 1
새 submit = queue_full
```

실행 중인 작업까지 용량에 포함하는 설계도 가능하지만 의미가 다릅니다. 공개 인터페이스, 문서, 테스트가 같은 정의를 사용해야 합니다.

## 7. 취소 규칙

C++ 표준 라이브러리는 임의의 스레드를 일반적으로 안전하게 강제 종료하는 기능을 제공하지 않습니다. `Work`는 협력적 취소를 위해 `std::stop_token`을 받습니다.

```cpp
using Work = std::function<std::string(std::stop_token)>;
```

`cancel()`은 중단 요청을 발행한 뒤 작업 종료를 기다리지 않고 반환할 수 있습니다. 작업이 토큰을 확인하지 않으면 `cancelled` 종료 상태로 전이되는 시점도 늦어집니다. 외부 스레드에서 호출한 `stop()`과 소멸자는 워커의 조인을 기다리므로 `Work`가 영원히 반환하지 않으면 이들도 끝나지 않습니다. 이는 구현 결함이 아니라 협력적 취소 방식의 한계입니다. 블로킹 I/O를 취소하려면 해당 API의 시간 제한이나 취소 기능을 별도로 연결해야 합니다.

## 8. 오류 경계

| 실패 | 표현 | 이유 |
|---|---|---|
| 빈 이름 | `SubmitError::empty_name` | 호출자가 수정할 수 있는 예상 가능한 거부 |
| 빈 호출 가능 객체 | `SubmitError::empty_work` | 실행할 수 없는 제출을 명시적으로 거부 |
| 큐 포화 | `SubmitError::queue_full` | 정상적인 백프레셔 분기 |
| 종료 후 제출 | `SubmitError::stopped` | 실행기 수명 상태에 따른 분기 |
| 존재하지 않는 ID 조회 | 빈 `optional` | 정상적인 부재 |
| `Work`의 표준 예외 | `failed` 스냅샷과 메시지 | 워커 스레드가 예외로 종료되지 않게 함 |
| `Work`의 알 수 없는 예외 | `failed`와 고정 메시지 | 프로세스 종료 방지 |
| 저널 생성 불가 | 생성자 예외 | 유효한 `JobRunner`를 만들 수 없음 |
| 생성 후 저널 추가 기록 실패 | `journal_healthy() == false` | 작업 실행은 계속하고 저널 상태를 관찰 가능하게 함 |

큐 포화와 I/O 오류처럼 성격이 다른 문제를 하나의 오류 문자열로 합치지 않습니다.

## 9. 저널 규칙

형식:

```text
<id>\t<status>\t<name>\t<message>\n
```

이름과 메시지에 포함된 탭과 줄바꿈은 공백으로 정규화합니다. 한 줄은 하나의 상태 전이를 나타냅니다.

예:

```text
1 queued complete
1 running complete
1 succeeded complete done
```

실제 파일에서는 각 필드를 탭으로 구분합니다.

생성 시점부터 저널을 열 수 없다면 생성자가 실패합니다. 생성 이후 디렉터리가 삭제되거나 저장 장치 오류로 추가 기록이 실패하면 작업 상태 전이는 계속 진행하고 `journal_healthy()`를 `false`로 바꿉니다. 이는 감사 기록과 작업 실행 중 후자를 우선하는 명시적인 정책입니다. 내구성 큐를 구현하려면 다른 오류 정책이 필요합니다.

기본 과제는 결정적인 상태 전이 순서를 위해 저널 I/O를 상태 뮤텍스 아래에서 수행합니다. 구조는 단순하지만 느린 저장 장치가 상태 API까지 지연시킬 수 있습니다. 저널 쓰기를 전용 스레드와 별도 큐로 분리한다면 기록 큐의 백프레셔, 상태 반영과 기록 완료의 관계, 종료 시 `flush` 순서를 새로 정의하고 검증해야 합니다.

저널의 목적은 다음과 같습니다.

- 상태 전이 관찰
- 실패 테스트의 근거 제공
- 수명과 종료 순서 확인

다음 기능은 제공하지 않습니다.

- 재시작 복구
- 정확히 한 번(exactly-once) 실행
- 전원 손실 후 내구성 보장

## 12. 실패 재현 순서

### 큐 포화

```text
블로킹 작업 제출
→ promise로 running 상태 확인
→ 두 번째 작업을 큐에 제출
→ 세 번째 작업 제출
→ queue_full 확인
→ 블로킹 작업 해제
```

임의의 `sleep`으로 실행 상태를 추측하지 않습니다.

### 실행 중 취소

```text
중단 요청을 인식하는 대기를 수행하는 작업 제출
→ 시작 promise 확인
→ cancel 호출
→ token으로 대기 해제
→ cancelled 종료 상태 확인
```

### 워커 예외

```text
runtime_error를 던지는 Work 제출
→ wait_for_terminal
→ 워커가 계속 살아 있는지 확인
→ 스냅샷의 failed 상태와 메시지 확인
→ 다음 정상 작업도 실행되는지 확인
```

## 13. 설계 검토 질문

- `JobRunner` 파괴 중 워커가 이미 파괴된 멤버를 읽을 수 있는가
- `cancel`과 워커 완료가 동시에 발생할 때 종료 상태가 두 번 기록되는가
- 큐에서 ID를 제거한 뒤에도 해당 레코드 수명이 유지되는가
- 콜백이 `JobRunner`를 다시 호출해도 교착 상태가 발생하지 않는가
- 저널 기록 실패와 상태 반영의 관계가 명확한가
- 여러 스레드가 동시에 `stop`을 호출해도 안전한 하나의 조인으로 수렴하는가
- `Work` 콜백에서 `stop`을 호출해도 자기 자신을 조인하지 않는가
- `wait_for_terminal`은 존재하지 않는 ID를 즉시 거부하는가
- `Work`가 토큰을 무시하면 외부 `stop()`이 계속 기다린다는 제한이 문서와 일치하는가
- 종료 레코드를 계속 보존할 때 장기 실행 프로세스의 메모리 정책은 무엇인가

참조 구현은 학습 범위 안에서 선택한 한 가지 설계를 보여 줍니다. 다른 설계도 가능하지만 공개 규칙과 테스트를 함께 변경해야 합니다.

## 14. 합리적인 확장

기본 과제를 완료한 뒤 한 번에 하나씩 확장합니다.

### 여러 워커

- 워커 수 매개변수
- 큐와 레코드 동기화 유지
- 같은 ID의 중복 실행 방지
- 모든 워커의 종료와 조인 관리

### 우선순위 큐

- 우선순위와 FIFO 보조 순서
- 기아 상태 방지 정책
- 기존 용량 의미 유지

### 재시작 복구

- 명세와 상태를 내구성 있는 형식으로 저장
- 비정상 종료 당시 `running` 상태의 불확실성 처리
- 재생과 중복 실행 정책
- 원자적 교체와 `fsync` 범위

### 기한

- 각 `JobSpec`에 `steady_clock::time_point` 추가
- 큐 대기 중 만료 처리
- 실행 작업에 남은 시간 예산 전달

모든 기능을 한 번에 추가하지 않습니다. 각 확장은 새로운 실패 조건과 검증 비용을 만듭니다.

[로컬 작업 실행기](../../exercises/01-modern-cpp/04-local-job-runner/README.md)의 스켈레톤을 단계별 명세에 따라 구현합니다. 참조 구현은 모든 검사를 통과한 뒤 상태, 오류, 조인 정책을 비교하는 용도로만 사용합니다.

## 완료 기준

### 기능

- 정상 작업, 실패한 작업, 취소된 작업을 처리합니다.
- 용량 제한 큐가 재현 가능한 조건에서 제출을 거부합니다.
- `stop` 이후 새 작업을 받지 않습니다.
- 정상 상태 전이는 저널에 기록되고 실행 중 저널 장애는 저널 상태 저하로 드러납니다.

### 설계

- 값, 소유자, 비소유자를 구분합니다.
- 상태와 출력·오류를 하나의 잠금 아래에서 반영합니다.
- 스레드 수명, 동시 `stop`의 수렴, 자기 조인 방지를 포함해 종료 순서를 완결합니다.
- 실패의 의미에 따라 표현 방식을 구분합니다.

### 검증

- 참조 구현과 완성한 스켈레톤의 테스트가 통과합니다.
- ASan·UBSan과 지원 환경의 TSan 검사가 통과합니다.
- 동시성 테스트에 임의의 `sleep`을 사용하지 않습니다.
- 지원하지 않는 범위와 내구성 한계를 설명합니다.

이 기준을 만족하면 Modern C++ 일반 트랙을 마친 것입니다. 이후 프로젝트에서는 모든 언어 기능을 다시 학습하기보다 구현에 필요한 도메인 지식을 추가로 익힙니다.
