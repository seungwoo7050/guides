# 캐시, 지역성과 AMAT

프로세서가 명령어를 실행할 때마다 주 메모리를 기다리면 빠른 실행 장치가 대부분 멈춥니다. 캐시는 최근 또는 주변에서 다시 사용할 가능성이 높은 메모리 블록을 작고 빠른 저장소에 두어 평균 접근 시간을 줄입니다. 캐시는 개별 변수가 아니라 캐시 라인 단위로 데이터를 옮기고, 제한된 집합 안에서 교체하며, 실패 비용이 적중 비용보다 훨씬 클 수 있습니다.

## 학습 목표

- 주소를 tag·set·offset으로 나누고 교체·쓰기 정책의 상태를 추적합니다.
- 3C 실패와 AMAT를 측정 가능한 cache 근거로 연결합니다.

## 선행 개념

2의 거듭제곱, 주소 비트와 CPU 시간의 평균 비용 모델을 알아야 합니다.

## 메모리 계층은 용량과 속도 사이의 절충입니다

대표적인 계층은 다음과 같습니다.

```text
레지스터
↓
L1 캐시
↓
L2 캐시
↓
공유 최종 단계 캐시
↓
DRAM
↓
저장장치
```

위쪽은 작고 빠르며 비트당 비용이 높습니다. 아래쪽은 크고 느립니다. 실제 프로세서의 단계 수, 공유 범위, 포함 관계와 지연 시간은 제품마다 다릅니다.

캐시는 ISA에서 직접 보이지 않는 경우가 많습니다. 같은 적재 명령도 L1 적중, 최종 단계 실패, TLB 실패 또는 원격 NUMA 접근에 따라 사이클 수가 달라질 수 있습니다.

## 지역성은 미래 접근을 예측하는 경험적 근거입니다

### 시간 지역성

최근에 읽거나 쓴 데이터를 가까운 미래에 다시 접근할 가능성이 높습니다.

```text
반복문 계수기
스택 프레임
자주 호출되는 코드
자주 조회하는 항목
```

### 공간 지역성

한 주소에 접근하면 가까운 주소도 곧 접근할 가능성이 높습니다.

```text
배열 순차 탐색
명령열
구조체의 인접 필드
```

지역성은 보장이 아닙니다. 큰 연결 리스트를 무작위로 따라가거나 작업 집합이 캐시보다 크면 같은 정책이 효과를 내지 못할 수 있습니다.

## 캐시 라인은 전송과 일관성 제어의 기본 단위입니다

64바이트 캐시 줄을 예로 들면 주소 하나를 읽을 때 주변 64바이트가 함께 들어올 수 있습니다.

```text
주소 0x1000 접근
→ 캐시 줄 [0x1000, 0x103f]을 가져옵니다.
```

순차 배열은 캐시 줄 안의 여러 원소를 사용하므로 공간 지역성을 얻습니다. 반대로 포인터 하나만 읽고 멀리 이동하면 가져온 나머지 바이트를 사용하지 않을 수 있습니다.

캐시 줄이 크면 최초 접근 실패마다 더 많은 주변 데이터를 가져오지만 다음 비용도 생깁니다.

- 사용하지 않는 바이트 전송
- 같은 캐시 용량에서 캐시 줄 수 감소
- 거짓 공유 범위 증가
- 메모리 대역폭 소비

## 주소를 오프셋, 집합 인덱스와 태그로 나눕니다

캐시 크기 32KiB, 캐시 줄 64B, 8-way 집합 연관이라고 가정하겠습니다.

```text
캐시 줄 수 = 32768 / 64 = 512
세트 수 = 512 / 8 = 64
```

2의 거듭제곱 구성이라면 주소의 하위 비트를 다음처럼 나눕니다.

```text
| 태그 | 세트 인덱스 6비트 | 블록 오프셋 6비트 |
```

- 오프셋은 캐시 줄 안의 바이트 위치입니다.
- 세트 인덱스는 확인할 세트를 고릅니다.
- 태그는 그 세트의 각 way가 어떤 메모리 블록인지 구분합니다.

실제 물리·가상 주소 인덱스 캐시에서는 주소 변환과 인덱스 조회 시점이 얽힐 수 있지만, 첫 모델에서는 물리 주소가 캐시에 들어온다고 두고 계산합니다.

## 연관도가 배치 자유도를 정합니다

### 직접 사상

세트마다 캐시 줄 하나만 있습니다. 조회와 교체가 단순하지만 같은 세트에 대응하는 두 블록이 계속 서로를 밀어낼 수 있습니다.

### 집합 연관

세트마다 여러 way를 둡니다. 4-way라면 같은 세트 안에서 네 블록 가운데 하나를 고를 수 있습니다.

### 완전 연관

어느 블록이든 모든 캐시 줄에 들어갈 수 있습니다. 충돌 실패는 줄지만 많은 태그를 동시에 비교해야 합니다.

연관도를 높이면 충돌을 줄일 수 있지만 적중 지연 시간, 면적과 전력 소모가 늘 수 있습니다. “높을수록 항상 빠릅니다”라고 결론 내리면 안 됩니다.

## 적중과 실패의 상태 전이

읽기 적중에서는 태그와 유효 비트를 확인하고 캐시 줄의 오프셋에서 데이터를 고릅니다.

읽기 실패에서는 다음이 필요할 수 있습니다.

1. 교체할 way를 고릅니다.
2. 교체 대상이 수정된 상태라면 하위 단계에 반영합니다.
3. 요청 블록을 하위 단계에서 가져옵니다.
4. 태그, 유효·수정 상태와 교체 메타데이터를 갱신합니다.
5. 요청 데이터를 반환합니다.

실패를 처리하는 동안 같은 세트의 새 요청을 막는지, 여러 실패를 동시에 추적하는지는 마이크로아키텍처 구현에 달려 있습니다.

## 교체 정책은 제한된 집합 안에서 내보낼 항목을 고릅니다

대표 정책은 다음과 같습니다.

- LRU 또는 LRU 근사
- 유사 LRU
- FIFO
- 무작위
- 재참조 예측 계열

정확한 LRU는 연관도가 커질수록 모든 접근 순서를 유지하는 비용이 큽니다. 하드웨어는 적은 비트로 근사하거나 작업 부하에 맞는 다른 정책을 사용할 수 있습니다.

이 가이드의 캐시 모의 실행기는 이해하기 쉬운 정확한 LRU를 사용합니다. 실제 CPU가 같은 정책을 쓴다는 뜻은 아닙니다.

## 쓰기 정책을 두 축으로 나눕니다

### 즉시 쓰기와 지연 쓰기

- 즉시 쓰기는 캐시 쓰기를 하위 단계에도 바로 전달합니다.
- 지연 쓰기는 캐시 줄을 수정된 상태로 표시하고 교체할 때 하위 단계에 반영합니다.

지연 쓰기는 같은 캐시 줄의 여러 쓰기를 합칠 수 있지만 수정 블록 교체, 일관성 유지와 비정상 종료 처리를 더 복잡하게 만듭니다. CPU 캐시의 지연 쓰기는 영구 저장장치의 내구성을 보장하는 데이터베이스 쓰기와 같은 규칙이 아닙니다.

### 쓰기 할당과 비할당

쓰기 실패에서 캐시 줄을 캐시에 가져올지 결정합니다.

- 쓰기 할당은 캐시 줄을 채운 뒤 캐시에 씁니다.
- 쓰기 비할당은 캐시에 넣지 않고 하위 단계로 보냅니다.

지연 쓰기와 쓰기 할당, 즉시 쓰기와 쓰기 비할당의 조합이 흔하지만 절대 규칙은 아닙니다.

## 3C 모델로 캐시 실패 원인을 분류합니다

### 최초 접근 실패

처음 접근한 블록이므로 어떤 캐시에도 아직 없습니다.

### 충돌 실패

전체 캐시 줄 수는 충분하지만 제한된 세트 대응 관계 때문에 밀려납니다. 같은 캐시 줄 수의 완전 연관 캐시라면 적중했을 접근입니다.

### 용량 실패

완전 연관 캐시라도 작업 집합이 전체 캐시 줄 수를 넘어서 밀려납니다.

다중 코어 일관성 실패나 미리 가져오기의 영향은 전통적인 3C만으로 모두 설명되지 않습니다. 그래도 코드와 데이터 배치 문제를 분석하는 출발점으로 유용합니다.

```sh
python3 exercises/processor-model/reference/processor-model.py cache \
  exercises/processor-model/fixtures/traces/cache.trace \
  --size 16 --block 4 --ways 1
```

결과에서 세 실패 분류의 합이 전체 실패와 같은지 확인하세요.

## AMAT는 실패율과 실패 비용을 함께 묶습니다

단일 단계의 첫 근사는 다음과 같습니다.

```text
AMAT = hit time + miss rate × miss penalty
```

L1 실패가 L2를 확인하는 구조라면 다음처럼 중첩할 수 있습니다.

```text
AMAT = L1 hit time
     + L1 miss rate × (L2 hit time + L2 miss rate × memory penalty)
```

여기서 L2 실패율이 L2에 도달한 접근 가운데 실패 비율인지, 전체 메모리 접근 대비 전역 실패율인지 구분해야 합니다. 분모가 다르면 같은 숫자를 식에 넣을 수 없습니다.

비순차 실행 코어는 여러 실패의 대기 시간을 겹칠 수 있으므로 AMAT가 곧 응용 프로그램의 정지 시간은 아닙니다. 대역폭이 포화되면 독립적인 실패도 서로 대기합니다. AMAT는 평균 지연 시간 모델이고 전체 실행 시간은 의존성과 겹침을 추가로 살펴야 합니다.

## 반복문 순서가 공간 지역성을 바꿉니다

C의 행 우선 배열을 다음처럼 읽습니다.

```c
for (row = 0; row < rows; ++row)
    for (column = 0; column < columns; ++column)
        sum += matrix[row * columns + column];
```

안쪽의 `column`이 증가하면 연속 주소를 읽습니다. 반복문을 뒤집으면 보폭이 `columns * element_size`가 됩니다.

[데이터 배치 벤치마크](../../examples/layout-benchmark/README.md)를 실행하세요.

```sh
make -C examples/layout-benchmark benchmark
```

두 체크섬은 같아야 합니다. 시간 비율은 CPU와 입력에 따라 달라지므로 고정 정답으로 사용하지 않습니다.

## 블로킹은 작업 단위를 캐시에 맞춥니다

행렬 곱셈처럼 큰 2차원 데이터를 여러 번 쓰는 작업은 전체 행·열을 한 번에 순회하기보다 작은 타일로 나눌 수 있습니다.

```text
큰 문제
→ 캐시에 들어갈 타일
→ 타일 안에서 반복 사용
→ 다음 타일
```

이 방식은 알고리즘 복잡도 표기 `O(n^3)`를 바꾸지 않아도 메모리 전송량을 줄일 수 있습니다. 점근 복잡도와 메모리 계층 비용은 서로 다른 설명 축입니다.

블록 크기는 다음 조건의 균형으로 정합니다.

- 여러 입력·출력 타일이 목표 캐시에 함께 들어갑니까?
- 연관도에 따른 충돌을 고려했습니까?
- 벡터 폭과 정렬에 맞습니까?
- 너무 작은 타일 때문에 반복문 부가 비용이 늘지 않습니까?

## 미리 가져오기는 이후 접근할 데이터를 먼저 요청합니다

하드웨어 미리 가져오기 장치는 순차 또는 일정한 보폭을 발견해 다음 캐시 줄을 가져올 수 있습니다. 소프트웨어 미리 가져오기 명령이나 컴파일러 내장 함수도 사용할 수 있습니다.

미리 가져오기가 늦으면 요청 실패의 대기를 숨기지 못하고, 너무 빠르면 아직 쓸 캐시 줄을 밀어내거나 대역폭을 소비합니다. 불규칙한 연결 구조에서는 정확도가 낮을 수 있습니다.

벤치마크에서 순차 접근이 빠른 이유를 캐시 적중만으로 단정하지 말고 미리 가져오기의 영향도 고려하세요.

## 구조체 배치는 캐시 라인 사용량과 거짓 공유를 바꿉니다

구조체 배열(AoS)은 객체별 필드를 모읍니다.

```text
{x0,y0,z0} {x1,y1,z1} {x2,y2,z2}
```

배열 구조체(SoA)는 필드별로 모읍니다.

```text
x0 x1 x2 ...
y0 y1 y2 ...
z0 z1 z2 ...
```

한 필드만 대량 처리하면 SoA가 캐시 줄 사용과 SIMD에 유리할 수 있습니다. 객체 전체를 함께 사용하면 AoS가 편리할 수 있습니다. 배치 변경은 ABI, 직렬화, 코드 복잡도와 갱신 패턴도 바꿉니다.

여러 스레드가 서로 다른 필드를 쓰더라도 같은 캐시 줄에 있으면 거짓 공유가 생길 수 있습니다. [다중 코어 문서](../04-parallel-execution/10-multicore-coherence-and-false-sharing.md)에서 일관성 상태로 확인합니다.

## 캐시 최적화 전에 정확성과 측정 범위를 고정합니다

다음 순서를 사용하세요.

1. 동일한 출력 또는 체크섬을 검증합니다.
2. 작업 집합과 접근 패턴을 적습니다.
3. 소스 반복문과 실제 어셈블리를 확인합니다.
4. 타이머와 계수기를 여러 번 측정합니다.
5. 캐시 실패 종류와 대역폭 가능성을 구분합니다.
6. 데이터 배치 또는 반복문 순서를 한 가지씩 바꿉니다.
7. 메모리 사용량과 다른 작업 부하의 회귀를 확인합니다.

캐시 줄 크기를 추측해 패딩을 넣거나, 측정 없이 모든 데이터를 타일로 바꾸면 코드만 복잡해질 수 있습니다.
