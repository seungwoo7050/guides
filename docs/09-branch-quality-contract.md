# 브랜치 품질 계약

`main`은 두 가지 역할을 함께 가진다.

1. 독자가 목표 업무까지 갈 수 있도록 브랜치와 트랙을 연결하는 로드맵
2. 새 브랜치가 기존 브랜치와 같은 구조·품질·완성도를 갖추었는지 사람이 판단하는 기준

이 문서는 두 번째 역할의 정본이다. 기존 브랜치에서 반복해서 확인되는 README, roadmap, 개념 문서, 실행 가능한 실습, 기준 결과, 준비·검증 절차와 누적 과제의 역할을 공통 계약으로 정리한다. 특정 파일 수나 한 가지 구현 형식을 복제하는 것이 목적은 아니다.

## 판정의 책임 경계

카탈로그와 문서 검사는 ID, 참조, 생성 결과와 내부 링크 같은 **기계적 무결성**만 확인한다. 다음 항목은 자동화가 증명하지 않는다.

- 설명이 정확하고 학습 순서가 타당한가
- 실습이 핵심 실패와 경계 조건을 제대로 드러내는가
- 종료 능력이 실제로 브랜치 전체에서 다뤄지는가
- 인접 브랜치와 책임이 적절히 나뉘는가
- 독자가 다음 프로젝트에 들어갈 만큼 준비됐는가

따라서 카탈로그의 `stable`은 검사 통과나 실제 원격 브랜치 완료의 동의어가 아니다. `main`에서 해당 브랜치의 최종 구조 역할, 소유 경계, 종료 능력과 트랙 위치를 사람이 **완성 목표 계약**으로 승인했다는 뜻이다. 실제 브랜치 완료는 구현 뒤 이 계약에 따라 존재하는 문서·실습·종료 근거를 사람이 다시 검토해 별도로 판단한다. 자동 검사는 두 판단에 필요한 보조 근거일 뿐이다.

## 서로 다른 세 가지 완료

| 완료 단위 | 의미 | 의미하지 않는 것 |
|---|---|---|
| 브랜치 완료 | 한 브랜치의 소유 범위와 종료 능력을 문서, 실습, 누적 과제에서 확인했다. | 해당 분야의 전문가가 됐다는 뜻이 아니다. |
| 트랙 완료 | 목표 업무의 필수 브랜치들을 연결해 트랙의 종료 작업을 수행할 준비가 됐다. | 권장·심화 브랜치를 모두 끝냈거나 실제 서비스를 소유했다는 뜻이 아니다. |
| 프로젝트 경험 | 실제 코드베이스에서 요구사항, 리뷰, 사용자·운영 제약을 겪으며 변경을 끝냈다. | 브랜치나 트랙의 완료 개수로 대신할 수 없다. |

브랜치 완료는 트랙의 구성 요소이고, 트랙 완료는 실제 프로젝트로 이동하기 위한 준비 상태다. 실제 프로젝트에서의 반복 기여와 운영 경험은 별도로 쌓아야 한다.

## 브랜치 종류와 품질 프로필

브랜치 종류는 `common-foundation`, `language-entry`, `field-entry`, `specialization` 네 가지다. 이는 카탈로그에서 브랜치가 맡는 역할을 나타낸다.

`data-engineering`이나 `agentic-systems`처럼 여러 기반을 결합하는 **교차 확장**은 다섯 번째 종류가 아니다. 하나 이상의 브랜치에서 얻은 능력을 새로운 상태·실패 모델에 연결하는 직교 특성이다. 어떤 종류의 브랜치에도 교차 확장 특성이 있을 수 있다.

품질 프로필도 종류와 별개다. 한 브랜치는 아래 프로필을 하나 이상 선택해 실습과 종료 근거의 형태를 정한다.

## 공통 구조 계약

새 브랜치는 원칙적으로 다음 역할을 제공한다. 기존 브랜치와 같은 이름을 사용할 필요는 없지만, 역할을 생략하거나 다른 방식으로 대체했다면 리뷰에서 이유와 대체 근거를 설명해야 한다.

| 역할 | 기대하는 내용 | 허용되는 변형 |
|---|---|---|
| 진입점 | 대상 독자, 목표 결과, 빠른 시작, 전체 학습 순서 | `README.md`와 roadmap 사이에 내용을 나눌 수 있다. |
| 범위 계약 | 선행 역량, 소유·비소유 범위, 종료 능력, 다음 경로 | roadmap, syllabus 또는 동등한 문서로 제공할 수 있다. |
| 개념 경로 | 핵심 상태, 책임, 사건, 실패, 검증 방법을 순서 있게 설명 | 장 수와 디렉터리 구조는 분야에 맞게 정한다. |
| 단계 실습 | 설명한 계약을 작은 단위에서 관찰·구현·진단한다. | 코드, 추론 문제, 실험, 운영 훈련, 하드웨어 관찰 등으로 구성할 수 있다. |
| 기대 결과 | 독자가 자신의 결과를 비교하고 차이를 설명할 근거 | reference 구현, 해설, trace, 측정 기준 또는 리뷰 예시가 될 수 있다. |
| 누적 종료 과제 | 여러 핵심 능력을 함께 사용해 종료 능력을 확인한다. | capstone 또는 그와 동등한 누적 최종 실습·설계 검토·운영 시나리오를 사용한다. |
| 재현 절차 | 준비, 실행, 확인, 정리 방법과 지원 환경 | `prepare.sh`, `verify.sh`가 기본이지만 분야에 맞는 동등한 절차를 허용한다. |
| 유지보수 정보 | 기여 규칙, 출처, 라이선스와 안전 제약 | 배포하는 코드·문서·데이터의 성격에 맞게 나눌 수 있다. |

권장 기본 배치는 다음과 같다.

```text
README.md
CONTRIBUTING.md
LICENSE.md와 필요한 라이선스 원문
docs/00-roadmap.md
docs/
exercises/
prepare.sh
verify.sh
```

이 배치는 새 브랜치 작성자가 먼저 고려할 기본값이지, 디렉터리 모양만으로 완성도를 판정하는 체크리스트가 아니다. 모델 구현 하나에 모든 학습을 누적하거나 실제 장비와 simulator를 병행하는 편이 더 타당하다면 그 구조를 사용할 수 있다.

브랜치 작성 과정의 커밋 이력은 [`CONTRIBUTING.md`](../CONTRIBUTING.md)의 커밋 구성 계약을 따른다. `c` 브랜치는 의미 단위 분리의 참고 사례이며, 정확한 커밋 수나 순서를 복제하는 기준은 아니다. 검토 가능한 이력은 유지보수와 리뷰를 돕지만, 그 자체로 내용의 정확성이나 완성 목표 계약 충족을 증명하지 않는다.

## `main` 선행 계약과 초안 기반 구현

새 브랜치는 빈 디렉터리에서 시작한다고 가정하지 않는다. 작성자가 `docs/`, 실습 기초틀, 코드나 설정을 먼저 준비했다면 그 폴더와 기존 이력이 구현의 출발점이다. 후속 작성자나 에이전트는 다음 순서를 따른다.

1. 최신 `main`의 대상 브랜치 객체와 관련 트랙·선형 경로를 읽고 `kind`, 관계, `owns`, `excludes`, 종료 능력을 수락 기준으로 고정한다.
2. 제공된 폴더의 현재 tree, 기존 문서·실습 의도, Git 상태와 커밋 이력을 먼저 복원한다. 사용자 변경을 초기화하거나 표준 템플릿으로 덮어쓰지 않는다.
3. 초안을 구조·품질·완성도 관점에서 목표 계약과 대조하고, `owns → 설명 → 실습·대표 실패 → 누적 종료 과제 → 종료 능력`의 공백을 찾는다.
4. 초안이 아직 커밋되지 않았다면 생성물·비밀정보를 제외한 작성자 기초틀을 가능한 한 별도의 기준 커밋으로 남겨 이후 보정과 구분한다.
5. 개념 단원, 대응 실습, 누적 종료 과제, 검증 인프라와 최종 품질 보정을 실제 작업 순서의 의미 단위로 완성하고 검증한다.

`main`은 사양과 척도로 읽는 것이지 대상 기술 브랜치의 파일 기반이 아니다. 이 저장소의 주제 브랜치는 독립 이력을 사용할 수 있으므로 `main`에서 일반 feature branch를 만들거나 `main`의 tree를 초안 폴더에 복사·병합하지 않는다. 표준 배치보다 기존 구조가 같은 역할을 더 적합하게 수행하면 보존하고 그 근거를 리뷰에서 설명한다.

## 내용 품질 기준

브랜치 전체 학습 경로는 다음 질문에 답해야 한다.

1. 어떤 실제 문제를 해결하며 결과물은 무엇인가
2. 어떤 상태와 자원을 누가 소유하는가
3. 어떤 사건과 입력이 상태를 바꾸는가
4. 정상·경계·실패 사례에서 무엇을 보존해야 하는가
5. 결과를 어떤 관찰, 테스트, 측정 또는 검토로 판단하는가
6. 그 근거가 보장하는 것과 보장하지 않는 것은 무엇인가
7. 이 브랜치가 다루지 않고 다른 브랜치에 맡기는 영역은 무엇인가

각 문서가 일곱 질문을 모두 반복할 필요는 없다. roadmap, 개념 문서, 실습과 종료 과제를 합친 **브랜치 전체**가 답하면 된다.

좋은 설명은 특정 도구의 명령 목록에 머무르지 않는다. 도구가 바뀌어도 남는 상태·책임·실패 원리를 먼저 설명하고, 선택한 도구가 그 원리를 어디까지 드러내거나 숨기는지 밝힌다. 버전, 플랫폼, 비용 또는 권한 때문에 재현 범위가 달라지면 그 한계도 기록한다.

교차 링크도 학습 계약의 일부다. 카탈로그에 등록된 ID만 승인된 내부 브랜치 계약으로 다룬다. `main`은 완성 상태를 먼저 설계하므로 원격 구현은 뒤따를 수 있다. 필요한 주제가 카탈로그에 없다면 외부 자료에 맡긴 범위인지, 현재 브랜치에서 제한적으로 설명하는 영역인지, 향후 브랜치 검토 후보인지 밝힌다. 카탈로그 밖 영역을 승인된 내부 경로처럼 표기하지 않는다.

## 실습 품질 기준

실습은 정답 파일의 존재가 아니라 학습 계약을 확인하는 수단이다.

- 시작 상태는 실행 가능하거나 실패를 재현할 수 있어야 하며, 무엇이 미완성인지 공개한다.
- 정상 경로뿐 아니라 대표적인 경계·실패 사례를 다룬다.
- 기대 결과는 구현 모양보다 외부 행동, 불변식, 관측 결과와 설명의 타당성을 우선한다.
- 실패 메시지나 검토 지침은 답을 노출하기보다 원인을 좁힐 단서를 준다.
- 기준 구현이 있다면 공개 계약을 만족하고, 한 가지 설계만 정답이라고 오해하게 만들지 않는다.
- 위험한 시스템·운영·보안 실습은 허가 범위, 격리, 자원 제한, 정리와 복구 절차를 명시한다.
- 외부 서비스나 실제 장비가 필요하면 대체 경로와 대체 경로가 보장하지 못하는 범위를 밝힌다.

자동 검증이 적합하지 않은 결과는 억지로 수치화하지 않는다. 설계 근거, 위협 분석, 시각 결과, 운영 판단처럼 사람의 검토가 필요한 항목은 평가 질문과 필요한 증거를 명시한다.

## 준비·검증 절차의 품질

`prepare.sh`와 `verify.sh`는 교육적 완성을 자동 판정하는 도구가 아니라, 독자와 리뷰어가 같은 상태를 재현하고 판단 근거를 얻는 공통 진입점이다. 동등한 절차로 대체하려면 아래 역할을 어떻게 수행하는지 설명한다.

- 준비 절차는 지원 환경과 필요한 도구·의존성을 확인하고, 준비 중 만든 상태를 추적 대상 source와 분리한다.
- 의존성·도구·컨테이너·데이터 판본은 결과를 다시 만들 수 있을 만큼 고정하거나 실제 사용 판본을 기록한다.
- 검증 절차는 검사 범위와 필수·선택 항목을 구분하며, 필수 항목을 실행하지 못한 상태를 성공으로 표시하지 않는다.
- 기준 구현이나 기대 결과가 있다면 통과를 확인하고, 의도적으로 미완성인 시작 상태나 알려진 잘못된 결과가 같은 판단 기준에서 거부되는지도 확인한다.
- 자동 검사기는 정답 소스의 문자열이나 내부 모양보다 공개 행동, 상태, 불변식과 관측 결과를 우선한다.
- 준비·검증·정리 절차는 추적 source와 학습자 작업을 예고 없이 덮어쓰거나 삭제하지 않는다.
- 임시 파일, 프로세스, 컨테이너와 장치 상태는 실행별로 구분하고 성공·실패·중단 뒤 정리 범위를 설명한다.
- 로그와 보고서는 성공 여부뿐 아니라 실행한 검사, 생략한 범위와 실패 원인을 검토할 수 있게 남긴다.

이 절차가 모두 동작해도 설명의 정확성, 학습 순서와 종료 능력의 충분성은 사람 검토 대상으로 남는다.

## 종료 근거의 연결

브랜치가 소유한다고 선언한 내용은 다음 흐름으로 추적할 수 있어야 한다.

```text
소유 범위
→ 학습 결과
→ 개념 설명
→ 단계 실습과 대표 실패
→ capstone 또는 동등한 누적 과제
→ 종료 능력
```

별도의 표 파일을 의무화하지는 않는다. roadmap, 실습 README와 종료 과제에서 이 연결을 사람이 따라갈 수 있으면 된다. 다음은 완성도 결함이다.

- `owns`에는 있지만 학습 경로에서 찾을 수 없는 내용
- 설명은 있지만 관찰·구현·추론할 기회가 없는 핵심 능력
- 단계 실습에는 있지만 누적 종료 과제에서 서로 연결되지 않는 능력
- 종료 능력에는 있지만 어떤 결과를 보고 판단할지 알 수 없는 주장
- 인접 브랜치가 소유한 내용을 출처와 경계 없이 다시 만든 설명

## 품질 프로필별 근거

프로필은 공통 계약을 대체하지 않는다. 분야마다 강한 근거의 모양이 다르므로 무엇을 더 깊게 검토할지 정한다.

| 프로필 | 특히 확인할 질문 | 적합한 누적 근거의 예 |
|---|---|---|
| 모델·이론 | 전제, 불변식, 반례, 복잡도와 모델의 한계가 드러나는가 | 증명 또는 설명, 반례 모음, oracle과 비교, 모델 구현과 해석 |
| 구현·애플리케이션 | 입력·출력·상태 계약과 통합 경계가 실제 동작으로 이어지는가 | 독립 구현, 통합 기능, 호환성·오류 사례, 사용자 흐름 |
| 운영·보안 | 권한, 위협, 장애 전파, 관측, 안전한 복구와 회귀 방지가 연결되는가 | 격리된 장애·공격 재현, runbook 실행, 최소 패치, 복구와 사후 분석 |
| 데이터·ML | 데이터 출처, 품질, 분할, 누수, 재현성, 평가와 오류 분석이 공개되는가 | 재현 가능한 pipeline·실험, baseline 비교, 데이터 검증, 모델·데이터 카드 |
| 하드웨어·그래픽스 | 시간·메모리·장치 제약과 측정 오차, simulator와 실제 환경의 차이를 설명하는가 | trace·benchmark, 장치 또는 simulator 실험, 시각 결과와 비시각적 정확성 근거 |

예를 들어 `database-systems`는 모델·이론과 구현 프로필을 함께 가질 수 있고, `web-infra`는 구현과 운영 프로필을 함께 가질 수 있다. 프로필 수가 많다고 더 완성된 브랜치인 것은 아니다. 소유 범위에 필요한 프로필만 선택한다.

## 사람 검토 기준

리뷰는 점수를 합산하는 방식이 아니다. 저자 외의 검토자가 다음 세 관점에서 핵심 공백이 있는지 판단한다.

### 구조

- 처음 온 독자가 시작 위치, 순서와 종료 지점을 찾을 수 있는가
- 필요한 환경을 준비하고 실습 뒤 안전하게 정리할 수 있는가
- 개념, 단계 실습과 누적 종료 과제가 서로 연결되는가
- 기여·출처·라이선스·지원 환경을 확인할 수 있는가

### 품질

- 설명과 기대 결과가 기술적으로 타당한가
- 대표적인 정상·경계·실패 조건을 다루는가
- 검증 또는 수동 검토의 근거와 한계를 구분하는가
- 안전, 권한, 데이터·자원 보존 조건을 필요한 만큼 다루는가
- 특정 제품 사용법보다 이 브랜치가 소유한 원리를 가르치는가

### 완성도

- 모든 핵심 `owns`와 종료 능력의 근거를 학습 경로에서 찾을 수 있는가
- capstone 또는 동등한 누적 최종 실습이 핵심 능력을 함께 요구하는가
- 선행 지식과 비소유 범위가 인접 브랜치에 정확히 연결되는가
- 독자가 완료 뒤 시도할 실제 프로젝트와 다음 심화 경로가 구체적인가
- 알려진 제약과 아직 보장하지 않는 범위가 숨겨져 있지 않은가

리뷰 결과는 다음처럼 해석한다.

- **충족**: 핵심 학습 결과와 종료 근거에 중대한 공백이 없다.
- **보완 필요**: 방향은 맞지만 브랜치 완료 판단을 막는 공백이 있다.
- **허용된 변형**: 표준 구조와 다르지만 같은 역할을 더 적합한 근거로 수행한다.

실제 구현에 미해결 `보완 필요` 항목이 있으면 브랜치 완료로 승인하지 않는다. 문장 다듬기처럼 종료 능력에 영향을 주지 않는 후속 개선은 남을 수 있다. 자동 검사 결과나 카탈로그의 `stable` 표기만으로 이 결정을 바꾸지 않는다.

## 완성 목표 계약과 브랜치 완료 흐름

1. 실제 결과물과 독자를 정하고 브랜치 종류를 하나 선택한다.
2. `owns`, `excludes`, 선행 관계와 종료 능력을 먼저 작성한다.
3. 필요한 품질 프로필을 선택하고 누적 종료 근거의 형태를 정한다.
4. 최종 상태의 구조·관계·종료 근거 설계를 사람이 검토하고 `main` 카탈로그와 트랙에 `stable` 목표 계약으로 먼저 연결한다.
5. 생성 문서와 검사를 갱신해 `main`을 먼저 게시한다.
6. 제공된 초안과 독립 이력을 출발점으로 개념 설명, 단계 실습, 대표 실패와 누적 종료 과제를 구현한다.
7. 저자는 기준 경로를 처음부터 끝까지 따라가며 알려진 제약을 기록한다.
8. 사람 리뷰어는 실제 브랜치의 구조·품질·완성도와 인접 브랜치 경계를 검토하고 중대한 공백을 해결한 뒤 브랜치 완료를 승인한다.

구현 중 `owns` 또는 종료 능력이 달라져야 한다면 후속 브랜치에만 예외를 만들지 않고 `main`의 목표 계약을 먼저 갱신한다. 사소한 문구 변경마다 전체 승인을 반복할 필요는 없지만, 경계·실습·누적 종료 근거가 바뀌는 변경은 품질 계약의 영향을 다시 확인한다.
