# 오류·검증·시간과 식별자

실패를 모두 하나의 예외나 `false`로 표현하면 호출자는 수정해야 할 입력, 현재 상태의 거절과 일시적인 실행 환경 문제를 구분할 수 없습니다. 오류 모델은 예외 클래스의 수보다 실패 뒤 호출자가 무엇을 할 수 있는지를 기준으로 설계합니다.

## 실패의 성격

애플리케이션에서는 적어도 다음을 구분합니다.

| 실패 | 예 | 일반적인 다음 행동 |
|---|---|---|
| 입력 계약 위반 | 빈 식별자, 음수 금액 | 입력을 수정합니다. |
| 현재 상태의 거절 | 잔액 부족, 이미 닫힌 실행기 | 상태를 확인하거나 다른 요청을 선택합니다. |
| 실행 환경 실패 | 파일 I/O, 시간 초과 | 원인을 기록하고 제한된 복구나 재시도를 검토합니다. |
| 프로그래밍 불변식 위반 | 도달할 수 없는 상태 | 결함으로 보고하고 원인을 수정합니다. |

업무상 거절을 일시적인 장애로 분류하면 정상 요청이 무의미하게 재시도될 수 있습니다. 반대로 실행 환경의 시간 초과를 입력 오류로 숨기면 호출자가 복구할 근거를 잃습니다.

## checked exception과 unchecked exception

Java의 checked exception은 호출부가 처리하거나 선언해야 합니다. 파일과 네트워크 같은 경계에서 자주 만납니다. unchecked exception은 타입 시그니처에 강제되지 않지만 실패 계약에서 사라지는 것은 아닙니다.

선택 기준은 기계적으로 “복구 가능하면 checked”가 아닙니다.

- 현재 계층이 의미 있게 처리할 수 있으면 처리합니다.
- 상위 경계가 결정해야 하면 원인을 보존해 전달합니다.
- 저수준 기술 예외를 공개 API 전체에 누출하지 않도록 의미 있는 경계에서 번역합니다.
- 예상 가능한 입력·상태 거절은 구체적인 타입과 메시지를 사용합니다.

```java
try {
  return Files.readString(path);
} catch (IOException error) {
  throw new ConfigurationLoadException("설정을 읽지 못했습니다: " + path, error);
}
```

원인 예외를 버리거나 로그를 남기고 성공값을 반환하지 않습니다. 같은 예외를 여러 계층에서 반복해서 로그로 남기면 한 실패가 여러 사건처럼 보일 수 있습니다.

## 검증 위치

같은 규칙이 여러 계층에 있어도 목적이 다를 수 있습니다.

- 전송 경계는 문자열 형식과 필수 필드를 빠르게 거부합니다.
- 값 객체 생성자는 언제나 참이어야 하는 불변식을 지킵니다.
- 애플리케이션 서비스는 현재 상태와 정책을 판단합니다.
- 데이터 저장소 제약은 경쟁하는 요청 사이에서도 마지막 무결성을 지킵니다.

값 객체가 사용자 권한이나 데이터베이스 조회를 직접 수행하게 하지 않습니다. 반대로 “금액은 음수가 아니다”처럼 항상 참인 규칙을 모든 서비스에서 반복하지 않습니다.

## 실패 뒤 상태

동작이 실패했을 때 객체와 외부 상태가 어떤 상태로 남는지 계약에 포함합니다.

```text
검증 실패       → 상태 변화 없음
정확한 연산 실패 → 상태 변화 없음
외부 저장 실패   → 메모리 상태와 저장 상태의 관계를 명시
취소·인터럽트    → 완료한 작업과 남은 작업을 명시
```

상태를 먼저 바꾸고 뒤늦게 예외를 내면 호출자가 재시도할 때 중복 효과가 생길 수 있습니다. 필요한 검증과 새 값 계산을 먼저 끝낸 뒤 상태를 한 번에 반영합니다.

## 자원 수명

파일, Stream, 소켓과 실행기는 명시적으로 닫아야 합니다. `AutoCloseable`은 소유자가 수명을 드러내는 도구입니다.

```java
try (BufferedReader reader = Files.newBufferedReader(path)) {
  return reader.lines().toList();
}
```

자원을 만든 코드가 기본 소유자입니다. 호출자에게 반환해 수명을 넘길 때는 누가 닫는지 API에 드러냅니다. 예외와 조기 반환에서도 정리가 실행되어야 합니다.

## 시간을 직접 읽지 않기

저장하거나 이벤트로 전달하는 순간은 `Instant`를 기본으로 두고 UTC로 보존합니다. 사용자의 지역 시간은 입력과 표시 경계에서 `ZoneId`와 함께 변환합니다.

테스트할 로직에서 `Instant.now()`를 직접 호출하지 않고 `Clock`을 주입합니다.

```java
public final class ExpiryPolicy {
  private final Clock clock;

  public ExpiryPolicy(Clock clock) {
    this.clock = Objects.requireNonNull(clock, "clock");
  }

  public boolean expired(Instant deadline) {
    return !clock.instant().isBefore(deadline);
  }
}
```

테스트에서는 `Clock.fixed`로 경계 시각을 고정합니다.

```java
Clock clock = Clock.fixed(
    Instant.parse("2026-01-02T03:04:05Z"),
    ZoneOffset.UTC);
```

마감 시각과 같은 순간을 포함하는지, 일광 절약 시간 전환과 현지 날짜를 어떻게 처리하는지 테스트 이름에 드러냅니다.

## 식별자의 계약

UUID를 사용한다는 사실만으로 식별자 설계가 끝나지 않습니다. 다음을 결정합니다.

- 누가 생성합니까?
- 저장 전에 생성합니까, 저장소가 생성합니까?
- 같은 요청을 다시 전달할 때 같은 식별자를 사용합니까?
- 외부에 내부 식별자를 그대로 노출합니까?
- 업무 대상 식별자, 요청 상관관계 식별자와 작업 식별자를 구분합니까?
- 같은 식별자로 다른 내용이 들어오면 어떻게 거부합니까?

식별자를 `String`으로 흩뿌리지 않고 값 객체로 감싸면 빈 값과 서로 다른 종류의 식별자를 섞는 실수를 줄일 수 있습니다.

```java
public record JobId(String value) {
  public JobId {
    if (value == null || value.isBlank()) {
      throw new IllegalArgumentException("작업 식별자가 필요합니다.");
    }
  }
}
```

## 민감한 정보와 진단

예외 메시지와 로그에 비밀번호, 토큰, 세션 식별자와 개인정보를 넣지 않습니다. 예상하지 못한 예외에는 스택 추적과 안전한 상관관계 식별자를 남기고, 예상 가능한 거절은 필요한 수준의 진단만 기록합니다.

사용자에게 보여 줄 메시지와 운영자가 원인을 좁힐 진단을 분리합니다. 내부 클래스 이름과 SQL 문장을 그대로 외부 응답으로 노출하지 않습니다.

## 완료 기준

- 입력 위반, 상태 거절, 실행 환경 실패와 불변식 위반을 구분합니다.
- 예외를 번역할 때 원인을 보존합니다.
- 실패 전에 검증과 새 값 계산을 끝내고 기존 상태를 보존합니다.
- 닫을 자원의 소유자와 종료 경로를 명시합니다.
- `Clock`으로 시간 경계를 재현합니다.
- 식별자의 생성, 재사용과 충돌 의미를 설명합니다.
