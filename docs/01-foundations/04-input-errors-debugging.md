# 입력 오류와 디버깅: 실패를 분류하고 재현하기

프로그램에 문제가 생겼을 때 곧바로 "어디가 잘못되었는가"부터 찾기보다 먼저 **어떤 종류의 실패인지** 구분해야 합니다.

사용자가 잘못된 값을 입력한 경우와 프로그램이 유효하지 않은 메모리에 접근한 경우는 원인도 다르고 대응 방법도 다릅니다. 코드 자체의 결함을 단순한 입력 오류처럼 처리해서는 안 됩니다.

## 실패 유형 구분하기

| 유형        | 예                   | 주된 대응                      |
| --------- | ------------------- | -------------------------- |
| 입력 계약 위반  | 인자 누락, 숫자가 아닌 문자열   | 명확한 진단, 적절한 종료 상태          |
| 도메인 규칙 위반 | 허용 범위를 벗어난 값        | 입력 거부, 기존 상태 보존            |
| 자원 확보 실패  | 메모리 할당 실패, 파일 열기 실패 | 확보한 자원 정리, 오류 전파           |
| 코드 결함     | 범위 밖 접근, 잘못된 포인터 사용 | 재현, 디버거와 sanitizer를 이용한 수정 |

예를 들어 배열 범위를 벗어난 접근 때문에 프로그램이 실패했다면 이를 `"입력이 잘못되었습니다"`라는 메시지로 감춰서는 안 됩니다. 입력이 잘못된 것과 프로그램 구현이 잘못된 것은 서로 다른 문제입니다.

## `strtol`로 숫자 문자열 전체 검증하기

`atoi`는 변환 실패와 정상적인 `0`을 구분하기 어렵고 범위 오류도 확인할 수 없습니다. 입력을 검증해야 한다면 `strtol`처럼 변환 결과를 세부적으로 확인할 수 있는 함수를 사용하는 편이 좋습니다.

```c
#include <ctype.h>
#include <errno.h>
#include <limits.h>
#include <stdlib.h>

int parse_long(const char *text, long *out_value)
{
    char *end;
    long value;

    if (text == NULL || out_value == NULL || *text == '\0' ||
        isspace((unsigned char)*text))
    {
        return -1;
    }

    errno = 0;
    value = strtol(text, &end, 10);

    if (errno == ERANGE || end == text || *end != '\0')
    {
        return -1;
    }

    *out_value = value;
    return 0;
}
```

이 함수의 계약에서는 앞쪽 공백도 허용하지 않는다고 가정합니다. `strtol` 자체는 앞쪽 공백을 건너뛰므로, 이를 금지하려면 호출 전에 별도로 검사해야 합니다.

검사 흐름은 다음과 같습니다.

1. `NULL` 포인터와 빈 문자열을 확인합니다.
2. 계약상 허용하지 않는 앞쪽 공백을 확인합니다.
3. `errno`를 `0`으로 초기화합니다.
4. `strtol`을 호출합니다.
5. 한 글자도 변환하지 못했는지 확인합니다.
6. 문자열 끝까지 모두 변환했는지 확인합니다.
7. 값이 `long`의 범위를 벗어났는지 확인합니다.
8. 모든 검사가 성공한 뒤에만 출력 매개변수를 변경합니다.

마지막 원칙이 특히 중요합니다. 실패한 경우 `*out_value`를 그대로 유지하면 호출자는 부분적으로 변경된 결과를 따로 처리하지 않아도 됩니다.

## 오류 메시지도 계약의 일부다

좋은 오류 메시지는 적어도 다음 내용을 판단할 수 있게 해야 합니다.

* 어떤 입력에서 문제가 발생했는가?
* 어떤 형식이나 값이 필요했는가?
* 프로그램은 실패를 어떤 종료 상태로 알리는가?

예를 들어 다음과 같이 잘못된 입력값을 함께 출력할 수 있습니다.

```c
fprintf(stderr, "오류: 정수가 아닙니다: %s\n", argv[index]);
return 2;
```

오류 메시지를 자동 테스트에서 검사할 수도 있습니다. 다만 테스트가 문장의 띄어쓰기나 표현 전체에 지나치게 의존하면 메시지를 조금만 개선해도 테스트가 깨질 수 있습니다.

필요하다면 다음처럼 안정적으로 유지할 부분을 따로 정합니다.

```text
오류:
잘못된 입력:
사용법:
```

사람이 읽는 설명은 개선할 수 있도록 두면서, 프로그램이나 테스트가 의존하는 최소한의 형식만 계약으로 고정하는 방식입니다.

## 최소 재현 만들기

오류를 수정하기 전에 먼저 **같은 문제를 반복해서 발생시킬 수 있는 조건**을 확보해야 합니다.

다음 정보를 기록합니다.

```text
실패한 실행 명령
사용한 입력 파일 또는 명령행 인자
컴파일 옵션
실제 stdout
실제 stderr
종료 상태
운영체제와 컴파일러
```

그다음 입력과 실행 조건을 하나씩 줄여도 같은 문제가 발생하는지 확인합니다.

예를 들어 처음에는 1000줄짜리 입력에서만 문제가 발생한다고 생각했더라도, 입력을 줄여 가다 보면 실제 원인이 마지막의 빈 줄 하나라는 사실을 발견할 수 있습니다.

재현 조건이 작아질수록 관련 없는 코드와 상태가 제거되므로 원인을 찾기도 쉬워집니다.

## 디버그 빌드 만들기

디버거로 문제를 확인할 때는 소스 코드와 실행 상태를 연결할 수 있는 정보를 포함해 빌드합니다.

```sh
cc -std=c99 -Wall -Wextra -Wpedantic -g -O0 source.c -o program
```

각 옵션의 역할은 다음과 같습니다.

* `-g`는 디버거가 소스 위치, 함수와 변수 정보를 확인할 수 있도록 디버그 정보를 생성합니다.
* `-O0`은 최적화를 끄므로 처음 디버깅할 때 소스 코드와 실제 실행 흐름을 비교하기 쉽습니다.
* 평소 사용하는 경고 옵션은 그대로 유지합니다.

다만 `-O0`에서 문제가 사라진다고 해서 결함이 해결된 것은 아닙니다. 최적화된 빌드에서만 나타나는 문제도 있습니다.

문제를 수정한 뒤에는 실제로 사용할 최적화 설정으로 다시 빌드해 같은 입력을 재검사해야 합니다.

## 디버거의 기본 사용 흐름

GDB에서는 다음과 같이 시작할 수 있습니다.

```sh
gdb ./program
(gdb) break main
(gdb) run 10 bad 30
(gdb) next
(gdb) print index
(gdb) print argv[index]
(gdb) backtrace
```

LLDB에서는 비슷한 작업을 다음과 같이 수행합니다.

```sh
lldb ./program
(lldb) breakpoint set --name main
(lldb) run 10 bad 30
(lldb) next
(lldb) frame variable index
(lldb) bt
```

처음에는 몇 가지 동작만 익혀도 충분합니다.

* 문제가 발생하기 전 위치에 breakpoint를 설정합니다.
* `next`로 현재 함수의 다음 문장까지 실행합니다.
* `step`으로 호출하는 함수 내부에 들어갑니다.
* 현재 변수와 인자의 값을 확인합니다.
* `backtrace`로 현재 위치까지 어떤 함수들이 호출되었는지 확인합니다.

디버거의 목적은 코드를 한 줄씩 무작정 따라가는 것이 아닙니다.

먼저 **어떤 값이 잘못되었을 것이라고 예상하는지** 정하고, breakpoint와 변수 확인을 통해 그 예상이 맞는지 검사합니다.

더 자세한 명령은 [디버거 부록](../90-appendix/01-debugger-reference.md)에서 다룹니다.

## sanitizer로 잘못된 실행 찾기

컴파일러가 제공하는 sanitizer를 사용하면 실행 중 발생하는 여러 종류의 잘못된 동작을 더 쉽게 찾을 수 있습니다.

```sh
cc -std=c99 -Wall -Wextra -Wpedantic -g \
    -fsanitize=address,undefined -fno-omit-frame-pointer \
    source.c -o program

./program
```

AddressSanitizer는 대표적으로 다음과 같은 메모리 오류를 찾는 데 도움이 됩니다.

* 힙이나 스택의 범위를 벗어난 메모리 접근
* 해제한 메모리를 다시 사용하는 오류
* 이미 해제한 메모리를 다시 해제하는 오류
* 일부 잘못된 메모리 사용

환경에 따라 누수 검사 기능도 함께 제공되거나 별도의 LeakSanitizer가 사용될 수 있습니다.

UndefinedBehaviorSanitizer는 대표적으로 다음과 같은 정의되지 않은 동작의 일부를 실행 중에 검사합니다.

* 부호 있는 정수 오버플로
* 잘못된 shift 연산
* 정렬 조건을 위반한 메모리 접근
* 일부 잘못된 산술 연산과 타입 사용

sanitizer가 활성화되어 있다고 해서 모든 결함을 발견할 수 있는 것은 아닙니다.

해당 코드가 실제로 실행되어야 검사할 수 있으므로, 테스트하지 않은 실행 경로의 결함은 그대로 남을 수 있습니다. 따라서 sanitizer도 충분한 테스트 입력과 함께 사용해야 합니다.

## 경고를 오류로 다루는 시점

학습 초기에는 경고를 무조건 제거하는 것보다 **경고가 무엇을 의미하는지 읽고 이해하는 능력**이 먼저 필요합니다.

코드의 기준이 안정된 뒤에는 연습문제나 자동 빌드에서 `-Werror`를 사용해 새로운 경고가 그대로 누적되는 것을 막을 수 있습니다.

```sh
cc -std=c99 -Wall -Wextra -Wpedantic -Werror source.c -o program
```

다만 경고를 없애는 것 자체가 목표가 되어서는 안 됩니다.

특히 캐스트를 추가해 경고를 억지로 숨기기 전에 다음을 확인합니다.

* 처음부터 잘못된 타입을 선택하지 않았는가?
* 부호 있는 정수와 부호 없는 정수를 의도하지 않게 섞고 있지 않은가?
* 형식 지정자와 실제 인자의 타입이 일치하는가?
* 무시한 반환값을 실제로 확인해야 하는 것은 아닌가?
* 변환하려는 값이 대상 타입의 범위 안에 있다는 근거가 있는가?

경고는 코드의 문제를 알려 주는 단서입니다. 경고 메시지만 사라지게 만드는 것이 아니라 **경고가 발생한 원인을 해결해야 합니다.**
