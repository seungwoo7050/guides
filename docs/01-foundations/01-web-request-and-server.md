# 웹 요청과 서버의 기본 구조

이 장의 목표는 Docker를 실행하는 것이 아닙니다. 먼저 서버가 실제로 무엇인지, 클라이언트가 어디에 연결하는지, 실패가 어느 계층에서 발생하는지 구분합니다.

완료하면 다음 문장을 자신의 말로 설명할 수 있어야 합니다.

> 서버는 특정 주소와 포트에서 연결을 기다리는 프로세스이며, HTTP는 그 연결 위에서 요청과 응답의 형식을 정합니다.

## 1. 요청 흐름을 확인할 실습 시스템

`exercises/01-request-and-process`의 작은 HTTP 서버를 사용합니다.

- `127.0.0.1:18081`에서 서버를 실행합니다.
- `/healthz`에 요청해 `200 OK`를 받습니다.
- 존재하지 않는 경로에서 `404 Not Found`를 확인합니다.
- 프로세스와 열린 포트를 관찰합니다.
- 서버를 종료한 뒤 HTTP 오류가 아니라 연결 실패가 발생하는 이유를 설명합니다.

처음 실행하기 전에 다음 결과를 예측합니다.

```sh
curl -i http://127.0.0.1:18081/healthz
curl -i http://127.0.0.1:18081/missing
```

두 명령은 모두 같은 프로세스의 같은 포트에 연결하지만 응답 상태는 다릅니다. 반면 서버 프로세스가 없으면 HTTP 응답 자체를 받을 수 없습니다.

## 2. URL을 입력하면 일어나는 일

다음 URL을 예로 듭니다.

```text
https://example.test:443/articles?id=10
```

구성 요소를 나누면 다음과 같습니다.

| 구성 요소 | 예 | 의미 |
|---|---|---|
| 스킴 | `https` | 사용할 애플리케이션 프로토콜과 TLS 사용 여부 |
| 호스트 | `example.test` | 연결할 서버를 찾기 위한 이름 |
| 포트 | `443` | 서버의 연결 지점 |
| 경로 | `/articles` | 서버에 요청할 자원 또는 라우트 |
| 쿼리 | `id=10` | 경로와 함께 전달하는 추가 입력 |

브라우저가 URL을 처리하는 전체 흐름을 단순화하면 다음과 같습니다.

```text
1. 호스트 이름을 IP 주소로 해석합니다.
2. IP 주소의 지정 포트로 TCP 연결을 맺습니다.
3. HTTPS라면 TLS 핸드셰이크를 수행합니다.
4. HTTP 요청을 전송합니다.
5. 서버가 HTTP 응답을 반환합니다.
6. 연결을 닫거나 다음 요청에 재사용합니다.
```

각 단계는 서로 다른 형태로 실패합니다. DNS가 실패하면 IP 주소를 얻지 못합니다. TCP 연결이 실패하면 HTTP 요청은 전송되지 않습니다. TLS 검증이 실패하면 TCP 연결은 만들어졌더라도 신뢰할 수 있는 HTTPS 요청 단계로 진행하지 못합니다. HTTP 404는 앞선 연결 단계가 성공한 뒤 서버가 보낸 정상적인 HTTP 응답입니다.

## 3. 클라이언트와 서버

클라이언트는 연결과 요청을 시작합니다. 서버는 연결이 들어오기를 기다립니다.

```text
클라이언트                          서버
   │                                 │
   │ TCP connect                     │ listen
   ├────────────────────────────────▶│
   │ HTTP request                    │ accept + read
   ├────────────────────────────────▶│
   │                                 │ 처리
   │ HTTP response                   │
   │◀────────────────────────────────┤
```

웹 브라우저와 `curl`은 HTTP 클라이언트입니다. Nginx, Apache, 애플리케이션 내장 서버는 HTTP 서버가 될 수 있습니다. MariaDB도 서버지만 HTTP가 아니라 MariaDB/MySQL 프로토콜을 사용합니다. PHP-FPM 역시 서버 프로세스지만 HTTP가 아니라 FastCGI를 사용합니다.

따라서 “서버가 살아 있다”는 말만으로는 부족합니다. 어떤 서버가 어떤 프로토콜에 응답하는지를 지정해야 합니다.

- Nginx가 HTTPS 요청에 응답합니다.
- PHP-FPM이 FastCGI 요청에 응답합니다.
- MariaDB가 데이터베이스 핸드셰이크와 쿼리에 응답합니다.

프로토콜이 다르면 검사 도구도 달라집니다.

## 4. IP 주소와 포트

### 4.1 `127.0.0.1`과 `localhost`

`127.0.0.1`은 IPv4 루프백 주소입니다. 네트워크 패킷이 외부 장치로 나가지 않고 같은 운영체제 안으로 돌아옵니다.

`localhost`는 일반적으로 루프백 주소로 해석되는 이름입니다. 환경에 따라 IPv4 `127.0.0.1` 또는 IPv6 `::1`로 해석될 수 있습니다. 이름과 주소는 같은 개념이 아닙니다.

```sh
getent hosts localhost 2>/dev/null || true
```

### 4.2 `0.0.0.0`

서버의 수신 설정에서 `0.0.0.0`은 “이 컴퓨터가 가진 모든 IPv4 인터페이스에서 연결을 받는다”는 뜻입니다.

클라이언트가 연결 대상으로 `0.0.0.0`을 사용하는 개념과 혼동하지 않습니다. 서버는 `0.0.0.0:8080`에서 기다릴 수 있지만 클라이언트는 실제로 도달 가능한 주소인 `127.0.0.1:8080`, LAN 주소 또는 도메인을 사용합니다.

### 4.3 포트

IP 주소가 컴퓨터 또는 네트워크 인터페이스를 가리킨다면 포트는 그 안에서 어떤 프로세스의 연결 지점인지 구분합니다.

```text
127.0.0.1:8080  → 개발 서버
127.0.0.1:3306  → 데이터베이스
127.0.0.1:9000  → FastCGI 서버
```

포트 번호가 프로세스를 자동으로 결정하지는 않습니다. 관례적인 기본값이 있을 뿐입니다. HTTP 서버를 3306에서 실행할 수도 있고 MariaDB를 다른 포트에서 실행할 수도 있습니다. 중요한 것은 클라이언트와 서버가 같은 포트를 사용하도록 설정되어 있는지입니다.

### 4.4 수신 대기와 연결

서버는 주소와 포트에 소켓을 바인드하고 연결을 기다립니다. 클라이언트는 그 주소와 포트로 연결합니다.

```text
서버: bind(127.0.0.1, 18081) → listen
클라이언트: connect(127.0.0.1, 18081)
```

서버가 해당 포트에서 기다리지 않으면 운영체제는 보통 즉시 연결을 거부합니다. 방화벽이나 네트워크 경로가 패킷을 버리면 응답을 받지 못한 채 기다리다가 타임아웃이 발생할 수 있습니다.

## 5. TCP와 HTTP의 관계

TCP는 순서가 보장된 바이트 스트림을 제공합니다. TCP 자체는 URL, 상태 코드, JSON을 모릅니다. HTTP가 TCP 연결 위에서 메시지 형식을 정의합니다.

간단한 HTTP 요청은 다음과 같습니다.

```http
GET /healthz HTTP/1.1
Host: 127.0.0.1:18081
User-Agent: curl/8.x
Accept: */*

```

응답은 다음과 같습니다.

```http
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Content-Length: 3

ok
```

포트가 열려 있다는 사실만으로 HTTP가 정상이라고 결론 내릴 수 없습니다.

- TCP 연결은 성공했지만 서버가 HTTP가 아닌 다른 프로토콜을 사용할 수 있습니다.
- HTTP 요청은 받지만 애플리케이션이 500을 반환할 수 있습니다.
- 요청은 성공하지만 응답 내용이 잘못될 수 있습니다.

운영 상태를 검사할 때는 확인하려는 수준에 맞는 실제 프로토콜을 사용해야 합니다.

## 6. HTTP 요청

### 6.1 메서드

메서드는 요청의 의도를 나타냅니다.

- `GET`: 자원 조회
- `POST`: 데이터 제출 또는 처리 요청
- `PUT`: 일반적으로 지정 자원의 전체 교체
- `PATCH`: 일부 변경
- `DELETE`: 삭제 요청

메서드 이름만으로 서버가 안전한 동작을 보장하지는 않습니다. 실제 동작은 서버 구현이 결정합니다. 다만 HTTP 의미론을 따를수록 캐시, 프록시, 클라이언트와의 상호운용성이 좋아집니다.

### 6.2 경로와 쿼리

```text
/search?q=container&page=2
```

- 경로: `/search`
- 쿼리 문자열: `q=container&page=2`

Nginx의 `location` 선택은 일반적으로 URI 경로를 기준으로 하고 애플리케이션은 쿼리 문자열을 입력값으로 사용할 수 있습니다.

### 6.3 헤더

헤더는 메시지의 메타데이터입니다.

- `Host`: 어떤 가상 호스트를 원하는지
- `Content-Type`: 본문 형식
- `Content-Length`: 본문 길이
- `Authorization`: 인증 정보
- `Accept`: 받을 수 있는 응답 형식

프록시를 여러 단계 거치면 각 계층이 헤더를 추가하거나 수정할 수 있습니다.

### 6.4 본문

`POST`나 `PUT` 요청은 본문에 JSON, 폼 데이터, 파일 등을 담을 수 있습니다. 서버는 `Content-Type`과 본문을 함께 해석합니다.

## 7. HTTP 응답

응답은 상태 줄, 헤더, 본문으로 구성됩니다.

### 7.1 상태 코드 범주

| 범주 | 의미 | 예 |
|---|---|---|
| 2xx | 요청 처리 성공 | 200, 201, 204 |
| 3xx | 리디렉션 또는 캐시 관련 응답 | 301, 302, 304 |
| 4xx | 요청을 처리할 수 없음 | 400, 401, 403, 404 |
| 5xx | 서버가 요청 처리 중 실패 | 500, 502, 503, 504 |

상태 코드만으로 원인을 확정하지 않습니다. 예를 들어 502는 게이트웨이가 업스트림에서 유효한 응답을 얻지 못했다는 뜻이지만, 업스트림 프로세스 종료, 포트 불일치, 이름 해석 실패, 프로토콜 불일치 등 여러 원인이 있을 수 있습니다.

### 7.2 `curl -i`와 `curl -v`

```sh
curl -i http://127.0.0.1:18081/healthz
```

`-i`는 응답 헤더를 본문과 함께 출력합니다.

```sh
curl -v http://127.0.0.1:18081/healthz
```

`-v`는 이름 해석, 연결 대상, 요청 헤더, 응답 헤더 등 진단 정보를 stderr에 출력합니다. 문제를 좁힐 때 유용하지만 자동 검증에서는 출력보다 종료 코드를 우선 사용합니다.

### 7.3 종료 코드

셸에서 명령의 성공 여부는 종료 코드로 전달됩니다.

```sh
curl -fsS http://127.0.0.1:18081/healthz
printf 'exit=%s\n' "$?"
```

일반적으로 0은 성공, 0이 아닌 값은 실패입니다. `curl`은 기본 설정에서 HTTP 404나 500도 “HTTP 응답을 받았다”는 의미로 종료 코드 0을 반환할 수 있습니다. 자동 검사에서는 `-f` 또는 `--fail-with-body`를 사용해 HTTP 오류를 0이 아닌 종료 코드로 처리합니다.

## 8. HTTPS가 추가하는 것

HTTPS는 HTTP를 TLS 연결 위에서 전달합니다.

TLS가 제공하려는 핵심 성질은 다음과 같습니다.

1. 전송 중인 내용을 제3자가 쉽게 읽거나 변조하지 못하게 합니다.
2. 클라이언트가 연결한 서버의 신원을 인증서 체인을 통해 검증합니다.

서버는 개인키와 인증서를 가집니다. 개인키는 외부에 공개하면 안 됩니다. 인증서는 공개키, 도메인 이름, 유효기간, 발급자 등의 정보를 담습니다.

공인 CA가 서명한 인증서는 클라이언트의 신뢰 저장소를 통해 검증됩니다. 자체 서명 인증서는 자신의 키로 직접 서명했기 때문에 암호화 연결은 만들 수 있지만 클라이언트가 별도로 신뢰하도록 설정하지 않은 한 제3자의 신원 보증을 제공하지 않습니다.

개발 환경에서 `curl -k`를 사용하면 인증서 검증을 끕니다. 인증서 문제를 의도적으로 무시하는 것이지 인증서를 신뢰하게 만드는 것이 아닙니다. 운영 환경에서 습관적으로 사용하면 중간자 공격과 인증서 구성 오류를 발견하지 못할 수 있습니다.

TLS 인증서 생성과 Nginx 설정은 4장에서 다룹니다.

## 9. 실행 중인 프로세스로서의 서버

### 9.1 프로그램과 프로세스

프로그램은 디스크에 저장된 코드와 데이터입니다. 프로세스는 그 프로그램이 실행되어 메모리, 열린 파일, 환경변수, PID 등의 상태를 가진 인스턴스입니다.

같은 프로그램을 여러 번 실행하면 서로 다른 프로세스가 됩니다.

```sh
ps -ef
```

### 9.2 PID

PID는 운영체제가 프로세스에 부여하는 식별자입니다. 프로세스가 종료되면 같은 숫자가 나중에 다른 프로세스에 재사용될 수 있습니다.

```sh
printf '%s\n' "$$"
```

셸에서 `$$`는 현재 셸의 PID입니다.

### 9.3 포그라운드와 백그라운드 실행

포그라운드 프로세스는 현재 터미널의 입력과 제어를 직접 받습니다. 명령 뒤에 `&`를 붙이면 셸은 프로세스를 백그라운드에서 실행하고 즉시 다음 명령을 받을 수 있습니다.

```sh
python3 server.py &
pid=$!
printf 'server pid=%s\n' "$pid"
```

`$!`는 가장 최근에 백그라운드로 시작한 프로세스의 PID입니다.

컨테이너에서는 주 프로세스가 포그라운드에 남아 있어야 컨테이너의 수명과 서비스의 수명을 일치시키기 쉽습니다. 이 문제는 2장에서 다룹니다.

### 9.4 시그널

시그널은 프로세스에 이벤트를 전달하는 운영체제 메커니즘입니다.

- `SIGTERM`: 정상 종료 기회를 주는 일반적인 종료 요청
- `SIGINT`: 터미널의 Ctrl-C와 연결되는 중단 요청
- `SIGKILL`: 프로세스가 처리하거나 무시할 수 없는 강제 종료

```sh
kill -TERM "$pid"
wait "$pid"
```

서버는 SIGTERM을 받으면 새 연결 수락을 중단하고 진행 중인 작업을 마친 뒤 파일이나 데이터베이스 상태를 정리할 수 있습니다. 바로 SIGKILL을 사용하면 이 기회를 잃습니다.

### 9.5 종료 코드

프로세스는 종료할 때 부모 프로세스에 정수 상태를 반환합니다.

```sh
false
printf '%s\n' "$?"   # 일반적으로 1
```

스크립트, 상태 검사, Compose는 이 값을 사용해 성공과 실패를 판단합니다.

## 10. 서버가 사용하는 운영체제 자원

### 10.1 파일과 디렉터리

서버는 설정, 인증서, 정적 파일, 로그, 데이터 파일을 읽고 씁니다. 경로가 맞아도 실행 사용자에게 필요한 권한이 없으면 실패합니다.

```sh
ls -l path/to/file
id
```

### 10.2 환경변수

환경변수는 부모 프로세스가 자식 프로세스에 전달하는 문자열 기반 설정입니다.

```sh
APP_PORT=18081 python3 server.py
```

환경변수는 편리하지만 비밀번호를 전달하면 프로세스 정보나 진단 출력에 노출될 수 있습니다. 뒤 장에서는 일반 설정, 비밀값, 영속 데이터를 분리합니다.

### 10.3 표준 스트림

프로세스는 기본적으로 세 스트림을 가집니다.

- 표준 입력, 파일 디스크립터 0
- 표준 출력, 파일 디스크립터 1
- 표준 오류, 파일 디스크립터 2

컨테이너 환경에서는 서버 로그를 일반 파일에만 남기기보다 표준 출력과 표준 오류로 보내는 방식이 관찰하기 쉽습니다. Docker가 이 출력을 수집해 `docker logs`로 보여줍니다.

## 12. 실패를 구분하는 기준

### DNS 실패

```text
Could not resolve host
```

이름에서 IP 주소를 얻지 못했습니다. 아직 대상 포트로 연결을 시도하지 못했습니다.

### 연결 거부

```text
Connection refused
```

대상 주소까지는 도달했지만 해당 포트에서 연결을 받는 프로세스가 없거나 운영체제가 즉시 거부했습니다.

### 타임아웃

일정 시간 동안 연결 또는 응답이 완료되지 않았습니다. 방화벽, 네트워크 단절, 과부하, 멈춘 프로세스 등 원인이 다양합니다.

### HTTP 404

HTTP 서버에 연결했고 유효한 응답을 받았습니다. 다만 요청한 경로에 대응하는 자원이 없다고 서버가 판단했습니다.

### HTTP 500

서버가 요청을 받았지만 처리 중 내부 오류가 발생했습니다. 서버 로그와 애플리케이션 로그를 확인해야 합니다.

### TLS 인증서 오류

TCP 연결 뒤 TLS 단계에서 인증서의 신뢰, 도메인, 유효기간 등을 검증하지 못했습니다. 아직 HTTP 상태 코드는 없습니다.

## 13. 실습

실습 위치:

```sh
python3 scripts/new-workspace.py exercises/01-request-and-process
cd exercises/01-request-and-process
```

### 실습 1: 시작 상태와 자신의 서버

```sh
./verify.sh workspace
```

시작 상태에서는 실패해야 합니다. `workspace/server.py`를 구현한 뒤 검증 스크립트를 읽고 다음을 찾습니다.

- 서버를 백그라운드로 시작하는 줄
- PID를 저장하는 줄
- 준비될 때까지 재시도하는 줄
- 200과 404를 각각 검사하는 줄
- 종료 시 서버 프로세스를 정리하는 줄

### 실습 2: 포트 변경

자신이 완성한 `workspace/server.py`는 `APP_PORT` 환경변수를 읽습니다.

```sh
APP_PORT=18082 python3 workspace/server.py
```

다른 터미널에서 다음 결과를 비교합니다.

```sh
curl -i http://127.0.0.1:18081/healthz
curl -i http://127.0.0.1:18082/healthz
```

실패한 명령이 HTTP 상태 코드를 받았는지, 연결 자체가 실패했는지 구분합니다.

### 실습 3: 수신 주소 변경

`APP_HOST=127.0.0.1`과 `APP_HOST=0.0.0.0`으로 각각 실행합니다. 같은 컴퓨터에서의 요청만으로는 차이가 드러나지 않을 수 있습니다. 중요한 것은 두 값의 의미를 설명하는 것입니다.

- `127.0.0.1`: 루프백 인터페이스에서만 수신
- `0.0.0.0`: 모든 IPv4 인터페이스에서 수신

Docker 컨테이너에서 호스트의 포트 게시를 통해 접근하려면 애플리케이션은 일반적으로 컨테이너 내부의 `0.0.0.0`에서 연결을 기다려야 합니다.

관찰 결과와 자신의 설명을 정리한 뒤에만 `reference/server.py`와 `./verify.sh reference`를 비교합니다.

## 14. 오류를 잘못 분류하기 쉬운 경우

### “포트가 열리면 애플리케이션은 정상입니다”

아닙니다. TCP 연결만 가능한 상태일 수 있습니다. 의미 있는 경로와 응답 내용을 검사해야 합니다.

### “localhost는 항상 내 노트북입니다”

`localhost`는 요청을 실행한 네트워크 네임스페이스 자체를 가리킵니다. 컨테이너 안의 `localhost`는 호스트가 아니라 그 컨테이너입니다.

### “404는 네트워크 오류입니다”

404를 받았다면 네트워크 연결과 HTTP 교환은 이미 성공했습니다. 경로 선택과 파일·라우팅을 확인해야 합니다.

### “SIGKILL로 끄는 것이 확실합니다”

프로세스를 즉시 없애는 데는 확실하지만 정상 종료와 상태 정리 기회를 제거합니다. 일반적인 종료는 SIGTERM부터 시작합니다.

## 15. 요청 경로 점검

- 서버는 주소와 포트에서 연결을 기다리는 프로세스입니다.
- TCP 연결과 HTTP 요청은 서로 다른 단계입니다.
- 404나 500은 연결 실패가 아니라 서버가 보낸 HTTP 응답입니다.
- `127.0.0.1`, `0.0.0.0`, 서비스 이름은 서로 다른 의미를 가집니다.
- 프로세스의 PID, 종료 코드, 표준 출력·오류, 시그널은 이후의 컨테이너 운영과 직접 연결됩니다.
- 장애 진단은 DNS → 연결 → 프로토콜 → 애플리케이션 순서로 확인 범위를 깊게 가져갑니다.
