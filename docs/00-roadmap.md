# Unix 시스템 관찰과 진단 가이드

Unix 계열 환경에서 발생한 문제를 해결하려면 명령을 많이 외우는 것보다 **어떤 객체를 보고 있는지, 어느 경계에서 상태가 달라졌는지, 어떤 관찰이 가설을 반증하는지**를 설명할 수 있어야 합니다. 이 가이드는 Unix 사용자 공간의 경로·파일 디스크립터·프로세스·권한·메모리·네트워크 엔드포인트·서비스 상태를 하나의 진단 모델로 연결합니다.

## 학습 목표

- Unix 사용자 공간의 증상을 상태, 소유권과 경계의 문제로 분류합니다.
- 읽기 전용 근거로 가설을 좁힌 뒤 최소 수정과 회귀 검사를 설계합니다.

## 종료 능력

가이드를 마친 독자는 다음을 할 수 있어야 합니다.

- 터미널, 셸, 프로세스와 커널의 역할을 구분합니다.
- 경로 문자열과 실제 파일 시스템 객체를 구분합니다.
- 파일 디스크립터, 열린 파일 상태와 자원 수명을 추적합니다.
- 실행 사용자, 작업 디렉터리, 환경과 권한을 하나의 실행 문맥으로 확인합니다.
- 프로세스의 부모·자식 관계, 상태, 프로세스 그룹과 시그널 흐름을 관찰합니다.
- 가상 메모리 크기, 실제 상주 메모리, 매핑과 페이지 폴트를 구분합니다.
- 이름, 주소, 포트, 수신 대기 소켓과 실제 연결을 분리해 확인합니다.
- 프로세스가 실행 중인 상태와 서비스가 준비된 상태를 구분합니다.
- 증상을 보존하고, 가설과 반증 조건을 적은 뒤, 읽기 전용 검사부터 수행합니다.
- 변경 하나를 적용한 뒤 정상·실패·회귀 조건을 모두 다시 검증합니다.

이 종료 능력은 운영체제 커널을 구현하는 능력이나 POSIX API를 C로 구현하는 능력과 다릅니다. 이 가이드의 중심은 **사용자 공간에서 관찰 가능한 근거를 이용해 실제 상태를 좁히는 것**입니다.

## 대상 독자

다음 정도를 전제로 합니다.

- 터미널에서 명령 한 줄을 실행할 수 있습니다.
- 파일과 디렉터리라는 개념을 알고 있습니다.
- 프로그램의 성공과 실패가 다를 수 있다는 사실을 알고 있습니다.
- Python 3를 실행할 수 있습니다. 누적 실습은 Python 표준 라이브러리만 사용합니다.

셸 스크립트 문법, C 시스템 프로그래밍, 네트워크 프로토콜 내부, 운영체제 구현을 먼저 배울 필요는 없습니다. 해당 영역을 더 깊게 공부할 때는 다음 가이드가 주 소유자입니다.

| 더 깊게 공부할 영역 | 주 소유 가이드 |
|---|---|
| 따옴표·확장·조건·반복·함수와 안전한 셸 프로그램 | `guide-shell-scripting` |
| `open`, `read`, `fork`, `exec`, `socket`의 C 구현 | `guide-c` |
| 스케줄링·동기화·페이지 교체·파일 시스템 정책 | `guide-operating-systems` |
| ISA·캐시·페이지 테이블 walk·TLB·메모리 순서 | `guide-computer-architecture` |
| Ethernet·IP·TCP·DNS·TLS·QUIC의 프로토콜 상태 | `guide-computer-networks` |
| Docker·Compose·공개 TLS·배포·백업과 운영 | `guide-web-infrastructure` |

이 가이드에서도 위 개념이 등장하지만, 현재 상태를 관찰하는 데 필요한 최소 모델까지만 설명합니다.

## 선행 개념

- 터미널에서 명령 한 줄을 실행하고 성공·실패 종료 상태를 구분할 수 있으면 시작할 수 있습니다.
- 셸 프로그래밍, C, 관리자 권한과 외부 네트워크는 선행 조건이 아닙니다.

| 사례 | 핵심 경계 | 관련 문서 |
|---|---|---|
| 01 명령 탐색 우선순위 | `PATH`, 실행 파일 정체성 | 01, 04 |
| 02 끊어진 심볼릭 링크 | 경로명과 대상 객체 | 02 |

| 04 삭제됐지만 열린 파일 | 경로명 수명과 열린 자원 수명 | 02, 03 |
| 05 잘못된 작업 디렉터리 | 실행 문맥과 상대 경로 | 01, 04, 08 |

권장 반복은 다음과 같습니다.

```text
증상 명령 실행
→ 예상과 실제 결과 기록
→ 상태를 바꾸지 않는 관찰 수행
→ 가설과 반증 조건 작성
→ 가장 작은 수정 적용
→ 정상 조건과 실패 조건 재검증
→ 다른 사례에 영향을 주지 않았는지 회귀 검사
```

완성 답안을 먼저 읽기보다 `skeleton/diagnoses.json`을 작업 공간으로 복사해 직접 조사한 뒤 `reference/diagnoses.json`과 비교합니다.

## 지원 환경

핵심 문서와 자동 검증은 다음 환경을 목표로 합니다.

- POSIX 계열 셸
- Python 3.12 이상
- macOS 또는 Linux
- 관리자 권한 불필요
- 외부 Python 패키지 불필요
- 외부 네트워크 접근 불필요

관찰 명령은 플랫폼에 따라 다를 수 있습니다.

| 목적 | Linux 예 | macOS 예 |
|---|---|---|
| 열린 파일·소켓 | `lsof`, `/proc` | `lsof` |
| 수신 대기 TCP | `ss -lnt` | `lsof -nP -iTCP -sTCP:LISTEN` |
| 메모리 매핑 | `/proc/PID/maps`, `pmap` | `vmmap PID` |
| 라우팅 | `ip route get` | `route -n get` |
| 서비스 상태 | `systemctl`, `journalctl` | `launchctl`, 통합 로그 |

이 명령이 설치되어 있지 않아도 핵심 실습은 Python 표준 라이브러리로 동작합니다. 문서는 플랫폼 도구의 출력을 외우는 대신 **무엇을 증명하려고 실행하는지**를 먼저 설명합니다.

## 저장소 준비와 전체 검증

Overlay를 저장소 루트에 압축 해제한 뒤 다음 순서로 실행합니다.

```sh
./prepare.sh
./verify.sh
```

`prepare.sh`는 source tree와 Git index를 변경하지 않고 최종 구조, 실행 권한과 fingerprint를 확인합니다. `verify.sh`는 격리 복제본에서 문서 링크, 실습의 기준 답안·미완성 시작점·잘못된 답안 거부 능력과 모든 재현 시나리오를 검사합니다.

## 완료 기준

다음 질문에 명령 이름만 나열하지 않고 상태 모델과 근거로 답할 수 있어야 합니다.

1. `command not found`와 “다른 실행 파일이 실행됨”은 어떻게 구분합니까?
2. 심볼릭 링크 경로가 존재하지만 대상이 없는 상태를 어떻게 확인합니까?
3. 출력이 없는 프로세스가 CPU를 소비하는지, 입력을 기다리는지, 이미 끝났는지 어떻게 구분합니까?
4. 파일을 삭제했는데 디스크 공간이 회수되지 않을 수 있는 이유는 무엇입니까?
5. 파일 모드가 읽기를 허용해도 접근이 실패할 수 있는 이유는 무엇입니까?
6. 가상 메모리 크기가 크다는 사실만으로 메모리 누수를 판정할 수 없는 이유는 무엇입니까?
7. 서버 프로세스가 존재하는데 연결이 거부되는 경우 무엇부터 확인합니까?
8. 프로세스가 실행 중이어도 서비스가 준비되지 않을 수 있는 이유는 무엇입니까?
9. `SIGTERM` 이후 자식 프로세스가 남는다면 어느 소유권 계약을 의심해야 합니까?
10. 복구 변경이 실제 원인을 해결했다는 사실을 어떻게 검증합니까?

## 범위 밖

- kernel, scheduler, filesystem 또는 network protocol 자체 구현은 이 가이드의 범위가 아닙니다.
- 실제 운영 service 변경, 외부 주소 scan, 관리자 권한 사용과 production 장애 조치는 실습하지 않습니다.

## 자동화의 한계

- 자동 검사는 임시 디렉터리, 자체 child process와 loopback listener만 만들고 모두 정리합니다.
- 실제 systemd·launchd, container runtime, 권한 정책과 production traffic의 상태를 대신 검증하지 않습니다.
- platform별 `ps`, `lsof`, `/proc`, `ss` 출력 차이는 한 도구의 결과가 아니라 독립 근거로 보완해야 합니다.
