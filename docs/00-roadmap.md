# Git 가이드 학습 지도

## 학습 목표

- Git 명령을 외우기보다 작업 트리, index, reference와 공유 범위의 상태 전이를 설명합니다.
- 변경 전에 결과와 복구 경로를 예측하고, 변경 뒤 근거로 검증합니다.

이 문서는 Git 가이드의 대상, 필수 경로, 실습 대응과 완료 조건을 먼저 고정합니다. Git의 모든 명령을 배우는 것이 목표가 아니라, 실제 프로젝트에서 다음 반복을 안전하게 수행하는 것이 목표입니다.

```text
상태 확인
→ 작은 변경
→ 목적별 검토
→ 커밋
→ 공유와 통합
→ 문제가 생기면 상태에 맞게 복구
```

## 대상 독자

다음 조건을 만족하면 시작할 수 있습니다.

- 터미널에서 현재 디렉터리를 확인하고 명령을 실행할 수 있습니다.
- 텍스트 파일을 편집할 수 있습니다.
- 프로그램 또는 문서를 작은 단위로 수정해 본 경험이 있습니다.

GitHub 계정과 원격 네트워크는 필수 선행조건이 아닙니다. 핵심 실습은 로컬 bare repository를 원격 역할로 사용합니다.

## 선행 개념

- 터미널의 현재 디렉터리, 명령 종료 상태와 텍스트 파일 편집을 이해하면 시작할 수 있습니다.
- GitHub 계정, 호스팅 서비스 경험이나 전역 Git 작성자 설정은 필요하지 않습니다.

## 지원 환경

필수 도구는 다음과 같습니다.

```text
Git 2.23 이상
Bash
POSIX 호환 셸
Python 3.12 이상
```

`git switch`를 사용하므로 Git 2.23 이상을 기준으로 합니다. macOS와 Linux의 일반적인 개발 환경을 대상으로 하며, Windows에서는 Git Bash 또는 동등한 POSIX 셸 환경이 필요합니다.

저장소의 최종 준비와 전체 검사는 루트에서 실행합니다.

```bash
./prepare.sh
./verify.sh
```

## 종료 능력

필수 경로를 마치면 다음을 설명하고 실행할 수 있어야 합니다.

1. 작업 트리, 인덱스, `HEAD`, 로컬 브랜치와 원격 추적 브랜치를 구분합니다.
2. `fetch`가 현재 브랜치와 작업 트리를 자동으로 바꾸지 않는 이유를 설명합니다.
3. 최신 원격 기본 브랜치에서 작업 브랜치를 만들고 최초 푸시로 upstream을 설정합니다.
4. 같은 파일에 섞인 변경을 목적별로 나누어 커밋합니다.
5. Pull Request의 base와 head를 확인하고 변경 이유와 검증 근거를 제공합니다.
6. merge와 rebase의 그래프 차이와 이력 재작성 여부를 설명합니다.
7. 충돌에서 두 변경 의도를 확인하고 해결하거나 `--abort`로 시작 전 상태로 돌아갑니다.
8. 아직 커밋하지 않은 변경, 로컬 커밋, 이미 공유한 커밋에 서로 다른 복구 방법을 선택합니다.
9. `reflog`로 잃어버린 참조를 찾고 즉시 복구 브랜치로 보존합니다.
10. `reset --hard`, `clean`, 강제 푸시 전에 손실 대상과 복구 지점을 확인합니다.

## 선택 학습 지도

[오픈소스에 작은 변경 기여하기](90-open-source-contribution.md)는 외부 저장소에 변경을 제안할 때만 필요합니다.

```text
필수 Git 과정 01–05
→ 저장소별 기여 규칙 조사
→ fork와 upstream 구성
→ 작은 변경 제안
→ 리뷰 반영과 정리
```

이 문서는 다음을 전제로 합니다.

- 필수 경로를 완료했습니다.
- 원본 저장소와 자신의 fork를 구분할 수 있습니다.
- 변경 전 기준 검증과 목적별 커밋을 수행할 수 있습니다.

## 실습 지도

### `sample`

```bash
./exercises/setup.sh sample
```

다음 내용을 재현합니다.

- 현재 저장소와 원격 기준 확인
- `origin/main`에서 작업 브랜치 생성
- 기능·테스트·문서 변경을 한 커밋으로 구성
- 무관한 오탈자를 별도 커밋으로 분리
- 개인 메모를 커밋에서 제외
- amend, reset, reflog와 stash 복구

### `team`

```bash
./exercises/setup.sh team
```

다음 내용을 재현합니다.

- 여러 복제가 같은 원격을 사용하는 상태
- fetch 전후 원격 추적 브랜치 차이
- 작업 브랜치 최초 푸시와 upstream
- 비선형 푸시 거부
- 같은 영역을 수정한 merge·rebase 충돌
- `--force-with-lease`의 보호 조건

실습 구조와 초기화 범위는 [로컬 Git 연습 환경](../exercises/README.md)에서 확인합니다.

## 권장 학습 반복

각 문서에서 다음 순서를 유지합니다.

```text
명령 실행 전 상태와 결과 예상
→ 읽기 전용 명령으로 현재 상태 확인
→ 한 가지 변경 실행
→ 작업 트리·인덱스·그래프 재확인
→ 프로젝트 검증
→ 실패하면 원인과 복구 조건 설명
```

예상 없이 명령을 실행하고 결과가 원하는 모습인지 눈으로만 확인하지 않습니다. Git은 같은 명령도 현재 작업 트리, 인덱스, 브랜치와 공유 범위에 따라 영향이 달라집니다.

## 완료 확인

다음 질문에 명령과 상태 그림으로 답할 수 있어야 합니다.

- `origin/main`은 원격 서버를 실시간으로 읽는 이름입니까?
- `git diff`가 비어 있는데 커밋될 변경이 남아 있을 수 있습니까?
- 작업 브랜치의 시작점과 upstream은 왜 서로 다를 수 있습니까?
- 게시하지 않은 커밋을 rebase하는 경우와 공유 브랜치를 다시 쓰는 경우의 위험은 어떻게 다릅니까?
- 충돌 표시의 두 쪽 가운데 하나만 선택하면 안 되는 경우는 무엇입니까?
- `restore`, `reset`, `revert` 가운데 어느 명령을 선택할지 무엇으로 판단합니까?
- reflog에서 찾은 커밋을 왜 즉시 브랜치로 보존해야 합니까?
- 강제 푸시 전에 어떤 원격 상태를 확인해야 합니까?

전체 자동 검사는 다음 한 명령으로 수행합니다.

```bash
./verify.sh
```

## 범위 밖

핵심 과정은 다음을 완전한 주제로 다루지 않습니다.

- Git object database와 plumbing 명령의 내부 구현
- 서버 관리자 관점의 Git 호스팅 구축
- 대규모 저장소 최적화와 partial clone 운영
- submodule, subtree와 monorepo 전략 전체
- `filter-repo`를 이용한 대규모 이력 정제
- GUI 클라이언트별 사용법
- 조직별 브랜치 보호와 CI 제품 설정

필요한 프로젝트에서 해당 기능을 만났을 때 별도 전문 문서와 저장소 정책을 확인합니다. 이 가이드의 핵심은 어떤 기능을 쓰더라도 먼저 현재 상태, 공유 범위와 복구 가능성을 확인하는 습관입니다.

## 자동화의 한계

- 자동 검사는 로컬 bare repository로 fetch, push, conflict와 recovery 상태를 재현합니다.
- 호스팅 서비스의 실제 Pull Request UI, branch protection, 권한 정책과 네트워크 장애는 자동화하지 않습니다.
- 검사가 통과해도 프로젝트별 CONTRIBUTING과 원격 정책을 사람이 확인해야 합니다.
