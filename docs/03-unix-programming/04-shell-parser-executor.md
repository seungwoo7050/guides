# 셸 파서와 실행기: 문법 처리와 실행 책임 분리

작은 셸을 구현할 때 어려운 점은 `fork`를 호출하는 방법 자체가 아닙니다. 입력 문자열을 어떤 규칙으로 해석하고, 그 결과를 어떤 중간 표현에 보존하며, 최종적으로 어떻게 실행 계획으로 바꿀지가 더 중요합니다.

입력을 읽는 즉시 `open`, `dup2`, `fork` 같은 시스템 호출을 실행하기 시작하면 뒤에서 문법 오류가 발견됐을 때 일부 명령만 이미 실행될 수 있습니다. 부분적으로 생성된 객체와 자식 프로세스를 한 함수에서 함께 정리해야 하는 문제도 생깁니다.

따라서 입력을 여러 단계를 거쳐 실행 가능한 구조로 변환합니다.

```text
입력 줄
→ lexer: token과 인용 정보 생성
→ parser: command·pipeline·redirection 구조 생성
→ expansion: 환경과 셸 상태를 문자열에 반영
→ validation: 실행에 필요한 불변식 확인
→ executor: pipe·fork·dup2·exec·wait 수행
→ 셸 관례 종료 상태
```

각 단계는 다음 단계가 원래 입력 문자열의 문법을 다시 추측하지 않아도 되도록 명확한 계약을 제공해야 합니다.

## 입력 계층과 파서 분리하기

대화형 입력, 파일 입력, 테스트가 직접 제공하는 문자열은 서로 다른 방식으로 명령 한 줄을 얻을 수 있습니다.

```c
char *read_command_line(const char *prompt, int interactive);
```

이 함수는 호출자에게 소유권이 넘어가는 한 줄의 문자열을 반환하고, 별도의 계약으로 EOF와 오류를 구분할 수 있습니다.

렉서는 입력이 터미널에서 왔는지 파일에서 왔는지 알 필요가 없습니다. 실행기 역시 프롬프트나 줄 편집기의 존재를 알아서는 안 됩니다.

이번 연습에서는 대화형 UI를 제외하고 명령 문자열 하나를 프로그램 인자로 전달합니다. 입력 인터페이스보다 렉서, 파서와 실행기 사이의 계약에 집중하기 위한 범위입니다.

## 렉서가 만드는 최소 토큰

기능을 확장한 셸에서는 다음과 같은 토큰을 사용할 수 있습니다.

```text
WORD
PIPE        |
REDIR_IN    <
REDIR_OUT   >
APPEND      >>
HEREDOC     <<
```

공백 자체는 토큰이 아니라 인용되지 않은 상태에서 `WORD`를 구분하는 역할을 합니다. 따옴표 안의 공백이나 `|`는 일반 문자로 `WORD`에 포함될 수 있습니다.

이번 연습에서 지원하는 토큰은 `WORD`와 `PIPE`뿐입니다.

`<`, `>`, `>>`, `<<`처럼 지원하지 않는 문법을 평범한 `WORD`로 조용히 처리하지 않고 지원 범위 밖의 문법으로 명시적으로 거부합니다.

## 렉서의 인용 상태

최소한 다음 상태를 구분할 수 있습니다.

```text
UNQUOTED
SINGLE_QUOTED
DOUBLE_QUOTED
ESCAPED
```

이번 연습에서는 다음 규칙을 사용합니다.

- 인용되지 않은 공백은 인자를 구분합니다.
- 작은따옴표 안의 문자는 그대로 `WORD`에 포함합니다.
- 큰따옴표 안에서는 공백과 `|`도 `WORD`의 일부입니다.
- 큰따옴표 안의 역슬래시는 다음 문자 하나를 리터럴로 처리합니다.
- 인용되지 않은 역슬래시도 다음 문자 하나를 리터럴로 처리합니다.
- 인용되지 않은 `|`는 `PIPE` 토큰이 됩니다.
- 서로 붙어 있는 인용 조각은 하나의 `WORD`로 결합합니다.
- `''`와 `""`는 길이가 0인 인자 하나를 만듭니다.

다음 입력을 생각해 봅니다.

```text
print one 'two three' "" ab"cd" escaped\ space
```

생성되는 `WORD`는 다음과 같습니다.

```text
print
one
two three
빈 문자열
abcd
escaped space
```

따옴표 자체는 최종 `argv`에 포함하지 않습니다.

입력이 끝났는데 따옴표가 닫히지 않았거나 마지막 역슬래시가 다음 문자를 기다리고 있다면 전체 입력을 문법 오류로 처리합니다.

## 빈 단어와 시작하지 않은 단어 구분하기

다음 두 입력은 의미가 다릅니다.

```text
공백만 있는 입력   → WORD 없음
""                → 길이 0인 WORD 하나
```

현재 단어 버퍼의 길이만 보고 토큰 생성 여부를 판단하면 빈 문자열 인자를 잃게 됩니다.

따라서 실제 문자 수와 별개로 하나의 단어가 시작되었는지를 나타내는 상태가 필요합니다.

```c
struct word_builder
{
    char *data;
    size_t length;
    size_t capacity;
    int started;
};
```

따옴표를 열었거나 이스케이프로 단어가 시작됐다면 결과 문자열의 길이가 0이어도 `WORD`는 존재합니다.

## 토큰과 문자열의 소유권

렉서가 문자열을 관리하는 방법은 크게 두 가지로 나눌 수 있습니다.

### 원본을 참조하는 방식

- 불필요한 복사가 적습니다.
- 원본 입력 문자열이 모든 토큰보다 오래 살아 있어야 합니다.
- 따옴표 제거와 이스케이프 처리 결과를 별도로 저장해야 할 수 있습니다.

### 토큰이 문자열을 소유하는 방식

- 각 토큰의 정리 책임이 명확합니다.
- 완성된 `WORD` 문자열의 소유권을 파서가 그대로 가져갈 수 있습니다.
- 중간 할당 실패에 대비한 정리 경로가 필요합니다.

이번 연습에서는 각 `WORD` 토큰이 완성된 문자열을 소유하고, 파서가 그 문자열의 소유권을 명령의 `argv`로 이전하는 구조를 사용합니다.

소유권을 이전한 뒤에는 원래 토큰의 포인터를 `NULL`로 바꿔 두 객체가 같은 메모리를 해제하지 않도록 합니다.

## 확장을 지원하려면 인용 정보가 더 필요합니다

이번 연습에서는 변수 확장을 지원하지 않습니다.

하지만 기능을 확장한 셸에서는 다음 입력의 인용 정보를 완성된 문자열 하나만으로 표현할 수 없습니다.

```text
pre"$HOME"'/$USER'
```

최종 문자열만 남기면 어느 부분에서 변수 확장을 허용하고 어느 부분에서는 금지해야 하는지 알 수 없기 때문입니다.

이 경우 하나의 `WORD`를 여러 구간으로 나누어 표현할 수 있습니다.

```c
enum quote_mode
{
    QUOTE_NONE,
    QUOTE_SINGLE,
    QUOTE_DOUBLE
};

struct word_part
{
    enum quote_mode mode;
    char *text;
    struct word_part *next;
};
```

앞의 입력은 다음과 같이 표현할 수 있습니다.

```text
NONE:   pre
DOUBLE: $HOME
SINGLE: /$USER
```

확장 단계에서는 각 구간의 인용 방식에 맞는 규칙을 적용한 뒤 최종 `argv` 문자열을 만듭니다.

현재처럼 기능 범위가 작은 단계에서는 필요하지 않은 구조를 미리 도입할 이유가 없습니다. 새로운 기능을 추가할 때 기존 표현으로 의미를 보존할 수 없게 되는 시점에 중간 표현을 확장합니다.

## 파서가 만드는 실행 전 구조

실행기가 원시 토큰을 다시 해석하도록 만들지 않습니다.

파서는 토큰을 실행하기 쉬운 구조로 바꿉니다.

```c
struct command
{
    char **argv;
    size_t argc;
};

struct pipeline
{
    struct command *commands;
    size_t count;
};
```

리다이렉션을 지원한다면 명령 인자와 별도의 구조에 저장합니다.

```c
struct redirection
{
    enum redirection_type type;
    char *target;
    struct redirection *next;
};
```

파서가 성공한 뒤에는 다음 불변식이 성립해야 합니다.

- 파이프라인 안에 빈 명령이 없습니다.
- 모든 명령의 `argc`는 0보다 큽니다.
- 각 `argv` 배열의 마지막 원소는 널 포인터입니다.
- 따옴표와 이스케이프 문자는 해석된 결과만 데이터에 남습니다.
- 리다이렉션 연산자와 대상은 `argv`에 포함되지 않습니다.
- 모든 리다이렉션에는 유효한 대상이 있습니다.
- 실행기가 토큰 문법을 다시 검사할 필요가 없습니다.

이번 연습에서는 최대 두 개의 명령만 정적 구조에 저장하지만 같은 불변식을 유지합니다.

## 문법 오류는 자식을 만들기 전에 처리하기

다음 입력은 `fork`를 호출하기 전에 거부합니다.

```text
빈 입력
| x
x |
x || y
x | | y
닫히지 않은 따옴표
입력 끝의 역슬래시
지원 범위를 넘는 두 개 이상의 파이프
```

문법 오류의 계약은 다음과 같이 정할 수 있습니다.

```text
종료 상태 2
stderr에 진단 출력
stdout에는 실행 결과 없음
자식 프로세스 생성 없음
파일 생성·작업 디렉터리 변경 등의 실행 부수효과 없음
부분적으로 만든 token·command 모두 해제
```

입력 앞부분을 먼저 실행한 뒤 나머지를 분석하다 문법 오류를 발견하면 하나의 명령줄이 가져야 할 문법 경계가 깨집니다.

따라서 전체 입력을 실행 가능한 구조로 검증한 뒤에만 실행기를 호출합니다.

## 리다이렉션은 `argv`에 포함되지 않습니다

기능을 확장한 셸에서 다음 입력을 생각해 봅니다.

```text
grep word < input.txt > output.txt
```

실제 프로그램에 전달하는 `argv`는 다음과 같습니다.

```text
["grep", "word", NULL]
```

다음 항목은 프로그램 인자가 아니라 셸이 처리해야 할 리다이렉션 정보입니다.

```text
< input.txt
> output.txt
```

따라서 파서는 이를 명령의 리다이렉션 목록으로 옮기고 `argv`에서는 제거합니다.

같은 종류의 리다이렉션이 여러 번 등장할 때 어떤 의미를 가질지도 문법 계약으로 정해야 합니다.

실제 셸과 비슷한 동작을 원한다면 리다이렉션을 왼쪽부터 차례대로 수행할 수 있습니다. 이 경우 앞의 파일도 실제로 열리므로 파일 생성이나 오류 같은 부수효과가 발생하고, 마지막으로 성공한 리다이렉션이 최종 FD 연결을 결정합니다.

반대로 같은 종류에서는 마지막 항목만 저장한다는 축소 규칙을 사용한다면 앞선 리다이렉션에서 발생했어야 할 부수효과가 사라진다는 차이를 문서에 명시해야 합니다.

## 실행기는 검증된 구조만 받습니다

명령 하나를 실행하는 기본 흐름은 다음과 같습니다.

```text
fork
→ 자식에서 exec
→ 부모에서 wait
→ 종료 상태 변환
```

두 명령으로 이루어진 파이프라인은 다음과 같습니다.

```text
pipe 생성
→ 왼쪽 자식 생성
→ 오른쪽 자식 생성
→ 부모의 pipe FD 닫기
→ 두 자식 wait
→ 오른쪽 명령의 상태 반환
```

실행기는 따옴표가 어떻게 해석됐는지 알 필요가 없습니다.

마찬가지로 파서는 파일 디스크립터를 어떤 순서로 `dup2`하고 닫아야 하는지 알 필요가 없습니다.

이 책임 분리가 각 계층을 독립적으로 테스트할 수 있는 경계를 만듭니다.

## 파이프라인과 리다이렉션의 적용 순서

기능을 확장한 셸에서는 각 명령의 실행을 다음 순서로 구성할 수 있습니다.

1. 필요한 파이프를 만듭니다.
2. `fork`합니다.
3. 자식에서 파이프라인의 표준 입력·출력을 연결합니다.
4. 명시적인 리다이렉션을 문법에 정의된 순서대로 적용합니다.
5. 사용하지 않는 모든 FD를 닫습니다.
6. 내장 명령을 실행하거나 `exec`를 호출합니다.
7. 부모가 더 이상 사용하지 않는 FD를 닫습니다.
8. 생성한 모든 자식을 회수합니다.

명시적인 출력 리다이렉션을 파이프라인 연결보다 나중에 적용하면 마지막 `dup2`가 최종 표준 출력을 결정합니다.

```text
producer > out.txt | consumer
```

이 규칙에서는 `producer`의 표준 출력이 `out.txt`로 연결되므로 파이프라인의 쓰기 끝에는 데이터가 들어가지 않을 수 있습니다.

어떤 연결이 우선하는지는 실행기가 임의로 결정할 문제가 아닙니다. 셸 문법이 정의한 의미를 실행기가 그대로 구현해야 합니다.

## 문법 오류와 실행 오류 구분하기

### 문법 오류

문법 오류는 입력만으로 판단할 수 있습니다.

- `fork` 전에 발견합니다.
- 실행에 따른 부수효과가 없어야 합니다.
- 상태 2처럼 별도의 결과로 표현할 수 있습니다.

### 실행 오류

실행 오류는 문법적으로 유효한 명령을 실제로 실행하는 과정에서 발생합니다.

대표적으로 다음이 있습니다.

```text
pipe 실패
fork 실패
dup2 실패
open 실패
exec 실패
waitpid 실패
```

이 시점에는 이미 일부 자식이 실행되고 있을 수 있습니다.

따라서 문법 오류와 달리 실패했으므로 아무 일도 일어나지 않았다는 보장을 할 수 없습니다. 부모는 이미 생성한 자식과 FD를 가능한 범위에서 정리해야 합니다.

명령을 찾을 수 없는 상황도 렉서나 파서의 오류가 아닙니다. 문법적으로는 올바른 명령이며 `exec` 단계에서 실패한 것입니다.

## 종료 상태 계약

이번 연습에서는 다음과 같은 종료 상태를 사용합니다.

```text
0~255   마지막 명령의 종료 상태
2       렉서·파서 또는 사용법 오류
126     명령을 찾았지만 실행할 수 없음
127     명령을 찾지 못함
128+N   시그널 N으로 종료
```

`execvp`가 실패하면 다른 함수를 호출하기 전에 `errno`를 저장합니다.

`ENOENT`는 127로, 그 밖의 대표적인 실행 실패는 126으로 변환합니다.

실제 셸은 `ENOTDIR`, 권한 문제, 디렉터리 실행 시도 등 더 많은 상황을 세분화할 수 있습니다. 이번 구현에서는 필요한 범위까지만 구분합니다.

파이프라인의 공개 종료 상태는 마지막 명령의 상태를 사용합니다. 그렇더라도 왼쪽을 포함한 모든 자식 프로세스는 반드시 회수해야 합니다.

## 변수 확장

기능을 확장하면 `$NAME`, `$?` 같은 표현을 실제 문자열로 변환하는 단계가 필요합니다.

인용 방식에 따라 확장 규칙도 달라집니다.

```text
작은따옴표
  변수 확장하지 않음

큰따옴표
  변수 확장 허용
  일반적인 필드 분할은 제한

인용되지 않은 상태
  변수 확장 뒤 필드 분할이나 glob 규칙이 추가될 수 있음
```

확장 결과가 빈 문자열일 때 하나의 `argv` 항목으로 남을지 완전히 사라질지도 인용 상태에 따라 달라질 수 있습니다.

환경 변수는 내부 맵이나 `KEY=VALUE` 목록으로 관리한 뒤 외부 명령을 실행하기 직전에 널 포인터로 끝나는 `char **envp` 형태로 만들 수 있습니다.

POSIX 셸의 전체 문법에는 다음과 같은 훨씬 넓은 처리 범위가 있습니다.

```text
parameter expansion
command substitution
field splitting
pathname expansion
```

축소된 셸을 구현한다면 지원하지 않는 문법을 실제 셸처럼 처리하는 척하지 말고 명시적으로 거부하거나 제한해야 합니다.

## 내장 명령은 부모 프로세스의 상태를 바꿀 수 있습니다

`cd`, 환경 변수 변경, 셸 종료 요청 같은 내장 명령은 현재 셸 프로세스 자체의 상태를 변경합니다.

이러한 명령을 항상 자식에서 실행하면 변경 사항이 부모 셸에 남지 않습니다.

따라서 일반적으로 다음과 같은 구분이 필요합니다.

```text
단일 명령이며
부모 상태를 변경하는 내장 명령
→ 부모에서 실행

파이프라인 안의 내장 명령
→ 자식에서 실행 가능
→ 상태 변경은 부모에 반영되지 않음
```

부모에서 내장 명령을 실행하면서 리다이렉션도 지원한다면 원래 표준 입출력을 임시로 보존해야 합니다.

```text
원래 FD를 dup
→ 리다이렉션 적용
→ 내장 명령 실행
→ 원래 FD 복구
→ 임시 FD close
```

정상 경로뿐 아니라 중간 실패 경로에서도 반드시 원래 상태로 복구해야 합니다.

이번 연습에서는 외부 명령만 실행해 이 복잡도를 의도적으로 제외합니다.

## heredoc은 별도의 수명 관리가 필요합니다

heredoc은 지정한 구분자가 나타날 때까지 여러 줄을 읽어 명령의 표준 입력으로 제공합니다.

이를 지원하려면 별도의 설계가 필요합니다.

- 본문을 파싱 중에 읽을 것인가, 실행 직전에 읽을 것인가?
- 구분자의 인용 여부가 확장 규칙에 어떤 영향을 주는가?
- 본문을 메모리, 파이프, 임시 파일 중 어디에 저장할 것인가?
- 입력이 매우 클 때 쓰는 쪽이 먼저 막히지는 않는가?
- `SIGINT`로 취소하면 이미 읽은 본문과 임시 자원을 어떻게 정리할 것인가?
- heredoc이 여러 개라면 어떤 순서로 입력받을 것인가?

단순한 구현에서는 실행 전에 heredoc 본문을 임시 파일에 저장하고 읽기 FD를 명령의 표준 입력에 연결할 수 있습니다.

파이프를 사용한다면 읽는 자식이 시작되기 전에 큰 본문을 모두 쓰려고 할 경우 파이프가 가득 차 쓰는 쪽이 멈출 수 있습니다. 따라서 저장 방법뿐 아니라 실행 순서까지 함께 고려해야 합니다.

## 대화형 입력과 Readline

대화형 UI는 파서와 분리된 입력 어댑터로 둡니다.

```text
Readline 또는 단순 표준 입력 리더
→ 소유권을 가진 문자열 또는 EOF·오류
→ 동일한 렉서·파서 API
```

부모 셸은 프롬프트에서 입력을 기다리는 동안 `SIGINT`를 받아 현재 입력 줄만 취소하고 계속 실행할 수 있습니다.

반면 실행 중인 자식은 `exec` 전에 `SIGINT`의 기본 동작을 복원해 Ctrl-C로 종료되게 할 수 있습니다.

Readline 콜백, 히스토리와 구체적인 시그널 정책은 [Readline 부록](../90-appendix/02-readline-integration.md)에서 다룹니다.

## 메모리 소유권 명확히 하기

입력 하나를 처리하는 동안 여러 단계에서 메모리가 할당될 수 있습니다.

```text
입력 줄
→ token 배열과 WORD 문자열
→ 인용 구간
→ expansion 결과
→ argv 배열
→ command / pipeline
```

각 단계에서는 이전 단계의 데이터를 어떻게 다룰지 명확히 정합니다.

```text
빌려서 참조
복제해서 새로 소유
소유권 이전
```

각 상위 객체가 자신이 소유한 하위 객체를 한 번에 정리할 수 있도록 정리 함수를 제공하면 부분 실패 경로가 단순해집니다.

```c
void token_list_destroy(struct token_list *tokens);
void pipeline_destroy(struct pipeline *pipeline);
```

파서가 토큰 문자열의 소유권을 명령으로 이전했다면 토큰 쪽 포인터는 `NULL`로 바꿉니다.

그러면 두 정리 함수가 같은 메모리를 중복해서 해제하지 않습니다.

## 동적 빌더와 오버플로

`WORD` 문자열과 `argv` 배열은 입력 크기에 따라 동적으로 확장해야 합니다.

기본 확장 순서는 다음과 같습니다.

```text
필요 길이 계산 전 오버플로 검사
→ 새 capacity 계산
→ realloc 결과를 임시 포인터에 저장
→ 성공 확인
→ 실제 포인터와 capacity 교체
```

새 인자 하나를 추가할 때 `argv`에는 마지막 널 포인터까지 필요하므로 필요한 슬롯 수는 다음과 같이 계산할 수 있습니다.

```text
argc + 2
```

```text
기존 인자
+ 새 인자 하나
+ 마지막 NULL
```

이 덧셈을 수행하기 전에 `argc <= SIZE_MAX - 2`인지 확인해야 합니다. 배열의 바이트 크기를 계산할 때는 슬롯 수가 `SIZE_MAX / sizeof *argv`를 넘지 않는지도 검사해야 합니다.

입력이 현실적으로 작을 것이라고 가정해 오버플로 검사를 생략하면 파서가 허용하는 공개 입력 범위 일부에서 잘못된 크기로 메모리를 할당할 수 있습니다.

## 파이프라인 생성 도중 실패한 경우

N단 파이프라인을 만드는 중 k번째 `fork`가 실패할 수 있습니다.

그 시점에는 이미 앞쪽 자식이 실행되고 있습니다.

따라서 부모는 다음과 같은 정리 절차를 수행해야 합니다.

- 부모가 소유한 모든 파이프 FD를 닫습니다.
- 이미 생성한 자식에 필요한 종료 정책을 적용합니다.
- 실제로 생성된 자식만 `waitpid`로 회수합니다.
- PID 배열과 임시 실행 계획을 해제합니다.
- 부모의 표준 FD를 변경했다면 원래 상태로 복구합니다.

`fork`가 실패했다고 해서 시스템 전체를 아무 일도 일어나지 않았던 상태로 되돌릴 수는 없습니다.

실패 계약에서는 되돌릴 수 없는 외부 효과와 반드시 정리할 수 있는 자원을 구분해야 합니다.

## 기능을 단계적으로 확장하기

처음부터 완전한 셸을 구현하려 하지 않습니다.

다음과 같이 기능을 단계별로 추가할 수 있습니다.

1. `WORD`만 사용하는 단일 외부 명령
2. 렉서의 토큰 출력
3. 작은따옴표·큰따옴표·이스케이프
4. 빈 인자와 붙어 있는 인용 조각
5. 두 명령 파이프라인
6. N단 파이프라인
7. `<`, `>`, `>>` 리다이렉션
8. 변수 확장
9. 부모 상태를 변경하는 내장 명령
10. heredoc
11. 대화형 입력과 시그널
12. 프로세스 그룹과 작업 제어

각 단계는 이전 단계의 테스트와 계약을 유지하면서 확장합니다.

새로운 기능의 의미를 기존 중간 표현으로 보존할 수 없다면 억지로 필드를 덧붙이기보다 표현 구조를 먼저 다시 설계하는 편이 낫습니다.

## 테스트도 계층별로 나누기

### 렉서·파서 테스트

실제 프로세스를 만들지 않고 토큰과 파싱 결과만 검사합니다.

- 인용 제거와 단어 경계
- 빈 문자열 인자
- 붙어 있는 인용 조각
- 닫히지 않은 따옴표 거부
- 입력 끝의 이스케이프 거부
- 빈 파이프라인 구간 거부
- 지원 범위를 넘는 파이프 개수 거부
- 오류 시 부분 할당 누수 없음

### 실행기 테스트

이미 검증된 명령이나 파이프라인 구조를 직접 실행합니다.

- 정확한 `argv` 전달
- 대용량 파이프라인 데이터 처리
- 126·127 종료 상태
- 시그널 종료 상태 변환
- 파이프라인의 마지막 명령 상태 선택
- 모든 자식 회수
- 모든 불필요한 FD 정리

### 통합 테스트

입력 문자열부터 실제 `stdout`, `stderr`와 종료 상태까지 전체 경로를 확인합니다.

호스트 셸의 결과와 비교할 때는 현재 구현과 호스트 셸의 문법 및 인용 규칙이 실제로 같은 경우에만 비교해야 합니다.

문법 오류에서 실행 부수효과가 없다는 사실을 검증하려면 실행되었을 때 특정 파일을 만드는 보조 프로그램을 준비할 수 있습니다.

잘못된 입력을 전달했을 때 그 파일이 생성되지 않는다면 파서 오류가 실행기에 도달하지 않았음을 확인할 수 있습니다.

## 실습

[command-runner](../../exercises/03-unix-programming/04-command-runner/README.md)에서는 명령 문자열 하나를 입력받아 다음 범위만 구현합니다.

```text
WORD
작은따옴표·큰따옴표
이스케이프
빈 인자
붙어 있는 인용 조각
인용되지 않은 파이프 최대 하나
외부 명령 실행
```

다음 항목을 검증합니다.

- 보조 프로그램이 실제로 받은 `argc`
- 각 `argv` 문자열과 빈 문자열 인자
- 닫히지 않은 따옴표 거부
- 입력 끝의 이스케이프 거부
- 빈 명령 거부
- 두 개 이상의 파이프 거부
- 문법 오류가 자식 프로세스의 부수효과를 만들지 않음
- 존재하지 않는 명령의 상태 127
- 실행할 수 없는 명령의 상태 126
- 시그널 종료를 셸 관례 상태로 변환
- 파이프라인의 마지막 명령 상태 선택
- 4 MiB 파이프라인과 제한 시간
- 반복 실행 사이의 상태 독립성

다음 기능은 이번 연습의 범위에 포함하지 않습니다.

```text
대화형 prompt
redirection
환경 변수 확장
builtin
heredoc
job control
```

또한 축소된 문법에서는 인용되지 않은 `<`, `>`, `;`, `&`를 명시적으로 거부합니다.

이 문자를 따옴표 안에 넣거나 이스케이프한 경우에만 일반 문자로 `argv`에 전달합니다.

지원하지 않는 셸 문법을 마치 구현된 것처럼 받아들이지 않는 것도 파서 계약의 일부입니다.

이 실습의 핵심은 문자열을 적당히 나눈 뒤 곧바로 `fork`하는 것이 아닙니다.

원시 입력을 문법적으로 검증된 실행 구조로 바꾸고, 그 구조가 완성된 뒤에만 프로세스 생성과 파일 디스크립터 조작을 시작하는 것이 목표입니다. 이를 통해 문법 오류와 실행 오류, 메모리 소유권과 프로세스 수명을 서로 다른 계층에서 관리할 수 있습니다.

구현과 검증을 마친 뒤에는 [`process-group-forwarding`](../../examples/process-group-forwarding/README.md)에서 고정된 `argv` 하나를 프로세스 그룹으로 실행하고 부모가 받은 종료 시그널을 그룹 전체에 전달하는 다음 경계를 관찰할 수 있습니다. 이 예제에는 파서, 리다이렉션, 파이프라인 구현이 없으므로 `command-runner`의 답안을 대신하지 않습니다.
