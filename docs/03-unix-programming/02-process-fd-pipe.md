# 프로세스·파일 디스크립터·파이프: 복제와 자원 수명

Unix에서 다른 프로그램을 실행하는 과정은 새 프로세스를 처음부터 만드는 것보다, **현재 프로세스를 복제한 뒤 자식 프로세스의 실행 이미지를 다른 프로그램으로 교체하는 과정**으로 이해하는 편이 정확합니다. 그 사이에 파일 디스크립터의 연결을 바꾸면 입력·출력 리다이렉션과 파이프라인을 구성할 수 있습니다.

어려운 점은 `fork`, `dup2`, `exec` 각각의 사용법이 아닙니다. `fork` 이후 어느 프로세스가 어떤 파일 디스크립터를 가지고 있는지, 어떤 디스크립터들이 같은 커널 상태를 공유하는지, 그리고 중간에 실패했을 때 이미 생성한 자식과 파이프를 누가 정리할지를 끝까지 추적하는 것이 핵심입니다.

## 프로그램과 프로세스

실행 파일은 디스크에 저장된 프로그램이고, 프로세스는 그 프로그램을 실제로 실행하는 인스턴스입니다.

프로세스는 대략 다음과 같은 상태를 가집니다.

* 코드, 전역 데이터, 힙과 스택으로 구성된 주소 공간
* 레지스터와 실행 문맥
* 파일 디스크립터 테이블
* PID와 부모 PID
* 현재 작업 디렉터리와 환경
* 사용자·그룹 정보
* 시그널 관련 상태

같은 실행 파일을 여러 번 실행하더라도 각각 별도의 PID와 주소 공간을 가진 프로세스가 만들어집니다.

`exec` 계열 함수는 이러한 프로세스 자체를 새로 만드는 것이 아니라 현재 프로세스의 실행 이미지(process image)를 새로운 프로그램으로 교체합니다.

## `fork`: 한 번 호출해 두 실행 흐름 만들기

```c
pid_t pid = fork();

if (pid < 0)
{
    /* 실패: 기존 프로세스만 존재 */
}
else if (pid == 0)
{
    /* 자식 */
}
else
{
    /* 부모, pid는 자식의 PID */
}
```

`fork`가 성공하면 부모와 자식은 모두 `fork` 다음 문장부터 실행을 이어갑니다. 반환값을 통해 어느 실행 흐름인지 구분합니다.

일반 메모리는 논리적으로 복제됩니다. 따라서 `fork` 이후 한쪽에서 변수를 변경해도 다른 프로세스의 변수에는 반영되지 않습니다.

현대 운영체제가 copy-on-write를 사용해 실제 메모리 복사를 늦추더라도 프로그래머가 의존해야 하는 모델은 서로 독립된 주소 공간입니다.

파일 디스크립터는 다르게 동작합니다. 부모와 자식의 파일 디스크립터 테이블은 각각 존재하지만, 대응하는 항목들이 같은 열린 파일 설명(open file description)을 가리킬 수 있습니다.

이 공유 관계는 파일 오프셋, 파일 상태 플래그와 파이프 EOF에 직접 영향을 줍니다.

## FD 번호와 열린 파일 설명은 다릅니다

```text
부모의 fd 3 ─┐
              ├─ 열린 파일 설명
자식의 fd 3 ─┘    ├─ 현재 파일 오프셋
                   ├─ 파일 상태 플래그
                   └─ 실제 파일
```

파일 디스크립터는 각 프로세스의 파일 디스크립터 테이블에 있는 정수 인덱스입니다.

반면 열린 파일 설명은 커널이 관리하는 별도의 객체입니다. `fork`, `dup`, `dup2`로 만들어진 여러 파일 디스크립터가 하나의 열린 파일 설명을 공유할 수 있습니다.

```c
int fd = open("out.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
int copy = dup(fd);

write(fd, "A", 1);
write(copy, "B", 1); /* 같은 파일 오프셋을 공유하므로 보통 AB */
```

여기서 중요한 것은 두 FD의 정수 값이 같은지가 아니라 **어떤 열린 파일 설명을 가리키는가**입니다.

## `exec`: 현재 실행 이미지를 교체하기

```c
char *arguments[] = {"printf", "%s\n", "child", NULL};
execvp(arguments[0], arguments);
```

`exec`가 성공하면 현재 프로세스의 실행 이미지가 새 프로그램으로 교체됩니다. 따라서 성공한 `exec` 호출은 원래 코드로 돌아오지 않습니다.

반환했다면 실패한 것입니다.

```c
execvp(arguments[0], arguments);
{
    int error_number = errno;

    dprintf(
        STDERR_FILENO,
        "%s: %s\n",
        arguments[0],
        strerror(error_number)
    );

    _exit(error_number == ENOENT ? 127 : 126);
}
```

이 실패 경로에서는 다음 사항이 중요합니다.

* `exec` 실패 직후의 `errno`를 다른 함수 호출 전에 저장합니다.
* 자식 프로세스의 실패 경로는 `_exit`로 종료합니다.
* `argv` 배열의 마지막 원소는 널 포인터여야 합니다.

`exit`는 `fork` 전에 부모가 가지고 있던 stdio 버퍼를 다시 flush하거나, 복제된 `atexit` 처리기를 실행해 의도하지 않은 중복 효과를 만들 수 있습니다. 따라서 `exec`에 실패한 자식은 일반적으로 `_exit`를 사용합니다.

다중 스레드 프로세스에서 `fork` 직후 `exec`까지의 구간에는 호출 가능한 함수에 추가 제약이 있습니다. 이 장의 단순 실행기는 그보다 좁은 단일 스레드 실행 모델을 전제로 합니다.

파일 디스크립터는 별도의 close-on-exec 설정이 없다면 `exec` 이후에도 유지될 수 있습니다. 이 특성 덕분에 자식에서 먼저 `dup2`로 표준 입력과 출력을 바꾼 뒤 외부 프로그램을 실행할 수 있습니다.

## `execvp`, `execve`와 환경

`execvp`는 명령 이름에 `/`가 없으면 현재 환경의 `PATH`를 이용해 실행 파일을 찾고, 현재 프로세스의 환경을 새 프로그램에 전달합니다.

환경을 직접 지정하려면 `execve`를 사용할 수 있습니다.

```c
execve(path, arguments, environment);
```

`execve`는 `PATH` 검색을 자동으로 수행하지 않습니다.

환경은 다음과 같은 `KEY=VALUE` 문자열을 가리키는 널 종료 포인터 배열입니다.

```text
PATH=/usr/bin:/bin
HOME=/home/user
LANG=ko_KR.UTF-8
...
NULL
```

권한이 높은 프로그램에서는 사용자로부터 받은 `PATH`와 환경을 그대로 신뢰해서는 안 됩니다.

반면 일반적인 대화형 셸이나 명령 실행기에서는 사용자의 환경을 그대로 따르는 것이 의도한 기능일 수 있습니다. 어떤 값을 전달할지는 프로그램의 역할과 신뢰 경계에 따라 결정해야 합니다.

## `waitpid`와 좀비 프로세스

자식이 종료하더라도 부모가 종료 상태를 회수하기 전까지 커널에는 해당 자식의 최소한의 정보가 남아 있을 수 있습니다. 이를 좀비 프로세스라고 합니다.

```c
int status;
pid_t result;

do
{
    result = waitpid(pid, &status, 0);
}
while (result < 0 && errno == EINTR);
```

`status`는 자식의 종료 코드를 그대로 담은 정수가 아닙니다. 상태 판별 매크로를 사용해 해석해야 합니다.

```c
if (WIFEXITED(status))
{
    int code = WEXITSTATUS(status);
}
else if (WIFSIGNALED(status))
{
    int signal_number = WTERMSIG(status);
}
```

CLI 실행기나 셸은 시그널로 종료된 프로세스를 다음과 같은 값으로 표현할 수 있습니다.

```text
128 + signal_number
```

이는 널리 사용되는 관례이며 `waitpid`가 직접 반환하는 원시 상태 값은 아닙니다.

부모가 생성한 모든 자식에 대해 **누가 `waitpid`를 호출할 것인지** 명확해야 합니다. 정상적으로 실행된 자식뿐 아니라 초기화나 `exec`에 실패한 자식도 회수 대상입니다.

## `dup2`와 리다이렉션

파일을 표준 출력으로 연결하려면 다음과 같이 구성할 수 있습니다.

```c
int fd = open("out.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);

if (fd < 0)
{
    /* 오류 */
}

if (dup2(fd, STDOUT_FILENO) < 0)
{
    /* 오류 */
}

close(fd);
```

`dup2(oldfd, newfd)`는 `newfd`가 `oldfd`와 같은 열린 파일 설명을 가리키도록 만듭니다.

`newfd`가 이미 열려 있었다면 기존 연결을 제거하고 새로운 연결로 교체합니다.

대표적인 셸 리다이렉션은 다음과 같이 대응할 수 있습니다.

```text
> 파일   O_WRONLY | O_CREAT | O_TRUNC
>> 파일  O_WRONLY | O_CREAT | O_APPEND
< 파일   O_RDONLY로 연 뒤 STDIN_FILENO에 dup2
```

외부 명령의 리다이렉션은 일반적으로 `fork` 이후 자식 프로세스에서 적용합니다.

부모에서 직접 `dup2`를 호출하면 부모 프로그램 자체의 표준 입력이나 출력이 바뀌기 때문입니다.

반대로 현재 셸 프로세스에서 실행해야 하는 builtin에 리다이렉션을 적용한다면 부모의 원래 FD를 `dup`으로 보존하고, 정상·오류 경로 모두에서 반드시 복구해야 합니다.

## `pipe`: 단방향 바이트 스트림

```c
int pipefd[2];

if (pipe(pipefd) < 0)
{
    /* 오류 */
}
```

파이프의 두 끝은 다음과 같은 역할을 합니다.

```text
pipefd[1]에 write
        ↓
   커널 파이프 버퍼
        ↓
pipefd[0]에서 read
```

파이프는 단방향 바이트 스트림입니다. 애플리케이션이 생각하는 메시지나 레코드 경계를 자체적으로 보존하지 않습니다.

파이프에서 특히 중요한 규칙은 EOF입니다.

> 읽기 쪽에서 EOF를 관찰하려면 해당 파이프의 쓰기 끝을 가리키는 모든 파일 디스크립터가 닫혀 있어야 합니다.

실제로 데이터를 쓰던 자식이 종료했더라도 부모나 다른 자식이 쓰기 끝의 복제본을 계속 가지고 있으면 읽는 쪽에서는 아직 writer가 존재한다고 판단할 수 있습니다.

그 결과 reader가 EOF를 기다리며 종료하지 않는 문제가 발생합니다.

## 두 명령을 파이프로 연결하기

두 명령을 연결하는 가장 기본적인 구조는 다음과 같습니다.

```text
왼쪽 명령의 stdout
        ↓
      파이프
        ↓
오른쪽 명령의 stdin
```

기본적인 실행 순서는 다음과 같습니다.

```text
파이프 생성

왼쪽 자식:
  pipe write end를 STDOUT_FILENO에 dup2
  원래 pipe read/write FD를 모두 close
  exec

오른쪽 자식:
  pipe read end를 STDIN_FILENO에 dup2
  원래 pipe read/write FD를 모두 close
  exec

부모:
  pipe read/write FD를 모두 close
  왼쪽 자식 wait
  오른쪽 자식 wait
```

각 프로세스가 어떤 파이프 끝을 유지해야 하는지 먼저 표로 정리하면 FD 누락을 줄일 수 있습니다.

| 프로세스   | read end            | write end            |
| ------ | ------------------- | -------------------- |
| 왼쪽 자식  | 닫음                  | stdout으로 복제한 뒤 원본 닫음 |
| 오른쪽 자식 | stdin으로 복제한 뒤 원본 닫음 | 닫음                   |
| 부모     | 닫음                  | 닫음                   |

`dup2`를 마친 뒤 원래 파이프 FD를 닫더라도 `STDIN_FILENO`나 `STDOUT_FILENO`에 만들어진 복제본은 그대로 유지됩니다.

따라서 **연결에 필요한 복제본만 남기고 원래 파이프 FD는 모두 닫는 것**이 기본 원칙입니다.

## 두 자식을 모두 시작한 뒤 기다립니다

다음 순서는 잘못된 구현입니다.

```text
왼쪽 자식 생성
왼쪽 자식이 끝날 때까지 wait
오른쪽 자식 생성
```

왼쪽 명령이 파이프 용량보다 많은 데이터를 출력하면 파이프 버퍼가 가득 찬 뒤 `write`가 막힐 수 있습니다.

하지만 데이터를 소비할 오른쪽 자식은 아직 생성되지 않았습니다.

```text
왼쪽 자식:
  파이프가 가득 차 write에서 대기

부모:
  왼쪽 자식 종료를 wait

오른쪽 자식:
  아직 존재하지 않음
```

이 상태에서는 서로 진행할 수 없어 교착 상태가 됩니다.

기본 순서는 다음과 같아야 합니다.

```text
파이프 생성
왼쪽 자식 생성
오른쪽 자식 생성
부모가 가진 파이프 끝 닫기
두 자식 wait
```

출력량이 작다면 모든 데이터가 파이프 버퍼에 들어가 잘못된 구현도 우연히 성공할 수 있습니다.

따라서 파이프라인 테스트에는 파이프 용량을 충분히 넘는 데이터를 포함해야 합니다.

## N단 파이프라인으로 확장하기

명령이 `N`개라면 일반적으로 인접한 명령을 연결하기 위해 `N - 1`개의 파이프가 필요합니다.

모든 파이프를 먼저 생성할 수도 있고, 이전 단계의 read end만 유지하면서 한 단계씩 생성할 수도 있습니다.

순차 생성 방식에서는 다음 상태를 관리할 수 있습니다.

```text
previous_read  이전 명령의 출력이 들어오는 FD
               첫 번째 명령에는 없음

current_pipe   현재 명령의 출력을 다음 명령으로 넘길 파이프
               마지막 명령에는 없음
```

각 자식은 다음 순서로 자신의 입출력을 구성합니다.

1. `previous_read`가 있다면 stdin으로 연결합니다.
2. 마지막 명령이 아니라면 현재 파이프의 write end를 stdout으로 연결합니다.
3. 명시적인 리다이렉션을 문법에서 정한 순서대로 적용합니다.
4. 상속받았지만 더 이상 사용하지 않는 모든 FD를 닫습니다.
5. `exec`를 호출합니다.

부모 역시 다음 단계에 필요하지 않은 FD는 즉시 닫는 편이 좋습니다.

이를 통해 불필요한 열린 파일 디스크립터 수를 줄이고, 파이프의 쓰기 끝이 예상보다 오래 살아 있어 EOF가 늦어지는 문제도 방지할 수 있습니다.

## 파이프와 리다이렉션의 적용 순서

다음 명령을 생각해 봅니다.

```text
producer > out.txt | consumer
```

문법에서 명시적 출력 리다이렉션이 파이프 연결보다 최종적으로 우선한다고 정했다면 자식에서는 다음 순서로 구성할 수 있습니다.

```text
파이프 write end를 stdout에 연결
→ out.txt를 stdout에 다시 연결
```

같은 `STDOUT_FILENO`에 여러 번 `dup2`하면 마지막 연결이 최종 목적지가 됩니다.

따라서 파이프와 리다이렉션의 의미는 단순히 `argv` 문자열을 순서대로 외부 프로그램에 전달하는 것으로 구현할 수 없습니다.

파서는 다음과 같은 실행 계획을 별도로 만들어 실행 단계에 전달해야 합니다.

```text
argv
입력 리다이렉션
출력 리다이렉션
append 여부
파이프 연결
...
```

## 자식의 메모리에 기록한 오류는 부모에게 전달되지 않습니다

`fork` 이후 부모와 자식의 일반 주소 공간은 서로 독립적입니다.

따라서 자식이 다음처럼 부모에게 전달할 목적으로 일반 변수에 값을 써도 동작하지 않습니다.

```text
자식:
  error = EXEC_FAILED

부모:
  error를 읽음  ← 자식이 변경한 값은 보이지 않음
```

단순한 명령 실행기에서는 보통 다음 채널을 사용합니다.

* 자식의 `stderr`: 사람이 읽는 오류 메시지
* 자식의 종료 상태: 성공·실패의 분류
* 필요한 경우 별도의 파이프: `exec` 이전에 발생한 상세 오류 전달

더 복잡한 오류 정보가 필요하다면 일반 메모리가 아니라 명시적인 IPC를 설계해야 합니다.

## 자식 생성 도중 실패한 경우

파이프라인을 만드는 중간에 실패할 수 있다는 점도 고려해야 합니다.

예를 들어 첫 번째 자식을 성공적으로 만든 뒤 두 번째 `fork`가 실패했다고 가정합니다.

이 시점에는 이미 첫 번째 자식이 실행 중일 수 있습니다.

따라서 함수가 실패했다는 사실이 다음을 의미하지는 않습니다.

```text
외부에 아무 변화도 일어나지 않았다
```

부모의 정리 순서는 대략 다음과 같이 설계할 수 있습니다.

```text
새로운 자식 생성 중단
→ 부모가 가진 모든 파이프 FD 닫기
→ 이미 생성한 자식에 필요한 종료 정책 적용
→ 생성된 모든 자식 wait
→ 임시 배열과 실행 계획 해제
→ 출력 매개변수를 변경하지 않고 오류 반환
```

부분적으로 생성된 FD를 정리해야 한다면 배열을 처음부터 `-1`로 초기화해 두는 것이 편리합니다.

```c
if (pipefd[0] >= 0)
{
    close(pipefd[0]);
    pipefd[0] = -1;
}
```

이렇게 하면 "현재 이 FD를 실제로 소유하고 있는가?"를 하나의 상태로 표현할 수 있습니다.

자식의 실패 경로는 부모의 일반 정리 코드로 돌아가서는 안 됩니다. 자식은 자신이 상속받은 불필요한 FD를 정리한 뒤 `_exit`로 짧게 종료하는 경로를 가져야 합니다.

## `waitpid` 실패와 여러 자식 회수하기

한 자식에 대한 `waitpid`가 실패했다고 해서 다른 자식을 그대로 버려서는 안 됩니다.

`EINTR`이라면 같은 자식에 대해 다시 시도합니다.

```c
do
{
    result = waitpid(pid, &status, 0);
}
while (result < 0 && errno == EINTR);
```

그 밖의 오류가 발생했더라도 이미 생성한 다른 자식 중 회수할 수 있는 자식은 계속 회수해야 합니다.

파이프라인의 외부 결과로 마지막 명령의 상태만 사용하더라도 왼쪽에 있는 모든 자식 역시 반드시 기다려야 합니다.

API 수준에서는 다음 두 종류의 결과를 분리할 수 있습니다.

```text
함수 반환값
    파이프라인을 생성하고 자식을 회수하는
    실행기 자체의 성공·실패

out_status
    마지막 명령이 반환한 shell-style 실행 상태
```

이렇게 하면 다음 두 상황을 구분할 수 있습니다.

```text
명령 자체가 정상적으로 실행된 뒤 상태 1로 종료
부모가 fork, pipe, waitpid 등에 실패
```

두 경우는 의미가 전혀 다르므로 하나의 반환값에 섞지 않는 편이 좋습니다.

## FD 누수와 멈춤 문제 진단하기

파이프라인이 끝나지 않는다면 먼저 파일 디스크립터 수명을 확인합니다.

1. 파이프의 쓰기 끝을 아직 가지고 있는 프로세스가 있습니까?
2. 부모와 모든 자식이 사용하지 않는 파이프 끝을 닫았습니까?
3. reader는 어떤 조건에서 입력이 끝났다고 판단합니까?
4. 부모가 자식을 기다리기 전에 직접 읽거나 써야 할 데이터가 있습니까?
5. writer가 파이프 용량 때문에 막혀 있는데 reader가 아직 시작되지 않은 것은 아닙니까?

FD 누수는 짧게 실행되고 곧바로 종료되는 프로그램에서는 잘 드러나지 않을 수 있습니다.

같은 부모 프로세스에서 파이프라인을 여러 번 실행하면서 열린 파일 디스크립터 수가 계속 증가하지 않는지 확인하는 테스트가 유용합니다.

플랫폼에 따라 다음과 같은 보조 수단을 사용할 수 있습니다.

```text
Linux   /proc/self/fd
macOS   fcntl 기반 검사, lsof 등의 외부 도구
```

이러한 검사는 플랫폼에 종속적이므로 핵심 동작 테스트와 분리해 조건부로 사용하는 편이 좋습니다.

## 큰 입력과 timeout으로 교착 상태 검출하기

연습에서는 대량의 데이터를 생성하는 프로그램과 그 데이터를 끝까지 소비하는 프로그램을 파이프로 연결합니다.

```text
emit-bytes 4194304 | expect-bytes 4194304
```

4 MiB 정도의 데이터는 일반적인 파이프 버퍼보다 충분히 크기 때문에 잘못된 실행 순서를 드러내는 데 사용할 수 있습니다.

이 테스트에서는 다음 항목을 함께 확인합니다.

* `wait` 전에 두 자식이 모두 생성되었습니다.
* 부모가 가지고 있던 파이프의 쓰기 끝을 닫았습니다.
* 읽기와 쓰기의 부분 성공을 반복해서 처리합니다.
* 전체 파이프라인이 제한된 시간 안에 종료됩니다.

timeout은 구현이 올바르다는 사실을 증명하는 장치가 아닙니다.

잘못된 구현이 영원히 멈춰 테스트 전체를 중단시키지 않도록 만드는 **실패 경계**입니다.

따라서 느린 실행 환경에서도 정상적인 처리가 충분히 끝날 수 있도록 여유 있는 제한 시간을 사용해야 합니다.

## 선택 관찰: 한 명령의 stdout redirection

파이프라인 답안을 보기 전에 [`fd-redirection`](../../examples/fd-redirection/README.md)에서 `open`으로 얻은 FD를 자식의 stdout에 연결하는 좁은 수명 경계를 관찰할 수 있습니다. 이 예제는 parser나 pipeline을 구현하지 않으며 truncate와 append의 open flag 차이, `dup2` 뒤 원본 FD 닫기, `exec` 실패 상태만 다룹니다.

## 실습

[command-pipeline](../../exercises/03-unix-programming/02-command-pipeline/README.md)에서 다음 항목을 구현하고 검증합니다.

* 입력 포인터와 `argv[0]` 검증
* 파이프 생성과 두 자식 프로세스 생성
* 자식의 stdin·stdout 연결
* 부모와 자식에서 사용하지 않는 모든 FD 닫기
* `exec` 실패를 126·127 상태로 변환
* `EINTR`를 고려한 `waitpid`
* 시그널 종료를 `128 + signal` 형태로 변환
* 마지막 명령의 상태만 `out_status`에 반영
* 생성 도중 실패한 경우 이미 만든 자식 회수
* 4 MiB 데이터를 이용한 순차 `wait` 교착 검출
* 반복 실행을 통한 FD 정리 검증

구현을 완료한 뒤에는 의도적으로 다음과 같은 결함을 넣어 테스트가 실제로 문제를 잡아내는지도 확인합니다.

```text
부모가 파이프의 쓰기 끝을 닫지 않음

또는

두 번째 자식을 만들기 전에
첫 번째 자식을 wait
```

두 경우 모두 정상적인 파이프라인이라면 발생해서는 안 되는 대기 상태를 만들 수 있습니다. timeout 기반 테스트가 이를 실패로 검출해야 합니다.

이 실습의 핵심은 `fork`와 `pipe`의 함수 사용법을 암기하는 데 있지 않습니다.

`fork`로 복제된 파일 디스크립터 가운데 각 프로세스가 실제로 필요한 것만 남기고, `dup2`와 `exec`로 입출력 관계를 구성하며, 정상 경로와 부분 실패 경로 모두에서 자식과 FD의 수명을 끝까지 관리하는 것이 목표입니다.
