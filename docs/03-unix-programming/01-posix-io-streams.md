# POSIX I/O와 레코드 리더: 부분 읽기·EOF·상태 관리

파일 디스크립터 기반 I/O에서는 한 번의 호출이 요청한 양을 모두 처리한다고 보장하지 않습니다. 커널은 실제로 처리한 바이트 수를 반환하지만, 애플리케이션은 한 줄, 한 프레임, 한 레코드와 같은 별도의 논리 단위를 다뤄야 할 수 있습니다. 시스템 호출의 경계와 애플리케이션의 데이터 경계가 일치하지 않으면 호출 사이에 상태를 보존해야 합니다.

이 장에서는 `read`와 `write`의 부분 성공, `EINTR`, EOF, 내부 버퍼, 반환 데이터의 소유권과 오류 이후의 상태를 하나의 레코드 리더 설계로 연결합니다.

## ISO C와 POSIX의 경계

ISO C 표준 라이브러리는 `FILE *`, `fopen`, `fread`, `fprintf` 같은 스트림 인터페이스를 제공합니다. 반면 파일 디스크립터와 다음 함수는 POSIX 인터페이스에 속합니다.

```c
#define _POSIX_C_SOURCE 200809L

#include <fcntl.h>
#include <sys/types.h>
#include <unistd.h>
```

```text
open, read, write, close
pipe, dup, fork, exec, poll ...
```

기능 테스트 매크로는 관련 시스템 헤더보다 먼저 정의하거나 빌드 옵션을 통해 번역 단위 전체에 적용합니다.

```sh
cc -D_POSIX_C_SOURCE=200809L ...
```

Windows의 네이티브 API는 같은 인터페이스와 계약을 제공하지 않습니다. 이 장의 코드는 POSIX.1-2008 계열 환경을 대상으로 합니다.

## 파일 디스크립터 모델

파일 디스크립터(FD)는 프로세스 안에서 사용하는 작은 정수입니다.

```text
0  표준 입력
1  표준 출력
2  표준 오류
```

FD는 파일 자체를 영구적으로 식별하는 값이 아닙니다. 프로세스의 파일 디스크립터 테이블에서 특정 항목을 가리키는 인덱스이며, 그 항목을 통해 파일, 파이프, 소켓, 터미널 같은 커널 객체에 접근합니다.

```c
int fd = open("input.txt", O_RDONLY);
```

`open`은 성공하면 0 이상의 파일 디스크립터를 반환하고, 실패하면 `-1`을 반환합니다.

기존의 `0`, `1`, `2`가 닫혀 있다면 새로 연 파일에 이 번호가 다시 할당될 수 있습니다. 정상적으로 연 파일의 FD가 항상 3 이상이라고 가정해서는 안 됩니다.

## `open`과 `close`의 소유권

```c
int fd = open(path, O_RDONLY);
if (fd < 0)
{
    /* 실패를 확인한 직후 errno 검사 */
}
```

파일을 새로 만들 수 있는 플래그를 사용한다면 모드 인자도 전달해야 합니다.

```c
int fd = open(
    path,
    O_WRONLY | O_CREAT | O_TRUNC,
    0644
);
```

`close(fd)`는 현재 프로세스의 파일 디스크립터 테이블에서 해당 항목을 닫습니다.

함수가 전달받은 FD까지 닫아야 하는지는 타입만으로 결정할 수 없습니다. 소유권 계약을 별도로 정해야 합니다.

```text
소유한 FD    함수가 정상·오류 경로 모두에서 닫을 책임을 가짐
빌린 FD      사용하는 동안만 접근하며 임의로 닫지 않음
이전한 FD    소유권 이전에 성공한 뒤 새 소유자가 닫을 책임을 가짐
```

닫힌 FD 번호는 즉시 다른 자원에 재사용될 수 있습니다. 따라서 `close`를 호출한 뒤 같은 번호를 무조건 다시 닫는 방식으로 복구해서는 안 됩니다. 그 번호가 이미 다른 자원에 재사용되었다면 엉뚱한 FD를 닫을 수 있습니다.

FD를 닫았다면 해당 FD의 소유 상태도 함께 종료해야 합니다.

## `read`의 세 가지 결과

```c
ssize_t count = read(fd, buffer, capacity);
```

| 결과 | 의미 |
|---|---|
| `count > 0` | `buffer[0..count)`에 실제로 읽은 바이트가 들어 있습니다. |
| `count == 0` | 양수 크기의 읽기에서 EOF를 확인했습니다. |
| `count == -1` | 오류가 발생했습니다. 반환 직후 `errno`를 확인합니다. |

요청한 `capacity`보다 적은 바이트가 반환되었다고 해서 오류인 것은 아닙니다. 파이프, 터미널, 소켓뿐 아니라 일반 파일에서도 짧은 읽기가 발생할 수 있음을 전제로 작성해야 합니다.

```c
ssize_t count = read(fd, buffer, sizeof buffer);
if (count > 0)
{
    consume(buffer, (size_t)count);
}
```

유효한 데이터의 길이는 항상 `read`의 반환값으로 판단합니다.

## `read`는 문자열을 만들지 않습니다

`read`는 읽은 데이터 뒤에 NUL 종료 문자를 자동으로 붙이지 않습니다.

```c
char buffer[1024];
ssize_t count = read(fd, buffer, sizeof buffer);
```

`count > 0`이더라도 `buffer`가 C 문자열이라는 보장은 없습니다.

문자열 함수에 전달해야 한다면 NUL 문자를 위한 공간을 한 바이트 남겨 두고 직접 종료해야 합니다.

```c
char buffer[1025];
ssize_t count = read(fd, buffer, 1024);

if (count > 0)
{
    buffer[count] = '\0';
}
```

입력 자체에 NUL 바이트가 포함될 수 있다면 `strlen`으로 데이터 길이를 판단해서는 안 됩니다. 바이트 배열과 실제 길이를 함께 전달해야 합니다.

## 부분 읽기와 바이트 스트림

양수 값을 반환한 짧은 읽기는 여러 상황에서 발생할 수 있습니다.

- 파이프나 터미널에 현재 일부 데이터만 준비되어 있습니다.
- 시그널이 발생하기 전에 일부 바이트가 이미 처리되었습니다.
- 장치나 파일 시스템이 요청보다 적은 양을 반환했습니다.
- 소켓의 상대가 데이터를 여러 번 나누어 전송했습니다.

요청한 크기보다 적게 읽었다는 이유만으로 EOF라고 판단하면 아직 남은 데이터를 일찍 잘라 버릴 수 있습니다.

EOF는 양수 크기로 호출한 `read`가 `0`을 반환했을 때 확인합니다.

바이트 스트림 자체에는 애플리케이션이 정의한 메시지 경계가 없습니다.

```text
쓰기 호출: "abc", "def"
읽기 결과: "ab", "cdef"가 될 수도 있음
```

따라서 한 번의 쓰기 호출과 한 번의 읽기 호출이 서로 대응한다고 가정해서는 안 됩니다.

## `write`와 부분 쓰기

`write`도 성공했더라도 요청한 전체 데이터를 한 번에 쓰지 않을 수 있습니다. 모든 데이터를 전달해야 한다면 쓰지 못한 부분을 반복해서 처리해야 합니다.

```c
#include <errno.h>
#include <limits.h>
#include <unistd.h>

int write_all(int fd, const void *data, size_t length)
{
    const unsigned char *cursor = data;

    while (length > 0)
    {
        size_t request = length;
        ssize_t count;

        if (request > (size_t)SSIZE_MAX)
        {
            request = (size_t)SSIZE_MAX;
        }

        count = write(fd, cursor, request);

        if (count > 0)
        {
            cursor += (size_t)count;
            length -= (size_t)count;
        }
        else if (count < 0 && errno == EINTR)
        {
            continue;
        }
        else
        {
            return -1;
        }
    }

    return 0;
}
```

한 번의 `write` 호출로 표현할 수 있는 크기를 넘지 않도록 매우 큰 데이터는 여러 조각으로 나누어 처리합니다.

남은 데이터가 있는데도 `write`가 진행되지 않는 예상 밖의 상황에서는 무한히 반복하지 않고 실패로 처리해야 합니다.

파이프나 소켓에서 반대쪽 읽기 끝이 사라지면 `SIGPIPE`가 전달되거나 `write`가 `EPIPE`로 실패할 수 있습니다. 시그널로 종료할지, 오류 반환값으로 처리할지는 프로그램 전체의 정책으로 정해야 합니다.

## `errno`와 `EINTR`

`errno`는 오류를 나타내는 반환값을 확인한 직후에만 의미 있게 해석합니다. 함수가 성공했다고 해서 이전의 `errno` 값이 자동으로 `0`이 되는 것은 아닙니다.

```c
ssize_t count;

do
{
    count = read(fd, buffer, capacity);
}
while (count < 0 && errno == EINTR);
```

시그널 때문에 데이터 전송이 시작되기 전에 시스템 호출이 중단되면 `EINTR`이 반환될 수 있습니다. 단순한 블로킹 리더라면 일반적으로 같은 작업을 다시 시도할 수 있습니다.

다만 종료 요청을 즉시 반영해야 하거나 마감 시각이 있는 작업이라면 같은 인자로 무조건 재시도해서는 안 됩니다. 시그널을 처리한 뒤 프로그램 상태와 남은 시간을 다시 계산해야 합니다.

## 읽기 조각과 레코드 경계

입력 데이터가 다음과 같다고 가정합니다.

```text
alpha\nbeta\ngamma
```

실제 `read` 결과는 다음처럼 나뉠 수 있습니다.

```text
[alp] [ha\nbeta\n] [gam] [ma]
```

하나의 레코드가 여러 번의 읽기에 걸쳐 들어올 수도 있고, 한 번의 읽기 안에 여러 레코드가 들어올 수도 있습니다.

따라서 `read` 한 번의 결과를 레코드 하나로 반환하는 구현으로는 레코드 기반 인터페이스의 계약을 지킬 수 없습니다.

## EOF와 레코드 구분자는 다릅니다

줄바꿈 문자를 레코드 구분자로 사용하고 반환 결과에서는 제거한다고 가정하면 다음 입력을 서로 구분해야 합니다.

```text
빈 스트림   → 즉시 EOF
"\n"        → 빈 레코드 하나, 이후 EOF
"\n\n"      → 빈 레코드 두 개, 이후 EOF
"last"      → "last" 한 개, 이후 EOF
"last\n"    → "last" 한 개, 가짜 빈 레코드 없이 EOF
```

EOF를 빈 문자열로 표현하면 실제 빈 레코드와 EOF를 구분할 수 없습니다.

따라서 레코드 내용과 별도로 호출 결과 상태를 반환해야 합니다.

```text
1   레코드를 하나 반환함
0   EOF이며 반환할 레코드가 남아 있지 않음
-1  잘못된 인자, I/O 오류 또는 메모리 오류
```

## 호출 사이의 상태

첫 번째 호출에서 `alpha`만 반환했더라도 같은 `read`에서 이미 가져온 `beta`의 일부를 버려서는 안 됩니다.

함수 내부의 자동 배열은 함수가 반환되면 수명이 끝나므로, 호출 사이에 데이터를 유지하려면 별도의 상태 객체가 필요합니다.

```c
struct record_reader
{
    int fd;
    char *pending;
    size_t length;
    size_t capacity;
    int eof;
    int failed;
    struct record_reader_allocator allocator;
};
```

이 객체는 다음 불변식을 유지합니다.

```text
length <= capacity
pending[0..length)는 아직 호출자에게 반환하지 않은 바이트
eof이면 더 이상 read를 호출하지 않음
failed이면 이후 next 호출도 -1
reader는 fd를 빌려 사용하며 destroy에서 닫지 않음
destroy 이후 다시 사용하려면 init으로 새 수명을 시작함
```

명시적인 리더 객체를 사용하면 여러 FD의 상태를 서로 독립적으로 유지할 수 있고, 읽기를 중간에 끝내더라도 내부 버퍼를 명확하게 정리할 수 있습니다.

## 내부 탐색 위치와 반복 비용

규모가 큰 구현에서는 버퍼 내부 위치를 더 세분화해 관리할 수 있습니다.

```text
0        begin        scan          end       capacity
| 소비됨 | 반환 후보 | 이미 검색함 | 미검색 데이터 | 빈 공간 |
```

다음 불변식을 유지합니다.

```text
begin <= scan <= end <= capacity
```

- `begin`: 다음 레코드 후보가 시작되는 위치입니다.
- `scan`: 이 위치 앞까지는 줄바꿈 문자가 없음을 이미 확인했습니다.
- `end`: 현재 저장된 실제 데이터의 끝입니다.
- `capacity`: 할당된 전체 버퍼 크기입니다.

매번 버퍼 처음부터 줄바꿈 문자를 다시 찾으면 긴 레코드를 처리할 때 같은 바이트를 반복해서 검사하게 됩니다.

간단한 연습에서는 `begin == 0`을 유지하고 레코드를 소비할 때마다 `memmove`로 남은 데이터를 앞으로 옮길 수 있습니다. 데이터 규모가 커지면 시작 위치와 탐색 위치를 따로 관리해 불필요한 반복을 줄일 수 있습니다.

## 버퍼 압축과 확장

버퍼 앞부분을 이미 소비했고 뒤쪽 공간이 부족하다면 남은 데이터를 앞으로 옮겨 공간을 확보할 수 있습니다.

```c
memmove(buffer, buffer + consumed, remaining);
```

원본과 목적지 범위가 겹칠 수 있으므로 `memcpy`가 아니라 `memmove`를 사용합니다.

압축한 뒤에도 공간이 부족하다면 버퍼 용량을 기하급수적으로 늘릴 수 있습니다.

```text
필요 길이 계산 전 덧셈 오버플로 검사
→ 새 capacity 계산
→ realloc 결과를 임시 포인터에 저장
→ 성공을 확인한 뒤 data와 capacity 교체
```

메모리 재할당에 실패하더라도 기존 포인터와 이미 읽어 둔 데이터는 그대로 유효해야 합니다.

따라서 `realloc`의 결과를 기존 포인터에 바로 대입해서는 안 됩니다.

## 반환 결과와 소유권

이 연습의 API에서는 레코드 하나를 반환할 때마다 새로운 NUL 종료 배열을 할당해 호출자에게 넘깁니다.

```c
int record_reader_next(
    struct record_reader *reader,
    char **out_record,
    size_t *out_length
);
```

출력 매개변수의 계약은 다음과 같습니다.

```text
반환 1   *out_record와 *out_length에 새 결과를 기록
반환 0   출력 매개변수를 변경하지 않음
반환 -1  출력 매개변수를 변경하지 않음
```

성공한 호출 뒤에는 호출자가 `free(*out_record)`로 반환된 메모리를 해제합니다.

끝의 NUL 문자는 사용 편의를 위해 추가한 한 바이트일 뿐이며, 실제 레코드 길이는 `*out_length`입니다. 입력에 NUL 바이트가 포함되어 있더라도 명시적인 길이와 `memcmp`를 사용하면 그대로 처리할 수 있습니다.

## 결과를 만든 뒤 내부 데이터를 소비하기

줄바꿈 문자의 위치를 찾았다고 해서 내부의 대기 데이터를 먼저 제거해서는 안 됩니다.

대기 데이터를 제거한 뒤 결과 배열 할당에 실패하면 아직 호출자에게 전달하지 않은 레코드까지 잃게 됩니다.

안전한 순서는 다음과 같습니다.

```text
레코드 경계 탐색
→ 결과 길이 오버플로 검사
→ 결과 배열 할당
→ 데이터 복사와 NUL 종료
→ 대기 데이터에서 해당 범위 소비
→ 출력 매개변수에 결과 확정
```

이 순서를 따르면 결과 생성에 실패하더라도 아직 반환하지 않은 내부 레코드는 보존할 수 있습니다.

다만 이미 `read`를 통해 커널에서 가져온 바이트까지 시스템 호출 이전 상태로 되돌릴 수 있다는 뜻은 아닙니다.

## 오류와 되돌리기의 한계

한 번의 `record_reader_next` 호출에서 여러 차례 `read`에 성공한 뒤 내부 버퍼를 확장하는 과정에서 메모리 할당이 실패할 수 있습니다.

이미 성공한 `read`는 일반 파일이라면 파일 오프셋을 전진시켰고, 파이프나 터미널이라면 커널에서 데이터를 소비했습니다. 이런 입력은 일반적으로 호출 전 상태로 되돌릴 수 없습니다.

따라서 다음과 같은 강한 보장을 API 계약으로 내세워서는 안 됩니다.

```text
실패하면 커널 스트림과 reader가 모두 호출 전 상태로 돌아감  ← 일반적으로 불가능
```

이 연습에서는 내부 버퍼 확장이나 I/O 오류가 발생하면 해당 리더를 영구 실패 상태로 전환합니다.

```text
내부 메모리 누수 없음
출력 매개변수 보존
다른 reader에는 영향 없음
이 reader의 이후 next 호출은 계속 -1
호출자가 빌려준 fd는 닫지 않음
```

오류가 발생한 뒤에도 같은 리더를 계속 사용할 수 있게 하려면 이미 읽은 데이터와 오류 원인을 함께 보존하는 더 복잡한 상태 머신이 필요합니다.

## 여러 리더와 FD 번호 재사용

FD마다 별도의 리더 객체를 두면 상태 경계가 명확해집니다.

```c
struct record_reader left;
struct record_reader right;

record_reader_init(&left, left_fd, NULL);
record_reader_init(&right, right_fd, NULL);
```

두 리더를 번갈아 호출하더라도 각각의 대기 데이터가 서로 섞이지 않아야 합니다.

반대로 FD 정수만을 키로 사용하는 전역 레지스트리는 여러 문제를 만듭니다.

- FD를 닫은 뒤 같은 번호가 전혀 다른 자원에 재사용될 수 있습니다.
- 호출자가 읽기를 중간에 끝냈을 때 상태를 정리할 명확한 진입점이 필요합니다.
- 전역 상태의 스레드 안전성을 별도로 보장해야 합니다.
- `dup`으로 만든 여러 FD가 같은 열린 파일 설명(open file description)을 공유한다는 관계를 단순한 정수 키만으로 표현하기 어렵습니다.

명시적인 리더 객체를 사용할 수 있는 API라면 전역 정적 상태보다 수명과 소유권이 분명하고 테스트도 단순해집니다.

## 지원하지 않는 범위

이 장에서 구현하는 단순한 블로킹 리더는 다음 상황을 지원하지 않습니다.

- 같은 FD를 리더 외부에서 동시에 `read`하는 경우
- 리더가 활성화된 동안 외부에서 `lseek`를 호출하는 경우
- `dup`된 두 FD를 각각 별도의 리더에서 섞어 사용하는 경우
- FD를 닫은 뒤 같은 번호가 재사용되었는지 자동으로 감지하는 기능
- `O_NONBLOCK` 환경에서 `EAGAIN` 이후 상태를 보존하고 나중에 이어서 처리하는 기능
- 같은 리더에 대한 여러 스레드의 동시 호출

지원하지 않는 조건을 정상적인 사용 사례에 암묵적으로 포함시키기보다 API가 보장하는 범위를 문서에 명확하게 적어야 합니다.

## 파이프로 부분 읽기 검증하기

일반 파일만 사용하면 실행 환경에 따라 데이터가 큰 덩어리로 한꺼번에 읽혀 부분 읽기와 상태 관리의 결함이 드러나지 않을 수 있습니다.

파이프를 사용하면 입력을 의도적으로 여러 조각으로 나누고 EOF가 발생하는 시점도 제어할 수 있습니다.

```text
쓰기: "ab"
쓰기: "c\nxy"
쓰기 끝 close

읽기:
여러 번의 read를 거쳐
"abc"
"xy"
반환
```

파이프에 연결된 모든 쓰기 끝이 닫혀야 읽는 쪽에서 EOF를 확인할 수 있습니다.

이 규칙은 다음 장에서 `fork`와 파이프를 함께 다룰 때 더욱 중요해집니다.

## 실습

[record-stream](../../exercises/03-unix-programming/01-record-stream/README.md)에서 다음 동작을 구현하고 검증합니다.

- 한 번의 `read`보다 긴 레코드
- 한 번의 `read`에 포함된 여러 레코드
- 연속된 줄바꿈 문자로 만들어지는 빈 레코드
- 줄바꿈 문자 없이 끝나는 마지막 레코드
- 줄바꿈 문자로 끝난 입력 뒤에 가짜 빈 레코드가 생기지 않는지 확인
- EOF 이후 반복 호출과 출력 매개변수 보존
- 내부 버퍼 확장과 메모리 할당 실패 주입
- 오류 발생 이후의 영구 실패 상태
- 두 리더의 교차 호출과 상태 격리
- 입력에 포함된 NUL과 명시적인 데이터 길이
- 리더의 `destroy`와 FD 소유권 분리

이 실습의 핵심은 `read`를 호출하는 방법 자체가 아닙니다. 시스템 호출이 제공하는 바이트 단위 결과를 애플리케이션이 요구하는 레코드 단위 인터페이스로 바꾸면서 호출 사이의 상태, 소유권과 오류 이후의 계약을 일관되게 유지하는 것이 목표입니다.
