# 계층, 캡슐화와 종단 경로

네트워크 계층화는 현실의 장비를 억지로 일곱 상자에 넣는 분류법보다 각 구성 요소가 무엇을 입력받고 무엇을 보장하는지 나누는 계약입니다. 계층을 나누면 애플리케이션은 Ethernet 매체 접근 방법을 몰라도 되고, 라우터는 HTTP 메서드를 몰라도 IP 목적지에 따라 패킷을 전달할 수 있습니다.

## 학습 목표

- 애플리케이션 데이터가 링크 프레임까지 캡슐화되는 경계를 추적합니다.
- 종단, 라우터와 링크가 각각 소유하는 상태와 증거를 구분합니다.

## 선행 개념

터미널에서 명령의 표준 출력과 종료 상태를 확인하고, 클라이언트와 서버가 요청·응답을 주고받는다는 기본 모델을 알고 있어야 합니다.

## 서비스 계약과 구현을 분리하기

상위 계층은 하위 계층이 제공하는 서비스를 사용하지만 하위 계층의 모든 내부 상태를 직접 제어하지 않습니다.

| 계층 | 대표 입력과 출력 | 핵심 식별자 | 대표 책임 |
|---|---|---|---|
| 애플리케이션 | 요청·응답, 메시지 | 이름, URI, 애플리케이션 ID | 의미와 업무 계약 |
| 전송 | 바이트 스트림 또는 데이터그램 | 포트와 연결 튜플 | 종단 프로세스 전달, 신뢰성·혼잡 제어 |
| 인터넷 | IP 패킷 | IP 주소와 프리픽스 | 여러 링크를 잇는 전달 |
| 링크 | 프레임 | 링크 계층 주소 | 한 링크 안의 다음 장비 전달 |
| 물리 | 신호와 비트 | 채널 | 매체를 통한 전송 |

이 표의 이름은 절대적인 경계가 아닙니다. 터널, VPN, 가상 스위치와 QUIC처럼 한 구현이 여러 전통적 역할을 묶거나 다른 계층 위에 다시 캡슐화할 수 있습니다. 중요한 것은 이름보다 각 헤더가 어느 범위에서 해석되고 어떤 상태를 선택하는지입니다.

## OSI 7계층과 Internet stack 대응

OSI 모델은 책임을 일곱 단계로 더 세분화합니다. 실제 Internet protocol 구현은 session과 presentation 역할을 독립 계층으로 고정하지 않는 경우가 많습니다.

| OSI 계층 | 대표 책임 | Internet 환경의 예 |
|---:|---|---|
| 7 Application | 사용자·업무 protocol 의미 | HTTP, DNS, SMTP |
| 6 표현 | 표현, 인코딩, 압축, 암호화 | JSON·CBOR 직렬화, TLS 레코드 처리 |
| 5 세션 | 대화 수립·유지·재개와 검사 지점 | 애플리케이션 세션, RPC 스트림, 재개 토큰 |
| 4 Transport | 종단 전달, 순서, 손실·흐름·혼잡 제어 | TCP, UDP, QUIC의 transport 기능 |
| 3 Network | 여러 링크 사이 주소와 경로 | IPv4, IPv6, ICMP |
| 2 데이터 링크 | 한 링크의 프레임 전달과 매체 접근 | Ethernet, Wi-Fi |
| 1 Physical | bit를 신호로 전송 | copper, fiber, radio |

이 대응은 분류 도구이지 프로토콜 하나를 한 칸에 영구 배치하는 법칙이 아닙니다. TLS는 애플리케이션이 사용하는 보안 프로토콜이면서 표현과 세션 역할을 일부 수행하고, QUIC은 UDP 위에서 전송·암호화·스트림 관리를 함께 구현합니다. 장애를 조사할 때는 계층 번호보다 실제 헤더, 상태와 실패 신호를 적습니다.

## 캡슐화는 바이트 앞뒤에 의미를 더합니다

브라우저가 HTTPS 요청을 보낼 때 개념적 경로는 다음과 같습니다.

```text
HTTP 메시지
→ TLS 레코드
→ TCP 바이트 스트림의 일부
→ IP 패킷 페이로드
→ Ethernet 프레임 페이로드
→ 링크의 신호
```

수신 측은 링크의 EtherType, IP의 Next Header 또는 Protocol, 전송 계층 포트와 애플리케이션 프로토콜 상태를 차례로 사용해 역다중화합니다. 헤더를 차례로 제거하는 데 그치지 않고 각 단계에서 길이, 체크섬, 상태와 정책을 검증합니다.

같은 데이터도 한 번의 고정된 포장으로 끝까지 이동하지 않습니다. 패킷이 라우터를 지날 때 링크 헤더는 다음 링크에 맞게 새로 만들어지고 IPv4 TTL 또는 IPv6 Hop Limit은 감소합니다. NAT가 없다면 출발지와 목적지 IP 및 전송 계층 포트는 대체로 종단까지 유지되지만, 단편화·터널링·정책 장비가 경로를 바꿀 수 있습니다.

## 각 범위에서 바뀌는 값

```text
애플리케이션 종단: HTTP 의미, TLS 세션
전송 종단:         TCP 순서 번호/ACK, UDP 데이터그램
라우팅 범위:       IP 주소와 프리픽스, TTL/Hop Limit
한 링크 범위:      출발지·목적지 MAC, FCS
```

라우터의 입력 프레임과 출력 프레임은 다른 링크의 프레임입니다. 따라서 원격 서버의 MAC 주소를 처음부터 알아내는 모델은 틀립니다. 호스트는 현재 링크에서 도달해야 할 **다음 홉**의 링크 계층 주소만 해석합니다.

## 다중화와 역다중화

여러 애플리케이션과 연결이 같은 인터페이스를 사용하려면 수신 측이 바이트를 올바른 소비자에게 돌려보낼 식별자가 필요합니다.

```text
EtherType 0x0800 → IPv4 처리기
IPv4 protocol 6 → TCP 처리기
TCP 목적지 포트 443 → 해당 수신 소켓
TLS ALPN h2 → HTTP/2 처리기
```

포트 하나만으로 TCP 연결을 식별하지는 않습니다. 일반적으로 로컬·원격 IP, 로컬·원격 포트와 전송 프로토콜의 조합이 필요합니다. 같은 서버 포트 `443`으로 많은 클라이언트 연결을 동시에 받을 수 있는 이유도 각 연결 tuple이 다르기 때문입니다.

## OSI 모델을 사용하는 방법

OSI 7계층은 대화를 정리할 때 유용하지만 패킷 하나가 언제나 정확히 일곱 개의 독립 헤더를 가진다는 뜻은 아닙니다. 실무 진단에서는 다음 질문이 더 직접적입니다.

1. 이름이 어떤 주소 후보로 해석되었나요?
2. 대상 주소에 어떤 경로와 다음 홉이 선택되었나요?
3. 다음 홉의 링크 계층 주소를 얻었나요?
4. 전송 연결 또는 데이터그램 교환이 성립했나요?
5. 암호화와 애플리케이션 프로토콜 계약이 맞나요?

한 단계의 성공은 다음 단계의 성공을 보장하지 않습니다. DNS가 성공해도 route가 없을 수 있고, TCP handshake가 끝나도 TLS 인증이나 HTTP 권한 검사가 실패할 수 있습니다.

## 바이트에서 계층을 확인하기

프로토콜 검사기의 읽기 전용 fixture는 FCS가 제외된 Ethernet II 프레임 안에 IPv4와 TCP SYN을 담습니다. 이 장에서는 parser를 아직 구현하지 않고 field offset을 손으로 예상합니다. checksum을 배운 뒤 root README 순서 4에서 workspace parser를 완성하고 공개 검사로 확인합니다.

```sh
cd exercises/protocol-inspector
sed -n '1,20p' fixtures/syn-frame.hex
```

출력에서 다음 연결을 확인하세요.

- Ethernet `ethertype`가 `0x0800`인지 확인합니다.
- IPv4 `protocol`이 TCP를 뜻하는 `6`인지 확인합니다.
- IPv4 페이로드 시작 위치가 IHL로 결정되는지 확인합니다.
- TCP 헤더 길이가 Data Offset으로 결정되고 나머지가 페이로드인지 확인합니다.

파서는 외부 길이 필드를 바로 믿지 않고 실제 바이트 수와 비교합니다. 캡슐화 형식을 읽는 코드에서 가장 먼저 지켜야 할 계약은 “다음 필드를 읽기 전에 그 바이트가 존재하는가”입니다.

## 계층별 증거를 남기기

연결 실패를 기록할 때 “네트워크가 안 됩니다”라고 끝내지 말고 관찰한 마지막 성공 지점을 남겨 보세요.

```text
이름 해석: A/AAAA 응답 확인
경로 선택: 출력 인터페이스와 다음 홉 확인
이웃 해석: neighbor entry 확인
전송: SYN 전송, SYN/ACK 미수신
정책: 로컬 방화벽 허용 확인, 중간 장비 미확인
```

이 형식은 원인이 DNS인지, 로컬 route인지, 원격 수신 대기인지, 경로 중간 손실인지 구분할 수 있게 합니다. 다음 장부터 각 단계가 사용하는 실제 필드와 상태를 살펴봅니다.

## 완료 기준

- 한 요청의 캡슐화 단위를 애플리케이션 메시지부터 프레임까지 순서대로 기록합니다.
- 라우터에서 바뀌는 필드와 종단에서만 해석하는 필드를 구분합니다.
- 장애 기록에 관찰 위치, 마지막 성공 계층과 아직 확인하지 못한 계층을 명시합니다.
