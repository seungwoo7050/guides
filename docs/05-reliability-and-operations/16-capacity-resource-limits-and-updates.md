# 용량, 자원 제한과 업데이트

서비스는 코드 오류가 없어도 자원이 고갈되면 실패할 수 있습니다. 메모리, CPU, 디스크, inode, PID, 파일 디스크립터, DB 연결, 외부 API 할당량은 모두 유한합니다. 반대로 제한을 설정했다고 충분한 용량이 생기는 것도 아닙니다.

이 장의 목표는 다음 순환을 만드는 것입니다.

```text
자원 예산 선언
→ 실제 사용량 측정
→ 포화도와 성장률 관찰
→ 제한·백프레셔 설정
→ 부하 시험
→ 증설 또는 최적화
→ 호스트·이미지·의존성 업데이트
→ 회귀와 롤백 검증
```

대응 실습은 [`exercises/16-capacity-and-updates`](../exercises/16-capacity-and-updates/)입니다.

## 1. 자원 예산

호스트 전체 자원을 서비스마다 합계 100%가 되도록 나누지 않습니다. 커널, Docker 데몬, 페이지 캐시, 로그 수집, 장애 시 급증을 위한 여유가 필요합니다.

예:

```text
호스트 메모리 4 GiB
- OS·Docker·관측 700 MiB
- DB 평상시 1.5 GiB, 순간 최대 2.0 GiB
- 애플리케이션 평상시 500 MiB, 순간 최대 900 MiB
- 게이트웨이 100 MiB
- 복구·배포 여유 500 MiB 이상
```

숫자는 측정 결과에 따라 갱신합니다.

## 2. 메모리

제한이 없으면 한 컨테이너가 호스트 메모리를 고갈시켜 다른 서비스와 Docker 데몬까지 영향을 줄 수 있습니다. 반대로 제한이 너무 낮으면 정상적인 순간 부하에서도 OOM kill이 발생합니다.

확인할 항목:

- 워킹 세트
- 캐시와 익명 메모리
- OOM으로 종료된 횟수
- 스왑 사용량과 지연 시간
- 애플리케이션 힙 제한
- DB 버퍼 설정
- 배포 중 이전·신규 컨테이너가 함께 실행될 때의 최대 사용량

Compose 예:

```yaml
services:
  app:
    mem_limit: 768m
    mem_reservation: 384m
```

사용하는 Compose 구현에서 실제로 적용됐는지 `docker inspect`로 확인합니다.

```sh
docker inspect --format '{{.HostConfig.Memory}}' container
```

애플리케이션 런타임이 컨테이너 제한을 인식하는지도 확인합니다.

## 3. CPU

CPU 제한은 한 컨테이너의 과도한 자원 사용이 다른 컨테이너에 미치는 영향을 줄일 수 있지만, 과도한 스로틀링은 지연 시간을 높일 수 있습니다.

관찰 항목:

- 호스트 부하와 실행 대기 프로세스
- 컨테이너 CPU 사용량
- 스로틀링된 시간
- 요청 지연 시간
- DB 쿼리 CPU
- 암호화·압축 백업 작업

평균 CPU가 낮아도 짧은 포화 구간이 꼬리 지연 시간(tail latency)을 악화시킬 수 있습니다.

## 4. PID와 프로세스

포크 폭탄(fork bomb), 잘못된 워커 설정, 좀비 프로세스 누적으로 PID가 고갈될 수 있습니다.

```yaml
services:
  app:
    pids_limit: 200
```

필요한 워커·서브프로세스 수를 측정하고 여유를 둡니다. PHP-FPM 워커, 백업 압축, 상태 검사 프로세스도 포함합니다.

## 5. 파일 디스크립터와 연결

하나의 요청은 클라이언트 소켓, 업스트림 소켓, 로그 파일, DB 연결을 사용할 수 있습니다.

확인:

```sh
ulimit -n
cat /proc/sys/fs/file-nr
ls /proc/<pid>/fd | wc -l
```

관계:

```text
동시 요청
→ 게이트웨이 연결
→ 애플리케이션 워커
→ DB 연결 풀
→ DB 최대 연결 수
```

애플리케이션 연결 풀의 합이 DB 최대 연결 수보다 크면 작은 순간 부하에도 연결 실패가 발생할 수 있습니다. 관리자·마이그레이션·백업용 연결 여유를 남깁니다.

## 6. 디스크와 inode

디스크 용량만 보지 않습니다.

- 데이터베이스 데이터
- 바이너리 로그·WAL
- 컨테이너 JSON 로그
- 이미지와 빌드 캐시
- 이전 릴리스
- 백업 스테이징
- 업로드
- inode 수

성장률로 고갈 시점을 추정합니다.

```text
남은 용량 / 최근 안정된 일평균 증가량 = 대략적인 고갈까지 남은 일수
```

증가가 선형이라는 보장은 없으므로 추세와 순간 급증을 함께 봅니다.

디스크가 거의 가득 찬 뒤 처음으로 정리 자동화를 실행하지 않습니다. 어떤 파일을 지워도 되는지 미리 분류합니다.

## 7. 네트워크와 외부 할당량

- 수신·송신 대역폭
- 연결 추적 테이블
- DNS 쿼리
- 레지스트리 pull 요청 제한
- ACME 요청 제한
- 이메일·결제 API 할당량
- 백업 저장소 요청·송신 비용

외부 서비스의 제한은 호스트 지표에 보이지 않을 수 있습니다. 응답 헤더, 공급자 지표, 애플리케이션 오류 분류를 관찰합니다.

## 8. 자원 제한과 백프레셔

제한은 피해 범위를 줄이지만 요청을 안전하게 처리하는 전략이 함께 필요합니다.

```text
입력률 > 처리률
→ 큐 증가
→ 메모리 사용량·지연 시간 증가
→ 타임아웃
→ 클라이언트 재시도
→ 입력률 추가 증가
```

대응:

- 크기가 제한된 큐
- 워커 동시성 제한
- 요청 본문·업로드 크기 제한
- 타임아웃 예산
- 요청 속도 제한
- 과부하 요청 차단
- 재시도 시점 안내(`Retry-After`)
- 백그라운드 작업 수락 제어

무제한 큐는 실패를 지연시킬 뿐 제거하지 않습니다.

## 9. 부하 시험

운영 환경에 처음부터 큰 부하를 주지 않습니다. 스테이징 또는 격리 환경에서 대표적인 워크로드를 사용합니다.

측정:

- 처리량
- p50·p95·p99 지연 시간
- 오류율
- CPU·메모리·DB 풀
- 큐 깊이
- 부하 종료 뒤 회복

부하 시험은 최대 숫자 경쟁이 아닙니다. 목표 사용자 부하와 순간 부하에서 SLO를 만족하는지 확인합니다.

데이터 크기와 쿼리 분포가 운영 환경과 너무 다르면 결과를 잘못 해석할 수 있습니다.

## 10. 용량 변경 결정

다음 중 무엇이 병목인지 구분합니다.

- CPU
- 메모리·GC
- DB 쿼리·잠금
- 스토리지 지연 시간
- 연결 풀
- 외부 의존성
- 애플리케이션 직렬화
- 게이트웨이 워커

단순히 호스트 크기를 늘리기 전에 증거를 수집합니다. 다만 사용자 영향이 진행 중이라면 임시 증설로 먼저 완화한 뒤 원인을 분석할 수 있습니다.

## 11. 업데이트 대상

```text
Linux 패키지와 커널
Docker Engine·Compose
베이스 이미지
애플리케이션 의존성
Nginx·PHP·MariaDB
CI action과 빌드 도구
백업·모니터링 에이전트
```

각 구성요소에 다음을 기록합니다.

- 현재 버전
- 지원 종료 시점
- 보안 공지 출처
- 업데이트 주기
- 호환성 검사
- 롤백 가능성
- 데이터 형식 변경 여부

## 12. 재현 가능한 업데이트

태그만 변경하고 운영 호스트에서 즉시 빌드하지 않습니다.

```text
베이스 이미지·의존성 버전 변경
→ CI 이미지 빌드
→ 테스트·검사·SBOM 생성
→ 스테이징 워크로드와 복원 테스트
→ 새 다이제스트 생성
→ 운영 배포
→ 관찰
```

베이스 이미지 다이제스트를 고정했다면 자동 의존성 업데이트 봇 또는 정기 작업으로 새 다이제스트 후보를 만듭니다. 고정은 업데이트 책임을 없애지 않습니다.

## 13. 호스트와 Docker 업데이트

업데이트 전에:

- 최근 백업과 외부 저장 확인
- 현재 릴리스와 롤백 이미지 확인
- 공급자 콘솔 접근 확인
- 디스크 여유
- 변경 내용과 알려진 호환성
- 유지보수 시간대

업데이트 뒤:

- 커널·Docker 버전
- 방화벽 규칙
- Compose 네트워크·볼륨
- systemd 유닛
- 컨테이너 재시작 정책
- 외부 TLS·스모크 테스트
- 로그·지표 전송

Docker 방화벽 백엔드나 기본 동작 변경이 네트워크 경계에 영향을 줄 수 있으므로 외부 포트 검사를 다시 수행합니다.

## 14. 롤링 업데이트가 아닌 단일 호스트

단일 인스턴스 Compose에서는 프로세스를 교체하는 동안 짧은 중단이 생길 수 있습니다. 이를 숨기지 않습니다.

가능한 완화:

- 게이트웨이와 애플리케이션을 분리해 게이트웨이는 유지
- 애플리케이션 정상 종료
- 준비 상태 검사 통과 전 트래픽 전달 금지
- 짧은 유지보수 안내
- 블루/그린 구성을 같은 호스트에서 임시로 함께 실행할 수 있는 자원 여유

같은 호스트의 블루/그린 구성은 호스트 장애에 대한 고가용성을 제공하지 않으며 배포 전환만 개선합니다. 이전·신규 DB 스키마의 호환성도 필요합니다.

## 15. 자동 업데이트의 경계

자동으로 적용하기 좋은 변경:

- CI가 검증한 의존성 업데이트 후보 생성
- 이미지 검사와 SBOM 갱신
- 스테이징 배포
- 비파괴적인 정기 재빌드

사람 승인이나 명시적인 유지보수가 필요한 변경:

- 커널 재부팅
- DB 메이저 버전 업그레이드
- 스토리지 형식 변경
- Docker 네트워크·방화벽 동작 변경
- 파괴적 마이그레이션
- 복원 절차가 바뀌는 백업 도구 변경

위험 수준과 검증 강도를 연결합니다.

## 16. 용량 검토

정기 검토에서 다음을 기록합니다.

```text
최근 최대·평상시 사용량
SLO 위반 구간
증가율과 예상 고갈일
자원 제한에 근접한 서비스
OOM·재시작·스로틀링
DB 연결·저장소
레지스트리·백업 보존 사용량
지원 종료 임박 구성요소
다음 변경과 담당자
```

검토 문서가 대시보드 스크린샷만 모아 둔 보고서가 되지 않도록 결정과 기한을 남깁니다.

## 17. 실습

[`exercises/16-capacity-and-updates`](../exercises/16-capacity-and-updates/)은 30일 호스트·서비스 지표와 구성요소 버전 목록을 제공합니다.

학습자는 다음을 계산·판정합니다.

1. 메모리·디스크 여유
2. 디스크와 백업 스테이징의 고갈 예상일
3. DB 풀과 최대 연결 수 불일치
4. 반복 OOM·재시작과 배포 겹침 위험
5. 지원 종료 또는 오래된 베이스 이미지 우선순위
6. 증설·제한·최적화 중 선택 근거
7. 업데이트 전·후 검증과 롤백 계획

자동 검사는 숫자 하나뿐 아니라 증거, 임계값, 소유자, 기한이 연결됐는지 확인합니다.
