# 런북: 데이터베이스 인증 실패

## 대상 증상과 사용자 영향

- 애플리케이션 로그에 access denied, authentication failed 또는 자격 증명 오류가 나타납니다.
- DB 컨테이너는 정상이어도 읽기·쓰기 경로가 실패할 수 있습니다.
- 비밀값 회전 직후 일부 워커만 실패할 수 있습니다.

## 필요한 권한과 도구

- 애플리케이션·DB 상태와 로그 읽기 권한
- 비밀값 **메타데이터와 버전** 읽기 권한
- DB 사용자·권한을 확인할 승인된 관리자 경로
- 비밀값 원본을 회전할 권한은 진단 권한과 분리하는 것이 좋습니다.

## 사전 안전 조건

- 비밀값을 로그, 터미널 공유 화면, 사고 문서에 출력하지 않습니다.
- 실패했다고 DB 사용자나 데이터를 먼저 삭제하지 않습니다.
- 현재와 이전 자격 증명의 유효 기간과 소비자 목록을 확인합니다.

## 1. 실패 범위 확인

- 모든 인스턴스가 실패하는가?
- 새 연결만 실패하는가, 기존 연결은 유지되는가?
- 특정 DB 사용자·데이터베이스만 실패하는가?
- 비밀값 회전 또는 배포 직후 시작됐는가?

```sh
cd /srv/example
docker compose ps -a
docker compose logs --since 15m --no-color app db
```

실제 비밀번호가 포함된 오류 문장은 외부 사고 채널로 복사하지 않습니다.

## 2. DB 자체 준비 상태 분리

DB의 로컬 프로토콜 상태 검사가 실패한다면 인증보다 DB 생명주기·디스크·복구 문제를 먼저 조사합니다.

```sh
docker compose ps db
docker compose logs --since 15m --no-color db
```

확인:

- DB 프로세스가 실행 중인가?
- 복구·업그레이드·디스크 고갈 상태인가?
- 기대한 데이터베이스와 사용자가 존재하는가?
- 계정이 잠겼거나 만료됐는가?

## 3. 비밀값 경로와 버전 확인

값을 읽어 화면에 표시하지 않고 다음 메타데이터만 확인합니다.

```sh
stat /etc/example/secrets/db_password_v2
readlink /etc/example/secrets/db_password_current 2>/dev/null || true
```

확인:

- Compose가 기대한 비밀값 이름을 마운트하는가?
- 호스트 파일 소유자·그룹·권한이 맞는가?
- 컨테이너 내부 경로가 설정과 같은가?
- 현재 포인터와 릴리스 매니페스트가 요구하는 비밀값 버전이 같은가?
- 파일 끝 줄바꿈이나 인코딩을 소비자가 어떻게 처리하는가?

## 4. 승인된 방식으로 자격 증명 검증

비밀번호를 명령행 인자로 넘기지 않습니다. DB 클라이언트가 보호된 옵션 파일, stdin 또는 비밀값 파일을 지원하면 그 경로를 사용합니다.

검증은 최소 권한의 읽기 전용 질의로 제한합니다.

```text
연결 성공
→ 현재 사용자 확인
→ 대상 database 접근
→ SELECT 1 또는 읽기 전용 query
```

관리자 자격 증명으로 성공했다는 사실은 애플리케이션 자격 증명이 정상이라는 뜻이 아닙니다.

## 5. 회전 상태 분기

### 새 자격 증명이 DB에 등록되지 않음

- 새 값을 후보로 유지합니다.
- 현재 포인터를 바꾸지 않습니다.
- DB에 새 자격 증명을 등록하고 별도 연결로 검증합니다.

### DB는 새 자격 증명을 허용하지만 애플리케이션이 이전 값을 사용

- 컨테이너 마운트와 프로세스 리로드 경계를 확인합니다.
- 연결 풀이 기존 연결을 계속 유지하는지 봅니다.
- 안전한 rolling restart 또는 연결 재생성을 수행합니다.

### 일부 워커만 실패

- 모든 복제본의 릴리스와 비밀값 버전을 비교합니다.
- 같은 서비스 안에 이전·신규 컨테이너가 섞였는지 확인합니다.

### 이전 자격 증명을 너무 일찍 폐기

- 감사 기록으로 누가 언제 폐기했는지 확인합니다.
- 새 자격 증명이 모든 소비자에서 동작하면 앞으로 진행합니다.
- 새 자격 증명도 실패하면 데이터·보안 소유자 승인 아래 제한적으로 이전 자격 증명 복구 또는 새 값 재발급을 결정합니다.

## 6. 가역 완화

- 검증된 현재 자격 증명 포인터로 되돌립니다.
- 실패한 새 릴리스가 다른 비밀값 스키마를 요구한다면 호환되는 이전 릴리스로 롤백합니다.
- 쓰기 경로를 일시 중지하고 읽기만 유지합니다.

실패한 자격 증명을 로그에 남기는 디버그 설정은 사용하지 않습니다.

## 7. 복구 확인

- 새 DB 연결이 성공합니다.
- 핵심 읽기·쓰기와 트랜잭션이 성공합니다.
- 모든 워커가 같은 비밀값 버전을 사용합니다.
- 폐기한 이전 자격 증명은 실제로 거부됩니다.
- 로그와 지표에 비밀값이 없습니다.
- DB 인증 오류율이 정상화됩니다.

## 8. 증거와 후속 작업

```text
실패한 secret 이름·version, 값 제외
영향받은 release와 instance
DB 사용자 상태
회전 timeline
Pointer 전환·rollback 결과
옛 credential 폐기 확인
재현 가능한 rotation test
```
