# 런북: 데이터 복원

## 대상 상황

- 잘못된 삭제, 데이터 손상 또는 호스트 손실 뒤 백업에서 데이터를 복원합니다.
- 전체 서비스를 되돌리는 대신 일부 레코드만 회수해야 할 수도 있습니다.
- 복원은 현재 운영 데이터베이스를 바로 덮어쓰는 작업이 아니라, 별도 환경에서 검증한 뒤 전환 여부를 결정하는 절차입니다.

## 필요한 역할

- 사고 지휘자
- 데이터 소유자
- 복원 실행자
- 애플리케이션 검증자
- 외부 전환 승인자

한 사람이 여러 역할을 맡더라도 결정과 실행 책임은 구분합니다.

## 사전 안전 조건

- 백업 원본과 매니페스트를 읽기 전용으로 취급합니다.
- 운영 DB에 바로 복원하지 않습니다.
- 이메일, 결제, 웹훅과 백그라운드 작업의 외부 부작용을 차단합니다.
- 선택한 백업이 RPO에 미치는 영향을 승인받습니다.

## 1. 복원 목표 정의

```text
전체 서비스 복구 또는 일부 데이터 회수
선택 백업 ID
복원해야 할 최신 시각
대상 애플리케이션 릴리스·스키마
허용 중단 시간
전환 또는 병합 방식
```

## 2. 백업 검증

- 매니페스트 스키마와 서명·출처
- 산출물 크기·체크섬
- 암호화 키 접근 가능 여부
- DB 엔진·버전 호환성
- 업로드 스냅샷과 DB 스냅샷의 일관성
- 악성 코드 또는 침해 시점 포함 가능성

체크섬이 일치하지 않는 산출물을 강제로 복원하지 않습니다.

## 3. 격리된 대상 준비

```text
빈 데이터베이스
빈 업로드 대상
외부 네트워크 제한
운영과 다른 프로젝트·볼륨 이름
안전한 테스트 비밀값
외부 부작용을 비활성화한 설정
```

대상에 기존 데이터가 있으면 기본적으로 중단합니다. 덮어쓰기는 별도 승인이 필요합니다.

## 4. 복원 수행

```text
복호화
→ DB 복원
→ 업로드 복원
→ 스키마 확인
→ 제약 조건·행 수 확인
→ 참조 무결성·체크섬 확인
→ 호환 애플리케이션 시작
```

복원 명령의 stdout·stderr와 종료 코드는 보존하되 비밀값과 개인정보는 기록 전에 마스킹합니다.

## 5. 애플리케이션 검증

- 대표 사용자 로그인 또는 승인된 인증 대체 경로
- 핵심 읽기
- 격리된 안전한 쓰기와 재조회
- 업로드 조회
- 백그라운드 작업 중복 여부
- 최신 이벤트 시각
- 스키마·릴리스 호환성

SQL 행 수만 확인하고 사용자 기능이 복구됐다고 판단하지 않습니다.

## 6. 전환 결정

### 전체 전환

- 쓰기를 중지하거나 복원 이후 변경분을 처리할 전략을 정합니다.
- 최종 변경분 반영 또는 유지보수 창을 적용합니다.
- DNS·트래픽 전환과 롤백 조건을 기록합니다.

### 일부 데이터 회수

- 어떤 레코드와 연관 데이터를 회수할지 정의합니다.
- 애플리케이션 API 또는 검증된 마이그레이션을 사용합니다.
- 외래 키, 감사 기록, 업무 불변식을 확인합니다.

운영 DB에 임시 SQL을 직접 적용하는 방식을 기본 절차로 두지 않습니다.

## 7. 복구 확인

- 외부 사용자 경로가 성공합니다.
- 복원된 최신 데이터 시각을 기준으로 실제 RPO를 계산합니다.
- 복구 선언부터 사용자 기능 정상화까지 실제 RTO를 계산합니다.
- 오류율, 지연 시간, 백그라운드 처리가 안정적입니다.
- 새 백업이 성공하고 이전의 손상 상태와 분리되어 보관됩니다.

## 8. 중단·에스컬레이션 조건

- 백업 무결성을 신뢰할 수 없습니다.
- 스키마 호환성이 확인되지 않습니다.
- 복원 데이터에 침해 흔적이 있습니다.
- 일부 데이터 회수가 다른 사용자나 업무 기록을 손상할 수 있습니다.
- 실제 RPO가 승인 범위를 초과합니다.

## 9. 증거와 후속 작업

```text
선택 백업·릴리스
체크섬·복원 종료 코드
복원된 최신 이벤트
검증한 사용자 경로
실제 RPO·RTO
전환·병합 승인
누락된 자동화와 런북 수정 사항
```
