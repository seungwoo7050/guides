# 런북: 디스크·inode 고갈

## 대상 증상과 사용자 영향

- 쓰기 실패, DB 중단, 이미지 pull 실패, 로그 기록 실패가 발생합니다.
- `No space left on device`는 바이트 부족뿐 아니라 inode 부족일 수 있습니다.
- 디스크 사용률이 높아도 무엇을 삭제해도 되는지는 별도 판단입니다.

## 사전 안전 조건

- DB 데이터, 업로드, 현재·롤백 이미지와 유일한 백업을 삭제하지 않습니다.
- 자동 `docker system prune -a`, `down -v`, 광범위한 `rm -rf`를 실행하지 않습니다.
- 먼저 파일 시스템과 증가 원인을 확인합니다.

## 1. 바이트와 inode 확인

```sh
df -h
df -i
findmnt
lsblk -f
```

기록:

- 어떤 마운트가 고갈됐는가?
- 바이트인가 inode인가?
- 읽기 전용 재마운트나 I/O 오류가 있는가?
- 증가 속도는 얼마인가?

## 2. 큰 범주 찾기

파일 시스템 경계를 넘지 않도록 `-x`를 사용합니다.

```sh
sudo du -x -h -d 1 /var 2>/dev/null | sort -h
sudo du -x -h -d 1 /srv 2>/dev/null | sort -h
docker system df
journalctl --disk-usage
```

삭제됐지만 열린 파일도 확인합니다.

```sh
sudo lsof +L1 2>/dev/null || true
```

파일을 삭제했는데 공간이 돌아오지 않는다면 프로세스가 열린 파일 디스크립터를 유지하고 있을 수 있습니다.

## 3. 원인 분류

### 컨테이너 로그 증가

- logging driver와 rotation 설정을 확인합니다.
- 특정 릴리스의 반복 오류가 로그 폭주를 만드는지 봅니다.
- 알려진 로그만 순환시키고 프로세스가 파일을 다시 여는지 확인합니다.

### 이미지·빌드 캐시 증가

- 현재와 롤백 릴리스가 참조하는 다이제스트를 먼저 목록화합니다.
- 미참조 캐시와 중간 이미지만 선택적으로 정리합니다.
- 운영 호스트에서 빌드하지 않는다면 빌드 캐시가 커지는 원인을 조사합니다.

### DB 데이터·WAL·바이너리 로그 증가

- DB별 안전한 보존·purge 명령을 사용합니다.
- 복제·백업·point-in-time recovery에 필요한 로그를 임의로 삭제하지 않습니다.
- 비정상 트랜잭션, vacuum·checkpoint 또는 보존 정책 실패를 조사합니다.

### 백업 스테이징 증가

- 외부 업로드와 체크섬 검증이 완료된 산출물만 스테이징에서 제거합니다.
- 마지막 성공 백업과 유일한 복사본을 삭제하지 않습니다.

### 업로드·업무 데이터 증가

- 사용자 데이터 보존 정책과 애플리케이션 삭제 경로를 따릅니다.
- 셸에서 임의 삭제하지 않습니다.

### inode 고갈

- 작은 파일이 대량 생성되는 캐시, 세션, 임시 디렉터리를 찾습니다.
- 생성 주체와 생명주기를 수정합니다.

## 4. 가역 완화

우선순위 예:

1. 비필수 쓰기·batch 작업 중지
2. 알려진 임시 파일 생성 중지
3. 보존 정책이 명확한 이전 로그 순환·압축
4. 검증 완료 백업 스테이징을 외부 확인 후 제거
5. 참조되지 않는 빌드 캐시 선택 정리
6. 디스크 확장 또는 새 볼륨 부착

DB가 이미 읽기 전용 또는 crash 상태라면 반복 재시작보다 공간을 확보하고 DB 복구 절차를 따릅니다.

## 5. 고위험 조치 승인 경계

다음은 자원 ID, 예상 회수량, 백업과 롤백 영향을 출력한 dry-run 뒤 승인합니다.

- Docker 이미지 일괄 삭제
- DB 로그 purge
- 업로드 삭제
- 파일 시스템 크기 조정
- 볼륨 이동
- 보존 정책 변경

## 6. 복구 확인

- 바이트와 inode에 운영 여유가 생겼습니다.
- DB와 애플리케이션 쓰기가 성공합니다.
- 재시작 반복이 멈췄습니다.
- 로그·백업·업로드 증가율이 정상화됩니다.
- 디스크 고갈 예측과 경보가 갱신됩니다.
- 같은 원인이 다시 증가할 때 충분히 이른 시점에 경보가 울립니다.
