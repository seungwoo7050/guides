# 백업, 복원과 재해 복구

백업 작업의 종료 코드가 0이라는 사실만으로 데이터가 복구 가능하다고 말할 수 없습니다. 운영에서 필요한 것은 파일 생성이 아니라 다음 전체 경로입니다.

```text
복구할 상태 식별
→ 일관된 시점의 데이터 획득
→ 무결성 확인
→ 호스트 밖으로 전송
→ 보존·암호화·삭제 권한 분리
→ 빈 환경에 복원
→ 애플리케이션 기능 검증
→ RPO·RTO 증거 기록
```

대응 실습은 [`exercises/15-disaster-recovery`](../exercises/15-disaster-recovery/)입니다.

## 1. 백업과 가용성은 다른 문제

백업은 손실된 상태를 과거 시점에서 복원합니다. 복제본이나 두 번째 호스트는 장애 중 서비스를 계속 제공할 수 있지만 잘못된 삭제, 손상, 랜섬웨어가 복제본에도 전파될 수 있습니다.

```text
가용성 장치: 장애 중 서비스를 계속 제공
백업: 과거의 독립된 상태로 되돌림
```

둘 중 하나가 다른 하나를 대신하지 않습니다. 이 과정은 단일 호스트를 기준으로 하므로 즉시 장애 조치(failover)보다 검증된 복원을 우선합니다.

## 2. 복구 대상 목록

호스트 전체를 막연히 백업하지 말고 상태별 복구 원본을 정합니다.

| 상태 | 복구 원본 | 일반적인 방법 |
|---|---|---|
| 애플리케이션 이미지 | 레지스트리 | 정확한 다이제스트로 pull |
| Compose·게이트웨이 설정 | Git 또는 릴리스 산출물 | 버전이 고정된 체크아웃 |
| 공개 환경 설정 | 배포 저장소 | 버전 관리 파일 |
| 런타임 비밀값 | 비밀값 원본 | 재주입 또는 재발급 |
| 데이터베이스 | 외부 백업 저장소 | DB 덤프·물리 백업 |
| 사용자 업로드 | 객체 백업 | 파일 스냅샷·동기화 |
| TLS 인증서 | ACME 재발급 또는 보호된 저장소 | 새 발급 우선 고려 |
| DNS 레코드 | 공급자와 버전 관리 레코드 문서 | API·관리 콘솔 |
| 운영 로그 | 외부 로그 저장소 | 보존 정책에 따라 조회 |
| 릴리스 이력 | 배포 기록 | 매니페스트 복원 |

이미지와 설정을 데이터 백업에 중복해 넣을 수는 있지만 무엇을 기준 원본으로 삼는지는 하나로 정합니다.

## 3. 일관된 백업

실행 중인 데이터 파일을 무작정 복사하면 서로 다른 시점의 페이지와 로그가 섞일 수 있습니다. 데이터베이스가 제공하는 일관된 덤프, 물리 백업 또는 파일 시스템 스냅샷 절차를 사용합니다.

### 논리 백업

예: SQL 덤프

장점:

- 내용을 비교적 쉽게 검사할 수 있습니다.
- 다른 인스턴스에 복원하기 쉽습니다.
- 스키마와 데이터를 선택할 수 있습니다.

주의:

- 큰 데이터에서는 생성·복원 시간이 길 수 있습니다.
- DB별 옵션과 권한을 알아야 합니다.
- 트랜잭션 일관성 옵션을 사용해야 합니다.

### 물리 백업

데이터 파일과 WAL·redo 로그를 DB가 정의한 방식으로 보존합니다.

장점:

- 큰 데이터의 빠른 복원과 시점 복구에 유리할 수 있습니다.

주의:

- DB 버전·스토리지 레이아웃 의존성이 큽니다.
- 단순 디렉터리 복사와 다릅니다.
- 복구 도구와 로그 보존 계약이 필요합니다.

초기의 작은 서비스에서는 논리 백업으로 시작해 실제 RTO를 측정하고 부족할 때 물리 백업을 검토합니다.

## 4. 데이터베이스와 업로드의 같은 시점

데이터베이스가 업로드 파일의 경로를 가리킨다면 둘의 시점이 다를 때 다음 문제가 생깁니다.

- DB 행은 있지만 파일이 없음
- 파일은 있지만 DB 행이 없음
- 파일 버전과 메타데이터가 다름

선택지:

- 쓰기를 잠시 정지하고 둘을 같은 시간 구간에 백업
- 애플리케이션 수준의 스냅샷 ID 기록
- 업로드를 콘텐츠 주소 기반의 불변 객체로 저장
- DB와 객체 저장소의 버전 관리·보존 정책 연결
- 복원 뒤 불일치 조정 수행

완전한 원자적 스냅샷이 어렵다면 불일치를 탐지하고 복구하는 정책을 명시합니다.

## 5. 백업 산출물과 매니페스트

각 백업에 기계 판독 가능한 매니페스트를 둡니다.

```yaml
schema_version: 1
backup_id: 2026-08-07T020000Z
created_at: 2026-08-07T02:00:00Z
source:
  service: notes
  release: 2026-08-01.2
  database_schema: 18
artifacts:
  - path: database.sql.gz.enc
    sha256: ...
    bytes: 123456
  - path: uploads.tar.zst.enc
    sha256: ...
    bytes: 987654
consistency:
  method: maintenance-window
  started_at: ...
  completed_at: ...
```

매니페스트에는 다음을 넣지 않습니다.

- 암호화 키
- 데이터베이스 비밀번호
- 사용자 개인정보 원문
- 복호화 자격 증명

체크섬은 우발적 손상을 탐지하는 데 사용합니다. 공격자가 산출물과 매니페스트를 모두 바꿀 수 있는 환경에서는 서명이나 변경 불가능한 저장소 정책이 필요합니다.

## 6. 암호화와 키 분리

백업에는 운영 데이터가 그대로 포함됩니다. 전송 중과 저장 시 암호화를 적용하고 복호화 키의 수명 주기를 별도로 관리합니다.

피해야 할 구조:

```text
운영 호스트
  ├─ 백업 파일
  └─ 유일한 복호화 키
```

호스트가 손상되면 둘 다 유출되거나 삭제될 수 있습니다.

검토할 것:

- 키 원본의 소유자
- 복구 담당자가 키에 접근하는 방법
- 키 회전과 오래된 백업 복호화
- 키 손실 시험
- 비상 접근 감사

## 7. 호스트 밖의 독립된 복사본

로컬 볼륨과 같은 호스트의 `/var/backups`만 사용하면 디스크·호스트 손실에서 보호되지 않습니다. 백업 스테이징은 가능하지만 성공 후 외부 저장소로 전송합니다.

외부 저장소 정책:

- 운영 자격 증명과 다른 삭제 권한
- 버전 관리 또는 객체 잠금(object lock) 검토
- 보존 정책
- 전송 실패 경보
- 저장소 자체의 접근 로그
- 다른 계정·리전 또는 오프라인 복사본 필요성
- 비용과 송신 트래픽 제한

한 운영 자격 증명이 운영 데이터와 모든 백업을 동시에 삭제할 수 있다면 피해 범위가 큽니다.

## 8. 보존 정책

예시:

```text
일별 14개
주별 8개
월별 12개
```

숫자를 그대로 복사하지 않습니다. 다음을 기준으로 정합니다.

- 오류 발견까지 걸리는 시간
- 법적·업무 보존 요구
- 저장 비용
- 스키마와 애플리케이션 호환성
- 복원 시험 범위
- 사용자 삭제 요구

오래된 백업을 많이 보존할수록 개인정보와 자격 증명 노출 범위도 커질 수 있습니다.

## 9. 백업 작업의 성공 조건

다음이 모두 확인돼야 합니다.

1. DB 도구 종료 코드 성공
2. 산출물이 비어 있지 않음
3. 예상 테이블·레코드 또는 메타데이터 존재
4. 체크섬 계산 성공
5. 암호화 성공
6. 외부 저장소 업로드 성공
7. 원격 객체 크기·체크섬 또는 공급자 검증 성공
8. 매니페스트 기록
9. 백업 경과 시간 지표 갱신
10. 실패 시 경보

파이프라인에서 앞 명령 실패가 뒤 명령 때문에 가려지지 않도록 셸의 파이프 실패 처리와 임시 파일의 원자적 교체를 사용합니다.

## 10. 복원은 별도 환경에서 시작

처음부터 손상된 운영 환경 위에 덮어쓰지 않습니다.

```text
빈 복원 대상 준비
→ 이미지·설정·비밀값 버전 확인
→ 백업 체크섬·서명 검증
→ 복호화
→ DB와 파일 복원
→ 스키마·행 수·업로드 정합성 검사
→ 애플리케이션을 격리된 주소로 실행
→ 기능 스모크 테스트
→ 전환 여부 결정
```

복원 실패가 원본과 기존 백업을 손상하지 않게 읽기 전용 원본에서 작업합니다.

## 11. 복원 검증

파일이 풀렸다는 사실보다 사용자 기능을 확인합니다.

- 핵심 테이블과 제약 조건이 있는가?
- 대표 행과 최근 데이터가 예상 범위인가?
- 업로드 체크섬이 맞는가?
- 애플리케이션이 로그인·읽기·쓰기 가능한가?
- 백그라운드 작업이 중복 실행되지 않는가?
- 스키마 버전이 릴리스와 호환되는가?
- 비밀값이 백업 시점의 폐기된 자격 증명에 묶여 있지 않은가?

복원 환경에서 외부 이메일·결제·웹훅을 실제로 보내지 않도록 차단합니다.

## 12. RPO 측정

장애 시각과 복원된 최신 이벤트 시각을 비교합니다.

```text
실제 데이터 손실 범위
= 장애 직전 마지막 성공 쓰기 시각 - 복원된 최신 쓰기 시각
```

마지막 백업 생성 시각만 보고 계산하지 않습니다. 백업이 실제로 외부에 저장·검증된 시각과 복원된 데이터의 최신 시점을 봅니다.

## 13. RTO 측정

다음 구간을 기록합니다.

```text
장애 확인
→ 복구 결정
→ 새 환경 준비
→ 산출물 획득
→ 복원
→ 검증
→ DNS·트래픽 전환
→ 사용자 기능 확인
```

자동화가 빨라도 자격 증명 승인이나 DNS 접근에 오래 걸릴 수 있습니다. 전체 경로를 측정합니다.

## 14. 재해 시나리오

### 호스트 전체 손실

레지스트리, Git, 비밀값 원본, 외부 백업에서 새 호스트를 구성합니다. 18장의 최종 실습에서 전체 절차를 검증합니다.

### 잘못된 데이터 삭제

현재 DB가 정상 실행 중이어도 과거 시점 복원이 필요합니다. 별도 DB에 복원한 뒤 필요한 레코드를 선택적으로 회수할지 전체 전환할지 결정합니다.

### 랜섬웨어 또는 관리자 자격 증명 탈취

현재 호스트에서 생성한 새 백업을 신뢰할 수 없을 수 있습니다. 공격 이전의 변경 불가능하거나 오프라인인 백업과 깨끗한 프로비저닝 원본이 필요합니다.

### 백업 저장소 손상

다른 계정·리전 또는 오프라인 복사본이 필요한지 운영 계약에서 정합니다.

### 암호화 키 손실

백업 산출물이 있어도 복원할 수 없습니다. 키 복구와 비상 접근을 별도로 시험합니다.

## 15. 복원 훈련

최소한 다음을 기록합니다.

```text
훈련 일시
사용한 백업 ID
복원 대상 환경
작업자
시작·종료 시각
복원된 최신 데이터 시점
검증한 사용자 경로
발견한 누락·수동 단계
실제 RPO·RTO
후속 조치와 담당자
```

같은 사람이 같은 익숙한 호스트에서만 반복하면 숨은 전제를 발견하기 어렵습니다. 가능한 경우 다른 작업자나 새 환경에서 수행합니다.

## 16. 실습

[`exercises/15-disaster-recovery`](../exercises/15-disaster-recovery/)은 합성 데이터베이스 덤프와 업로드를 사용합니다.

학습자는 다음을 구현합니다.

1. 원본 상태를 읽기 전용으로 취급
2. 산출물별 체크섬과 크기를 매니페스트에 기록
3. 완성 전 백업을 `current`로 노출하지 않음
4. 손상된 산출물 복원 거부
5. 빈 대상에만 기본 복원
6. DB 행과 업로드 체크섬의 참조 정합성 검사
7. 복원 뒤 사용자 수준 스모크 검증
8. 실제 RPO·RTO 결과 기록

실제 개인정보나 운영 자격 증명은 사용하지 않습니다.
