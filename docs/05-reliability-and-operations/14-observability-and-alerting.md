# 관측성과 경보

관측성은 로그 수집기를 설치하는 일이 아닙니다. 외부 증상과 내부 상태를 연결해 다음 질문에 답할 수 있는 능력입니다.

```text
무엇이 실패했는가?
언제 시작됐는가?
누가 영향을 받는가?
어느 릴리스와 구성 변경 뒤 발생했는가?
어떤 의존 경계까지 성공했는가?
지금 완화가 필요한가, 분석을 계속해도 되는가?
복구됐다는 증거는 무엇인가?
```

대응 실습은 [`exercises/14-observability`](../exercises/14-observability/)입니다.

## 1. 관측 신호

### 로그

개별 이벤트의 구체적인 문맥을 기록합니다.

```json
{
  "timestamp": "2026-08-07T12:00:00Z",
  "level": "error",
  "service": "app",
  "release": "2026-08-07.1",
  "request_id": "req-...",
  "event": "database_query_failed",
  "error_class": "timeout",
  "duration_ms": 2000
}
```

### 지표

시간에 따른 수치와 분포를 집계합니다.

```text
http_requests_total
http_request_duration_seconds
http_errors_total
db_pool_in_use
container_restarts_total
backup_age_seconds
certificate_expiry_seconds
```

### 트레이스

하나의 요청이 게이트웨이, 애플리케이션, 데이터베이스, 외부 API를 거치는 구간을 연결합니다. 단일 호스트의 작은 서비스에서도 느린 요청과 의존 경계를 찾는 데 유용할 수 있습니다.

### 프로파일

CPU, 메모리 할당, 잠금 경합처럼 프로세스 내부 자원 사용을 분석합니다. 상시 사용 여부와 보존 비용을 정합니다.

모든 신호를 처음부터 도입할 필요는 없습니다. 최소 기준선은 구조화 로그, 핵심 지표, 외부 상태 검사, 실제 대응으로 이어지는 경보입니다.

## 2. 사용자 관점과 내부 관점

### 외부 관점

호스트 밖에서 다음을 확인합니다.

- DNS 해석
- TCP 연결
- TLS 호스트 이름·체인·만료
- HTTP 상태와 응답 계약
- 실제 사용자 경로의 지연 시간

### 내부 관점

- 컨테이너·프로세스 상태
- CPU·메모리·디스크·inode
- 재시작 횟수
- DB 연결·쿼리 오류
- 큐·워커 지연
- 백업·인증서 갱신 작업

외부 실패와 내부 신호를 함께 봐야 합니다.

```text
외부 5xx 증가 + 애플리케이션 DB 타임아웃 증가
→ 데이터베이스 경계 조사

외부 TLS 실패 + 애플리케이션·게이트웨이 정상
→ 인증서·DNS 경계 조사
```

## 3. 상태 검사 다시 구분하기

07장에서 다룬 상태를 운영 신호에 연결합니다.

### Liveness

프로세스가 회복 불가능하게 멈췄는지 판단합니다. 외부 의존성 실패를 무조건 포함하면 재시작 폭주를 만들 수 있습니다.

### 준비 상태 검사(Readiness)

현재 새 요청을 받을 준비가 됐는지 판단합니다. 마이그레이션, 연결 풀, 필수 내부 자원 상태를 포함할 수 있습니다.

### 스모크 또는 합성 검사

호스트 밖에서 실제 사용자 경로를 검사합니다. 공개 DNS와 TLS를 통과해야 합니다.

세 검사의 실패 의미와 자동 반응을 다르게 설정합니다.

## 4. 구조화 로그 계약

문자열 문장만 남기면 검색과 집계가 어렵습니다. 최소 필드를 정합니다.

| 필드 | 의미 |
|---|---|
| `timestamp` | 시간대가 명확한 이벤트 시각 |
| `level` | debug·info·warn·error |
| `service` | 이벤트 소유 구성요소 |
| `environment` | 운영·스테이징 환경 |
| `release` | 실행 이미지와 연결되는 릴리스 ID |
| `event` | 안정된 기계 판독 이벤트 이름 |
| `request_id` | 한 HTTP 요청 안의 상관관계 |
| `trace_id` | 여러 서비스 구간의 상관관계 |
| `duration_ms` | 작업 시간, 있을 때 |
| `error_class` | timeout·validation·dependency 등 안정된 분류 |

로그의 `message`는 사람이 읽는 설명이고 `event`와 분류 필드는 조회·집계를 위한 계약입니다.

## 5. 상관관계 ID

게이트웨이에서 들어온 request ID를 검증하거나 새로 만들고 애플리케이션에 전달합니다. 외부 사용자가 지나치게 긴 값이나 제어 문자를 주입하지 못하도록 형식과 길이를 제한합니다.

구분:

- 요청 ID: 한 HTTP 요청
- 트레이스 ID: 여러 span으로 이어지는 분산 요청
- 작업 ID: 재시도 사이에서도 같은 업무 작업
- 사용자 ID: 사용자 주체, 개인정보 정책 적용
- 릴리스 ID: 배포 단위

모든 상관관계 정보를 요청 ID 하나로 대신하지 않습니다.

## 6. 민감 정보와 카디널리티

로그에 비밀값, 토큰, 비밀번호, 전체 요청 본문을 남기지 않습니다.

지표 레이블에는 값 종류가 무한히 늘어나는 항목을 넣지 않습니다.

나쁜 예:

```text
http_requests_total{user_id="...",request_id="...",url="/notes/12345"}
```

좋은 예:

```text
http_requests_total{method="GET",route="/notes/:id",status_class="2xx"}
```

높은 카디널리티는 지표 저장 비용과 조회 성능을 급격히 악화시킵니다. 구체적인 ID는 로그나 트레이스에서 찾습니다.

## 7. 핵심 지표

### 요청

- 요청 수
- 4xx·5xx 비율
- 지연 시간 분포
- 활성 요청 수
- 타임아웃

평균만 보지 않고 백분위수 또는 히스토그램을 사용합니다. 소수의 매우 느린 요청이 평균에 가려질 수 있습니다.

### 자원

- CPU 사용량과 스로틀링
- 메모리 워킹 세트와 OOM
- 디스크 바이트·inode 사용률
- 네트워크 오류
- 프로세스·PID 수

### 데이터베이스

- 연결 풀 사용률
- 연결 실패
- 쿼리 지연 시간
- 잠금 대기와 데드락
- 저장소 증가
- 백업 성공 여부와 경과 시간

### 배포·운영

- 현재 릴리스
- 마지막 성공 배포
- 컨테이너 재시작
- 인증서 만료까지 남은 시간
- 백업 복원 훈련 이후 경과 시간
- 경보 전달 실패

### 업무 지표

서비스가 실제로 제공해야 하는 결과를 나타냅니다.

- 생성 성공 수
- 처리 대기량
- 결제 성공률
- 동기화 지연

업무 지표가 0인 상태가 정상적인 비수기인지 장애인지는 문맥과 함께 판단합니다.

## 8. SLI와 SLO

SLI는 실제 측정치이고 SLO는 목표입니다.

예:

```text
SLI: 외부 합성 검사의 성공 비율
SLO: 최근 30일 99.5% 이상
```

좋은 SLI는 사용자 경험과 가깝습니다. 컨테이너 실행 비율은 운영 지표지만 사용자가 기능을 쓸 수 있는지를 직접 나타내지는 않을 수 있습니다.

초기 서비스의 최소 SLI:

- 핵심 경로 성공률
- 핵심 경로 지연 시간
- 데이터 최신성 또는 작업 지연
- 복원 시험 성공 여부와 소요 시간

## 9. 경보 원칙

좋은 경보는 다음을 만족합니다.

- 실제 사용자 영향 또는 임박한 자원 고갈을 나타냅니다.
- 수신자가 취할 수 있는 행동이 있습니다.
- 긴급도와 대응 시간이 명확합니다.
- 관련 대시보드와 런북이 연결됩니다.
- 일시적인 한 번의 급등보다 지속 조건을 고려합니다.

증상 기반 경보를 우선합니다.

```text
좋음: 외부 핵심 경로 성공률이 10분간 목표 이하
보조: 데이터베이스 CPU 90%
```

CPU가 높아도 사용자가 영향을 받지 않을 수 있고 CPU가 낮아도 deadlock으로 모든 요청이 실패할 수 있습니다.

## 10. 경보 수준

한 가지 예:

### 즉시 호출(Page)

즉시 사람이 대응해야 합니다.

- 핵심 사용자 경로 지속 실패
- 데이터 손실 진행 가능성
- 인증서 임박 만료
- 디스크 고갈 임박
- 백업과 복구 원본 동시 위험

### 티켓(Ticket)

근무 시간 안에 처리할 수 있습니다.

- 베이스 이미지 업데이트 필요
- 디스크 증가 추세
- 복원 훈련 기한 초과
- 비긴급 경고율 상승

### 대시보드 전용

추세와 분석에는 필요하지만 매번 사람을 호출하지 않습니다.

경보가 너무 자주 잘못 울리면 운영자는 무시하게 됩니다. 알림을 끄기 전에 조건과 사용자 신호를 개선합니다.

## 11. 경보에 포함할 문맥

```text
무슨 환경·서비스인가?
언제 시작됐는가?
현재 값과 임계값은 무엇인가?
어떤 사용자가 영향을 받는가?
최근 배포는 무엇인가?
어디서 로그·지표를 보는가?
첫 안전 조치는 무엇인가?
어떤 런북을 따르는가?
```

경보 메시지에 비밀값이나 전체 개인정보를 넣지 않습니다.

## 12. 대시보드

대시보드는 모든 지표를 한 화면에 넣는 곳이 아닙니다.

권장 계층:

### 서비스 개요

- 사용자 성공률과 지연 시간
- 현재 릴리스
- 주요 의존성
- 활성 사고

### 자원

- 호스트 CPU·메모리·디스크
- 컨테이너 재시작·제한
- DB 풀과 저장소

### 배포 비교

- 릴리스 마커
- 배포 전후 오류·지연 시간
- 롤백 이벤트

### 복구 준비

- 백업 경과 시간
- 복원 훈련 결과
- 인증서 만료까지 남은 시간
- 베이스 이미지 경과 시간

## 13. 로그 전달과 장애

컨테이너 stdout만 호스트 로컬에 두면 호스트 손실과 함께 사고 증거도 사라질 수 있습니다. 필요에 따라 외부 로그 목적지로 전달합니다.

결정할 것:

- 전송 실패 때 애플리케이션을 막을 것인가?
- 로컬 버퍼 크기와 디스크 한계
- 백프레셔와 드롭 정책
- TLS와 인증
- 보존 기간
- 개인정보 삭제 요청
- 목적지 장애 경보

로그 수집 장애가 운영 서비스 전체를 멈추게 할지 신중히 결정합니다. 일반적으로 업무 요청은 계속 처리하되 손실을 탐지하고 제한된 로컬 버퍼를 둡니다.

## 14. 트레이스 도입 경계

여러 서비스·큐·외부 API를 거치면 트레이스의 가치가 커집니다. 단일 서비스에서도 느린 DB 쿼리를 찾는 데 사용할 수 있습니다.

도입 시 확인:

- 샘플링 정책
- 트레이스 컨텍스트의 신뢰 경계
- 개인정보·비밀값 속성 기록 금지
- 익스포터 실패 처리
- 컬렉터의 자원 제한
- 로그·지표와 릴리스 ID 연결

관측 시스템이 장애를 증폭하지 않도록 비동기 전송, 제한된 큐와 드롭 정책을 둡니다.

## 15. 배포와 관측성

배포 워크플로는 다음 마커를 남깁니다.

```text
release_id
이미지 다이제스트
소스 리비전
시작·완료·롤백 시각
```

문제가 발생하면 배포 전후의 같은 시간 창을 비교합니다. “최근 배포가 있었으니 원인이다”라고 단정하지 않고 상관관계를 증거로 확인합니다.

## 16. 관측 시스템 자체 검사

- 외부 프로브가 실행되고 있는가?
- 지표 수집이 끊기지 않았는가?
- 로그 파이프라인이 지연되지 않았는가?
- 경보 규칙 평가기가 정상인가?
- 알림 채널로 테스트 메시지가 도착하는가?
- 시간 동기화가 정상인가?

아무 경보가 없다는 사실만으로 정상 상태라고 판단할 수는 없습니다.

## 17. 실습

[`exercises/14-observability`](../exercises/14-observability/)은 표준 라이브러리 HTTP 서비스를 실행하고 다음을 검증합니다.

- `/healthz`와 `/readyz`의 의미가 다름
- 요청마다 제한된 request ID 생성·전달
- JSON 로그에 서비스·릴리스·이벤트·처리 시간 필드 포함
- 토큰·쿠키가 로그에 남지 않음
- `/metrics`에서 요청·오류·지연 시간 집계
- 경로 파라미터 대신 안정된 라우트 레이블 사용
- 의존 서비스 실패가 준비 상태와 사용자 응답에 다르게 반영됨
- 릴리스 변경 뒤 로그와 지표에서 새 릴리스 식별

도구 설치보다 신호의 의미와 스키마를 먼저 고정합니다.
