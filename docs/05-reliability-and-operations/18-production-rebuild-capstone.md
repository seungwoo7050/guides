# 공개 서비스 재구축 최종 실습

이 과정의 최종 검증은 기존 서버에서 설정을 조금 고치는 작업이 아닙니다. **기존 호스트가 사라졌다고 가정하고** 외부에 보존한 원본만으로 새 호스트에 서비스를 복구합니다.

```text
새 Linux 호스트
+ 버전이 관리되는 프로비저닝 계약
+ 정확한 릴리스 매니페스트와 이미지 다이제스트
+ 비밀값 원본 또는 재발급 권한
+ 외부 백업
+ DNS 제어권
+ 관측 체계·런북
= 복구 가능한 공개 서비스
```

대응 실습은 [`exercises/18-production-rebuild`](../exercises/18-production-rebuild/)입니다. 자동 실습은 계획과 증거 스키마를 검증하며, 실제 완료 여부는 별도의 폐기 가능한 VPS에서 확인합니다.

## 1. 최종 실습의 목표

다음 상황을 가정합니다.

- 기존 운영 호스트에 접근할 수 없습니다.
- 기존 컨테이너와 로컬 볼륨을 사용할 수 없습니다.
- 새 공개 IP가 할당됩니다.
- 레지스트리, Git, 비밀값 원본, DNS 공급자와 외부 백업에는 접근할 수 있습니다.
- 복구 작업자는 기존 호스트의 셸 이력을 볼 수 없습니다.

완료 조건은 다음과 같습니다.

1. 새 호스트를 준비합니다.
2. 정확한 릴리스 이미지를 실행합니다.
3. 외부 백업을 복원합니다.
4. 새 공개 TLS 인증서를 발급합니다.
5. DNS를 새 호스트로 전환합니다.
6. 외부에서 핵심 읽기·쓰기 경로를 확인합니다.
7. 로그·지표·경보가 정상임을 확인합니다.
8. 실제 RPO·RTO를 기록합니다.
9. 이전 호스트 없이 롤백·재배포할 수 있습니다.

## 2. 사용하면 안 되는 것

- 기존 호스트의 파일을 즉석에서 복사
- `latest` 태그
- 개인 PC에만 있는 비밀값
- 기억에 의존한 수동 설정
- 검증되지 않은 가장 최근 백업
- `curl -k`만 사용하는 성공 판정
- 운영 DNS를 먼저 바꾸고 나중에 검증
- 복구 중 운영 환경의 외부 부작용을 제한 없이 실행

숨은 의존성을 찾아내는 것이 이 최종 실습의 목적입니다.

## 3. 시작 전 증거 묶음

### 릴리스

```text
릴리스 매니페스트
이미지 다이제스트와 레지스트리 위치
소스 리비전
스키마·설정 호환 범위
SBOM·provenance 검증 결과
이전 롤백 가능 릴리스
```

### 인프라

```text
지원 OS와 호스트 크기
필요한 공개·관리 포트
Docker·Compose 설치 절차
호스트 디렉터리와 권한
systemd 또는 시작 정책
방화벽·IPv6 정책
```

### 신원과 비밀값

```text
SSH 관리자 키
레지스트리 pull 자격 증명
런타임 비밀값 원본 또는 재발급 절차
DNS API·관리 접근 권한
백업 복호화 키
ACME 계정 또는 재등록 절차
```

실제 값이 아니라 접근 경로와 소유자를 문서화합니다.

### 데이터

```text
선택한 백업 ID
매니페스트와 체크섬
DB 스키마 버전
업로드 스냅샷
복원 명령
기대 행·객체 검증값
```

### 운영

```text
외부 스모크 테스트
관측 엔드포인트
경보 테스트
사고 대응·롤백 런북
RTO·RPO 목표
연락 경로
```

## 4. 단계 0: 복구 선언

작업 시작 시각과 목표를 기록합니다.

```yaml
exercise_id: rebuild-2026-08-07
started_at: 2026-08-07T13:00:00Z
target_rto_minutes: 240
target_rpo_minutes: 1440
selected_release: 2026-08-01.2
selected_backup: 2026-08-07T020000Z
incident_commander: operator-a
```

복구 중 새 쓰기를 허용할지, 유지보수 페이지를 제공할지 정합니다.

## 5. 단계 1: 새 호스트 준비

- 기대한 OS·아키텍처 확인
- 업데이트와 재부팅
- 관리자 사용자·SSH 검증
- 시간 동기화
- Docker Engine·Compose 설치
- Docker daemon 접근 주체 확인
- 호스트 방화벽과 공개 포트 확인
- 운영 디렉터리와 권한 확인
- 디스크·inode 여유 확인

증거로 다음 정보를 남깁니다.

```text
os-release
Docker·Compose 버전
관리 사용자와 그룹
수신 대기 포트
방화벽 결과
파일 시스템 구성
```

설정을 변경한 뒤에는 별도 SSH 세션에서 다시 접속할 수 있는지 확인합니다.

## 6. 단계 2: 릴리스 획득과 검증

```text
매니페스트 서명·스키마 확인
→ 이미지 다이제스트 pull
→ provenance·SBOM 정책 확인
→ OCI 레이블과 소스 리비전 비교
→ 렌더링된 Compose 설정 확인
```

운영 호스트에서 소스를 빌드하지 않습니다.

```sh
docker compose config >/dev/null
```

모든 이미지가 매니페스트에 기록된 정확한 다이제스트인지 검사합니다.

## 7. 단계 3: 비밀값 주입

- 안전한 `umask` 사용
- 버전이 명시된 비밀값 파일 사용
- 소유자·그룹·권한 확인
- Compose가 요구하는 비밀값 이름 확인
- 값 자체는 로그에 출력하지 않음
- 폐기된 자격 증명이 아닌지 확인
- DNS·백업 자격 증명은 애플리케이션 컨테이너와 분리

비밀값이 누락되면 애플리케이션을 부분적으로 공개하지 않습니다.

## 8. 단계 4: 데이터 복원

DNS를 전환하기 전에 격리된 상태에서 수행합니다.

```text
백업 매니페스트 검증
→ 체크섬 확인
→ 복호화
→ 빈 DB·업로드 대상 준비
→ 복원
→ 스키마·행·객체 검증
→ 외부 부작용을 비활성화한 애플리케이션 시작
→ 내부 스모크 테스트
```

복원에 실패해도 백업 원본을 수정하지 않습니다. 다른 백업을 선택하면 RPO에 어떤 영향을 주는지 기록합니다.

## 9. 단계 5: 게이트웨이와 TLS

새 호스트를 임시 이름 또는 직접 주소로 검증합니다.

- 80·443 포트 접근
- ACME 검증 절차
- 호스트 이름 SAN
- 전체 인증서 체인
- 만료 시각
- HTTP→HTTPS 리디렉션
- 게이트웨이→애플리케이션→DB 경로

DNS 전환 전에 가능한 검사를 최대한 수행합니다. 공개 호스트 이름의 인증서를 발급하려면 DNS가 새 호스트를 가리켜야 하는 경우 TTL과 전환 시간대를 계획합니다.

## 10. 단계 6: DNS 전환

- 변경 전 레코드 저장
- A·AAAA 일관성 확인
- 새 IP 적용
- 권한 있는 네임서버 확인
- 여러 외부 리졸버에서 확인
- IPv4·IPv6 외부 요청 확인
- 이전 엔드포인트와 캐시 유지 시간 관찰

DNS가 전파되는 동안 이전 호스트가 없다면 유지보수 응답 또는 일부 실패를 수용해야 합니다. 이 시간도 RTO에 포함합니다.

## 11. 단계 7: 외부 기능 검증

다음 순서로 검사합니다.

```text
DNS
→ TCP 443
→ TLS 호스트 이름·체인
→ 게이트웨이 상태
→ 애플리케이션 준비 상태
→ 핵심 읽기
→ 격리된 안전한 쓰기
→ 쓰기 결과 재조회
→ 백그라운드 처리
```

성공 여부는 응답 코드뿐 아니라 필요한 응답 본문과 데이터 계약까지 확인해 판정합니다.

## 12. 단계 8: 관측과 경보

- 로그에 새 호스트·릴리스가 나타나는지 확인
- 요청 ID로 외부 스모크 테스트를 추적
- 지표 수집 또는 전송 성공 확인
- 외부 프로브 성공 확인
- 인증서 만료 지표 확인
- 백업 경과 시간 지표 확인
- 테스트 경보 전달 확인
- 호스트 디스크·메모리 관찰

관측 시스템이 새 호스트를 자동으로 발견한다고 가정하지 않습니다.

## 13. 단계 9: 운영 상태 확정

모든 검증이 끝난 뒤에만 다음 상태를 기록합니다.

```yaml
current_release: 2026-08-01.2
previous_release: null
host_id: provider-instance-...
public_ip: 198.51.100.20
activated_at: 2026-08-07T15:25:00Z
restored_backup: 2026-08-07T020000Z
external_smoke: passed
```

기존 호스트가 없더라도 레지스트리에 남아 있는 호환 릴리스를 별도의 롤백 대상으로 지정할 수 있습니다.

## 14. 실제 RPO와 RTO

### RPO

```text
장애 직전 마지막으로 확인된 정상 쓰기 시각
- 복원된 데이터의 최신 정상 쓰기 시각
```

### RTO

```text
복구 선언 시각
→ 외부 핵심 읽기·쓰기 성공 시각
```

목표를 초과했다면 숨기지 않고 그대로 기록합니다. 가장 오래 걸린 단계와 자동화 후보를 남깁니다.

## 15. 의도적 실패 주입

정상 재구축을 한 번 성공한 것만으로는 충분하지 않습니다. 다음 중 일부를 별도의 폐기 가능한 환경에서 재현합니다.

### 잘못된 이미지 다이제스트

사전 검사가 실행 상태를 변경하기 전에 거부해야 합니다.

### 누락된 비밀값

애플리케이션이 명확히 실패하고, 게이트웨이가 정상인 것처럼 핵심 기능을 제공하지 않아야 합니다.

### 손상된 백업

체크섬 또는 복원 검증 단계에서 중단해야 합니다.

### 인증서 호스트 이름 불일치

외부 스모크 테스트가 `-k` 없이 실패해야 합니다.

### 디스크 부족

복원하거나 이미지를 pull하기 전에 사전 검사에서 공간 부족을 발견해야 합니다.

### 잘못된 릴리스

현재 데이터와 호환되는 이전의 정확한 다이제스트로 롤백하고 외부 스모크 테스트를 다시 통과해야 합니다.

## 16. 호스트 폐기 검증

재구축을 마친 뒤 기존 호스트나 임시 복원 호스트를 폐기할 때는 다음을 확인합니다.

- DNS·트래픽이 더 이상 해당 호스트를 향하지 않음
- 필요한 로그·증거 보존
- 백업 스테이징 데이터의 외부 전송 완료
- 자격 증명 폐기
- 레지스트리·DNS·백업 접근 토큰의 회전 필요성 판단
- 공급자 볼륨·스냅샷 삭제 정책 적용
- 자산 목록에서 제거

호스트만 삭제하고 자격 증명이나 DNS 레코드를 남겨 두지 않습니다.

## 17. 산출해야 할 증거

압축 파일이나 학습 저장소에 실제 운영 비밀값을 넣지 않습니다. 별도의 접근 통제 위치에 다음을 보존합니다.

```text
실행한 런북 버전
릴리스·백업 매니페스트 다이제스트
단계별 시작·종료 시각
검사 명령과 민감 정보를 제거한 결과
실제 RPO·RTO
실패와 수동 개입
경보 테스트 결과
롤백 테스트 결과
후속 작업 담당자·기한
```

## 18. 최종 실습 평가 기준

### 재현성

다른 작업자가 문서와 필요한 권한만으로 같은 절차를 수행할 수 있습니다.

### 기준 원본

이미지, 설정, 비밀값과 데이터의 기준 원본이 명확합니다.

### 안전성

운영 전환 전에 격리된 환경에서 검증하고, 파괴적인 조치에는 안전 장치를 둡니다.

### 관측 가능성

각 단계의 성공·실패를 외부와 내부 증거로 확인할 수 있습니다.

### 복구 가능성

손상된 백업, 잘못된 릴리스, 누락된 비밀값을 안전하게 거부하거나 이전 상태로 되돌릴 수 있습니다.

### 명확한 한계

단일 호스트 구조의 중단 가능성과 잔여 위험을 숨기지 않습니다.

## 19. 자동 실습

[`exercises/18-production-rebuild`](../exercises/18-production-rebuild/)은 실제 VPS를 만들지 않습니다. 대신 완전한 재구축 계획과 증거 색인을 검사합니다.

자동 검증 항목은 다음과 같습니다.

- 단계 순서가 안전한가?
- 정확한 다이제스트와 백업 ID가 있는가?
- 비밀값이 포함되지 않았는가?
- DNS 전환 전에 복원과 내부 스모크 테스트를 수행하는가?
- 외부 TLS 검증에서 `-k`를 사용하지 않는가?
- RPO·RTO를 측정할 시각 정보가 있는가?
- 경보, 롤백, 손상된 백업에 대한 실패 훈련이 있는가?
- 각 수동 단계에 담당자와 중단 조건이 있는가?

이 검사를 통과한 뒤 실제 폐기 가능한 호스트에서 런북을 실행해야 최종 실습이 완료됩니다.

## 20. 과정 종료 질문

다음 질문에 정확한 경로와 증거로 답합니다.

1. 현재 운영 이미지 다이제스트는 무엇인가?
2. 호스트가 사라졌을 때 어느 백업과 릴리스를 선택하는가?
3. 복호화 키와 DNS 권한에 누가 접근할 수 있는가?
4. 데이터 복원 성공을 어떤 사용자 기능으로 확인하는가?
