# 멱등성과 단일 업무 효과

## 목표

전달 횟수를 통제하려는 시도와 업무 효과의 개수를 통제하는 설계를 구분하고, 요청·이벤트별 멱등성 키의 범위와 충돌 규칙을 정합니다.

## 문제

네트워크와 메시지 브로커는 다음 상황을 피할 수 없습니다.

```text
상태 변경 성공
→ 응답 또는 ACK 유실
→ 호출자나 브로커가 같은 입력을 다시 전달
```

전송 계층이 “한 번만 전달”을 제공하더라도 데이터베이스, 외부 API와 프로세스 재시작까지 하나의 원자적 경계로 묶지는 못합니다. 따라서 업무 효과가 하나만 남는지는 소비자가 직접 보장해야 합니다.

멱등성은 같은 입력을 여러 번 받았을 때 단순히 같은 HTTP 상태 코드를 반환하는 성질이 아닙니다. **같은 업무 연산의 최종 상태 변경과 외부 효과가 한 번만 생기고, 이후 호출자가 그 결과를 다시 확인할 수 있는 계약**입니다.

## 계약

### 키의 범위를 업무 연산과 맞춥니다

키는 문자열 하나가 아니라 다음 범위 안에서 해석됩니다.

```text
요청 주체
명령 종류
대상 자원
입력 지문
키의 보존 기간
```

`op-123`을 예약 생성과 예약 취소에 동시에 사용하거나, 같은 키에 다른 수량을 보내면 이전 결과를 잘못 재사용할 수 있습니다. 서버는 키와 입력 지문을 함께 저장하고 충돌을 거절합니다.

이벤트 처리에서는 발행자가 만든 `event_id`와 소비자가 수행하는 업무 연산 키가 다를 수 있습니다.

```text
event_id       = 전달 단위의 식별자
operation_key  = 업무 효과의 식별자
```

하나의 업무 효과가 여러 이벤트로 표현되거나 같은 이벤트가 여러 대상에 효과를 만들면 두 식별자를 구분해야 합니다.

### 중복 기록과 상태 변경을 같은 transaction에 둡니다

다음 순서는 안전하지 않습니다.

```text
업무 상태 변경
→ commit
→ 별도 transaction으로 processed_event 기록
```

첫 commit 뒤 프로세스가 멈추면 재전달된 이벤트가 상태를 다시 바꿉니다.

다음 중 하나를 사용합니다.

- 상태 변경과 `processed_event` 삽입을 같은 transaction에 둡니다.
- 업무 테이블의 고유 키가 중복 효과 자체를 거절하게 합니다.
- 상태 전이를 현재 버전과 함께 조건부 갱신합니다.
- 외부 효과는 별도의 Outbox와 멱등성 키로 전달합니다.

### 이전 결과를 저장합니다

중복 요청을 무시하기만 하면 호출자는 결과를 알 수 없습니다. 멱등성 레코드에는 다음을 남길 수 있습니다.

- 입력 지문
- 현재 상태
- 응답에 필요한 결과 식별자
- 생성·완료 시각
- 실패가 재시도 가능한지
- 보존 종료 시각

완료된 요청은 이전 결과를 반환합니다. 진행 중인 요청은 `PENDING`을 반환하며, 동일 키의 동시 실행을 막습니다.

### 외부 효과도 별도 경계로 검증합니다

이메일, 결제와 다른 서비스 명령은 로컬 DB transaction 안에 들어오지 않습니다. 외부 시스템이 멱등성 키를 지원하면 같은 키를 전달합니다. 지원하지 않으면 Outbox 상태와 외부 조회를 사용해 적용 여부를 확인해야 합니다.

“DB 행이 하나”만 확인하고 외부 결제가 두 번 실행되는 문제를 놓치면 단일 업무 효과가 아닙니다.

## 실패 조건

- 재시도마다 새 키를 만듭니다.
- 키만 비교하고 입력 지문을 비교하지 않습니다.
- 상태 변경 뒤 별도 transaction으로 처리 완료를 기록합니다.
- 중복 요청을 `200`으로 응답하지만 실제 결과를 반환하지 않습니다.
- 멱등성 레코드를 너무 일찍 삭제해 늦은 재전달을 새 요청으로 봅니다.
- event ID 중복 제거만으로 서로 다른 이벤트가 만드는 같은 업무 효과까지 안전하다고 가정합니다.
- 로컬 DB만 검사하고 외부 효과의 개수를 확인하지 않습니다.

## 검증

검사는 다음 실패 지점을 의도적으로 만듭니다.

```text
효과 적용
→ ACK 직전에 중단
→ 같은 event_id 재전달
→ 효과 횟수와 합계가 그대로인지 확인
```

동시 중복 요청도 확인합니다. 같은 키를 동시에 처리했을 때 둘 다 상태를 변경해서는 안 됩니다. 한 실행이 결과를 만들고 다른 실행은 그 결과를 관찰해야 합니다.

## 완료 조건

- 키의 주체·명령·대상·입력 범위를 정의할 수 있습니다.
- 같은 키와 다른 입력의 충돌을 거절합니다.
- 중복 기록과 상태 변경을 같은 transaction 경계로 설명할 수 있습니다.
- 로컬 상태와 외부 효과의 개수를 함께 검증합니다.
