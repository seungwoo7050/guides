# 읽기 모델, 지연 이벤트와 재구축

## 목표

원본 이벤트와 읽기 모델 사이의 지연·순서 역전·중복을 다루고, projection을 처음부터 재구축할 수 있는 계약을 설계합니다.

## 문제

읽기 모델은 여러 서비스의 데이터를 조회하기 편한 형태로 복제합니다. 그러나 복제본은 원본과 같은 시점의 상태를 보장하지 않습니다.

다음 상황이 정상적으로 발생할 수 있습니다.

- 생성 이벤트보다 상태 변경 이벤트가 먼저 도착합니다.
- 소비자가 중단된 동안 이벤트가 쌓입니다.
- checkpoint 저장 전후에 프로세스가 중단되어 이벤트가 다시 처리됩니다.
- 오래된 이벤트가 재전달됩니다.
- projection 코드가 바뀌어 전체 재구축이 필요합니다.

읽기 모델을 쓰기 판단의 정본처럼 사용하면 지연된 상태로 잘못된 결정을 내릴 수 있습니다.

## 계약

### 원본과 projection을 구분합니다

읽기 모델에는 다음 정보를 노출할 수 있습니다.

- 원본 aggregate의 버전 또는 sequence
- projection이 마지막으로 처리한 위치
- 갱신 시각
- 데이터가 불완전하거나 재구축 중인지
- 보류 중인 이벤트 수

강한 일관성이 필요한 명령은 원본 소유 서비스에서 판정합니다. 읽기 모델은 조회와 검색을 위해 사용합니다.

### 대상보다 먼저 온 이벤트를 버리지 않습니다

대상이 아직 없을 때 상태 변경 이벤트가 도착하면 다음 중 하나를 선택합니다.

- aggregate별 보류 저장소에 보관합니다.
- 원본 로그 위치를 남기고 나중에 다시 읽습니다.
- 일정 시간 뒤 정본을 조회해 전체 상태를 재구성합니다.
- 계약 위반으로 분류해 운영자에게 넘깁니다.

보류에는 최대 보존 기간과 처리 주체가 필요합니다. 영구히 쌓이는 보류 저장소는 복구 설계가 아닙니다.

### 적용과 checkpoint 순서를 지킵니다

일반적인 at-least-once 소비에서는 다음 순서가 안전합니다.

```text
이벤트 읽기
→ 멱등하게 projection 적용
→ 적용 결과 commit
→ checkpoint 전진
```

checkpoint를 먼저 전진시키면 적용 전에 중단된 이벤트를 잃습니다. 적용 뒤 checkpoint 전에 중단되면 같은 이벤트가 다시 처리되므로 projection 적용이 멱등해야 합니다.

### 재구축 가능성을 기본 요구사항으로 둡니다

projection은 파생 데이터입니다. 코드 또는 스키마가 바뀌면 다음 절차로 재구축할 수 있어야 합니다.

1. 새 projection 저장소를 만듭니다.
2. 고정된 시작 위치부터 이벤트를 재생합니다.
3. 현재 처리 위치와 lag를 기록합니다.
4. 원본과 핵심 합계·개수를 비교합니다.
5. 준비가 끝난 뒤 읽기 트래픽을 전환합니다.
6. 이전 projection을 일정 기간 보존합니다.

재구축 중 새 이벤트를 어떻게 따라잡을지도 정해야 합니다. snapshot과 로그를 함께 사용할 때는 snapshot 버전과 이후 시작 위치를 연결합니다.

## 실패 조건

- 대상이 없으면 이벤트를 버립니다.
- checkpoint를 projection 적용 전에 저장합니다.
- 재전달된 이벤트가 집계 값을 다시 증가시킵니다.
- 읽기 모델의 갱신 위치와 시각을 알 수 없습니다.
- projection을 처음부터 재구축하는 경로가 없습니다.
- 재구축 완료를 행 수 하나만으로 판단합니다.
- 지연된 읽기 모델을 수량 차감 같은 쓰기 판정에 사용합니다.

## 검증

다음 실패 지점을 검사합니다.

```text
이벤트 적용 뒤 checkpoint 전 중단
→ 재시작
→ 같은 이벤트 재처리
→ 최종 projection은 한 번만 반영
```

```text
checkpoint 전진 뒤 적용 전 중단을 주입
→ 이벤트가 유실되는 잘못된 구현을 검사가 탐지
```

전체 로그를 새 projection에 재생한 결과가 기존 정상 projection과 같아야 합니다.

- 빈 저장소에서 projection을 재구축하고 결과를 비교할 수 있습니다.
