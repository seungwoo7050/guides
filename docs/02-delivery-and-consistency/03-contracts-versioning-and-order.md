# 계약, 버전과 순서

## 목표

이벤트와 동기 API의 형식뿐 아니라 의미·호환성·순서 범위를 계약으로 만들고, 혼합 버전 배포와 순서 역전을 안전하게 처리합니다.

## 문제

직렬화가 성공했다고 계약이 호환되는 것은 아닙니다.

```json
{"amount": 1000}
```

위 필드가 원인지 센트인지, 세금 포함인지, 음수를 허용하는지 알 수 없다면 타입은 같아도 업무 의미는 다릅니다. 이벤트 채널 이름, 파티션 키와 enum 값도 계약의 일부입니다.

또한 분산 시스템에서 모든 이벤트의 전역 순서를 보장하는 것은 비싸고 대개 필요하지 않습니다. 실제로 필요한 것은 특정 aggregate나 업무 연산 안의 순서입니다.

## 계약

### 형식과 의미를 함께 공개합니다

계약에는 다음을 포함합니다.

- 이벤트 또는 API 이름
- 스키마 버전
- 필드 타입과 필수 여부
- 단위, 시간대와 정밀도
- enum의 확장 규칙
- `null`과 누락의 차이
- 키와 중복 판정 기준
- 순서를 보장하는 범위
- 보존·재처리 기간
- 생산자와 소비자의 책임

발행자 코드, 문서와 소비자 코드가 각자 문자열을 보관하면 조용한 drift가 생깁니다. 공개 계약 산출물이나 동일한 검증 규칙을 참조해야 합니다.

### 변경을 additive·breaking으로 분류합니다

일반적으로 소비자가 모르는 필드를 무시할 수 있다면 선택 필드 추가는 additive 변경입니다. 다음은 별도 검토가 필요합니다.

- 필수 필드 추가
- 필드 의미 또는 단위 변경
- enum 값 추가를 소비자가 거절하는 경우
- 필드 제거
- 같은 이름에 다른 업무 상태 사용
- 파티션 키 변경
- 순서 보장 범위 변경

호환성 검사는 JSON 모양만 비교하지 않고 이전 소비자가 새 이벤트를 처리하는 경우와 새 소비자가 이전 이벤트를 처리하는 경우를 모두 봅니다.

### 필요한 순서만 보장합니다

한 예약의 상태 전이가 순서대로 처리되어야 한다면 `reservation_id`를 파티션 키로 사용할 수 있습니다.

```text
reservation-1: CREATED(1) → ACCEPTED(2) → COMPLETED(3)
reservation-2: CREATED(1) → REJECTED(2)
```

서로 다른 예약 사이의 전역 순서는 필요하지 않습니다. aggregate별 sequence를 사용하면 소비자는 다음을 구분할 수 있습니다.

- 같은 sequence 재전달: 중복
- 다음 sequence: 적용 가능
- 더 큰 sequence: 중간 이벤트가 오지 않았으므로 보류
- 더 작은 sequence: 오래된 이벤트
- 지원하지 않는 schema version: 격리 또는 DLQ

### 동기 API도 혼합 버전을 견뎌야 합니다

롤링 배포 중에는 이전 생산자와 새 소비자, 새 생산자와 이전 소비자가 함께 실행됩니다. 동기 API도 응답 필드, 오류 코드와 enum 확장을 additive하게 설계하고, 제거 변경은 소비자 전환을 확인한 뒤 진행합니다.

consumer-driven contract는 모든 업무 의미를 대신하지 않지만 실제 소비자가 의존하는 응답을 배포 전에 확인하는 근거가 됩니다.

## 실패 조건

- 생산자와 소비자가 채널 이름을 각각 하드코딩합니다.
- 필드 타입만 같으면 의미도 호환된다고 봅니다.
- enum에 새 값이 오면 소비자가 예외로 중단됩니다.
- 파티션 키를 바꾸면서 순서 계약을 갱신하지 않습니다.
- arrival time으로 업무 순서를 결정합니다.
- 지원하지 않는 버전을 조용히 무시합니다.
- 전역 순서가 필요하지 않은데 단일 파티션으로 모든 처리를 직렬화합니다.

## 검증

검사는 다음 조합을 포함합니다.

- 이전 소비자 + 새 additive 이벤트
- 새 소비자 + 이전 이벤트
- 잘못된 채널 이름
- 지원하지 않는 schema version
- 같은 aggregate의 sequence `2 → 1 → 3`
- 같은 event ID 재전달
- 서로 다른 aggregate의 병렬 처리

적용·보류·중복 무시·격리 결과를 각각 확인합니다.
