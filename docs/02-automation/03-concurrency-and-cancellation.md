# 동시성, 취소와 자원 한계

## 학습 목표

병렬성은 기능을 완성한 뒤 독립 작업의 처리량을 높이기 위해 추가합니다. 이 장은 [`command-checker` 8단계](../../exercises/command-checker/README.md#8단계-병렬-실행과-원자적-보고서)와 연결됩니다.

## 선행 개념

- 완성된 순차 subprocess 계약과 mutable shared state의 race 위험

## 먼저 순차 계약을 완성합니다

다음이 순차 실행에서 결정적이어야 합니다.

- 한 사례의 입력과 결과
- 실패 메시지
- 모든 사례를 계속 실행할지 여부
- 결과 표시 순서
- 최종 종료 상태

이 경계가 틀린 상태에서 병렬화를 넣으면 경쟁 문제와 업무 규칙 오류를 구분하기 어렵습니다.

## thread, process와 async 선택

| 모델 | 적합한 작업 | 주의점 |
|---|---|---|
| `ThreadPoolExecutor` | 외부 프로세스·파일·네트워크 대기 | 공유 가변 상태, 종료와 예외 집계 |
| `ProcessPoolExecutor` | 독립적인 CPU 집약 계산 | 직렬화, 시작 비용, 프로세스 수명 |
| `asyncio` | 많은 비동기 I/O를 하나의 이벤트 루프로 조립 | 호출 스택 전체의 async 계약, 취소 처리 |

`command-checker`의 사례는 대부분 외부 프로세스를 기다리므로 thread pool이 단순합니다. Python bytecode CPU 연산을 빠르게 만들기 위해 thread를 늘리는 선택과는 다릅니다.

## 동시 실행 수를 제한합니다

```python
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=jobs) as executor:
    results = list(executor.map(run_one, cases))
```

`max_workers`는 1 이상이며 입력 수와 시스템 자원에 맞게 제한합니다. 사례 수만큼 무제한 thread나 프로세스를 만들지 않습니다.

## 완료 순서와 표시 순서를 구분합니다

병렬 작업은 완료 순서가 매번 달라질 수 있습니다. 보고서가 입력 순서를 계약으로 한다면 실행과 표시를 분리합니다.

```text
실제 완료 순서: 빠른 사례부터
최종 결과 순서: 명세에 기록된 순서
```

`executor.map`은 입력 순서대로 결과를 돌려줍니다. `as_completed`를 사용한다면 원래 index를 함께 보관해 재정렬합니다.

## 공유 상태를 줄입니다

각 작업이 다음을 공유하면 충돌할 수 있습니다.

- 같은 작업 디렉터리
- 같은 출력 파일
- 고정 포트
- 전역 환경 변수
- 가변 dict나 list
- 하나의 난수 생성기

병렬 실행은 격리를 제공하지 않습니다. 사례별 임시 디렉터리와 불변 입력을 사용하고, 결과는 반환값으로 모읍니다.

## 취소는 신호이지 완료가 아닙니다

Future에 취소를 요청해도 이미 실행 중인 외부 프로세스가 자동으로 사라지지는 않습니다. 각 작업이 자체 deadline과 프로세스 그룹 정리를 소유해야 합니다.

```text
상위 실행기 취소
→ 새 작업 제출 중지
→ 각 실행 중 작업에 deadline/취소 전달
→ 작업이 자원 정리
→ 결과 또는 취소 상태 집계
```

취소를 요청한 쪽이 자원을 직접 닫으면 작업 thread와 경쟁할 수 있습니다. 자원 소유자가 정리하는 경계를 유지합니다.

## timeout의 층위를 구분합니다

- 사례 timeout: 검사 대상 한 건의 deadline
- 전체 실행 timeout: 모든 사례를 포함한 작업의 상한
- 종료 유예: SIGTERM 뒤 정상 정리 기회

하나의 숫자를 모든 층위에 재사용하지 않습니다.

## 예외 집계

worker 예외를 첫 번째에서 즉시 다시 발생시키면 나머지 작업의 상태를 잃을 수 있습니다. 다음을 구분합니다.

- 예상 가능한 사례 불일치: `Result`
- 해당 사례의 실행 환경 오류: 호출자에게 예외
- 프로그래밍 오류: 숨기지 않고 전체 검증 실패

필요한 경우 어떤 사례가 어떤 예외로 실패했는지 보존합니다.

## 병렬 보고서 저장

각 worker가 같은 JSON 파일을 직접 갱신하지 않습니다.

```text
각 worker가 Result를 반환
→ 입력 순서로 전체 결과 확정
→ 한 곳에서 JSON/JUnit 직렬화
→ 임시 파일 완성
→ 최종 경로 교체
```

이 구조는 lock 범위를 줄이고 두 보고서가 같은 결과 집합을 사용하게 합니다.

## 결정적 테스트

`sleep` 길이만으로 순서를 추측하지 않습니다. 시작 barrier, 명시적인 event 또는 fixture 신호를 사용해 다음 상황을 재현합니다.

- 두 작업의 완료 순서 역전
- 하나의 worker 예외
- timeout과 정상 작업의 동시 존재
- 보고서 저장 실패
- 결과 순서가 입력 순서를 유지하는지

- 완료 순서와 최종 표시 순서를 구분합니다.
- 각 작업이 자신의 프로세스와 파일을 정리합니다.
