# 동시성, 취소와 자원 제한

## 학습 목표

동시 실행은 순차 동작이 완성되고 검증된 뒤 독립된 작업의 처리량을 높이기 위해 추가합니다. 이 장은 [`command-checker` 8단계](../../exercises/command-checker/README.md#8단계-병렬-실행과-원자적-보고서)와 연결됩니다.

## 선행 개념

- 외부 프로세스 한 건을 순차적으로 실행하는 동작이 완성되어 있어야 합니다.
- 가변 상태를 여러 스레드가 공유할 때 경쟁 상태가 발생할 수 있음을 이해해야 합니다.

## 순차 실행 규칙부터 완성하기

동시 실행을 추가하기 전에 다음 동작이 순차 실행에서 항상 같아야 합니다.

- 각 사례에 전달할 입력과 관찰할 결과
- 실패 메시지 형식
- 사례 하나가 실패해도 나머지를 계속 실행할지 여부
- 결과를 표시하는 순서
- 전체 종료 상태

순차 동작이 잘못된 상태에서 동시성을 추가하면 업무 규칙의 오류와 경쟁 상태를 구분하기 어렵습니다.

## 스레드, 프로세스, `asyncio` 선택하기

| 모델 | 적합한 작업 | 주의점 |
|---|---|---|
| `ThreadPoolExecutor` | 외부 프로세스·파일·네트워크 I/O 대기 | 공유 가변 상태, 종료 절차, 예외 집계 |
| `ProcessPoolExecutor` | 서로 독립적인 CPU 집약 계산 | 데이터 직렬화, 프로세스 시작 비용, 하위 프로세스 수명 |
| `asyncio` | 많은 비동기 I/O 작업을 하나의 이벤트 루프에서 처리 | 호출 경로 전체의 비동기 인터페이스, 취소 전파와 정리 |

`command-checker`의 각 사례는 대부분 외부 프로세스가 끝나기를 기다리므로 스레드 풀이 가장 단순합니다. 이는 CPython에서 Python 바이트코드로 수행하는 CPU 집약 작업을 스레드 수만 늘려 빠르게 만드는 경우와 다릅니다.

## 동시 작업 수 제한하기

```python
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=jobs) as executor:
    results = list(executor.map(run_one, cases))
```

`max_workers`는 1 이상이어야 하며 입력 크기와 시스템 자원에 맞게 제한해야 합니다. 사례 수만큼 스레드나 프로세스를 제한 없이 만들면 파일 디스크립터, 메모리, 프로세스 수 제한을 쉽게 초과할 수 있습니다.

## 완료 순서와 결과 순서 구분하기

동시에 실행한 작업은 매번 다른 순서로 끝날 수 있습니다. 보고서가 입력 순서를 보장해야 한다면 실행 완료 순서와 최종 결과 순서를 분리합니다.

```text
실제 완료 순서: 먼저 끝난 사례부터
최종 결과 순서: 명세 파일에 기록된 순서
```

`executor.map()`은 내부 작업의 완료 순서와 관계없이 입력 순서대로 결과를 반환합니다. `as_completed()`를 사용한다면 각 Future와 원래 인덱스를 함께 저장한 뒤 최종 결과를 재정렬해야 합니다.

## 공유 상태 줄이기

각 작업이 다음 자원을 공유하면 충돌할 수 있습니다.

- 같은 작업 디렉터리
- 같은 출력 파일
- 같은 고정 포트
- 프로세스 전역 환경 변수
- 가변 `dict`나 `list`
- 하나의 난수 생성기

동시에 실행한다고 해서 작업이 자동으로 격리되지는 않습니다. 사례마다 임시 디렉터리를 따로 사용하고, 입력은 불변 값으로 전달하며, 결과는 워커 함수의 반환값으로 수집합니다.

## 취소 요청과 정리 완료 구분하기

Future에 취소를 요청해도 이미 실행 중인 함수나 그 함수가 시작한 외부 프로세스가 자동으로 종료되지는 않습니다. 각 작업이 자체 제한 시간과 프로세스 그룹 정리 절차를 책임져야 합니다.

```text
상위 실행기에서 취소를 요청한다
→ 새 작업 제출을 중단한다
→ 실행 중인 작업에 취소 신호나 마감 시각을 전달한다
→ 각 작업이 자신이 연 파일과 프로세스를 정리한다
→ 완료·실패·취소 결과를 모은다
```

상위 실행기가 워커가 사용 중인 파일이나 파이프를 직접 닫으면 워커 스레드와 경쟁할 수 있습니다. 자원을 만든 코드가 정리하도록 책임을 유지합니다.

## 제한 시간의 종류 구분하기

- 사례 제한 시간: 검사 대상 한 건이 끝나야 하는 시각
- 전체 실행 제한 시간: 모든 사례를 포함한 작업 전체의 상한
- 종료 유예 시간: `SIGTERM`을 보낸 뒤 정상 정리를 기다리는 시간

의미가 다른 세 시간 제한에 하나의 숫자를 무조건 재사용하지 않습니다.

## 워커 예외 모으기

첫 번째 워커 예외를 즉시 다시 발생시키면 아직 실행 중인 작업의 상태나 다른 실패 원인을 잃을 수 있습니다. 다음 상황을 구분해야 합니다.

- 예상 가능한 결과 불일치: `Result`로 반환
- 해당 사례를 시작하거나 관찰할 수 없는 실행 환경 오류: 예외로 전달
- 구현 자체의 프로그래밍 오류: 숨기지 않고 전체 검증 실패로 처리

예외를 모아 처리해야 한다면 어느 사례에서 어떤 예외가 발생했는지 함께 보존합니다.

## 병렬 실행 결과를 한곳에서 저장하기

각 워커가 같은 JSON이나 JUnit 파일을 직접 수정하게 해서는 안 됩니다.

```text
각 워커가 Result를 반환한다
→ 입력 순서에 맞춰 전체 결과를 확정한다
→ 한곳에서 JSON과 JUnit을 직렬화한다
→ 임시 파일을 완성한다
→ 최종 경로로 교체한다
```

이 구조는 잠금이 필요한 범위를 줄이고 JSON과 JUnit 보고서가 정확히 같은 결과 집합을 사용하도록 합니다.

## 동시성 테스트를 재현 가능하게 만들기

`sleep()` 시간만 조절해 작업 순서를 추측하면 느린 시스템이나 부하가 높은 환경에서 테스트가 간헐적으로 실패할 수 있습니다. 시작 배리어, `Event`, `fixture`가 보내는 명시적 신호를 사용해 다음 상황을 재현합니다.

- 두 작업이 입력 순서와 반대로 완료됨
- 워커 하나에서 예외가 발생함
- 제한 시간에 걸린 작업과 정상 작업이 함께 존재함
- 보고서 저장이 실패함
- 완료 순서와 관계없이 결과가 입력 순서를 유지함

## 연결 실습

- [command-checker 8단계](../../exercises/command-checker/README.md#8단계-병렬-실행과-원자적-보고서)에서 배리어와 이벤트로 완료 순서를 제어합니다.
- 제한된 워커 수, 실제 완료 순서, 최종 결과 순서를 서로 독립적으로 검증합니다.

## 완료 기준

- 순차 실행의 동작과 오류 처리가 먼저 완성되어 있습니다.
- 동시에 실행하는 작업 수가 제한되어 있습니다.
- 워커가 공유 보고서 파일을 직접 수정하지 않습니다.
- 실제 완료 순서와 사용자에게 표시할 결과 순서를 구분합니다.
- 각 작업이 자신이 만든 프로세스와 파일을 정리합니다.
- 취소 요청과 자원 정리가 끝난 상태를 구분합니다.
