# 스레드 동기화와 종료 설계: 공유 불변식·조건 변수·시간

스레드는 같은 프로세스의 주소 공간을 공유하면서 각각 독립적으로 실행되는 흐름입니다. 데이터를 쉽게 공유할 수 있는 만큼 경쟁 상태도 쉽게 발생합니다.

`pthread` 함수를 호출하는 문법보다 중요한 것은 **어떤 데이터를 어떤 동기화 규칙으로 보호할 것인지, 그리고 어떤 상태 전이까지 하나의 임계 구역에서 완료할 것인지**를 일관되게 설계하는 일입니다.

## 프로세스와 스레드

한 프로세스에 속한 스레드는 일반적으로 다음 자원을 공유합니다.

* 코드와 전역 객체
* 힙에 할당된 메모리
* 파일 디스크립터 테이블
* 프로세스 환경과 작업 디렉터리

반면 각 스레드는 별도의 스택, 레지스터와 실행 문맥을 가집니다.

지역 변수는 일반적으로 해당 스레드의 스택에 존재하지만, 그 주소를 다른 스레드에 전달하면 여러 스레드가 같은 객체에 접근할 수 있습니다.

프로세스끼리는 주소 공간이 분리되어 있어 데이터를 주고받으려면 IPC가 필요하지만, 같은 프로세스의 스레드는 동일한 객체에 직접 접근할 수 있습니다. 이러한 편의성은 동시에 데이터 경쟁이 발생하기 쉬운 이유이기도 합니다.

## 스레드 생성과 join

스레드가 실행할 함수는 다음과 같은 형태를 사용합니다.

```c
void *worker_main(void *opaque)
{
    struct worker_argument *argument = opaque;

    /* 작업 */
    return NULL;
}
```

`pthread_create`로 새로운 스레드를 생성합니다.

```c
pthread_t thread;
int error = pthread_create(&thread, NULL, worker_main, &argument);
```

많은 POSIX 시스템 호출이 실패할 때 `-1`을 반환하고 `errno`를 설정하는 것과 달리, `pthread` 함수는 일반적으로 오류 번호를 직접 반환합니다.

```c
if (error != 0)
{
    fprintf(stderr, "pthread_create: %s\n", strerror(error));
}
```

join 가능한 스레드는 `pthread_join`으로 종료를 기다리고 관련 자원을 회수합니다.

```c
error = pthread_join(thread, NULL);
```

join하지 않을 스레드라면 detach 정책을 명확히 정해야 합니다.

생성한 각 스레드에 대해 **누가 join하거나 detach할 것인지**를 정하는 것도 자원 소유권의 일부입니다.

## 스레드 인자의 수명

다음 코드는 잘못된 패턴입니다.

```c
for (int index = 0; index < count; index++)
{
    pthread_create(&threads[index], NULL, worker_main, &index);
}
```

모든 스레드에 동일한 루프 변수 `index`의 주소를 전달하고 있습니다.

작업 스레드가 실제로 값을 읽는 시점에는 `index`가 이미 다음 값으로 바뀌었을 수 있으며, 함수를 빠져나간 뒤라면 객체의 수명 자체가 끝났을 수도 있습니다.

각 스레드가 서로 다른 객체를 참조하도록 구성합니다.

```c
for (size_t index = 0; index < count; index++)
{
    arguments[index].id = index;
    pthread_create(
        &threads[index],
        NULL,
        worker_main,
        &arguments[index]
    );
}
```

호출자 스택에 있는 `arguments` 배열은 모든 작업 스레드가 사용을 마칠 때까지 유효해야 합니다.

인자를 동적으로 할당하고 작업 스레드가 직접 해제하도록 설계했다면, 어느 시점에 소유권이 작업 스레드로 이전되는지도 명확하게 정해야 합니다.

## 데이터 경쟁은 정의되지 않은 동작입니다

두 스레드가 동기화 없이 같은 메모리 위치에 접근하고 그중 적어도 하나가 값을 변경한다면 데이터 경쟁(data race)이 발생할 수 있습니다.

```c
shared_count++; /* 읽기, 계산, 쓰기로 이루어진 복합 연산 */
```

소스 코드에서 하나의 연산처럼 보이거나 특정 환경에서 실행 결과가 반복해서 정상적으로 나왔다고 해서 자동으로 동기화되는 것은 아닙니다.

데이터 경쟁은 단순히 "가끔 값이 틀릴 수 있는 문제"가 아니라 정의되지 않은 동작입니다.

따라서 먼저 공유 상태 자체를 줄이고, 가능한 데이터는 작업 스레드별로 분리합니다. 실제로 공유해야 하는 상태에는 뮤텍스, 조건 변수 또는 요구 사항에 맞는 C atomic을 사용합니다.

이 장에서는 뮤텍스를 이용해 공유 불변식을 보호하는 설계에 집중합니다.

## 뮤텍스의 생명주기

뮤텍스 역시 초기화와 사용, 해제라는 생명주기를 가집니다.

```c
pthread_mutex_t mutex;

int error = pthread_mutex_init(&mutex, NULL);
if (error != 0)
{
    /* 초기화 실패 */
}
```

초기화한 뮤텍스를 사용해 임계 구역을 보호합니다.

```c
pthread_mutex_lock(&mutex);

/* 임계 구역 */

pthread_mutex_unlock(&mutex);
```

더 이상 어떤 스레드도 해당 뮤텍스에 접근하지 않고, 뮤텍스가 잠겨 있지 않을 때 해제합니다.

```c
pthread_mutex_destroy(&mutex);
```

초기화하지 않은 뮤텍스나 아직 잠겨 있는 뮤텍스, 다른 스레드가 계속 사용할 가능성이 있는 뮤텍스를 해제해서는 안 됩니다.

따라서 상위 객체의 수명과 함께 뮤텍스의 초기화 상태도 관리해야 합니다.

정적 저장 기간을 갖는 단일 뮤텍스에는 `PTHREAD_MUTEX_INITIALIZER`를 사용할 수 있습니다. 반면 동적 배열이나 일부 요소만 초기화된 상태를 정리해야 하는 경우에는 명시적인 `init`과 `destroy`가 일반적으로 더 적합합니다.

## 뮤텍스는 특정 메모리를 자동으로 보호하지 않습니다

다음과 같이 뮤텍스와 데이터가 같은 구조체 안에 있다고 가정해 보겠습니다.

```c
struct account
{
    unsigned long id;
    long balance;
    pthread_mutex_t mutex;
};
```

`mutex`와 `balance`가 같은 구조체 안에 있다는 사실만으로 둘 사이에 특별한 관계가 생기는 것은 아닙니다.

프로그램 전체에서 일관된 보호 규칙을 지켜야 합니다.

```text
account.mutex는 account.balance와 관련 불변식을 보호한다.
balance를 읽거나 변경할 때는 항상 해당 mutex를 잠근다.
```

읽기 함수에도 같은 규칙이 적용됩니다.

```c
int account_get_balance(struct account *account, long *out_balance)
{
    long snapshot;

    pthread_mutex_lock(&account->mutex);
    snapshot = account->balance;
    pthread_mutex_unlock(&account->mutex);

    *out_balance = snapshot;
    return 0;
}
```

일부 경로에서만 잠금을 사용하고 다른 경로에서는 값을 직접 읽는다면 보호 계약은 이미 깨진 것입니다.

"읽기만 하므로 안전하다"는 가정도 다른 스레드가 동시에 값을 변경할 수 있다면 성립하지 않습니다.

## 임계 구역은 불변식을 기준으로 정합니다

다음 두 작업을 각각 별도의 임계 구역에서 수행하면 두 작업 사이에 다른 스레드가 개입할 수 있습니다.

```text
잔액이 충분한지 확인
잔액을 차감
```

검증과 변경이 하나의 상태 전이라면 하나의 임계 구역 안에서 완료해야 합니다.

```c
pthread_mutex_lock(&account->mutex);

if (account->balance >= amount)
{
    account->balance -= amount;
    result = 0;
}

pthread_mutex_unlock(&account->mutex);
```

여러 필드가 함께 하나의 불변식을 구성한다면 관련된 읽기와 쓰기도 함께 보호해야 합니다.

또한 임계 구역 안에서 외부 콜백, 느린 I/O 또는 다른 계층에서 잠금을 획득하는 함수를 호출하면 예상하지 못한 대기나 복잡한 잠금 순서가 생길 수 있습니다.

가능하면 이러한 작업은 임계 구역 밖으로 옮기고, 반드시 필요한 경우에는 잠금 관계를 명시적인 계약으로 관리합니다.

## 두 객체의 잠금과 교착 상태

계좌 간 이체처럼 두 객체의 상태를 동시에 변경해야 하는 작업에서는 두 계좌를 함께 잠가야 전체 잔액 합과 같은 불변식을 보호할 수 있습니다.

하지만 잠금 순서가 다르면 교착 상태(deadlock)가 발생할 수 있습니다.

```text
스레드 A: 계좌 1 잠금 → 계좌 2 잠금
스레드 B: 계좌 2 잠금 → 계좌 1 잠금
```

각 스레드가 상대방이 보유한 잠금을 기다리면 어느 쪽도 진행할 수 없습니다.

이를 피하려면 모든 스레드가 동일한 전역 순서에 따라 잠금을 획득해야 합니다.

```text
항상 작은 account ID를 먼저 잠그고 큰 ID를 나중에 잠근다.
```

```c
struct account *first = source->id < destination->id
    ? source : destination;

struct account *second = source->id < destination->id
    ? destination : source;
```

서로 관련 없는 객체의 포인터를 `<`로 비교해 잠금 순서를 결정하는 것은 이식 가능한 일반 규칙이 아닙니다.

잠금 순서를 정하려면 명시적이고 유일한 ID나 상위 컨테이너의 인덱스처럼 안정적인 기준을 사용하는 편이 명확합니다.

두 인자가 실제로 같은 객체라면 같은 비재귀 뮤텍스를 두 번 잠그지 않도록 별도로 처리해야 합니다.

반대로 서로 다른 객체가 같은 ID를 가진다면 전역 잠금 순서를 유일하게 정할 수 없으므로 이러한 상태를 허용하지 않도록 계약을 정할 수 있습니다.

## 이체는 하나의 원자적 상태 전이입니다

계좌 이체의 계약을 다음과 같이 정의할 수 있습니다.

```text
전제:
  amount >= 0
  두 객체가 초기화되어 있음
  서로 다른 객체라면 ID가 다름

성공 조건:
  source의 잔액이 충분함
  destination의 덧셈이 LONG_MAX를 넘지 않음

성공 결과:
  source -= amount
  destination += amount
  두 계좌의 잔액 합 보존

실패 결과:
  두 잔액 모두 호출 전과 동일
```

검증과 두 상태 갱신은 모두 두 뮤텍스를 보유한 상태에서 수행합니다.

`source`에서 먼저 금액을 차감한 뒤 `destination`의 오버플로를 발견한다면, 실패했을 때 상태를 원래대로 유지한다는 보장을 지킬 수 없습니다.

따라서 필요한 조건을 먼저 모두 검증한 뒤 두 값을 함께 변경합니다.

같은 계좌로 이체하는 경우에는 잔액이 충분하면 성공하지만 실제 상태는 바뀌지 않는 것으로 계약을 정할 수도 있습니다. 이 경우에는 동일한 뮤텍스를 한 번만 잠급니다.

## 여러 뮤텍스를 사용할 때의 해제 순서

두 번째 뮤텍스의 잠금에 실패했다면 이미 획득한 첫 번째 뮤텍스를 해제한 뒤 오류를 반환해야 합니다.

```c
if (pthread_mutex_lock(&first->mutex) != 0)
{
    return -1;
}

if (pthread_mutex_lock(&second->mutex) != 0)
{
    pthread_mutex_unlock(&first->mutex);
    return -1;
}
```

여러 잠금을 중첩해서 사용한다면 일반적으로 획득한 순서의 역순으로 해제하는 편이 제어 흐름을 이해하기 쉽습니다.

`unlock` 실패를 무시할 것인지 치명적인 상태로 처리할 것인지도 라이브러리의 오류 처리 정책에 따라 정해야 합니다.

뮤텍스의 소유권을 위반한 상태를 일반적인 입력 오류처럼 복구 가능한 상황으로 취급해서는 안 됩니다.

## 상태용 뮤텍스와 출력용 뮤텍스를 분리할 수 있습니다

느린 로그 출력을 잔액을 보호하는 뮤텍스 안에서 수행하면 다른 작업 스레드도 출력이 끝날 때까지 상태에 접근할 수 없습니다.

서로 다른 불변식을 보호한다면 뮤텍스를 분리할 수 있습니다.

```text
state mutex  잔액·큐·종료 플래그와 같은 업무 상태 보호
log mutex    여러 스레드의 한 줄 출력이 서로 섞이지 않도록 직렬화
```

뮤텍스를 지나치게 세분화하면 잠금 순서가 복잡해집니다. 반대로 모든 상태를 하나의 뮤텍스로 보호하면 불필요하게 넓은 범위에서 경합이 발생합니다.

따라서 뮤텍스는 코드의 함수 단위가 아니라 **보호해야 하는 불변식**을 기준으로 나눕니다.

로그에 현재 상태의 값이 필요하다면 상태 뮤텍스를 잠근 상태에서 필요한 값을 복사한 뒤 잠금을 풀고 출력할 수 있습니다.

이때 출력되는 값은 로그가 실제로 기록되는 시점의 최신 상태가 아니라, 값을 복사한 특정 시점의 스냅샷입니다.

## 조건 변수는 조건 그 자체가 아닙니다

뮤텍스는 여러 스레드가 동시에 공유 상태를 변경하지 못하도록 합니다.

조건 변수(condition variable)는 특정 상태가 만들어질 때까지 스레드가 효율적으로 기다릴 수 있도록 합니다.

```c
pthread_mutex_lock(&queue->mutex);

while (queue->length == 0 && !queue->closed)
{
    pthread_cond_wait(&queue->not_empty, &queue->mutex);
}

/* 조건을 다시 확인한 뒤 처리 */

pthread_mutex_unlock(&queue->mutex);
```

`pthread_cond_wait`는 대기 상태로 들어가면서 뮤텍스를 풀고, 깨어난 뒤에는 다시 뮤텍스를 획득한 상태로 반환합니다.

조건은 반드시 `if`가 아니라 `while`로 다시 검사해야 합니다.

* 허위 깨움(spurious wakeup)이 발생할 수 있습니다.
* 여러 대기자가 같은 상태 변화를 통지받을 수 있습니다.
* 깨어난 스레드가 다시 뮤텍스를 얻기 전에 다른 스레드가 상태를 먼저 소비할 수 있습니다.
* `signal` 자체는 과거의 상태 변화를 저장해 두는 큐가 아닙니다.

실제로 기다리는 조건은 `queue->length > 0`과 같은 공유 상태입니다.

조건 변수는 그 조건이 변했음을 알려 주는 수단일 뿐입니다.

## 종료 역시 하나의 상태 전이입니다

작업 스레드가 반복적으로 실행되는 프로그램에서는 단순히 스레드를 생성하는 것뿐 아니라 어떻게 종료할지도 설계해야 합니다.

예를 들어 다음과 같은 상태 전이를 둘 수 있습니다.

```text
RUNNING → STOP_REQUESTED → DRAINING → STOPPED
```

종료를 요청할 때는 공유 상태를 변경하고, 해당 상태를 기다리고 있는 스레드도 깨워야 합니다.

```c
pthread_mutex_lock(&state->mutex);

state->stopping = 1;
pthread_cond_broadcast(&state->changed);

pthread_mutex_unlock(&state->mutex);
```

종료 플래그만 변경하고 조건 변수를 깨우지 않으면 잠들어 있는 작업 스레드가 새로운 종료 상태를 관찰하지 못할 수 있습니다.

종료 정책에서는 적어도 다음 사항을 정해야 합니다.

* 새로운 작업의 수락을 언제 중단할 것인가?
* 큐에 남아 있는 작업을 모두 처리할 것인가, 버릴 것인가?
* 누가 모든 작업 스레드를 join할 것인가?
* 작업 스레드가 외부 I/O에서 블록된 상태라면 어떻게 깨울 것인가?
* 종료 도중 생성된 부분 결과를 어떤 상태로 남길 것인가?

`pthread_cancel`은 cancellation point와 cleanup handler를 포함해 고려해야 할 규칙이 많습니다.

초기 설계에서는 공유 종료 상태를 설정하고 작업 스레드가 이를 확인해 정상적인 제어 흐름으로 반환하도록 만드는 편이 단순합니다.

## 단조 시계와 wall clock

달력상의 시각과 경과 시간을 측정하는 시계는 구분해서 사용해야 합니다.

```c
struct timespec now;
clock_gettime(CLOCK_MONOTONIC, &now);
```

wall clock은 관리자에 의한 시각 변경이나 NTP 보정, 시스템의 시간 정책 등에 따라 값이 달라질 수 있습니다.

반면 타임아웃, 데드라인과 경과 시간을 계산할 때는 일반적으로 `CLOCK_MONOTONIC`처럼 시간의 진행을 측정하기 위한 시계를 사용합니다.

시간을 밀리초 단위의 정수로 변환한다면 다음 문제도 확인해야 합니다.

* `tv_sec * 1000` 계산의 오버플로
* 나노초를 밀리초로 변환하면서 생기는 정밀도 손실
* signed와 unsigned 타입의 혼합
* 데드라인을 더할 때 발생하는 자리 올림

가능하면 `struct timespec` 값을 그대로 유지하고, 비교·덧셈·차감을 담당하는 작은 헬퍼 함수를 두는 편이 안전합니다.

## 상대 sleep과 절대 데드라인

바쁜 대기(busy waiting)는 조건이 충족될 때까지 CPU를 계속 사용합니다.

```c
while (before_deadline())
{
    /* 아무것도 하지 않음 */
}
```

`nanosleep`을 사용하면 대기하는 동안 CPU를 다른 작업에 양보할 수 있지만 시그널에 의해 중단될 수 있습니다.

```c
struct timespec remaining = requested;

while (nanosleep(&remaining, &remaining) < 0 && errno == EINTR)
{
    /* 남은 시간만큼 다시 대기 */
}
```

주기적으로 실행되는 작업에서 매번 "작업을 마친 뒤 10ms 대기"하는 방식을 사용하면 작업 수행 시간과 스케줄링 지연이 매 주기마다 누적될 수 있습니다.

다음 절대 데드라인을 기준으로 실행 시점을 계산하면 이러한 누적 오차를 줄일 수 있습니다.

```text
next_deadline += period

현재 시각이 deadline보다 이르면:
    남은 시간만큼 대기

이미 deadline을 지났다면:
    정해 둔 지연 정책 적용
```

조건 변수의 timed wait가 어떤 시계를 기준으로 동작하는지도 확인해야 합니다. 환경에 따라 조건 변수의 속성을 설정해 monotonic clock을 사용할 수 있습니다.

## 뮤텍스가 일부만 초기화된 경우

뮤텍스 배열을 초기화하다가 `k`번째 요소에서 실패할 수 있습니다.

```c
size_t initialized = 0;

for (size_t index = 0; index < count; index++)
{
    int error = pthread_mutex_init(&items[index].mutex, NULL);

    if (error != 0)
    {
        while (initialized > 0)
        {
            initialized--;
            pthread_mutex_destroy(&items[initialized].mutex);
        }

        return error;
    }

    initialized++;
}
```

초기화에 성공한 뮤텍스의 개수를 추적하고 그만큼만 해제합니다.

아직 초기화되지 않은 객체에 `pthread_mutex_destroy`를 호출해서는 안 됩니다.

부분 초기화 실패는 "전체 객체가 만들어졌는가"만 확인해서는 처리할 수 없습니다. **어디까지 초기화에 성공했는지**도 상태의 일부로 관리해야 합니다.

## 일부 스레드만 생성된 경우

N개의 스레드를 만들던 중 `k`번째 `pthread_create`에서 실패할 수도 있습니다.

이 시점에는 앞에서 생성한 작업 스레드가 이미 실행되고 있습니다.

정리 순서는 다음과 같이 설계할 수 있습니다.

```text
종료 상태 설정
→ 잠든 worker 깨우기
→ 실제로 생성된 스레드만 join
→ worker 인자와 공유 자원 정리
→ 오류 반환
```

생성되지 않은 `pthread_t` 값에 대해 join을 시도해서는 안 됩니다.

작업 스레드가 시작 게이트에서 기다리는 구조라면 실패 경로에서도 해당 게이트를 열거나 종료 상태를 전달해야 합니다.

그렇지 않으면 이미 생성된 스레드가 게이트에서 영원히 기다리고, 이를 join하려는 스레드 역시 끝나지 않을 수 있습니다.

## 공정성, 기아와 성능

교착 상태가 없다고 해서 모든 스레드가 공정하게 실행된다는 뜻은 아닙니다.

한 스레드가 계속해서 잠금을 먼저 획득하면 다른 스레드가 오랫동안 실행 기회를 얻지 못하는 기아(starvation)가 발생할 수 있습니다.

기본 POSIX 뮤텍스가 강한 공정성을 보장한다고 가정해서는 안 됩니다.

필요하다면 다음 항목을 직접 측정합니다.

* 스레드별 작업 성공 횟수
* 평균·최대 잠금 대기 시간
* 임계 구역의 실행 시간
* 잠금 경합률
* 조건 변수의 wakeup 패턴
* 작업 분배의 불균형

`usleep(1)`과 같은 임의의 지연을 넣으면 특정 실행에서 잠금 경쟁 양상이 달라질 수는 있지만, 그것이 공정성을 보장하는 것은 아닙니다.

## 동시성 테스트는 실행 순서보다 불변식을 확인합니다

계좌 이체 프로그램이라면 다음과 같은 성질을 검사할 수 있습니다.

```text
모든 잔액은 음수가 아님
전체 잔액 합은 시작할 때와 동일
overflow 실패 뒤 두 잔액이 그대로 보존됨
모든 worker가 종료함
정해진 timeout 안에 실행이 끝남
```

여러 작업 스레드를 비슷한 시점에 실행하려면 barrier나 `mutex + condition variable`로 만든 시작 게이트를 사용할 수 있습니다.

단순히 `sleep`을 사용한 뒤 "아마 비슷한 시점에 시작했을 것"이라고 추정해서는 안 됩니다.

일정한 최종 잔액을 기대하는 테스트라면 양방향 이체 횟수와 초기 조건을 대칭적으로 구성할 수 있습니다.

중요한 것은 개별 스레드의 정확한 실행 순서를 고정하는 것이 아니라, 실행 순서와 관계없이 유지되어야 하는 불변식을 검사하는 것입니다.

## sanitizer와 도구의 한계

ThreadSanitizer는 다음과 같이 사용할 수 있습니다.

```sh
cc -fsanitize=thread ...
```

실제로 실행된 경로에서 데이터 경쟁을 찾는 데 유용하지만 다음 사실까지 증명하지는 않습니다.

* 모든 가능한 interleaving이 안전함
* 교착 상태가 존재하지 않음
* 업무 불변식이 올바름
* 기아가 발생하지 않음
* 타임아웃이 정확함

AddressSanitizer와 동시에 사용할 수 없는 환경이 많으므로 별도의 빌드 대상으로 두는 편이 좋습니다.

외부 타임아웃을 사용하면 프로그램이 무한히 대기하는 상황을 제한할 수 있지만, 정상적인 종료 논리가 올바르다는 사실 자체를 증명하는 것은 아닙니다.

각 도구가 발견할 수 있는 문제와 발견하지 못하는 문제를 구분해야 합니다.

## 객체 해제 계약

`account_destroy`를 호출하려면 다음과 같은 전제가 필요합니다.

```text
어떤 worker도 더 이상 account에 접근하지 않음
해당 mutex를 아무도 보유하지 않음
관련된 모든 worker가 join된 상태임
```

이러한 조건을 보장하지 않은 채 뮤텍스를 해제하고 `initialized` 플래그를 변경하면 다른 스레드가 이미 파괴된 동기화 객체에 접근할 수 있습니다.

해제 함수가 자신의 뮤텍스만 사용한다고 해서 객체 전체의 수명 문제를 해결할 수 있는 것은 아닙니다.

관련 스레드를 종료하고 객체에 더 이상 접근하지 못하도록 만드는 책임은 상위 소유자가 보장해야 합니다.

## 실습

[account-simulator](../../exercises/04-concurrency/01-account-simulator/README.md)에서 다음 내용을 구현하고 확인합니다.

* 계좌별 뮤텍스 초기화와 반복적인 해제 처리
* 잔액 읽기의 동기화와 출력 매개변수 보존
* 명시적인 ID를 기준으로 한 두 뮤텍스의 잠금 순서
* 같은 객체와 같은 ID를 가진 서로 다른 객체의 구분
* 잔액 부족·음수 금액·목적지 오버플로 검증
* 실패했을 때 두 잔액이 그대로 유지되는지 확인
* 같은 계좌로 이체할 때 하나의 잠금만 사용하는 처리
* 두 계좌의 합을 일관된 스냅샷으로 읽기
* 8개 작업 스레드의 양방향 반복 이체
* 조건 변수 기반 시작 게이트
* 전체 합과 개별 잔액에 대한 불변식
* 타임아웃, AddressSanitizer·UndefinedBehaviorSanitizer와 ThreadSanitizer

검사는 특정한 출력 순서가 아니라 상태 계약을 확인하는 데 초점을 맞춥니다.

기본 구현을 완료한 뒤 한 방향에서만 의도적으로 ID 잠금 순서를 어겨 보고, 타임아웃이나 ThreadSanitizer뿐 아니라 기본 불변식과 교착 상태 검사에서 문제가 어떻게 드러나는지 관찰합니다.
