# 성능식, CPI와 Amdahl의 법칙

성능 개선을 말하려면 어떤 작업량의 어떤 지표가 얼마나 바뀌었는지 먼저 고정해야 합니다. 클록 주파수, 소스 코드 줄 수 또는 벤치마크 한 번의 경과 시간만으로는 원인을 설명할 수 없습니다. 명령어 수, CPI, 클록 주기와 시스템 잡음을 분리해야 개선과 우연을 구분할 수 있습니다.

## 학습 목표

- CPU 시간, CPI, IPC, Amdahl과 AMAT의 단위와 가정을 구분합니다.
- 동일한 정답 검증과 반복 분포를 포함한 성능 근거를 기록합니다.

## 선행 개념

비율 계산과 ISA 수준의 명령 실행 흐름을 이해해야 합니다.

## 지연 시간과 처리량

### 지연 시간

작업 하나가 시작해서 끝날 때까지 걸린 시간입니다.

### 처리량

단위 시간에 완료한 작업 수입니다.

파이프라인은 여러 작업을 겹쳐 처리량을 높일 수 있지만 개별 작업의 지연 시간을 줄이지 않을 수 있습니다. 서버에서도 처리량이 늘어도 p99 요청 지연 시간이 나빠질 수 있으므로 두 지표를 섞지 않습니다.

## CPU 실행 시간의 기본 분해

대표적인 식은 다음과 같습니다.

```text
CPU time
= instruction count × cycles per instruction × clock cycle time
= instruction count × CPI / clock frequency
```

세 항은 독립적이지 않습니다.

- 복잡한 명령은 명령 수를 줄여도 CPI나 클록 주기를 늘릴 수 있습니다.
- 깊은 파이프라인은 높은 주파수를 얻는 대신 분기 예측 실패 비용을 늘릴 수 있습니다.
- 벡터화는 명령 수를 줄여도 메모리 대역폭이 병목이면 전체 개선이 작을 수 있습니다.

완성된 계산의 출력 형태는 reference source를 열지 않는 black-box oracle로 다음처럼 확인합니다.

```sh
python3 exercises/processor-model/reference/processor-model.py \
  perf cpu --instructions 1000000000 --cpi 2 --ghz 2
```

결과는 `2×10^9 cycles / 2×10^9 cycles/s = 1s`입니다.

## 평균 CPI

명령 종류별 비율과 CPI가 주어지면 가중 평균을 계산할 수 있습니다.

```text
average CPI = Σ(instruction fraction_i × CPI_i)
```

| 종류 | 비율 | CPI |
|---|---:|---:|
| ALU | 50% | 1 |
| 적재·저장 | 30% | 2 |
| 분기 | 20% | 3 |

```text
0.5×1 + 0.3×2 + 0.2×3 = 1.7
```

실제 비순차 실행 프로세서의 CPI는 명령마다 고정 비용을 더하는 것보다 복잡합니다. 캐시 실패, 의존성, 분기 예측 실패와 실행 포트 경쟁이 겹칩니다. 표는 원인을 분해하는 출발점이며 현대 CPU의 정확한 타이밍 모델이 아닙니다.

## IPC와 CPI

같은 측정 구간과 완료 명령 정의를 사용하면 다음 관계가 있습니다.

```text
IPC = instruction count / cycles
CPI = cycles / instruction count
```

명령 수가 0이 아니면 서로 역수입니다. 슈퍼스칼라 프로세서에서는 IPC가 1보다 클 수 있으므로 “명령 하나는 최소 한 사이클이므로 CPI는 항상 1 이상입니다”라는 주장은 단일 발행 스칼라 모델에만 맞습니다.

## 경과 시간과 CPU 시간

프로그램의 경과 시간에는 다음이 섞일 수 있습니다.

- 실제 CPU 실행
- 스케줄러에게 CPU를 받지 못한 시간
- 디스크·네트워크 I/O 대기
- 페이지 폴트 처리
- 다른 프로세스와 자원 경쟁
- 타이머 대기

CPU 아키텍처 개선을 평가하면서 네트워크 왕복이 대부분인 벤치마크를 사용하면 원인을 찾기 어렵습니다. 사용자 경험을 평가하면서 CPU 시간만 보면 I/O 병목을 놓칩니다.

| 질문 | 먼저 볼 지표 |
|---|---|
| 함수 계산 비용 | 프로세스·스레드 CPU 시간, 사이클, 명령 수 |
| 사용자가 기다린 시간 | 단조 증가 시계로 잰 경과 시간과 지연 분포 |
| 서버 수용량 | 처리량, CPU 사용률, 대기열 |
| 메모리 계층 영향 | 캐시·TLB 사건, 대역폭, 정지 관련 계수기 |

## 속도 향상률

```text
speedup = old time / new time
```

기존 10초, 개선 8초라면 speedup은 `1.25x`이고 시간 감소율은 20%입니다. “25% 빨라졌습니다”와 “시간이 20% 줄었습니다”를 같은 수치처럼 사용하지 않습니다.

비교할 때는 다음 조건을 고정합니다.

- 입력과 정답
- 컴파일러와 중요한 옵션
- 스레드 수와 CPU 배치
- 준비 실행과 반복 방식
- 측정 구간
- correctness 검사

최적화 뒤 결과가 달라졌다면 성능 비교가 아닙니다.

## Amdahl의 법칙

전체 시간에서 개선 가능한 비율을 `f`, 그 부분의 speedup을 `s`라고 하면 다음과 같습니다.

```text
overall speedup = 1 / ((1 - f) + f / s)
```

전체의 40%만 8배 빨라지면 다음 명령으로 계산할 수 있습니다.

```sh
python3 exercises/processor-model/reference/processor-model.py \
  perf amdahl --fraction 0.4 --speedup 8
```

개선 가능한 부분을 무한히 빠르게 해도 전체 speedup의 상한은 `1 / (1-f)`입니다. 40%만 개선하면 최대 약 `1.667x`입니다.

Amdahl의 법칙은 병렬화가 쓸모없다는 결론이 아니라 개선 대상을 프로파일로 확인하라는 경고입니다. 고정 작업량과 작업량을 함께 늘리는 측정은 가정이 다릅니다.

## AMAT

단일 캐시 수준의 평균 접근 시간은 다음처럼 근사할 수 있습니다.

```text
AMAT = hit time + miss rate × miss penalty
```

적중 시간 1ns, 실패율 5%, 실패 비용 80ns라면 평균은 5ns입니다.

```sh
python3 exercises/processor-model/reference/processor-model.py \
  perf amat --hit-time 1 --miss-rate 0.05 --miss-penalty 80
```

다단계 캐시는 각 수준의 조건부 실패율을 구분해 식을 중첩합니다. L2 실패율이 L2에 도달한 접근 가운데 실패한 비율인지 전체 메모리 접근 대비 비율인지 확인하지 않으면 같은 식에 넣을 수 없습니다.

비순차 코어는 여러 실패의 대기 시간을 겹칠 수 있으므로 AMAT가 곧 응용 프로그램의 정지 시간은 아닙니다. 대역폭이 포화되면 독립 실패도 서로 대기합니다.

## 벤치마크 설계

### 결과가 실제로 사용되게 합니다

컴파일러가 계산 전체를 제거하지 못하도록 체크섬이나 외부 관찰 결과를 남깁니다. 서로 다른 구현은 같은 체크섬을 만들어야 합니다.

### 단조 증가 시계를 사용합니다

시스템 시각 조정의 영향을 피하려면 경과 시간에 단조 증가 시계를 사용합니다. 너무 짧은 구간은 타이머 호출 비용과 해상도에 묻히므로 반복 횟수나 작업량을 늘립니다.

### 여러 번 측정합니다

한 번의 최솟값이나 평균만 남기지 않고 분포와 이상치를 확인합니다. 주파수 조절, 열 제한, CPU 이동과 백그라운드 작업이 결과를 흔듭니다.

### 순서를 바꿉니다

항상 A 뒤에 B를 실행하면 캐시 준비와 열 상태가 한쪽에 치우칠 수 있습니다. `A→B`, `B→A`를 교차하거나 프로세스를 분리하고 공유 상태를 기록합니다.

### 작업 집합을 정합니다

작은 입력은 L1에 들어가고 큰 입력은 메모리 대역폭을 사용할 수 있습니다. 어떤 계층을 관찰하는지 먼저 정합니다.

## 컴파일러가 만든 코드를 확인합니다

소스가 같아도 최적화 옵션에 따라 다음이 달라집니다.

- 반복문 펼치기
- 벡터화
- 함수 인라인
- 분기 제거
- 상수 접기
- 명령 선택

[분기 벤치마크](../../examples/branch-benchmark/README.md)는 조건문이 분기 없는 코드로 변환될 수 있음을 보여 줍니다. [벡터화 보고서](../../examples/vectorization-report/README.md)는 컴파일러가 성공·실패 이유를 기록하는 방법을 다룹니다.

“분기 예측기가 빨랐습니다”라고 결론 내리기 전에 실제 분기 명령이 남아 있는지 확인합니다.

## 하드웨어 계수기

Linux의 `perf stat`가 허용되는 환경에서는 다음과 같은 사건을 요청할 수 있습니다.

```sh
perf stat -e cycles,instructions,branches,branch-misses ./program
```

CPU와 커널 권한에 따라 사건이 없거나 계수기가 다중화될 수 있습니다. 사건 이름과 의미도 마이크로아키텍처에 따라 다릅니다.

1. 사건이 실제로 지원되는지 확인합니다.
2. 다중화 비율과 측정 구간을 확인합니다.
3. 사용자·커널·프로세스·시스템 전체 가운데 범위를 확인합니다.
4. 파생 비율의 분모가 같은지 확인합니다.
5. 소스·어셈블리·입력 패턴과 함께 해석합니다.

캐시 실패가 늘었다는 사실만으로 경과 시간 증가가 모두 그 실패 때문이라고 단정할 수 없습니다. 메모리 대기가 계산과 겹치거나 대역폭에 여유가 있을 수 있습니다.

## 직접 구현하기

workspace를 만든 뒤 `exercises/processor-model/workspace/processor_model/perf.py`에서 다음 세 함수를 완성합니다.

```text
cpu_time(instructions, cpi, frequency_ghz)
amdahl(fraction, enhanced_speedup)
amat(hit_time, miss_rate, miss_penalty)
```

구현 전에 단위를 고정합니다.

```text
frequency_ghz × 10^9 = cycles per second
CPU seconds = instructions × CPI / cycles per second
fraction ∈ [0, 1]
miss_rate ∈ [0, 1]
시간과 speedup 인자는 유한한 양수
```

`fraction == 1`이면 개선되지 않은 부분이 없으므로 무한 개선 상한을 유한한 수로 잘못 만들지 않습니다. NaN과 infinity도 정상 숫자로 통과시키지 않습니다.

현재 장까지의 누적 검사는 다음과 같습니다.

```sh
cd exercises/processor-model
make stage-03 EXERCISE_IMPL=workspace
```

이 대상은 1~3장의 `BitsTests`, `IsaTests`, `PerformanceTests`만 실행합니다. 아직 구현하지 않은 데이터패스와 파이프라인 모듈은 호출하지 않습니다.


“최적화 후 2배 빨라졌습니다”보다 동일한 체크섬, 입력 크기, 반복 분포, 옵션과 확인하지 못한 조건까지 남긴 기록이 반증 가능합니다.
