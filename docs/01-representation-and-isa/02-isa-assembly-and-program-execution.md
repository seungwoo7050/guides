# ISA, 어셈블리와 프로그램 실행

명령어 집합 구조(ISA)는 소프트웨어와 프로세서가 합의하는 경계입니다. 명령어 인코딩, 레지스터, 주소 계산, 예외와 메모리 연산의 의미를 정의합니다. 반면 명령어를 몇 단계 파이프라인으로 실행하는지나 캐시 크기가 얼마인지는 보통 ISA 계약 밖의 마이크로아키텍처 선택입니다.

## 학습 목표

- ISA, ABI와 마이크로아키텍처의 책임 경계를 구분합니다.
- 레지스터·PC·메모리의 변화를 명령 단위 상태 전이로 추적합니다.

## 선행 개념

고정 폭 정수와 바이트 순서를 이해하고 명령행에서 작은 프로그램을 실행할 수 있어야 합니다.

## ISA와 마이크로아키텍처를 분리합니다

같은 ISA 바이너리는 서로 다른 프로세서에서 실행될 수 있습니다.

```text
같은 ISA
├─ 작은 순차 실행 코어
├─ 넓은 비순차 실행 코어
└─ 모의 실행기 또는 가상 머신
```

모두 구조적으로 보이는 레지스터와 메모리 결과는 ISA가 정한 방식으로 보여야 하지만, 사이클 수와 내부 상태는 다를 수 있습니다. 특별한 구현을 지정하지 않고 “이 ISA 명령어는 항상 한 사이클입니다”라고 말할 수는 없습니다.

RISC-V 비권한 명세도 소프트웨어에서 관찰할 수 있는 명령을 정의하고 특정 캐시 줄 크기나 파이프라인 구현에 의존하지 않도록 설계됩니다. 이 가이드의 `Tiny-RISC`도 ISA 층의 의미를 다루지만 실제 RISC-V 인코딩을 구현하지는 않습니다.

## 레지스터는 이름 있는 작은 저장소입니다

레지스터 파일은 ALU 피연산자와 결과를 빠르게 주고받습니다. RISC 계열 ISA에서는 일반적으로 정수 레지스터를 고정 개수 제공하고, 명령 인코딩 안에 레지스터 번호를 넣습니다.

RISC-V RV32I에는 32개의 정수 레지스터가 있으며 `x0`은 항상 0으로 읽힙니다. MIPS의 `$zero`와 같은 역할입니다. ABI는 같은 물리 레지스터에 `sp`, `ra`, 인자 레지스터처럼 의미 있는 이름을 부여합니다.

레지스터 이름은 세 층을 구분해야 합니다.

- 인코딩의 레지스터 번호
- 어셈블리 문법의 ISA 이름
- ABI가 정한 역할 이름

ABI 역할은 함수 호출 규칙이고 명령 자체의 산술 의미와는 다릅니다.

## load/store 구조는 계산과 메모리 접근을 나눕니다

대표적인 RISC 명령 흐름은 다음과 같습니다.

```text
load:  memory → register
ALU:   register operands → register result
store: register → memory
```

메모리 안의 두 값을 바로 더해 메모리에 쓰는 복합 명령 대신, 적재 명령으로 레지스터에 가져와 계산하고 저장합니다.

```text
lw   r1, 0(r2)
add  r3, r1, r4
sw   r3, 0(r2)
```

`0(r2)`는 기준 레지스터 `r2`와 즉시값 오프셋 `0`을 더해 주소를 만드는 표기입니다. 실제 ISA마다 즉시값 폭, 부호 확장, 정렬과 예외 규칙이 다릅니다.

## 즉시값은 명령어 안에 들어가는 작은 상수입니다

명령 폭은 제한되어 있으므로 큰 상수를 한 명령에 모두 넣지 못할 수 있습니다. 어셈블러는 의사 명령 하나를 여러 실제 명령으로 확장할 수 있습니다.

```text
소스 어셈블리의 한 줄
≠ 반드시 기계어 명령 한 개
```

반대로 압축 명령처럼 같은 의미를 더 짧은 인코딩으로 표현하는 ISA 확장도 있습니다. 성능을 분석할 때는 소스 코드 줄 수가 아니라 실제 명령열을 확인해야 합니다.

## PC와 분기가 다음 명령어를 정합니다

프로그램 카운터는 다음에 가져올 명령 주소를 나타냅니다. 일반 명령은 다음 순차 주소로 진행하고 분기·점프·예외는 다른 주소를 선택합니다.

조건 분기를 개념적으로 쓰면 다음과 같습니다.

```text
if condition:
    PC = target
else:
    PC = next
```

ISA는 조건과 목적지 계산 방식을 정의합니다. 분기 목적지를 언제 알 수 있고 잘못 가져온 명령을 어떻게 버리는지는 [파이프라인과 위험 요소](../02-in-order-execution/05-pipeline-hazards-and-branching.md)의 마이크로아키텍처 문제입니다.

## 명령어 형식은 해석에 필요한 필드를 배치합니다

고정 폭 RISC 명령은 흔히 다음 정보를 포함합니다.

- 연산 코드
- 목적지 레지스터
- 소스 레지스터
- 즉시값 또는 기능 필드

모든 명령이 같은 필드를 같은 위치에 둘 필요는 없습니다. RISC-V는 R/I/S/B/U/J 형식으로 즉시값과 레지스터 필드를 재배치합니다. 공통 레지스터 필드 위치를 유지하면 해독 회로를 단순화할 수 있지만 즉시값을 조립하는 논리가 필요합니다.

이진 인코딩을 손으로 읽을 때는 다음 순서를 따르세요.

1. 명령 폭과 바이트 순서를 확인합니다.
2. 연산 코드 필드로 형식을 고릅니다.
3. 레지스터 필드와 기능 필드를 분리합니다.
4. 즉시값 조각을 명세의 순서대로 합칩니다.
5. 부호 확장과 정렬 단위를 적용합니다.

## 어셈블리, 목적 파일과 실행 파일은 서로 다릅니다

소스에서 프로세스가 되기까지의 대표 흐름은 다음과 같습니다.

```text
C/C++ 소스
→ 컴파일러가 어셈블리 또는 기계어 생성
→ 어셈블러가 재배치 가능한 목적 파일 생성
→ 링커가 심볼과 재배치 정보를 해결
→ 로더가 실행 구간을 주소 공간에 배치
→ 진입점부터 실행
```

### 어셈블러

레이블을 명령 주소로 바꾸고 명령 이름을 인코딩으로 변환합니다. 아직 최종 주소를 알 수 없는 참조는 재배치 정보로 남길 수 있습니다.

### 링커

여러 목적 파일과 라이브러리의 심볼을 연결하고 구역을 배치합니다. 정적 라이브러리에서 필요한 목적 파일을 고르고, 재배치 정보를 최종 주소에 맞게 적용합니다.

### 로더

운영체제가 실행 파일과 공유 라이브러리를 가상 주소 공간에 대응시키고 스택, 인자와 진입 상태를 준비합니다. 이 과정은 Unix 시스템 가이드의 프로세스·가상 메모리와 이어집니다.

“컴파일러가 실행 파일을 만듭니다”라는 표현은 편리하지만 어셈블러·링커·로더의 실패를 구분하기에는 부족합니다.

## ABI는 독립적으로 만든 코드가 함께 호출되게 합니다

ISA가 같아도 함수 인자, 반환값, 스택 정렬과 보존 레지스터 규칙이 다르면 목적 파일을 연결해 호출할 수 없습니다. 응용 프로그램 이진 인터페이스(ABI)가 이 규칙을 정합니다.

함수 호출에서 레지스터는 흔히 두 범주로 나뉩니다.

### 호출자가 보존하는 레지스터

호출한 함수가 값 보존이 필요하면 호출 전에 저장합니다. 호출받은 함수는 자유롭게 덮어쓸 수 있습니다.

### 호출받은 함수가 보존하는 레지스터

호출받은 함수가 사용했다면 반환 전에 원래 값을 복원합니다.

한 범주가 항상 더 빠른 것은 아닙니다. 함수의 호출 그래프와 레지스터 압박에 따라 저장 횟수가 달라집니다.

## 스택 프레임은 호출별 상태를 분리합니다

레지스터만으로 부족한 지역 값, 반환 주소, 보존할 레지스터와 인자 일부를 스택에 둘 수 있습니다.

```text
높은 주소
┌────────────────┐
│ caller frame   │
├────────────────┤
│ return/saved   │
│ local/spill    │ ← current frame
├────────────────┤
│ callee frame   │
└────────────────┘
낮은 주소
```

스택이 어느 방향으로 자라는지, 프레임 포인터를 항상 쓰는지, 반환 주소가 레지스터인지 메모리인지 등은 ISA와 ABI에 따라 다릅니다. 그림 하나를 모든 아키텍처의 물리 배치로 일반화하면 안 됩니다.

재귀 호출마다 독립된 프레임이 필요하지만, 컴파일러가 꼬리 호출로 프레임을 재사용하거나 지역 값을 레지스터에만 두면 소스와 스택 모양이 일대일로 대응하지 않습니다.

## 함수 호출을 명령어 수준으로 따라갑니다

다음 C 함수를 생각해 보세요.

```c
int add_one(int value)
{
    return value + 1;
}
```

어셈블리를 볼 때 다음 질문을 순서대로 답합니다.

1. 인자는 어느 레지스터 또는 스택 위치에 들어갑니까?
2. 반환 주소는 누가 만듭니까?
3. 지역 계산에 어떤 명령을 사용합니까?
4. 반환값은 어디에 둡니까?
5. 호출받은 함수가 보존해야 할 레지스터를 수정했다면 어디서 복원합니까?

짧은 함수는 인라인되어 호출 자체가 사라질 수 있으므로 컴파일러 선택 사항과 실제 심볼을 확인하세요.

## 시스템 호출은 일반 함수 호출과 다른 권한 경계입니다

일반 라이브러리 호출은 같은 권한 수준의 코드로 이동할 수 있습니다. 시스템 호출 명령은 정해진 레지스터와 트랩 방식을 사용해 커널로 제어를 넘깁니다.

```text
사용자 코드
→ 라이브러리 감싸기 함수
→ 시스템 호출 명령
→ 커널 처리기
→ 사용자 모드로 복귀
```

모든 `read()` 호출이 매번 동일한 시스템 호출 명령 하나와 일대일로 대응한다고 단정하지 마세요. 라이브러리 버퍼링, vDSO, 실행 환경의 감싸기 함수와 오류 처리가 사이에 있을 수 있습니다.

## Tiny-RISC로 구조적 상태를 관찰합니다

`Tiny-RISC`에는 `r0`부터 `r7`까지 8개 레지스터, 32비트 순환 정수, 리틀 엔디언 바이트 메모리와 다음 명령이 있습니다.

```text
li add addi sub and or xor
lw sw
beq bne j
halt
```

상세 계약은 [Tiny-RISC 명세](../../exercises/processor-model/spec/tiny-risc-isa.md)에 있습니다.

reference source를 열지 않고 Tiny-RISC 출력 계약만 관찰하려면 다음 black-box 명령을 사용합니다.

```sh
python3 exercises/processor-model/reference/processor-model.py \
  isa exercises/processor-model/fixtures/programs/sum.asm \
  --max-steps 100
```

결과에서 다음을 확인하세요.

- `r0`은 쓰기 명령 뒤에도 0입니다.
- 반복문의 분기가 PC를 되돌립니다.
- `sw`와 `lw`가 같은 32비트 값을 공유합니다.
- 반복문 때문에 명령 수와 소스 코드 줄 수가 다릅니다.

## 실제 컴파일러 출력을 확인하는 절차

호스트 컴파일러가 제공되면 작은 함수를 어셈블리로 만들 수 있습니다.

```sh
cc -O2 -S example.c -o example.s
```

다만 호스트가 x86-64라면 RISC-V나 MIPS 어셈블리가 나오지 않습니다. 교차 컴파일러가 없다면 호스트 출력에서 다음 일반 요소만 관찰하세요.

- 적재·저장과 산술 연산의 구분
- 비교와 제어 이동
- 호출 전후 레지스터와 스택 변화
- 반복문의 역방향 분기

명령 이름을 다른 ISA에 그대로 대응시키기보다 의미와 데이터 흐름을 먼저 비교하세요.

## ISA 문서를 읽는 순서

공식 명세 전체를 처음부터 외우기보다 한 명령을 다음 순서로 추적하면 됩니다.

1. 피연산자와 결과 폭
2. 소스·목적지 레지스터
3. 즉시값 조립과 확장
4. 주소와 정렬
5. 예외 조건
6. PC 변화
7. 메모리 순서 또는 원자성 조건
8. 권한 수준 제한

어셈블리 문법 설명만 읽으면 예외와 메모리 순서를 놓치기 쉽습니다.

## 직접 확인할 문제

1. `x0` 또는 `$zero`처럼 0 레지스터가 있으면 어떤 명령열이 단순해지는지 예를 들어 보세요.
2. 의사 명령 한 줄을 명령 한 개로 세면 안 되는 이유를 설명해 보세요.
3. 호출자가 보존하는 정책과 호출받은 함수가 보존하는 정책이 모두 필요한 이유를 호출 그래프 관점에서 설명해 보세요.
4. `lw`가 정렬되지 않은 주소에서 실패할 때 ISA 폴트와 C의 잘못된 포인터 문제를 구분해 보세요.
5. 같은 ISA의 두 프로세서가 다른 파이프라인과 캐시를 가져도 같은 실행 파일을 실행할 수 있는 이유를 설명해 보세요.
