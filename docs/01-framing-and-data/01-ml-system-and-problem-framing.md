# 모델이 아니라 의사결정 문제부터 정의하기

머신러닝 프로젝트는 “어떤 모델을 쓸 것인가”보다 먼저 **누가, 언제, 어떤 정보를 보고, 어떤 action을 바꾸려는가**를 정해야 한다. 이 계약이 없으면 높은 점수의 모델을 만들어도 실제 문제를 풀지 못한다.

## 1. 모델은 전체 시스템의 한 구성요소다

모델은 보통 다음 함수로 볼 수 있다.

```text
현재까지 관측한 입력 x
→ score 또는 확률 p
→ decision rule
→ action
→ 이후 관측되는 결과 y
```

여기서 모델은 `x → p`만 담당한다. 실제 제품 결과는 다음에도 좌우된다.

- 입력이 정확한 시점에 준비되는가
- score를 어떤 threshold로 action에 바꾸는가
- 사람이 예측을 따르거나 무시하는가
- action이 이후 label 자체를 바꾸는가
- 모델이 없는 기존 절차보다 나은가
- 잘못된 action의 비용과 복구 방법이 무엇인가

따라서 “정확도 90%”는 시스템 요구사항이 아니다. 어떤 모집단에서 어떤 시점의 어떤 label을 예측했고, 그 결과가 어떤 action을 개선했는지가 함께 있어야 한다.

## 2. Prediction contract

문제 정의 문서에는 최소한 다음 항목이 들어가야 한다.

| 항목 | 질문 |
|---|---|
| 대상 모집단 | 누구 또는 무엇을 예측 대상으로 삼는가? |
| 관측 단위 | 한 row는 사용자, 거래, 장치, 문서, 시점 중 무엇인가? |
| 관측 시점 | 모델이 예측할 때 실제로 알 수 있는 정보의 cutoff는 언제인가? |
| label | 무엇을 참으로 간주하며 누가 어떻게 기록하는가? |
| outcome window | 예측 시점 이후 어느 기간의 결과를 label로 삼는가? |
| horizon | 얼마나 먼 미래를 예측하는가? |
| action | score를 본 뒤 어떤 행동이 달라지는가? |
| 오류 비용 | false positive와 false negative의 비용은 각각 무엇인가? |
| abstention | 확신이 낮을 때 예측을 보류할 수 있는가? |
| latency | action 전에 결과를 언제까지 제공해야 하는가? |
| fallback | 모델이 없거나 입력이 불완전할 때 무엇을 하는가? |

예를 들어 “고객 이탈 예측”만으로는 부족하다.

```text
매주 월요일 00:00에 활성 유료 계정을 관측한다.
그 시점 이전 30일의 사용량과 장애 기록만 사용한다.
향후 30일 안에 자발적으로 유료 계약을 종료하면 positive label이다.
점수가 높은 계정은 고객 성공팀의 검토 queue에 들어간다.
계정을 자동 차단하거나 가격을 변경하지 않는다.
```

이 정의가 있어야 feature cutoff, split, metric과 monitoring을 설계할 수 있다.

## 3. 관측과 label 사이의 시간

가장 흔한 오류는 미래 정보를 과거 예측에 섞는 것이다. 다음 네 시점을 분리한다.

```text
t_observe    feature를 읽을 수 있는 마지막 시점
t_predict    모델을 실행하는 시점
t_act        action을 시작할 수 있는 시점
t_label      결과가 확정되는 시점
```

이상적인 관계는 다음과 같다.

```text
t_observe <= t_predict <= t_act < t_label
```

`refund_completed` 같은 feature가 label 확정 뒤에 기록된다면 학습 dataset에서 강한 신호로 보이더라도 실제 예측 시점에는 사용할 수 없다. timestamp가 존재한다는 사실만으로 안전하지 않다. 각 feature가 **언제 생성되고 언제 조회 가능해지는지**를 확인해야 한다.

## 4. 예측 문제와 의사결정 문제

분류 모델은 보통 score 또는 확률을 학습한다. 실제 action은 별도의 결정 규칙이다.

```text
통계 문제: P(y=1 | x)를 얼마나 잘 추정하는가?
결정 문제: 어떤 p에서 어떤 action을 선택하는가?
```

두 문제를 섞으면 다음 오류가 생긴다.

- 모델을 다시 학습해야 할 문제와 threshold만 바꿔도 되는 문제를 구분하지 못한다.
- 0.5를 자연법칙처럼 사용한다.
- 비용·capacity·사람 검토 가능량을 metric에서 제외한다.
- 같은 probability를 서로 다른 제품 환경에서 같은 action으로 사용한다.

모델은 가능하면 score를 제공하고, action 정책은 versioned configuration으로 분리한다.

## 5. 먼저 baseline을 정의한다

머신러닝 없이 가능한 기준을 적는다.

- 항상 다수 class 예측
- 최근 관측값 그대로 사용
- 간단한 업무 규칙
- 기존 사람 판단
- 현재 운영 중인 모델
- 무작위 또는 queue 순서

baseline은 낮은 점수를 만들기 위한 장식이 아니다. 새로운 시스템이 추가하는 비용과 위험을 정당화할 비교 대상이다.

다음 질문에 답하지 못하면 복잡한 모델을 시작하지 않는다.

```text
현재 절차의 비용과 품질은 무엇인가?
어떤 실패를 줄이려는가?
얼마나 개선돼야 개발·운영 비용을 정당화하는가?
모델이 틀렸을 때 기존 절차로 돌아갈 수 있는가?
```

## 6. 학습 가능한 문제인지 확인한다

모든 업무 문제가 예측 문제는 아니다.

### 규칙이 더 적합한 경우

- 요구사항이 명시적이고 거의 변하지 않는다.
- 오류를 설명하고 반드시 같은 결과를 내야 한다.
- 필요한 정보가 이미 완전하게 존재한다.
- 규칙 수가 작고 유지보수 가능하다.

### 검색·집계가 더 적합한 경우

- 정답이 기존 데이터에 직접 저장돼 있다.
- 모델이 아니라 query 또는 index가 필요하다.
- label을 예측할 이유가 없다.

### 인과 실험이 필요한 경우

- “누가 이탈할까?”가 아니라 “할인을 주면 이탈이 줄까?”가 핵심이다.
- 관측 데이터의 상관관계로 intervention 효과를 주장하려 한다.
- 과거 정책이 누구에게 action을 제공했는지 편향돼 있다.

### ML이 유용할 수 있는 경우

- 명시적 규칙으로 표현하기 어려운 반복 패턴이 있다.
- 과거 관측과 결과가 충분하며 생성 과정이 이해 가능하다.
- 확률적 오류를 허용하고 측정할 수 있다.
- 입력과 label이 운영 시점에도 같은 의미로 수집된다.
- 모델 결과가 실제 action과 연결된다.

## 7. 성공 조건을 여러 층으로 나눈다

### 데이터 성공

- 필요한 모집단과 기간을 포함한다.
- label이 일관되게 계산된다.
- 누락·중복·지연을 측정한다.

### 모델 성공

- 고정된 validation 계약에서 baseline보다 낫다.
- 중요한 slice에서 실패를 숨기지 않는다.
- calibration과 uncertainty가 사용 목적에 적합하다.

### 제품 성공

- action 이후 실제 비용·시간·사용자 결과가 개선된다.
- 사람 작업량과 false alarm이 감당 가능하다.

### 운영 성공

- 입력 schema와 artifact가 호환된다.
- latency·throughput·비용 budget을 지킨다.
- 장애 시 fallback과 rollback이 작동한다.

한 층의 성공을 다른 층의 성공으로 대체하지 않는다. offline AUC가 높다고 제품 성과가 자동으로 개선되지 않는다.

## 8. 비범위와 위험을 먼저 적는다

문제 문서에는 다음도 포함한다.

- 사용하면 안 되는 모집단
- 자동화하면 안 되는 action
- 사람이 최종 판단해야 하는 조건
- 입력이 부족할 때 보류하는 조건
- 알려진 편향과 대표성 부족
- 법률·정책·안전 검토가 필요한 영역
- 모델이 증명하지 못하는 인과 주장

비범위는 실패를 숨기는 면책 문구가 아니다. 모델의 유효 범위를 테스트와 운영 정책으로 제한하는 계약이다.

## 9. 대표적인 실패

### Model-first development

```text
“Transformer를 써 보자”
→ 맞는 dataset을 찾는다
→ 점수를 만든다
→ 나중에 사용처를 고민한다
```

해결책은 architecture 선택 전에 problem contract와 baseline을 리뷰하는 것이다.

### Proxy label을 실제 목표로 오인

“불만 고객”을 직접 관측할 수 없어 “고객센터 연락”을 label로 사용하면, 연락하지 못하거나 다른 채널을 사용하는 집단이 빠진다. proxy가 무엇을 놓치는지 기록해야 한다.

### Action이 label을 바꾸는 피드백

모델이 high-risk 사용자에게만 지원을 제공하면 이후 label은 모델 정책의 결과를 포함한다. 다음 학습에서 “지원받은 사용자는 안전하다”는 잘못된 관계를 배울 수 있다.

### 단위 중복

한 사용자의 여러 row를 독립 표본으로 취급하면 평가 집합에 같은 사용자의 패턴이 들어가 과도하게 낙관적일 수 있다.

## 10. 리뷰 질문

- 예측 단위와 실제 action 단위가 같은가?
- feature cutoff 뒤에 생성된 정보가 들어갈 수 있는가?
- label이 누락되는 사람은 누구인가?
- baseline은 실제 운영 기준과 비교 가능한가?
- false positive·false negative·abstention 비용을 누가 부담하는가?
- model score와 action threshold의 소유자는 누구인가?
- 모델 없이도 풀 수 있는 규칙·query 문제는 아닌가?
- offline 성공이 어떤 online 가설로 이어지는가?
- 사용하지 말아야 할 범위를 코드와 정책으로 강제할 수 있는가?
