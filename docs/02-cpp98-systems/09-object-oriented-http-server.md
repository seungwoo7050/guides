# HTTP 서버의 객체 경계

## 서버 내부의 책임을 나눕니다

소켓 서버의 모든 기능을 `Server` 클래스 하나에 넣으면 파서, 라우트 선택, 파일 접근, CGI와 연결 수명이 뒤엉킵니다. 바이트 스트림을 요청 객체로 바꾸는 단계부터 응답을 전송하는 단계까지 책임과 상태 소유자를 나눠야 실패 원인을 좁힐 수 있습니다.

## 요청과 응답이 이동하는 경로

```text
TCP 바이트 → HttpDecoder → Request → ServerSelector/Router → Handler
                                                          ↓
TCP 바이트 ← ResponseWriter ← Response ←──────────────────┘

설정 → 파싱·검증 → 실행 시점 라우트
CGI 요청 → 자식 표준 입출력과 프로세스 수명 → Response
```

전송 계층, 프로토콜, 라우팅, 애플리케이션 동작과 프로세스 어댑터를 분리하면 각 실패를 독립적으로 검증할 수 있습니다.

## 사용 방법

다음 다섯 실습 디렉터리를 차례로 구현합니다. 각 단계의 테스트를 통과한 뒤 다음 단계로 이동합니다.

```text
1. 01-parser: 증분 HTTP 파서와 요청
2. 02-config-router: 설정 검증과 라우팅
3. 03-nonblocking-server: 논블로킹 연결과 최소 HTTP 처리
4. 04-cgi-process: CGI 프로세스와 제한 시간
5. 05-integrated-server: 파서·라우터·소켓·CGI 통합
```

처음 구현에서는 `Content-Length`로 길이가 정해진 본문만 지원해도 됩니다. `Transfer-Encoding: chunked`는 기본 구조가 안정된 뒤 확장합니다. 지원하지 않는 전송 인코딩은 모호하게 처리하지 말고 명시적으로 거부합니다.

## 1단계: 바이트 스트림에서 HTTP 요청까지

### 1. 전송 계층과 프로토콜의 경계

```text
소켓 읽기
→ Connection 입력 버퍼
→ HttpDecoder.feed(bytes)
→ 완성된 Request 또는 추가 입력 필요·오류
→ 애플리케이션
```

각 계층의 책임은 다음과 같습니다.

- `Connection`: 바이트를 읽고 쓰며 버퍼와 파일 디스크립터 수명을 관리합니다.
- `HttpDecoder`: 바이트 흐름을 HTTP 메시지의 경계와 필드로 해석합니다.
- 애플리케이션: 유효한 `Request`를 라우터와 핸들러에 전달합니다.

파서가 소켓에서 직접 `recv`하면 분할 입력 테스트가 어려워지고 다른 전송 계층에서 재사용할 수 없습니다.

### 2. 증분 파서의 반환 상태

한 번의 `feed`로 요청이 완성되지 않을 수 있습니다.

```cpp
class DecodeResult
{
public:
    enum Status
    {
        NEED_MORE,
        COMPLETE,
        ERROR
    };
};
```

파서가 유지해야 할 최소 상태는 다음과 같습니다.

```text
현재 파싱 단계
아직 소비하지 않은 바이트
현재 요청 줄
수집한 헤더
예상 본문 길이
현재까지 받은 본문 바이트 수
```

연결 유지를 지원하면 한 요청 뒤 남은 바이트가 다음 요청의 시작일 수 있습니다. 파서는 소비한 바이트 수를 반환하거나 내부에 잔여 바이트를 보존해야 합니다.

### 3. 요청 줄

요청 줄 형식은 다음과 같습니다.

```text
METHOD SP request-target SP HTTP-version CRLF
```

검증 항목:

- 필드가 정확히 세 개인지
- 메서드나 요청 대상이 비어 있지 않은지
- 지원하는 HTTP 버전인지
- 요청 줄 길이 상한을 넘지 않는지
- 허용하지 않는 제어 문자가 없는지
- 메서드 토큰 형식과 대소문자 정책이 명확한지

문법적으로 잘못된 메서드와 문법은 맞지만 지원하지 않는 메서드를 구분합니다.

```text
토큰 문법 오류                → 잘못된 요청
유효한 메서드지만 구현이 미지원 → 메서드 불허 또는 미구현
```

### 4. 헤더

헤더 필드는 이름, `:`, 값으로 구성됩니다.

```text
Host: example.test
Content-Length: 12
```

다음 정책을 명시합니다.

- 헤더 이름은 대소문자를 구분하지 않습니다.
- 이름에 허용되는 문자를 제한합니다.
- 값 앞뒤의 선택적 공백 처리 방식을 정합니다.
- 구식 줄 접기 형식은 단순 구현에서 거부합니다.
- 같은 이름의 헤더가 반복될 때 결합·보존·거부 정책을 정합니다.
- 헤더 개수, 한 줄 길이와 전체 바이트 상한을 둡니다.
- HTTP/1.1 요청에서 `Host` 요구사항을 검사합니다.

단순 구현에서는 소문자로 정규화한 이름을 `std::map<std::string, std::string>`에 저장할 수 있습니다. 다만 중복이 의미 있는 헤더를 무조건 마지막 값으로 덮어쓰면 안 됩니다.

### 5. 본문 프레이밍

HTTP 메시지의 본문 길이는 소켓 읽기 경계가 아니라 프로토콜 필드로 결정됩니다.

첫 구현의 범위:

- 본문이 없는 요청
- `Content-Length`가 있는 고정 길이 본문
- 최대 본문 크기
- 길이보다 적게 받았으면 `NEED_MORE`
- 정확한 길이를 소비하면 요청 완료

검증 항목:

- `Content-Length`가 부호 없는 10진수 형식인지
- 대상 크기 타입의 범위를 넘지 않는지
- 중복 길이 값이 충돌하지 않는지
- 설정된 본문 상한을 넘지 않는지
- 헤더와 본문 일부가 같은 읽기에 들어오는지
- `Transfer-Encoding`과 `Content-Length`가 함께 온 모호한 요청을 거부하는지

`recv == 0`을 본문 완료로 해석하지 않습니다. 고정 길이 본문이 덜 온 상태에서 상대가 닫으면 불완전한 요청입니다.

### 6. 청크 전송 본문은 확장으로 두기

기본 파서가 안정된 뒤 다음 상태를 추가합니다.

```text
chunk-size 줄
→ 청크 데이터
→ 청크 뒤 CRLF
→ 다음 크기
→ 크기 0인 마지막 청크
→ 선택적 trailer
```

검증 항목:

- 16진수 청크 크기 형식
- 청크 확장 처리 정책
- 각 청크와 전체 본문 상한
- `Content-Length`와 함께 온 경우의 거부 정책
- 마지막 청크와 trailer의 정확한 종료

처음부터 청크 전송까지 구현하면 파서 상태와 라우팅·핸들러 오류를 동시에 디버깅하게 됩니다. 고정 길이 본문 테스트를 통과한 뒤 추가합니다.

### 1단계에서 확인할 동작

다음 입력을 소켓 없이 `feed` 호출만으로 검증합니다.

- 요청 줄이 여러 조각으로 나뉘어 들어옴
- 여러 헤더가 한 번에 들어옴
- 헤더와 본문 일부가 같은 조각에 들어옴
- 한 `feed`에 요청 두 개가 들어옴
- 너무 긴 요청 줄이나 헤더
- 잘못된 `Content-Length`
- 본문 상한 초과
- 본문이 덜 온 상태의 EOF

## 2단계: 요청과 응답을 안정된 타입으로 만들기

### 7. 원시 문자열을 의미 있는 타입으로 변환하기

```cpp
class Request
{
public:
    const std::string &method() const;
    const std::string &target() const;
    const HeaderMap &headers() const;
    const std::string &body() const;

private:
    // 파서나 빌더만 생성하도록 제한할 수 있습니다.
};
```

핸들러가 원시 입력 버퍼나 파서 내부 상태를 보지 않게 합니다. `Request`가 생성됐다면 지원 범위 안의 최소 HTTP 문법 검증이 끝났다고 믿을 수 있어야 합니다.

필요하면 다음 개념을 값 객체로 분리합니다.

- `Method`
- `RequestTarget`
- `HttpVersion`
- `HeaderName`
- `StatusCode`

모든 문자열을 작은 클래스로 바꾸지는 않습니다. 반복되는 검증을 모으거나 잘못된 조합을 실제로 막는 타입만 만듭니다.

### 8. 직렬화 전 응답 상태

```cpp
class Response
{
public:
    Response(int status, const std::string &body);

    void setHeader(const std::string &name,
                   const std::string &value);

    int status() const;
    const HeaderMap &headers() const;
    const std::string &body() const;

private:
    int status_;
    HeaderMap headers_;
    std::string body_;
};
```

`ResponseWriter`가 최종 바이트를 만듭니다.

```text
Response
→ 상태 줄
→ 헤더
→ 빈 줄
→ 본문
```

`Content-Length`, 연결 종료 정책과 본문을 허용하지 않는 상태·메서드 규칙은 직렬화 경계에서 일관되게 처리합니다. 핸들러가 CRLF 문자열을 직접 조립하면 같은 응답 규칙이 여러 곳에 중복됩니다.

### 9. 오류를 세 계층으로 분리하기

| 계층 | 예 | 처리 결과 |
|---|---|---|
| 프레이밍·파싱 | 잘못된 요청 줄, 본문 길이 모순 | 프로토콜 오류 응답 또는 연결 종료 |
| 라우팅·애플리케이션 | 라우트 없음, 메서드 불허 | 안정적인 HTTP 상태 |
| 시스템·내부 | 파일 열기 실패, CGI 파이프 오류 | 내부 로그와 일반화된 서버 오류 |

파서는 라우트 존재 여부를 알지 않습니다. 파일 핸들러가 요청 프레이밍 오류를 판단하지 않습니다. 각 계층의 오류를 요청 처리 경계에서 `Response`로 변환합니다.

### 10. 연결과 요청 수명 분리하기

한 연결은 여러 요청을 순서대로 처리할 수 있습니다.

```text
Connection
├── 입출력 버퍼
├── HttpDecoder
├── 현재 요청 처리 상태
└── 종료 정책
```

`Request`는 HTTP 메시지 하나의 값입니다. 연결 파일 디스크립터, 유휴 제한 시간이나 상대 종료 상태를 요청 객체에 넣지 않습니다.

처음에는 요청 하나를 처리한 뒤 연결을 닫아도 됩니다. 다만 타입 경계가 이후 연결 유지 기능을 막지 않도록 구성합니다.

### 2단계에서 확인할 동작

- 파서 테스트가 소켓 없이 실행됩니다.
- 핸들러 테스트가 파서 없이 `Request`를 직접 만들어 실행됩니다.
- 응답 직렬화 테스트가 핸들러 없이 실행됩니다.
- 핸들러가 CRLF나 파일 디스크립터를 알지 않습니다.
- 연결이 라우트와 파일 경로 규칙을 알지 않습니다.

## 3단계: 설정과 라우팅

### 11. 설정을 모두 검증한 뒤 런타임에 반영하기

```text
설정 텍스트
→ 토큰
→ 문법 구조
→ 의미 검증
→ 불변 실행 설정
```

파싱하면서 현재 설정 객체를 한 항목씩 수정하면 마지막 오류에서 반쯤 바뀐 상태가 남습니다. 후보 설정을 완성하고 전체 검증이 성공한 뒤 `swap`으로 반영합니다.

### 12. 토큰화 도구의 책임

토큰화 도구는 의미를 판단하지 않고 최소 단위와 위치를 만듭니다.

```text
식별자
숫자
경로 또는 문자열
{
}
;
파일 끝
```

각 토큰에 줄과 열을 보존하면 파싱 오류를 구체적으로 보고할 수 있습니다. 주석과 따옴표 처리 규칙도 문법에 맞게 제한합니다.

### 13. 파서와 검증기의 책임

파서가 확인할 내용:

- 블록 구조
- 지시어 이름과 인자 목록
- `server`, `route` 같은 문법 단위

검증기가 확인할 내용:

- 포트 범위
- 필수 지시어
- 중복 수신 대기나 라우트
- 본문 상한 범위
- 허용 메서드 목록
- 루트·리다이렉트·CGI 설정의 모순

문법적으로 읽을 수 있다는 사실과 실행 가능한 설정이라는 사실을 구분합니다.

### 14. 서버 선택

하나의 리스너에서 여러 서버 설정을 사용할 수 있다면 다음 값으로 서버를 선택합니다.

- 실제 로컬 끝점
- 정규화한 `Host` 헤더
- 기본 서버

```cpp
const ServerConfig &selectServer(
    const Endpoint &local,
    const std::string &host,
    const Configuration &config);
```

호스트 이름의 대소문자, 선택적 포트와 IPv6 표기 정책을 명확히 합니다. 선택 함수에는 네트워크 객체 전체가 아니라 필요한 값만 전달합니다.

### 15. 라우트 선택

접두 경로 라우팅이라면 가장 긴 일치를 명시적으로 구현합니다.

```text
/          → 기본 라우트
/images    → 이미지 핸들러
/images/v2 → 더 구체적인 핸들러
```

단순 문자열 접두 비교만 사용하면 `/images2`가 `/images`에 잘못 일치할 수 있습니다. 경로 구성 요소 경계와 끝 슬래시 정책을 함께 검사합니다.

라우트 선택 결과는 별도 값으로 표현합니다.

```cpp
class RouteMatch
{
public:
    const RouteConfig &route() const;
    const std::string &remainingPath() const;
};
```

라우트 선택과 파일 시스템 접근을 섞지 않습니다. 선택된 라우트가 정적 파일, 리다이렉트나 CGI 중 어떤 핸들러를 사용할지는 다음 경계에서 결정합니다.

### 16. URL 경로와 파일 경로의 차이

요청 경로를 루트 문자열 뒤에 바로 붙이면 `..`, 중복 슬래시, 퍼센트 인코딩과 심볼릭 링크 때문에 문서 루트 밖으로 벗어날 수 있습니다.

필요한 처리 순서는 다음과 같습니다.

```text
요청 대상에서 경로와 질의 분리
→ 허용한 규칙으로 퍼센트 디코딩
→ 경로 구성 요소 정규화
→ 라우트 루트와 결합
→ 실제 접근 경로가 허용된 루트 안인지 확인
```

퍼센트 디코딩으로 `/`나 `..`가 새로 생길 수 있으므로 디코딩과 정규화 순서를 테스트로 고정합니다. 문자열 접두 비교만으로 루트 경계를 검사하면 `/var/www2`를 `/var/www` 아래로 오인할 수 있습니다. 심볼릭 링크를 허용할지, 존재하지 않는 대상의 상위 경로를 어떻게 검사할지도 명시합니다.

### 3단계에서 확인할 동작

- 설정 오류가 발생하면 현재 런타임 설정이 유지됩니다.
- 라우트 선택 테스트가 파일 시스템 없이 실행됩니다.
- 가장 긴 접두 경로와 구성 요소 경계가 결정적입니다.
- 경로 정규화가 루트 탈출을 거부합니다.
- 서버·라우트 선택이 이벤트 루프와 분리되어 있습니다.

## 4단계: 핸들러로 응답 만들기

### 17. 작은 핸들러 인터페이스

```cpp
class Handler
{
public:
    virtual ~Handler() {}
    virtual Response handle(
        const Request &request,
        const RouteMatch &route) = 0;
};
```

구체 구현은 파일 시스템이나 프로세스 실행기 같은 의존성을 생성자에서 받습니다. 전역 단일 객체나 서버 내부 상태를 직접 찾지 않게 합니다.

### 18. GET과 정적 파일

정적 파일 핸들러의 흐름은 다음과 같습니다.

```text
정규화된 경로 확인
→ 메타데이터 확인
→ 디렉터리와 색인 정책 적용
→ 파일 열기
→ 콘텐츠 타입 결정
→ Response 생성
```

작은 파일은 본문 문자열로 읽어도 됩니다. 큰 파일을 지원하려면 응답이 전체 본문을 메모리에 소유하는 모델 대신 파일 전송 상태를 연결의 출력 생산자와 이어야 합니다. 첫 구현에서 두 모델을 동시에 해결하지 않습니다.

검증 항목:

- 존재하지 않는 대상
- 디렉터리 요청
- 읽기 권한 없음
- 빈 파일
- 큰 파일
- 알 수 없는 콘텐츠 타입
- 파일 검사와 열기 사이에 대상이 바뀌는 경우

보안 판단을 메타데이터 검사 한 번에만 의존하지 않습니다. 가능한 경우 실제로 연 파일 디스크립터를 기준으로 후속 작업을 수행합니다.

### 19. POST와 업로드

POST가 항상 파일 업로드를 뜻하지는 않습니다. 구현 범위를 명확히 정합니다.

단순 업로드 핸들러라면 다음을 처리합니다.

- 파서 단계에서 본문 상한 적용
- 대상 경로 정규화
- 같은 디렉터리의 임시 파일에 쓰기
- 부분 파일 쓰기와 중단 처리
- 덮어쓰기 정책
- 성공 뒤 이름 교체
- 실패 시 임시 파일 정리

기존 파일을 먼저 지우고 새 내용을 쓰면 중간 실패 때 데이터가 사라질 수 있습니다. 후보 파일을 완성한 뒤 반영합니다. 이름 교체의 원자성과 전원 손실 뒤 내구성은 파일 시스템과 `fsync` 정책에 따라 별도 검토해야 합니다.

### 20. DELETE

DELETE 핸들러는 대상 확인과 삭제 정책을 분리합니다.

- 파일만 허용합니까?
- 디렉터리는 거부합니까?
- 존재하지 않는 대상은 어떤 상태를 반환합니까?
- 루트 밖 경로를 거부합니까?
- 심볼릭 링크 자체를 지웁니까, 링크 대상을 따릅니까?

삭제 전에 라우트와 경로 검증이 완료되어야 합니다. 검사와 삭제 사이의 변경 가능성도 고려합니다.

### 21. 리다이렉트와 오류 응답

리다이렉트 핸들러는 상태와 `Location` 헤더를 만듭니다. 사용자 정의 오류 페이지를 처리하다 다시 실패했을 때 같은 오류 핸들러를 재귀 호출하지 않도록 작은 기본 응답을 둡니다.

```text
원래 오류
→ 사용자 정의 오류 페이지 시도
→ 실패 시 내장 기본 본문
```

하위 계층이 HTTP 상태를 제각각 결정하지 않도록 오류 종류를 상태 코드로 변환하는 표를 애플리케이션 경계에 둡니다. 내부 경로나 시스템 오류 문자열은 외부 응답에 그대로 노출하지 않습니다.

### 22. 핸들러 선택

```text
RouteMatch
→ 리다이렉트 설정 여부
→ CGI 매핑 여부
→ 메서드별 핸들러
→ 정적 기본 처리
```

팩터리나 등록부가 구체 핸들러를 선택할 수 있습니다. 새 핸들러 추가가 이벤트 루프나 `HttpDecoder` 수정으로 이어지지 않는지 확인합니다.

### 4단계에서 확인할 동작

- 정적 GET, 단순 POST와 DELETE가 독립적인 핸들러 테스트를 가집니다.
- 핸들러는 소켓 파일 디스크립터를 받지 않습니다.
- 라우트 선택과 파일 접근이 다른 함수에 있습니다.
- 오류 상태 변환이 한곳에 모여 있습니다.
- 새 핸들러를 추가해도 `HttpDecoder`와 이벤트 루프가 바뀌지 않습니다.

## 5단계: CGI 프로세스를 이벤트 루프에 통합하기

### 23. CGI 프로세스 모델

```text
서버 부모 프로세스
├── 자식 표준 입력 파이프  ← 요청 본문
├── 자식 표준 출력 파이프 → CGI 출력
└── 자식 프로세스
```

필요한 시스템 호출:

- `pipe`
- `fork`
- 자식에서 `dup2`
- 사용하지 않는 파이프 끝 닫기
- `execve`
- 부모에서 파이프를 논블로킹으로 설정
- `waitpid(..., WNOHANG)`

CGI 프로세스를 생성했다고 요청 처리가 끝난 것은 아닙니다. 요청 본문을 모두 쓰고, 출력을 모두 읽고, 자식 종료 상태까지 회수해야 합니다.

CGI 환경 변수와 실행 인자는 검증된 요청·라우트 값에서 구성합니다. 사용자 입력을 셸 명령 문자열로 조립하지 말고 `execve`에 프로그램 경로와 인자 배열을 직접 전달합니다.

### 24. 파일 디스크립터 소유자 정리

| 파일 디스크립터 | 부모 사용 | 자식 사용 | 닫는 시점 |
|---|---|---|---|
| 표준 입력 읽기 끝 | 닫음 | 표준 입력으로 복제 | 자식에서 `dup2` 뒤 원본 닫기 |
| 표준 입력 쓰기 끝 | 요청 본문 전송 | 닫음 | 전송 완료·오류·취소 |
| 표준 출력 읽기 끝 | CGI 출력 수신 | 닫음 | EOF와 처리 완료 |
| 표준 출력 쓰기 끝 | 닫음 | 표준 출력으로 복제 | 자식에서 `dup2` 뒤 원본 닫기 |

`fork` 뒤 부모와 자식이 불필요한 파이프 끝을 닫지 않으면 읽기 측이 EOF를 영원히 받지 못할 수 있습니다.

### 25. 자식 생성 실패 경로

각 단계의 정리를 명시합니다.

```text
첫 파이프 성공
→ 둘째 파이프 실패
→ 첫 파이프 양 끝 닫기

파이프 생성 성공
→ fork 실패
→ 모든 파이프 닫기

자식에서 execve 실패
→ 제한된 진단 후 _exit
```

`fork` 뒤 자식에서는 복잡한 C++ 런타임 동작, 버퍼링된 iostream과 잠금 사용을 최소화하고 가능한 한 빨리 `execve`합니다. `execve` 실패 시 일반 `exit` 대신 `_exit`를 사용해 부모의 버퍼나 종료 처리기를 중복 실행하지 않습니다.

### 26. CGI 상태 객체

```cpp
class CgiProcess
{
public:
    enum State
    {
        WRITING_INPUT,
        READING_OUTPUT,
        WAITING_EXIT,
        COMPLETE,
        FAILED
    };

    // 자식 PID, 파이프 소유자, 오프셋, 기한과 출력 버퍼
};
```

클라이언트 `Connection` 하나가 CGI 파이프의 모든 세부 상태까지 직접 관리하지 않게 합니다. 다만 어떤 요청 작업이 어떤 CGI 프로세스와 연결되어 있는지는 상위 작업 객체가 소유해야 합니다.

입력 쓰기와 출력 읽기가 동시에 진행될 수 있으므로 상태를 단일 직선 단계로만 가정하지 않습니다. 구현이 두 방향을 동시에 다루지 않는다면 데드록을 피할 수 있는 본문 크기·처리 순서 제한을 명시해야 합니다.

### 27. 이벤트 루프 통합

`Poller`가 소켓 외의 파이프 파일 디스크립터도 다룰 수 있으면 같은 준비 상태 모델을 사용할 수 있습니다.

- 표준 입력 파이프 쓰기 가능 → 요청 본문의 일부 전송
- 표준 출력 파이프 읽기 가능 → 출력의 일부 수신
- 출력 EOF → 남은 출력 파싱과 자식 상태 확인
- 주기적 `waitpid(WNOHANG)` → 종료 상태 회수
- 기한 만료 → 자식 종료 정책 실행

블로킹 `waitpid`나 요청 본문 전체를 한 번에 쓰는 동작은 다른 클라이언트 처리를 멈출 수 있습니다.

제한 시간에 자식을 종료할 때는 신호 전송만으로 끝내지 않습니다. 필요하면 유예 뒤 강제 종료하고 반드시 `waitpid`로 회수해 좀비 프로세스를 남기지 않습니다.

### 28. CGI 출력 파싱

CGI 출력은 헤더와 본문 경계를 가집니다.

```text
Status: 201 Created
Content-Type: text/plain

본문
```

검증 항목:

- 헤더와 본문 구분자
- `Status` 형식과 범위
- `Content-Type` 기본값 또는 필수 정책
- 헤더와 전체 출력 상한
- 자식이 비정상 종료했지만 일부 출력이 있는 경우
- 헤더가 끝나기 전 EOF
- 서버가 직접 관리해야 하는 hop-by-hop 헤더 처리

CGI 출력을 곧바로 클라이언트 소켓에 전달하면 잘못된 헤더나 크기 상한을 검사하기 어렵습니다. 최소한 헤더가 완성될 때까지 별도 버퍼에서 해석합니다.

### 5단계에서 확인할 동작

- 모든 파이프 끝과 자식 PID의 소유자를 지목할 수 있습니다.
- 자식이 읽지 않을 때 표준 입력 쓰기가 다른 연결을 막지 않습니다.
- 자식 표준 출력이 여러 조각으로 도착해도 처리합니다.
- 제한 시간 뒤 자식 프로세스와 파이프가 남지 않습니다.
- `execve` 실패와 잘못된 CGI 출력이 안정적인 응답으로 변환됩니다.

## 6단계: 연결 유지, 제한 시간과 통합 검증

### 29. 연결 유지

응답을 모두 보낸 뒤 같은 연결에서 다음 요청을 처리할 수 있습니다.

필요한 상태:

```text
현재 요청을 처리 중입니까?
응답을 모두 전송했습니까?
디코더 버퍼에 다음 요청 바이트가 남아 있습니까?
요청이나 응답이 연결 종료를 요구합니까?
```

처음에는 한 요청의 응답을 완료하기 전 다음 요청을 디스패치하지 않는 순차 처리로 단순화할 수 있습니다. HTTP 파이프라이닝을 지원하지 않는다면 명시하고, 처리 중에도 입력 버퍼가 무한히 커지지 않도록 상한을 둡니다.

HTTP/1.1의 연결 유지 기본값과 `Connection: close` 처리를 일관되게 구현합니다. 지원 범위를 단순화해 항상 닫는다면 응답에도 그 정책을 명시합니다.

### 30. 제한 시간 종류 구분

| 제한 시간 | 보호 대상 |
|---|---|
| 요청 줄·헤더 제한 시간 | 헤더를 지나치게 천천히 보내는 클라이언트 |
| 본문 제한 시간 | 완료되지 않는 업로드 |
| 연결 유지 유휴 시간 | 사용하지 않는 연결 |
| CGI 제한 시간 | 끝나지 않는 자식 프로세스 |
| 출력 정체 시간 | 응답을 읽지 않는 클라이언트 |

하나의 `lastActivity`로 모든 의미를 섞으면 잘못된 시점에 연결을 닫을 수 있습니다. 작업별 시작 시각이나 기한을 상태에 둡니다. 경과 시간에는 시스템 시각 변경의 영향을 받지 않는 단조 시계를 사용합니다.

### 31. 책임 배치

프로젝트 규모에 따라 일부 객체를 합칠 수 있지만 다음 경계는 유지합니다.

| 객체 | 소유·책임 |
|---|---|
| `Listener` | 수신 대기 파일 디스크립터 |
| `Connection` | 클라이언트 파일 디스크립터, 바이트 입출력, 닫기 상태 |
| `Poller` | 운영체제 준비 상태 백엔드 |
| `HttpDecoder` | 증분 HTTP 파싱 상태 |
| `Request` | 완성된 요청 값 |
| `Configuration` | 검증된 서버·라우트 설정 |
| `ServerSelector` | 로컬 끝점과 Host로 서버 선택 |
| `Router` | 요청 경로로 라우트 선택 |
| `Handler` | 요청을 응답이나 비동기 작업으로 변환 |
| `CgiProcess` | 자식 PID와 파이프 I/O 상태 |
| `ResponseWriter` | 응답 직렬화 |

클래스 수를 맞추는 것이 목적은 아닙니다. 다음 책임이 뒤섞이지 않게 하는 것이 목적입니다.

- 파일 디스크립터 수명
- 프로토콜 파싱
- 서버·라우트 선택
- 파일·프로세스 같은 외부 동작
- HTTP 바이트 직렬화

### 32. 피해야 할 구조

- `Server` 하나가 소켓, 파서, 설정, 라우트, 파일과 CGI를 모두 담당
- 파서가 소켓에서 직접 읽기
- 핸들러가 원시 설정 텍스트를 다시 해석
- 라우트 선택 중 파일 시스템 접근
- 모든 오류를 연결 종료 하나로 처리
- 하위 계층이 HTTP 상태 줄과 헤더 문자열을 직접 조립
- 같은 파일 디스크립터를 연결, 서버와 CGI가 각각 소유한다고 가정
- 설정 파싱 중 현재 적용 중인 설정을 항목별로 수정

### 33. 테스트 계층

#### 순수 단위 테스트

- 토큰화 도구
- 설정 파서와 검증기
- 증분 `HttpDecoder`
- 라우트 선택
- 경로 정규화
- 응답 직렬화

#### 어댑터 테스트

- 임시 디렉터리를 사용하는 정적 파일 핸들러
- 업로드 실패 시 임시 파일 정리와 기존 파일 보존
- CGI 프로세스와 파이프
- 제한 시간 상태 전이

#### 소켓 통합 테스트

- 분할된 요청 줄·헤더·본문
- 같은 읽기에 여러 요청
- 여러 클라이언트
- 느린 수신자와 출력 상한
- 연결 유지
- 상대 종료

#### 블랙박스 테스트

실제 서버 프로세스를 시작하고 외부 클라이언트로 핵심 시나리오를 검증합니다. 준비 상태 확인, 제한 시간, 로그 수집과 종료 정리는 테스트 도구가 담당합니다. 임의의 `sleep`만으로 서버 준비를 추측하지 않습니다.

### 34. 웹 프레임워크로의 전이

직접 구현한 구성은 다른 객체지향 언어와 프레임워크에서도 대응할 수 있습니다.

| 직접 만든 서버 | 프레임워크에서 보이는 형태 |
|---|---|
| `Request` | 요청 객체 |
| `Router` | 라우팅 표 |
| `Handler` | 컨트롤러 또는 엔드포인트 |
| 핸들러 전후 처리 | 미들웨어 또는 필터 |
| `Response` | 응답 객체 |
| 애플리케이션 서비스 | 서비스 계층 |
| 저장 경계 | 저장소 인터페이스 |
| 설정 | 애플리케이션·서버 설정 |
| 이벤트 루프 | 런타임 또는 서버 구현 |

프레임워크는 HTTP 프레이밍과 연결 관리의 일부를 대신합니다. 그러나 라우트, 입력 검증, 서비스 책임, 오류 경계와 외부 자원 수명에 대한 판단은 그대로 필요합니다.

## 종합 구현 순서

1. 소켓 없는 `HttpDecoder`와 테스트
2. `Request`, `Response`, `ResponseWriter`
3. 연결당 요청 하나를 처리한 뒤 닫는 서버
4. 후보 설정 파싱·검증·반영
5. 서버와 라우트 선택
6. 정적 GET
7. POST 업로드와 실패 시 롤백
8. DELETE
9. 사용자 정의 오류와 리다이렉트
10. CGI 파이프 상태 관리
11. 연결 유지
12. 작업별 제한 시간
13. 다중 클라이언트 블랙박스 테스트

각 단계에서는 다음 단계의 기능을 미리 끌어오지 않습니다. 파서가 안정되기 전에 CGI를 붙이지 않습니다.

## 변경 요구사항으로 설계 검증하기

- 메모리만 사용하는 새 핸들러를 추가합니다.
- 라우트별 본문 상한을 다르게 설정합니다.
- 요청 로깅 데코레이터를 추가합니다.
- CGI 제한 시간 정책을 교체합니다.
- 정적 파일 읽기를 전체 메모리 적재에서 스트리밍으로 바꿉니다.
- 설정 다시 읽기에 실패하면 기존 설정을 유지합니다.

각 변경이 이벤트 루프, 디코더, 라우터와 핸들러 중 어디까지 퍼지는지 기록합니다. 기능과 무관한 계층까지 수정해야 한다면 책임 경계를 다시 검토합니다.

## HTTP 계층을 통합할 때 자주 발생하는 오류

- 한 번의 `recv`가 HTTP 요청 하나라고 가정합니다.
- 헤더가 완성되기 전에 라우트를 선택합니다.
- `Content-Length`의 형식과 범위를 검사하지 않습니다.
- `Transfer-Encoding`과 `Content-Length`의 모순을 허용합니다.
- `Request`가 파일 디스크립터와 연결 제한 시간까지 소유합니다.
- 설정 파싱 중 현재 적용 중인 설정을 수정합니다.
- URL 경로를 문서 루트와 문자열로 바로 이어 붙입니다.
- 파일 핸들러가 라우트 선택을 다시 수행합니다.
- CGI 파이프의 불필요한 끝을 닫지 않아 EOF가 오지 않습니다.
- 블로킹 `waitpid`로 전체 이벤트 루프를 멈춥니다.
- 연결 유지에서 디코더의 잔여 바이트를 버립니다.
- 모든 제한 시간을 하나의 활동 시각으로 처리합니다.
- 사용자 정의 오류 페이지 실패가 무한 재귀를 만듭니다.

## HTTP 서버 구조 점검

- `Connection`과 `Request`가 각각 어떤 상태를 소유합니까?
- 파서가 소켓 없이 테스트 가능합니까?
- 프레이밍 오류와 라우트 오류를 서로 다른 계층에서 처리합니까?
- 설정 전체가 성공하기 전 현재 런타임 상태를 건드리지 않습니까?
- 라우트 선택과 파일 시스템 접근이 분리되어 있습니까?
- CGI의 모든 파이프 끝과 자식 PID 소유자를 지목할 수 있습니까?
- 새 핸들러를 추가할 때 이벤트 루프와 `HttpDecoder`를 수정하지 않아도 됩니까?
- 연결 유지에서 다음 요청의 바이트를 잃지 않습니까?
- 이 구조를 다른 언어의 라우터·컨트롤러·서비스 구조와 대응할 수 있습니까?
