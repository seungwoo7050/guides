# 객체에 책임을 배치하는 법

## 코드가 커질수록 책임의 경계가 필요합니다

클래스를 만들 줄 알아도 프로그램이 객체지향적으로 설계되는 것은 아닙니다. 전역 상태를 클래스로 옮기고 모든 필드에 접근자와 설정자를 붙이면, 데이터는 객체 안에 있지만 규칙과 판단은 여전히 외부에 흩어집니다.

어떤 상태와 규칙이 함께 변하는지 찾고 그 불변식을 지킬 책임을 적절한 객체에 배치해야 합니다. 아래 요청 처리 흐름에서 각 객체가 알아야 할 정보와 변경 이유를 하나씩 나눠 봅니다.

## 요청을 처리하는 객체의 역할

```text
입력 → RequestParser → Request → CommandService → KeyValueStore
                                      ↓
                                  Response → Formatter → 출력
```

화살표마다 전달되는 값과 실패를 적고, 각 상자는 자기 불변식을 하나만 책임지게 합니다.

## 명령 서비스를 단계별로 분리

`../exercises/02-cpp98-systems/object-model/command-service/03-responsibilities`는 동작은 맞지만 책임이 뒤섞인 시작 코드와, 같은 입출력을 유지하면서 `RequestParser`, `KeyValueStore`, `CommandService`, `ResponseFormatter`로 분리한 참조 구현을 제공합니다.

```sh
cd ../exercises/02-cpp98-systems/object-model/command-service/03-responsibilities
make observe
make exercise-test
make test
make interface-check
```

`make interface-check`는 각 헤더를 외부 호출자처럼 포함하고 파싱, 저장,
서비스 실행과 응답 변환을 연결합니다. 파일 이름이나 특정 문자열을 찾는
검사와 달리 공개 타입이 실제로 함께 컴파일되고 같은 동작을 만드는지
확인합니다. 저장 용량 검사를 `main`으로 옮겨 본 뒤에도 이 검사가 어떤
설계 문제까지는 잡지 못하는지 함께 기록해 보세요.

## 1. 절차적 코드에서 시작하기

처음부터 완벽한 객체 구조를 설계하려 하지 않습니다. 먼저 작동하는 작은 흐름을 만든 뒤, 변경과 오류가 모이는 지점을 관찰합니다.

```cpp
void execute(
    const std::vector<std::string> &tokens,
    std::map<std::string, std::string> &values,
    std::ostream &out)
{
    if (tokens.empty())
        return;

    if (tokens[0] == "PUT")
    {
        if (tokens.size() != 3)
            out << "ERR arguments\n";
        else
            values[tokens[1]] = tokens[2];
    }
    else if (tokens[0] == "GET")
    {
        // 조회, 오류 처리, 출력이 한곳에 섞임
    }
}
```

이 코드는 작은 범위에서는 충분합니다. 문제는 기능이 늘면서 다음 변경 이유가 한 함수에 쌓인다는 점입니다.

- 입력 문법 변경
- 키 검증 규칙 변경
- 저장 정책 변경
- 응답 형식 변경
- 새 명령 추가

리팩터링은 “클래스를 많이 만드는 작업”이 아니라 이 변경 이유를 적절한 경계로 나누는 작업입니다.

## 2. 불변식부터 찾기

불변식은 공개 동작 전후에 항상 참이어야 하는 조건입니다.

예를 들어 키-값 저장소의 규칙이 다음과 같다고 하겠습니다.

```text
- key는 비어 있지 않습니다.
- key는 영문자, 숫자와 '_'만 포함합니다.
- 저장 가능한 항목 수에는 상한이 있습니다.
- 한 key에는 현재 값이 최대 하나입니다.
```

이 규칙을 모든 호출자가 반복 검사하게 하면 누락이 생깁니다. 키 생성과 저장소 변경 경로에 규칙을 모아야 합니다.

```cpp
class Key
{
public:
    explicit Key(const std::string &text);
    const std::string &text() const;

private:
    std::string text_;
};
```

`Key` 생성자가 성공했다는 사실만으로 형식이 유효하다고 믿을 수 있습니다. 이후의 객체는 같은 검사를 반복하지 않습니다.

## 3. 클래스를 찾는 기준

입력 문장의 명사를 전부 클래스로 만들지 않습니다. 다음 질문 중 여러 개에 답이 “예”라면 독립 객체 후보가 됩니다.

- 자기만의 불변식이 있습니까?
- 상태와 행동이 함께 변합니까?
- 독립된 수명을 가집니까?
- 다른 부분과 다른 이유로 변경됩니까?
- 별도로 테스트할 가치가 있습니까?
- 의미 있는 타입으로 표현하면 잘못된 조합을 막을 수 있습니까?

`Color`, `Manager`, `Data`처럼 이름만으로 책임을 알 수 없는 타입은 다시 검토합니다.

## 4. 상태와 행동을 함께 두기

다음 설계는 필드를 숨겼지만 규칙은 외부에 남아 있습니다.

```cpp
if (account.balance() >= amount)
    account.setBalance(account.balance() - amount);
```

동시에 두 호출이 들어오거나 중간에 규칙이 추가되면 모든 호출 지점을 찾아야 합니다. 객체에게 의미 있는 행동을 요청합니다.

```cpp
if (!account.withdraw(amount))
    return insufficientFunds();
```

이 방식의 장점은 단순히 코드가 짧다는 것이 아닙니다.

- 잔액 변경 경로가 한곳에 모입니다.
- 음수 금액, 수수료, 한도를 객체가 일관되게 검사합니다.
- 호출자는 내부 표현을 모릅니다.

이를 흔히 **Tell, Don’t Ask**라고 표현합니다. 절대 규칙은 아닙니다. 조회가 본질인 읽기 모델이나 화면 출력에서는 관측 함수가 필요합니다. 중요한 것은 상태를 꺼낸 뒤 외부에서 객체의 핵심 규칙을 다시 구현하지 않는 것입니다.

## 5. 접근자와 설정자를 추가하기 전에

```cpp
class Session
{
public:
    void setRegistered(bool value);
    void setNick(const std::string &nick);
    void setUser(const std::string &user);
};
```

이 API는 다음 잘못된 상태를 허용할 수 있습니다.

- nick이나 user가 없는데 registered가 true
- 이미 등록된 뒤 nick과 user가 모순되게 변경
- 등록 완료 이벤트가 여러 번 발생

상태 전이를 의미 있는 함수로 제한합니다.

```cpp
class Session
{
public:
    void setNick(const Nick &nick);
    void setUser(const UserInfo &user);
    bool completeRegistration();
    bool isRegistered() const;
};
```

`completeRegistration`은 필요한 정보가 모두 있는지 확인하고 한 번만 전이시킵니다.

## 6. 객체 사이의 협력

객체는 혼자 모든 일을 하지 않습니다. 각 객체가 작은 책임을 맡고 메시지를 주고받습니다.

```text
입력 문자열
→ RequestParser
→ Request
→ CommandService
→ KeyValueStore
→ Response
→ ResponseFormatter
```

각 경계의 질문은 다음과 같습니다.

- `RequestParser`: 문자열이 문법적으로 유효합니까?
- `Request`: 어떤 명령과 인자가 있습니까?
- `CommandService`: 요청을 어떤 도메인 동작으로 연결합니까?
- `KeyValueStore`: 저장 규칙과 현재 상태를 지킵니까?
- `ResponseFormatter`: 결과를 어떤 문자열로 표현합니까?

파서가 저장소를 직접 바꾸거나 Store가 스트림에 출력하면 변경 이유가 다시 섞입니다.

## 7. 조합을 기본 선택으로 사용하기

조합은 한 객체가 다른 객체를 멤버나 참조로 사용해 책임을 조합하는 방식입니다.

```cpp
class Application
{
public:
    Application(KeyValueStore &store, std::ostream &out)
        : store_(store), out_(out)
    {}

    void run();

private:
    KeyValueStore &store_; // 소유하지 않고 빌림
    std::ostream &out_;    // 소유하지 않고 빌림
};
```

조합은 다음을 분명하게 합니다.

- 포함된 객체의 수명 관계
- 외부에서 주입된 의존성
- 어떤 기능을 위임하는지
- 구현을 바꿀 수 있는 경계

코드 몇 줄을 재사용하려는 이유만으로 상속하지 않습니다. 상속은 다음 문서에서 대체 가능성의 계약으로 다룹니다.

## 8. 상태 전이 명시

여러 불리언으로 상태를 표현하면 불가능한 조합이 생기기 쉽습니다.

```cpp
bool connected;
bool registered;
bool closing;
```

세 값은 8개 조합을 만들지만 실제로 허용되는 상태는 훨씬 적을 수 있습니다.

```cpp
class ConnectionState
{
public:
    enum Value
    {
        ACCEPTED,
        REGISTERING,
        ACTIVE,
        CLOSING,
        CLOSED
    };
};
```

상태 기계를 설계할 때는 다음을 표로 적습니다.

| 현재 상태 | 이벤트 | 다음 상태 | 거부 조건 |
|---|---|---|---|
| ACCEPTED | 첫 정보 수신 | REGISTERING | 형식 오류 |
| REGISTERING | 필수 정보 완료 | ACTIVE | 중복 또는 누락 |
| ACTIVE | 종료 요청 | CLOSING | 없음 |
| CLOSING | 출력 완료 | CLOSED | 없음 |

객체는 허용된 전이만 공개 함수로 제공합니다. 상태 값 자체를 설정자로 노출하지 않습니다.

## 9. 응집도와 변경 이유

응집도가 높은 클래스는 관련된 상태와 동작을 함께 가집니다. 클래스가 다음 이유로 모두 변경된다면 책임이 너무 많습니다.

- 입력 문법 변경
- 저장 방식 변경
- 화면 출력 변경
- 네트워크 전송 변경
- 접근 권한 변경

클래스 크기보다 **서로 다른 변경 이유가 몇 개인지**가 더 중요합니다. 반대로 한 줄 함수마다 클래스를 만들면 흐름을 추적하기 어려워집니다. 분리는 독립된 규칙, 수명, 변경 또는 교체 가능성이 있을 때 합니다.

## 10. 계층 경계 좁히기

도메인 객체가 스트림, 소켓 파일 디스크립터나 파일 경로를 직접 알게 하면 테스트와 재사용이 어렵습니다.

```text
외부 표현 계층: 문자열, 파일, socket
응용 계층: 요청을 사용 사례로 연결
도메인 계층: 상태와 규칙
```

예를 들어 `KeyValueStore::put`은 `std::cout`에 오류를 출력하지 않습니다. 성공 여부나 도메인 결과를 반환하고, 외부 경계가 이를 문자열 또는 HTTP 상태로 바꿉니다.

## 11. 역할을 설명하는 용어

용어를 먼저 외우기보다 리팩터링한 객체를 분류하는 데 사용합니다.

### 값 객체

속성으로 구분되고 값이 같으면 동등합니다. 유효한 값만 만들며 복사 뒤 독립적입니다.

- `Key`
- `UserId`
- `Path`
- `Money`

### 식별자를 가진 객체

속성이 같아도 별개의 수명을 가집니다. 시간에 따라 상태가 변합니다.

- 연결
- 세션
- 주문

### 서비스

한 값 객체에 자연스럽게 속하지 않는 사용 사례를 조정합니다.

- 요청을 저장소 동작으로 연결
- 여러 객체가 참여하는 거래 수행

모든 로직을 `SomethingService`에 넣으면 도메인 객체가 빈 데이터 가방이 됩니다. 서비스는 조정하고, 개별 객체의 불변식은 객체 자신이 지킵니다.

## 12. 다른 객체지향 언어로 전이되는 원칙

| 원칙 | C++ 표현 | 다른 언어의 흔한 표현 |
|---|---|---|
| 유효한 값만 생성 | 생성자 검증 | 생성자, 팩터리, 레코드 검증 |
| 읽기 전용 경계 | `const T&`, `const` 멤버 | 불변 객체, 읽기 전용 속성 |
| 협력 구성 | 멤버와 참조 | 생성자 주입, 조합 |
| 상태 전이 제한 | 비공개 상태 + 의미 있는 함수 | 메서드, 리듀서, 상태 객체 |
| 값 객체 | 값 의미를 가진 클래스 | 레코드, 데이터 클래스, 구조체 |

문법이 달라도 “누가 규칙을 알고 누가 상태를 바꾸는가”라는 질문은 그대로 남습니다.

## 단계형 실습: 요청 처리기 리팩터링

### 시작 코드

한 함수가 입력 파싱, 저장소 변경과 출력까지 수행하는 절차적 프로그램에서 시작합니다.

### 1단계: 값 객체 추출

- `Key`
- `Value`
- `Request`
- `Response`

잘못된 키는 `Key` 객체가 되지 못하게 합니다.

### 2단계: 책임 분리

- `RequestParser`
- `KeyValueStore`
- `CommandService`
- `ResponseFormatter`

각 타입의 책임과 변경 이유를 한 문장으로 기록합니다.

### 3단계: 상태 규칙 이동

저장소 최대 크기, 중복 키 정책과 삭제 규칙을 `KeyValueStore` 안으로 이동합니다.

### 4단계: 출력 교체

텍스트 formatter를 JSON과 비슷한 formatter로 교체합니다. Store와 서비스는 수정하지 않습니다.

### 5단계: 변경으로 검증

다음 요구사항을 하나씩 적용하고 수정 파일을 기록합니다.

- 키 길이 상한 추가
- `PUT`의 덮어쓰기 금지
- 저장소 전체 읽기 전용 모드
- 출력 형식 변경
- 새 명령 `EXISTS`

같은 요구가 여러 계층을 불필요하게 바꾼다면 책임 경계를 다시 봅니다.

## 책임 분리 과정에서 생기는 혼선

- 모든 명사를 클래스로 만듭니다.
- 공개 접근자와 설정자로 비공개 필드를 그대로 노출합니다.
- 파서가 저장소와 출력까지 담당합니다.
- 모든 동작을 하나의 서비스에 모읍니다.
- 상속이 필요하지 않은 포함 관계를 상속으로 표현합니다.
- 상태를 여러 불리언으로 흩어 불가능한 조합을 허용합니다.
- 디자인 패턴 이름을 적용한 뒤 어떤 문제를 해결했는지 설명하지 못합니다.

## 객체별 책임 배치 점검

- 각 클래스가 지키는 불변식을 한 문장으로 쓸 수 있습니까?
- 한 상태 변경이 어느 공개 함수만 통과하는지 지목할 수 있습니까?
- 접근자를 추가하지 않고 객체에게 행동을 요청할 수 있습니까?
- 조합 관계의 소유자와 빌린 의존 관계를 구분할 수 있습니까?
- 새 요구사항 하나가 어느 객체만 변경해야 정상인지 예측할 수 있습니까?
- 절차적 버전보다 객체 버전이 실제로 해결한 문제를 설명할 수 있습니까?
