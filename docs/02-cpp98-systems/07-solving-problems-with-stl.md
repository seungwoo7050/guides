# STL로 문제를 해결하는 방법

## 자료구조보다 필요한 연산을 먼저 확인합니다

익숙한 컨테이너부터 고르면 주요 연산의 비용이나 순서 규칙이 요구사항과 어긋날 수 있습니다. 입력의 식별 방식과 불변식을 먼저 찾고, 평균·최악·상각 비용을 비교해 컨테이너와 알고리즘을 선택합니다.

## 요구사항에서 구현을 선택하는 과정

```text
불변식 → 주요 연산 → 규모·입력 경계 → 컨테이너 선택
       → 알고리즘 선택 → 복잡도 기록 → 정상·실패·경계 테스트
```

자료구조 이름부터 고르지 않습니다. 무엇을 얼마나 자주 해야 하는지 먼저 적습니다.

## 세 문제로 컨테이너 선택 연습

[STL 문제 해결 실습](../../exercises/02-cpp98-systems/generic-programming/stl-problems/README.md)에는 날짜 조회기, RPN 계산기와 레코드 정렬기가 독립된 실행 단위로 들어 있습니다.

## 1. 자료구조를 고르기 전에 적을 내용

```text
식별 방식: 위치, 키, 우선순위, 연결 관계 중 무엇입니까?
주요 연산: 어떤 연산이 얼마나 자주 일어납니까?
불변식: 순서, 중복, 안정성, 메모리 상한 중 무엇을 지켜야 합니까?
비용 경계: 평균 비용으로 충분합니까, 최악 지연이 중요합니까?
```

예를 들면 다음과 같습니다.

```text
불변식: 날짜 하나에는 값이 최대 하나입니다.
주요 연산: 입력은 한 번 적재하고, 특정 날짜 이하의 가장 가까운 값 조회가 대부분입니다.
규모: 수천~수만 항목이며 키 순서가 필요합니다.
선택: std::map<Date, Value>
비용: 삽입·lower_bound O(log n), 공간 O(n)
검증: 빈 map, 첫 날짜보다 이른 요청, 정확히 일치하는 날짜, 중복 날짜
```

## 2. 평균, 최악과 상각 비용

- **평균 비용**: 입력 분포나 해시 분산 같은 가정 아래의 평균 비용
- **최악 비용**: 허용된 입력 중 가장 비싼 경우
- **상각 비용**: 여러 연산의 총비용을 연산 수로 나눈 보장

`vector::push_back`은 용량이 부족한 한 번의 호출에서 O(n)개의 원소를 옮길 수 있습니다. 하지만 용량을 기하급수적으로 늘리는 구현에서는 연속된 끝 삽입의 상각 비용이 O(1)입니다. 이는 입력 확률에 의존하는 평균 비용과 다릅니다.

Big-O는 실제 실행 시간을 초 단위로 예측하지 않습니다. 캐시 지역성, 메모리 할당, 원소 크기와 비교 비용은 별도로 측정해야 합니다.

## 3. 주요 컨테이너 선택

| 구조 | 강점 | 주의점 |
|---|---|---|
| `vector` | 연속 저장, 인덱스 접근, 빠른 순회, 끝 삽입 | 재할당과 중간 원소 이동 |
| `deque` | 양 끝 삽입·삭제, 임의 접근 | 연속 메모리가 아니며 무효화 규칙이 복잡함 |
| `list` | 위치를 이미 알 때 O(1) 삽입·삭제 | 탐색 O(n), 노드별 할당, 낮은 캐시 지역성 |
| `map` | 정렬된 고유 키, 범위 검색과 이전 원소 탐색 | O(log n), 비교 함수 규칙 |
| `set` | 정렬된 포함 여부 확인과 중복 제거 | 키에 값을 연결해야 하면 `map` 검토 |
| `stack` | LIFO 동작 강제 | 임의 순회와 검색에 부적합 |

중간 삽입이 O(1)이라는 이유만으로 `list`를 선택하지 않습니다. 삽입 위치를 찾는 데 O(n)이 들 수 있고, 실제 순회 성능은 `vector`보다 나쁠 수 있습니다.

## 4. `vector`와 `deque`

순차 처리와 인덱스 접근이 중심이면 `vector`를 기본 후보로 둡니다. 연속 저장은 캐시 지역성과 C API 연동에 유리합니다.

양 끝 삽입이 빈번하고 앞쪽 삽입으로 전체 원소를 옮기는 비용을 피해야 한다면 `deque`를 검토합니다. 다만 원소가 하나의 연속 버퍼에 있다고 가정해 포인터 산술을 하거나 단일 버퍼를 요구하는 API에 넘겨서는 안 됩니다.

같은 알고리즘을 여러 컨테이너에 적용할 때는 공통 반복자 연산만 사용합니다. 코드 중복을 줄이려다 컨테이너별 최적화가 필요한 지점을 숨기지 않습니다.

## 5. `map`, `set`과 `lower_bound`

`map::lower_bound(key)`는 `key`보다 작지 않은 첫 원소를 가리킵니다.

특정 날짜 이하의 가장 가까운 값을 찾으려면 경계를 정확히 처리해야 합니다.

```cpp
Map::const_iterator it = values.lower_bound(requested);

if (it != values.end() && !(requested < it->first) && !(it->first < requested))
    return it->second; // 정확히 일치

if (it == values.begin())
    throw NoPreviousValue();

--it;
return it->second;
```

동등성은 비교 함수 기준으로 `!(a < b) && !(b < a)`로 판단합니다. 빈 `map`, 첫 키보다 작은 요청, 마지막 키보다 큰 요청과 정확히 일치하는 키를 각각 테스트합니다.

## 6. 파일 입력을 값으로 바꾸는 단계

```text
파일 열기
→ 헤더 확인
→ 한 줄 읽기
→ 구분자로 필드 분리
→ 필드 형식 검사
→ 타입 변환과 범위 검사
→ 값 객체 생성
→ 컨테이너 삽입
```

한 줄을 처리하다 오류가 발생했을 때의 정책을 먼저 정합니다.

- 전체 처리를 중단합니까?
- 잘못된 줄만 보고하고 계속합니까?
- 중복 키를 거부합니까, 마지막 값으로 덮어씁니까?
- 행 번호와 원본 일부를 오류에 포함합니까?

`stringstream >> value`가 성공해도 뒤에 불필요한 문자가 남을 수 있습니다. 입력 전체가 소비됐는지 확인합니다.

## 7. 날짜 값 객체

날짜를 문자열 그대로 키로 사용하려면 사전식 순서가 시간 순서와 일치하는 고정 형식인지 확인해야 합니다. `YYYY-MM-DD` 형식이라도 존재하지 않는 날짜는 거부해야 합니다.

```cpp
class Date
{
public:
    static Date parse(const std::string &text);
    bool operator<(const Date &other) const;

private:
    Date(int year, int month, int day);
    int year_;
    int month_;
    int day_;
};
```

검증 항목은 다음과 같습니다.

- 정확한 구분자와 필드 폭
- 월 범위 1~12
- 월별 일 수
- 윤년 계산
- 뒤에 추가 문자가 없는지

잘못된 날짜를 `map`에 넣은 뒤 나중에 처리하지 않습니다. 컨테이너에는 이미 유효성이 확인된 키만 저장합니다.

## 8. 스택 기반 계산

역폴란드 표기법(RPN)은 LIFO가 문제의 불변식과 일치하는 사례입니다.

```text
숫자 → 스택에 push
연산자 → 피연산자 두 개 pop → 계산 → 결과 push
입력 종료 → 스택에 값이 정확히 하나면 성공
```

다음 조건을 확인합니다.

- 피연산자가 두 개 미만인 스택 언더플로
- 뺄셈과 나눗셈에서 피연산자 순서
- 0으로 나누기
- 숫자도 연산자도 아닌 토큰
- 종료 시 값이 여러 개 남는 경우
- 산술 오버플로 정책

```cpp
int right = stack.top(); stack.pop();
int left  = stack.top(); stack.pop();
stack.push(left - right);
```

부호 있는 정수 오버플로는 정의되지 않은 동작이므로 연산 전에 범위를 검사하거나 더 넓은 중간 타입과 명시적인 정책을 사용합니다.

스택을 순회하거나 중간 원소를 검색해야 한다면 자료구조 선택이 요구사항과 맞는지 다시 확인합니다.

## 9. 알고리즘과 컨테이너 분리

같은 계산을 다른 자료구조에도 적용해야 한다면 핵심 알고리즘을 반복자 범위나 작은 템플릿으로 표현할 수 있습니다. 실습에서는 입력 순서를 보존해야 하는 레코드를 `vector`에 담고 `std::stable_sort`의 동작을 확인합니다.

```cpp
template <class RandomAccessIterator>
void sortRange(RandomAccessIterator first, RandomAccessIterator last);
```

다음 차이까지 억지로 하나로 합치지 않습니다.

- 컨테이너별 삽입 API
- 반복자 무효화 대응
- 성능 때문에 필요한 별도 저장 구조
- 출력과 시간 측정

공통화의 목적은 중복된 줄 수를 최소화하는 것이 아니라 같은 알고리즘 불변식을 한곳에서 검증하는 것입니다.

## 10. 정렬 정확성 검증

성능을 측정하기 전에 다음을 확인합니다.

- 결과가 비내림차순입니까?
- 입력과 결과의 원소 수가 같습니까?
- 각 중복 원소의 개수가 보존됩니까?
- 빈 입력과 원소 하나를 처리합니까?
- 이미 정렬된 입력과 역순 입력을 처리합니까?
- 무작위 입력에서 기준 정렬 결과와 일치합니까?

공통 접두 범위만 일치한다고 성공으로 처리하지 않습니다. 길이와 모든 원소를 함께 비교합니다.

## 11. 벤치마크 해석

측정 전에 포함할 구간을 정의합니다.

- 문자열 파싱을 포함합니까?
- 컨테이너 복사를 포함합니까?
- 출력은 제외했습니까?
- 같은 최적화 옵션으로 빌드했습니까?
- 여러 번 실행해 변동을 확인했습니까?

입력이 너무 작아 실행 시간이 시계 해상도보다 짧으면 수치가 의미 없을 수 있습니다. 벤치마크는 실제 구현 후보를 비교할 뿐 Big-O를 증명하지 않습니다. 복잡도가 같아도 캐시 지역성과 할당 횟수에 따라 실제 성능이 달라질 수 있습니다.

## 12. 정렬 규칙을 코드로 표현하기

정렬하기 전에 우선순위 필드와 같은 키를 가진 레코드의 상대 순서를 보존할지 정합니다. 비교 함수는 두 값의 선후 관계만 판단하고 외부 상태를 변경하지 않아야 합니다.

```cpp
struct RecordLess
{
    bool operator()(const Record &left, const Record &right) const
    {
        return left.value < right.value;
    }
};
```

같은 키의 입력 순서가 의미 있다면 `std::stable_sort`를 사용합니다. 상대 순서가 중요하지 않고 범위가 임의 접근 반복자를 제공한다면 `std::sort`가 단순한 선택입니다. 어떤 알고리즘을 사용하든 비교 함수가 엄격 약순서를 지키는지 먼저 확인합니다.

## 13. 결과가 입력의 순열인지 검증하기

결과가 오름차순이라는 사실만 확인하면 원소 누락이나 중복 생성 오류를 놓칠 수 있습니다. 다음 조건을 함께 검사합니다.

- 인접한 두 원소가 정렬 규칙에 맞습니다.
- 정렬 전후의 길이와 각 값의 개수가 같습니다.

같은 키의 입력 순서를 보존해야 한다면 원래 위치를 안정적인 식별자로 함께 저장하고, 정렬 뒤 상대 순서가 바뀌지 않았는지도 확인합니다.

## 14. 측정 범위 분리

입력 파싱과 출력은 정렬 시간에 포함하지 않습니다. 입력을 레코드로 변환한 뒤 정렬 호출 직전과 직후만 측정합니다. 결과와 진단 출력을 분리하면 자동 테스트가 쉬워집니다.

작은 입력은 시계 해상도보다 빨리 끝날 수 있으므로 여러 입력 크기에서 반복 측정하고 중앙값이나 분포를 비교합니다. 사용한 시계가 CPU 시간인지 실제 경과 시간인지도 기록합니다.

## 15. 결정적인 결과와 오류 출력

같은 입력에는 같은 결과와 같은 순서의 오류가 나와야 테스트와 디버깅이 쉽습니다.

- 입력 순서를 보존할지 정합니다.
- `map`의 키 정렬 순서와 입력 삽입 순서를 혼동하지 않습니다.
- 로캘에 따라 숫자 출력이 달라지지 않게 합니다.
- 첫 오류에서 중단할지 모든 오류를 수집할지 정합니다.
- 시간 측정 출력과 프로그램 결과 출력을 분리합니다.

5. 실행 전 예상 스택 상태를 표로 작성

## 단계형 실습 C: 레코드 정렬기

1. 정확성만 구현
2. 입력을 엄격하게 파싱

4. 기준 정렬과 결과 대조
5. 정렬 시간 측정 구간 분리
6. 무작위·중복·경계 입력 자동 생성

## 컨테이너 선택과 복잡도에서 자주 발생하는 실수

- `list`의 삽입 O(1)만 보고 위치 탐색 O(n)을 누락합니다.
- `lower_bound`가 `begin()`인데 먼저 감소시킵니다.
- 날짜 문자열의 형식만 보고 실제 달력 유효성을 검사하지 않습니다.
- RPN 계산에서 왼쪽과 오른쪽 피연산자 순서를 바꿉니다.
- 정렬 순서만 보고 원소 수와 중복 개수 보존을 확인하지 않습니다.
- 작은 벤치마크 수치를 복잡도 분석의 증명처럼 해석합니다.

## 다른 언어의 표준 컨테이너와 비교

언어마다 컨테이너 이름과 성능 특성은 다르지만 선택 과정은 같습니다.

```text
불변식 → 주요 연산 → 규모 → 후보 구조 → 비용 → 경계 테스트
```

Python의 `dict`, Java의 `TreeMap`, C#의 `SortedDictionary`, Rust의 `BTreeMap`도 각각의 구체적인 순서와 복잡도 규칙을 확인해야 합니다. 구현체의 우연한 순회 순서를 사용자 인터페이스의 보장으로 굳히지 않습니다.

## 문제 풀이 선택 점검

- 선택한 컨테이너에서 가장 빈번한 연산과 그 비용을 설명할 수 있습니까?
- 평균 비용과 최악 비용 중 어느 쪽이 요구사항에 더 중요합니까?
- `lower_bound` 결과의 빈 범위, 처음, 정확한 일치와 끝 경계를 처리했습니까?
- 스택 계산 종료 시 원소가 정확히 하나여야 하는 이유는 무엇입니까?
- 정렬 결과가 입력의 순열임을 어떻게 검증합니까?
- 측정에서 파싱과 출력을 제외했습니까?
- 측정 결과와 복잡도 분석이 서로 다른 역할을 한다는 점을 설명할 수 있습니까?
