# STL로 문제를 해결하는 법

## 자료구조보다 필요한 연산을 먼저 확인합니다

익숙한 컨테이너부터 고르면 주요 연산의 비용이나 순서 계약이 요구사항과 어긋날 수 있습니다. 입력에서 식별 방식과 불변식을 먼저 찾고, 평균·최악·상각 비용을 비교해 컨테이너와 알고리즘을 선택합니다.

## 요구사항에서 구현을 선택하는 과정

```text
불변식 → 주요 연산 → 규모·입력 경계 → container 선택
       → algorithm 선택 → 복잡도 기록 → 정상·실패·경계 테스트
```

자료구조 이름부터 고르지 않습니다. 먼저 무엇을 얼마나 자주 해야 하는지 씁니다.

## 1. 자료구조를 고르기 전에 적을 내용

```text
식별 방식: 위치, key, 우선순위, 연결 관계 중 무엇입니까?
주요 연산: 어떤 연산이 얼마나 자주 일어납니까?
불변식: 순서, 중복, 안정성, 메모리 상한 중 무엇을 지켜야 합니까?
비용 경계: 평균 비용으로 충분한가, 최악 지연이 중요합니까?
```

예:

```text
불변식: 날짜 하나에는 값이 최대 하나입니다.
주요 연산: 입력 1회, 날짜 이하의 가장 가까운 값 조회가 대부분입니다.
규모: 수천~수만 항목, 결과 순서가 필요합니다.
선택: std::map<Date, Value>.
비용: 삽입·lower_bound O(log n), 공간 O(n).
검증: 빈 `map`, 첫 날짜보다 작은 요청, 정확히 일치하는 날짜와 중복 날짜입니다.
```

## 2. 평균, 최악과 상각

- **평균**: 입력 분포나 해시 분산 같은 가정 아래 평균 비용
- **최악**: 허용된 입력 중 가장 비싼 경우
- **상각**: 여러 연산의 총비용을 연산 수로 나눈 보장

`vector::push_back`은 용량이 가득 찬 한 번의 호출에서 O(n) 복사를 할 수 있지만, 용량을 기하급수적으로 늘리면 연속 추가의 상각 비용은 O(1)입니다. 이는 확률 주장이 아닙니다.

Big-O는 실제 시간을 초 단위로 예측하지 않습니다. 캐시 지역성, 할당, 원소 크기와 비교 비용은 측정 대상입니다.

## 3. 주요 컨테이너 선택

| 구조 | 강점 | 주의점 |
|---|---|---|
| `vector` | 연속 저장, 인덱스, 빠른 순회, 끝 삽입 | 재할당과 중간 이동 |
| `deque` | 양 끝 삽입, 무작위 접근 | 연속 메모리 아님, 무효화 규칙 확인 |
| `list` | 위치를 이미 알 때 삽입·삭제 | 탐색 O(n), 노드 할당, 낮은 캐시 지역성 |
| `map` | 정렬된 고유 키, 범위와 바로 앞 원소 | O(log n), 비교 함수 계약 |
| `set` | 정렬된 포함 여부 확인과 중복 제거 | 값을 함께 저장해야 하면 `map` 검토 |
| `stack` | LIFO 제약 | 임의 순회·검색에 부적합 |

“중간 삽입이 O(1)”이라는 이유만으로 list를 고르지 않습니다. 삽입 위치를 찾는 데 O(n)이 들고 순회 성능이 나쁠 수 있습니다.

## 4. `vector`와 `deque`

순차 처리와 인덱스가 중심이면 `vector`를 기본 후보로 둡니다. 연속 저장은 CPU 캐시와 C API 연동에 유리합니다.

양 끝 삽입이 빈번하고 앞쪽 삽입 때문에 전체 이동을 피해야 한다면 `deque`를 검토합니다. 그러나 데이터가 연속하다고 가정해 포인터 arithmetic이나 단일 버퍼 API에 넘기지 않습니다.

같은 알고리즘을 여러 컨테이너에 적용할 때는 공통 반복자 연산만 사용합니다. 구현을 공유하느라 컨테이너별 최적화가 필요한 지점을 숨기지 않습니다.

## 5. `map`, `set`과 `lower_bound`

`map::lower_bound(key)`는 `key`보다 작지 않은 첫 원소를 가리킵니다.

날짜 이하의 가장 가까운 값을 찾으려면 경계를 조심합니다.

```cpp
Map::const_iterator it = values.lower_bound(requested);

if (it != values.end() && !(requested < it->first) && !(it->first < requested))
    return it->second; // exact match

if (it == values.begin())
    throw NoPreviousValue();

--it;
return it->second;
```

실제 코드에서는 `Date::operator<`와 동등성 정책을 한곳에 둡니다. 빈 `map`, 첫 키 이전, 마지막 키 이후와 정확히 일치하는 키를 각각 테스트합니다.

## 6. 파일 입력을 값으로 바꾸는 단계

```text
파일 열기
→ 헤더 확인
→ 한 줄 읽기
→ delimiter 분리
→ 각 필드 형식 검사
→ 타입 변환과 범위 검사
→ 값 객체 생성
→ container 삽입
```

한 줄을 읽는 동안 오류가 나면 다음을 결정합니다.

- 전체 처리를 중단할 것입니까?
- 잘못된 줄만 보고하고 계속할 것입니까?
- 같은 키 중복을 거부할 것인가, 마지막 값으로 덮을 것입니까?
- 행 번호와 원본 일부를 오류에 포함할 것입니까?

정책을 구현 전에 적습니다. `stringstream >> value`가 성공했다고 뒤에 불필요한 문자가 없는 것은 아닙니다. 입력 전체 소비를 확인합니다.

## 7. 날짜 값 객체

날짜를 문자열 그대로 사용하면 사전식 순서가 실제 시간 순서와 같은 형식인지 검증해야 합니다. `YYYY-MM-DD`처럼 고정 폭이라도 존재하지 않는 날짜를 거부해야 합니다.

```cpp
class Date
{
public:
    static Date parse(const std::string &text);
    bool operator<(const Date &other) const;

private:
    Date(int year, int month, int day);
    int year_;
    int month_;
    int day_;
};
```

검증 항목:

- 정확한 구분자와 폭
- 월 1~12
- 월별 일 수
- 윤년
- 추가 문자 없음

잘못된 날짜를 map에 넣은 뒤 나중에 처리하지 않습니다. 컨테이너는 이미 유효한 키만 받게 합니다.

## 8. 스택 기반 계산

Reverse Polish Notation은 LIFO가 문제의 불변식과 일치하는 사례입니다.

```text
숫자 → stack에 push
연산자 → 피연산자 두 개 pop, 계산 결과 push
끝 → stack에 값이 정확히 하나여야 성공
```

주의할 점:

- 피연산자가 두 개 미만이면 스택 언더플로
- 뺄셈과 나눗셈은 pop 순서가 중요
- 0으로 나누기
- 토큰이 숫자와 연산자 중 어느 것도 아님
- 끝났는데 값이 여러 개 남음
- 오버플로 정책

```cpp
int right = stack.top(); stack.pop();
int left  = stack.top(); stack.pop();
stack.push(left - right);
```

스택을 순회하거나 중간 값을 찾고 싶다면 구조 선택이 틀렸을 수 있습니다.

## 9. 알고리즘과 컨테이너 분리

같은 계산을 다른 자료구조에도 적용해야 한다면 알고리즘의 핵심을 반복자 범위나 작은 템플릿으로 표현합니다. 실습에서는 입력 순서 보존이 필요한 레코드를 `vector`에 담고 `std::stable_sort`의 계약을 확인합니다.

```cpp
template <class RandomAccessIterator>
void sortRange(RandomAccessIterator first, RandomAccessIterator last);
```

하지만 다음은 억지로 공통화하지 않습니다.

- 컨테이너별 삽입 API 차이
- 반복자 무효화 대응
- 성능을 위해 필요한 별도 저장 구조
- 출력과 시간 측정

공통화의 목표는 중복 줄 수 최소화가 아니라 **동일한 알고리즘 불변식을 한곳에서 검증하는 것**입니다.

## 10. 정렬 정확성 검증

성능을 재기 전에 다음을 확인합니다.

- 결과가 비내림차순입니까?
- 입력 원소 수와 결과 원소 수가 같은가?
- 중복 원소 개수가 보존됩니까?
- 빈 입력과 한 원소가 처리됩니까?
- 이미 정렬된 입력과 역순 입력이 처리됩니까?
- 무작위 입력에서 `std::sort` 결과와 같은가?

공통 접두 범위만 같다고 성공 처리하지 않습니다. 길이와 모든 값을 비교합니다.

## 11. 벤치마크를 해석하는 법

측정 전에 구간을 정의합니다.

- 문자열 파싱을 포함합니까?
- 컨테이너 복사를 포함합니까?
- 출력은 제외했습니까?
- 같은 최적화 플래그를 사용했습니까?
- 여러 번 실행하고 변동을 확인했습니까?

작은 입력에서 시계 해상도보다 실행 시간이 짧으면 수치가 의미 없을 수 있습니다. 벤치마크는 실제 구현 후보를 비교하지만 Big-O를 증명하지는 않습니다. Big-O가 같더라도 캐시 지역성과 할당 차이를 함께 확인합니다.

## 12. 정렬 규칙을 코드로 표현하기

정렬을 시작하기 전에 어떤 필드가 우선하는지, 같은 키를 가진 레코드의 순서를 유지해야 하는지 정합니다. 비교 함수는 두 값의 선후 관계만 답하고 외부 상태를 변경하지 않아야 합니다.

```cpp
struct RecordLess
{
    bool operator()(const Record &left, const Record &right) const
    {
        return left.value < right.value;
    }
};
```

같은 키의 입력 순서가 의미 있다면 `std::stable_sort`를 사용합니다. 순서가 중요하지 않고 임의 접근 반복자를 제공하는 범위라면 `std::sort`가 단순한 선택입니다. 어떤 함수를 사용하든 비교 함수가 엄격 약순서 계약을 지키는지 먼저 확인합니다.

## 13. 결과가 입력의 순열인지 검증하기

오름차순이라는 사실만 확인하면 원소가 누락되거나 중복된 오류를 놓칠 수 있습니다. 테스트에서는 다음 두 조건을 함께 검사합니다.

- 인접한 두 원소의 순서가 정렬 규칙과 맞습니다.
- 정렬 전후의 길이와 각 값의 개수가 같습니다.

같은 키의 입력 순서를 보존해야 한다면 원래 위치를 안정적인 식별자로 함께 저장하고, 정렬 뒤 상대 순서가 바뀌지 않았는지도 확인합니다.

## 14. 측정 범위를 분리하기

입력 파싱과 출력은 정렬 시간에 포함하지 않습니다. 입력을 레코드로 변환한 뒤 정렬 호출 직전과 직후만 측정하고, 결과는 표준 출력으로, 측정값과 오류는 표준 오류로 보냅니다. 작은 입력은 시계 해상도보다 빨리 끝날 수 있으므로 여러 입력 크기에서 반복해서 측정하고 중앙값을 비교하는 편이 안전합니다.

## 15. 결정적 결과와 오류 출력

같은 입력에 같은 결과와 오류 순서를 내야 테스트와 디버깅이 쉽습니다.

- 입력 순서를 보존할지 정합니다.
- `map`의 정렬 순서와 삽입 순서를 혼동하지 않습니다.
- locale에 따라 숫자 출력이 바뀌지 않게 합니다.
- 첫 오류에서 중단할지 모든 오류를 모을지 정합니다.
- 시간 측정 출력과 결과 출력을 분리합니다.

## 컨테이너 선택과 복잡도 실수

- list의 삽입 O(1)만 보고 위치 탐색 O(n)을 누락합니다.
- `lower_bound`가 `begin()`인데 먼저 감소시킵니다.
- 날짜 문자열 형식만 보고 실제 달력 유효성을 검사하지 않습니다.
- RPN에서 오른쪽·왼쪽 피연산자 순서를 바꿉니다.
- 정렬 뒤 값만 보고 중복 개수나 길이를 확인하지 않습니다.
- 작은 벤치마크 수치를 복잡도 증명처럼 해석합니다.
- 정렬 결과의 순서만 보고 원소의 누락이나 중복을 확인하지 않습니다.

## Python·Java와 비교하는 표준 컨테이너

언어마다 컨테이너 이름과 성능 특성은 다르지만 선택 과정은 같습니다.

```text
불변식 → 주요 연산 → 규모 → 후보 구조 → 비용 → 경계 테스트
```

Python의 `dict`, Java의 `TreeMap`, C#의 `SortedDictionary`, Rust의 `BTreeMap`도 구체 계약을 확인해야 합니다. 구현체의 우연한 순회 순서를 사용자 계약으로 굳히지 않습니다.

## 문제 풀이 선택 점검

- 선택한 컨테이너의 가장 빈번한 연산과 비용을 말할 수 있습니까?
- 평균 비용과 최악 비용 중 어느 것이 요구사항에 중요합니까?
- `lower_bound` 결과의 네 가지 경계를 처리했습니까?
- 스택 계산 종료 시 원소가 하나여야 하는 이유는 무엇입니까?
- 정렬 결과가 입력의 permutation임을 어떻게 검증합니까?
- 측정에서 파싱과 출력을 제외했습니까?
- 측정 결과와 복잡도 분석이 서로 다른 역할을 한다는 점을 설명할 수 있습니까?
