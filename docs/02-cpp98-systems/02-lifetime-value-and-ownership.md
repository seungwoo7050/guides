# 객체 수명, 값 의미론과 소유권

## 주소보다 객체의 수명을 먼저 확인합니다

C++에서는 수명이 끝난 객체에 접근하거나 같은 자원을 두 번 정리하는 오류가 큰 장애로 이어집니다. 복사와 대입을 구분하지 못하면 정상 경로에서는 작동하지만 예외나 자기 대입에서 망가지는 타입을 만들기 쉽습니다. 저장 공간 확보부터 소멸까지 객체 상태를 따라가며 소유자와 실패 뒤 보장을 확인합니다.

## 저장 공간과 객체 수명의 관계

```text
저장 공간 확보 → 생성 완료 → 유효한 객체 수명 → 소멸 → 저장 공간 반환
                         ├→ 복사: 독립된 값입니까?
                         └→ 소유: 누가 자원을 정리합니까?

자원 수명 = 객체 수명  →  RAII
```

주소가 남아 있다는 사실과 객체가 살아 있다는 사실을 구분하는 것이 이 문서의 출발점입니다.

## 1. 저장 공간과 객체 수명의 차이

주소가 존재한다고 그 위치에 유효한 객체가 있다는 뜻은 아닙니다.

```text
저장 공간 확보
→ 생성 완료
→ 객체 수명
→ 소멸 시작
→ 저장 공간 반환 또는 재사용
```

- 자동 객체는 선언에 실행이 도달할 때 생성됩니다.
- 정상 흐름이나 예외로 범위를 벗어나면 역순으로 소멸합니다.
- `new T`는 저장 공간 확보와 `T` 생성을 함께 시도합니다.
- `delete`는 소멸자를 호출한 뒤 저장 공간을 반환합니다.

파괴된 객체의 옛 주소가 숫자로 남아 있어도 그 주소를 통해 객체를 사용할 수 없습니다.

## 2. 생성과 소멸 순서

객체의 생성 순서는 다음과 같습니다.

1. 가상 기반 클래스가 있다면 가상 기반 클래스
2. 직접 기반 클래스
3. 멤버 선언 순서
4. 생성자 본문

소멸은 반대 순서입니다. 초기화 리스트의 표기 순서를 바꿔도 멤버 선언 순서가 실제 순서를 결정합니다.

```cpp
class Session
{
public:
    Session(const std::string &name)
        : name_(name), count_(0)
    {}

private:
    std::string name_; // 먼저 생성
    int count_;        // 다음 생성
};
```

한 멤버가 다른 멤버에 의존하면 선언 순서 자체가 그 의존성을 표현해야 합니다.

## 3. 생성자 실패

가장 바깥 객체의 생성자가 완료되기 전에 예외가 나면 그 객체의 소멸자는 호출되지 않습니다. 다만 이미 생성이 끝난 기반 클래스와 멤버는 역순으로 소멸합니다.

따라서 생성자 본문에서 원시 자원 여러 개를 직접 다루기보다, 각각을 이미 RAII를 지키는 멤버에 맡기는 편이 안전합니다.

```text
member A 생성 성공
member B 생성 중 실패
→ A 소멸
→ 가장 바깥 객체의 소멸자는 호출되지 않음
```

## 4. `new`와 `delete`

```cpp
Widget *one = new Widget;
delete one;

Widget *many = new Widget[10];
delete[] many;
```

`new[]`와 `delete[]`를 바꾸어 쓰면 안 됩니다. 할당에 성공했더라도 생성자가 실패할 수 있습니다. 직접 여러 포인터를 소유하면 어느 단계까지 성공했는지 수동으로 추적해야 합니다.

동적 할당은 “객체를 크게 만들기 위한 기본 선택”이 아닙니다. 수명이 현재 범위를 넘어야 하거나 개수가 런타임에 결정되는 등 명확한 이유가 있을 때 사용합니다.

## 5. 소유와 대여

포인터나 참조는 소유권을 자동으로 표현하지 않습니다.

```cpp
void inspect(const Record &record);   // 빌려 읽음
void mutate(Record &record);          // 빌려 변경
Record *find(int id);                 // 없을 수 있는 비소유 관찰일 수 있음
Record *create();                     // 호출자가 소유할 수도 있음
```

마지막 두 함수는 타입만 보고 소유자를 알 수 없습니다. 문서와 이름, 객체 구조로 다음 질문에 답해야 합니다.

- 누가 자원을 획득했습니까?
- 누가 정리합니까?
- 빌린 참조는 언제까지 유효합니까?
- 소유권을 다른 객체로 넘길 수 있습니까?

C++98 코드에서는 소유를 표현하는 표준 타입이 제한적이므로 복사를 막은 소유자 클래스를 직접 만듭니다.

## 6. RAII

RAII는 자원의 수명을 객체 수명에 묶는 방식입니다.

```cpp
class File
{
public:
    explicit File(const char *path);
    ~File();

private:
    File(const File &);
    File &operator=(const File &);

    int fd_;
};
```

생성자가 파일을 열고 소멸자가 닫으면 함수가 어느 경로로 끝나도 정리가 한곳에 모입니다.

RAII 대상은 메모리에 한정되지 않습니다.

- 파일 디스크립터
- 소켓
- 락
- 임시 파일
- 등록 상태
- 변경했다가 복원해야 하는 스트림 설정

## 7. 복사 생성자

복사 생성자는 아직 존재하지 않는 새 객체를 만듭니다.

```cpp
Buffer copy(original);
```

컴파일러가 만든 기본 복사는 각 멤버를 복사합니다. 소유 포인터가 있다면 주소만 복사되어 두 객체가 같은 메모리를 소유하게 될 수 있습니다.

```cpp
class Buffer
{
public:
    Buffer(const char *text);
    Buffer(const Buffer &other);
    ~Buffer();

private:
    char *data_;
    std::size_t size_;
};
```

값 타입이라면 복사 뒤 원본과 사본의 수명과 변경이 독립적이어야 합니다. 이를 위해 새 저장 공간을 확보하고 내용을 복사하는 깊은 복사가 필요합니다.

## 8. 복사 대입

복사 대입은 이미 유효한 객체의 값을 교체합니다.

```cpp
second = first;
```

대상은 기존 자원을 가지고 있으므로 다음 문제가 추가됩니다.

- 새 복사 준비가 실패할 수 있습니다.
- 기존 자원을 먼저 버리면 실패 시 대상 값까지 잃습니다.
- `value = value`에서는 자신이 읽을 원본을 먼저 지울 수 있습니다.

따라서 “기존 자원 해제 → 새 자원 할당” 순서는 취약합니다.

## 9. Rule of Three와 Canonical Form

직접 자원을 소유해 다음 중 하나를 정의해야 한다면 나머지도 함께 검토합니다.

1. 복사 생성자
2. 복사 대입 연산자
3. 소멸자

이것이 Rule of Three입니다. 학습 과정에서 자주 사용하는 Canonical Form은 여기에 기본 생성자를 함께 나열하기도 합니다. 두 용어를 동일하게 취급하지 않습니다.

모든 클래스가 이 함수를 직접 구현해야 하는 것은 아닙니다. `std::string`, `std::vector`처럼 올바른 값 의미를 가진 멤버만 보유한다면 컴파일러 생성 연산이 더 정확할 수 있습니다.

복사가 의미 없는 자원 소유자는 C++98에서 복사 연산을 비공개으로 선언해 막습니다.

```cpp
private:
    Socket(const Socket &);
    Socket &operator=(const Socket &);
```

## 10. copy-and-swap

copy-and-swap은 새 값을 대상 밖에서 준비한 뒤 마지막에 교체합니다.

```cpp
Buffer &Buffer::operator=(const Buffer &other)
{
    Buffer candidate(other); // 실패하면 *this는 그대로
    swap(candidate);         // 예외를 던지지 않아야 함
    return *this;
}
```

성공 뒤 `candidate`는 대상의 옛 자원을 가지며 함수가 끝날 때 정리합니다.

```text
후보 생성
→ 완성되면 무던짐 swap
→ 옛 상태는 후보 소멸자가 정리
```

이 패턴은 self-assignment에도 안전합니다. 비용은 임시 복사와 swap이므로 모든 연산에 자동 적용할 정답은 아닙니다.

## 11. 예외 안전성의 세 수준

| 보장 | 실패 뒤 상태 |
|---|---|
| 기본 보장 | 누수 없이 유효하고 파괴 가능하지만 값은 달라질 수 있습니다. |
| 강한 보장 | 성공하거나 호출 전 관측 상태가 그대로 남습니다. |
| 무예외 보장 | 예외를 밖으로 내보내지 않습니다. |

소멸자와 `swap` 같은 정리·반영 연산은 예외를 던지지 않아야 합니다. 강한 예외 안전성은 이름이 아니라 실제 구현 순서로 증명합니다.

```text
원본을 건드리지 않고 후보 준비
→ 모든 작업 성공
→ 실패하지 않는 한 단계로 공개
```

## 12. 값 타입 사례: 고정소수점 수

수치를 원시 정수와 scale로 저장하는 타입은 값 의미론을 연습하기 좋습니다.

```cpp
class Fixed
{
public:
    Fixed();
    explicit Fixed(int value);
    explicit Fixed(double value);

    double toDouble() const;
    int raw() const;

    Fixed operator+(const Fixed &other) const;
    bool operator<(const Fixed &other) const;

private:
    int raw_;
    static const int fractionalBits_ = 8;
};
```

설계할 때 다음을 먼저 정합니다.

- 표현 가능한 범위
- 변환 시 반올림 방식
- 오버플로 정책
- 비교가 원시 값 비교와 같은지
- `operator+`가 피연산자를 변경하지 않는지

연산자 오버로딩은 타입의 의미를 자연스럽게 표현할 때만 사용합니다. `operator+`가 왼쪽 값을 몰래 바꾸거나 비교가 외부 상태에 의존하면 내장 연산자의 기대를 깨뜨립니다.

## 13. 현대 C++에서는 무엇이 달라지는가

원리는 같고 표현 도구가 더 분명해집니다.

| 의도 | C++98 | 현대 C++ |
|---|---|---|
| 복사 금지 | 비공개 선언 | `= delete` |
| 단독 소유 | 직접 소유자 작성 | `std::unique_ptr` |
| 소유권 이전 | 별도 `release`/`swap` 계약 | 이동 생성자/이동 대입 |
| 기본 연산 사용 | 직접 생략 | `= default` |
| 자원 직접 소유 최소화 | Rule of Three | Rule of Zero |

현대 C++의 핵심도 동일합니다. **어떤 자원을 누가 언제까지 소유하는지 타입과 객체 구조로 드러냅니다.**

## 14. 다형적 객체 복사 예고

기반 클래스 포인터가 가리키는 실제 파생 클래스 타입을 모르는 상태에서 값을 복사하면 슬라이싱이 생깁니다. 각 파생 클래스가 자기 타입을 복사하는 `clone()`을 제공할 수 있지만, 반환된 포인터의 소유자와 부분 복사 실패 처리는 별도로 설계해야 합니다. 자세한 내용은 다형성 문서에서 다룹니다.

## 작은 실습: `TextBuffer`

다음 불변식을 가진 동적 문자열 타입을 만듭니다.

```text
- data_는 유효한 null 종료 문자열을 가리키거나 빈 상태입니다.
- size_는 문자열 길이와 일치합니다.
- 복사한 두 객체는 독립적입니다.
```

필요한 공개 함수:

```cpp
class TextBuffer
{
public:
    TextBuffer();
    explicit TextBuffer(const char *text);
    TextBuffer(const TextBuffer &other);
    ~TextBuffer();
    TextBuffer &operator=(const TextBuffer &other);

    const char *c_str() const;
    std::size_t size() const;
    void swap(TextBuffer &other) throw();

private:
    char *data_;
    std::size_t size_;
};
```

### 지원을 단계적으로 줄이기

1. 완성된 생성자와 소멸자를 읽습니다.
2. 복사 생성자 본문만 빈 상태로 작성합니다.
3. 테스트만 보고 복사 대입을 작성합니다.
4. copy-and-swap으로 다시 구현합니다.
5. `Key`, `Value`, `Request`가 이 타입을 값으로 사용하게 합니다.

### 실패 주입

- 원본과 사본 중 하나를 변경합니다.
- 자기 대입을 실행합니다.
- 빈 문자열과 긴 문자열을 복사합니다.
- 할당 실패를 흉내 내는 테스트 타입으로 강한 예외 안전성을 확인합니다.
- 생성·복사·소멸 횟수를 세어 누수와 이중 파괴를 찾습니다.

## 복사·할당에서 생기는 수명 오류

- 소멸자만 작성하고 복사 연산은 기본 동작에 맡깁니다.
- 대입에서 먼저 기존 자원을 지웁니다.
- 생성자 본문에서 여러 원시 포인터를 획득한 뒤 중간 실패를 처리하지 않습니다.
- 빌린 참조를 소유자보다 오래 보관합니다.
- `delete`와 `delete[]`를 혼동합니다.
- 이동된 현대 C++ 객체의 이전 값을 가정합니다.

## Rust·Java와 비교하는 소유권

Java와 C#은 메모리를 GC가 관리하지만 파일, 소켓, 잠금 같은 외부 자원은 여전히 명시적 수명이 필요합니다. `try-with-resources`, `using`, `finally`는 RAII와 문법은 다르지만 같은 질문에 답합니다. 값 객체의 불변식, 복사 독립성, 소유와 대여의 경계는 모든 객체지향 언어에서 유지됩니다.

## 수명과 예외 안전성 점검

- 객체 생성에 실패했을 때 가장 바깥 소멸자가 호출되지 않는 이유는 무엇입니까?
- 복사 생성자와 복사 대입의 실패 경로가 어떻게 다른가?
- 소유 포인터를 가진 타입의 기본 복사가 위험한 이유는 무엇입니까?
- copy-and-swap의 실제 반영 지점은 어디입니까?
- 강한 예외 안전성을 구현 순서로 설명할 수 있습니까?
- 포인터가 존재해도 대상 객체를 사용할 수 없는 경우를 세 가지 말할 수 있습니까?
