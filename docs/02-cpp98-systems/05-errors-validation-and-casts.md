# 오류 처리, 입력 검증과 타입 경계

## 실패도 인터페이스의 일부입니다

모든 실패를 `false`나 문자열 하나로 표현하면 호출자는 무엇을 복구할 수 있는지 알기 어렵습니다. 반대로 모든 문제에 예외를 사용하면 정상적인 분기까지 숨은 제어 흐름이 됩니다. 실패의 종류와 처리 책임을 구분하고, 입력 변환부터 상태 반영까지 각 단계가 무엇을 보장해야 하는지 확인합니다.

## 입력에서 오류 응답까지

```text
원시 입력 → 문법 검증 → 타입 변환 → 도메인 검증 → 상태 변경
   실패 A      실패 B       실패 C          실패 D
                                      ↓
                              애플리케이션 경계
                                      ↓
                                외부 오류 표현
```

캐스트는 표현이나 타입을 변환할 뿐입니다. 값의 범위, 객체 수명과 실제 동적 타입은 별도로 검증해야 합니다.

## 1. 실패 분류

| 종류 | 예 | 일반적인 처리 위치 |
|---|---|---|
| 외부 입력 오류 | 잘못된 숫자, 누락된 인자 | 파서 또는 요청 경계 |
| 도메인 규칙 위반 | 중복 키, 잔액 부족 | 도메인 객체 또는 서비스 |
| 시스템 오류 | `open`, `read`, `socket` 실패 | 시스템 어댑터와 상위 경계 |
| 자원 부족 | 메모리 할당 실패 | 복구 정책이 있는 상위 경계 |
| 프로그래밍 오류 | 불가능한 상태, 유효하지 않은 반복자 | 단언문과 코드 수정 |
| 일시적인 상태 | 논블로킹 I/O의 `EAGAIN` | 재시도 또는 준비 상태 대기 |

분류가 중요한 이유는 호출자가 실패 종류마다 다르게 행동해야 하기 때문입니다. 잘못된 사용자 입력은 오류 응답으로 바꿀 수 있지만, 내부 불변식 위반을 정상 입력 오류처럼 처리하고 계속 실행하면 결함을 숨기게 됩니다.

## 2. 반환값과 예외

반환값이 적합한 경우는 다음과 같습니다.

- 실패가 흔한 정상 분기입니다.
- 호출자가 즉시 다른 동작을 선택해야 합니다.
- 실패 종류가 작고 명확합니다.

```cpp
bool Store::contains(const Key &key) const;
```

예외가 적합한 경우는 다음과 같습니다.

- 현재 함수가 의미 있는 결과를 만들 수 없습니다.
- 여러 호출 계층을 건너 처리 책임이 있는 경계까지 전달해야 합니다.
- 생성자가 유효한 객체를 만들지 못했습니다.
- 실패가 일반적인 제어 흐름이 아닙니다.

```cpp
Key::Key(const std::string &text)
{
    if (!isValid(text))
        throw std::invalid_argument("키가 올바르지 않습니다");
}
```

같은 실패를 반환값과 예외로 중복 표현하지 않습니다.

## 3. 예외의 실행 흐름

예외가 던져지면 적절한 처리기를 찾을 때까지 호출 스택을 되감습니다. 이 과정에서 생성이 완료된 자동 객체의 소멸자가 역순으로 호출됩니다.

```cpp
void process()
{
    File input("data.txt");
    Buffer buffer;
    parse(input, buffer); // 여기서 예외 발생
} // 스택 되감기 중 Buffer와 File이 역순으로 소멸
```

정리만 필요하다면 각 단계에서 예외를 잡지 않고 RAII에 맡깁니다. 중간 계층이 아무 처리도 하지 않은 채 잡았다가 다시 던지면 코드만 복잡해지고 같은 오류를 여러 번 기록하기 쉽습니다.

## 4. 예외를 받는 방법

```cpp
try
{
    run();
}
catch (const DomainError &error)
{
    report(error.what());
}
```

예외는 일반적으로 `const` 참조로 받습니다.

- 불필요한 복사를 피합니다.
- 파생 예외의 동적 타입을 슬라이싱하지 않습니다.

현재 처리 중인 예외를 그대로 다시 던질 때는 `throw;`를 사용합니다.

```cpp
catch (const std::exception &error)
{
    log(error.what());
    throw;
}
```

`throw error;`는 새 예외 객체를 값으로 던지므로 파생 타입 정보가 사라질 수 있습니다.

## 5. 예외를 잡는 위치

예외는 실제 처리 책임이 있는 경계에서 잡습니다.

- 파서 경계: 잘못된 입력을 구조화된 파싱 오류로 변환
- 애플리케이션 경계: 도메인 실패를 사용자 응답으로 변환
- 프로세스 최상위: 진단을 기록하고 안전하게 종료하거나 요청 단위로 격리

다음 이유만으로 예외를 잡지 않습니다.

- 예외가 발생할 수 있다는 이유
- 모든 함수에서 로그를 남기기 위해
- 정리 코드를 실행하기 위해

정리는 RAII가 담당합니다. 로그는 필요한 문맥을 가진 경계에서 한 번 기록합니다.

## 6. 소멸자와 예외

스택을 되감는 중에 소멸자가 다시 예외를 내보내면 `std::terminate`가 호출됩니다. 자원 정리 소멸자는 예외를 밖으로 내보내지 않도록 설계하고, 실패를 보고해야 하는 작업은 별도 함수로 제공합니다.

```cpp
class Transaction
{
public:
    void commit();   // 실패 보고 가능
    void rollback() throw();
    ~Transaction() throw();
};
```

소멸자에서 실패를 숨기라는 뜻은 아닙니다. 업무상 성공 여부가 중요한 `commit`, `flush`, `close`는 명시적으로 호출하고 결과를 확인해야 합니다. 소멸자는 남은 자원을 안전하게 정리하는 최후의 경계입니다.

## 7. 예외 안전성 보장

| 보장 | 실패 뒤 상태 |
|---|---|
| 기본 보장 | 객체는 유효하고 정리할 수 있으며 자원 누수가 없습니다. 값은 달라질 수 있습니다. |
| 강한 보장 | 연산이 성공하거나, 관찰 가능한 상태가 호출 전과 같습니다. |
| 무예외 보장 | 예외가 함수 밖으로 전달되지 않습니다. |

모든 연산에 강한 예외 보장이 필요한 것은 아닙니다. 호출자가 실제로 요구하는 수준과 구현 비용을 함께 고려합니다.

## 8. 후보 상태를 준비한 뒤 반영하기

기존 상태를 교체하는 연산에 강한 예외 보장이 필요하면 대상 밖에서 후보를 완성한 뒤 한 번에 반영합니다.

```cpp
void Configuration::replace(const Specification &spec)
{
    Configuration candidate;
    candidate.parse(spec);
    candidate.validate();
    swap(candidate); // 반영 단계, 예외를 던지지 않아야 함
}
```

다음 질문에 모두 답할 수 있어야 강한 예외 보장을 주장할 수 있습니다.

1. 후보 생성 중 획득한 자원이 실패 시 모두 정리됩니까?
2. 후보를 만드는 동안 기존 상태를 변경하지 않습니까?
3. 최종 반영 연산은 실패하지 않습니까?
4. 성공 뒤 기존 상태는 누가 정리합니까?
5. 별칭 관계나 자기 대입이 입력을 무효화하지 않습니까?

## 9. 처리 방식이 다른 오류만 타입으로 구분합니다

예외 클래스를 많이 만드는 것 자체가 좋은 설계는 아닙니다. 호출자가 실제로 다르게 처리해야 할 때만 타입을 나눕니다.

```cpp
class ParseError : public std::runtime_error
{
public:
    explicit ParseError(const std::string &message)
        : std::runtime_error(message)
    {}
};

class ConflictError : public std::runtime_error
{
public:
    explicit ConflictError(const std::string &message)
        : std::runtime_error(message)
    {}
};
```

오류 메시지 문자열을 분석해 분기하지 말고 타입이나 구조화된 오류 코드를 사용합니다. 반대로 입력 위치마다 별도 예외 클래스를 만들 필요는 없습니다. 행, 열, 입력 조각과 원인은 하나의 파싱 오류 객체에 데이터로 담을 수 있습니다.

## 10. 입력 파싱 단계 나누기

```text
원시 문자열
→ 토큰 분리
→ 형식 검사
→ 타입 변환
→ 범위 검사
→ 도메인 값 객체
```

`"12abc"`를 숫자 12로 인정할지, 입력 전체를 소비해야 할지 먼저 정합니다. 빈 문자열, 앞뒤 공백, 부호, 앞에 붙은 0과 로캘 처리도 인터페이스 규칙입니다.

```cpp
long parseLong(const std::string &text)
{
    char *end = 0;
    errno = 0;
    const long value = std::strtol(text.c_str(), &end, 10);

    if (text.empty() || end == text.c_str() || *end != '\0')
        throw ParseError("정수가 아닙니다");
    if (errno == ERANGE)
        throw ParseError("정수 범위를 벗어났습니다");
    return value;
}
```

`errno`는 호출 직전에 0으로 초기화하고 변환 직후 검사합니다. 그 사이에 다른 라이브러리 함수를 호출하지 않습니다.

## 11. 숫자 변환에서 검사할 항목

- 입력을 한 글자도 소비하지 않았습니까?
- 변환되지 않은 문자가 남아 있습니까?
- 대상 타입의 범위를 벗어났습니까?
- 부호를 허용합니까?
- 부동소수점 입력에서 NaN과 무한대를 허용합니까?
- 정수로 변환할 때 소수 부분을 어떻게 처리합니까?
- 오버플로와 언더플로를 어떻게 보고합니까?

캐스트는 이 검사를 대신하지 않습니다.

## 12. `static_cast`

컴파일 시점에 관계를 확인할 수 있는 명시적 변환에 사용합니다.

```cpp
double measured = 42.75;
int whole = static_cast<int>(measured);
```

소수 부분은 버려집니다. 절단된 값이 대상 정수 타입으로 표현되지 않으면 동작이 정의되지 않으므로, 캐스트 전에 범위를 검사해야 합니다.

상속 계층의 안전한 업캐스트에도 사용할 수 있습니다.

```cpp
Derived *derived = 0;
Base *base = static_cast<Base *>(derived);
```

기반 클래스에서 파생 클래스로 내려가는 캐스트도 문법상 가능할 수 있지만 실제 동적 타입을 검사하지 않습니다. 외부 불변식으로 타입이 확실하게 보장되지 않는다면 `dynamic_cast`를 사용합니다.

## 13. `dynamic_cast`

가상 함수가 있는 다형적 계층에서 객체의 실제 타입을 실행 시점에 확인합니다.

```cpp
SpecialHandler *special = dynamic_cast<SpecialHandler *>(handler);
if (special == 0)
{
    // 실제 타입이 일치하지 않음
}
```

- 포인터 캐스트 실패: 널 포인터 반환
- 참조 캐스트 실패: `std::bad_cast` 예외 발생

불일치가 정상 분기라면 포인터 형태가 자연스럽습니다. 반드시 특정 타입이어야 하는 규칙이 깨진 것이라면 참조 캐스트와 예외가 의미 있을 수 있습니다.

`dynamic_cast` 연쇄가 반복되면 타입을 외부에서 판별하기보다 가상 함수나 방문자 패턴으로 동작을 객체에 옮길 수 있는지 검토합니다.

## 14. `reinterpret_cast`

`reinterpret_cast`는 낮은 수준의 주소 표현을 바꿉니다. 다음을 보장하지 않습니다.

- 객체 데이터의 복사나 직렬화
- 포인터가 살아 있는 객체를 가리킨다는 사실
- 객체 수명 연장
- 소유권 이전
- 임의 정수 값을 주소로 바꾼 뒤 안전하게 역참조할 수 있다는 보장

구현이 포인터 값을 담을 수 있는 `uintptr_t`를 제공하는 경우 다음과 같은 주소 토큰을 만들 수 있습니다.

```cpp
typedef uintptr_t AddressToken;
AddressToken token = reinterpret_cast<AddressToken>(pointer);
Payload *again = reinterpret_cast<Payload *>(token);
```

포인터를 정수로 바꿨다가 되돌리는 표현이 지원되더라도 원래 객체의 수명이 끝났다면 `again`은 댕글링 포인터입니다. 주소 값을 파일이나 네트워크에 저장하는 것은 객체 직렬화가 아닙니다.

C++98 표준은 범용 포인터 정수 타입을 필수로 제공하지 않습니다. 대상 환경의 `<stdint.h>`가 `uintptr_t`를 제공하는지 확인해야 합니다.

## 15. `const_cast`

`const_cast`는 `const`와 `volatile` 한정만 변경합니다.

```cpp
const Widget *source = getWidget();
Widget *mutableView = const_cast<Widget *>(source);
```

원래 객체가 실제로 비상수 객체라면 일시적으로 제거한 `const`를 통해 수정할 수 있습니다. 원래부터 `const`로 정의된 객체를 수정하면 정의되지 않은 동작입니다. 잘못 설계된 인터페이스의 상수성 경계를 숨기는 용도로 사용하지 않습니다.

## 16. C 스타일 캐스트를 피하는 이유

C 스타일 캐스트 하나는 숫자 변환, 상속 계층 변환, `const` 제거와 주소 재해석을 여러 방식으로 시도할 수 있습니다. 코드만 보고 어떤 위험을 감수한 변환인지 알기 어렵습니다.

C++ 캐스트는 의도를 구분합니다.

```text
값 변환·알려진 타입 관계 → static_cast
실행 시점 계층 확인       → dynamic_cast
주소 표현 재해석          → reinterpret_cast
cv 한정만 변경            → const_cast
```

먼저 캐스트 없이 더 정확한 타입이나 함수 시그니처로 표현할 수 있는지 검토합니다.

## 17. 내부 오류를 외부 표현으로 변환하는 경계

내부 예외 문자열을 그대로 사용자에게 전달하지 않습니다. 로그와 외부 응답은 목적이 다릅니다.

```cpp
Response Application::execute(const Request &request)
{
    try
    {
        return router_.dispatch(request);
    }
    catch (const ParseError &error)
    {
        log_.write(error.what());
        return Response::badRequest("요청이 올바르지 않습니다");
    }
    catch (const ConflictError &error)
    {
        log_.write(error.what());
        return Response::conflict("현재 상태와 충돌합니다");
    }
}
```

- 내부 로그: 원인, 위치와 디버깅에 필요한 문맥
- 외부 응답: 안정적인 오류 코드와 공개해도 되는 설명

네트워크 서버에서는 한 요청의 오류가 전체 프로세스를 종료하지 않도록 요청 처리 경계를 둡니다. 다만 메모리 할당 실패처럼 복구 정책이 없는 오류까지 무조건 정상 응답으로 바꾸고 계속 실행해서는 안 됩니다.

## 단계형 실습: 안전한 요청 경계

### 1단계: 파싱 오류

명령 이름, 인자 수와 숫자 형식을 검사합니다. 오류를 단순 문자열이 아니라 `ParseError`와 위치 정보로 표현합니다.

### 2단계: 도메인 오류

중복 키, 저장 한도 초과와 존재하지 않는 키 삭제를 서로 다른 결과나 예외로 표현합니다.

### 3단계: 최상위 변환

애플리케이션 경계 한곳에서 내부 실패를 `Response`로 변환합니다. 하위 계층은 출력 문자열을 만들지 않습니다.

### 4단계: 강한 예외 보장

설정이나 여러 항목을 한 번에 바꾸는 기능은 후보 객체에서 준비한 뒤 `swap`으로 반영합니다.

### 5단계: 스칼라 변환기

다음 입력의 결과를 먼저 적고 변환기를 작성합니다.

```text
"0"
"-42"
"42abc"
"2147483648"
"nan"
"+inf"
" 12"
```

### 6단계: 캐스트 실험

- 다형적 기반 클래스에서 포인터 `dynamic_cast`의 성공과 실패
- 참조 캐스트 실패와 `std::bad_cast`
- 포인터를 정수로 바꿨다가 되돌린 뒤 원본 객체를 파괴한 경우
- 원래 상수 객체를 `const_cast`로 수정하는 코드는 작성만 하고 실행하지 않습니다.

## 오류 분류와 상태 보존에서 자주 발생하는 실수

- 정리만 하려고 모든 함수에서 예외를 잡습니다.
- `catch (...)`로 메모리 할당 실패와 프로그래밍 오류까지 삼킵니다.
- `throw error;`로 다시 던져 동적 타입을 잃습니다.
- 기존 상태를 먼저 변경한 뒤 입력을 검증합니다.
- `strtol`이 일부 문자만 소비한 입력을 성공으로 취급합니다.
- 캐스트가 값의 범위나 포인터 수명을 검증한다고 가정합니다.
- 내부 파일 경로와 시스템 오류를 사용자 응답에 그대로 노출합니다.

## 다른 언어의 오류 처리와 비교

Java·C#의 예외, Rust의 `Result`, Go의 오류 반환값은 문법과 비용 모델이 다릅니다. 그러나 다음 원칙은 같습니다.

- 실패 종류를 구분합니다.
- 처리 책임이 있는 경계까지만 전달합니다.
- 실패 뒤 상태를 명확히 보장합니다.
- 외부 입력을 도메인 타입으로 바꾸기 전에 검증합니다.
- 내부 진단 정보와 사용자 응답을 분리합니다.
