# 가변 인자와 포맷 API: 타입 계약과 상태 관리

가변 인자 함수는 호출할 때마다 인자의 수와 타입을 다르게 전달할 수 있습니다. 편리한 대신 `...` 뒤에 전달된 값에는 인자의 개수와 타입을 설명하는 정보가 자동으로 따라오지 않습니다.

따라서 함수는 인자 개수, 종결 표시 또는 포맷 문자열처럼 별도의 계약을 사용해 어디까지 읽을지, 다음 값을 어떤 타입으로 해석할지 결정해야 합니다.

이 장의 목표는 `printf` 전체를 다시 구현하는 것이 아닙니다. **정적 타입 정보가 충분하지 않은 API에서 타입 계약, 순회 상태와 실패를 어떻게 통제하는지** 작은 포맷터를 통해 확인합니다.

## 고정 매개변수와 `...`

```c
int log_values(const char *label, size_t count, ...);
```

`label`과 `count`는 고정 매개변수이고, `...` 뒤에는 호출자가 가변 인자를 전달합니다.

함수 본문에서는 가변 인자에 이름으로 직접 접근할 수 없습니다. `<stdarg.h>`가 제공하는 인터페이스를 사용해 정해진 순서대로 읽어야 합니다.

C99 기준으로 가변 인자 함수에는 `...` 앞에 최소 하나의 고정 매개변수가 필요합니다. `va_start`는 마지막 고정 매개변수를 기준으로 가변 인자 순회를 시작합니다.

## 핵심 인터페이스와 생명주기

```c
#include <stdarg.h>

int sum_ints(size_t count, ...)
{
    va_list arguments;
    int total = 0;

    va_start(arguments, count);

    for (size_t index = 0; index < count; index++)
    {
        total += va_arg(arguments, int);
    }

    va_end(arguments);
    return total;
}
```

`<stdarg.h>`의 핵심 인터페이스는 다음과 같습니다.

* `va_list`: 현재 가변 인자 순회 상태를 나타냅니다.
* `va_start(list, last_fixed)`: 첫 번째 가변 인자를 읽을 수 있도록 목록을 초기화합니다.
* `va_arg(list, type)`: 다음 인자를 `type`으로 읽고 순회 위치를 다음 인자로 이동합니다.
* `va_end(list)`: 해당 순회를 종료합니다.
* `va_copy(destination, source)`: 독립적으로 순회할 수 있는 목록을 복사해 초기화합니다.

`va_start`나 `va_copy`로 초기화한 각각의 `va_list`에는 대응하는 `va_end`가 필요합니다. 정상 반환뿐 아니라 중간 오류 경로에서도 이 규칙을 지켜야 합니다.

`va_list`의 실제 표현은 구현마다 다릅니다. 단순한 포인터일 수도 있고 배열이나 구조체와 비슷한 형태일 수도 있으며, 더 복잡한 호출 상태를 포함할 수도 있습니다.

따라서 다음과 같은 일반 대입이나 바이트 복사를 이식 가능한 복사 방법으로 사용해서는 안 됩니다.

```c
copy = arguments;              /* 일반적인 복사 방법으로 가정하지 않음 */
memcpy(&copy, &arguments, ...);
```

독립적인 순회가 필요하다면 `va_copy`를 사용합니다.

## 가변 인자에는 타입 메타데이터가 없다

다음 호출은 문법적으로 컴파일될 수 있지만 함수의 계약을 위반합니다.

```c
sum_ints(3, 10, 20);      /* 약속한 개수보다 인자가 적음 */
sum_ints(2, 10, 2.5);     /* 두 번째 가변 인자가 int가 아님 */
```

`va_arg(arguments, int)`는 다음 인자가 실제로 `int`인지 확인한 뒤 값을 꺼내는 연산이 아닙니다.

호출자가 실제로 전달한 타입과 `va_arg`에서 요구한 타입이 규칙에 맞지 않으면 정의되지 않은 동작이 발생할 수 있습니다.

이미 실행 중인 함수에는 원래 인자의 타입을 일반적으로 복구할 수 있는 메타데이터가 없기 때문에 다음 두 종류의 오류를 구분해야 합니다.

```text
함수가 관찰할 수 있는 오류
    NULL 포인터
    잘못된 capacity
    지원하지 않는 포맷 문법
    표현 가능한 길이 초과

가변 인자 계약 위반
    인자 개수 부족
    포맷과 실제 전달 타입 불일치
```

첫 번째 종류는 함수가 검사하고 정상적인 오류로 반환할 수 있습니다.

두 번째 종류는 일반적인 런타임 검사만으로 안전하게 복구할 수 없습니다. 따라서 잘못된 가변 인자 타입을 일부러 전달하는 테스트는 정상적인 오류 경로를 검사하는 테스트가 아니라 정의되지 않은 동작을 실행하는 테스트가 될 수 있습니다.

## 기본 인자 승격

가변 인자로 전달되는 값에는 기본 인자 승격이 적용됩니다. 따라서 소스 코드에 적힌 원래 타입과 `va_arg`에서 읽어야 하는 타입이 항상 같지는 않습니다.

### 작은 정수형

`char`, `signed char`, `unsigned char`, `short`, `unsigned short`와 같은 타입에는 정수 승격이 적용됩니다.

구체적인 결과는 해당 구현의 타입 범위에 따라 달라지지만 일반적인 환경에서는 `int` 또는 `unsigned int`로 전달됩니다.

```c
char letter = 'A';

consume(letter);
```

수신 측에서는 승격된 타입으로 읽어야 합니다.

```c
int value = va_arg(arguments, int);
```

다음처럼 원래 선언 타입을 그대로 사용하는 것은 잘못된 방식입니다.

```c
char value = va_arg(arguments, char); /* 잘못된 접근 */
```

### 부동소수점형

`float`는 가변 인자로 전달될 때 `double`로 승격됩니다.

```c
float ratio = 1.5f;

consume(ratio);
```

따라서 수신 측에서는 다음과 같이 읽습니다.

```c
double value = va_arg(arguments, double);
```

### 배열과 함수

일반적인 함수 호출과 마찬가지로 배열 표현식은 적절한 포인터로 변환되고, 함수 지정자는 함수 포인터로 변환됩니다.

따라서 포맷 지정자와 `va_arg`의 타입은 호출부에 적힌 선언 형태가 아니라 **실제로 전달되는 타입**을 기준으로 정해야 합니다.

## 인자의 끝을 알리는 방법

가변 인자 함수는 스스로 인자의 개수를 알 수 없습니다. 따라서 어디까지 읽어야 하는지 별도의 계약이 필요합니다.

대표적인 방법은 세 가지입니다.

### 개수 전달

```c
int sum_ints(size_t count, ...);
```

고정 매개변수로 뒤따르는 인자의 개수를 전달합니다.

구조는 단순하지만 호출자가 개수와 실제 인자 수를 정확히 맞춰야 합니다.

```c
sum_ints(3, 10, 20, 30);
```

### 종결 표시

특정 값을 마지막 인자로 두어 순회의 끝을 나타낼 수 있습니다.

```c
const char *first_nonempty(const char *first, ...);
```

예를 들어 계약을 다음처럼 정할 수 있습니다.

```c
first_nonempty("one", "two", (const char *)NULL);
```

sentinel 역시 가변 인자이므로 **어떤 타입의 값을 전달해야 하는지**까지 계약에 포함해야 합니다.

단순한 정수 상수 `0`과 포인터 sentinel을 같은 것으로 가정하지 않고, 필요한 경우 위처럼 정확한 포인터 타입으로 변환해 전달합니다.

### 포맷 문자열

```c
int diagnostic_format(
    char *buffer,
    size_t capacity,
    const char *format,
    ...
);
```

포맷 문자열 자체가 뒤따르는 인자의 수와 타입을 설명하도록 만들 수 있습니다.

```text
%s    다음 인자는 const char *
%d    다음 인자는 int
%%    인자를 소비하지 않고 '%' 출력
```

이 경우 포맷 문자열은 단순한 출력 데이터가 아닙니다. **뒤따르는 인자를 어떻게 해석해야 하는지 설명하는 런타임 타입 계약**의 역할을 합니다.

따라서 포맷 문자열과 실제 전달 인자가 반드시 일치해야 합니다.

## 제한된 포맷 문법부터 정의하기

교육용 포맷터에서는 처음부터 `printf`의 모든 기능을 구현할 필요가 없습니다.

먼저 지원 범위를 작게 고정합니다.

```text
일반 문자    그대로 출력
%%          '%' 하나 출력
%s          문자열 출력
%d          부호 있는 10진수 정수 출력
```

동시에 경계 조건의 처리 방식도 먼저 정합니다.

* 문자열 끝에 `%` 하나만 남으면 어떻게 하는가
* 지원하지 않는 `%x`를 만나면 어떻게 하는가
* `%s`에 null 포인터가 전달되면 어떻게 하는가
* 결과 길이가 반환 타입으로 표현할 수 있는 범위를 넘으면 어떻게 하는가
* 버퍼가 전체 결과보다 작으면 오류인가, 잘림인가

이번 연습에서는 다음 계약을 사용한다고 가정합니다.

```text
%s에 null 포인터
    → "(null)" 출력

지원하지 않는 지시자
    → 형식 오류

문자열 끝의 단독 %
    → 형식 오류

버퍼 부족
    → 정상적인 잘림

길이 표현 범위 초과
    → 오류
```

폭, 정밀도, 길이 수정자와 다른 표준 `printf` 기능은 이 기본 계약이 안정된 뒤 별도로 확장합니다.

## 핵심 로직은 `v` 함수로 분리하기

가변 인자 API를 설계할 때는 `...`를 직접 받는 함수와 `va_list`를 받는 핵심 함수를 나누는 패턴이 유용합니다.

```c
int diagnostic_vformat(
    char *buffer,
    size_t capacity,
    const char *format,
    va_list arguments
);

int diagnostic_format(
    char *buffer,
    size_t capacity,
    const char *format,
    ...
)
{
    int result;
    va_list arguments;

    va_start(arguments, format);

    result = diagnostic_vformat(
        buffer,
        capacity,
        format,
        arguments
    );

    va_end(arguments);
    return result;
}
```

이 구조에는 몇 가지 장점이 있습니다.

* 여러 가변 인자 wrapper가 같은 포맷 로직을 재사용할 수 있습니다.
* 포맷 파싱과 출력 정책을 한곳에 모을 수 있습니다.
* 이미 존재하는 `va_list`를 다른 계층으로 전달할 수 있습니다.
* `...` 자체를 다른 함수의 `...`로 직접 전달할 수 없다는 제약을 해결할 수 있습니다.

표준 라이브러리의 `printf`와 `vprintf`, `snprintf`와 `vsnprintf`도 이와 비슷한 형태의 인터페이스를 제공합니다.

## `va_list`는 순회하면서 상태가 바뀐다

`va_arg`를 호출하면 현재 목록의 읽기 위치가 다음 인자로 이동합니다.

따라서 한 번 끝까지 읽은 목록을 처음 상태로 되돌아간 것처럼 다시 사용할 수 있다고 가정해서는 안 됩니다.

전달받은 목록을 직접 소비하지 않고 독립적인 순회 상태를 만들고 싶다면 `va_copy`를 사용합니다.

```c
int diagnostic_vformat(
    char *buffer,
    size_t capacity,
    const char *format,
    va_list arguments
)
{
    int result;
    va_list copy;

    va_copy(copy, arguments);

    result = format_with_copy(
        buffer,
        capacity,
        format,
        copy
    );

    va_end(copy);
    return result;
}
```

`format_with_copy`는 `copy`를 자유롭게 소비할 수 있지만 `diagnostic_vformat`이 받은 원래 목록을 직접 순회하지는 않습니다.

`va_list`를 받는 함수는 다음 사항을 계약으로 명확히 하는 편이 좋습니다.

```text
이 함수가 전달된 목록을 직접 소비하는가?
아니면 내부에서 복사본을 만들어 원래 순회 상태를 보존하는가?
```

일반 함수의 값 전달 규칙만 보고 `va_list`도 항상 독립적인 값으로 자동 복사된다고 가정해서는 안 됩니다.

## 한 번 순회와 두 번 순회

포맷터는 크게 한 번 순회하는 방식과 두 번 순회하는 방식으로 구현할 수 있습니다.

### 한 번 순회

포맷과 인자를 한 번 읽으면서 두 작업을 동시에 수행합니다.

```text
전체 결과에 필요한 길이 계산
+
현재 버퍼에 들어가는 범위까지 실제 기록
```

예를 들어 필요한 전체 길이가 100바이트인데 버퍼에는 16바이트만 들어간다고 해도 전체 길이는 계속 100으로 계산해야 합니다.

따라서 다음 두 값을 구분해야 합니다.

```text
논리적인 전체 결과 길이
실제로 버퍼에 기록한 길이
```

이 방식은 순회가 한 번이면 되지만 형식 오류를 중간에서 발견했을 때 이미 일부 출력이 기록되어 있을 수 있습니다.

### 두 번 순회

두 패스로 나눌 수도 있습니다.

```text
첫 번째 패스
    포맷을 해석하고 필요한 전체 길이 계산

두 번째 패스
    실제 버퍼에 결과 기록
```

두 패스가 각각 가변 인자를 읽는다면 독립된 `va_list`가 필요합니다.

```c
va_list measure_arguments;
va_list write_arguments;

va_copy(measure_arguments, arguments);
va_copy(write_arguments, arguments);

/* 각각 독립적으로 순회 */

va_end(write_arguments);
va_end(measure_arguments);
```

첫 번째 패스에서 형식 오류와 전체 길이를 확인한 뒤 두 번째 패스에서 쓰기를 시작하도록 만들면 잘못된 형식 때문에 버퍼에 부분 결과가 남는 것을 피하기 쉽습니다.

반면 포맷과 인자를 두 번 순회해야 하고 구현이 길어집니다.

어느 방식을 선택하든 중요한 것은 실패했을 때 버퍼가 어떤 상태로 남는지를 API에서 명시하는 것입니다.

## 버퍼 계약

`snprintf`와 비슷한 형태의 버퍼 계약을 정의할 수 있습니다.

```text
capacity == 0
    → buffer는 NULL이어도 됨
    → buffer를 역참조하지 않음

capacity > 0
    → buffer는 최소 capacity 바이트를 쓸 수 있어야 함

성공
    → 반환값은 필요했던 전체 문자 수
      (마지막 NUL은 제외)

버퍼가 충분함
    → 전체 결과 기록
    → 마지막에 NUL 기록

버퍼가 부족함
    → 가능한 범위까지만 기록
    → 공간이 있다면 NUL 종료
    → 전체 필요 길이는 계속 계산

형식 오류 또는 반환형 범위 초과
    → -1 반환
```

여기서는 다음 세 값을 정확히 구분해야 합니다.

```text
전체 결과에 필요한 문자 수
실제로 기록된 결과 문자 수
마지막 NUL까지 포함한 버퍼 용량
```

예를 들어 `capacity == 1`이라면 일반 문자를 하나도 저장할 수 없지만 다음 상태는 만들 수 있습니다.

```c
buffer[0] = '\0';
```

반면 `capacity == 0`에서는 `buffer`에 전혀 접근하지 않습니다.

## 출력 누적기로 경계를 모으기

포맷 지시자마다 직접 용량을 검사하면 같은 경계 처리가 여러 곳에 반복됩니다.

따라서 출력 상태를 하나의 구조체에 모을 수 있습니다.

```c
struct output
{
    char *buffer;
    size_t capacity;
    size_t length;
    int failed;
};
```

여기서 `length`를 **현재까지 필요한 전체 논리적 길이**라고 정의할 수 있습니다.

문자 하나를 추가하는 helper가 다음 책임을 맡습니다.

* 전체 필요 길이를 증가시킵니다.
* `size_t` 덧셈 overflow를 검사합니다.
* 실제 버퍼에 쓸 공간이 있을 때만 기록합니다.
* 문자열 결과라면 마지막 NUL을 위한 공간을 남깁니다.
* 오류가 발생하면 이후 처리가 정해진 실패 상태를 벗어나지 않도록 합니다.

예를 들어 `%s`, `%d`와 일반 문자가 모두 동일한 `output` 인터페이스를 사용하면 버퍼 잘림과 길이 계산 정책을 한곳에서 관리할 수 있습니다.

## 길이와 반환형의 표현 범위

내부 길이를 `size_t`로 계산하더라도 공개 API의 반환형이 `int`라면 모든 `size_t` 값을 반환할 수 있는 것은 아닙니다.

따라서 두 종류의 범위를 확인해야 합니다.

```text
1. size_t 자체의 계산 overflow
2. 최종 길이가 INT_MAX를 넘는지
```

개념적인 순서는 다음과 같습니다.

```text
길이를 더하기 전에 size_t overflow 확인
→ 전체 길이 계산
→ 전체 길이가 INT_MAX 이하인지 확인
→ 안전할 때만 int로 변환
```

단순한 캐스트는 표현할 수 없는 큰 값을 안전한 값으로 바꾸지 않습니다.

공개 반환형으로 결과를 표현할 수 없다면 해당 API가 정한 오류로 처리해야 합니다.

## `INT_MIN`을 10진수로 변환하기

부호 있는 정수를 문자열로 만들 때 다음 방식은 문제가 있습니다.

```c
if (value < 0)
{
    value = -value;
}
```

`int`의 가장 작은 값인 `INT_MIN`은 대응하는 양의 크기가 `int`로 표현되지 않을 수 있습니다.

예를 들어 32비트 `int`라면 다음과 같습니다.

```text
INT_MIN = -2147483648
INT_MAX =  2147483647
```

따라서 음수를 먼저 양의 `int`로 만들려고 하지 않고 대응하는 unsigned 타입에서 magnitude를 계산할 수 있습니다.

```c
unsigned int magnitude;

if (value < 0)
{
    magnitude = 0u - (unsigned int)value;
}
else
{
    magnitude = (unsigned int)value;
}
```

부호 없는 정수의 모듈러 산술 규칙을 이용하면 `INT_MIN`의 절댓값에 해당하는 magnitude도 `unsigned int` 범위에서 표현할 수 있습니다.

이후 각 자릿수를 임시 버퍼에 역순으로 저장한 뒤 뒤집거나, 다른 방식으로 높은 자리부터 출력할 수 있습니다.

핵심은 **부호 있는 타입 안에서 표현할 수 없는 양의 값을 만들려고 하지 않는 것**입니다.

## `%c`와 문자열 내부의 NUL

이번 기본 포맷에는 `%c`가 없지만 포맷 API를 확장할 때 중요한 경계가 하나 있습니다.

예를 들어 다음 호출을 허용한다고 가정합니다.

```c
diagnostic_format(
    buffer,
    capacity,
    "A%cB",
    0
);
```

`%c`의 인자는 기본 인자 승격 때문에 `int`로 읽습니다.

충분한 공간이 있다면 결과 바이트는 다음처럼 될 수 있습니다.

```text
'A' 00 'B' 00
```

앞의 `00`은 `%c`가 출력한 데이터이고, 마지막 `00`은 결과 버퍼의 종료 NUL입니다.

이 경우 논리적인 출력 데이터에는 첫 번째 NUL 뒤에도 `'B'`가 존재합니다. 그러나 `strlen`이나 `%s`로 결과를 관찰하면 첫 NUL에서 문자열이 끝난 것으로 보입니다.

따라서 `%c`에서 NUL 문자까지 허용한다면 다음 두 개념을 구분해야 합니다.

```text
반환값이 나타내는 출력 바이트 수
C 문자열 함수로 관찰할 수 있는 접두사 길이
```

임의 바이트가 포함될 수 있는 결과를 검사할 때는 `strlen`이나 `strcmp`가 아니라 반환된 길이와 `memcmp` 같은 바이트 단위 인터페이스를 사용해야 합니다.

즉, **항상 일반적인 C 문자열로만 관찰할 수 있는 결과**와 **내부에 NUL을 포함할 수 있는 바이트 결과**는 서로 다른 계약입니다.

## 형식 오류 뒤 버퍼 상태

지원하지 않는 `%x`나 문자열 끝의 단독 `%`를 만났을 때 버퍼를 어떻게 남길지도 정해야 합니다.

가능한 정책은 여러 가지입니다.

```text
1. 버퍼를 빈 문자열로 되돌림

2. 오류를 발견하기 전까지 기록한 접두사를 유지

3. 임시 공간에서 전체 결과를 완성한 뒤
   성공했을 때만 호출자 버퍼에 반영

4. 첫 번째 패스에서 전체 포맷 문법을 검증한 뒤
   오류가 없을 때만 쓰기 시작
```

이번 연습에서는 다음 계약을 사용합니다.

```text
형식 오류 발생:
    오류 이전까지 기록된 접두사는 유지
    가능한 경우 정상적으로 NUL 종료
    반환값은 -1
```

이는 실패했을 때 호출 전 버퍼 내용을 보존하는 강한 실패 보장이 아닙니다.

대신 **버퍼 자체는 유효하게 종료된 부분 결과로 남을 수 있지만, 반환값이 음수라면 그 내용을 정상적인 포맷 결과로 사용해서는 안 된다**는 계약입니다.

이 차이를 호출자가 알 수 있도록 문서화해야 합니다.

## 포맷 문자열은 신뢰 경계다

일반적인 `printf` 계열 함수에서는 외부 입력을 포맷 문자열 자리에 직접 전달해서는 안 됩니다.

```c
printf(user_text);       /* 피해야 하는 패턴 */
printf("%s", user_text); /* 데이터를 인자로 전달 */
```

첫 번째 코드에서는 `user_text` 안의 `%`가 단순한 문자 데이터가 아니라 포맷 지시자로 해석됩니다.

그 결과 실제로 전달하지 않은 가변 인자를 읽으려고 하거나, 지원되는 포맷에 따라 메모리 접근과 같은 문제가 발생할 수 있습니다.

따라서 로그와 진단 API에서도 다음 두 역할을 분리합니다.

```text
format
    → 프로그램이 정의한 형식 계약

data
    → 출력할 외부 데이터
```

사용자 입력을 출력해야 한다면 포맷 문자열 자체로 사용하지 않고 `%s` 등의 데이터 인자로 전달합니다.

자체 포맷 함수를 구현할 때도 외부 입력을 포맷으로 허용하는지부터 신뢰 경계를 명확히 정해야 합니다.

## 컴파일러의 format 검사

GCC와 Clang 계열 컴파일러에서는 비표준 attribute를 사용해 자체 가변 인자 함수를 `printf` 계열처럼 검사하도록 만들 수 있습니다.

이를 활용하면 일부 포맷 문자열과 실제 인자의 타입 불일치를 컴파일 단계에서 발견할 수 있습니다.

하지만 이 기능은 C99 표준 자체의 기능이 아니며, 컴파일러가 이해하는 것은 해당 attribute가 지정한 표준 포맷 규칙입니다.

자체 포맷터가 다음처럼 표준 `printf`와 다른 문법을 사용한다면 주의해야 합니다.

```text
printf는 지원하지만 자체 API는 지원하지 않는 지시자
자체 API만 지원하는 별도 지시자
서로 다른 null 처리 규칙
서로 다른 길이 수정자 규칙
```

따라서 format attribute는 추가적인 정적 진단 수단으로 사용할 수 있지만 자체 API의 실제 계약과 테스트를 대신할 수는 없습니다.

## 오류 계약 점검표

가변 인자 기반 포맷 API를 설계할 때는 적어도 다음 항목을 정해야 합니다.

* `format == NULL`을 허용하는가
* `capacity > 0`인데 `buffer == NULL`이면 어떻게 처리하는가
* `capacity == 0`일 때 `buffer == NULL`을 허용하는가
* `%s`에 null 포인터가 전달되면 오류인가, 특정 문자열로 표현하는가
* 지원하지 않는 포맷 지시자를 만나면 어떤 값을 반환하는가
* 문자열 끝의 단독 `%`를 어떻게 처리하는가
* 내부 길이 계산에서 overflow가 발생하면 어떻게 처리하는가
* 전체 길이가 공개 반환형의 범위를 넘으면 어떻게 처리하는가
* 버퍼 부족을 오류로 처리하는가, 정상적인 잘림으로 처리하는가
* 잘림이 발생해도 전체 필요 길이를 반환하는가
* 형식 오류 전에 기록된 접두사는 어떤 상태로 남는가
* `va_list`를 받는 함수가 전달된 순회 상태를 소비하는가
* 원래 순회 상태를 보존해야 한다면 내부에서 `va_copy`를 사용하는가

반면 다음 항목은 같은 종류의 런타임 오류로 다뤄서는 안 됩니다.

```text
포맷이 %d라고 했는데 호출자가 double을 전달
필요한 가변 인자보다 적은 수의 인자를 전달
sentinel 계약과 다른 타입의 값을 전달
```

이런 경우는 함수가 안전하게 감지해서 오류 코드로 돌려주는 일반적인 입력 오류가 아니라 **호출자가 가변 인자 타입 계약을 위반한 것**입니다.

가변 인자 API를 안전하게 다루는 핵심은 `va_arg` 사용법 자체보다 이 경계를 분명히 이해하는 데 있습니다.

```text
컴파일러가 알고 있는 고정 매개변수의 타입
+
포맷·개수·sentinel이 제공하는 런타임 계약
+
va_list의 순차적인 소비 상태
+
실패했을 때 남겨 둘 출력 상태
```

이 네 요소를 일관되게 정의해야 타입 정보가 제한된 가변 인자 API를 예측 가능한 인터페이스로 만들 수 있습니다.

## 실습

[diagnostic-formatter](../../exercises/02-c-language/04-diagnostic-formatter/README.md)에서 다음을 구현합니다.

- `%s`, `%d`, `%%`
- 널 문자열의 `(null)` 표현
- 용량 0, 1, 정확한 크기와 잘림
- 모든 성공 경로의 NUL 종료
- `INT_MIN`, `INT_MAX`
- 지원하지 않는 지정자와 단독 `%`
- 전체 필요 길이의 overflow와 `int` 표현 범위
- `va_copy`를 이용한 원본 목록 보존

표준 `printf` 전체 재현이 아니라, 숨은 타입 계약과 소비되는 상태, 버퍼의 부분 성공을 정확히 다루는 것이 목표입니다.
