# C 메모리 모델: 포인터·수명·소유권

포인터는 주소를 나타내는 값을 저장하지만, 주소값만으로 접근의 유효성을 판단할 수는 없습니다. 포인터를 안전하게 사용하려면 그 포인터가 어떤 객체를 가리키는지, 객체의 수명이 끝나지 않았는지, 접근 가능한 범위가 어디까지인지, 읽기와 쓰기 중 무엇이 허용되는지, 그리고 동적으로 확보한 자원이라면 누가 해제할 책임을 갖는지까지 함께 추적해야 합니다.

## 객체·주소·수명

```c
int number = 42;
int *pointer = &number;
```

`number`는 타입과 값을 가지며 일정한 저장 공간과 수명을 갖는 객체입니다. `pointer` 역시 별도의 객체이며, 그 값으로 `number`를 가리키는 포인터를 저장하고 있습니다.

```c
printf("%d\n", *pointer);
*pointer = 7;
```

포인터를 간접 참조하려면 적어도 다음 조건을 만족해야 합니다.

1. 포인터가 해당 접근에 적합한 타입과 정렬을 가진 객체를 가리켜야 합니다.
2. 그 객체의 수명이 아직 끝나지 않아야 합니다.
3. 접근 위치가 해당 객체 또는 배열에서 허용되는 범위 안에 있어야 합니다.
4. 수행하려는 읽기 또는 쓰기가 해당 객체에 허용되어야 합니다.

포인터 값이 존재한다는 사실과 그 포인터를 안전하게 간접 참조할 수 있다는 사실은 서로 다릅니다.

## null 포인터와 dangling 포인터는 다르다

null 포인터는 어떤 객체도 가리키지 않는 포인터 값입니다. null 포인터를 간접 참조해서는 안 됩니다.

그러나 포인터가 null이 아니라는 사실만으로 유효한 객체를 가리킨다고 판단할 수도 없습니다.

```c
int *bad_pointer(void)
{
    int local = 10;
    return &local;
}
```

`local`은 함수가 반환되면 수명이 끝나는 자동 저장 기간의 객체입니다. 따라서 반환된 포인터는 더 이상 살아 있는 객체를 가리키지 않는 dangling 포인터가 됩니다.

동적으로 할당한 객체를 `free`한 뒤에도 같은 문제가 발생합니다.

```c
free(pointer);
pointer = NULL;
```

`pointer`를 `NULL`로 바꾸면 이 변수 자체를 다시 잘못 사용하는 위험은 줄일 수 있습니다. 하지만 같은 객체를 가리키던 다른 포인터까지 자동으로 변경되는 것은 아닙니다. 다른 별칭은 여전히 dangling 상태로 남아 있을 수 있습니다.

## 값 전달과 출력 매개변수

C의 함수 인자는 값으로 전달됩니다. 포인터 역시 예외가 아닙니다.

```c
int allocate_int(int **out_value)
{
    int *value = malloc(sizeof *value);

    if (value == NULL)
    {
        return -1;
    }

    *value = 0;
    *out_value = value;
    return 0;
}
```

호출자가 가진 포인터 자체를 변경하려면 그 포인터의 주소를 전달해야 하므로 `int **`와 같은 형태가 필요합니다.

출력 매개변수를 사용하는 API에서는 가능한 한 작업이 성공한 뒤에 결과를 기록하는 편이 좋습니다. 위 함수는 메모리 할당에 실패하면 `*out_value`를 건드리지 않으므로 호출자가 기존 상태를 그대로 유지할 수 있습니다.

이러한 실패 계약은 함수마다 일관되게 정해 두어야 합니다.

## 배열과 포인터

```c
int values[4] = {10, 20, 30, 40};
```

`values`는 네 개의 `int` 원소로 이루어진 하나의 배열 객체입니다.

배열과 포인터는 같은 것이 아닙니다. 배열은 자신의 크기와 저장 공간을 갖는 객체이며, 포인터 변수와는 `sizeof`의 결과, 대입 가능 여부와 객체의 성질이 다릅니다.

다만 배열 이름은 대부분의 식에서 첫 번째 원소를 가리키는 포인터로 변환됩니다.

```c
size_t count = sizeof values / sizeof values[0];

int *begin = values;
int *end = values + count;
```

`end`는 배열의 마지막 원소 바로 다음 위치를 가리키는 one-past 포인터입니다. 이러한 포인터를 만들고 같은 배열을 기준으로 비교하는 것은 허용되지만, `*end`처럼 간접 참조해서는 안 됩니다.

포인터 산술 역시 기본적으로 하나의 배열 객체와 그 바로 다음 위치의 범위 안에서만 다뤄야 합니다.

함수에 배열을 전달한다고 해서 배열의 길이가 함께 전달되는 것은 아닙니다.

```c
void process(const int *values, size_t count);
```

필요한 길이는 별도의 인자로 전달하고, 포인터와 길이를 하나의 계약으로 관리합니다.

## 문자열의 불변식

C 문자열은 접근 가능한 문자 배열 안에 NUL 문자 `'\0'`로 끝나는 문자열 표현을 갖습니다.

용량을 별도로 관리하는 문자열 버퍼라면 다음과 같은 불변식을 정할 수 있습니다.

```text
length < capacity
data[length] == '\0'
```

`strlen`은 NUL 문자를 만날 때까지 계속 메모리를 읽습니다. 따라서 접근 가능한 범위 안에 NUL 종료가 존재하지 않는 버퍼를 `strlen`에 전달하면 허용된 범위를 벗어나 읽을 수 있습니다.

문자열을 복사하거나 연결할 때도 실제 문자 수뿐 아니라 마지막 NUL 문자 한 바이트까지 저장할 공간이 필요합니다.

`memcpy`와 `memmove` 역시 크기를 자동으로 검사하지 않습니다.

* 원본과 대상 범위가 겹치지 않을 때는 `memcpy`를 사용할 수 있습니다.
* 두 범위가 겹칠 가능성이 있다면 `memmove`를 사용해야 합니다.

어느 함수를 사용하든 호출자가 읽을 범위와 쓸 범위가 모두 유효한지 먼저 보장해야 합니다.

## 동적 메모리와 소유권

```c
char *copy = malloc(length + 1);
```

동적 메모리를 확보했다면 단순히 포인터값만 추적해서는 부족합니다. 코드에서 다음 질문에 답할 수 있어야 합니다.

* 현재 이 할당을 소유하는 것은 누구인가?
* 어느 코드가 최종적으로 `free`할 책임을 갖는가?
* 소유권이 다른 객체나 함수로 이전되는가?
* 모든 성공·실패 경로에서 정확히 한 번만 해제되는가?
* 빌려준 포인터가 원래 소유 객체보다 오래 남지는 않는가?

C에는 소유권을 자동으로 추적하거나 강제하는 언어 기능이 없습니다. 따라서 소유권은 함수 계약, 자료구조와 제어 흐름을 통해 프로그램이 직접 표현해야 합니다.

## `realloc`의 실패 계약

다음 패턴은 피해야 합니다.

```c
buffer = realloc(buffer, new_capacity);

if (buffer == NULL)
{
    /* 기존 포인터를 잃을 수 있음 */
}
```

크기가 0보다 큰 재할당이라면 다음처럼 임시 포인터를 사용합니다.

```c
char *resized;

resized = realloc(buffer, new_capacity);
if (resized == NULL)
{
    return -1;
}

buffer = resized;
```

`new_capacity > 0`인 일반적인 재할당에서 `realloc`이 실패하면 기존 할당은 그대로 유지됩니다. 결과를 기존 포인터에 바로 대입하면 실패했을 때 원래 할당을 가리키던 유일한 포인터를 잃어 메모리 누수가 발생할 수 있습니다.

따라서 성공 여부를 확인한 뒤에만 소유 포인터를 교체합니다.

크기 0을 `realloc`에 전달하는 경우에는 별도의 규칙과 구현별 동작이 개입할 수 있으므로, 일반적인 버퍼 성장 코드에서는 크기 0을 별도로 처리하는 편이 명확합니다.

## 할당 크기의 overflow

다음과 같은 배열 할당에서는 곱셈 자체가 표현 가능한 범위를 벗어나는지 먼저 확인해야 합니다.

```c
if (count > SIZE_MAX / sizeof *items)
{
    return -1;
}

items = malloc(count * sizeof *items);
```

먼저 곱셈을 수행한 뒤 결과가 이상한지 검사하는 방식은 올바르지 않습니다. 부호 없는 정수 연산은 이미 작은 값으로 되돌아간 뒤일 수 있기 때문입니다.

따라서 연산을 수행하기 전에 나눗셈 등을 이용해 가능한 범위를 확인합니다.

문자열 크기를 계산할 때의 덧셈도 마찬가지입니다.

```c
if (left_length > SIZE_MAX - right_length - 1)
{
    return -1;
}
```

메모리 안전성은 포인터뿐 아니라 포인터가 사용할 크기 계산에서부터 시작합니다.

## 포인터 선언과 `const`

선언에서 `*`는 포인터 타입을 나타내고, 식에서 `*`는 포인터가 가리키는 객체에 접근하는 간접 참조 연산자입니다.

```c
int *value_pointer;
const char *read_only_view;
int **out_pointer;
```

`const`의 위치도 인터페이스 계약의 일부입니다.

```c
const char *text;         /* text를 통해 문자를 수정하지 않음 */
char *const fixed = buf;  /* fixed 자체가 가리키는 주소를 바꾸지 않음 */
const char *const both = text;
```

`const`는 소유권이나 수명을 나타내지 않습니다.

`const char *`만 보고 그 포인터가 문자열 리터럴을 가리키는지, 호출자가 소유한 메모리를 잠시 빌린 것인지, 다른 객체가 소유한 동적 메모리를 가리키는지 알 수는 없습니다. 이러한 정보는 별도의 API 계약으로 정해야 합니다.

다중 포인터에서는 각 간접 참조 단계의 수정 가능성을 따로 고려해야 합니다.

예를 들어 `char **`를 `const char **`로 단순히 호환되는 타입이라고 생각해서는 안 됩니다. 이러한 변환이 허용된다면 수정 가능한 포인터 슬롯을 통해 실제로는 수정할 수 없는 객체를 가리키는 주소를 저장하는 경로가 생길 수 있기 때문입니다.

## 2차원 배열과 포인터 배열

```c
int matrix[3][4];
```

`matrix`는 `int[4]` 배열 세 개가 연속해서 들어 있는 하나의 배열 객체입니다.

대부분의 식에서 `matrix`가 포인터로 변환될 때 그 타입은 첫 행을 가리키는 다음 형태가 됩니다.

```c
int (*)[4]
```

따라서 함수는 다음처럼 받을 수 있습니다.

```c
void print_matrix(const int matrix[][4], size_t rows);
```

다음 선언은 전혀 다른 구조입니다.

```c
char *words[4];
```

`words`는 네 개의 포인터를 원소로 갖는 배열이며, 각각의 포인터가 서로 다른 문자 배열을 가리킬 수 있습니다.

따라서 `int **`는 일반적인 `int[3][4]` 배열을 대신하는 타입이 아닙니다. 둘은 실제 메모리 배치와 포인터 산술 방식이 다릅니다.

함수의 매개변수 타입은 데이터가 겉으로 몇 차원처럼 보이는지가 아니라 실제 객체가 메모리에 어떻게 배치되어 있는지에 맞춰 정해야 합니다.

## 바이트 표현·정렬·별칭

`void *`는 특정 객체 타입에 종속되지 않는 객체 포인터 인터페이스가 필요할 때 사용합니다.

```c
void *memory;
```

`void *` 자체로는 가리키는 객체를 간접 참조할 수 없습니다. 실제 접근에는 어떤 타입의 객체인지에 대한 별도의 계약이 필요합니다.

객체의 저장된 바이트 표현을 확인할 때는 문자 타입을 이용할 수 있습니다.

```c
const unsigned char *bytes =
    (const unsigned char *)&number;
```

반면 주소를 임의의 다른 객체 타입 포인터로 캐스트한 뒤 읽는 것은 별개의 문제입니다. 해당 접근은 정렬 조건과 객체의 타입·별칭 규칙을 만족해야 합니다.

즉, 문법적으로 포인터 캐스트를 작성할 수 있다는 사실이 그 포인터를 간접 참조하는 행위까지 정의되어 있다는 뜻은 아닙니다.

이 때문에 구조체의 메모리 내용을 그대로 파일이나 네트워크 형식으로 사용하는 것도 피해야 합니다.

구조체 표현에는 다음과 같은 구현 의존 요소가 포함될 수 있습니다.

* padding
* 정렬
* 정수 타입의 크기
* 바이트 순서

지속적으로 사용할 직렬화 형식은 필드의 크기와 표현 순서를 별도로 정의해야 합니다.

## 문자열과 바이트 버퍼 구분

모든 `char *`가 C 문자열인 것은 아닙니다.

문자열 함수는 전달된 메모리가 접근 가능한 범위 안에서 NUL 문자로 종료된다는 선행조건을 요구합니다.

```c
char data[4] = {'A', '\0', 'B', '\0'};
```

이 배열에는 네 바이트가 저장되어 있지만 다음 결과는 `1`입니다.

```c
strlen(data)
```

문자열 길이는 첫 번째 NUL 문자 전까지의 문자 수이기 때문입니다.

따라서 다음 두 값은 구분해야 합니다.

* 메모리에 저장된 바이트 수
* C 문자열로 해석했을 때의 문자열 길이

문자열 리터럴의 내용을 수정해서는 안 됩니다.

```c
const char *name = "reader";
```

문자열 함수와 바이트 함수 역시 요구하는 계약이 다릅니다.

* `strlen`, `strcmp`, `strchr` 등은 유효한 NUL 종료 문자열을 요구합니다.
* `memcpy`, `memmove`, `memcmp` 등은 명시적으로 전달한 바이트 수만 사용합니다.

범위가 겹치지 않는 것이 보장되면 `memcpy`, 겹칠 가능성이 있다면 `memmove`를 사용합니다. 임의의 바이트 배열을 비교할 때는 문자열 함수가 아니라 길이와 `memcmp` 같은 바이트 단위 인터페이스를 사용합니다.

`strcpy`는 대상 버퍼의 용량을 알지 못합니다.

`strncpy` 역시 일반적인 의미의 "안전한 `strcpy`"가 아닙니다. 지정한 범위 안에 원본의 NUL 문자가 없으면 결과의 NUL 종료를 보장하지 않으며, 원본 문자열이 짧으면 남은 영역을 NUL 바이트로 채우는 별도의 동작도 수행합니다.

따라서 필요한 크기를 먼저 계산하거나, 버퍼 용량을 명시적으로 받는 인터페이스를 설계하는 편이 더 명확합니다.

`strdup`은 널리 사용되지만 ISO C99가 정의하는 함수는 아닙니다. POSIX 인터페이스를 사용할지, 필요한 복제 함수를 프로젝트 내부에서 제공할지는 프로젝트의 이식성 기준에 따라 결정합니다.

## `malloc`·`calloc`·`free`

```c
int *items = malloc(count * sizeof *items);
```

C에서는 `malloc`이 반환하는 `void *`를 객체 포인터 타입으로 암시적으로 변환할 수 있으므로 불필요한 캐스트를 추가하지 않는 것이 일반적입니다.

`sizeof *items`처럼 작성하면 `items`가 가리키는 타입이 바뀌었을 때 크기 계산도 함께 따라가므로 타입 이름을 반복해서 적는 방식보다 오류 가능성을 줄일 수 있습니다.

각 함수의 기본 성질은 다음과 같습니다.

* `malloc`은 요청한 크기의 저장 공간을 제공하며 그 내용은 초기화되어 있지 않습니다.
* `calloc(count, size)`은 원소 수와 원소 크기를 별도로 전달받아 저장 공간을 확보하고 모든 비트를 0으로 초기화합니다.
* `free(NULL)`은 아무 동작도 하지 않습니다.
* `free`는 동적으로 할당한 객체의 수명을 끝내지만 같은 객체를 가리키던 다른 포인터를 자동으로 변경하지 않습니다.

`calloc`은 두 크기 인수를 별도로 받기 때문에 호출자가 `count * size`를 먼저 계산해서 넘길 필요가 없습니다. 그러나 반환값이 `NULL`인지 확인해야 한다는 점은 다른 할당 함수와 같습니다.

크기가 0인 할당의 반환값에 프로그램 고유의 의미를 부여하는 것도 피하는 편이 좋습니다. 예를 들어 빈 컨테이너 상태를 다음처럼 명시적으로 표현하면 구현의 세부 동작에 덜 의존할 수 있습니다.

```text
data == NULL
length == 0
capacity == 0
```

## 소유권을 API에 기록하기

포인터를 전달하거나 반환하는 API에서는 각각의 포인터가 어떤 역할을 갖는지 정해 두는 것이 좋습니다.

| 역할 | 함수의 동작            | 호출 이후의 책임                |
| -- | ----------------- | ------------------------ |
| 빌림 | 기존 객체를 잠시 참조      | 기존 소유자가 계속 관리            |
| 복제 | 별도의 객체를 새로 할당     | 새 소유자가 새 객체를 해제          |
| 이전 | 기존 객체의 소유권을 받음    | 성공 이후 이전 소유자는 사용·해제하지 않음 |
| 분리 | 보관하던 객체의 소유권을 내보냄 | 반환받은 쪽이 새 소유자가 됨         |

예를 들어 다음 함수가 있다고 가정합니다.

```c
int string_join(
    const char *left,
    const char *right,
    char **out_result
);
```

이 API의 계약은 다음처럼 정의할 수 있습니다.

* `left`와 `right`는 함수 호출 동안만 빌려 사용합니다.
* 함수는 두 문자열의 소유권을 가져가지 않습니다.
* 성공하면 `*out_result`는 새로 할당한 문자열을 가리킵니다.
* 호출자가 최종적으로 `free(*out_result)`해야 합니다.
* 실패하면 `*out_result`를 변경하지 않습니다.

소유권 규칙은 함수 이름, `const`, 문서와 실제 호출 패턴에서 일관되게 드러나야 합니다.

## 실패 중 상태 교체

동적 자원을 소유하는 객체의 상태를 변경할 때는 가능한 한 새 상태를 먼저 완성한 뒤 기존 상태를 교체하는 구조를 사용합니다.

```text
필요한 크기와 overflow 확인
→ 새 자원 확보
→ 새 상태 구성
→ 객체의 상태 교체
→ 이전 자원 정리
```

새 자원을 확보하기도 전에 기존 객체의 필드를 변경하면 이후 작업이 실패했을 때 호출자에게 불완전한 중간 상태를 남길 수 있습니다.

모든 API가 실패 시 기존 상태를 완전히 보존할 필요는 없습니다. 그러나 적어도 다음 중 어떤 계약을 제공하는지는 명확해야 합니다.

* 실패하면 호출 전 상태를 그대로 유지한다.
* 실패하더라도 객체는 유효하지만 일부 상태가 변경될 수 있다.
* 실패 이후 객체는 정상적으로 재사용할 수 없으며 정리만 허용한다.

호출자는 이 실패 계약을 알아야 이후 동작을 안전하게 결정할 수 있습니다.

## 흔한 결함 점검표

다음은 포인터와 동적 메모리를 다룰 때 반복해서 발생하는 오류입니다.

* 초기화하지 않은 포인터 간접 참조
* 수명이 끝날 지역 객체의 주소 반환
* `free`한 객체를 다시 사용
* 같은 동적 객체를 두 번 해제
* 배열 길이가 함수에 자동으로 전달된다고 가정
* one-past 포인터 간접 참조
* 문자열 용량에서 마지막 NUL 한 바이트 누락
* 일반 바이트 버퍼를 C 문자열로 취급
* 서로 겹치는 영역에 `memcpy` 사용
* 할당 크기의 overflow를 연산 후에 검사
* `realloc` 결과를 기존 소유 포인터에 바로 대입
* 재할당될 수 있는 버퍼의 내부 주소를 장기간 보관
* 빌린 포인터를 자신이 소유한 것처럼 `free`

AddressSanitizer와 UndefinedBehaviorSanitizer는 이러한 문제 가운데 많은 부분을 발견하는 데 도움이 됩니다.

하지만 실행하지 않은 코드 경로까지 검사하지는 않으며, 잘못 작성된 소유권 계약이나 API 설계를 자동으로 바로잡아 주지도 않습니다.

도구의 진단과 별개로 코드가 어떤 객체를 소유하고 언제 그 소유권을 이전하는지 사람이 추적할 수 있어야 합니다.

## 성장 가능한 소유 문자열

다음과 같이 자신의 동적 버퍼를 소유하는 문자열 구조체를 생각할 수 있습니다.

```c
struct owned_string
{
    char *data;
    size_t length;
    size_t capacity;
};
```

이 구조체의 유효 상태를 다음처럼 정의할 수 있습니다.

```text
빈 상태:
  data == NULL
  length == 0
  capacity == 0

할당 상태:
  data != NULL
  length < capacity
  data[length] == '\0'
```

`append`가 강한 실패 보장을 제공한다면 계약은 다음과 같습니다.

```text
성공:
  새 문자열과 length, capacity를 모두 반영

실패:
  호출 전 data, 내용, length, capacity를 모두 보존
```

이러한 버퍼에서는 자기 자신의 데이터를 다시 입력으로 사용하는 경우도 주의해야 합니다.

예를 들어 `data` 전체나 `data` 내부의 일부 영역을 `append`의 원본으로 전달했다고 가정합니다. 버퍼 확장 과정에서 `realloc`이 메모리를 다른 위치로 옮기면 이전에 저장해 둔 내부 포인터는 더 이상 유효하지 않습니다.

따라서 원본이 현재 버퍼 내부를 가리킬 수 있다면 재할당 전에 버퍼 시작점으로부터의 offset을 기록하고, 재할당에 성공한 뒤 새로운 `data`를 기준으로 원본 위치를 다시 계산해야 합니다.

이 문제는 성장 가능한 배열이나 문자열 내부의 원소 주소를 외부에서 장기간 보관할 때도 동일하게 발생합니다.

## 정리 함수는 반복 호출 가능하게 만들기

동적 자원을 소유하는 객체의 정리 함수는 객체를 다시 명확한 빈 상태로 되돌리도록 만들면 사용하기 편합니다.

```c
void owned_string_destroy(struct owned_string *string)
{
    free(string->data);

    string->data = NULL;
    string->length = 0;
    string->capacity = 0;
}
```

`free(NULL)`은 안전하므로 위 함수가 정상적인 빈 상태를 유지한다면 같은 객체에 대해 다시 호출해도 문제가 발생하지 않습니다.

정리 이후 객체를 명확한 빈 상태로 되돌리는 구조는 특히 다음 상황에서 유용합니다.

* 부분적으로만 초기화된 객체를 정리할 때
* 여러 단계의 초기화 중 오류가 발생했을 때
* 하나의 공통 오류 경로에서 자원을 정리할 때
* 이미 정리된 객체를 다시 정리할 가능성이 있을 때

중요한 것은 단순히 모든 포인터를 `NULL`로 만드는 것이 아니라, 구조체 전체가 다시 정의된 유효 상태를 만족하도록 만드는 것입니다.
