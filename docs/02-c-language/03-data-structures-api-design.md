# 자료구조와 API 설계: 불변식·소유권·실패 보장

자료구조를 구현할 때 중요한 것은 어떤 필드를 둘지 정하는 것만이 아닙니다. 객체가 유효하려면 어떤 조건을 항상 만족해야 하는지 정의하고, 모든 공개 연산이 그 조건을 깨뜨리지 않도록 만드는 것이 핵심입니다.

API 역시 정상적인 결과만 정의해서는 부족합니다. 잘못된 인자, 범위 오류, 메모리 부족과 같은 실패가 발생했을 때 반환값뿐 아니라 객체와 출력 인자가 어떤 상태로 남는지도 계약에 포함해야 합니다.

## `struct`, `typedef`와 `enum`

구조체 객체는 다른 구조체 객체에 대입하거나 함수의 인자와 반환값으로 사용할 수 있습니다.

```c
struct point
{
    int x;
    int y;
};

struct point first = {1, 2};
struct point second = first;
```

구조체 대입은 각 멤버의 값을 복사합니다. 그러나 포인터 멤버가 있다고 해서 그 포인터가 가리키는 자원까지 복제되는 것은 아닙니다.

```c
struct user
{
    char *name;
};
```

예를 들어 다음 대입 뒤에는 두 구조체의 `name`이 같은 할당을 가리킬 수 있습니다.

```c
struct user second = first;
```

이 상태에서 `first`와 `second`를 서로 독립된 소유자로 취급해 각각 같은 메모리를 해제하면 이중 해제가 발생합니다.

독립적인 복사본이 필요하다면 별도의 깊은 복사 연산과 그 실패 계약을 정의해야 합니다.

```c
int user_clone(
    const struct user *source,
    struct user *out_user
);
```

`typedef`는 기존 타입에 다른 이름을 붙일 뿐, 그 타입에 새로운 소유권 의미를 부여하지 않습니다.

특히 포인터 타입 자체를 `typedef`로 숨기면 간접 참조 수준, null 가능성, 소유 여부가 코드에서 잘 드러나지 않을 수 있으므로 신중하게 사용합니다.

`enum`은 상태와 결과를 의미 있는 이름으로 표현할 때 유용합니다.

```c
enum parse_status
{
    PARSE_OK,
    PARSE_EMPTY,
    PARSE_INVALID,
    PARSE_NO_MEMORY
};
```

다만 열거형의 실제 크기와 내부 표현은 외부 저장 형식의 일부로 가정하지 않습니다. 파일이나 네트워크 프로토콜에서는 별도의 명시적인 표현을 정의합니다.

## 값 객체와 자원 소유 객체

다음과 같은 구조체는 단순한 값 객체로 다루기 쉽습니다.

```c
struct rectangle
{
    int width;
    int height;
};
```

모든 멤버가 값 자체이므로 일반적인 구조체 복사가 자연스럽습니다.

반면 동적 메모리, 파일 디스크립터, mutex와 같은 외부 자원을 보유하는 구조체에는 별도의 수명과 소유권 규칙이 필요합니다.

```c
struct document
{
    char *text;
    size_t length;
};
```

이런 객체에는 보통 다음과 같은 함수군을 둡니다.

```c
void document_init(struct document *document);
void document_destroy(struct document *document);

int document_set(
    struct document *document,
    const char *text
);

int document_clone(
    const struct document *source,
    struct document *out_document
);
```

`init`과 `destroy`를 사용하는 인터페이스에서는 보통 호출자가 구조체 자체의 저장 공간을 준비하고 구현은 그 내부 자원만 관리합니다.

반면 `create`와 `destroy`를 사용하는 인터페이스에서는 구현이 객체 자체까지 동적으로 할당할 수도 있습니다.

이름만으로 모든 계약을 추측하게 해서는 안 됩니다. `destroy`가 내부 자원만 해제하는지, 객체 자체까지 해제하는지도 명확히 정해야 합니다.

구조체 전체를 0으로 채우는 방식 역시 모든 타입에 사용할 수 있는 일반적인 초기화 방법은 아닙니다.

포인터와 길이만 가진 단순한 구조체에는 적절할 수 있지만, 파일 디스크립터에서 `0`은 유효한 값이고 mutex나 외부 라이브러리의 핸들은 전용 초기화 함수가 필요할 수 있습니다.

각 자원에 맞는 유효한 초기 상태를 별도로 정의해야 합니다.

## 소유권을 드러내는 동사

함수 이름만으로 계약 전체를 표현할 수는 없지만, 일관된 동사를 사용하면 호출자의 오해를 줄일 수 있습니다.

| 동사        | 일반적으로 기대하는 의미             |
| --------- | ------------------------- |
| `init`    | 이미 존재하는 객체를 유효한 초기 상태로 만듦 |
| `create`  | 객체나 자원을 새로 만들고 소유권을 제공    |
| `clone`   | 원본과 독립적으로 정리할 수 있는 복사본 생성 |
| `take`    | 성공하면 전달받은 자원의 소유권을 가져감    |
| `release` | 보유하던 소유권을 호출자에게 넘김        |
| `destroy` | 객체가 소유한 자원을 정리            |

이 의미는 관례일 뿐 언어가 강제하는 규칙은 아닙니다. 프로젝트 안에서 의미를 정했다면 일관되게 사용해야 합니다.

함수 문서에는 이름과 함께 다음 항목을 명확히 기록합니다.

* null 인자를 허용하는가
* 입력 포인터를 빌리는가, 복제하는가, 소유권을 넘겨받는가
* 성공 이후 어느 쪽이 자원을 소유하는가
* 실패하면 소유권이 이동하는가
* 출력 인자와 입력 객체는 어떤 상태로 남는가

## 동적 배열의 불변식

다음과 같은 동적 배열을 생각할 수 있습니다.

```c
struct int_vector
{
    int *data;
    size_t size;
    size_t capacity;
};
```

이 구현에서는 다음과 같은 불변식을 정할 수 있습니다.

```text
size <= capacity

capacity == 0이면
    data == NULL

capacity > 0이면
    data는 최소 capacity개의 int를 저장할 수 있는 영역을 가리킴

0 <= i < size인 원소는 유효한 값으로 초기화되어 있음
```

이 조건은 C 언어가 정해 주는 것이 아니라 해당 자료구조가 스스로 정하는 계약입니다.

유효한 `int_vector`를 받는 공개 연산은 함수 진입 시 이 불변식을 전제로 하며, 성공적으로 반환할 때도 다시 같은 불변식을 만족해야 합니다.

실패 시에도 최소한 문서에서 약속한 상태 조건은 유지해야 합니다.

## API를 상태 전이로 보기

자료구조의 연산은 값을 계산하는 함수라기보다 객체의 상태를 다른 상태로 바꾸는 연산으로 볼 수 있습니다.

예를 들어 `push`의 계약을 다음처럼 표현할 수 있습니다.

```text
초기 상태:
    유효한 vector V
    추가할 값 x

성공:
    기존 원소는 유지됨
    마지막 원소가 x가 됨
    size가 1 증가함

실패:
    문서에서 약속한 실패 상태를 만족함
```

실패 보장은 크게 두 수준으로 구분해서 생각할 수 있습니다.

**기본 보장(basic guarantee)**은 연산에 실패하더라도 객체가 여전히 유효하며 이후 정리하거나 다시 사용할 수 있음을 의미합니다. 다만 일부 상태는 바뀌었을 수 있습니다.

**강한 보장(strong guarantee)**은 연산에 실패하면 호출 전의 관찰 가능한 상태를 그대로 유지한다는 의미입니다.

작은 동적 컨테이너의 `push`는 새 자원 확보와 검증을 먼저 수행하고 마지막에 상태를 교체하면 비교적 쉽게 강한 실패 보장을 제공할 수 있습니다.

## 소유·빌림·이전

포인터를 사용하는 API에서는 각 포인터의 역할을 명확히 구분합니다.

* **owned**: 함수나 객체가 자원의 해제 책임을 가집니다.
* **borrowed const**: 자원을 소유하지 않으며 호출 동안 읽기만 합니다.
* **borrowed mutable**: 자원을 소유하지 않지만 허용된 범위에서 수정할 수 있습니다.
* **transferred**: 성공을 기준으로 자원의 해제 책임이 다른 쪽으로 이동합니다.

예를 들어 다음 함수가 있다고 가정합니다.

```c
int vector_get(
    const struct int_vector *vector,
    size_t index,
    int *out_value
);
```

이 인터페이스에서 `vector`는 읽기 전용으로 빌린 객체입니다.

`out_value`는 호출자가 소유하는 쓰기 가능한 객체를 가리킵니다. 함수는 두 포인터가 가리키는 어떤 자원도 해제하지 않습니다.

이처럼 포인터 타입만으로 드러나지 않는 정보는 API 계약으로 보완해야 합니다.

## 출력 매개변수의 실패 보존

출력 매개변수를 사용하는 함수에서는 모든 검증을 끝낸 뒤 결과를 쓰는 구조가 유용합니다.

```c
int vector_get(
    const struct int_vector *vector,
    size_t index,
    int *out_value
)
{
    if (vector == NULL ||
        out_value == NULL ||
        index >= vector->size)
    {
        return -1;
    }

    *out_value = vector->data[index];
    return 0;
}
```

이 함수는 실패할 경우 `*out_value`를 변경하지 않습니다.

따라서 문서에서 이 동작을 보장한다면 호출자는 다음과 같이 실패 전의 값을 그대로 사용할 수 있습니다.

```text
성공:
    out_value에 결과 기록

실패:
    out_value의 기존 값 유지
```

출력 인자를 언제 변경하는지까지 API 계약의 일부로 보는 것이 중요합니다.

## opaque type과 공개 구조체

작은 교육용 자료구조에서는 내부 필드를 공개해 불변식과 메모리 배치를 직접 관찰하게 할 수 있습니다.

반대로 라이브러리에서는 구조체 정의를 숨기고 불완전 타입만 공개할 수 있습니다.

```c
struct int_vector;

struct int_vector *int_vector_create(void);
void int_vector_destroy(struct int_vector *vector);
```

이 방식에서는 호출자가 내부 필드에 직접 접근할 수 없으므로 구현이 불변식을 통제하기 쉽고, 내부 표현을 변경할 여지도 커집니다.

대신 새로운 계약도 생깁니다.

* 객체를 누가 할당하는가
* 생성 실패는 어떻게 표현하는가
* 객체의 실제 크기를 호출자가 알아야 하는가
* 라이브러리 버전 사이에서 ABI를 어떻게 유지하는가
* 반환된 내부 view가 존재한다면 언제까지 유효한가

필드를 공개하는 방식과 숨기는 방식 중 어느 하나가 항상 우월한 것은 아닙니다. 외부에서 어느 수준까지 구현 세부 사항에 의존하도록 허용할지에 따라 선택합니다.

## 용량 증가 정책

동적 배열의 용량을 원소 하나가 추가될 때마다 정확히 한 칸씩 늘리면 반복적인 재할당과 복사가 발생할 수 있습니다.

따라서 보통은 다음처럼 기하급수적으로 용량을 늘립니다.

```text
0 → 4 → 8 → 16 → 32
```

용량을 늘리기 전에는 다음을 확인해야 합니다.

* 증가 계산 자체가 `SIZE_MAX`를 넘지 않는가
* `new_capacity * sizeof(element)`가 표현 가능한 범위를 넘지 않는가
* 할당이 실패했을 때 기존 `data`, `size`, `capacity`를 유지할 수 있는가
* 구현이 허용하는 최대 용량을 넘지 않는가

예를 들어 단순히 다음 계산부터 수행해서는 안 됩니다.

```c
new_capacity = vector->capacity * 2;
```

곱셈 전에 범위를 확인해야 합니다.

용량 증가 비율 자체는 보통 구현 세부 사항입니다. 그러나 이 정책은 재할당 빈도, 메모리 상한, 실패 가능 지점과 포인터 무효화 시점에 영향을 줍니다.

따라서 외부 코드가 이러한 특성에 의존해야 한다면 그 부분만 별도의 API 계약으로 명시해야 합니다.

## 부분 초기화와 정리

여러 자원을 차례대로 확보하는 초기화 함수는 중간 단계에서 실패할 수 있습니다.

```c
int component_init(struct component *component)
{
    component->buffer = NULL;
    component->fd = -1;

    component->buffer = malloc(1024);
    if (component->buffer == NULL)
    {
        return -1;
    }

    component->fd = open(...);
    if (component->fd == -1)
    {
        component_destroy(component);
        return -1;
    }

    return 0;
}
```

이 패턴에서는 각 필드를 먼저 정리 가능한 초기 상태로 만들어 둡니다.

예를 들어 다음과 같은 규칙을 사용할 수 있습니다.

```text
buffer == NULL
    → 할당된 버퍼 없음

fd == -1
    → 열린 파일 디스크립터 없음
```

그러면 `component_destroy` 하나가 완전히 초기화된 객체뿐 아니라 일부 자원만 확보한 객체도 처리할 수 있습니다.

여러 자원을 확보했다면 일반적으로 획득한 순서의 반대로 정리합니다.

중요한 것은 특정 `goto` 패턴이나 함수 형태가 아니라, 어느 단계에서 실패하더라도 지금까지 확보한 자원을 정확히 한 번씩 정리할 수 있는 구조를 만드는 것입니다.

## 오류 코드 설계

내부 함수라면 성공과 실패만 구분하는 것으로 충분할 수 있습니다.

```c
return 0;
return -1;
```

반면 호출자가 실패 원인에 따라 실제로 다른 복구 동작을 해야 한다면 결과 타입을 세분화할 수 있습니다.

```c
enum vector_result
{
    VECTOR_OK = 0,
    VECTOR_INVALID = -1,
    VECTOR_NO_MEMORY = -2,
    VECTOR_RANGE = -3
};
```

예를 들어 호출자는 다음처럼 다른 행동을 할 수 있습니다.

```text
VECTOR_RANGE
    → 입력 인덱스를 오류로 처리

VECTOR_NO_MEMORY
    → 상위 계층에 자원 부족 전달

VECTOR_INVALID
    → 호출 계약 위반 처리
```

오류 종류를 늘리면 그만큼 API와 테스트의 상태 공간도 커집니다.

호출자가 동일하게 처리할 실패를 단지 더 자세히 구분하기 위해 오류 코드를 늘릴 필요는 없습니다. 실제 복구 행동이나 사용자에게 전달할 의미가 달라질 때 구분하는 편이 좋습니다.

## allocator 주입

메모리 부족 테스트를 실제 시스템의 메모리 상태에 의존하면 특정 실패 지점을 재현하기 어렵습니다.

필요하다면 메모리 연산을 추상화해 테스트에서 교체할 수 있습니다.

```c
struct allocator
{
    void *context;

    void *(*resize)(
        void *context,
        void *pointer,
        size_t size
    );

    void (*release)(
        void *context,
        void *pointer
    );
};
```

테스트용 allocator는 예를 들어 세 번째 할당 요청에서 반드시 실패하도록 만들 수 있습니다.

```text
1번째 요청 → 성공
2번째 요청 → 성공
3번째 요청 → 실패
```

그러면 실제 메모리 부족을 기다리지 않고 다음 계약을 결정적으로 검사할 수 있습니다.

* 실패했을 때 기존 데이터가 유지되는가
* 이미 확보한 자원이 모두 정리되는가
* 출력 인자가 변경되지 않는가
* 객체의 불변식이 유지되는가

이 추상화의 목적이 실패 경로 검증이라면 그 범위를 그 목적에 맞게 제한합니다. 단순히 모든 메모리 연산을 일반화하는 것 자체가 목표가 되어서는 안 됩니다.

## 연결 리스트와 컨테이너 선택

단순 연결 리스트의 노드는 다음처럼 표현할 수 있습니다.

```c
struct node
{
    char *value;
    struct node *next;
};
```

각 노드를 별도로 할당하는 구조에서는 새로운 노드를 추가한다고 해서 기존 노드 자체가 다른 주소로 이동하지는 않습니다.

대신 다음과 같은 비용이 있습니다.

* 인덱스로 접근하려면 앞에서부터 순회해야 함
* 노드별 동적 할당이 필요할 수 있음
* 각 노드에 링크를 저장할 공간이 추가로 필요함
* 메모리가 연속되지 않아 순차 접근의 지역성이 떨어질 수 있음

머리 노드 자체를 바꾸는 함수는 호출자가 가진 포인터 슬롯을 수정해야 합니다.

```c
int list_push_front(
    struct node **head,
    const char *value
);
```

노드를 삭제하면서 순회할 때는 현재 노드를 해제하기 전에 다음 노드의 주소를 보존해야 합니다.

```c
struct node *next = current->next;

node_destroy(current);
current = next;
```

동적 배열과 연결 리스트를 단순히 "삽입이 많은가"만으로 선택해서는 안 됩니다.

| 기준        | 동적 배열           | 연결 리스트                     |
| --------- | --------------- | -------------------------- |
| 임의 인덱스 접근 | 빠름              | 선형 탐색 필요                   |
| 순차 처리     | 연속된 메모리         | 포인터를 따라 이동                 |
| 중간 삽입·삭제  | 원소 이동이 필요할 수 있음 | 필요한 노드 위치를 알고 있다면 링크 변경 중심 |
| 원소 주소 안정성 | 재할당 시 무효화될 수 있음 | 노드가 살아 있는 동안 유지            |
| 할당 횟수     | 비교적 적음          | 일반적으로 노드마다 필요              |
| 추가 메모리    | 여유 capacity     | 노드별 링크 필드                  |

연결 리스트도 삽입 위치를 먼저 탐색해야 한다면 전체 연산은 선형 시간이 걸릴 수 있습니다. 따라서 자료구조 선택은 단일 연산의 이론적인 비용이 아니라 실제 접근 패턴 전체를 기준으로 해야 합니다.

다음 항목을 함께 고려합니다.

* 원소 수
* 순차 접근과 임의 접근의 비율
* 삽입과 삭제가 발생하는 위치
* 원소 주소의 안정성이 필요한가
* 최대 메모리 사용량
* 동적 할당 횟수
* 실패 가능한 지점의 수

## 헤더가 제공해야 하는 계약

공개 헤더와 API 문서는 호출자가 최소한 다음 내용을 알 수 있게 해야 합니다.

* 객체를 어떤 함수로 초기화하고 정리하는가
* 각 입력 포인터에 null을 허용하는가
* 어느 포인터를 단순히 빌리는가
* 어느 자원을 복제하는가
* 어느 시점에 소유권이 이전되는가
* 성공과 실패를 어떤 값으로 구분하는가
* 각 실패 뒤 객체는 어떤 상태인가
* 실패 시 출력 매개변수는 변경되는가
* 반환된 내부 포인터나 view는 언제 무효화되는가
* 같은 객체를 동시에 여러 스레드에서 사용해도 되는가
* 서로 다른 객체에 대한 동시 호출은 허용되는가

구현에만 필요한 보조 함수와 파일 내부 상태는 가능하면 `.c` 파일 안에서 `static`으로 제한합니다.

공개 구조체를 선택했더라도 호출자가 필드를 직접 수정하는 것을 공식적으로 지원하는지, 아니면 읽기만 허용하는지에 대한 규칙은 별도로 정해야 합니다.

구조체 정의가 공개되어 있다는 사실만으로 모든 필드 조작이 지원되는 것은 아닙니다.

## `errno`와 자체 오류 타입

자체 라이브러리의 모든 오류를 무조건 `errno`에 저장할 필요는 없습니다.

`errno`는 특정 C 또는 POSIX 인터페이스가 오류를 보고할 때 사용하는 보조 수단입니다. 함수가 성공했다고 해서 자동으로 `0`으로 초기화되는 것도 아닙니다.

따라서 일반적으로 다음과 같이 사용합니다.

```text
함수 반환값으로 실패 여부 확인
→ 그 함수의 계약이 errno를 정의한 경우에만 errno 해석
```

`errno`를 확인해야 하는 함수라면 다른 함수 호출로 값이 바뀌기 전에 필요한 값을 보존해야 할 수도 있습니다.

자체 API에서 성공과 실패만 구분하면 충분하다면 다음과 같은 단순한 결과로 충분할 수 있습니다.

```text
0  → 성공
-1 → 실패
```

호출자가 실패 종류에 따라 다른 동작을 수행해야 할 때만 별도의 `enum`이나 상세 오류 객체를 추가합니다.

오류 종류가 늘어날수록 구현뿐 아니라 호출자 코드, 테스트와 문서가 다뤄야 하는 계약도 함께 늘어납니다.

## 불변식 검사와 `assert`

개발 중에는 내부 프로그래밍 오류를 빠르게 발견하기 위해 불변식을 `assert`로 검사할 수 있습니다.

```c
assert(vector->size <= vector->capacity);
```

예를 들어 공개 함수가 입력 인자의 유효성을 확인한 뒤 내부 객체의 불변식을 검사하고, 성공적으로 상태를 변경한 뒤 다시 검사할 수 있습니다.

```text
외부 입력 검증
→ 진입 시 내부 불변식 검사
→ 연산 수행
→ 성공 상태의 불변식 검사
→ 반환
```

그러나 `assert`는 외부 입력 검증이나 복구 가능한 오류 처리를 대신하지 않습니다.

`NDEBUG`가 정의된 빌드에서는 `assert` 표현식 자체가 제거될 수 있으므로 다음과 같이 반드시 실행되어야 하는 동작을 넣어서도 안 됩니다.

```c
assert(initialize_resource() == 0); /* 피해야 함 */
```

불변식 검사의 목적은 사용자 입력을 처리하는 것이 아니라 내부 코드가 이미 정해 놓은 규칙을 깨뜨린 위치를 빠르게 찾는 것입니다.

## 상태 머신

단순한 컨테이너보다 복잡한 연결, 파서, 작업 객체에는 명시적인 상태가 필요할 수 있습니다.

```c
enum connection_state
{
    CONNECTION_NEW,
    CONNECTION_OPEN,
    CONNECTION_CLOSED,
    CONNECTION_FAILED
};
```

허용되는 상태 전이를 따로 정의할 수 있습니다.

```text
NEW  → OPEN
NEW  → FAILED

OPEN → CLOSED
OPEN → FAILED
```

예를 들어 이미 `CLOSED`인 연결에 다시 `open`을 적용하거나, `FAILED` 상태를 아무 검증 없이 `OPEN`으로 바꾸는 동작은 허용하지 않을 수 있습니다.

중요한 것은 상태 값을 저장하는 것 자체가 아니라 어떤 연산이 어느 상태에서 허용되며 성공과 실패 뒤 어떤 상태로 이동하는지를 정하는 것입니다.

여러 스레드가 같은 상태를 동시에 읽고 변경할 수 있다면 상태 검사와 갱신 사이에 경쟁 조건이 생길 수 있습니다.

이 경우에는 상태 머신의 규칙뿐 아니라 이후 동시성 영역에서 다루는 동기화 경계까지 함께 설계해야 합니다.

## 함수 포인터와 callback

함수 포인터를 사용하면 자료구조에 특정 동작을 외부에서 주입할 수 있습니다.

```c
typedef int (*item_predicate)(
    const void *item,
    void *context
);
```

예를 들어 컨테이너가 원소를 순회하면서 호출자가 제공한 조건 함수를 실행하도록 만들 수 있습니다.

하지만 callback을 받는다는 사실만으로 계약이 완성되지는 않습니다.

최소한 다음 내용을 정해야 합니다.

* callback은 언제 호출되는가
* 어느 스레드에서 호출되는가
* 전달된 포인터는 호출 이후에도 유효한가
* callback이 컨테이너를 다시 호출해도 되는가
* callback 중 컨테이너를 수정해도 되는가
* callback이 실패를 반환하면 순회를 중단하는가
* 이미 수행한 변경은 유지되는가
* `context`가 가리키는 객체를 누가 소유하는가
* callback 자체나 `context`를 얼마 동안 보관하는가

특히 callback 내부에서 같은 컨테이너를 다시 조작할 수 있는지에 대한 재진입성 규칙이 없으면 구현과 호출자가 서로 다른 가정을 하기 쉽습니다.

함수 포인터를 지나치게 일반화하면 정적 타입 검사가 약해지고 수명과 소유권 관계도 추적하기 어려워질 수 있습니다.

allocator 주입이나 명확한 순회 callback처럼 **왜 동작을 외부에서 주입해야 하는지가 분명한 경계부터 사용하는 것**이 좋습니다.
