# C 프로그램 모델: 번역 단위·선언·링크

C 소스는 한 번에 실행 파일이 되지 않습니다. 전처리, 번역과 링크 단계를 거치며, 각 단계가 보는 이름과 책임이 다릅니다. 여러 파일 프로젝트를 시작하려면 문법보다 먼저 이 경계를 이해해야 합니다.

## 빌드 흐름

```text
.c + 포함된 헤더
  ↓ 전처리
번역 단위
  ↓ 컴파일·어셈블
오브젝트 파일(.o)
  ↓ 링크
실행 파일 또는 라이브러리
  ↓ 운영체제가 적재
프로세스
```

`cc`는 이 도구들을 순서대로 호출하는 드라이버입니다.

```sh
cc -std=c99 -Wall -Wextra -Wpedantic main.c text.c -o textstat
```

한 줄 명령이 여러 단계를 숨기므로 오류가 어느 단계에서 발생했는지 구분해야 합니다.

## 각 단계 관찰하기

```sh
cc -std=c99 -E main.c -o main.i
cc -std=c99 -S main.c -o main.s
cc -std=c99 -c main.c -o main.o
cc main.o text.o -o textstat
```

- 전처리는 `#include`, 매크로와 조건부 컴파일을 처리합니다.
- 컴파일은 타입과 문법을 검사해 대상 코드로 변환합니다.
- 오브젝트 파일은 코드, 데이터, 심볼과 재배치 정보를 담습니다.
- 링크는 여러 오브젝트와 라이브러리의 정의를 연결합니다.

## 번역 단위

C가 독립적으로 컴파일하는 실질적 단위는 전처리된 `.c` 파일 하나입니다.

```text
main.c + 포함된 헤더 → 번역 단위 A
text.c + 포함된 헤더 → 번역 단위 B
```

A는 B의 함수 본문을 자동으로 보지 못합니다. 호출할 이름의 선언은 알아야 하고, 실제 정의는 링크 때 찾아야 합니다.

## 선언과 정의

선언은 이름과 타입을 알립니다.

```c
size_t text_length(const char *text);
extern unsigned long processed_count;
```

정의는 함수 본문이나 객체의 저장 공간을 제공합니다.

```c
size_t text_length(const char *text)
{
    /* ... */
}

unsigned long processed_count = 0;
```

보통 외부 링크를 가진 정의는 프로그램 전체에 하나만 존재해야 합니다. 선언만 있고 정의를 링크하지 않으면 undefined reference가 발생하고, 정의가 여러 개면 multiple definition이 발생합니다.

## 헤더는 공개 계약이다

```c
#ifndef TEXTKIT_H
#define TEXTKIT_H

#include <stddef.h>

size_t textkit_length(const char *text);
size_t textkit_word_count(const char *text);

#endif
```

좋은 헤더는 다음 조건을 갖습니다.

- 자신이 사용하는 타입의 헤더를 직접 포함합니다.
- 여러 번 포함해도 안전합니다.
- 호출자에게 필요한 선언만 공개합니다.
- 변경 가능한 전역 객체와 일반 함수 본문을 넣지 않습니다.
- C 파일이 자신의 공개 헤더를 먼저 포함해 선언과 정의 불일치를 발견합니다.

```c
#include "textkit.h"
```

## 내부 구현 숨기기

파일 범위 함수에 `static`을 붙이면 현재 번역 단위 안에서만 연결됩니다.

```c
static int is_separator(char value)
{
    return value == ' ' || value == '\t' || value == '\n';
}
```

공개 API가 아닌 보조 이름은 내부 링크로 제한합니다. 이로써 다른 파일과 이름이 충돌하지 않고 변경 범위도 줄어듭니다.

블록 안의 `static`은 다른 의미로 객체의 저장 기간을 프로그램 전체로 늘립니다. 이름의 스코프, 링크와 객체의 저장 기간은 분리해 생각합니다.

## 주요 오류 단계

| 단계 | 증상 | 먼저 확인할 것 |
|---|---|---|
| 전처리 | 헤더를 찾지 못함 | `-I`, 파일 경로, include 이름 |
| 컴파일 | 문법·타입·형식 경고 | 선언, 반환형, 인자 타입 |
| 링크 | undefined/multiple symbol | 누락된 `.o`, 중복 정의, 라이브러리 순서 |
| 실행 | 잘못된 결과·비정상 종료 | 입력 계약, 메모리, 시스템 호출 |

정의되지 않은 동작을 포함한 코드도 앞 단계를 통과할 수 있습니다.

## `main`과 외부 계약

```c
int main(int argc, char *argv[])
{
    if (argc != 2)
    {
        return 2;
    }
    return 0;
}
```

운영체제와 shell이 관찰하는 것은 stdout, stderr와 종료 상태입니다. 라이브러리 함수의 내부 반환값과 프로세스 종료 상태를 구분합니다.

## C99에서 먼저 고정할 언어 규칙

Part 1을 건너뛴 독자도 다음 규칙은 확인해야 합니다.

- 자동 저장 기간의 지역 객체는 명시적으로 초기화하지 않으면 정해진 초기값이 없습니다.
- 파일 범위 객체와 `static` 객체는 명시적 초기값이 없으면 0에 해당하는 값으로 초기화됩니다.
- 일반 함수 인자는 값으로 전달됩니다. 호출자의 객체를 바꾸려면 유효한 포인터와 별도 계약이 필요합니다.
- 배열 길이는 함수에 자동 전달되지 않습니다. 포인터와 길이를 함께 넘깁니다.
- 인자가 없는 함수 선언은 `function(void)`로 씁니다. `function()`은 오래된 C에서 매개변수 정보가 지정되지 않았다는 뜻일 수 있습니다.
- `size_t`는 크기와 개수를 표현하는 부호 없는 타입입니다. `int`와 섞어 비교할 때 변환 규칙을 먼저 확인합니다.

```c
void print_banner(void);
size_t text_length(const char *text);
```

정확한 타입은 단순한 표기가 아니라 호출·형식 지정자·산술 범위를 결정하는 계약입니다.

## 암시적 변환과 경고

C는 한 식에 여러 산술 타입이 있으면 공통 타입을 선택합니다. 특히 음수 `int`와 `size_t`를 비교하면 음수가 큰 부호 없는 값으로 변환될 수 있습니다.

```c
int index = -1;
size_t length = 10;

if (index < length)
{
    /* 직관과 다른 결과가 될 수 있습니다. */
}
```

캐스트는 위험한 값을 안전하게 만들지 않습니다. 먼저 값의 범위를 검증하고, 의도한 변환을 설명할 수 있을 때만 사용합니다.

```c
if (index >= 0 && (size_t)index < length)
{
    /* 범위 확인 뒤 변환 */
}
```

컴파일러 경고는 이 문제의 일부를 찾지만 모든 값 흐름을 증명하지는 않습니다. 경고를 없애기 위해 무조건 캐스트를 추가하지 않습니다.

## 스코프·링크·저장 기간

서로 비슷해 보이는 세 질문을 분리합니다.

| 개념 | 질문 | 대표 예 |
|---|---|---|
| 스코프 | 이름을 소스의 어디에서 사용할 수 있는가 | 블록, 파일, 함수 prototype |
| 링크 | 다른 선언의 같은 이름과 연결되는가 | 외부 링크, 내부 링크, 링크 없음 |
| 저장 기간 | 객체가 언제 생성되고 수명이 끝나는가 | 자동, 정적, 동적 |

지역 변수는 보통 블록 스코프, 링크 없음, 자동 저장 기간을 가집니다. 파일 범위 일반 함수는 외부 링크를 가지며, 파일 범위 `static` 함수는 내부 링크를 가집니다. 블록 안의 `static` 객체는 이름의 스코프는 블록에 남아 있지만 저장 기간은 프로그램 전체입니다.

이 구분은 전역 상태를 이해할 때 중요합니다. 이름이 보이지 않는다는 사실과 객체가 존재하지 않는다는 사실은 같지 않습니다.

## 오브젝트와 심볼 관찰

링크 문제를 추측하기보다 산출물을 직접 볼 수 있습니다.

```sh
nm main.o
nm textkit.o
ar t libtextkit.a
nm libtextkit.a
```

도구 출력 표기는 플랫폼마다 다르지만 다음을 구분하는 데 유용합니다.

- 현재 파일이 정의한 외부 심볼
- 아직 다른 오브젝트에서 해결해야 하는 심볼
- 내부 링크로 제한된 이름
- archive에 실제로 들어 있는 멤버

헤더에 선언이 있다는 사실은 최종 정의가 존재한다는 뜻이 아닙니다. 반대로 정의가 있어도 최종 링크 명령에 해당 오브젝트가 없으면 해결되지 않습니다.

## 정의되지 않은 동작과 진단의 한계

다음은 컴파일과 링크를 통과해도 결과가 규정되지 않을 수 있습니다.

- 배열 범위 밖 접근
- 초기화하지 않은 값 읽기
- 부호 있는 정수 overflow
- 0으로 정수 나눗셈
- 실제 인자 타입과 맞지 않는 `printf` 형식
- 수명이 끝난 객체 접근

정의되지 않은 동작은 “항상 crash한다”는 뜻이 아닙니다. 현재 실행에서 원하는 출력이 나왔다는 사실도 올바름의 근거가 아닙니다. 경고, 테스트, debugger와 sanitizer를 함께 사용하되 각 도구가 실행하지 않은 경로와 논리 계약까지 보장하지는 않는다는 한계를 기록합니다.

## 정적 라이브러리

```sh
cc -Iinclude -std=c99 -Wall -Wextra -Wpedantic -c src/textkit.c -o textkit.o
ar rcs libtextkit.a textkit.o
cc -Iinclude app/main.c libtextkit.a -o textstat
```

정적 라이브러리는 여러 오브젝트를 보관하는 archive입니다. 링크할 때 필요한 멤버가 최종 실행 파일에 포함됩니다. 라이브러리 자체가 실행되는 것은 아닙니다.

링커가 보통 왼쪽에서 오른쪽으로 필요한 심볼을 판단하므로 정적 라이브러리는 이를 사용하는 오브젝트 뒤에 두는 것이 안전합니다.
