# C 프로그램 모델: 번역 단위·선언·링키지

C 소스 파일이 곧바로 실행 파일로 바뀌는 것은 아닙니다. 각 `.c` 파일은 전처리를 거쳐 하나의 번역 단위가 되고, 번역 단위별로 독립적으로 컴파일·어셈블됩니다. 이후 여러 오브젝트 파일을 링크해 최종 실행 파일을 만듭니다.

여러 파일로 구성된 C 프로젝트를 다루려면 문법뿐 아니라 소스 파일, 번역 단위, 오브젝트 파일, 실행 파일의 관계를 이해해야 합니다.

## 빌드 흐름

```text
.c 파일 + 포함된 헤더
  ↓ 전처리
번역 단위
  ↓ 컴파일·어셈블
오브젝트 파일(.o)
  ↓ 링크
실행 파일 또는 라이브러리
  ↓ 운영체제가 적재
프로세스
```

`cc`는 전처리기, 컴파일러, 어셈블러, 링커를 필요한 순서대로 호출하는 컴파일러 드라이버입니다.

```sh
cc -std=c99 -Wall -Wextra -Wpedantic main.c text.c -o textstat
```

한 줄의 명령으로 전체 빌드를 수행할 수 있지만 내부에서는 여러 단계가 차례로 실행됩니다. 문제가 발생하면 어느 단계에서 실패했는지 먼저 구분해야 합니다.

## 각 단계 관찰하기

각 단계의 결과물을 따로 생성하면 빌드 과정을 직접 확인할 수 있습니다.

```sh
cc -std=c99 -E main.c -o main.i
cc -std=c99 -S main.c -o main.s
cc -std=c99 -c main.c -o main.o
cc main.o text.o -o textstat
```

- 전처리 단계에서는 `#include`, 매크로, 조건부 컴파일 지시문을 처리합니다.
- 컴파일 단계에서는 C 문법과 타입 규칙을 검사하고 대상 코드를 생성합니다.
- 오브젝트 파일에는 코드, 데이터, 심볼, 재배치 정보가 들어 있습니다.
- 링크 단계에서는 여러 오브젝트 파일과 라이브러리가 참조하는 심볼을 실제 정의와 연결합니다.

빌드 오류를 모두 "컴파일 오류"라고 부르지 말고 전처리, 컴파일, 링크 중 어느 단계의 오류인지 구분하는 습관을 들여야 합니다.

## 번역 단위

C에서 독립적으로 컴파일되는 실질적인 단위는 전처리를 마친 `.c` 파일 하나입니다.

```text
main.c + 포함된 헤더 → 번역 단위 A
text.c + 포함된 헤더 → 번역 단위 B
```

번역 단위 A를 컴파일할 때 번역 단위 B의 함수 본문은 입력에 포함되지 않습니다. A에서 B의 함수를 호출하려면 컴파일 시점에 함수 선언을 알고 있어야 하며, 실제 정의는 이후 링크 단계에서 제공되어야 합니다.

이 때문에 프로그램을 여러 파일로 나눌 때 선언과 정의를 분리하고 헤더를 통해 인터페이스를 공유합니다.

## 선언과 정의

선언은 컴파일러에 이름과 타입을 알려 줍니다.

```c
size_t text_length(const char *text);
extern unsigned long processed_count;
```

정의는 함수 구현이나 객체의 실제 저장 공간을 제공합니다.

```c
size_t text_length(const char *text)
{
    /* ... */
}

unsigned long processed_count = 0;
```

같은 함수나 객체를 여러 번 선언할 수는 있지만, 외부 링키지를 갖는 대상의 실제 정의는 일반적으로 프로그램 전체에 하나만 있어야 합니다.

선언은 있지만 최종 링크에 정의가 포함되지 않으면 `undefined reference`와 같은 오류가 발생합니다. 반대로 같은 외부 정의가 여러 곳에 있으면 `multiple definition`과 같은 오류가 발생합니다.

## 헤더는 공개 인터페이스의 계약이다

헤더에는 여러 번역 단위가 공유해야 하는 선언을 둡니다.

```c
#ifndef TEXTKIT_H
#define TEXTKIT_H

#include <stddef.h>

size_t textkit_length(const char *text);
size_t textkit_word_count(const char *text);

#endif
```

공개 헤더는 다음 원칙을 따르는 것이 좋습니다.

- 헤더 안에서 사용하는 타입에 필요한 다른 헤더를 직접 포함합니다.
- 여러 번 포함해도 문제가 없도록 include guard를 둡니다.
- 호출자가 알아야 하는 선언만 공개합니다.
- 변경 가능한 전역 객체의 정의나 일반 함수의 외부 정의를 넣지 않습니다.
- 구현 파일에서도 자신의 공개 헤더를 직접 포함해 선언과 정의가 일치하는지 컴파일 단계에서 확인합니다.

```c
#include "textkit.h"
```

헤더는 단순한 선언 모음이 아니라 구현과 호출자가 함께 따라야 하는 인터페이스 계약입니다.

## 내부 구현 숨기기

파일 범위에서 선언한 함수에 `static`을 붙이면 그 이름은 내부 링키지를 갖습니다.

```c
static int is_separator(char value)
{
    return value == ' ' || value == '\t' || value == '\n';
}
```

이 함수는 현재 번역 단위의 구현에서만 사용할 수 있으며 다른 번역 단위에서는 같은 이름을 참조할 수 없습니다.

외부에 공개할 필요가 없는 보조 함수와 파일 내부 상태는 가능한 한 내부 링키지로 제한하는 편이 좋습니다. 다른 파일과의 이름 충돌을 막고, 구현 변경이 영향을 미치는 범위도 줄일 수 있습니다.

블록 내부에서 선언한 `static`은 다른 의미를 갖습니다.

```c
void function(void)
{
    static unsigned long count;
}
```

이 경우 `count`라는 이름의 스코프는 블록으로 제한되지만 객체는 정적 저장 기간을 갖습니다. 따라서 이름의 스코프, 링키지, 객체의 저장 기간을 서로 구분해야 합니다.

## 단계별 주요 오류

| 단계 | 대표적인 증상 | 먼저 확인할 항목 |
| --- | --- | --- |
| 전처리 | 헤더를 찾지 못함 | `-I`, 파일 경로, `#include` 이름 |
| 컴파일 | 문법·타입·형식 관련 오류와 경고 | 선언, 반환형, 인자 타입 |
| 링크 | 미정의 심볼, 중복 정의 | 누락된 `.o`, 중복 정의, 라이브러리 지정 |
| 실행 | 잘못된 결과, 비정상 종료 | 입력 계약, 메모리 접근, 시스템 호출 결과 |

컴파일과 링크에 성공했다고 프로그램이 올바른 것은 아닙니다. 정의되지 않은 동작을 포함한 코드도 모든 빌드 단계를 통과할 수 있습니다.

## `main`과 프로그램의 외부 계약

```c
int main(int argc, char *argv[])
{
    if (argc != 2)
    {
        return 2;
    }
    return 0;
}
```

`main`의 반환값은 프로세스의 종료 상태로 전달됩니다.

프로그램을 실행한 셸이나 부모 프로세스가 주로 관찰하는 것은 표준 출력(`stdout`), 표준 오류(`stderr`), 종료 상태입니다. 따라서 내부 함수의 반환값과 최종 프로세스의 종료 상태를 구분해야 합니다.

라이브러리 함수가 반환하는 오류 코드와 CLI 프로그램이 외부에 전달하는 종료 상태는 서로 다른 계약일 수 있습니다.

## C99에서 먼저 확인할 언어 규칙

1부를 건너뛴 경우 다음 규칙부터 확인합니다.

- 자동 저장 기간을 갖는 지역 객체는 명시적으로 초기화하지 않으면 값이 정해져 있지 않습니다.
- 파일 범위 객체와 정적 저장 기간을 갖는 객체는 명시적인 초기값이 없으면 0에 해당하는 값으로 초기화됩니다.
- 일반 함수의 인자는 값으로 전달됩니다. 호출자의 객체를 수정하려면 그 객체를 가리키는 포인터를 전달해야 합니다.
- 배열 길이는 함수에 자동으로 전달되지 않습니다. 필요한 경우 포인터와 길이를 함께 전달합니다.
- 인자가 없는 함수를 선언할 때는 `function(void)`를 사용합니다. C99에서 `function()`은 매개변수가 없다는 뜻이 아니라 매개변수 정보가 지정되지 않은 함수 선언입니다.
- `size_t`는 객체의 크기와 개수를 표현하는 부호 없는 정수 타입입니다. `int`와 비교하거나 함께 계산할 때는 정수 변환 규칙을 확인해야 합니다.

```c
void print_banner(void);
size_t text_length(const char *text);
```

타입은 단순한 표기가 아닙니다. 함수 호출 방식, 사용할 형식 지정자, 표현 가능한 값의 범위를 결정하는 인터페이스의 일부입니다.

## 암시적 변환과 경고

C에서는 하나의 식에 서로 다른 산술 타입이 사용되면 정해진 규칙에 따라 공통 타입으로 변환됩니다.

특히 부호 있는 정수와 `size_t` 같은 부호 없는 정수를 비교할 때 주의해야 합니다.

```c
int index = -1;
size_t length = 10;

if (index < length)
{
    /* 예상과 다른 결과가 나올 수 있습니다. */
}
```

이 비교에서는 `index`가 부호 없는 타입으로 변환될 수 있습니다. 그 결과 `-1`이 매우 큰 양수로 해석되어 직관과 다른 결과가 나올 수 있습니다.

캐스트를 추가한다고 위험한 값이 안전해지는 것은 아닙니다. 먼저 값의 범위를 검사하고 변환이 유효함을 보장한 뒤, 의도를 명확히 드러낼 필요가 있을 때만 변환합니다.

```c
if (index >= 0 && (size_t)index < length)
{
    /* 범위를 확인한 뒤 변환 */
}
```

컴파일러 경고는 이러한 문제 일부를 찾아낼 수 있지만 모든 값의 흐름과 프로그램 논리를 증명하지는 않습니다. 경고를 없애기 위해 무조건 캐스트를 추가해서는 안 됩니다.

## 스코프·링키지·저장 기간

C에서는 비슷해 보이는 다음 세 개념을 구분해야 합니다.

| 개념 | 묻는 질문 | 대표적인 예 |
| --- | --- | --- |
| 스코프 | 이 이름을 소스 코드의 어디에서 사용할 수 있는가? | 블록 스코프, 파일 스코프, 함수 프로토타입 스코프 |
| 링키지 | 서로 다른 선언이 같은 대상을 가리키는가? | 외부 링키지, 내부 링키지, 링키지 없음 |
| 저장 기간 | 객체가 언제 생성되고 언제까지 존재하는가? | 자동, 정적, 동적 저장 기간 |

일반적인 지역 변수는 블록 스코프를 가지며 링키지는 없고 자동 저장 기간을 갖습니다.

파일 범위에 선언한 일반 함수는 외부 링키지를 갖습니다.

```c
int parse_text(const char *text);
```

같은 위치에서 `static`을 사용하면 내부 링키지를 갖습니다.

```c
static int parse_token(const char *text);
```

반면 블록 내부의 `static` 객체는 이름의 스코프가 블록으로 제한되지만 객체 자체는 프로그램이 실행되는 동안 계속 존재합니다.

이 구분은 전역 상태와 파일 내부 상태를 이해할 때 특히 중요합니다. 어떤 위치에서 이름이 보이지 않는다는 사실과 객체가 존재하지 않는다는 사실은 같은 의미가 아닙니다.

## 오브젝트 파일과 심볼 관찰하기

링크 문제를 추측만 하지 말고 실제 빌드 산출물을 확인할 수 있습니다.

```sh
nm main.o
nm textkit.o
ar t libtextkit.a
nm libtextkit.a
```

출력 형식은 플랫폼과 도구체인에 따라 다르지만, 이러한 도구로 다음 항목을 확인할 수 있습니다.

- 현재 오브젝트 파일이 정의한 외부 심볼
- 다른 오브젝트 파일에서 정의해야 하는 미해결 심볼
- 내부 링키지를 갖는 심볼
- 정적 라이브러리에 실제로 포함된 오브젝트 파일

헤더에 함수가 선언되어 있다는 사실만으로 실제 정의가 존재한다고 보장할 수는 없습니다.

반대로 정의가 존재하더라도 해당 오브젝트 파일이나 라이브러리가 최종 링크 명령에 포함되지 않으면 그 정의를 사용할 수 없습니다.

## 정의되지 않은 동작과 진단의 한계

다음 코드는 컴파일과 링크에 성공하더라도 결과가 C 언어에서 규정되지 않을 수 있습니다.

- 배열 범위를 벗어난 접근
- 초기화하지 않은 값 읽기
- 부호 있는 정수 오버플로
- 정수를 0으로 나누기
- 실제 인자 타입과 맞지 않는 `printf` 형식 지정자 사용
- 수명이 끝난 객체에 접근하기

정의되지 않은 동작이 발생해도 프로그램이 반드시 즉시 충돌하는 것은 아닙니다. 한 번 실행했을 때 기대한 출력이 나왔다는 사실도 프로그램이 올바르다는 근거가 되지 않습니다.

컴파일러 경고, 테스트, 디버거, Sanitizer는 서로 다른 종류의 문제를 발견하는 데 도움이 됩니다. 그러나 어떤 도구도 실행되지 않은 경로나 프로그램의 논리적 계약까지 자동으로 보장하지는 않습니다.

따라서 각 검증 방법이 무엇을 확인했고 무엇을 확인하지 못했는지도 구분해야 합니다.

## 정적 라이브러리

여러 오브젝트 파일을 하나의 정적 라이브러리로 묶을 수 있습니다.

```sh
cc -Iinclude -std=c99 -Wall -Wextra -Wpedantic -c src/textkit.c -o textkit.o
ar rcs libtextkit.a textkit.o
cc -Iinclude app/main.c libtextkit.a -o textstat
```

정적 라이브러리는 여러 오브젝트 파일을 보관하는 아카이브입니다. 라이브러리 자체가 실행되는 것이 아니라 링크 단계에서 필요한 오브젝트 코드가 최종 실행 파일에 포함됩니다.

세부 동작은 링커마다 다르지만, 전통적인 Unix 계열 정적 링크에서는 입력을 왼쪽에서 오른쪽으로 처리하면서 아직 해결되지 않은 심볼을 기준으로 라이브러리 멤버를 선택하는 경우가 많습니다.

따라서 정적 라이브러리는 일반적으로 그 라이브러리를 사용하는 오브젝트 파일 뒤에 두는 편이 안전합니다.

```sh
cc main.o textkit.o -lhelper -o textstat
```

라이브러리 순서에 따라 링크 결과가 달라질 수 있다는 점도 소스 코드 컴파일과 링크가 별개의 단계임을 보여 줍니다.

## 실습

[textkit 연습](../../exercises/02-c-language/01-textkit/README.md)에서 다음 과정을 직접 확인합니다.

1. 헤더에 선언된 공개 함수를 구현합니다.
2. 구현 파일을 오브젝트 파일로 독립적으로 컴파일합니다.
3. 오브젝트 파일로 정적 라이브러리를 만듭니다.
4. 테스트 프로그램과 CLI 프로그램을 각각 링크합니다.
5. 링크 명령에서 라이브러리를 제외해 미정의 심볼 오류를 확인합니다.
6. 헤더의 선언과 구현의 정의를 의도적으로 다르게 만들어 컴파일 단계에서 불일치를 확인합니다.

이 실습의 목적은 Makefile 문법 자체를 익히는 것이 아닙니다.

소스 파일이 번역 단위를 이루고, 각 번역 단위가 오브젝트 파일로 만들어진 뒤, 여러 오브젝트 파일과 라이브러리가 링크되어 하나의 프로그램을 구성하는 과정을 직접 설명할 수 있어야 합니다.
