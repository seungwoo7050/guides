# 개발 역량의 넓이와 깊이

브랜치 개수, 언어 개수와 사용한 프레임워크 수는 실력을 직접 나타내지 않는다. 개발 역량은 **어느 범위의 문제를 얼마나 적은 지시로, 어떤 근거를 남기며, 실패까지 책임지는가**로 판단한다.

## 다섯 단계

| 단계 | 설명 | 대표 결과 |
|---|---|---|
| 0. 탐색 | 용어와 책임 경계를 알고 자료를 찾는다. | 올바른 브랜치·문서·담당자에 문제를 연결한다. |
| 1. 안내된 구현 | 요구사항과 검증 방법이 주어지면 작은 변경을 완성한다. | skeleton 또는 명확한 issue를 구현한다. |
| 2. 프로젝트 기여 | 기존 코드베이스에서 범위를 복원하고 작은 기능·버그 수정을 독립적으로 끝낸다. | 테스트·문서·PR·검증 근거를 함께 제출한다. |
| 3. 하위 시스템 소유 | 모호한 문제를 설계·마이그레이션·배포·운영·복구까지 책임진다. | 장기 상태와 실패 계약을 보존한다. |
| 4. 도메인 리드 | 여러 팀의 기준·도구·기술 방향을 만들고 중요한 위험을 줄인다. | 조직 전체의 속도·품질·신뢰성을 높인다. |

`guides`의 기본 설계 목표는 독자가 **2단계 프로젝트 기여에 진입할 준비**를 갖추는 것이다. 브랜치 내부의 capstone 또는 동등한 누적 최종 실습을 완료했다는 사실만으로 실제 프로젝트 기여를 끝냈다고 보지는 않는다. 일부 심화 브랜치는 3단계의 문제를 소개하지만, 실제 하위 시스템 소유 능력은 운영 경험과 반복 기여 없이 형성되지 않는다.

## 완료 단위와 역량 단계

- **브랜치 완료**는 한 브랜치의 소유 범위와 종료 능력을 사람의 판단으로 확인한 상태다.
- **트랙 완료**는 목표 업무의 필수 브랜치들을 연결해 트랙의 종료 작업을 시도할 준비가 된 상태다. 권장·심화 브랜치까지 모두 끝냈다는 뜻은 아니다.
- **프로젝트 기여**는 실제 코드베이스에서 요구사항, 리뷰, 호환성, 사용자·운영 제약을 겪으며 변경을 끝낸 상태다.

따라서 브랜치 개수의 합으로 역량 단계를 올리지 않는다. 트랙을 완료한 독자도 첫 실제 프로젝트에서는 안내가 필요할 수 있고, 특정 브랜치를 완료하지 않은 실무자도 경험으로 같은 종료 능력을 이미 가질 수 있다. 자세한 브랜치 판정 기준은 [브랜치 품질 계약](09-branch-quality-contract.md)을 따른다.

## 일반적으로 강한 개발자의 폭

```text
주 도메인 1개: 하위 시스템 소유 수준
인접 도메인 2~4개: 프로젝트 기여·장애 진단 수준
공통 기반: 변경·관측·검증을 독립적으로 수행
관련 없는 영역: 책임과 연결 지점 인지 수준
```

예를 들어 강한 백엔드 개발자는 Spring API만 잘 작성하는 사람이 아니다.

- 애플리케이션 상태와 데이터 소유권을 깊게 다룬다.
- SQL·트랜잭션·배포·관측·보안은 독립적으로 협업할 정도로 안다.
- DBMS 내부, 커널, 네트워크 프로토콜 전체를 직접 구현할 필요는 없지만 문제를 잘못된 계층에 넘기지 않는다.

## 높은 가치가 생기는 깊이

높은 보상을 받는 개발자는 대개 다음 중 하나 이상에서 대체하기 어렵다.

- 대규모 분산 시스템과 데이터 일관성
- 데이터베이스·저장 엔진·질의 성능
- 보안·취약점·격리와 사고 대응
- 플랫폼·신뢰성·대규모 전달 자동화
- ML 모델·데이터·추론 시스템
- 컴파일러·성능·메모리·저수준 시스템
- 그래픽스·모바일·임베디드처럼 플랫폼 제약이 강한 분야

그러나 희소한 기술 지식만으로는 부족하다. 다음 능력이 함께 있어야 한다.

1. 처음 보는 실패를 재현한다.
2. 증상과 root cause를 분리한다.
3. 안전한 변경·마이그레이션·rollback을 설계한다.
4. 운영 부작용과 비용을 예측한다.
5. 다른 개발자가 더 빨리 안전하게 일하도록 기준과 도구를 만든다.
6. 기술 결정이 제품·사용자·사업에 미치는 영향을 설명한다.

## 넓이의 잘못된 형태

다음은 넓이가 아니다.

- 여러 언어로 동일한 CRUD 예제를 반복한다.
- 프레임워크 설치와 기본 튜토리얼을 많이 완료한다.
- 도구 이름과 옵션을 외우지만 실패 상태를 설명하지 못한다.
- AI가 생성한 구현을 검증하지 않고 병합한다.

의미 있는 넓이는 **계층 사이 계약과 실패 전파를 이해하는 능력**이다.

## 깊이의 잘못된 형태

다음은 실무 깊이가 아니다.

- 내부 구현을 외우지만 실제 요구사항을 변경 단위로 만들지 못한다.
- benchmark 한 번으로 일반 성능 주장을 한다.
- 정상 경로만 구현하고 복구·관측·호환성을 무시한다.
- 자기 영역 밖의 제약을 고려하지 않아 다른 팀의 위험을 키운다.

의미 있는 깊이는 **새로운 문제를 증거로 좁히고, 실패 뒤에도 보존해야 할 상태를 설계하는 능력**이다.

## guides를 이용한 성장 모델

```text
브랜치 1개 완료
→ 작은 프로젝트 기여
→ 같은 영역의 반복 기여
→ 인접 브랜치 1개 추가
→ 실제 장애·성능·보안·마이그레이션 경험
→ 하위 시스템 소유
```

여러 브랜치를 연속으로 읽는 것보다 한 브랜치 뒤 실제 프로젝트에 사용하고 돌아오는 편이 깊이를 더 빠르게 만든다.
