# 디버거 실전 가이드: 가설을 실행 상태로 검증하기

GDB와 LLDB는 프로그램을 대신 이해해 주는 도구가 아닙니다. 소스 코드를 바탕으로 세운 가설을 실제 호출 스택, 변수, 메모리와 스레드 상태를 통해 확인하는 관찰 도구입니다.

처음부터 끝까지 무작정 한 줄씩 실행하기보다 재현할 입력, 멈출 조건, 확인할 불변식을 먼저 정합니다.

## 조사할 수 있는 빌드 준비하기

```sh
cc -std=c99 -Wall -Wextra -Wpedantic \
    -g -O0 source.c -o program
```

- `-g`: 소스의 줄 번호, 변수와 타입 등 디버깅에 필요한 정보를 포함합니다.
- `-O0`: 처음 조사할 때 소스 코드와 실제 실행 흐름의 차이를 줄입니다.
- 컴파일러 경고는 가능하면 디버거를 사용하기 전에 해결합니다.

최적화된 빌드에서는 변수가 제거되거나 레지스터에만 존재할 수 있고, 함수가 인라인되거나 소스 코드의 문장 순서와 실제 명령 실행 순서가 다르게 보일 수 있습니다.

결함이 `-O2`에서만 나타난다면 실제로 문제가 발생하는 최적화 옵션으로도 다시 조사해야 합니다. `-O0`에서 문제가 재현되지 않는다고 해서 결함이 사라진 것은 아닙니다.

Sanitizer를 사용하면서 디버그 정보도 유지할 수 있습니다.

```sh
cc -g -O1 -fsanitize=address,undefined \
    -fno-omit-frame-pointer source.c -o program
```

이 경우 Sanitizer는 잘못된 메모리 접근에 가까운 지점을 찾아내고, 디버거는 그 시점의 호출 스택과 값을 자세히 확인하는 역할을 합니다.

## 디버거 시작하기

```sh
# GDB
gdb ./program

# LLDB
lldb ./program
```

명령행 인자를 전달해 프로그램을 실행할 수 있습니다.

```text
GDB:  run input.txt 42
LLDB: run input.txt 42
```

셸 리다이렉션이 필요하다면 디버거가 제공하는 실행 설정을 사용합니다. 가능하다면 작은 입력 파일을 명령행 인자로 넘길 수 있도록 프로그램을 구성하는 편이 재현하기 쉽습니다.

복잡한 인용 처리 때문에 재현 명령 자체가 달라지지 않도록 실제 조사에 사용한 명령도 함께 기록합니다.

## 주요 명령 대응표

| 목적 | GDB | LLDB |
|---|---|---|
| 함수에 브레이크포인트 설정 | `break main` | `breakpoint set -n main` |
| 파일·줄에 브레이크포인트 설정 | `break file.c:42` | `breakpoint set -f file.c -l 42` |
| 실행 | `run a b` | `run a b` |
| 다시 실행 | `run` | `run` |
| 다음 소스 줄로 이동 | `next` | `next` |
| 함수 안으로 진입 | `step` | `step` |
| 현재 함수가 끝날 때까지 실행 | `finish` | `finish` |
| 계속 실행 | `continue` | `continue` |
| 현재 위치의 소스 확인 | `list` | `source list` |
| 변수 출력 | `print value` | `frame variable value` |
| 임의의 식 평가 | `print *pointer` | `expression -- *pointer` |
| 호출 스택 확인 | `backtrace` | `bt` |
| 모든 스레드의 스택 확인 | `thread apply all bt` | `thread backtrace all` |
| 프레임 선택 | `frame 2` | `frame select 2` |
| 브레이크포인트 목록 | `info breakpoints` | `breakpoint list` |
| 브레이크포인트 삭제 | `delete 1` | `breakpoint delete 1` |
| 레지스터 확인 | `info registers` | `register read` |
| 종료 | `quit` | `quit` |

명령 이름과 세부 동작은 디버거 버전과 환경에 따라 달라질 수 있습니다. 실제 설치된 디버거의 `help` 출력을 기준으로 확인합니다.

## 브레이크포인트는 질문을 표현합니다

항상 `main`에서 멈춘 뒤 프로그램 전체를 한 줄씩 따라가면 불필요한 정보가 지나치게 많아집니다.

대신 조사하려는 질문을 브레이크포인트로 바꿉니다.

```text
이 함수가 잘못된 length를 받는 순간은 언제인가?
vector의 불변식이 처음 깨지는 호출은 무엇인가?
두 번째 `fork`가 실패한 뒤 정리 경로에 실제로 진입하는가?
오류가 발생한 뒤 출력 매개변수를 변경하는 문장이 실행되는가?
```

GDB:

```text
break vector_push
break parser.c:180
```

LLDB:

```text
breakpoint set -n vector_push
breakpoint set -f parser.c -l 180
```

브레이크포인트에 도달할 때마다 명령을 자동으로 실행하거나 일정 횟수만큼 무시하도록 설정할 수도 있습니다.

처음 조사할 때는 조건을 가능한 한 단순하게 유지하는 편이 좋습니다.

## 조건부 브레이크포인트

반복문이 수천 번 실행되는 상황에서는 불변식이 깨지는 순간에만 멈추도록 조건을 지정할 수 있습니다.

GDB:

```text
break vector.c:80 if index >= vector->length
break account.c:120 if source->balance < 0
```

LLDB:

```text
breakpoint set -f vector.c -l 80 -c 'index >= vector->length'
breakpoint set -f account.c -l 120 -c 'source->balance < 0'
```

조건식 자체에서 잘못된 포인터를 역참조하면 디버거의 식 평가도 실패할 수 있습니다.

복잡한 객체를 조건식에서 바로 참조하기 전에 포인터가 유효한지, 객체의 수명이 끝나지 않았는지 먼저 확인합니다.

## 호출 스택과 프레임

프로그램이 충돌했거나 브레이크포인트에서 멈췄다면 먼저 호출 스택을 확인합니다.

```text
GDB:  backtrace
LLDB: bt
```

호출 스택의 각 프레임은 현재 함수가 어떤 호출 경로를 통해 실행되었는지 보여 줍니다.

```text
frame 0  실제 오류가 발생한 함수
frame 1  잘못된 인자를 전달한 호출자일 수 있음
frame N  외부 API 진입점이나 입력을 받은 위치
```

프로그램이 실제로 충돌한 위치와 결함이 처음 발생한 위치가 같다는 보장은 없습니다.

예를 들어 이전에 발생한 범위 밖 쓰기가 메모리 할당기의 메타데이터를 손상한 뒤 훨씬 나중에 실행된 `free`에서 프로그램이 충돌할 수 있습니다.

따라서 스택의 상위 프레임을 따라가면서 값이 처음 계약을 벗어난 지점을 찾습니다.

## 변수 하나가 아니라 불변식을 함께 확인하기

개별 변수 하나만 출력하기보다 서로 관계를 갖는 값을 묶어서 확인합니다.

```text
print vector->data
print vector->length
print vector->capacity
print vector->length <= vector->capacity
```

```text
print reader->pending
print reader->length
print reader->capacity
print reader->eof
print reader->failed
```

다음 질문을 기준으로 상태를 확인합니다.

- 이 포인터는 `NULL`인가?
- 포인터가 가리키는 객체의 수명은 아직 유효한가?
- `index`는 `length`보다 작은가?
- 출력 매개변수가 성공이 확정되기 전에 변경되었는가?
- 파일 디스크립터의 소유 상태와 실제 정수 값이 일치하는가?
- 뮤텍스를 보유해야 읽을 수 있는 값을 잠금 없이 읽고 있는가?

디버거에서 값을 읽는다고 해서 동시성 계약이 자동으로 안전해지는 것은 아닙니다.

다른 스레드가 계속 실행 중이라면 관찰한 값이 곧바로 달라질 수 있으므로 프로세스가 멈춘 상태인지와 해당 값의 잠금 관계를 함께 확인합니다.

## 포인터와 메모리 관찰하기

GDB:

```text
print pointer
print *pointer
x/16xb pointer
x/8wd values
x/s text
```

LLDB:

```text
frame variable pointer
expression -- *pointer
memory read --format x --size 1 --count 16 pointer
memory read --format d --size 4 --count 8 values
memory read --format c --size 1 text
```

메모리를 직접 확인할 때는 출력 형식과 원소 크기가 실제 타입과 일치하는지 확인합니다.

임의의 주소를 읽는 명령도 해당 주소가 유효하지 않으면 실패할 수 있습니다.

문자열을 `x/s`로 확인하는 방법은 NUL 종료가 보장될 때만 적절합니다.

중간에 NUL 문자가 포함될 수 있는 버퍼라면 문자열로 해석하지 말고 명시적인 길이만큼 바이트 단위로 관찰합니다.

## 세그멘테이션 오류 조사 순서

```sh
gdb ./program
(gdb) run failing-input
(gdb) backtrace
(gdb) frame 0
(gdb) print pointer
(gdb) print length
```

다음 순서로 질문합니다.

1. 어떤 시그널과 어떤 문장에서 프로그램이 멈췄는가?
2. 문제가 된 주소는 어디에서 만들어졌는가?
3. 포인터가 가리키던 객체의 수명은 아직 유효한가?
4. `index`, `length`, `capacity`가 지켜야 하는 계약은 무엇인가?
5. 같은 포인터를 이전에 `free`한 경로가 있는가?
6. 함수가 반환한 지역 변수의 주소나 자료구조가 성장하기 전의 내부 포인터를 보관하고 있는가?
7. 실제 충돌보다 앞서 잘못된 쓰기가 발생했을 가능성이 있는가?

AddressSanitizer가 메모리의 할당·해제 시점에 대한 호출 스택을 제공했다면 디버거의 현재 호출 스택과 함께 비교합니다.

## Watchpoint: 누가 이 값을 바꾸는가

값이 잘못되었다는 사실은 알지만 어디에서 변경되었는지 모른다면 watchpoint를 사용할 수 있습니다.

GDB:

```text
watch vector->length
continue
```

LLDB:

```text
watchpoint set expression -- vector->length
continue
```

Watchpoint를 사용하면 특정 메모리 위치에 대한 접근이 발생했을 때 실행을 멈출 수 있습니다. 읽기와 쓰기 중 어떤 접근을 감시하는지는 명령과 옵션에 따라 다릅니다.

하드웨어 watchpoint의 개수는 제한되어 있으며, 동적으로 할당한 객체가 이동하거나 해제되면 기존에 감시하던 주소가 더 이상 같은 논리 객체를 나타내지 않을 수 있습니다.

특히 `realloc`으로 내부 버퍼 주소가 달라질 수 있는 자료구조에서는 새 주소에 watchpoint를 다시 설정해야 합니다.

## 함수 반환과 실패 경로 조사하기

오류 처리 코드를 조사할 때는 성공 경로만 따라가서는 안 됩니다.

```text
break allocator_fail_point
run failing-case
next
print object->length
print object->data
finish
print result
```

실패 경로에서는 다음 사항을 확인합니다.

- 실패 전에 확보한 자원이 모두 정리되는가?
- 출력 매개변수는 성공 확정 전의 값을 유지하는가?
- 객체의 불변식이 유지되는가?
- 복구할 수 없는 실패라면 실패 상태가 제대로 설정되는가?
- 호출자가 실패한 객체를 안전하게 `destroy`할 수 있는가?

`finish`는 현재 함수가 반환할 때까지 실행을 계속하고 반환값을 확인하는 데 사용할 수 있습니다.

다만 최적화 수준과 ABI에 따라 반환값이 표시되는 방식은 달라질 수 있습니다.

## 스레드 조사하기

GDB:

```text
info threads
thread 3
thread apply all bt
```

LLDB:

```text
thread list
thread select 3
thread backtrace all
```

교착 상태를 조사할 때는 다음 순서를 따릅니다.

1. 모든 스레드의 호출 스택을 확인합니다.
2. 각 스레드가 어떤 뮤텍스나 조건 변수에서 기다리고 있는지 확인합니다.
3. 해당 잠금을 보유한 스레드의 호출 스택을 찾습니다.
4. 잠금 획득 순서가 프로그램에서 정한 전역 규칙과 일치하는지 확인합니다.
5. 조건 변수 대기라면 실제 대기 조건을 다시 확인합니다.

모든 스레드가 `pthread_mutex_lock` 내부에서 멈췄다고 해서 곧바로 뮤텍스 구현 자체를 분석할 필요는 없습니다.

먼저 프로그램이 어떤 순서로 잠금을 획득하는지 잠금 순서 그래프를 그려 보는 편이 효과적입니다.

데이터 경쟁은 디버거에서 한 단계씩 실행하는 동안 우연히 사라질 수 있습니다.

따라서 동시성 결함은 ThreadSanitizer나 배리어 기반 재현 테스트와 함께 조사합니다.

## 스레드별 브레이크포인트와 스케줄러의 영향

브레이크포인트에 도달했을 때 프로세스 전체가 멈추는지 특정 스레드만 멈추는지는 디버거와 실행 설정에 따라 달라질 수 있습니다.

한 스레드만 멈추고 다른 스레드가 계속 실행된다면 공유 상태도 계속 변할 수 있습니다.

반대로 모든 스레드를 동시에 멈추면 실제 프로그램에서 발생하던 타이밍이 크게 달라질 수 있습니다.

따라서 동시성 문제가 디버거에서는 재현되지 않았다는 이유만으로 프로그램이 안전하다고 판단해서는 안 됩니다.

디버거는 가능한 모든 실행 순서를 검증하는 도구가 아니라 특정 실행 순서를 관찰하는 도구입니다.

## `fork`와 여러 프로세스 조사하기

GDB에서는 다음 설정을 사용할 수 있습니다.

```text
set follow-fork-mode child
set detach-on-fork off
```

- `follow-fork-mode parent|child`: `fork` 이후 부모와 자식 중 어느 프로세스를 따라갈지 지정합니다.
- `detach-on-fork off`: 따라가지 않는 프로세스에서도 즉시 분리하지 않도록 설정할 수 있습니다.

LLDB의 `fork`·`vfork` 지원은 플랫폼에 따른 차이가 큽니다.

필요하면 다음 방법을 함께 사용합니다.

- 자식 프로세스만 실행하는 작은 보조 프로그램
- 표준 오류나 오류 전달용 파이프를 통한 진단
- PID와 파일 디스크립터를 포함하는 구조화된 로그
- `strace`, `ktrace`, `dtruss` 같은 운영체제별 시스템 호출 추적 도구
- 자동 제한 시간과 프로세스 그룹 정리

`fork` 이후 자식 프로세스에 브레이크포인트를 설정했다면 부모 프로세스가 `wait` 중인지, 파이프의 어느 끝을 어떤 프로세스가 아직 열어 두고 있는지도 함께 확인합니다.

## `exec` 이후의 브레이크포인트

`exec`가 성공하면 현재 프로세스의 프로그램 이미지가 새 실행 파일로 교체됩니다.

따라서 디버거가 새 실행 파일의 심볼을 어떤 방식으로 추적하는지 확인해야 합니다.

경우에 따라서는 `exec` 대상인 보조 프로그램에 디버거를 직접 연결해 `argv`와 시작 상태의 계약부터 검증하는 편이 더 단순합니다.

반면 `exec`가 실패하면 프로그램 이미지는 교체되지 않습니다.

따라서 자식 프로세스가 `_exit(126)`이나 `_exit(127)`을 호출하기 직전에 브레이크포인트를 설정해 `errno`와 아직 열려 있는 파일 디스크립터를 확인할 수 있습니다.

## 시그널 조사하기

GDB와 LLDB에서는 특정 시그널을 디버거가 가로채 멈출지, 출력할지, 프로그램에 그대로 전달할지 설정할 수 있습니다.

GDB 예:

```text
handle SIGUSR1 nostop noprint pass
handle SIGTERM stop print pass
```

LLDB 예:

```text
process handle SIGUSR1 --stop false --notify false --pass true
```

디버거가 시그널을 가로채면 프로그램의 시그널 핸들러가 원래 예상한 시점과 다르게 실행될 수 있습니다.

따라서 self-pipe 기반 시그널 처리를 조사한다면 디버거에서 사용한 시그널 처리 정책도 함께 기록합니다.

시그널 핸들러 내부를 한 단계씩 따라가면 타이밍과 비동기 실행 문맥 자체가 크게 달라질 수 있습니다.

가능하면 핸들러는 작게 유지하고 일반 이벤트 루프에서 실제 이벤트를 처리하는 함수에 브레이크포인트를 설정하는 편이 좋습니다.

## 코어 덤프

운영체제 설정이 허용한다면 비정상 종료 당시의 프로세스 상태를 코어 파일로 남길 수 있습니다.

```sh
ulimit -c unlimited
./program failing-input
```

GDB:

```sh
gdb ./program core
```

LLDB에서 코어 파일을 여는 방법과 지원되는 파일 형식은 플랫폼에 따라 달라질 수 있습니다.

코어 덤프에서는 다음 정보를 확인할 수 있습니다.

- 프로그램을 종료시킨 시그널
- 종료 당시 각 스레드의 호출 스택
- 레지스터와 메모리 상태
- 확인 가능한 일부 전역 변수와 지역 변수

실행 중에 발생했던 외부 상태 변화나 모든 로그가 코어 파일에 포함되는 것은 아닙니다.

또한 분석에 사용하는 실행 파일과 디버그 심볼은 코어 파일이 생성된 시점의 빌드와 정확히 일치해야 합니다.

코어 파일에는 비밀번호, 토큰, 개인정보나 실제 입력 데이터가 그대로 포함될 수 있습니다. 따라서 보관·전송·삭제 정책도 필요합니다.

## 공유 라이브러리와 심볼

디버거가 예상한 함수 이름을 찾지 못한다면 다음 사항을 확인합니다.

- 실행 파일과 공유 라이브러리에 디버그 정보가 포함되어 있는가?
- 심볼이 제거(strip)되었는가?
- 실제로 로드된 라이브러리가 예상한 버전인가?
- 소스 경로가 빌드 당시 환경과 달라졌는가?
- 함수가 인라인되었거나 최적화 과정에서 제거되었는가?

GDB의 `info sharedlibrary`나 LLDB의 `image list` 계열 명령을 사용하면 실제로 로드된 모듈을 확인할 수 있습니다.

## 디버거의 조작도 프로그램 상태를 바꿀 수 있습니다

디버거에서 식을 평가한다고 해서 항상 프로그램을 수동적으로 관찰하기만 하는 것은 아닙니다.

```text
GDB:  call function()
LLDB: expression -- function()
```

이 명령은 실제 함수를 호출하므로 전역 상태, 잠금, I/O와 힙 상태를 변경할 수 있습니다.

조사 대상 프로그램에 새로운 부수효과를 만들지 않도록 가능하면 읽기 전용 식을 중심으로 사용합니다.

디버거에서 변수 값을 강제로 변경하는 기능도 가설을 빠르게 확인하는 데는 유용할 수 있습니다.

그러나 값을 인위적으로 변경한 뒤 프로그램이 정상적으로 실행되었다는 사실은 원래 프로그램이 올바르게 동작한다는 증거가 아닙니다.

## Sanitizer와 디버거의 역할 구분하기

| 도구 | 강점 | 한계 |
|---|---|---|
| 컴파일러 경고 | 정적인 타입·형식·제어 흐름 문제 진단 | 실제 실행 상태는 알 수 없음 |
| ASan | 잘못된 힙·스택 접근과 use-after-free 탐지 | 실제로 실행된 경로만 관찰 |
| UBSan | 일부 정의되지 않은 동작 탐지 | 모든 종류의 UB를 발견하지는 않음 |
| TSan | 실행된 경로에서 데이터 경쟁 탐지 | 논리적 교착 상태와 불변식은 별도 검증 필요 |
| 디버거 | 특정 시점의 호출 스택·값·메모리 확인 | 실행 타이밍을 바꾸며 정확성을 자동으로 증명하지 않음 |
| 테스트 | 공개 계약과 회귀 동작 검증 | 작성한 테스트 사례에 한정 |

한 도구에서 문제가 발견되지 않았다는 사실을 다른 종류의 문제까지 없다는 의미로 확대해서 해석해서는 안 됩니다.

각 도구가 무엇을 확인할 수 있고 무엇은 확인할 수 없는지 구분해서 사용합니다.

## 조사 기록 남기기

다음 정보만 기록해도 같은 문제를 다시 재현하기 훨씬 쉬워집니다.

```text
기준 커밋과 컴파일러 버전
빌드 명령과 옵션
실행 명령, 환경과 입력
예상 결과와 실제 결과
멈춘 시그널·위치·스레드
관찰한 변수와 불변식
반증된 가설
수정 내용
수정 뒤 다시 실행한 테스트·Sanitizer
```

재현 입력에 사용한 임시 파일도 가능하면 테스트 픽스처로 남깁니다.

다만 개인정보나 비밀값처럼 저장해서는 안 되는 데이터는 먼저 제거해야 합니다.

## 권장 조사 순서

1. 경고 없이 동일한 빌드를 재현합니다.
2. 실패 입력과 종료 상태를 자동화된 테스트로 고정합니다.
3. 해당 결함을 찾는 데 적합한 Sanitizer가 있다면 먼저 실행합니다.
4. 충돌이나 불변식 위반이 발생하기 직전에 브레이크포인트를 설정합니다.
5. 호출 스택을 확인하고 프레임을 따라가며 잘못된 값의 출처를 추적합니다.
6. 포인터·길이·용량·소유 상태처럼 서로 관계된 값을 함께 확인합니다.
7. 수정한 뒤에는 원래 실패 사례뿐 아니라 전체 회귀 테스트를 실행합니다.
8. 다른 컴파일러와 실제 최적화 빌드에서도 다시 확인합니다.

디버거 세션에서 우연히 결함의 원인을 찾아냈다는 사실만으로 조사가 끝나는 것은 아닙니다.

최종적으로는 같은 실패를 자동으로 재현할 수 있고, 수정 뒤 그 결함이 다시 발생하는 것을 막는 테스트가 남아 있어야 합니다.
