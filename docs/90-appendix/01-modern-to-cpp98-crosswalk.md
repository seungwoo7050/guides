# Modern C++에서 C++98로 이동할 때의 대응표

## 목적

Modern C++의 기본 도구를 익힌 뒤 C++98 제약 프로젝트로 이동하면 “편의 기능이 없으니 예전 방식으로 대충 작성한다”는 오해가 생기기 쉽습니다. 실제로 사라지는 것은 도구이며, 소유권·불변식·실패 보장 같은 설계 책임은 그대로 남습니다.

## 소유권과 수명

| Modern C++ | C++98에서 필요한 결정 |
|---|---|
| Rule of Zero | 직접 자원을 가진 타입은 Rule of Three를 구현하거나 복사를 금지합니다. |
| `unique_ptr<T>` | 소유자를 하나로 제한하고 소멸자에서 해제합니다. 복사 생성자·대입을 private 선언해 막을 수 있습니다. |
| `shared_ptr<T>` | 공유 소유가 정말 필요하면 별도 reference counting 설계를 검토하지만, 대부분은 상위 객체가 수명을 소유하도록 재배치합니다. |
| `weak_ptr<T>` | 관찰자가 소유자보다 오래 살 수 없도록 구조를 바꾸거나 명시적 등록 해제를 둡니다. |
| 이동 생성자·이동 대입 | 복사 비용을 감수하거나 복사를 금지합니다. “소유권 이전처럼 보이는 얕은 복사”를 만들면 안 됩니다. |

C++98에서 raw pointer를 사용한다는 사실만으로 소유권이 불분명해도 되는 것은 아닙니다. 공개 API 문서와 클래스 책임이 다음을 답해야 합니다.

- 누가 생성하는가
- 누가 해제하는가
- 비소유 포인터가 언제까지 유효한가
- 복사할 때 자원이 공유되는가, 복제되는가, 복사가 금지되는가

## 값 타입과 타입 안전성

| Modern C++ | C++98 대응 |
|---|---|
| `enum class` | enum 이름을 namespace 또는 클래스 안에 두고 정수와의 암묵 변환을 경계합니다. |
| defaulted 비교 | `operator==`, `operator<`를 직접 구현하고 서로 모순되지 않게 테스트합니다. |
| 강한 typedef·wrapper | `explicit` 생성자를 가진 작은 클래스로 표현합니다. |
| `constexpr` | compile-time 계산보다 불변식과 const-correctness를 우선합니다. |
| `string_view`, `span` | `const std::string&`, pointer+length 또는 iterator pair를 사용하고 수명 전제를 문서화합니다. |

## 오류 표현

| Modern C++ | C++98 대응 |
|---|---|
| `optional<T>` | `bool` + 출력 매개변수, 상태 객체 또는 별도 result 클래스를 사용합니다. |
| `variant<A, B>` | tagged union 또는 공통 인터페이스를 사용하되 활성 상태를 명시적으로 추적합니다. |
| `expected<T, E>` | 성공 여부와 오류 값을 함께 가진 result 타입을 직접 정의할 수 있습니다. |
| `std::error_code` | 프로젝트 오류 enum과 메시지·원인을 분리합니다. |

출력 매개변수를 사용할 때는 실패 뒤 출력 값이 유지되는지, 초기화되는지, 부분 변경되는지 반드시 정합니다.

## 알고리즘과 호출 가능 객체

| Modern C++ | C++98 대응 |
|---|---|
| lambda | 함수 객체, 함수 포인터 또는 멤버 함수 포인터 |
| ranges | iterator pair와 `<algorithm>` |
| concepts | 문서화된 요구조건, compile-fail test와 명확한 진단 helper |
| range-for | 명시적 iterator loop |
| `std::function` | 고정된 인터페이스, 함수 객체 또는 command hierarchy |

C++98에서도 수동 loop보다 표준 알고리즘이 의도를 더 잘 표현하는 경우가 많습니다. 다만 복잡한 함수 객체가 loop보다 읽기 어려우면 단순한 loop가 낫습니다.

## 동시성과 시스템 자원

C++98 표준에는 thread가 없습니다. 프로젝트가 POSIX thread 또는 다른 API를 사용할 경우 다음을 직접 관리합니다.

- thread 생성 실패
- join 책임
- mutex 초기화와 파괴
- 조건 변수 predicate
- 종료 플래그의 동기화
- timeout에 사용할 시계

Modern C++의 `jthread`와 stop token을 사용할 수 없더라도 종료 순서는 명시해야 합니다.

```text
새 작업 거부
→ 대기 중 작업 처리 또는 취소
→ 실행 중 작업에 종료 신호
→ thread join
→ 공유 자원 파괴
```

## 선택 기준

C++98 프로젝트를 진행할 때 Modern C++ API를 모방하는 데 시간을 쓰지 않습니다. 다음 질문으로 필요한 설계만 남깁니다.

1. 이 자원의 단일 소유자는 누구인가
2. 객체가 항상 만족해야 하는 불변식은 무엇인가
3. 복사는 깊은 복사인가, 금지인가
4. 실패 뒤 객체는 어떤 상태인가
5. 종료 시 어떤 자원을 어떤 순서로 정리하는가

이 다섯 질문에 답할 수 있다면 도구가 달라도 동일한 설계 원리를 유지할 수 있습니다.
