# Modern C++에서 C++98로 전환할 때의 대응표

## 목적

Modern C++의 기본 도구를 익힌 뒤 C++98 제약이 있는 프로젝트로 이동하면, 편의 기능이 없으므로 예전 방식으로 대충 작성해도 된다고 오해하기 쉽습니다. 사라지는 것은 도구이지 소유권, 불변식과 실패 뒤 상태를 설계할 책임이 아닙니다.

## 소유권과 수명

| Modern C++ | C++98에서 필요한 결정 |
|---|---|
| Rule of Zero | 직접 자원을 소유한 타입은 Rule of Three를 구현하거나 복사를 금지합니다. |
| `unique_ptr<T>` | 소유자를 하나로 제한하고 소멸자에서 해제합니다. 복사 생성자와 대입 연산자를 비공개로 선언해 복사를 막을 수 있습니다. |
| `shared_ptr<T>` | 공유 소유가 정말 필요하면 참조 계수와 순환 참조 정책을 별도로 설계합니다. 가능하면 상위 객체 하나가 수명을 소유하도록 구조를 바꿉니다. |
| `weak_ptr<T>` | 관찰자가 소유자보다 오래 살지 않게 구성하거나, 명시적인 등록 해제와 무효화 규칙을 둡니다. |
| 이동 생성자·이동 대입 | 복사 비용을 감수하거나 복사를 금지하고 `swap`, `release` 같은 명시적 인계 함수를 사용합니다. 얕은 복사를 소유권 이전처럼 사용해서는 안 됩니다. |

C++98의 `std::auto_ptr`는 복사 시 소유권이 이전되는 특수한 의미를 가지며 배열과 표준 컨테이너 원소에 적합하지 않습니다. Modern C++의 `unique_ptr`를 그대로 대체한다고 가정하지 않습니다.

C++98에서 원시 포인터를 사용하더라도 소유권은 명확해야 합니다. 공개 인터페이스와 클래스 책임이 다음 질문에 답해야 합니다.

- 누가 생성합니까?
- 누가 해제합니까?
- 비소유 포인터나 참조는 언제까지 유효합니까?
- 복사할 때 자원이 공유됩니까, 복제됩니까, 아니면 복사가 금지됩니까?

## 값 타입과 타입 안전성

| Modern C++ | C++98 대응 |
|---|---|
| `enum class` | 열거자 이름을 클래스나 네임스페이스 안에 두고 정수와의 암묵 변환을 인터페이스에서 제한합니다. |
| 기본 비교 연산 | `operator==`, `operator<`를 직접 구현하고 서로 모순되지 않게 테스트합니다. |
| 강한 typedef·래퍼 | `explicit` 생성자를 가진 작은 값 클래스로 표현합니다. |
| `constexpr` | 컴파일 시점 계산을 억지로 흉내 내기보다 불변식과 `const` 정확성을 우선합니다. |
| `string_view`, `span` | `const std::string&`, 포인터와 길이, 반복자 쌍을 사용하고 원본 수명 전제를 문서화합니다. |

## 오류 표현

| Modern C++ | C++98 대응 |
|---|---|
| `optional<T>` | `bool`과 출력 매개변수, 상태 객체 또는 별도 결과 클래스를 사용합니다. |
| `variant<A, B>` | 태그가 있는 공용체나 공통 인터페이스를 사용하고 현재 활성 상태를 명시적으로 추적합니다. |
| `expected<T, E>` | 성공값과 오류값 중 하나를 보유하는 프로젝트 전용 결과 타입을 정의할 수 있습니다. |
| `std::error_code` | `errno`를 즉시 보존하거나 프로젝트 오류 열거형과 원인 데이터를 분리합니다. |

출력 매개변수를 사용할 때는 실패 뒤 출력값이 유지되는지, 초기화되는지, 부분적으로 변경될 수 있는지 반드시 정합니다. 명확한 이유가 없다면 임시 값에 결과를 만든 뒤 성공 시에만 출력값에 반영합니다.

## 알고리즘과 호출 가능 객체

| Modern C++ | C++98 대응 |
|---|---|
| 람다 | 함수 객체, 함수 포인터 또는 멤버 함수 포인터 |
| ranges | 반복자 쌍과 `<algorithm>` |
| concepts | 문서화한 타입 요구사항, 컴파일 실패 테스트와 작은 진단 보조 코드 |
| 범위 기반 `for` | 명시적인 반복자 루프 |
| `std::function` | 고정된 가상 인터페이스, 함수 객체 또는 명령 객체 계층 |

C++98에서도 표준 알고리즘이 수동 반복문보다 의도를 잘 표현하는 경우가 많습니다. 반대로 복잡한 함수 객체 때문에 흐름이 더 어려워진다면 단순한 반복문이 낫습니다.

## 동시성과 시스템 자원

C++98 표준에는 스레드 라이브러리가 없습니다. 프로젝트가 POSIX 스레드나 다른 플랫폼 API를 사용한다면 다음을 직접 관리합니다.

- 스레드 생성 실패
- 조인 책임
- 뮤텍스와 조건 변수의 초기화·파괴
- 조건 변수 대기 조건
- 종료 플래그의 동기화
- 제한 시간에 사용할 시계

Modern C++의 `jthread`와 `stop_token`을 사용할 수 없더라도 종료 순서는 명시해야 합니다.

```text
새 작업 거부
→ 대기 작업 처리 또는 취소
→ 실행 작업에 종료 요청
→ 스레드 조인
→ 공유 자원 파괴
```

## 선택 기준

C++98 프로젝트에서 Modern C++ API를 모방하는 데 시간을 쓰지 않습니다. 다음 질문으로 필요한 설계만 남깁니다.

1. 이 자원의 단일 소유자는 누구입니까?
2. 객체가 항상 만족해야 하는 불변식은 무엇입니까?
3. 복사는 깊은 복사입니까, 금지됩니까?
4. 실패 뒤 객체는 어떤 상태입니까?
5. 종료 시 어떤 자원을 어떤 순서로 정리합니까?

이 질문에 답할 수 있다면 사용할 수 있는 문법이 달라도 같은 설계 원칙을 유지할 수 있습니다.
