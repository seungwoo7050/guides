# Unix 텍스트 도구로 CLI 검증하기

명령행 프로그램은 stdout, stderr와 종료 상태라는 안정적인 외부 경계를 제공합니다. POSIX shell과 `cmp`, `diff`, `grep`, `sed`, `awk`를 활용하면 별도의 테스트 프레임워크 없이도 유용한 시스템 테스트를 구성할 수 있습니다.

목표는 각 도구의 문법을 많이 외우는 것이 아니라, **어떤 결과를 어떤 관찰 채널에서 확인하고 어떤 도구로 검증해야 하는지 구분하는 것**입니다.

## 세 가지 관찰 채널

```text
stdout       정상 데이터
stderr       진단과 오류
exit status  성공·실패 또는 결과 분류
```

각 채널은 따로 관찰합니다.

```sh
./program >actual.out 2>actual.err
status=$?
```

오류 메시지가 올바르게 출력되더라도 종료 상태가 0이면 자동화 도구는 실행이 성공했다고 판단할 수 있습니다. 반대로 정상 출력이 맞더라도 실패 상태로 종료됐다면 전체 계약은 충족되지 않은 것입니다.

stdout과 stderr를 합치면 어느 채널에서 출력된 데이터인지 구분하기 어려워지고 실제 출력 순서도 해석하기 까다로워질 수 있습니다. 따라서 진단을 위해 필요한 경우에만 `2>&1`을 사용합니다.

## shell script의 최소 골격

```sh
#!/bin/sh
set -eu

fail()
{
    printf '실패: %s\n' "$*" >&2
    exit 1
}

actual=$(./program input) || fail "프로그램이 실패 상태로 끝났습니다"
[ "$actual" = "expected" ] || fail "예상과 다른 출력입니다"

printf '검사 통과\n'
```

* `set -e`는 별도로 처리하지 않은 명령이 실패했을 때 스크립트를 중단하게 합니다.
* `set -u`는 정의하지 않은 변수를 사용했을 때 오류로 처리합니다.

다만 `set -e`만으로 모든 실패를 안전하게 처리할 수 있다고 가정해서는 안 됩니다. 조건식, `if`, `!`, 파이프라인과 명령 치환 안에서는 동작이 달라질 수 있습니다.

중요한 명령의 종료 상태는 직접 저장하고 검사합니다.

`pipefail`은 여러 shell에서 제공하지만 POSIX 표준 기능은 아닙니다. `/bin/sh` 호환성이 필요하다면 파이프라인의 각 단계를 임시 파일과 별도의 명령으로 나누거나 Python 헬퍼를 사용합니다.

## 예상된 실패의 종료 상태를 안전하게 확인하기

실패를 기대하는 명령은 종료 상태를 직접 저장합니다.

```sh
set +e
./program bad-input >"$tmp/out" 2>"$tmp/err"
status=$?
set -e

[ "$status" -eq 2 ] || fail "문법 오류 상태가 2가 아닙니다"
```

또는 `if` 문맥을 사용할 수 있습니다.

```sh
if ./program bad-input >"$tmp/out" 2>"$tmp/err"
then
    fail "실패해야 하는 입력이 성공했습니다"
else
    status=$?
fi
```

`$?`는 반드시 검사하려는 명령 바로 다음에 저장합니다.

그 사이에 다른 `printf`, `test`나 정리 명령이 실행되면 `$?`는 해당 명령의 종료 상태로 덮어써집니다.

## 임시 디렉터리와 정리

현재 디렉터리나 `/tmp/result`처럼 고정된 경로에 테스트 파일을 만들면 반복 실행, 병렬 실행이나 다른 사용자의 작업과 충돌할 수 있습니다.

```sh
tmp=$(mktemp -d) || exit 1
trap 'rm -rf "$tmp"' EXIT HUP INT TERM
```

테스트가 생성하는 파일은 모두 이 디렉터리 아래에 둡니다.

```text
$tmp/stdout
$tmp/stderr
$tmp/expected
$tmp/work/
```

`trap`에 전달하는 문자열 안에 사용자 입력이나 검증 대상 경로를 코드처럼 삽입해서는 안 됩니다.

임시 디렉터리의 경로를 변수에 저장하고 일관되게 인용합니다.

## 정확한 바이트 비교: `cmp`

두 파일이 바이트 단위로 완전히 같은지만 확인하려면 `cmp`가 적합합니다.

```sh
cmp -s "$tmp/expected.bin" "$tmp/actual.bin" \
    || fail "바이트열이 다릅니다"
```

다음과 같은 경우에는 내용이 텍스트처럼 보여도 `cmp`를 사용하는 편이 안전합니다.

* 마지막 개행 문자의 유무가 계약에 포함되는 경우
* NUL 바이트가 포함될 수 있는 경우
* 공백과 탭을 정확히 구분해야 하는 경우
* 사람이 읽을 차이보다 자동 성공·실패 판정이 중요한 경우

명령 치환은 끝부분의 개행 문자를 제거하므로 정확한 바이트 비교에는 적합하지 않습니다.

```sh
actual=$(printf 'a\n\n')  # 끝의 개행 문자들이 제거됨
```

정확한 바이트를 확인할 때는 파일 리디렉션을 사용합니다.

shell 변수 자체도 NUL 바이트를 안전하게 보존할 수 없습니다.

## 사람이 읽기 좋은 차이: `diff`

텍스트의 줄 단위 차이를 사람이 확인해야 한다면 `diff`를 사용합니다.

```sh
if ! diff -u "$tmp/expected.txt" "$tmp/actual.txt"
then
    fail "텍스트 출력이 다릅니다"
fi
```

기대 결과는 heredoc으로 만들 수 있습니다.

```sh
cat >"$tmp/expected.txt" <<'EXPECTED'
count=3
minimum=-1
maximum=7
EXPECTED
```

delimiter를 인용하면 기대값 안에서 shell 변수나 명령 치환이 확장되지 않습니다.

출력 순서가 계약에 포함되지 않는다면 비교 전에 정렬할 수도 있습니다. 다만 정렬하면 원래 출력의 순서 오류를 숨길 수 있습니다.

따라서 **순서가 아니라 값의 집합만 중요하다는 것이 실제 계약일 때만** 이러한 정규화를 사용합니다.

## 특정 내용의 존재·부재 검사: `grep`

```sh
grep -q '^ready$' "$tmp/actual" \
    || fail "ready 행이 없습니다"

if grep -q 'fatal' "$tmp/actual"
then
    fail "예상하지 않은 fatal 문구가 있습니다"
fi
```

`grep`은 특정 패턴이 존재하는지 확인하는 데 적합합니다.

전체 출력이 정확히 일치하는지를 검증하는 도구는 아닙니다. 기대한 한 줄이 존재하더라도 그 뒤에 잘못된 출력이 추가로 있을 수 있습니다.

고정 문자열을 찾을 때는 `grep -F`를 사용하면 정규식 메타문자가 해석되는 것을 피할 수 있습니다.

```sh
grep -Fq 'a+b' "$tmp/actual"
```

패턴이 `-`로 시작할 수 있다면 `--`를 지원하는 구현인지 확인하거나, 이러한 입력을 안전하게 처리할 수 있는 고정된 패턴 사용 방식을 정합니다.

## 단순한 변환과 줄 선택: `sed`

```sh
sed 's/[[:space:]]*$//' "$tmp/actual" >"$tmp/normalized"
```

비결정적인 PID나 절대 임시 경로처럼 테스트마다 달라질 수 있는 값만 제거한 뒤 나머지 구조를 비교할 수 있습니다.

다만 정규화를 지나치게 적용하면 실제 결함까지 숨길 수 있습니다.

```text
허용된 비결정성만 제거
의미 있는 필드, 개수와 순서는 그대로 검사
```

예를 들어 모든 숫자를 `<number>`로 치환하면 PID 차이뿐 아니라 잘못된 개수나 상태 값까지 놓칠 수 있습니다.

## AWK의 레코드·필드 모델

AWK는 기본적으로 한 줄을 하나의 레코드로 읽고 공백을 기준으로 필드를 나눕니다.

```awk
pattern { action }
```

주요 자동 변수는 다음과 같습니다.

| 이름              | 의미            |
| --------------- | ------------- |
| `$0`            | 현재 줄 전체       |
| `$1`, `$2`, ... | 각 필드          |
| `NF`            | 현재 줄의 필드 수    |
| `NR`            | 지금까지 읽은 레코드 수 |
| `FS`            | 입력 필드 구분자     |
| `OFS`           | 출력 필드 구분자     |

```sh
awk '$3 == "done" { count++ } END { print count + 0 }' log.txt
```

AWK는 필드 검사, 집계와 작은 상태 머신을 작성하는 데 적합합니다.

## 출력 형식 전체를 검사합니다

모든 줄이 다음 형식을 따른다고 가정합니다.

```text
<timestamp> <worker-id> <state>
```

```sh
awk '
    /^[0-9]+ [1-9][0-9]* (start|work|done)$/ { next }
    {
        printf "%d번째 줄 형식 오류: %s\n", NR, $0 > "/dev/stderr"
        bad = 1
    }
    END { exit bad }
' "$tmp/log"
```

올바른 줄은 `next`로 넘기고, 나머지 줄은 오류로 처리합니다.

정규식에서 `^`와 `$`를 빼면 일부만 형식에 맞는 줄이나 뒤에 불필요한 문자가 붙은 줄까지 통과할 수 있습니다.

빈 파일을 허용할지도 별도로 정해야 합니다.

위 스크립트는 입력이 0줄이어도 성공하므로 최소 한 줄이 필요하다면 다음과 같이 조건을 추가할 수 있습니다.

```awk
END {
    if (NR == 0)
        bad = 1
    exit bad
}
```

## 연관 배열로 상태 불변식을 검사합니다

AWK의 연관 배열을 사용하면 ID별 상태를 추적할 수 있습니다.

```awk
$3 == "done" {
    if (finished[$2]) {
        printf "%d번째 줄: %s의 done이 중복됨\n", NR, $2 > "/dev/stderr"
        bad = 1
    }
    finished[$2] = 1
}

END { exit bad }
```

동시성 로그에서는 다음과 같은 조건을 검사할 수 있습니다.

* worker ID가 허용된 범위에 있는가?
* 허용된 상태 이름만 출력되는가?
* `start` 전에 `work`가 나타나지 않는가?
* `done` 뒤에 추가 작업이 나타나지 않는가?
* ID별 작업 횟수가 올바른가?
* 전체 시작 수와 종료 수가 일치하는가?
* 전체 합계나 보존량이 유지되는가?
* timestamp가 정수 형식인가?

스케줄러에 따라 전체 출력 순서가 달라질 수 있다면 고정된 완전 순서를 기대해서는 안 됩니다.

대신 반드시 지켜져야 하는 상태 전이와 불변식을 검사합니다.

## stdout·stderr·종료 상태를 함께 검증합니다

```sh
set +e
./program bad-input >"$tmp/out" 2>"$tmp/err"
status=$?
set -e

[ "$status" -eq 2 ] || fail "상태: 기대 2, 실제 $status"
[ ! -s "$tmp/out" ] || fail "실패 시 stdout은 비어야 합니다"
grep -Fq '오류:' "$tmp/err" || fail "진단 문구가 없습니다"
```

오류 메시지 전체가 공개 API가 아니라면 오류의 핵심 분류만 검사할 수 있습니다.

반대로 CLI의 정확한 문구 자체가 자동화 계약의 일부라면 전체 출력을 파일 단위로 비교해야 합니다.

시스템 오류 문자열은 locale에 따라 달라질 수 있으므로 `strerror`가 반환한 전체 문구를 고정된 기대값으로 사용하는 것은 신중해야 합니다.

## 바이너리 데이터와 NUL 바이트

shell 변수는 NUL 바이트를 보존하지 못합니다.

바이너리 데이터를 검사할 때는 파일 크기, `cmp`, `od` 또는 작은 Python 헬퍼를 사용합니다.

```sh
bytes=$(wc -c <"$tmp/output")
[ "$bytes" -eq 4 ] || fail "바이트 수가 다릅니다"

cmp -s "$tmp/expected.bin" "$tmp/output" \
    || fail "바이너리 출력이 다릅니다"
```

사람이 실제 바이트를 확인하려면 `od`를 사용할 수 있습니다.

```sh
od -An -tx1 "$tmp/output"
```

다만 `od`가 출력하는 공백이나 형식을 테스트 계약으로 삼기보다 실제 바이너리 파일을 `cmp`로 비교하는 편이 견고합니다.

## fixture와 작은 헬퍼

테스트가 호스트 시스템의 `printf`, `head`, `yes` 구현 차이에 지나치게 의존하지 않도록 한 가지 목적만 수행하는 작은 C 헬퍼를 만들 수 있습니다.

* 정확한 바이트 수를 출력하는 generator
* 정확한 바이트 수를 읽고 검사하는 consumer
* 지정한 종료 상태로 끝나는 프로그램
* 자신에게 특정 시그널을 보내 종료하는 프로그램
* 각 `argv` 항목과 길이를 출력하는 프로그램
* 실행되면 marker file을 만드는 프로그램

헬퍼 프로그램도 본 코드와 동일한 엄격한 warning 옵션으로 빌드합니다.

테스트 헬퍼 자체가 복잡해지면 테스트 코드가 또 다른 결함의 원인이 될 수 있습니다.

## 큰 파이프라인 검증

작은 입력은 파이프 버퍼 안에 전부 들어갈 수 있으므로 잘못된 `wait` 순서나 파일 디스크립터 관리가 있어도 우연히 테스트를 통과할 수 있습니다.

generator와 consumer 헬퍼를 이용해 수 MiB 단위의 데이터를 전송해 봅니다.

```text
emit-bytes 4194304 | expect-bytes 4194304
```

단순히 최종 종료 상태만 확인해서는 충분하지 않습니다.

다음 조건도 함께 검사합니다.

* 정확한 바이트 수가 도착했는가?
* 정해진 timeout 안에 종료했는가?
* generator와 consumer가 모두 회수되었는가?
* 예상하지 않은 stderr 출력이 없는가?
* 반복해서 실행해도 열린 FD 수가 증가하지 않는가?

## timeout과 프로세스 그룹 정리

프로세스, 파이프나 스레드를 검사하는 테스트는 결함이 있을 경우 무한히 대기할 수 있습니다.

GNU `timeout`은 편리하지만 POSIX 표준 명령은 아닙니다.

```sh
timeout 5 ./program
```

이식성이 필요하다면 Python을 사용할 수 있습니다.

```python
subprocess.run(command, timeout=5, check=True)
```

검사 대상 프로세스가 다시 자식 프로세스를 생성한다면 부모 PID 하나만 종료해서는 손자 프로세스가 남을 수 있습니다.

이 경우 새 세션이나 프로세스 그룹에서 실행하고, timeout이 발생하면 전체 그룹을 종료한 뒤 `wait`로 회수합니다.

```python
process = subprocess.Popen(command, start_new_session=True)
os.killpg(process.pid, signal.SIGKILL)
process.wait()
```

timeout은 정상 실행 시간보다 충분히 여유 있게 설정해 느린 CI 환경에서 발생하는 거짓 실패를 줄입니다.

timeout 안에 끝났다는 사실은 성능을 보장하는 것이 아니라 **무한히 대기하지 않았음을 관찰한 것**입니다.

## 경쟁 상태를 `sleep`으로 만들지 않습니다

다음 방식은 프로그램이 실제로 준비됐는지 보장하지 않습니다.

```sh
sleep 0.1
kill -USR1 "$pid"
```

느린 환경에서는 시그널 핸들러가 설치되기 전에 시그널이 전달될 수도 있습니다.

보다 안정적인 방식은 명시적인 준비 신호를 사용하는 것입니다.

```text
프로그램이 "ready pid=..." 출력
→ 테스트가 해당 줄을 timeout 안에 읽음
→ 준비가 확인된 뒤 signal 전송
```

스레드 테스트에서도 임의의 `sleep` 대신 barrier, condition variable 또는 pipe handshake를 사용해 시작 시점을 조정합니다.

## 부분 순서와 비결정성

전체 출력 순서가 결정되어 있지 않더라도 일부 관계는 반드시 지켜져야 할 수 있습니다.

```text
ready는 event보다 먼저 나타남
start(id)는 done(id)보다 먼저 나타남
종료 메시지 뒤에는 추가 업무 로그가 없음
```

AWK 상태 머신이나 Python 테스트를 사용해 이러한 부분 순서(partial order)를 검사할 수 있습니다.

전체 출력을 정렬한 뒤 비교하면 실제 순서 위반을 숨길 수 있으므로 주의해야 합니다.

## 재실행과 테스트 독립성

프로그램을 한 번만 실행해서는 전역 상태 오염, 임시 파일 누락이나 파일 디스크립터 누수를 발견하지 못할 수 있습니다.

다음과 같은 반복 검사를 사용할 수 있습니다.

* 같은 프로세스에서 API를 여러 번 호출
* 실행 파일을 여러 번 시작
* 동일한 입력을 순서만 바꾸어 실행
* 성공 뒤 실패, 실패 뒤 성공을 연속해서 실행
* 실행이 끝날 때마다 임시 디렉터리가 예상한 상태인지 확인

테스트 사이에서 상태를 공유해야 할 명확한 이유가 없다면 fixture는 각 테스트 사례마다 새로 만듭니다.

## failure injection

오류 경로를 검사하기 위해 실제 메모리 부족이나 드문 시스템 오류가 발생하기를 기다릴 필요는 없습니다.

실패를 주입할 수 있는 경계를 마련합니다.

* allocator callback이 N번째 호출에서 실패
* 헬퍼 프로그램이 지정한 상태로 종료
* 유효하지 않은 파일 디스크립터 전달
* reader가 닫힌 파이프 사용
* 잘못된 parser 입력
* 목적지 값이 오버플로 직전인 상태

실패를 주입한 뒤에는 단순히 반환값만 확인하지 않습니다.

출력 매개변수, 기존 객체의 불변식과 이후 정상적으로 정리할 수 있는지도 함께 확인합니다.

## known-bad 구현으로 테스트 품질을 확인합니다

정상 구현이 모든 테스트를 통과한다고 해서 테스트가 충분하다는 뜻은 아닙니다.

의도적으로 알려진 결함을 넣은 구현이 실제로 실패하는지도 확인할 수 있습니다.

```text
문자열의 마지막 NUL 한 바이트 누락
realloc 반환값을 원래 포인터에 바로 대입
부모 프로세스가 파이프 write end를 계속 열어 둠
문법 오류 뒤에도 왼쪽 command 실행
두 mutex의 잠금 순서 반전
```

반드시 완전한 mutation testing 프레임워크가 필요한 것은 아닙니다.

핵심 실패 조건마다 작은 broken fixture나 의도적으로 잘못된 구현을 만들어 현재 테스트가 해당 결함을 잡아내는지 확인할 수 있습니다.

## 실패 메시지에는 재현 정보를 포함합니다

테스트가 실패했을 때는 최소한 다음 정보를 확인할 수 있어야 합니다.

* 테스트 사례 이름
* 실행 명령 또는 입력
* 기대한 종료 상태와 실제 종료 상태
* stdout·stderr 파일 경로나 짧은 출력 내용
* timeout 발생 여부
* 임시 결과를 보존할 수 있는 방법

단순히 `test failed` 한 줄만 출력하면 원인을 파악하기 위해 테스트 코드 자체를 다시 읽어야 합니다.

C 테스트 매크로에서도 파일, 줄 번호와 실패한 식을 함께 출력할 수 있습니다.

```c
#define CHECK(expression) do {                                      \
    if (!(expression))                                              \
    {                                                               \
        fprintf(stderr, "%s:%d: 실패: %s\n",                        \
                __FILE__, __LINE__, #expression);                   \
        return 1;                                                   \
    }                                                               \
} while (0)
```

## 도구 선택 기준

| 질문                                     | 적합한 도구      |
| -------------------------------------- | ----------- |
| 바이트가 완전히 같은가?                          | `cmp`       |
| 텍스트 차이를 사람이 확인해야 하는가?                  | `diff`      |
| 특정 문자열이 존재하거나 없어야 하는가?                 | `grep`      |
| 허용된 비결정성만 정규화해야 하는가?                   | `sed`       |
| 필드 검사·집계·상태 추적이 필요한가?                  | `awk`       |
| 명령 조립·리디렉션·종료 상태 관리가 필요한가?             | POSIX shell |
| timeout·signal·process group 제어가 필요한가? | Python 헬퍼   |
| 메모리·UB·data race를 관찰해야 하는가?            | sanitizer   |

한 가지 도구로 모든 검증을 해결하려고 하지 않습니다.

검증하려는 계약에 맞는 가장 단순한 도구를 선택합니다.

## 테스트의 한계

CLI 테스트는 프로그램의 공개 동작을 확인하는 데 효과적이지만 다음 사실까지 직접 증명하지는 않습니다.

* 내부 메모리 누수가 없음
* 데이터 경쟁이 없음
* 모든 가능한 interleaving이 안전함
* 테스트하지 않은 입력에서도 항상 안전함
* 성능 상한을 언제나 만족함

따라서 unit test, integration test, 코드 리뷰, sanitizer와 debugger를 함께 사용합니다.

새니타이저를 통과했다는 사실 역시 실제로 실행한 입력과 실행 경로에 대한 근거일 뿐입니다.

## 기존 예제와 연결하기

`examples/text-checks`에서는 다음과 같은 검증 방식을 확인할 수 있습니다.

* `cmp`: 정확한 도움말 출력과 바이트 결과 비교
* `diff`: 사람이 읽기 좋은 정상 출력 비교
* `grep`: 오류 메시지의 존재와 stdout 부재 확인
* `awk`: 로그 형식, ID별 상태와 줄 수 검사
* 임시 디렉터리와 `trap`을 이용한 정리
* 실패 시 0이 아닌 종료 상태 반환

```sh
make -C examples/text-checks check
```
