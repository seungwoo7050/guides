# 터미널, 프로세스와 커널

터미널 화면에 보이는 한 줄은 여러 계층을 통과한 결과입니다. 셸이 입력을 해석하지 못한 실패, 프로그램이 잘못된 인자를 받은 실패, 커널이 자원 접근을 거부한 실패, 프로그램이 정상적으로 입력을 기다리는 상태를 구분하려면 각 계층의 역할부터 나눠야 합니다.

## 학습 목표

이 문서를 마치면 다음을 할 수 있어야 합니다.

- 터미널, 셸, 프로그램, 프로세스와 커널을 구분합니다.
- 현재 작업 디렉터리, 환경, 사용자와 파일 디스크립터가 프로세스 상태임을 설명합니다.
- 명령 탐색 결과와 실제 실행 파일을 확인합니다.
- stdout, stderr와 종료 상태를 독립된 결과로 기록합니다.
- 프롬프트가 돌아오지 않는 상태를 실행 중·입력 대기·미완성 셸 입력으로 나눕니다.

## 선행 개념

- 터미널의 exit status와 OS가 process/file 자원을 중개하는 기본 모델

## 실행 경로

```text
사용자 입력
  │
  ▼
터미널 또는 의사 터미널
  │ 바이트 전달
  ▼
셸 프로세스
  ├─ 입력 문법 해석
  ├─ 명령 탐색
  ├─ 파일 디스크립터 연결
  ├─ 셸 내장 명령 실행
  └─ 외부 프로그램 프로세스 생성
          │ 시스템 호출
          ▼
        커널
          ├─ 자격 정보 확인
          ├─ 경로와 실행 파일 확인
          ├─ 메모리·FD·시그널 상태 준비
          └─ CPU에서 스레드 실행
                  │
                  ▼
          stdout / stderr / 종료 상태
```

### 터미널

터미널 애플리케이션은 창, 키보드 입력, 화면 출력과 세션 연결을 담당합니다. `pwd`, `python3`, `git`의 의미를 직접 해석하지 않습니다. 터미널은 보통 의사 터미널(PTY)을 통해 셸이나 포그라운드 프로세스 그룹과 바이트를 주고받습니다.

### 셸

셸은 문자열을 명령 문장으로 해석하고 실행 대상을 결정합니다. 현재 디렉터리를 바꾸는 `cd`처럼 현재 셸 자체의 상태를 변경해야 하는 동작은 셸 내장 명령으로 구현되는 경우가 많습니다.

```sh
printf 'login shell: %s\n' "${SHELL-unknown}"
ps -p $$ -o pid=,ppid=,state=,command=
```

`$SHELL`은 계정에 설정된 로그인 셸을 나타내며 현재 실행 중인 셸과 항상 같지는 않습니다. 실제 프로세스는 `ps` 같은 관찰로 확인합니다.

셸 문법의 세부 규칙은 `guide-shell-scripting`이 담당합니다. 여기서는 **셸이 외부 프로그램보다 먼저 문자열을 해석한다**는 경계만 사용합니다.

### 프로그램과 프로세스

프로그램은 실행 가능한 파일이나 스크립트입니다. 프로세스는 프로그램이 실행되면서 커널이 관리하는 상태입니다. 같은 프로그램 파일을 여러 번 실행하면 서로 다른 프로세스가 생길 수 있습니다.

프로세스는 대략 다음 상태를 가집니다.

```text
PID와 부모 PID
사용자·그룹 자격 정보
현재 작업 디렉터리
환경 변수
가상 주소 공간
파일 디스크립터 표
시그널 처리 상태
하나 이상의 스레드
```

프로그램 파일만 같다고 실행 결과가 같지는 않습니다. 현재 디렉터리, 환경, 사용자, 열린 파일과 입력이 다르면 결과도 달라질 수 있습니다.

### 커널 경계

사용자 공간 프로그램은 파일을 열거나 프로세스를 만들고 소켓을 사용할 때 커널 경계를 통과합니다. 커널은 자원 존재 여부, 권한, 상태와 제한을 검사하고 성공 결과나 오류를 돌려줍니다.

```text
애플리케이션 의도
→ 라이브러리·런타임
→ 시스템 호출
→ 커널 검사
→ 자원 상태 변경 또는 오류
```

시스템 호출 성공은 업무 목적이 맞았다는 뜻이 아닙니다. 허용된 권한으로 잘못된 파일을 변경할 수도 있으므로 “요청이 허용됨”과 “변경 대상이 올바름”을 구분해야 합니다.

## 실행 문맥 관찰

문제를 재현하기 전에 최소 실행 문맥을 기록합니다.

```sh
date '+%Y-%m-%d %H:%M:%S %z'
pwd
id
printf 'shell_pid=%s\n' "$$"
printf 'PATH=%s\n' "$PATH"
```

모든 환경 변수를 그대로 저장하면 비밀값이 노출될 수 있습니다. 증상에 필요한 키만 선택하고 token, password, private key는 기록하지 않습니다.

### 현재 디렉터리

상대 경로는 프로세스의 현재 작업 디렉터리에서 시작합니다. 두 터미널 탭은 서로 다른 셸 프로세스이므로 한 탭의 `cd`가 다른 탭을 바꾸지 않습니다.

```sh
pwd
```

서비스가 대화형 셸에서는 동작하지만 감독자 아래에서 실패한다면 작업 디렉터리가 다를 가능성을 확인합니다.

### 명령 탐색

화면에 입력한 이름과 실행된 파일의 정체성을 분리합니다.

```sh
type command-name
command -v command-name
```

지원하는 셸에서는 모든 후보를 확인할 수 있습니다.

```sh
type -a command-name
```

`PATH` 앞쪽에 오래된 실행 파일이 있으면 명령은 존재하지만 예상과 다른 프로그램이 실행될 수 있습니다. 버전 문자열만 보지 말고 실제 경로, 파일 유형과 설치 출처를 함께 확인합니다.

```sh
resolved=$(command -v command-name) || exit 1
printf 'resolved=%s\n' "$resolved"
file "$resolved"
```

명령 탐색 캐시를 사용하는 셸도 있습니다. 파일을 교체한 뒤에도 결과가 이상하면 현재 셸의 매뉴얼에 따라 캐시를 갱신하거나 새 셸에서 재검증합니다.

## 세 가지 결과 통로

프로세스는 보통 다음 결과를 남깁니다.

| 결과 | 의미 |
|---|---|
| stdout | 정상 결과나 다음 프로그램이 소비할 데이터 |
| stderr | 진단과 오류 문맥 |
| 종료 상태 | 부모가 성공·실패·별도 상태를 판단할 정수 |

터미널에서는 stdout과 stderr가 같은 화면에 섞일 수 있지만 서로 다른 스트림입니다.

```sh
command >stdout.log 2>stderr.log
status=$?
printf 'status=%s\n' "$status"
```

종료 상태는 실패 명령 직후 저장합니다. 다른 명령을 실행하면 `$?`는 덮어써집니다.

```sh
false
status=$?
printf 'status=%s\n' "$status"
```

출력이 없다고 실패한 것도 아니며, 오류 문장이 보인다고 반드시 non-zero로 종료한 것도 아닙니다. 자동 검증은 문장, 종료 상태와 실제 대상 상태를 함께 확인해야 합니다.

## 프롬프트가 돌아오지 않을 때

### 정상 실행 중

```sh
sleep 10
```

출력이 없어도 프로세스는 실행 중일 수 있습니다.

### 입력 대기

```sh
cat
```

`cat`은 stdin에서 EOF를 기다립니다. 터미널에서 `Ctrl+D`는 문자를 보내는 것이 아니라 입력 끝 조건을 전달할 수 있습니다.

### 셸 입력 미완성

닫히지 않은 따옴표나 미완성 구문이 있으면 외부 프로그램은 아직 시작되지 않았습니다. 셸은 보조 프롬프트로 추가 입력을 기다릴 수 있습니다. 현재 입력을 취소하려면 일반적으로 `Ctrl+C`를 사용합니다.

### 계산 또는 I/O 대기

프로세스가 CPU를 계속 사용하거나 파일·소켓·잠금·자식 종료를 기다릴 수 있습니다. 화면만 보고 “멈춤”이라고 판단하지 않습니다. [프로세스, 시그널과 작업 제어](../02-process-and-resource-observation/01-processes-signals-and-jobs.md)에서 상태를 더 좁힙니다.

## 읽기 전용 진단 순서

```text
1. 정확한 입력과 시각을 기록합니다.
2. 현재 디렉터리와 사용자를 확인합니다.
3. 명령 이름이 어떤 실행 파일로 해석되는지 확인합니다.
4. stdout, stderr와 종료 상태를 분리합니다.
5. 프로세스가 생성됐는지 확인합니다.
6. 상태를 바꾸지 않는 관찰로 다음 계층을 선택합니다.
```

처음부터 `sudo`, 재설치, 설정 전체 초기화나 강제 종료를 사용하지 않습니다. 이런 변경은 원래 증상을 지우고 새로운 상태를 만들 수 있습니다.
