# 사용자, 권한과 환경

같은 실행 파일도 사용자·그룹, 현재 디렉터리, 환경, `umask`와 열린 자원이 다르면 다른 결과를 만듭니다. 권한 문제를 해결한다고 모든 파일을 `777`로 바꾸거나 `sudo`를 추가하면 원인 대신 새로운 공격면과 소유권 문제를 만들 수 있습니다.

## 학습 목표

- 프로세스 자격 정보와 파일 모드의 관계를 설명합니다.
- 일반 파일과 디렉터리의 읽기·쓰기·실행 비트 의미를 구분합니다.
- 부모 디렉터리 탐색 권한이 경로 접근에 필요함을 설명합니다.
- 환경 변수와 `PATH`, 현재 디렉터리, `umask`를 실행 문맥으로 확인합니다.
- `sudo` 전후의 사용자·환경·생성 파일 소유권 차이를 추적합니다.
- 비밀값을 노출하지 않고 필요한 환경만 기록합니다.

## 선행 개념

- path resolution·process 문맥과 file/directory mode 차이

## 실행 문맥

```text
프로세스
├─ real/effective UID
├─ real/effective GID와 추가 그룹
├─ 현재 작업 디렉터리
├─ 환경 변수
├─ umask
├─ resource limits
└─ 열린 파일 디스크립터
```

권한 진단은 파일 모드 한 줄로 끝나지 않습니다.

```text
경로 구성 요소 탐색
→ 각 부모 디렉터리 x 권한
→ 대상 객체 유형과 작업
→ owner/group/other mode 선택
→ ACL·확장 보안 정책·마운트 옵션
→ 허용 또는 오류
```

## 사용자와 그룹

```sh
whoami
id
```

커널은 주로 숫자 UID와 GID를 사용하며 사용자 이름은 사람이 읽기 위한 매핑입니다. `id`로 기본 그룹과 추가 그룹을 함께 확인합니다.

실행 중인 프로세스는 로그인 시점의 자격 정보를 유지할 수 있습니다. 계정의 그룹 구성을 바꾼 뒤 기존 셸에서 결과가 달라지지 않는다면 새 로그인 세션에서 확인합니다.

프로세스별 사용자:

```sh
ps -p PID -o pid=,ppid=,user=,group=,command=
```

서비스 관리자나 컨테이너가 예상과 다른 사용자로 프로세스를 실행할 수 있습니다. 파일 소유권만 보지 말고 실제 프로세스 자격을 확인합니다.

## 파일과 디렉터리 모드

```text
-rwxr-x---
 │││ │││ │││
 owner group other
```

### 일반 파일

- 읽기: 내용 읽기
- 쓰기: 내용 변경
- 실행: 프로그램으로 실행 시도 허용

실행 비트가 있어도 형식, interpreter, architecture, mount option 때문에 실행이 실패할 수 있습니다.

### 디렉터리

- 읽기: 항목 이름 목록 읽기
- 쓰기: 항목 생성·삭제·이름 변경
- 실행: 디렉터리 통과와 이름 lookup

파일이 읽기 가능해 보여도 부모 디렉터리에 실행 권한이 없으면 경로를 따라갈 수 없습니다. 반대로 파일 삭제는 파일의 쓰기 비트보다 부모 디렉터리에서 항목을 변경할 권한과 더 직접적으로 관련됩니다.

Linux에서는 설치되어 있다면 다음이 유용합니다.

```sh
namei -l path/to/item
```

macOS에서는 각 부모 디렉터리를 `ls -ld`나 `stat`으로 확인합니다.

## ACL과 추가 경계

기본 모드가 허용해 보여도 다음이 접근을 제한할 수 있습니다.

- ACL
- read-only 또는 `noexec` 같은 mount option
- macOS sandbox·privacy control·extended attribute
- Linux security module 정책
- 컨테이너 namespace와 bind mount

Linux:

```sh
getfacl path
```

macOS:

```sh
ls -le path
xattr -l path
```

도구가 없거나 권한이 부족할 수 있습니다. 먼저 기본 모드와 경로 탐색을 확인한 뒤 추가 경계로 이동합니다.

## `umask`

`umask`는 새 객체의 기본 권한에서 비트를 제거합니다.

```sh
umask
```

대표 모델:

```text
regular file base 0666
 directory base   0777
최종 모드 = base에서 umask 비트 제거
```

`umask 077`이라면 일반적으로 새 파일은 소유자만 읽고 쓸 수 있는 `0600`, 디렉터리는 `0700`이 됩니다. 애플리케이션이 명시 모드를 사용하거나 ACL 기본값이 있으면 결과는 달라질 수 있습니다.

현재 셸 상태를 바꾸지 않고 관찰하려면 하위 셸을 사용합니다.

```sh
(
  umask 077
  mkdir private-dir
  printf 'data\n' > private-file
  ls -ld private-dir private-file
)
```

## 환경과 `PATH`

환경 변수는 부모에서 자식으로 전달되는 문자열 key-value 집합입니다. 모든 프로그램이 같은 변수를 같은 의미로 해석하지는 않습니다.

증상과 관련된 변수만 확인합니다.

```sh
printf 'PATH=%s\n' "$PATH"
printf 'HOME=%s\n' "${HOME-}"
printf 'TMPDIR=%s\n' "${TMPDIR-}"
```

전체 `env` 출력을 로그나 이슈에 붙이면 token, credential, endpoint가 노출될 수 있습니다.

### `PATH` 우선순위

`PATH`는 디렉터리를 순서대로 탐색합니다. 앞쪽 후보가 선택되므로 오래된 도구, 가짜 wrapper나 다른 architecture 실행 파일이 예상 도구를 가릴 수 있습니다.

```sh
command -v tool
type -a tool 2>/dev/null || true
```

수정 전에는 다음을 기록합니다.

```text
현재 PATH
선택된 절대 경로
후보 파일의 소유자·모드·유형
예상한 설치 위치
실제 버전 또는 checksum
```

`PATH`에 현재 디렉터리 `.`나 쓰기 가능한 공유 디렉터리를 앞쪽에 두면 신뢰하지 않은 실행 파일이 선택될 수 있습니다.

## `sudo`와 권한 상승

`sudo`는 단순히 “같은 명령을 더 강하게 실행”하는 기능이 아닙니다. 사용자, 그룹, 환경, 홈 디렉터리 해석, 생성 파일 소유권과 캐시 위치가 달라질 수 있습니다.

`sudo`를 붙이기 전에 확인합니다.

```text
어떤 시스템 자원을 변경해야 합니까?
현재 사용자가 왜 접근할 수 없어야 합니까?
명령이 어떤 파일을 생성·수정합니까?
환경 변수가 보존되거나 제거되면 결과가 달라집니까?
더 좁은 권한으로 수행할 방법이 있습니까?
```

빌드나 package command를 `sudo`로 실행해 작업 디렉터리에 root 소유 파일을 만들면 이후 일반 사용자 작업이 실패할 수 있습니다. 결과만 `chown -R`로 덮기 전에 생성 경로와 실행 주체를 고칩니다.

## 작업 디렉터리와 설정

프로그램이 `./config.json`을 사용하면 설정 위치는 실행 파일 위치가 아니라 현재 작업 디렉터리에 따라 달라집니다.

```text
interactive shell cwd: /project
supervisor cwd: /
relative path: ./config.json
```

대화형 실행만 성공한다면 다음을 비교합니다.

- `pwd`
- 사용자와 그룹
- 선택된 실행 파일
- 전달된 환경
- 설정 파일의 절대 경로
- 생성 파일의 위치와 소유권

설정 경로를 명시적으로 전달하거나 supervisor에서 작업 디렉터리를 계약으로 지정하는 것이 우연한 현재 위치에 의존하는 것보다 낫습니다.

## 안전한 권한 진단 순서

```text
1. 실패 프로세스의 실제 사용자·그룹을 확인합니다.
2. 현재 디렉터리와 대상 절대 경로를 확인합니다.
3. 각 부모 디렉터리 탐색 권한을 확인합니다.
4. 대상 유형·소유자·모드·ACL을 확인합니다.
5. mount·sandbox·container 경계를 확인합니다.
6. 필요한 최소 권한을 정의합니다.
7. 변경 하나를 적용하고 일반 사용자 경로로 다시 검증합니다.
```

`chmod -R 777`, 무조건적인 `sudo`, 보안 정책 전체 비활성화는 원인 분석이 아닙니다.

## 완료 기준

- 파일 모드가 허용해 보여도 부모 디렉터리 때문에 접근이 실패할 수 있음을 설명할 수 있습니다.
- `PATH` 문제에서 설치를 반복하기 전에 실제 선택된 파일을 확인할 수 있습니다.
- `sudo`가 사용자뿐 아니라 환경과 생성 파일 소유권을 바꿀 수 있음을 설명할 수 있습니다.
- 서비스의 상대 경로 실패를 작업 디렉터리와 연결해 진단할 수 있습니다.
- 비밀값을 노출하지 않고 필요한 환경 근거만 수집할 수 있습니다.
