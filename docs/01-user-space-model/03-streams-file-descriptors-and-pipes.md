# 스트림, 파일 디스크립터와 파이프

프로세스는 일반 파일, 파이프, 터미널과 소켓처럼 성질이 다른 자원을 정수 파일 디스크립터로 참조합니다. “모든 것이 파일”이라는 표현은 인터페이스의 공통점을 설명할 뿐, 각 자원의 메시지 경계·종료·대기 의미가 같다는 뜻은 아닙니다.

## 학습 목표

- 파일 디스크립터 표, 열린 파일 상태와 실제 자원을 구분합니다.
- stdin, stdout, stderr가 단순한 관례가 아니라 프로세스의 초기 FD 연결임을 설명합니다.
- 복제·상속된 FD가 같은 offset이나 자원 수명을 공유할 수 있음을 설명합니다.
- EOF가 “현재 데이터 없음”이 아니라 writer 참조 수명과 관련됨을 설명합니다.
- 파이프가 끝나지 않는 원인을 남아 있는 쓰기 끝에서 찾습니다.
- 삭제된 경로와 열린 FD가 독립적인 수명을 가짐을 설명합니다.

## 선행 개념

- 경로/열린 객체의 차이와 stdin·stdout·stderr 구분

## 세 단계 모델

```text
프로세스 파일 디스크립터 표
  fd 0 ─┐
  fd 1 ─┼─► 열린 파일 상태
  fd 2 ─┘      ├─ 현재 offset
  fd 3 ─────►  ├─ 접근·상태 flag
                └─ 참조된 커널 객체
                       ├─ regular file
                       ├─ terminal/PTY
                       ├─ pipe/FIFO
                       └─ socket
```

파일 디스크립터 숫자는 프로세스 로컬입니다. 다른 프로세스의 `3`은 전혀 다른 자원을 가리킬 수 있습니다. `close`된 숫자는 곧 다른 `open` 결과로 재사용될 수 있으므로 숫자 자체를 영구 식별자로 사용하면 안 됩니다.

## 표준 스트림

프로세스 시작 시 일반적으로 다음 연결이 있습니다.

| FD | 이름 | 흔한 연결 |
|---:|---|---|
| 0 | stdin | 터미널, 파일, 파이프 |
| 1 | stdout | 터미널, 파일, 파이프 |
| 2 | stderr | 터미널, 파일, 파이프 |

```sh
printf 'normal\n'
printf 'diagnostic\n' >&2
```

같은 화면에 보일 수 있지만 자동화에서는 분리해 수집할 수 있습니다.

```sh
command >stdout.log 2>stderr.log
status=$?
```

셸의 복잡한 redirection 문법은 `guide-shell-scripting`이 담당합니다. 여기서는 셸이 프로그램 시작 전에 FD 연결을 바꾼다는 사실만 사용합니다.

## 열린 파일 상태와 offset

같은 경로를 두 번 독립적으로 열면 일반적으로 별도 열린 파일 상태와 offset을 갖습니다. 반면 `dup`이나 `fork`로 복제된 FD는 같은 열린 상태를 참조해 offset과 일부 상태를 공유할 수 있습니다.

```text
fd 3 ─┐
      ├─► open file description(offset=128) ─► object
fd 7 ─┘
```

따라서 두 실행 주체가 독립적으로 읽는다고 생각했지만 실제로는 offset을 서로 움직일 수 있습니다. 관찰할 때는 경로뿐 아니라 어떤 프로세스의 어떤 FD가 같은 객체를 공유하는지 확인합니다.

Linux:

```sh
ls -l /proc/PID/fd
cat /proc/PID/fdinfo/FD
```

macOS와 Linux 공통으로 설치되어 있다면:

```sh
lsof -p PID
```

`lsof` 출력도 순간 스냅샷이므로 검사 직후 상태가 달라질 수 있습니다.

## 읽기, 대기와 EOF

스트림은 바이트 순서이며 자동 메시지 경계를 제공하지 않습니다. 한 번의 읽기가 요청한 크기를 모두 채운다고 가정하면 안 됩니다.

읽기 결과의 일반적 의미:

```text
양수   실제로 읽은 바이트 수
0      EOF
오류   대기 불가, 중단, 권한 또는 자원 문제 등
```

EOF는 “지금 당장 데이터가 없다”와 다릅니다. 파이프나 소켓에서 상대가 나중에 더 쓸 수 있으면 읽기는 기다릴 수 있습니다.

### 파이프 EOF

```text
reader
  │ read
  ▼
pipe buffer
  ▲
  ├─ writer A
  └─ writer B
```

모든 쓰기 끝 참조가 닫히고 버퍼가 비어야 reader가 EOF를 볼 수 있습니다. 부모나 형제 프로세스에 필요 없는 쓰기 FD가 하나 남아 있으면 reader는 끝나지 않을 수 있습니다.

진단 질문:

- 어떤 프로세스가 read에서 기다립니까?
- 파이프의 쓰기 끝을 가진 프로세스가 남아 있습니까?
- `fork` 후 부모와 자식이 불필요한 FD를 닫았습니까?
- 예상한 producer가 종료했습니까?

## 입력을 기다리는 프로세스

출력이 없고 CPU도 거의 쓰지 않는 프로세스는 stdin, FIFO, socket, lock, timer나 자식 종료를 기다릴 수 있습니다. “멈췄다”는 표현 대신 기다리는 자원을 찾습니다.

```sh
ps -p PID -o pid=,ppid=,state=,etime=,command=
lsof -p PID
```

Linux에서 충분한 권한이 있다면 `/proc/PID/fd`, `/proc/PID/wchan` 같은 정보를 보조 근거로 사용할 수 있습니다. 하나의 상태 문자만으로 정확한 대기 이유를 단정하지 않습니다.

## 삭제됐지만 열린 객체

경로가 제거되어도 프로세스의 FD가 객체를 참조하면 계속 읽거나 쓸 수 있습니다.

```text
unlink(path)
→ directory entry 제거
→ open FD는 객체 참조 유지
→ 마지막 참조가 닫힐 때 회수 가능
```

로그 파일을 이름으로 삭제한 뒤 프로세스가 계속 같은 FD에 쓰면 디스크 사용량은 증가하지만 경로로 찾기 어렵습니다. `lsof`의 deleted 표시나 `/proc/PID/fd` 링크를 확인합니다.

## 파일 디스크립터 상속

새 프로세스를 시작할 때 의도하지 않은 FD가 상속되면 다음 문제가 생길 수 있습니다.

- 파이프 writer가 남아 EOF가 오지 않음
- 비밀 파일이나 socket이 자식에 노출됨
- 서비스 재시작 후 오래된 listener가 유지됨
- 삭제된 파일 참조가 계속 남음

실행 전에 필요 없는 FD를 닫고, 지원되는 API에서 close-on-exec 계약을 사용합니다. 구체적인 C 구현은 `guide-c`가 담당합니다.

## 관찰 순서

```text
1. 프로세스와 PID를 정확히 식별합니다.
2. stdin/stdout/stderr 연결을 확인합니다.
3. 추가 FD와 대상 유형을 확인합니다.
4. 같은 열린 상태를 공유할 가능성을 확인합니다.
5. reader가 기다리면 writer 참조가 남았는지 확인합니다.
6. 경로가 사라졌다면 열린 FD가 객체를 유지하는지 확인합니다.
7. 종료나 재시작 전에 데이터 손실과 다른 연결 영향을 검토합니다.
```

## 완료 기준

- FD 숫자와 실제 커널 객체를 구분할 수 있습니다.

- 출력이 없는 프로세스를 무조건 종료하지 않고 대기 자원을 찾는 순서를 제시할 수 있습니다.
