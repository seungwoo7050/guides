# 동시성·잠금과 실행기

동시에 실행되는 두 작업이 같은 상태를 읽고 갱신하면 각 작업이 단독으로는 올바르더라도 전체 결과가 틀릴 수 있습니다. 동시성 문제는 “컴퓨터가 빨라서 가끔 생기는 현상”이 아니라 원자성, 가시성, 작업 수와 종료 경계를 정의하지 않은 설계 문제입니다.

## 스레드와 공유 상태

한 JVM의 여러 스레드는 힙 객체를 공유할 수 있습니다. 각 스레드는 자신의 호출 스택을 가지지만 같은 객체 필드를 읽고 쓸 수 있습니다.

다음 연산은 코드 한 줄처럼 보여도 여러 단계입니다.

```text
현재 값 읽기 → 변경 가능 여부 판단 → 새 값 쓰기
```

두 스레드가 같은 현재 값을 읽으면 둘 다 성공했다고 판단하고 한 변경을 덮어쓸 수 있습니다. 이 문제를 lost update라고 부를 수 있지만 이름보다 어떤 단계가 함께 원자적이어야 하는지가 중요합니다.

## 가시성과 원자성

`volatile`은 한 스레드가 쓴 값을 다른 스레드가 관찰하도록 돕고 재정렬에 경계를 만듭니다. 그러나 읽기·판단·쓰기 전체를 하나의 연산으로 만들지 않습니다.

```java
volatile int balance;

if (balance >= amount) {
  balance -= amount;
}
```

위 코드는 여전히 경쟁합니다. 여러 동작과 필드가 하나의 불변식을 지키면 잠금이나 상태를 한 번에 교체하는 설계가 필요합니다.

`AtomicLong`의 `addAndGet`처럼 단일 값의 원자적 갱신은 유용합니다. 그러나 “잔액이 충분할 때만 차감하고 기록도 함께 추가”처럼 여러 조건과 상태가 결합되면 원자 변수 하나로 계약이 완성되지 않습니다.

## 경쟁을 결정적으로 재현하기

동시성 테스트에서 `Thread.sleep`으로 실행 순서를 추측하지 않습니다. `CountDownLatch`, `CyclicBarrier` 또는 제어 가능한 실행기로 두 작업이 같은 지점에 도착하도록 만듭니다.

[동시 상태 갱신 실습](../../exercises/02-runtime-and-concurrency/01-concurrent-state-update/README.md)은 두 작업이 같은 값을 읽은 뒤 진행하게 하여 경쟁을 반복해서 재현합니다.

테스트는 최종 값만 확인하지 않습니다.

- 성공한 작업 수
- 승인된 값의 합계
- 최종 상태
- 기록된 변경 수
- 작업 스레드에서 발생한 예외

한 값만 보면 서로 모순되는 결과를 놓칠 수 있습니다.

## 잠금 범위

한 JVM 안의 짧은 임계 구역에는 `synchronized`나 `ReentrantLock`을 사용할 수 있습니다.

```java
lock.lock();
try {
  long next = Math.subtractExact(balance, amount);
  if (next < 0) {
    throw new IllegalStateException("잔액이 부족합니다.");
  }
  balance = next;
} finally {
  lock.unlock();
}
```

잠금 안에는 함께 지켜야 하는 상태 검증과 변경만 둡니다. 네트워크 호출, 파일 I/O와 오래 걸리는 콜백을 잠금 안에서 실행하면 관련 없는 작업까지 대기합니다.

여러 잠금을 사용한다면 획득 순서를 고정합니다. 순서가 바뀌면 서로 상대 잠금을 기다리는 deadlock이 생길 수 있습니다. 가능한 한 하나의 불변식을 하나의 소유 객체와 잠금으로 묶습니다.

JVM 잠금은 다른 프로세스나 다른 호스트의 상태를 보호하지 않습니다. 데이터베이스와 분산 시스템의 동시성은 각각 해당 전문 가이드에서 다룹니다.

## 불변 객체와 상태 격리

공유하지 않으면 잠글 필요도 줄어듭니다.

- 생성 뒤 바뀌지 않는 record와 값 객체를 전달합니다.
- 가변 컬렉션의 복사본이나 스냅샷을 반환합니다.
- 상태의 단일 소유자를 정하고 명령을 통해 변경합니다.
- 스레드마다 독립된 지역 상태를 사용합니다.

동시성 도구를 추가하기 전에 공유 상태 자체를 줄일 수 있는지 확인합니다.

## 실행기의 전체 계약

스레드 풀은 작업자 수만 정한다고 완성되지 않습니다.

- 작업자 수
- 대기열 종류와 용량
- 포화 시 거절 정책
- 작업 예외 관찰 방법
- 작업별 시간 제한과 취소
- 인터럽트 처리
- 정상 종료의 대기 시간
- 제한 시간 이후 강제 종료
- 스레드 이름과 진단 정보

무제한 큐는 요청을 거절하지 않는 대신 메모리와 지연 시간을 제한 없이 늘릴 수 있습니다. 제한된 큐와 명시적인 `RejectedExecutionException`은 과부하를 호출자에게 드러냅니다.

[실행기 수명 주기 실습](../../exercises/02-runtime-and-concurrency/02-executor-lifecycle/README.md)에서 고정된 작업자와 큐, 거절, 취소와 종료를 구현합니다.

## `Future`와 작업 예외

작업을 제출한 뒤 `Future`를 관찰하지 않으면 작업 스레드의 예외가 테스트와 호출자에게 전달되지 않을 수 있습니다.

```java
try {
  future.get();
} catch (InterruptedException error) {
  Thread.currentThread().interrupt();
  throw new IllegalStateException("작업 대기가 중단되었습니다.", error);
} catch (ExecutionException error) {
  throw new IllegalStateException("작업이 실패했습니다.", error.getCause());
}
```

여러 작업을 제출했다면 일부 결과만 읽고 끝내지 않습니다. 모든 Future의 성공·실패를 수집하고 전체 제한 시간을 적용합니다.

`CompletableFuture`는 비동기 결과 합성을 편리하게 하지만 기본 비동기 메서드가 공용 풀을 사용할 수 있습니다. 실행기, 실패 변환과 취소 전파를 명시합니다. 긴 체인 안에서 예외를 빈 결과로 바꾸지 않습니다.

## 인터럽트와 취소

인터럽트는 스레드를 강제로 죽이는 명령이 아니라 중단 요청입니다. 블로킹 메서드가 `InterruptedException`을 던지면 다음 중 하나를 수행합니다.

- 현재 계층이 정리한 뒤 예외를 상위로 전달합니다.
- 다른 예외로 번역해야 하면 `Thread.currentThread().interrupt()`로 상태를 복원합니다.

잡고 무시하면 상위 종료 절차가 중단 요청을 알 수 없습니다. 반복 작업은 주기적으로 인터럽트 상태를 확인하고 일관된 상태에서 빠져나옵니다.

## 실행기 종료

정상 종료의 기본 흐름은 다음과 같습니다.

```text
새 작업 수락 중단
→ 이미 제출된 작업 완료 대기
→ 제한 시간 초과 시 남은 작업 취소
→ 두 번째 제한 시간 안에 종료 확인
→ 인터럽트가 오면 상태 복원
```

`shutdown()`만 호출하고 기다리지 않으면 JVM이 남은 스레드 때문에 종료되지 않거나 작업이 끝났는지 알 수 없습니다. 반대로 바로 `shutdownNow()`를 호출하면 완료할 수 있었던 작업을 불필요하게 잃을 수 있습니다.

## 성능과 측정

스레드 수를 늘린다고 처리량이 항상 늘지 않습니다. CPU 작업과 블로킹 작업의 비율, 큐 대기, 잠금 경쟁과 외부 제한을 측정합니다. 먼저 정확성을 통과한 뒤 JFR로 스레드 생성, 잠금과 실행 흐름을 관찰합니다.

이 가이드의 JFR 검사는 실행 시간 자체를 합격 조건으로 사용하지 않습니다. 이벤트가 생성되고 읽을 수 있는지만 확인합니다.

## 완료 기준

- 가시성과 원자성의 차이를 설명합니다.
- `volatile`, atomic type과 잠금의 적용 범위를 구분합니다.
- latch나 barrier로 경쟁 순서를 재현합니다.
- 잠금 안에서 외부 I/O를 수행하지 않습니다.
- 제한된 실행기의 큐, 거절과 종료 정책을 설명합니다.
- 모든 작업 예외를 호출자나 테스트에 전달합니다.
- 인터럽트를 무시하지 않고 종료 뒤 스레드가 남지 않게 합니다.
