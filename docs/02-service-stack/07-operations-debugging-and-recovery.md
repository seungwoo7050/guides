# 운영, 장애 진단과 복구

앞 장까지는 시스템을 구성했습니다. 이 장에서는 새 서비스를 추가하지 않습니다. 정상 구성을 의도적으로 깨뜨리고 증상과 관찰 결과를 바탕으로 실패 계층을 좁힙니다.

오류 메시지를 보자마자 여러 설정을 한꺼번에 바꾸면 원인을 찾기 어렵습니다. 가설을 하나씩 세우고 비용이 낮은 검사부터 수행합니다.

```text
증상
→ 어느 계층까지 성공했는가?
→ 다음 경계는 무엇인가?
→ 관찰 가능한 증거는 무엇인가?
→ 한 가지 원인만 수정
→ 같은 검사로 복구 확인
```

## 1. 시스템 상태의 계층

“서비스가 정상이다”라는 단일 상태만으로는 충분하지 않습니다.

### 컨테이너 상태

- created
- running
- exited
- restarting
- paused

PID 1의 실행 상태를 나타냅니다.

### 상태 검사 결과

- 검사 시작 중
- 정상
- 비정상

구성된 `healthcheck`의 결과입니다. 검사 명령 자체가 잘못되면 실제 서비스 상태와 다를 수 있습니다.

### 프로세스 상태

주 프로세스와 워커가 존재하는가? 좀비 프로세스가 있거나 충돌을 반복하는가?

### 네트워크 상태

- 이름이 해석되는가?
- 포트에서 연결을 기다리고 있는가?
- TCP 연결이 되는가?
- 방화벽이나 네트워크가 통신을 허용하는가?

### 프로토콜 상태

- TLS 핸드셰이크가 되는가?
- HTTP 요청에 유효한 응답이 오는가?
- FastCGI 요청에 응답하는가?
- 데이터베이스 핸드셰이크와 쿼리가 되는가?

### 애플리케이션 상태

- 스키마가 현재 버전인가?
- 의존 서비스에 접근 가능한가?
- 핵심 기능이 동작하는가?

### 데이터 상태

- 볼륨이 올바르게 마운트됐는가?
- 필요한 파일과 테이블이 있는가?
- 백업에서 복원할 수 있는가?

상위 상태는 하위 상태가 충족되어야 의미가 있습니다. 애플리케이션 기능을 검사하기 전에 컨테이너와 프로세스가 살아 있는지 먼저 확인합니다.

## 2. 생존, 준비 상태와 기본 동작 검사

용어는 플랫폼마다 조금씩 다르게 사용되지만 검사 목적은 구분합니다.

### 생존 검사

프로세스가 교착 상태나 회복 불가능한 상태인지 판정합니다. 실패하면 재시작이 도움이 될 수 있습니다.

외부 의존성을 너무 깊게 포함하지 않습니다. 데이터베이스의 일시적인 장애 때문에 정상 애플리케이션 프로세스를 계속 재시작하면 장애를 증폭할 수 있습니다.

### 준비 상태 검사

현재 요청을 받을 준비가 됐는지 판정합니다. 준비되지 않은 인스턴스에는 트래픽을 보내지 않는 데 사용합니다.

데이터베이스 스키마를 변경하는 중이거나 워커 풀이 아직 준비되지 않았다면 요청을 받을 수 없습니다.

### 기본 동작 검사

배포 또는 시작 뒤 외부 관점에서 가장 중요한 경로가 동작하는지 확인합니다.

```text
호스트 → HTTPS 게이트웨이 → FastCGI 애플리케이션 → 데이터베이스 쿼리
```

기본 동작 검사가 실패했다고 모든 컨테이너를 재시작하지 않습니다. 어느 내부 상태 검사까지 성공했는지 비교합니다.

Docker Compose의 단일 `healthcheck`는 생존 여부와 요청 준비 상태를 별도 필드로 구분하지 않습니다. 어떤 의미로 사용할지 문서화합니다.

## 3. 서비스 프로토콜에 맞는 상태 검사

### Nginx

```sh
curl -kfsS https://127.0.0.1/healthz >/dev/null
```

Nginx가 TLS와 HTTP 요청에 응답하는지 확인합니다. `/healthz`는 가벼운 `return 200` 경로로 둡니다.

### PHP-FPM

```sh
REQUEST_METHOD=GET \
SCRIPT_NAME=/ping \
SCRIPT_FILENAME=/ping \
cgi-fcgi -bind -connect 127.0.0.1:9000 | grep -q pong
```

FPM은 HTTP 서버가 아니므로 `curl http://127.0.0.1:9000`을 사용하지 않습니다.

### MariaDB

```sh
mariadb-admin \
  --protocol=socket \
  --socket=/run/mysqld/mysqld.sock \
  -uroot -p"..." \
  ping --silent
```

데이터베이스 프로토콜 응답을 확인합니다. 단순 `pgrep mariadbd`보다 더 깊은 수준을 검사합니다.

### 전체 애플리케이션

```sh
curl -kfsS https://127.0.0.1:20443/api/notes >/dev/null
```

게이트웨이, 애플리케이션, 데이터베이스의 읽기 경로 전체를 확인합니다. 이 검사는 내부 상태 검사보다 실패 원인이 많고 비용도 크므로 별도의 기본 동작 검사로 사용합니다.

## 4. 좋은 상태 검사의 조건

- 빠르게 끝납니다.
- 명확한 제한 시간이 있습니다.
- 읽기 전용입니다.
- 반복해도 상태를 바꾸지 않습니다.
- 로그를 과도하게 만들지 않습니다.
- 해당 서비스가 실제로 사용하는 프로토콜을 사용합니다.
- 무엇을 확인하고 무엇을 확인하지 않는지 문서화합니다.

나쁜 예:

```text
매 5초마다 대형 통계 쿼리 실행
외부 결제 API까지 호출
실패하면 데이터를 자동 수정
응답 내용은 보지 않고 프로세스 이름만 확인
```

## 5. 잘못된 상태 검사

컨테이너가 `unhealthy`라고 해서 서비스가 반드시 고장 난 것은 아닙니다.

- 검사 도구가 이미지에 없음
- 잘못된 경로나 포트
- 셸이 없는 이미지에서 `CMD-SHELL` 사용
- 초기화 시간보다 짧은 `start_period`
- 비밀값 경로 오타
- 정상 응답 본문과 `grep` 패턴 불일치
- 실행 사용자 권한 부족

다음 두 결과를 비교합니다.

```sh
docker compose ps
docker inspect --format '{{json .State.Health}}' container-name
```

상태 검사 기록에는 각 시도의 출력과 종료 코드가 있습니다. 검사 명령을 컨테이너 안에서 직접 실행해 재현합니다.

## 6. `depends_on`의 실제 범위

```yaml
depends_on:
  db:
    condition: service_healthy
```

Compose는 시작할 때 데이터베이스 상태 검사가 통과할 때까지 애플리케이션 시작을 지연할 수 있습니다. 하지만 다음 상황까지 해결하지는 않습니다.

1. 애플리케이션 실행 뒤 데이터베이스가 재시작됨
2. 기존 DB 연결이 끊김
3. DNS가 새 컨테이너 주소를 반환함
4. 애플리케이션 연결 풀이 실패한 연결을 정리해야 함

애플리케이션은 실행 중 연결 오류를 처리하고 제한적으로 재시도해야 합니다.

`depends_on`이 없어도 애플리케이션이 결국 시작할 수 있도록 자체 재시도를 두면 구성 간 결합을 줄일 수 있습니다. 다만 설정 오류를 오랫동안 재시도하지 않도록 인증 실패와 일시적인 연결 실패는 구분해야 합니다.

## 7. 재시도 설계

### 고정 간격

```sh
for _ in $(seq 1 30); do
    check && exit 0
    sleep 2
done
exit 1
```

단순하고 예측 가능합니다. 짧은 로컬 초기화에 적합합니다.

### 지수 간격

```text
1s → 2s → 4s → 8s → 최대 30s
```

다수 인스턴스가 동시에 장애 난 서비스에 요청하는 부하를 줄일 수 있습니다. 무작위 지연을 추가하면 동기화된 재시도를 분산할 수 있습니다.

### 반드시 정할 것

- 개별 시도 제한 시간
- 최대 시도 횟수 또는 전체 시간
- 재시도 가능한 오류
- 최종 실패 메시지
- 종료 코드

네트워크 호출에 제한 시간이 없으면 반복 횟수보다 한 번의 호출이 더 오래 멈출 수 있습니다.

## 8. 표준 진단 순서

다음 순서를 기본으로 사용합니다.

```text
1. Compose가 기대한 서비스를 만들었는가?
2. 컨테이너의 PID 1이 실행 중인가?
3. 로그의 최초 오류는 무엇인가?
4. 예상 주소와 포트에서 연결을 기다리는가?
5. 서비스 이름이 올바른 IP로 해석되는가?
6. TCP 연결이 되는가?
7. 해당 프로토콜 요청에 응답하는가?
8. 설정과 비밀값의 출처가 맞는가?
9. 파일 경로와 권한이 맞는가?
10. 볼륨에 기대한 상태가 있는가?
11. 의존 서비스의 실제 기능이 준비됐는가?
```

상위 단계에서 실패했다면 그보다 깊은 검사는 의미가 없거나 오해를 만들 수 있습니다.

## 9. Compose 상태 확인

```sh
docker compose ps -a
```

확인할 항목:

- 서비스와 컨테이너 이름
- 상태
- 종료 코드
- 상태 검사 결과
- 공개한 포트

컨테이너가 없다면 프로필, Compose 파일, 프로젝트 이름, `docker compose config`를 확인합니다.

```sh
docker compose config --services
docker compose config
```

환경변수 보간 결과가 예상과 같은지 확인합니다. 출력에 비밀값이 포함될 수 있으므로 공유 전에 검토합니다.

## 10. 로그 읽기

```sh
docker compose logs --timestamps
docker compose logs --tail=100 app
docker compose logs -f gateway app db
```

### 최초 오류 찾기

재시작을 반복할 때는 같은 최종 오류가 수백 번 나타날 수 있습니다. 그보다 앞의 최초 설정 오류가 실제 원인일 수 있습니다.

### 1차 오류와 2차 오류 구분

예:

```text
1차: 애플리케이션이 데이터베이스 인증에 실패
2차: 애플리케이션이 종료
3차: 게이트웨이가 애플리케이션 연결 실패로 502 반환
4차: 기본 동작 검사 실패
```

게이트웨이의 502 응답만 보고 Nginx 설정을 바꾸면 원인을 놓칠 수 있습니다.

### 로그의 비밀값 보호

- 전체 환경변수 덤프 금지
- 비밀번호가 포함된 DSN 출력 금지
- 비밀값 처리 구간에서 셸의 `set -x` 사용 금지
- HTTP `Authorization` 헤더 출력 제한

## 11. 프로세스 확인

```sh
docker compose top
docker compose exec app ps -o pid,ppid,user,stat,command -ef
```

확인 질문:

- PID 1은 기대한 서버인가, 셸인가?
- 워커가 생성됐는가?
- 프로세스가 계속 새 PID로 바뀌는가?
- 실행 사용자는 누구인가?
- 종료됐지만 회수되지 않은 프로세스가 누적되는가?

컨테이너가 종료됐다면 `docker exec`을 사용할 수 없습니다. 로그와 검사 결과를 사용하거나 시작 명령을 임시로 덮어써 셸을 실행합니다.

```sh
docker compose run --rm --entrypoint sh app
```

이 디버깅 컨테이너는 일반 실행과 환경·볼륨 구성이 다를 수 있으므로 차이를 확인합니다.

## 12. 수신 대기와 연결 확인

컨테이너 안에서:

```sh
ss -ltnp
ss -lxnp
```

도구가 없다면 언어 런타임으로 TCP 연결을 시험할 수 있습니다.

```sh
php -r '$s=@fsockopen("db",3306,$e,$m,2); exit($s?0:1);'
```

게이트웨이에서 애플리케이션 이름 확인:

```sh
docker compose exec gateway getent hosts app
```

TCP 연결 확인:

```sh
docker compose exec gateway sh -c 'nc -z app 9000'
```

이미지에 `nc`가 없다면 진단 목적으로 별도 도구 컨테이너를 같은 네트워크에 실행할 수 있습니다. 운영 이미지를 디버깅 도구 때문에 비대하게 만들 필요는 없습니다.

```sh
docker run --rm -it --network PROJECT_app-net nicolaka/netshoot
```

제3자 이미지를 사용할 때는 출처와 태그를 검토합니다. 가이드의 자동 검증은 추가 진단 이미지에 의존하지 않습니다.

## 13. DNS 확인

```sh
getent hosts db
```

실패하면 다음을 확인합니다.

- Compose 서비스 이름 오타
- 공통 네트워크 연결 여부
- 다른 Compose 프로젝트의 서비스 이름 사용
- `network_mode`와 사용자 정의 네트워크 충돌
- 컨테이너가 이미 종료됐는가

DNS 성공은 포트 연결 성공을 의미하지 않습니다.

## 14. HTTP와 TLS 확인

```sh
curl -vk https://127.0.0.1:20443/healthz
```

`-v` 출력에서 단계별로 확인합니다.

- 연결한 IP와 포트
- TLS 프로토콜과 인증서
- 보낸 요청 줄과 `Host` 헤더
- 받은 상태와 헤더

인증서 검증까지 확인하려면 `-k`를 제거하고 신뢰할 CA 파일을 지정합니다.

```sh
curl --cacert development.crt https://localhost:20443/healthz
```

SAN에 `localhost`가 있고 해당 인증서를 신뢰하도록 지정해야 합니다.

TLS 상세:

```sh
openssl s_client \
  -connect 127.0.0.1:20443 \
  -servername localhost \
  -showcerts </dev/null
```

## 15. FastCGI 확인

게이트웨이가 502를 반환하면 애플리케이션의 FPM을 직접 검사합니다.

```sh
docker compose exec app sh -c '
  REQUEST_METHOD=GET \
  SCRIPT_NAME=/ping \
  SCRIPT_FILENAME=/ping \
  cgi-fcgi -bind -connect 127.0.0.1:9000
'
```

결과에 따라 다음처럼 범위를 좁힙니다.

- FastCGI 연결 자체가 실패: FPM 프로세스, 수신 주소, 워커 풀 설정 문제
- FPM ping은 성공하지만 게이트웨이는 502: 게이트웨이 DNS·포트·네트워크·FastCGI 설정 문제
- FPM ping과 게이트웨이 연결은 성공하지만 PHP 파일 실행 실패: `SCRIPT_FILENAME`, 파일 권한, PHP 코드 문제

## 16. 데이터베이스 확인

### 데이터베이스 컨테이너의 로컬 소켓

```sh
docker compose exec db mariadb-admin \
  --protocol=socket \
  --socket=/run/mysqld/mysqld.sock \
  ping --silent
```

### 애플리케이션에서 TCP

```sh
docker compose exec app php -r '
$pdo = new PDO(
    "mysql:host=db;port=3306;dbname=appdb;charset=utf8mb4",
    "appuser",
    getenv("DB_PASSWORD")
);
echo $pdo->query("SELECT 1")->fetchColumn(), PHP_EOL;
'
```

실제 애플리케이션은 비밀번호를 파일에서 읽어 환경변수로 내보낼 수 있습니다. 디버깅 명령에서 비밀번호를 셸 기록에 직접 쓰지 않습니다.

데이터베이스 오류는 다음처럼 구분합니다.

- `getaddrinfo failed`: 이름 해석 문제
- `Connection refused`: 서버 또는 포트 문제
- 제한 시간 초과: 네트워크·과부하 가능성
- `Access denied`: 사용자, 비밀번호, 호스트 권한 문제
- `Unknown database`: 초기화 또는 데이터베이스 이름 문제
- 테이블을 찾지 못함: 스키마 마이그레이션 문제

## 17. 파일과 권한 확인

```sh
id
ls -ld /var /var/www /var/www/html
ls -l /var/www/html/index.php
stat /var/www/html/index.php
```

경로의 모든 상위 디렉터리에 접근 권한이 필요합니다. Linux에서는 `namei -l`이 유용합니다.

```sh
namei -l /var/www/html/index.php
```

확인할 항목:

- 실제 실행 사용자 UID/GID
- 파일 소유자와 그룹
- 읽기·쓰기·실행 권한 비트
- 호스트 경로 마운트가 이미지 파일을 가렸는가
- SELinux 레이블이 필요한 호스트인가
- 읽기 전용 마운트에 쓰려고 하는가

문제 해결을 위해 무조건 `chmod -R 777`을 사용하지 않습니다. 원인을 숨기고 불필요한 쓰기 권한을 줍니다.

## 18. 볼륨 확인

```sh
docker volume ls
docker volume inspect PROJECT_db-data
docker inspect container-name --format '{{json .Mounts}}'
```

확인 질문:

- 기대한 볼륨 이름인가?
- 다른 Compose 프로젝트 이름으로 새 볼륨을 만든 것은 아닌가?
- 마운트 대상이 정확한가?
- 호스트 경로 마운트의 원본 경로가 존재하는가?
- 빈 호스트 디렉터리가 이미지 내용을 가렸는가?
- `down -v`를 실행했는가?

데이터가 “사라진” 경우 새 빈 볼륨을 마운트했을 가능성이 있습니다. 기존 볼륨부터 삭제하지 말고 목록과 마운트 상태를 먼저 확인합니다.

## 19. PID 1과 정상 종료

```sh
docker compose kill -s TERM app
docker compose logs app
```

정상적인 흐름:

1. Docker가 PID 1에 SIGTERM 전송
2. 서버가 새 작업 수락 중단
3. 진행 중 요청 정리
4. 로그와 버퍼 반영
5. 종료 코드 반환

시작 셸이 PID 1이고 실제 서버를 백그라운드로 실행하면 시그널 전달이 끊길 수 있습니다.

```sh
exec "$@"
```

데이터베이스는 강제 종료 뒤 충돌 복구를 수행할 수 있지만 이를 정상 운영 방식으로 삼지 않습니다.

## 20. 재시작 정책과 반복 충돌

`restart: unless-stopped`는 일시적인 프로세스 충돌 복구에 도움이 될 수 있습니다. 하지만 잘못된 설정에서는 다음 흐름이 반복됩니다.

```text
시작
→ 설정 오류
→ 즉시 종료
→ 자동 재시작
→ 같은 오류 반복
```

확인:

```sh
docker inspect container-name --format '{{.RestartCount}}'
docker compose logs --tail=200 service
```

진단 중에는 재시작 정책을 임시로 끄거나 `docker compose stop`으로 반복을 멈추고 최초 오류를 확인합니다.

## 21. 보안 기본선

이 가이드는 전체 보안 설계를 다루지 않지만 다음 기본선은 유지합니다.

### 공개 포트 최소화

- 게이트웨이만 호스트에 게시
- 애플리케이션 FastCGI와 데이터베이스는 내부 네트워크에서만 사용
- 개발 포트는 가능하면 `127.0.0.1`에 바인드

### 비특권 실행

- Nginx 워커, PHP-FPM 워커, MariaDB는 전용 사용자 사용
- 관리자 초기화가 필요하면 완료 뒤 권한 강등
- 불필요한 Linux capability 제거 검토

### 비밀값 분리

- Dockerfile, Git, Compose의 평문 값에 직접 넣지 않음
- 파일 권한 제한
- 로그에 출력하지 않음
- 회전 절차 마련

### 읽기 전용

- 게이트웨이의 애플리케이션 코드 마운트는 읽기 전용
- 불변 코드와 쓰기 데이터 경로 분리

### 이미지 관리

- 불필요한 패키지 제거
- 베이스 이미지 정기 재빌드
- 가변 외부 다운로드에는 버전과 체크섬 사용
- 취약점 검사 결과만 믿지 않고 실제 노출 범위와 수정 사항을 검토

### TLS 키

- 개인키 읽기 권한 최소화
- 이미지 레이어와 공개 저장소에 넣지 않음
- 공인 환경에서 자동 갱신과 인증서 체인 검증

## 22. 재현성 관리

### 태그와 다이제스트

```dockerfile
FROM php:8.3-fpm-bookworm
```

주·부 버전과 배포판을 고정하지만 태그가 보안 수정판으로 이동할 수 있습니다. 바이트 단위로 고정하려면 다이제스트를 사용합니다.

```dockerfile
FROM php:8.3-fpm-bookworm@sha256:...
```

다이제스트 고정은 자동으로 보안 수정판을 받지 않으므로 별도의 갱신 절차가 필요합니다.

### 외부 다운로드

```sh
curl -fsSLo tool.phar URL
printf '%s  %s\n' "$EXPECTED_SHA256" tool.phar | sha256sum -c -
```

URL이 `latest` 파일을 가리키면 같은 빌드가 다른 결과를 만들 수 있습니다.

### 패키지 버전

배포판 저장소의 정확한 패키지 버전을 고정하면 재현성은 높아지지만 해당 버전이 저장소에서 제거되면 빌드가 실패할 수 있습니다. 시점별 저장소나 잠금 파일 전략이 필요합니다.

### 정기 재빌드

이미지가 불변이라는 것은 영원히 안전하다는 뜻이 아닙니다. 베이스 이미지와 의존성의 수정 사항을 포함하도록 정기적으로 재빌드하고 기본 동작을 검사합니다.

## 23. 백업과 복구 훈련

백업 정책에는 최소한 다음 항목이 있어야 합니다.

- 무엇을 백업하는가?
- 얼마나 자주 하는가?
- 어디에 보관하는가?
- 같은 장애 도메인 밖에 사본이 있는가?
- 암호화와 접근 권한은?
- 보존 기간은?
- 복원 순서와 예상 시간은?

### 복구 연습

1. 별도 프로젝트 이름으로 빈 데이터베이스 실행
2. 백업 복원
3. 스키마 버전 확인
4. 행 수와 핵심 쿼리 확인
5. 애플리케이션을 연결해 기본 동작 검사
6. 걸린 시간과 수동 단계를 기록

운영 장애가 발생한 뒤 처음으로 복원 명령을 작성하지 않습니다.

## 24. 증상별 우선 계층

| 증상 | 먼저 확인 | 다음 확인 |
|---|---|---|
| `Could not resolve host` | 서비스 이름, 네트워크 | 컨테이너 실행 상태 |
| `Connection refused` | 프로세스, 수신 포트 | 포트 설정, 네트워크 |
| 제한 시간 초과 | 네트워크 경로, 부하 | 방화벽, 쿼리, 워커 고갈 |
| TLS 인증서 오류 | SAN, 신뢰 CA, 유효기간 | 서버 이름, 인증서 체인 |
| HTTP 404 | `location`, `root`, `try_files` | 파일 존재, 애플리케이션 경로 |
| HTTP 403 | 파일·디렉터리 권한 | 실행 사용자, 마운트 방식 |
| HTTP 500 | 애플리케이션/FPM 로그 | 데이터베이스, 코드, 환경변수 |
| HTTP 502 | 애플리케이션/FPM 실행, FastCGI 포트 | DNS, `SCRIPT_FILENAME` |
| 데이터베이스 접근 거부 | 사용자·비밀번호·호스트 | 비밀값 출처, 초기 SQL |
| 알 수 없는 데이터베이스/테이블 | 초기화/스키마 변경 | `DB_NAME`, 볼륨 |
| 데이터 초기화 | 볼륨 이름과 마운트 | `down -v`, 프로젝트 이름 |
| 재시작 반복 | 최초 종료 로그 | 재시작 정책, 설정 |
| 비정상인데 요청 성공 | 상태 검사 명령 | 도구, `start_period`, 권한 |

이 표는 원인을 확정하는 표가 아니라 검사 시작점을 정하기 위한 표입니다.

## 25. 장애 실습

저장소 루트에서 분석 기록용 workspace를 먼저 만듭니다. 각 시나리오는 6장의 완성 스택 복사본에 한 가지 결함만 주입합니다. 학습자는 기준 소스나 시나리오 자체를 수정하지 않고 관찰 결과를 `workspace/evidence.md`에 기록합니다.

```sh
python3 scripts/new-workspace.py exercises/07-troubleshooting
cd exercises/07-troubleshooting
./verify.sh template
```

각 시나리오의 override 파일은 변수 하나만 바꿉니다. 아래 여섯 시나리오를 관찰한 뒤 최초 실패 구성요소, 읽기 전용 명령과 민감 정보를 제거한 핵심 출력, 2차 증상, 수정·복구 결정, 구성요소·외부 사용자 경로·데이터의 재검증을 해당 절에 작성합니다.

### 시나리오 1: 잘못된 데이터베이스 호스트

```sh
./run-scenario.sh wrong-db-host
```

예상 결과:

- 데이터베이스는 정상 상태입니다.
- 애플리케이션 초기화는 이름 해석 또는 연결 단계에서 실패합니다.
- 게이트웨이는 애플리케이션이 준비되기를 기다리므로 정상 사용자 경로를 제공하지 못합니다.

진단 목표: 게이트웨이 설정을 바꾸지 않고 애플리케이션 로그와 서비스 DNS에서 원인을 찾습니다.

### 시나리오 2: 잘못된 데이터베이스 비밀번호

```sh
./run-scenario.sh wrong-db-password
```

예상 결과:

- `db` 이름과 3306 포트까지는 도달합니다.
- 인증 단계에서 실패합니다.
- 연결 실패와 자격 증명 실패를 로그로 구분합니다.

### 시나리오 3: 존재하지 않는 비밀값 경로

```sh
./run-scenario.sh missing-secret
```

예상 결과:

- 애플리케이션은 데이터베이스 연결을 시도하기 전에 종료합니다.
- 로그에는 비밀값이 아니라 읽을 수 없는 경로가 표시됩니다.
- 설정 누락을 네트워크 장애로 오인하지 않습니다.

### 시나리오 4: 잘못된 FastCGI 포트

```sh
./run-scenario.sh wrong-fcgi-port
```

예상 결과:

- 게이트웨이 자체의 `/healthz`는 성공하고 컨테이너도 정상 상태일 수 있습니다.
- 애플리케이션의 FPM 연결 확인은 성공합니다.
- 애플리케이션을 거치는 `/health` 요청만 502를 반환합니다.

진단 목표: 얕은 상태 검사가 전체 사용자 경로를 보장하지 않는다는 사실을 확인합니다.

### 시나리오 5: 잘못된 상태 검사

```sh
./run-scenario.sh broken-healthcheck
```

예상 결과:

- 외부 `/health` 요청은 200을 반환합니다.
- Docker 상태 검사 결과만 비정상입니다.
- 상태 검사 기록에서 실제 검사 명령과 종료 코드를 확인합니다.

### 시나리오 6: 볼륨 삭제에 의한 데이터 손실

```sh
./run-scenario.sh data-loss
```

예상 결과:

- 일반 애플리케이션·게이트웨이 재생성에서는 메모가 유지됩니다.
- `down -v`로 데이터베이스 볼륨을 삭제하면 사용자가 추가한 메모가 사라집니다.
- 새 데이터베이스가 초기화되면서 초기 데이터만 다시 생성됩니다.

이 시나리오는 백업 복원을 대신하지 않습니다. 5장의 백업 파일을 별도 위치에 보존하고 빈 DB에 복원하는 절차는 별도로 반복해야 합니다.

여섯 시나리오와 분석 기록을 각각 검사합니다.

```sh
./verify.sh scenarios
./verify.sh workspace
```

자동 검사는 여섯 절의 필수 구조와 관찰 명령의 안전한 형태만 판정합니다. 출력이 실제 관찰과 일치하는지, 최초 실패 경계와 복구 판단이 타당한지는 [실습 README](../exercises/07-troubleshooting/README.md)의 수동 검토 기준으로 확인합니다. 외부 백업이 없으면 `data-loss`에서 삭제된 사용자의 note는 복구할 수 없으며 빈 볼륨을 재초기화하는 것은 복구 증거가 아닙니다. 이 분석을 끝낸 뒤 [운영 계약](08-production-contract-and-threat-model.md)으로 이동합니다.

## 27. 전체 스택 확인

- 깨끗한 환경에서 이미지가 빌드됩니다.
- 외부에는 게이트웨이 포트만 게시됩니다.
- 서비스는 사용자 정의 네트워크에서 이름으로 통신합니다.
- 데이터베이스 데이터는 컨테이너 재생성 뒤에도 남습니다.
- 빈 볼륨에서만 데이터베이스 초기화가 실행됩니다.
- 애플리케이션 초기화는 반복 실행해도 초기 데이터를 중복하지 않습니다.
- 비밀값은 이미지와 Compose 평문 설정에 포함되지 않습니다.
- 각 서비스의 실제 프로토콜로 상태를 검사합니다.
- 주 프로세스가 포그라운드의 PID 1이며 SIGTERM으로 종료됩니다.
- 404, 403, 500, 502, 데이터베이스 인증 실패를 구분할 수 있습니다.
- 백업을 빈 데이터베이스에 복원하고 애플리케이션의 기본 동작까지 검사합니다.

## 28. 진단을 방해하는 습관

### “재시작하면 대부분 해결됩니다”

일시적인 교착 상태나 일부 일회성 오류에는 도움이 될 수 있지만 설정, 권한, 데이터 손상은 그대로입니다. 재시작 전에 증거를 수집합니다.

### “상태 검사가 실패하면 컨테이너를 종료하면 됩니다”

상태 검사 자체가 틀릴 수 있고 생존 여부와 요청 준비 상태가 섞일 수 있습니다. 검사 명령을 직접 재현합니다.

### “로그 마지막 줄이 원인입니다”

마지막 줄은 2차 실패일 수 있습니다. 시간 순으로 최초 오류를 찾습니다.

### “디버깅을 위해 777과 관리자 권한을 쓰면 됩니다”

잠시 증상을 바꿀 수 있지만 원인을 숨기고 권한 경계를 없앱니다. 필요한 주체와 경로를 식별합니다.

### “백업 파일이 만들어졌으니 끝입니다”

복원과 검증을 통과해야 합니다.

## 29. 장애 대응 원칙

- 시스템 상태를 컨테이너, 프로세스, 네트워크, 프로토콜, 애플리케이션, 데이터 계층으로 나눕니다.
- 생존, 준비 상태, 기본 동작 검사의 목적을 구분합니다.
- 상태 검사는 실제 서비스 프로토콜을 사용하고 부작용이 없어야 합니다.
- `depends_on`은 시작 순서를 제어하며 실행 중 재연결을 대신하지 않습니다.
- 진단은 비용이 낮은 하위 검사에서 상위 기능으로 이동합니다.
- 최초 오류와 연쇄 오류를 분리합니다.
- 포트, DNS, 파일 권한, 볼륨 마운트를 실제 명령으로 확인합니다.
- 재시작 정책은 설정 오류를 고치지 않습니다.
- 보안 기본선과 재현성은 별도 운영 절차를 요구합니다.
- 백업은 복원 훈련으로 검증합니다.
