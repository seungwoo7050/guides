# 파이프라인의 위험 요소와 분기

파이프라인은 한 명령어를 짧은 단계로 나누고 서로 다른 명령어의 단계를 겹쳐 처리량을 높입니다. 프로세서에서는 레지스터 의존성, 메모리 접근과 잘못된 분기 예측처럼 단계를 멈추거나 이미 진행한 결과를 버려야 하는 상황도 다뤄야 합니다.

## 학습 목표

- 구조·데이터·제어 위험을 구분하고 stall, forwarding, flush로 대응합니다.
- 주파수 변화와 CPI 변화를 함께 사용해 파이프라인 성능을 판단합니다.

## 선행 개념

데이터패스의 IF·ID·EX·MEM·WB 경로와 register read/write 시점을 알아야 합니다.

## 5단계 순차 실행 모델

교육용 RISC 파이프라인은 흔히 다음 다섯 단계를 사용합니다.

| 단계 | 역할 |
|---|---|
| IF | PC가 가리키는 명령어를 가져옵니다. |
| ID | 명령어를 해독하고 소스 레지스터를 읽습니다. |
| EX | ALU 연산, 주소 또는 분기 조건을 계산합니다. |
| MEM | 데이터 메모리를 읽거나 씁니다. |
| WB | 결과를 목적지 레지스터에 반영합니다. |

명령어 하나의 지연 시간은 여전히 여러 사이클입니다. 파이프라인이 채워진 뒤에는 이상적인 스칼라 파이프라인이 사이클마다 명령어 하나를 완료하므로 CPI가 1에 가까워집니다.

```text
사이클: 1  2  3  4  5  6  7
I0:    IF ID EX MEM WB
I1:       IF ID EX MEM WB
I2:          IF ID EX MEM WB
```

명령어가 `n`개일 때 이상적인 사이클 수는 대략 `파이프라인 깊이 + n - 1`입니다. 실제로는 위험 요소를 처리하는 정지와 비우기 비용이 더해집니다.

## 단계 사이에는 파이프라인 레지스터가 필요합니다

각 단계의 출력은 다음 클록 에지에서 파이프라인 레지스터에 저장됩니다.

```text
IF/ID → ID/EX → EX/MEM → MEM/WB
```

명령 비트뿐 아니라 소스 값, 목적지 레지스터 번호, 제어 신호와 예외 정보도 함께 이동해야 합니다. 데이터만 넘기고 `reg_write` 대상 번호를 잃으면 뒤 단계가 어느 레지스터를 갱신해야 하는지 알 수 없습니다.

파이프라인 레지스터 자체도 clock-to-Q 지연, 설정 시간과 전력을 소비합니다. 단계를 계속 잘게 나눈다고 클록 주파수가 끝없이 높아지는 것은 아닙니다.

## 구조적 위험은 같은 자원을 동시에 요구할 때 생깁니다

명령어 가져오기와 데이터 적재가 단일 포트 메모리를 같은 사이클에 요구하면 충돌합니다.

```text
I0: MEM에서 데이터 읽기
I3: IF에서 명령어 읽기
```

해결 방법은 다음 가운데 하나입니다.

- 한 명령어를 정지시킵니다.
- 명령어 메모리와 데이터 메모리 또는 캐시를 분리합니다.
- 다중 포트 자원을 사용합니다.
- 단계 배치를 바꿉니다.

자원을 늘리면 면적, 전력과 타이밍 비용이 생깁니다. 위험 요소를 없애는 데도 대가가 따릅니다.

## 데이터 위험은 명령어 사이의 값 의존성입니다

다음 명령어열을 보겠습니다.

```text
add r1, r2, r3
sub r4, r1, r5
```

두 번째 명령어는 첫 번째 명령어가 만든 `r1` 값이 필요합니다. 프로그램 순서를 유지하는 5단계 파이프라인에서 대표적으로 다루는 의존성은 RAW입니다.

### RAW: 쓰기 이후 읽기

뒤의 명령어가 앞 명령어의 결과를 읽습니다. 실제 데이터 의존성이므로 값이 준비되기 전에는 실행할 수 없습니다.

### WAR: 읽기 이후 쓰기

뒤의 명령어가 앞 명령어가 읽을 레지스터를 먼저 덮어쓸 위험입니다.

### WAW: 쓰기 이후 쓰기

두 명령어가 같은 목적지에 쓰는 순서가 뒤바뀔 위험입니다.

단순한 순차 발행·순차 완료 파이프라인에서는 WAR와 WAW가 나타나지 않을 수 있습니다. 비순차 실행에서는 레지스터 이름 바꾸기로 거짓 의존성을 제거합니다.

## 전달 경로는 결과를 레지스터에 쓰기 전에 우회 전달합니다

`add` 결과는 EX 단계 끝에 계산되지만 레지스터 파일에는 WB 단계에서 기록됩니다. 다음 명령어의 EX 입력으로 EX/MEM 또는 MEM/WB 값을 바로 선택하면 기다리는 사이클을 줄일 수 있습니다.

```text
add의 EX 결과
   └──────────────→ 다음 명령어의 EX 피연산자
```

전달 장치는 다음 항목을 비교합니다.

- 앞 명령어의 목적지 레지스터
- 현재 EX 명령의 소스 레지스터
- 앞 명령어의 레지스터 쓰기 활성화 여부
- 목적지가 0번 레지스터인지 여부

가장 가까운 생산자의 최신 값을 선택해야 합니다. 앞선 두 명령어가 같은 레지스터를 썼다면 더 오래된 값을 전달해서는 안 됩니다.

## 적재 직후 사용 위험은 전달 경로만으로 해결되지 않습니다

```text
lw  r1, 0(r2)
add r3, r1, r4
```

적재한 데이터는 MEM 단계가 끝나야 준비됩니다. 바로 다음 명령어는 같은 사이클의 EX 시작 시점에 피연산자가 필요하므로 한 사이클의 빈 단계가 필요합니다.

```text
사이클: 1  2  3  4  5  6  7  8
lw:     IF ID EX MEM WB
add:       IF ID ST EX MEM WB
```

프로세서와 파이프라인 분할 방식에 따라 세부 타이밍은 달라질 수 있습니다. 다만 “ALU 전달 경로가 있으므로 모든 RAW 정지가 사라집니다”라는 결론은 틀립니다.

```sh
python3 exercises/processor-model/reference/processor-model.py pipeline \
  exercises/processor-model/fixtures/traces/pipeline-load-use.trace \
  --forwarding full
```

`data_stalls=1`을 확인한 뒤 `--forwarding none`으로 실행한 결과와 사이클 수를 비교하세요.

## 정지는 앞단 상태를 유지하고 빈 단계를 삽입합니다

적재 직후 사용 위험을 처리하는 제어 방식은 보통 다음과 같습니다.

```text
PC 쓰기 비활성화
IF/ID 쓰기 비활성화
ID/EX 제어 신호를 no-op으로 변경
```

즉, 값을 소비하는 명령어는 ID에 머물고 앞의 적재 명령어는 진행하며 EX에는 빈 단계가 들어갑니다. “파이프라인 전체를 멈춥니다”라고만 쓰지 말고, 어떤 레지스터를 유지하고 어느 단계를 비우는지 밝혀야 구현이 정확해집니다.

## 제어 위험은 다음 PC를 늦게 아는 문제입니다

분기 결과가 EX에서 결정된다면 그동안 IF와 ID에는 순차 경로의 명령어가 들어와 있습니다. 분기가 실제로 일어났다면 이 뒤따르는 명령어를 아키텍처 상태에 반영해서는 안 됩니다.

해결 전략은 다음과 같습니다.

- 분기 결과가 나올 때까지 명령어 가져오기를 멈춥니다.
- 항상 분기하지 않음 또는 분기함으로 정적으로 예측합니다.
- 과거 실행 결과를 이용해 동적으로 예측합니다.
- 컴파일러가 분기 지연 슬롯을 채우도록 정한 ISA를 사용할 수 있습니다.
- 분기 목적지를 더 이른 단계에서 계산합니다.

잘못 예측해 가져온 명령어는 비우고 올바른 목적지부터 다시 가져옵니다.

```sh
python3 exercises/processor-model/reference/processor-model.py pipeline \
  exercises/processor-model/fixtures/traces/pipeline-branch.trace \
  --branch-penalty 2
```

추적 입력은 레이블이 있는 정적 명령열입니다. `@taken`이 붙은 분기가 EX에서 해소되면 모의 실행기는 IF와 ID의 순차 경로 명령을 버리고 레이블이 가리키는 목적지 인덱스부터 다시 가져옵니다. 추적 입력의 잘못된 경로 명령 두 개는 실행 기록에는 남지만 WB에는 도달하지 않습니다.

## 1비트 예측기는 반복문 경계에서 두 번 틀릴 수 있습니다

지난 결과를 그대로 사용하는 1비트 예측기를 생각해 보세요.

반복문에서는 대부분 분기하고 마지막에만 분기하지 않습니다. 마지막 결과 때문에 예측기가 “분기하지 않음”으로 바뀌면, 다음 반복문 진입 때 첫 분기도 분기하지 않는다고 예측해 다시 틀릴 수 있습니다.

2비트 포화 계수기는 한 번의 반대 결과만으로 예측 방향을 바꾸지 않습니다.

```text
강한 분기하지 않음
약한 분기하지 않음
약한 분기함
강한 분기함
```

두 번 연속 반대 결과가 나와야 큰 방향이 바뀌도록 만들어 반복 패턴에 더 안정적입니다. 실제 예측기는 전역·지역 이력, 목적지 버퍼와 반환 주소 예측기를 결합할 수 있지만 기본 질문은 같습니다.

```text
어떤 이력을 키로 저장합니까?
어떤 상태로 다음 방향을 예측합니까?
언제 상태를 갱신합니까?
잘못 추측한 상태를 어떻게 복구합니까?
```

## 분기 실패 비용과 예측 정확도를 함께 봅니다

분기 명령어 비율을 `b`, 예측 실패율을 `m`, 실패 비용을 `p`라고 하면 추가 CPI를 다음처럼 근사할 수 있습니다.

```text
분기 정지 CPI ≈ b × m × p
```

분기 명령어가 20%, 예측 실패율이 5%, 실패 비용이 15사이클이면 약 `0.15 CPI`가 추가됩니다. 실패율이 작아 보여도 깊은 파이프라인에서는 한 번 틀렸을 때의 비용이 큽니다.

정확도만 비교하면 안 됩니다. 예측기 조회 지연, 저장 공간, 전력과 목적지 정보의 준비 시점도 클록과 명령 가져오기 대역폭에 영향을 줍니다.

## 예외는 오래된 명령어부터 보이게 해야 합니다

여러 명령어가 파이프라인에 있을 때 뒤따르는 명령어가 먼저 폴트를 발견할 수 있습니다. 정밀한 예외를 제공하려면 다음 상태가 보여야 합니다.

- 폴트가 난 명령어보다 앞선 명령어는 모두 완료된 상태입니다.
- 폴트가 난 명령어와 그 뒤의 명령어는 아키텍처 상태에 반영되지 않습니다.
- 폴트가 난 PC와 원인을 복구할 수 있습니다.

순차 파이프라인에서는 뒤따르는 명령어의 쓰기 신호를 끄고 파이프라인을 비우는 방식으로 비교적 단순하게 구현할 수 있습니다. 비순차 코어는 재정렬 버퍼의 완료 확정 순서를 이용합니다.

## 파이프라인 성능을 계산할 때 클록도 포함합니다

파이프라인을 깊게 만들면 단계별 논리를 줄여 클록 주기를 낮출 수 있습니다. 동시에 다음 비용이 늘어날 수 있습니다.

- 파이프라인 레지스터 비용
- 분기 예측 실패 비용
- 전달 경로와 우회 멀티플렉서
- 제어 복잡성
- 전력

따라서 다음 비교가 필요합니다.

```text
기존 실행 시간 = IC × 기존 CPI × 기존 클록 주기
새 실행 시간 = IC × 새 CPI × 새 클록 주기
```

단계 수만 보고 더 빠르다고 결론 내릴 수 없습니다.

## 실행 추적표를 손으로 그리는 순서

1. 의존 관계 그래프를 그립니다.
2. 각 생산자의 결과가 어느 단계 끝에 준비되는지 적습니다.
3. 소비자가 어느 단계 시작에 값을 요구하는지 적습니다.
4. 전달 경로가 연결되는지 확인합니다.
5. 해결되지 않으면 유지할 파이프라인 레지스터와 빈 단계의 위치를 표시합니다.
6. 실제로 분기했을 때 잘못 가져온 뒤따르는 명령어를 표시하고 비웁니다.
7. 완료 사이클과 CPI를 계산합니다.

## 직접 확인할 문제

1. `add r1,...` 뒤에 독립 명령어 하나가 있고 그다음 `sub ...,r1,...`가 올 때, 전달 경로 유무에 따른 정지를 그려 보세요.
2. 저장 명령어의 주소 소스와 데이터 소스가 각각 어느 단계까지 필요할 수 있는지 설명해 보세요.
3. 분기를 ID에서 해결할 때와 EX에서 해결할 때의 임계 경로, 비울 단계 수와 상충 관계를 적어 보세요.
4. 1비트 예측기와 2비트 예측기가 `T T T N` 패턴을 두 번 반복해서 만날 때 실패 횟수를 계산해 보세요.
5. 더 깊은 파이프라인에서 주파수가 20% 오르고 분기 비용 때문에 CPI가 15% 늘었다면 전체 속도 향상 비율을 계산해 보세요.
