# 비밀번호, 세션과 쿠키

로그인은 입력한 비밀번호가 맞는지 확인하는 단계와, 이후 요청에서도 같은 사용자를 안전하게 식별하는 단계로 나뉩니다. 비밀번호 원문과 세션 토큰은 유출되면 곧바로 악용될 수 있으므로 데이터베이스에도 그대로 저장하지 않습니다.

## 목표

- 검증된 비밀번호 해싱 함수를 사용해 비밀번호를 저장하고 확인합니다.
- 예측할 수 없는 불투명 세션 토큰을 발급하고 데이터베이스에는 다이제스트만 저장합니다.
- 쿠키 속성과 세션 수명을 일관되게 관리합니다.
- 로그인, 로그아웃, 만료, 토큰 교체, 계정 정지 이후의 동작을 정의합니다.
- 인증 오류와 운영 로그에 비밀값을 노출하지 않습니다.

## 비밀번호는 복호화할 값이 아닙니다

서비스는 원문 비밀번호를 복원할 필요가 없습니다. 검증된 비밀번호 해싱 라이브러리를 사용해 솔트와 비용 설정이 포함된 해시를 저장합니다.

```ts
const passwordHash = await passwordHasher.hash(password);
const matches = await passwordHasher.verify(user.passwordHash, candidate);
```

SHA-256 같은 일반 해시 함수를 한 번 적용하거나 직접 솔트·해시 형식을 설계해서는 안 됩니다. Argon2id나 scrypt처럼 비밀번호 저장용으로 검토된 알고리즘을 신뢰할 수 있는 라이브러리로 사용하고, 배포 환경에서 허용 가능한 지연 시간과 메모리 사용량을 측정합니다.

## 입력 규칙

비밀번호 정책은 사용성과 공격 비용을 함께 고려해야 합니다.

- 지나치게 짧은 값은 거부하되 충분히 긴 최대 길이를 허용합니다.
- 임의의 대문자·소문자·특수문자 조합만 강제하기보다 긴 암호 문구를 허용합니다.
- 유니코드 정규화 정책을 명시합니다.
- 로그, 검증 상세 정보, 텔레메트리에 원문을 남기지 않습니다.
- 회원가입과 비밀번호 변경에 같은 규칙을 적용합니다.

로그인 실패 응답으로 이메일 주소의 가입 여부를 필요 이상 드러내지 않습니다. 내부 로그에는 속도 제한과 조사에 필요한 식별자를 남길 수 있지만 비밀번호는 절대 기록하지 않습니다.

## 비밀번호 해시 갱신

시간이 지나면 비용 설정을 높여야 할 수 있습니다. 로그인에 성공했을 때 저장된 해시가 이전 설정으로 생성되었는지 확인하고 현재 설정으로 다시 해싱할 수 있습니다.

```text
비밀번호 검증 성공
→ 재해싱 필요 여부 확인
→ 새 해시 저장
→ 로그인 계속 진행
```

비밀번호를 변경할 때는 기존 비밀번호 재확인, 새 해시 저장, 기존 세션 폐기 정책을 함께 정의합니다.

## 세션 토큰

세션 토큰은 암호학적으로 안전한 난수 생성기로 충분한 엔트로피를 가진 바이트를 생성해 만듭니다.

```ts
const token = randomBytes(32).toString("base64url");
const digest = createHash("sha256").update(token).digest("hex");
```

여기서 SHA-256은 비밀번호가 아니라 이미 무작위인 토큰을 데이터베이스에 안전하게 식별하기 위한 다이제스트에 사용합니다. 데이터베이스에는 다이제스트만 저장하고 원문 토큰은 쿠키로 한 번 전달합니다.

```sql
create table sessions (
  id uuid primary key,
  user_id uuid not null references users(id) on delete cascade,
  token_digest text not null unique,
  expires_at timestamptz not null,
  created_at timestamptz not null,
  last_seen_at timestamptz,
  revoked_at timestamptz
);
```

각 요청에서는 쿠키의 토큰을 같은 방식으로 다이제스트로 변환해 세션을 찾고, 세션 만료·폐기 여부와 사용자 계정 상태를 함께 확인합니다.

## 쿠키 속성

```ts
reply.setCookie("app_session", token, {
  path: "/",
  httpOnly: true,
  secure: config.production,
  sameSite: "lax",
  maxAge: 60 * 60 * 24 * 14
});
```

- `HttpOnly`: JavaScript에서 세션 토큰을 읽지 못하게 합니다.
- `Secure`: HTTPS 연결에서만 쿠키를 전송합니다. 운영 환경에서는 필수입니다.
- `SameSite`: 교차 사이트 요청에서 쿠키 전송을 제한하지만 CSRF 방어 전체를 대신하지는 않습니다.
- `Path`: 필요한 경로에만 쿠키를 전송합니다. 삭제할 때도 발급할 때와 같은 값을 사용해야 합니다.
- `Domain`: 특별한 이유가 없다면 호스트 전용 쿠키를 사용합니다.
- `Max-Age` 또는 `Expires`: 브라우저의 쿠키 수명과 서버의 세션 만료 시점을 함께 설정합니다.

쿠키 이름, 경로, 도메인을 발급할 때와 삭제할 때 다르게 지정하면 브라우저에 기존 쿠키가 남을 수 있습니다.

## 로그인 흐름

```text
이메일·비밀번호 파싱
→ 사용자 조회
→ 비밀번호 검증
→ 계정 활성 상태 확인
→ 새 세션 토큰 생성
→ 다이제스트 저장
→ 쿠키 발급
→ 공개 가능한 사용자 DTO 반환
```

비밀번호 검증에는 CPU와 메모리 비용이 들기 때문에 로그인 시도에 속도 제한이 필요합니다. IP 주소만으로 차단하면 공유 네트워크의 정상 사용자까지 막을 수 있고, 계정만으로 차단하면 공격자가 특정 사용자의 로그인을 방해할 수 있습니다. 여러 신호와 점진적인 제한을 함께 사용합니다.

## 세션 고정 방지와 토큰 교체

인증 전에 사용하던 세션 식별자를 로그인 후에도 그대로 유지해서는 안 됩니다. 로그인, 권한 상승, 비밀번호 변경 같은 보안 경계에서는 새 토큰을 발급하고 이전 세션을 폐기합니다.

동시에 허용할 세션 수, 기기 목록 제공 여부, 전체 로그아웃 동작을 제품 요구사항으로 정합니다. 로그아웃은 브라우저 쿠키 삭제뿐 아니라 서버의 세션 폐기까지 완료되어야 합니다.

## 요청 인증

Fastify 훅이나 인증 플러그인이 쿠키를 읽고 요청의 사용자 문맥을 만듭니다.

```ts
interface Actor {
  userId: string;
  sessionId: string;
  accountStatus: "active" | "suspended";
}
```

각 라우트에서 토큰 파싱을 반복하지 않습니다. 인증이 선택 사항인 라우트와 필수인 라우트를 명확히 구분합니다. 사용자 계정이 정지되거나 삭제되었다면 만료되지 않은 세션도 거부해야 합니다.

## 만료와 정리

최종 만료 기준은 서버의 `expires_at`입니다. 쿠키가 브라우저에 남아 있어도 서버에서 만료된 세션은 거부합니다. 슬라이딩 만료를 사용한다면 요청마다 데이터베이스 쓰기가 발생하지 않도록 갱신 간격과 최대 절대 수명을 정합니다.

만료되거나 폐기된 세션 행은 정기적으로 정리하되 감사 요구사항과 데이터 보존 정책을 함께 고려합니다.

## 비밀번호 재설정

비밀번호 재설정 토큰도 원문은 사용자에게 전달하고 데이터베이스에는 다이제스트만 저장합니다.

- 짧은 만료 시간
- 한 번 사용한 뒤 즉시 폐기
- 새 토큰을 발급할 때 기존 토큰을 폐기할지에 대한 정책
- 재설정 성공 후 기존 세션 전체를 폐기할지에 대한 정책
- 계정 존재 여부를 과도하게 드러내지 않는 응답

재설정 토큰 저장과 이메일 전송 사이에 실패가 발생했을 때의 상태도 정의합니다. 이메일 운영의 세부 내용은 이 가이드의 범위가 아니지만 토큰 수명과 사용 규칙은 인증 설계의 일부입니다.

## 로그와 오류 응답

다음 값은 기록하지 않습니다.

- 원문 비밀번호
- 세션 쿠키
- `Authorization` 헤더
- 비밀번호 재설정 토큰
- 전체 비밀번호 해시

로그에는 요청 ID, 사용자 ID, 세션 ID 같은 비민감 내부 식별자, 처리 결과 코드, 속도 제한 결과를 남길 수 있습니다. 클라이언트에는 로그인 실패를 안정적인 일반 오류로 반환합니다.

## 흔한 오류

- 비밀번호를 복호화 가능한 방식으로 암호화하거나 일반 해시를 한 번 적용해 저장합니다.
- 자체 솔트·해시 형식을 설계합니다.
- 세션 원문 토큰을 데이터베이스에 저장합니다.
- 브라우저 쿠키만 지우고 서버 세션은 남겨 둡니다.
- 만료된 세션이나 정지된 사용자 상태를 확인하지 않습니다.
- 로그인 전후에 같은 세션 토큰을 유지합니다.
- 쿠키나 비밀번호를 로그에 기록합니다.

## 연결 실습

[`세션과 권한`](../../exercises/06-security/README.md)의 취약한 `skeleton/`에서 세션 폐기, 쿠키 경로, 인증 결과를 검사합니다.

## 완료 기준

- 비밀번호 해시와 무작위 세션 토큰의 다이제스트가 다른 목적으로 사용된다는 점을 설명할 수 있습니다.
- 로그인, 로그아웃, 만료, 토큰 교체 흐름을 구현할 수 있습니다.
- 쿠키의 `HttpOnly`, `Secure`, `SameSite`, `Path` 속성이 무엇을 보장하는지 설명할 수 있습니다.
- 각 요청에서 계정 상태와 세션 상태를 함께 확인합니다.
- 저장소, 로그, 오류 응답에 인증 비밀값을 노출하지 않습니다.
