# 권한, CSRF와 CORS

로그인했다는 사실만으로 모든 리소스를 읽고 수정할 수 있는 것은 아닙니다. 화면에서 버튼을 숨기는 것은 사용자 인터페이스를 조정하는 것일 뿐입니다. HTTP와 WebSocket의 모든 변경 경계에서 서버가 현재 사용자, 대상 리소스, 요청한 작업을 다시 확인해야 합니다.

## 목표

- 인증과 권한 판정을 구분합니다.
- 역할과 리소스 소유권을 하나의 정책으로 표현합니다.
- 401, 403, 리소스 존재를 숨기기 위한 404 응답 정책을 구분합니다.
- 쿠키 기반 인증에서 CSRF를 방어합니다.
- CORS를 브라우저의 교차 출처 응답 접근 정책으로 정확히 설정합니다.
- HTTP와 WebSocket에 같은 도메인 권한 규칙을 적용합니다.

## 인증과 권한 판정

```text
인증(authentication) → 요청한 사용자가 누구인가
권한(authorization)  → 이 사용자가 해당 리소스에 이 작업을 수행할 수 있는가
```

예를 들어 `viewer`는 메모를 읽을 수 있지만 수정할 수 없습니다.

| 역할 | 읽기 | 내용 수정 | 구성원 관리 | 삭제 |
|---|---:|---:|---:|---:|
| owner | 가능 | 가능 | 가능 | 가능 |
| editor | 가능 | 가능 | 불가 | 불가 |
| viewer | 가능 | 불가 | 불가 | 불가 |

이 표는 기본 규칙일 뿐입니다. 실제 판정에는 계정 상태, 리소스의 보관 여부, 변경 대상 사용자, 현재 역할 같은 조건도 포함될 수 있습니다.

## 권한 정책은 서버의 한 위치에서 관리합니다

```ts
function assertCanEditNote(actor: Actor, membership: Membership, note: Note): void {
  if (actor.accountStatus !== "active") throw new Forbidden("account_inactive");
  if (note.archivedAt) throw new Conflict("note_archived");
  if (!(["owner", "editor"] as const).includes(membership.role)) {
    throw new Forbidden("note_write_forbidden");
  }
}
```

HTTP 라우트, 서비스, WebSocket 핸들러에 서로 다른 역할 규칙을 복사하지 않습니다. 전송 계층은 사용자 문맥과 명령을 만들고 공통 정책을 호출합니다.

클라이언트가 보낸 역할을 권한 판정에 사용해서는 안 됩니다. 멤버십 정보는 서버가 데이터베이스나 신뢰할 수 있는 캐시에서 조회해야 합니다.

## 조회 범위에 권한 조건을 포함합니다

메모를 ID로 먼저 조회한 뒤 소유자를 확인하는 대신, 현재 사용자에게 보이는 메모만 조회하도록 쿼리할 수 있습니다.

```sql
select n.id, n.title, m.role
from notes n
join note_members m on m.note_id = n.id
where n.id = $1 and m.user_id = $2;
```

이 방식은 권한 확인 전에 데이터를 사용하거나 로그에 노출할 위험을 줄입니다. 다만 권한이 없는 요청에 403과 404 중 무엇을 반환할지는 제품의 외부 공개 정책에 따라 정해야 합니다.

## 401, 403, 404

- **401 Unauthorized**: 유효한 인증 정보가 없습니다.
- **403 Forbidden**: 사용자는 식별했지만 요청한 작업을 허용하지 않습니다.
- **404 Not Found**: 리소스가 없거나, 존재 자체를 공개하지 않는 정책을 적용했습니다.

다른 사용자의 비공개 메모 존재 여부를 알려 줄 필요가 없다면 읽기 요청에 404를 반환할 수 있습니다. 관리 화면처럼 권한 부족을 명확히 알려야 하는 경우에는 403이 더 적합할 수 있습니다. 같은 API 안에서는 선택한 정책을 일관되게 적용합니다.

## 객체 수준 권한 누락을 막습니다

다음과 같은 URL의 식별자를 바꾸어 다른 사용자의 리소스를 수정할 수 있어서는 안 됩니다.

```text
PATCH /notes/{noteId}
```

`noteId`가 올바른 형식이라는 사실과 현재 사용자가 그 메모를 수정할 권한이 있다는 사실은 별개입니다. 목록에서 해당 메모를 보았는지, 화면에 수정 버튼이 있었는지와 관계없이 서버에서 권한을 검사합니다.

## 역할 변경에는 별도의 불변식이 필요합니다

구성원의 역할을 변경하는 API는 일반적인 내용 수정 API보다 강한 규칙이 필요합니다.

- `owner`만 역할을 변경할 수 있음
- 마지막 `owner`를 `viewer`로 낮출 수 없음
- 사용자가 자신의 권한을 임의로 높일 수 없음
- 정지된 사용자를 초대할 수 없음
- 변경 전후 역할과 작업 수행자를 감사 기록에 저장
- 멤버십 변경과 감사 이벤트 기록을 하나의 트랜잭션으로 처리

권한 체계가 스스로 유효하지 않은 상태를 만들지 않도록 불변식을 정의합니다.

## CSRF가 발생하는 이유

브라우저는 다른 사이트에서 시작된 요청에도 대상 도메인의 쿠키를 자동으로 포함할 수 있습니다. 공격자 사이트가 쿠키 값을 읽지 못하더라도 사용자의 인증 정보가 포함된 상태 변경 요청을 보낼 수 있습니다.

쿠키 기반 인증의 상태 변경 요청에는 다음 방어 수단을 조합합니다.

1. `SameSite=Lax` 또는 더 엄격한 쿠키 정책
2. HTTPS와 `Secure` 쿠키
3. `Origin`, 필요한 경우 `Referer`의 정확한 검증
4. CSRF 토큰
5. 상태 변경 요청에 `GET`을 사용하지 않음

`SameSite` 하나가 모든 브라우저, 탐색 방식, 서브도메인 조건에서 CSRF를 완전히 막는다고 가정해서는 안 됩니다.

## Origin 검증

```ts
function requireTrustedOrigin(origin: string | undefined, allowed: Set<string>): void {
  if (!origin || !allowed.has(origin)) throw new Forbidden("untrusted_origin");
}
```

문자열 접두사나 접미사로 검사하면 `https://trusted.example.attacker.test` 같은 출처를 잘못 허용할 수 있습니다. URL을 정규화한 뒤 정확한 출처 집합과 비교합니다.

브라우저가 아닌 클라이언트처럼 `Origin` 헤더가 없는 요청을 허용할지는 엔드포인트와 인증 방식별로 별도 정책을 정합니다.

## CSRF 토큰

서버 세션과 연결된 예측 불가능한 토큰을 폼이나 응답으로 제공하고, 상태 변경 요청의 헤더나 본문에 포함된 값을 검증할 수 있습니다. 이중 제출 쿠키 방식을 사용할 수도 있지만 쿠키 값과 요청 값의 무결성, 동일 사이트 조건을 정확히 이해해야 합니다.

토큰은 다음 조건을 충족해야 합니다.

- 공격자 사이트에서 읽을 수 없음
- 세션과 연결되거나 검증 가능한 서명이 포함됨
- 타이밍 공격을 피할 수 있는 안전한 비교 사용
- 로그에 원문을 남기지 않음
- 로그아웃이나 세션 토큰 교체 시 함께 갱신하는 정책 보유

## CORS는 서버의 접근 제어가 아닙니다

CORS는 브라우저가 다른 출처에서 받은 응답을 JavaScript에 공개할지 결정하는 프로토콜입니다. `curl`이나 서버 간 요청을 차단하지 않으며 인증과 권한 검사를 대신하지 않습니다.

인증 정보를 포함한 요청을 허용할 때는 와일드카드 출처를 사용할 수 없습니다.

```ts
const allowedOrigins = new Set([
  "https://app.example.com",
  "https://admin.example.com"
]);
```

요청의 `Origin` 값을 검증 없이 그대로 응답에 반영하지 않습니다. 프리플라이트 응답에서는 메서드와 헤더를 필요한 범위로 제한하고, 캐시가 출처별 응답을 섞지 않도록 필요한 경우 `Vary: Origin`을 설정합니다.

## WebSocket 업그레이드와 메시지 권한

WebSocket 연결에서도 브라우저가 쿠키를 전송할 수 있습니다. 업그레이드 시 다음 항목을 검사합니다.

- 정확한 `Origin`
- 세션 쿠키와 만료 여부
- 계정 상태
- 연결 후 `board.join` 메시지의 멤버십

연결이 유지되는 동안 역할이 바뀌거나 계정이 정지될 수 있습니다. 각 상태 변경 메시지에서 현재 권한을 다시 검사하거나, 갱신 주기가 짧고 무효화 방법이 명확한 캐시 정책을 사용합니다.

## 관리자 기능

`admin` 불리언 하나로 모든 작업을 허용하기보다 필요한 권한과 감사 요구사항을 구체적으로 정의합니다.

- 작업 대상 사용자와 수행자가 같은 사람인지
- 관리자가 자신의 계정을 정지할 수 있는지
- 작업 사유 입력이 필요한지
- 세션 폐기와 감사 기록이 함께 성공하는지
- 민감한 정보 조회에 별도 권한이 필요한지

관리자 화면이 일반 사용자에게 보이지 않는다는 이유로 관리자 API의 검사를 약하게 만들어서는 안 됩니다.

## 검증 행렬

각 상태 변경 API에서 최소한 다음 경우를 검사합니다.

```text
인증 정보 없음             → 401
구성원이 아님              → 403 또는 정책상 404
viewer                     → 읽기 성공, 쓰기 거부
editor                     → 내용 수정 성공, 역할 변경 거부
owner                      → 허용된 관리 작업 성공
다른 사용자의 리소스 ID   → 거부
신뢰하지 않는 Origin      → 거부
로그아웃한 세션            → 401
정지된 계정의 기존 세션   → 정책에 따라 401 또는 403
```

HTTP와 WebSocket에 같은 권한 행렬을 적용합니다.

## 흔한 오류

- 화면에서 버튼을 숨긴 것으로 권한 검사를 끝냅니다.
- 클라이언트가 보낸 역할을 신뢰합니다.
- 식별자 형식 검증을 소유권 검증으로 착각합니다.
- CORS를 인증이나 권한 방어 수단으로 설명합니다.
- 인증 정보가 포함된 요청에서 출처를 검증 없이 그대로 반영합니다.
- 쿠키 인증을 사용하는 상태 변경 요청에 CSRF 방어가 없습니다.
- WebSocket 연결 시점에만 권한을 확인하고 이후 메시지는 모두 허용합니다.
