# 마이그레이션과 트랜잭션

애플리케이션 코드와 데이터베이스 스키마는 서로 다른 시점에 배포될 수 있습니다. 마이그레이션 절차가 개발자 메모에만 남아 있거나 여러 쓰기가 각각 커밋되면 재배포나 중간 실패 시 데이터가 일관되지 않은 상태로 남습니다. 스키마 변경과 도메인 데이터 쓰기 모두 **어디까지를 한 번에 적용하고, 실패하면 어떤 상태가 남아야 하는지** 먼저 정의해야 합니다.

## 목표

- 마이그레이션을 순서가 있는 변경 이력으로 관리하고, 적용된 파일을 수정하지 않습니다.
- 빈 데이터베이스와 기존 데이터가 있는 데이터베이스에서 마이그레이션을 검증합니다.
- 함께 성공하거나 실패해야 하는 쓰기를 하나의 트랜잭션으로 묶습니다.
- 격리 수준, 잠금, 교착 상태, 재시도의 기본 원리를 설명합니다.
- 애플리케이션 배포와 스키마 변경을 호환 가능한 단계로 나눕니다.

## 마이그레이션은 현재 스키마가 아니라 변경 이력입니다

```text
001_create_users.sql
002_create_notes.sql
003_add_note_version.sql
```

이미 적용된 마이그레이션 파일을 나중에 수정하면 기존 환경과 새 환경의 최종 스키마가 달라질 수 있습니다. 잘못된 변경은 새 마이그레이션을 추가해 바로잡습니다.

마이그레이션 실행기는 다음 정보를 기록해야 합니다.

- 마이그레이션 식별자와 적용 순서
- 적용 시각
- 체크섬 또는 파일 변경 여부
- 실패한 마이그레이션의 상태

여러 애플리케이션 인스턴스가 동시에 마이그레이션을 실행하지 않도록 잠금을 사용하거나 별도의 릴리스 단계에서 한 번만 실행합니다.

## 빈 데이터베이스와 업그레이드 경로를 모두 검사합니다

다음 두 경로를 모두 검증해야 합니다.

```text
빈 데이터베이스 → 모든 마이그레이션을 순서대로 적용 → 현재 스키마
이전 릴리스의 데이터베이스 → 새 마이그레이션만 적용 → 현재 스키마
```

새 개발 환경에서는 성공해도 실제 데이터가 있는 운영 환경에서는 실패할 수 있습니다. 기존 행이 있는 테이블에 기본값이나 사전 데이터 보정 없이 `NOT NULL` 열을 추가하는 경우가 대표적입니다.

## 확장–이관–축소 방식

하위 호환성을 유지해야 하는 스키마 변경은 여러 릴리스로 나눌 수 있습니다.

예를 들어 `users.name`을 `display_name`으로 바꾸는 과정을 생각해 봅니다.

1. **확장**: nullable인 새 열을 추가하고 새 코드가 두 열을 모두 읽을 수 있게 합니다.
2. **이관**: 기존 행을 배치 단위로 보정하고 누락된 행이 없는지 측정합니다.
3. **전환**: 모든 쓰기 코드가 새 열을 사용하도록 배포합니다.
4. **축소**: 이전 버전의 코드가 모두 사라진 뒤 기존 열을 제거하고 제약 조건을 강화합니다.

한 번의 열 이름 변경으로도 기술적으로 처리할 수 있지만, 여러 버전이 동시에 실행되거나 롤백이 필요한 환경에서는 호환되지 않을 수 있습니다.

## 데이터 보정은 별도 작업으로 다룹니다

큰 테이블의 모든 행을 한 트랜잭션에서 변경하면 잠금 시간, WAL 크기, 복제 지연이 크게 늘 수 있습니다. 배치 기준 키, 재시작 위치, 처리 속도, 완료 검증을 가진 별도 작업으로 나눕니다.

```sql
with batch as (
  select id
  from users
  where id > $1
    and display_name is null
  order by id
  limit $2
  for update skip locked
)
update users as u
set display_name = u.name
from batch
where u.id = batch.id
returning u.id;
```

PostgreSQL에서 실제 배치 갱신은 CTE나 키 목록을 이용해 구현할 수 있습니다. 핵심은 작업이 중단되어도 이어서 실행할 수 있고, 이미 처리한 행을 안전하게 건너뛸 수 있어야 한다는 점입니다.

## 트랜잭션은 원자적인 도메인 작업 단위입니다

메모 수정과 활동 기록이 함께 성공해야 한다고 가정합니다.

```ts
await db.transaction().execute(async (trx) => {
  const note = await updateNoteIfCurrent(trx, command);
  if (!note) throw new VersionConflict();
  await appendActivity(trx, {
    noteId: note.id,
    actorId: command.actorId,
    version: note.version,
    occurredAt: clock.now()
  });
});
```

콜백에서 오류가 발생하면 두 쓰기 모두 롤백됩니다. 트랜잭션 안에서 외부 HTTP 요청, 이메일 전송, 메시지 브로커 응답을 오래 기다려서는 안 됩니다. 데이터베이스 트랜잭션이 원자성을 보장할 수 있는 범위는 해당 데이터베이스의 상태뿐입니다.

## 트랜잭션 경계를 너무 작거나 크게 잡지 않습니다

경계가 너무 작으면 부분 성공이 발생합니다.

```text
메모 수정 커밋
→ 활동 기록 삽입 실패
→ 감사 기록이 없는 변경 발생
```

경계가 너무 크면 불필요하게 오래 잠금을 유지합니다.

```text
데이터베이스 잠금 획득
→ 외부 API 타임아웃을 10초 동안 대기
→ 다른 요청도 같은 행의 잠금을 기다림
```

유스 케이스의 데이터베이스 불변식을 보호할 수 있는 가장 짧은 범위로 트랜잭션을 제한합니다.

## 격리 수준의 기본 원리

여러 트랜잭션은 동시에 실행됩니다. 기본 격리 수준에서도 다음 문제를 고려해야 합니다.

- 두 요청이 같은 행을 읽고 각각 갱신해 한쪽 변경이 사라지는 갱신 손실
- 서로 다른 행을 읽고 각각 쓰면서 테이블 전체의 규칙을 깨는 쓰기 편향
- 잠금을 서로 반대 순서로 획득해 발생하는 교착 상태
- 직렬화 실패

모든 문제를 높은 격리 수준 하나로 해결하려 하지 않습니다. 조건부 `UPDATE`, 고유 제약 조건, 명시적인 행 잠금, 직렬화 가능 트랜잭션 중 보호하려는 불변식에 맞는 수단을 선택합니다.

## 행 잠금

다음 순번을 하나의 행에서 할당해야 한다면 `FOR UPDATE`로 해당 카운터 행을 잠글 수 있습니다.

```sql
select next_sequence
from board_counters
where board_id = $1
for update;
```

잠금을 사용할 때는 모든 코드 경로가 자원을 같은 순서로 획득하게 합니다. 행 잠금은 트랜잭션이 끝날 때까지 유지됩니다.

## 교착 상태와 재시도

PostgreSQL은 교착 상태를 감지하면 관련 트랜잭션 중 하나를 중단합니다. 직렬화 실패도 동시 실행 과정에서 정상적으로 발생할 수 있습니다. 다음 조건을 모두 충족할 때만 재시도합니다.

- 전체 트랜잭션을 처음부터 다시 실행할 수 있습니다.
- 트랜잭션 안에 외부 부수 효과가 없습니다.
- 시도 횟수와 전체 제한 시간이 정해져 있습니다.
- 무작위 지연을 사용해 여러 요청이 동시에 다시 충돌하는 상황을 줄입니다.
- 재시도 가능한 오류 코드를 좁게 정의합니다.

모든 데이터베이스 오류를 무제한 재시도하면 장애를 더 크게 만들 수 있습니다.

## 커밋 이후의 외부 부수 효과

데이터베이스 커밋과 메시지 발행을 하나의 트랜잭션으로 묶을 수 없다면 단순히 “커밋한 뒤 발행한다”로 끝내서는 안 됩니다. 작은 단일 애플리케이션에서는 발행 실패를 기록하고 재시도할 수 있습니다. 여러 서비스 사이의 확실한 전달은 아웃박스 패턴 같은 분산 시스템 주제입니다. 이 가이드에서는 데이터베이스 트랜잭션이 보장하지 못하는 경계까지 이해합니다.

## 마이그레이션과 애플리케이션 배포

릴리스 전에 다음 항목을 확인합니다.

- 새 코드가 이전 스키마에서도 시작할 수 있는가
- 마이그레이션 후 이전 코드로 롤백할 수 있는가
- 오래 실행되는 마이그레이션이 요청 지연 시간을 악화시키는가
- 마이그레이션 실패를 자동으로 다시 실행해도 안전한가
- 마이그레이션 완료 전에 준비 상태 검사가 트래픽을 허용하지 않는가

스키마 마이그레이션을 모든 애플리케이션 인스턴스의 일반 시작 과정에 무조건 포함하면 인스턴스 간 경쟁과 긴 재시작이 발생할 수 있습니다. 별도의 릴리스 작업으로 실행하는 방식을 고려합니다.

## 검증 항목

최소한 다음을 검사합니다.

- 빈 데이터베이스에 모든 마이그레이션 적용
- 이전 버전의 스냅샷에서 업그레이드
- 같은 마이그레이션을 다시 실행했을 때의 처리 방식
- 중간 실패 후 부분적으로 변경된 스키마가 남는지
- 트랜잭션의 두 번째 쓰기 실패와 전체 롤백
- 같은 버전을 대상으로 한 동시 갱신
- 교착 상태와 직렬화 실패 처리
- 연결 풀과 프로세스 정리

## 흔한 오류

- 이미 적용된 마이그레이션 파일을 직접 수정합니다.
- 현재 스키마 덤프만 관리하고 변경 이력을 남기지 않습니다.
- 기존 데이터가 있는 업그레이드 경로를 검사하지 않습니다.
- 트랜잭션 안에서 외부 API를 호출합니다.
- 모든 데이터베이스 오류를 같은 방식으로 재시도합니다.
- 파괴적인 스키마 변경과 코드 배포를 한 단계에서 처리합니다.
- 모든 애플리케이션 인스턴스가 동시에 마이그레이션을 실행하게 둡니다.
