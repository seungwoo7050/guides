# React 컴포넌트와 상태

React는 DOM 조작 코드를 줄이는 도구라기보다 **현재 상태로부터 화면을 선언적으로 구성하는 모델**입니다. 컴포넌트는 파일 길이가 아니라 책임, 상태 소유권, 재사용할 UI 계약을 기준으로 나눕니다.

## 목표

- 컴포넌트, props, state의 역할을 구분합니다.
- 상태를 필요한 범위에서 가장 가까운 공통 소유자에게 둡니다.
- 이전 상태를 기준으로 다음 상태를 안전하게 계산합니다.
- 기존 값에서 계산할 수 있는 값을 중복 상태로 저장하지 않습니다.
- 서버·URL·컴포넌트 상태의 기준 위치를 구분합니다.

## 컴포넌트는 입력을 받아 UI를 반환합니다

```tsx
type TaskItemProps = {
  task: Task;
  onToggle: (id: string) => void;
};

export function TaskItem({ task, onToggle }: TaskItemProps) {
  return (
    <li>
      <label>
        <input
          type="checkbox"
          checked={task.completed}
          onChange={() => onToggle(task.id)}
        />
        {task.title}
      </label>
    </li>
  );
}
```

props는 부모 컴포넌트가 제공하는 입력입니다. 자식 컴포넌트는 전달받은 props를 직접 변경하지 않습니다. 변경이 필요하면 콜백으로 의도를 전달하고, 상태 소유자가 새 상태를 계산합니다.

## state는 렌더링 사이에 보존되는 값입니다

```tsx
const [tasks, setTasks] = useState<Task[]>([]);
```

일반 지역 변수는 렌더링할 때마다 다시 계산됩니다. 사용자 상호작용 이후에도 보존되어 다음 렌더링에 영향을 주는 값만 state로 둡니다.

다음 값은 state로 관리할 수 있습니다.

- 입력 중인 초안
- 선택된 탭
- 모달 열림 여부
- 클라이언트가 임시로 만든 낙관적 항목

다음 값은 일반적으로 기존 상태에서 계산합니다.

```tsx
const openCount = tasks.filter((task) => !task.completed).length;
```

`tasks`와 `openCount`를 각각 state로 관리하면 어느 한쪽의 변경을 빠뜨려 두 값이 어긋날 수 있습니다.

## 이전 상태에 의존할 때는 함수형 업데이트를 사용합니다

```tsx
setTasks((current) => current.map((task) =>
  task.id === id ? { ...task, completed: !task.completed } : task
));
```

여러 상태 변경이 일괄 처리될 수 있고 콜백이 이전 렌더링의 값을 참조할 수도 있습니다. 다음 상태가 이전 상태에 의존한다면 업데이트 함수를 사용합니다.

```tsx
setCount(count + 1);
setCount(count + 1); // 같은 렌더링의 count를 사용하므로 1만 증가할 수 있음

setCount((value) => value + 1);
setCount((value) => value + 1); // 2 증가
```

## 상태를 직접 변경하지 않습니다

```tsx
// 피합니다.
tasks.push(newTask);
setTasks(tasks);
```

같은 배열 참조를 다시 전달하면 React가 상태가 바뀌지 않은 것으로 판단할 수 있고, 메모이제이션을 비롯한 참조 동일성 계약도 깨집니다.

```tsx
setTasks((current) => [...current, newTask]);
```

중첩 객체는 실제로 변경되는 경로마다 새 객체를 만듭니다. 모든 값을 무조건 깊은 복사하기보다 상태 구조를 단순하게 유지합니다.

## 상태를 출처별로 구분합니다

| 상태 | 기준 위치 | 예시 |
|---|---|---|
| 서버 상태 | API·데이터베이스 | 보드, 구성원, 활동 기록 |
| URL 상태 | 주소 | 검색어, 선택한 보드, 페이지 번호 |
| 실시간 상태 | 서버 연결과 메시지 시퀀스 | 접속 상태, 커서, 패치 시퀀스 |
| 컴포넌트 상태 | 해당 컴포넌트 | 입력 초안, 메뉴 열림 여부 |

서버 상태를 여러 컴포넌트의 독립적인 `useState`에 복사하면 새로고침이나 변경 요청 이후 값이 서로 달라질 수 있습니다. 하나의 데이터 경계에서 가져와 자식 컴포넌트에 전달하거나, 필요에 맞는 캐시 계층을 사용합니다.

## 상태를 상위로 올리는 기준

형제 컴포넌트 둘이 같은 값을 읽거나 변경해야 한다면 가장 가까운 공통 부모가 그 상태를 소유할 수 있습니다. 하지만 모든 상태를 페이지 루트로 올리면 작은 입력 변경까지 전체 컴포넌트 트리의 책임으로 확장됩니다.

다음 질문으로 소유 위치를 결정합니다.

1. 이 값을 실제로 변경하는 주체는 누구인가?
2. 이 값을 함께 읽어야 하는 가장 가까운 범위는 어디인가?
3. URL이나 서버에 이미 기준값이 있는가?
4. 별도 상태가 아니라 기존 값에서 계산할 수 있는가?

## 컴포넌트 경계

다음과 같은 이유가 있을 때 컴포넌트를 분리합니다.

- 독립적인 UI 의미와 접근성 계약이 있습니다.
- 별도의 상태 생명주기를 가집니다.
- 여러 위치에서 재사용됩니다.
- 테스트에서 독립적으로 검증할 동작이 있습니다.
- 서버와 클라이언트 사이의 경계를 좁힐 수 있습니다.

JSX가 일정 줄 수를 넘었다는 이유만으로 의미 없는 래퍼 컴포넌트를 만들 필요는 없습니다.

## `key`는 항목의 식별자입니다

```tsx
{tasks.map((task) => <TaskItem key={task.id} task={task} />)}
```

`key`는 단순한 DOM 최적화 힌트가 아니라 이전 컴포넌트 인스턴스와 다음 항목을 연결하는 식별자입니다. 정렬·삽입·삭제가 발생하는 목록에서 배열 인덱스를 사용하면 입력 상태나 포커스가 다른 항목에 연결될 수 있습니다.

## 상태 초기화

다른 리소스의 편집 화면으로 전환할 때 자식 컴포넌트의 상태를 명시적으로 초기화해야 할 수 있습니다. `key`를 사용해 컴포넌트 식별자를 바꾸거나, 리소스 ID 변경을 상태 구조에 반영합니다. 모든 props를 Effect로 state에 복사해 계속 맞추는 방식은 같은 값을 두 곳에서 관리하게 만듭니다.

## 흔한 오류

- props를 직접 변경합니다.
- 계산 가능한 값을 별도 state로 저장합니다.
- 이전 값에 의존하면서 현재 렌더링이 캡처한 값으로 상태를 변경합니다.
- 서버 값이나 URL 값을 독립적인 컴포넌트 state로 복사합니다.
- 배열 인덱스를 항목 식별자로 사용합니다.
- 모든 상태를 전역이나 페이지 루트에 둡니다.
