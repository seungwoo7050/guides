# 관계 모델과 관계 대수

## 학습 목표

이 문서를 마치면 다음을 설명할 수 있어야 한다.

- 테이블의 현재 행 순서와 디스크 위치가 관계의 의미가 아닌 이유
- 키, tuple, attribute와 relation의 차이
- 선택·사영·조인·집합 연산으로 질의를 분해하는 방법
- SQL의 중복 허용 의미가 순수 관계 모델과 달라지는 지점
- 실행 계획을 보기 전에 질의의 논리 계약을 먼저 고정해야 하는 이유

## 선행지식

간단한 테이블을 만들고 `SELECT ... FROM ... WHERE ...`를 작성해 본 경험이면 충분하다. 인덱스와 실행 계획은 아직 몰라도 된다.

## 파일 묶음이 아니라 논리 계약에서 시작한다

데이터베이스를 “행을 저장한 파일”로만 보면 질문이 곧바로 저장 위치와 탐색 방법으로 내려간다. 그러나 저장 방식은 바뀔 수 있다. heap file을 사용하다가 index를 추가해도, page 크기가 달라져도, buffer pool에 남아 있어도 같은 질의는 같은 논리 결과를 내야 한다.

관계 모델은 먼저 다음을 정한다.

```text
어떤 종류의 사실을 저장하는가
각 사실을 어떤 속성으로 표현하는가
무엇이 한 tuple을 식별하는가
어떤 연산이 의미를 보존하는가
```

예를 들어 다음 두 관계가 있다고 하자.

```text
User(id, email, grade)
Order(id, user_id, total_cents)
```

`User.id`가 사용자를 식별하고 `Order.user_id`가 사용자를 참조한다는 규칙은 파일 위치와 독립적이다. 인덱스는 이 계약을 더 빠르게 만족시키기 위한 물리구조이지, 계약 자체가 아니다.

## 관계의 핵심 구성요소

- **attribute**: 관계가 표현하는 속성이다. SQL의 column에 가깝다.
- **tuple**: 한 사실의 속성 값을 묶은 것이다. SQL의 row에 가깝다.
- **heading**: attribute 이름과 domain의 집합이다.
- **relation**: 같은 heading을 가진 tuple의 집합이다.
- **candidate key**: tuple 하나를 유일하게 식별할 수 있는 최소 attribute 집합이다.

관계는 본질적으로 순서가 없다. 다음이 보였다고 해서 `id=1`이 언제나 첫 번째라는 계약은 없다.

```text
id | email
1  | a@example.test
2  | b@example.test
```

정렬이 결과 의미에 필요하면 `ORDER BY` 같은 별도 계약이 있어야 한다.

## 기본 관계 연산

관계 대수의 중요한 성질은 **연산 결과가 다시 관계**라는 점이다. 따라서 작은 연산을 합성해 큰 질의를 만들 수 있다.

| 연산 | 질문 | SQL에서 가까운 표현 |
|---|---|---|
| 선택 `σ` | 어떤 tuple을 남기는가 | `WHERE` |
| 사영 `π` | 어떤 attribute를 반환하는가 | `SELECT column` |
| 이름 변경 `ρ` | 이름 충돌을 어떻게 피하는가 | alias |
| 합집합 | 양쪽 결과를 함께 포함하는가 | `UNION` |
| 차집합 | 왼쪽에만 있는 tuple은 무엇인가 | `EXCEPT` |
| 곱 | 가능한 모든 tuple 조합은 무엇인가 | `CROSS JOIN` |
| 조인 | 조건을 만족하는 조합은 무엇인가 | `JOIN ... ON` |

“양수 금액 주문이 있는 사용자의 이메일”은 다음처럼 분해할 수 있다.

```text
paid_orders = σ total_cents > 0 (Order)
matched = User ⋈ User.id = paid_orders.user_id paid_orders
answer = π email (matched)
```

이 표현은 특정 실행 순서를 명령하지 않는다. DBMS는 의미를 보존하는 범위에서 필터를 먼저 적용하거나, index를 이용해 조인 상대를 찾거나, 조인 순서를 바꿀 수 있다.

## 조인은 단순히 표를 붙이는 문법이 아니다

조인은 후보 조합을 만들고 조건을 만족하는 조합만 남기는 연산으로 봐야 한다.

```text
|A × B| = |A| × |B|
|A ⋈ B| = key 유일성·값 분포·조건 선택도에 따라 달라짐
```

조인 조건이 빠지면 결과가 폭발한다. 조인 key가 유일하지 않으면 한쪽의 한 행이 여러 행과 결합한다. 외래 키와 유일 제약은 데이터 무결성뿐 아니라 결과 크기 추정에도 중요한 정보다.

다음 데이터를 보자.

```text
User
id | email
1  | a@example.test
2  | b@example.test

Order
id | user_id | total_cents
10 | 1       | 5000
11 | 1       | 0
12 | 3       | 9000
```

양수 주문을 가진 사용자를 찾으면 `Order.id=11`은 금액 조건에서 제거되고, `Order.id=12`는 대응 사용자가 없으므로 내부 조인 결과에서 제거된다. 최종 이메일은 하나다.

이 예시는 다음 실패 지점을 동시에 드러낸다.

- 참조 무결성이 깨진 주문
- 한 사용자의 중복 주문
- 0이라는 경계값
- 내부 조인에서 사라지는 unmatched tuple

질의를 작성하기 전에 이 손실 지점을 말할 수 있어야 한다.

## 집합 의미와 bag 의미

순수 관계 모델은 보통 중복 없는 집합으로 설명한다. SQL은 기본적으로 중복을 보존하는 bag에 가깝다.

```sql
SELECT grade FROM users;
SELECT DISTINCT grade FROM users;
```

두 질의는 같은 column을 읽지만 의미가 다르다. 첫 번째는 사용자 수만큼 등급이 반복될 수 있다. 두 번째는 서로 다른 등급만 남긴다. `DISTINCT`는 표시 옵션이 아니라 결과 의미를 바꾸며, hash 또는 sort 같은 물리 연산을 요구할 수 있다.

`UNION`과 `UNION ALL`도 같은 차이를 갖는다.

- `UNION`: 중복을 제거한다.
- `UNION ALL`: 입력의 multiplicity를 보존한다.

중복 제거가 업무 계약인지, 우연히 중복이 생겨 이를 감추려는 것인지 구분해야 한다. 잘못된 join을 `DISTINCT`로 덮으면 의미 오류와 비용을 함께 숨긴다.

## 질의 계약을 네 줄로 고정한다

실행 계획이나 index를 논하기 전에 다음을 적는다.

```text
입력 관계:
반환 attribute:
남길 tuple 조건:
중복과 순서 규칙:
```

예:

```text
입력 관계: users, orders
반환 attribute: users.id, users.email
조건: 양수 주문이 하나 이상 존재
중복: 사용자별 한 행
순서: email 오름차순
```

이 계약이 있어야 다음 질문에 답할 수 있다.

- 내부 조인과 외부 조인 중 어느 것이 맞는가
- `EXISTS`와 join 중 어떤 형태가 의미를 더 직접 표현하는가
- 중복 제거가 필요한가
- 정렬 key에 동률 해소 key가 필요한가
- plan 변경 뒤에도 결과가 같은가

## 논리와 물리를 분리하되 연결한다

논리 모델만 알면 비용을 설명하기 어렵고, 물리구조만 알면 무엇을 보존해야 하는지 잃는다.

```text
논리 계약: 어떤 tuple을 반환해야 하는가
물리 계획: 그 tuple을 어떤 page·index·join 연산으로 찾는가
```

옵티마이저는 논리적으로 동치인 표현 사이에서 비용이 낮다고 추정한 계획을 선택한다. 따라서 동치 변환이 가능한 이유는 관계 의미에서 오고, 어느 변환이 싼지는 통계와 저장 구조에서 온다.
