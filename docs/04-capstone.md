# 누적 프로젝트: 동시 작업 원장

이 프로젝트는 앞선 장의 개념을 독립된 작은 문제로 끝내지 않고 하나의 Java 애플리케이션 계약으로 통합합니다. 네트워크, 데이터베이스와 프레임워크는 사용하지 않습니다. Java 언어·JVM·동시성·Maven·테스트 자체에 집중합니다.

실습 경로는 [동시 작업 원장](../exercises/04-capstone/01-concurrent-job-ledger/README.md)입니다.

## 문제

초기 잔액을 가진 원장이 credit과 debit 작업을 비동기로 처리합니다. 각 작업은 고유한 `JobId`를 가지며 같은 작업이 반복 제출되어도 상태에는 한 번만 반영되어야 합니다.

```text
submit(command)
→ 제한된 실행기에 작업 수락
→ 같은 JobId 확인
→ 잔액 규칙 검증
→ 정확한 정수 연산
→ 원자적인 상태 반영
→ 고정 가능한 시각으로 receipt 생성
```

## 구현 단계

### 1. 유효한 값 만들기

다음을 record나 enum으로 표현합니다.

- `JobId`
- `CreditJob`
- `DebitJob`
- `JobReceipt`
- `JobKind`

생성 시점에 다음을 거부합니다.

- `null` 또는 빈 식별자
- 0 이하의 금액
- `null` command와 시간

### 2. 닫힌 명령 계층

`JobCommand`는 credit과 debit만 허용하는 sealed interface입니다. 각 명령은 자신의 식별자와 금액을 제공합니다.

같은 식별자로 완전히 같은 명령이 다시 들어오면 기존 결과를 반환합니다. 같은 식별자로 다른 종류나 금액이 들어오면 충돌로 거부합니다.

### 3. 정확한 상태 전이

- credit은 `Math.addExact`를 사용합니다.
- debit은 `Math.subtractExact`를 사용합니다.
- debit 뒤 잔액이 음수가 되면 기존 상태를 유지하고 거부합니다.
- 실패한 작업도 같은 식별자로 다시 제출했을 때 같은 실패 결과를 관찰합니다.

검증과 새 값 계산을 끝낸 뒤 잔액을 한 번만 바꿉니다.

### 4. 시간과 결과

`Clock`을 생성자에서 받습니다. receipt의 완료 시각은 `clock.instant()`로 만듭니다. 테스트는 `Clock.fixed`를 사용해 같은 결과를 재현합니다.

### 5. 동시 제출과 단일 적용

여러 스레드가 같은 `JobId`를 동시에 제출해도 실제 작업은 하나만 실행되어야 합니다. Map에 결과만 나중에 기록하면 두 작업이 모두 시작될 수 있으므로 “실행 중인 결과 자리” 자체를 원자적으로 등록합니다.

잔액과 receipt 생성에 필요한 상태 전이는 하나의 잠금 범위에서 수행합니다. 외부 네트워크나 파일 I/O는 잠금 안에 넣지 않습니다.

### 6. 제한된 실행기

작업자 수와 대기열 크기를 생성 시점에 고정합니다. 큐가 가득 차면 호출자에게 `RejectedExecutionException`을 전달하고 작업 Map에 불완전한 자리를 남기지 않습니다.

### 7. 종료

원장은 `AutoCloseable`을 구현합니다.

```text
새 작업 거부
→ 이미 수락한 작업 완료 대기
→ 제한 시간 초과 시 취소
→ 인터럽트 상태 복원
```

닫힌 뒤 제출은 즉시 거부합니다.

## 테스트해야 할 계약

- credit과 debit의 정상 결과
- 잔액 부족과 오버플로 뒤 상태 보존
- 고정된 완료 시각
- 같은 command의 반복 제출이 같은 결과를 반환함
- 같은 식별자의 다른 command 충돌
- 여러 스레드의 동일 작업 제출이 한 번만 반영됨
- 제한된 큐의 포화와 거절
- close 뒤 제출 거부
- 작업 예외가 `CompletionStage`에 전달됨

시간 기반 `sleep`으로 합격 여부를 정하지 않습니다. latch와 제어 가능한 `Clock`으로 포화와 동시 실행을 재현합니다.

## 완료 순서

```sh
./mvnw \
  -f exercises/04-capstone/01-concurrent-job-ledger/skeleton/pom.xml \
  test
```

처음에는 계약 테스트가 실패해야 합니다. skeleton 구현을 수정한 뒤 모든 테스트를 통과시키고 저장소 루트에서 전체 검증을 실행합니다.

```sh
./verify.sh
```

reference는 정답 문구가 아니라 하나의 비교 가능한 설계입니다. 자신의 구현이 같은 외부 계약을 더 명확하게 지킨다면 구조가 달라도 됩니다.

- 실행기 포화가 호출자에게 어떻게 전달됩니까?
- 실패한 작업과 성공한 작업은 재제출 때 어떻게 동작합니까?
- 종료 중 새 작업과 이미 수락된 작업은 각각 어떻게 처리됩니까?
- 루트 `verify.sh`의 각 단계가 무엇을 증명합니까?
