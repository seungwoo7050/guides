# HTTP API 모델

HTTP API는 JSON을 주고받는 함수 호출이 아닙니다. HTTP 메서드, 요청 대상, 상태 코드, 헤더, 본문뿐 아니라 캐시와 인증 의미까지 포함하는 공개 계약입니다. 잘 설계한 API는 정상 응답뿐 아니라 잘못된 입력, 인증 실패, 권한 부족, 존재하지 않는 리소스, 상태 충돌, 내부 오류를 일관되게 구분합니다.

## 목표

- 리소스와 유스 케이스에 맞는 HTTP 메서드와 경로를 선택합니다.
- 요청의 경로·쿼리·헤더·본문을 구분합니다.
- 상태 코드와 일관된 오류 응답 본문을 설계합니다.
- 멱등성, 페이지네이션, 버전 충돌의 기본 계약을 이해합니다.
- 전송 계층과 도메인 계층의 책임을 분리합니다.

## 리소스와 경로

```text
GET    /boards
POST   /boards
GET    /boards/:id
PATCH  /boards/:id
DELETE /boards/:id
GET    /boards/:id/activity
```

경로에는 주로 리소스의 식별자와 관계를, 쿼리에는 필터링·정렬·페이지네이션 조건을 표현합니다.

```text
GET /boards?role=editor&cursor=abc&limit=20
```

모든 작업을 `/doSomething` 형태의 POST 요청으로 만들면 캐시, 멱등성, HTTP 메서드가 제공하는 의미를 활용하기 어렵습니다. 반대로 복잡한 도메인 명령을 무리하게 단순 CRUD 용어에 맞출 필요도 없습니다.

## HTTP 메서드의 기본 의미

| 메서드 | 일반적인 의미 | 반복 요청의 성질 |
|---|---|---|
| GET | 리소스 조회 | 안전하고 멱등해야 함 |
| POST | 컬렉션에 리소스 생성 또는 명령 실행 | 기본적으로 멱등하지 않음 |
| PUT | 리소스 전체 대체 | 같은 요청은 멱등하도록 설계 |
| PATCH | 리소스 일부 변경 | 작업 정의에 따라 달라짐 |
| DELETE | 리소스 삭제 | 반복해도 같은 최종 상태를 목표로 함 |

GET 요청으로 서버 상태를 변경해서는 안 됩니다. 브라우저, 프록시, 크롤러가 사용자의 명시적인 동작 없이 GET 요청을 미리 보낼 수 있습니다.

## 입력 위치

- 경로 매개변수: 어떤 리소스를 대상으로 하는지
- 쿼리: 조회 범위와 표현 방식
- 헤더: 인증, 조건부 요청, 콘텐츠 협상, 추적 정보
- 본문: 생성하거나 변경할 구조화된 데이터

어느 위치에 있든 모두 외부 입력입니다. TypeScript 클라이언트가 만든 요청이라도 서버에서 런타임 검증을 수행해야 합니다.

## 상태 코드

| 상태 | 계약 |
|---:|---|
| 200 | 요청 성공, 응답 본문 있음 |
| 201 | 리소스 생성 성공, 필요하면 `Location` 헤더 제공 |
| 204 | 요청 성공, 응답 본문 없음 |
| 400 | 요청 형식이나 값이 계약에 맞지 않음 |
| 401 | 유효한 인증 정보가 없거나 인증에 실패함 |
| 403 | 사용자 신원은 확인했지만 작업 권한이 없음 |
| 404 | 라우트 또는 외부에서 조회할 수 있는 리소스가 없음 |
| 409 | 현재 상태·버전·고유성 제약과 충돌함 |
| 429 | 허용된 요청 빈도를 초과함 |
| 500 | 예상하지 못한 서버 내부 오류가 발생함 |
| 503 | 서버가 일시적으로 요청을 처리할 준비가 되지 않음 |

모든 실패를 200과 `{ success: false }`로 반환하면 브라우저·프록시·모니터링 도구·클라이언트가 이해하는 HTTP 표준 의미를 잃게 됩니다.

## 일관된 오류 응답 본문

```json
{
  "code": "invalid_request",
  "message": "요청 형식이 올바르지 않습니다.",
  "details": [
    { "path": "title", "reason": "too_long" }
  ],
  "requestId": "req_01..."
}
```

`code`는 클라이언트가 분기할 수 있도록 안정적으로 유지합니다. `message`에는 외부에 공개해도 되는 일반적인 설명을 담습니다. 스택 추적, SQL 문장, 파일 경로, 토큰, 개인정보를 응답에 포함해서는 안 됩니다. 검증 세부 정보도 공개 범위를 정해 변환합니다.

## 리소스 존재 여부와 권한

권한이 없는 사용자가 리소스의 존재 여부를 알아서는 안 되는 제품에서는 403 대신 404를 반환할 수 있습니다. 이는 모든 API에 적용되는 절대적인 보안 규칙이 아니라 외부에 어떤 정보를 공개할지에 관한 계약입니다. 내부 로그에는 실제 판정 원인을 구분해 기록합니다.

## 페이지네이션

큰 컬렉션을 제한 없이 반환해서는 안 됩니다.

```text
GET /activity?cursor=evt_42&limit=50
```

커서는 정렬 기준과 함께 안정적으로 정의해야 합니다. 오프셋 페이지네이션은 조회 도중 항목이 삽입되거나 삭제되면 중복과 누락이 발생할 수 있습니다. 데이터가 적은 관리 화면에서는 오프셋 방식으로 충분할 수 있지만, 선택한 방식의 한계를 명시해야 합니다.

## 버전 충돌

클라이언트가 읽은 버전과 서버의 현재 버전이 같을 때만 변경을 허용할 수 있습니다.

```http
PATCH /boards/42/items/7
If-Match: "12"
```

또는 요청 본문에 `baseVersion`을 포함할 수 있습니다. 오래된 요청은 409 또는 조건부 요청에 맞는 412로 거부하고, 현재 값을 제공하거나 다시 조회할 방법을 알려야 합니다. 마지막 요청이 항상 이기는 방식을 선택한다면 사용자의 변경이 유실될 수 있음을 계약으로 받아들이는 것입니다.

## 멱등성

네트워크 타임아웃이 발생하면 클라이언트는 POST 요청이 서버에서 처리되었는지 알 수 없습니다. 중복 실행이 위험한 명령에는 멱등성 키를 받을 수 있습니다.

```http
Idempotency-Key: 3f3c...
```

서버는 키의 적용 범위, 보관 기간, 같은 키로 다른 본문이 들어왔을 때의 처리 방식, 기존 결과의 재사용 방식을 정의해야 합니다. 헤더 이름만 추가한다고 정확히 한 번만 실행되는 효과가 생기지는 않습니다.

## 콘텐츠 타입과 본문 크기 제한

요청과 응답의 `Content-Type`을 확인하고 예상보다 큰 본문은 제한합니다. JSON 구문 분석 실패와 스키마 검증 실패를 내부적으로 구분하되, 외부에 제공하는 오류 형식은 일관되게 유지합니다.

## 흔한 오류

- GET 요청으로 서버 상태를 변경합니다.
- 모든 오류를 200이나 500으로 반환합니다.
- 검증 라이브러리의 내부 오류 구조를 그대로 노출합니다.
- 컬렉션 조회에 개수 제한이 없습니다.
- 동시 변경을 처리할 버전 계약이 없습니다.
- 타임아웃 뒤 중복 실행이 위험한 POST 요청을 무조건 재시도합니다.

## 완료 기준

- 리소스 경로, HTTP 메서드, 입력 위치를 선택한 이유를 설명합니다.
- 400·401·403·404·409·500 상태를 구분합니다.
- 클라이언트가 분기할 수 있는 안정적인 오류 코드를 제공합니다.
- 컬렉션의 페이지네이션과 동시 변경 계약을 정의합니다.
- 재시도해도 안전한 명령과 그렇지 않은 명령을 구분합니다.
