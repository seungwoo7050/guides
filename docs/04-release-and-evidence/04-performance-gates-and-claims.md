# 성능 기준과 측정 주장

## 목표

성능 목표, 특정 환경에서 얻은 측정값과 아직 검증하지 못한 주장을 구분하고, 정확성 조건을 통과한 실행만 성능 판정에 사용합니다.

## 문제

처리량이 높아도 요청 일부를 버리거나 같은 효과를 두 번 적용했다면 좋은 결과가 아닙니다. 평균 지연 시간만 기록하면 긴 꼬리 지연과 첫 실행 실패를 숨길 수 있습니다.

개발 노트북의 한 번 측정값을 운영 용량으로 일반화하거나, 환경·부하·오류 수를 기록하지 않고 “초당 만 건 처리”라고 쓰면 재현할 수 없는 주장입니다.

## 계약

### 목표와 측정값을 분리합니다

```text
목표: p95 < 200ms, 오류율 < 0.1%, 중복 효과 0
측정: 특정 commit·JDK·CPU·부하에서 얻은 sample
판정: PASS / FAIL / UNVERIFIED
```

목표는 제품 계약이며 측정은 특정 조건의 관찰입니다. 측정 환경이 다르면 직접 비교하지 않습니다.

### 실행 조건을 고정합니다

다음 정보를 함께 남깁니다.

- release manifest 또는 commit
- JDK와 운영체제
- CPU 구조와 사용 가능한 core
- heap과 container limit
- instance·worker·connection pool 수
- 데이터 크기와 초기 상태
- 요청 수, concurrency와 arrival pattern
- warm-up 포함 여부
- 반복 횟수와 실행 순서
- timeout·retry 설정
- fault 주입 여부

한 번에 하나의 가설만 바꿉니다.

### 정확성 gate를 먼저 통과합니다

각 실행에서 다음을 확인합니다.

- 제출한 고유 operation 수
- 최종 완료·거절·실패 수
- 중복 효과 수
- 누락된 결과 수
- queue에서 버린 작업 수
- 외부 효과 수
- projection과 원본의 차이

합계가 맞지 않으면 지연 시간이 빠르더라도 `FAIL`입니다.

### PASS·FAIL·UNVERIFIED를 구분합니다

- `PASS`: 필수 sample과 정확성 근거가 모두 있고 목표를 만족합니다.
- `FAIL`: 측정은 유효하지만 시간·오류·정확성 조건을 만족하지 못합니다.
- `UNVERIFIED`: sample 수, 완료 수, 환경 또는 정확성 근거가 부족해 판정할 수 없습니다.

첫 실행 실패를 뒤의 평균으로 숨기지 않습니다. warm-up을 제외한다면 사전에 규칙을 정하고 운영 시작 경로의 성능은 별도로 검사합니다.

### 병목 주장을 근거와 연결합니다

“DB가 병목이다”라는 주장은 다음 근거가 필요합니다.

- CPU·allocation·lock·I/O profile
- connection pool 대기
- query plan과 실행 시간
- broker lag
- queue age
- dependency latency
- 변경 전후 같은 workload의 결과

여러 설정을 동시에 바꾸면 원인을 분리할 수 없습니다.

## 실패 조건

- 정확성 검사를 하지 않고 처리량만 기록합니다.
- 평균만 보고 p95·p99와 최대값을 숨깁니다.
- 실패한 첫 실행을 제외하고 규칙을 나중에 바꿉니다.
- 오류와 버린 작업을 완료 수에 포함합니다.
- 환경과 release 조합을 기록하지 않습니다.
- sample이 부족한데 PASS 또는 FAIL로 단정합니다.
- 한 번에 여러 설정을 바꾸고 특정 변경의 효과라고 주장합니다.

## 검증

판정기는 다음을 구분해야 합니다.

- 충분한 반복·정확한 완료 수·시간 목표 충족: `PASS`
- 중복 또는 누락이 있음: `FAIL`
- 필수 반복이나 완료 수 근거가 없음: `UNVERIFIED`
- 첫 실행 실패 뒤 나머지만 성공: 규칙에 따라 `FAIL`
- 평균은 빠르지만 최대 또는 p95가 기준 초과: `FAIL`

## 실습

[performance-gate 실습](../../exercises/04-release-and-evidence/04-performance-gate/README.md)은 정확성·반복 수와 시간 기준을 함께 판정합니다.

## 완료 조건

- 목표·측정·판정을 분리해 기록합니다.
- 성능 실행에 release와 환경 정보를 연결합니다.
- 정확성 gate를 성능 gate보다 먼저 적용합니다.
- 근거가 부족한 상태를 `UNVERIFIED`로 남길 수 있습니다.
