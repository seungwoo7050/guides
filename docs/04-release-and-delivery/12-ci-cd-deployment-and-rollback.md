# CI/CD, 배포와 롤백

배포는 `docker compose up -d` 한 줄이 아닙니다. 후보 릴리스를 선택하고 호환성을 검사하고 실행 상태를 바꾼 뒤 사용자 경로를 확인해야 현재 릴리스로 확정할 수 있는 **상태 전이**입니다.

이 장의 목표는 다음 규칙을 구현하는 것입니다.

```text
검증되지 않은 산출물은 운영 배포 후보가 아님
동시에 둘 이상의 배포가 상태를 바꾸지 않음
현재 릴리스는 스모크 테스트 전에는 확정되지 않음
실패하면 원인을 보존한 채 이전 호환 릴리스로 돌아감
DB 변경이 이전 애플리케이션의 실행 가능성을 깨뜨리지 않음
누가 무엇을 언제 배포했는지 기록됨
```

대응 실습은 [`exercises/12-deployment-rollback`](../exercises/12-deployment-rollback/)입니다.

## 1. CI와 CD의 책임 분리

### CI

소스 변경이 배포 가능한 산출물이 될 수 있는지 검증합니다.

```text
포맷·lint
→ 단위·통합 테스트
→ 이미지 빌드
→ 이미지 정책·취약점 검사
→ SBOM·provenance 생성
→ 레지스트리 push
→ 다이제스트와 매니페스트 생성
```

### Delivery

검증된 산출물을 특정 환경의 배포 후보로 만듭니다.

```text
릴리스 승인
→ 환경별 설정·비밀값 존재 확인
→ 스테이징 또는 카나리 검증
→ 운영 배포 대기
```

### Deployment

실제 운영 환경의 실행 상태를 바꿉니다.

```text
배포 잠금
→ 사전 검사
→ 백업 또는 복구 지점 확인
→ 마이그레이션
→ 이미지 pull
→ 새 컨테이너 시작
→ 준비 상태 확인
→ 외부 스모크 테스트
→ 릴리스 확정
```

세 경계를 하나의 워크플로에 구현하더라도 논리적 책임은 분리합니다.

## 2. 배포 입력은 릴리스 매니페스트 하나

배포 스크립트가 브랜치나 변경 가능한 태그를 직접 해석하지 않게 합니다.

나쁜 입력:

```text
main
latest
현재 디렉터리의 Dockerfile
```

좋은 입력:

```text
릴리스 매니페스트 URI 또는 검증된 파일
```

매니페스트에서 정확한 다이제스트, 소스 리비전, 스키마 호환 범위, 스모크 테스트 경로를 읽습니다.

배포 시점에 이미지 태그를 다시 다이제스트로 해석하면 태그가 검증 이후 바뀌었을 수 있습니다.

## 3. 배포 동시성

두 배포가 동시에 실행되면 다음 경쟁이 생길 수 있습니다.

- 서로 다른 이미지 pull과 컨테이너 재생성
- 마이그레이션 중복 실행
- `current-release.json` 덮어쓰기
- 한 배포의 스모크 테스트가 다른 배포를 검사
- 롤백 대상이 잘못 기록됨

환경별 배포 잠금을 둡니다.

```text
운영 환경에는 한 번에 하나의 상태 변경 배포만 허용
```

CI 제품의 동시성 제어 기능, 호스트 파일 잠금, 중앙 잠금 중 하나를 사용할 수 있습니다. 잠금의 만료·소유자·강제 해제 절차를 문서화합니다.

## 4. 배포 전 검사

상태를 바꾸기 전에 실패할 수 있는 검사를 최대한 수행합니다.

### 산출물

- 매니페스트 형식과 서명·provenance가 유효한가?
- 모든 이미지 다이제스트를 레지스트리에서 pull할 수 있는가?
- 아키텍처가 호스트와 맞는가?
- 필요한 이전 릴리스가 레지스트리에 남아 있는가?

### 환경

- 디스크와 inode 여유가 있는가?
- Docker daemon이 정상인가?
- 설정 스키마와 비밀값 버전이 맞는가?
- 공개 포트가 예상 프로세스에 의해 사용 중인가?
- 백업 또는 복구 지점이 최근에 성공했는가?

### 호환성

- 현재 DB 스키마가 후보 릴리스의 허용 범위 안인가?
- 마이그레이션 뒤 현재 릴리스가 계속 동작할 수 있는가?
- 롤백 릴리스가 마이그레이션 뒤에도 동작하는가?

사전 검사가 실패하면 현재 릴리스를 건드리지 않습니다.

## 5. 마이그레이션과 expand-contract

가장 위험한 롤백 실패는 애플리케이션 이미지는 되돌렸지만 스키마가 이전 코드와 호환되지 않는 경우입니다.

안전한 일반 흐름:

```text
1. Expand
   새 컬럼·테이블·인덱스를 이전 코드와 호환되게 추가
2. Migrate
   새 코드가 기존 구조와 새 구조를 함께 처리
3. Backfill
   기존 데이터를 제한된 배치 단위로 채움
4. Switch
   읽기·쓰기의 기준 원본을 새 구조로 전환
5. Contract
   이전 릴리스가 더 이상 필요 없음을 확인한 뒤 기존 구조 제거
```

한 릴리스에서 컬럼을 즉시 이름 변경하거나 삭제하면 이전 애플리케이션으로 롤백하지 못할 수 있습니다.

모든 마이그레이션이 자동 롤백 가능한 것은 아닙니다. 데이터를 파괴하는 작업은 별도 승인, 백업, 복원 검증을 요구합니다.

## 6. Compose 배포의 상태 전이

단일 호스트 기준선에서 한 가지 구현 흐름은 다음과 같습니다.

```sh
# 1. manifest에서 exact image digest를 환경 파일에 기록
# 2. pull
# 3. config 렌더링 검사
docker compose config >/dev/null
# 4. 필요한 migration 실행
# 5. container 재생성
docker compose up -d --remove-orphans
# 6. 내부 readiness 대기
# 7. 호스트 밖에서 smoke test
```

`docker compose up`의 종료 코드가 0이라고 모든 서비스가 준비된 것은 아닙니다. 준비 상태와 외부 스모크 테스트를 별도로 확인합니다.

Compose가 새 컨테이너를 시작하는 방식은 서비스 구성과 버전에 따라 짧은 중단을 만들 수 있습니다. 무중단이 필수라면 단일 인스턴스 Compose 구성보다 더 강한 배포 구조가 필요합니다.

## 7. 스모크 테스트

스모크 테스트는 가장 중요한 사용자 경로를 작고 안전하게 검사합니다.

최소 구성:

- 공개 DNS 사용
- 인증서 검증 활성화
- 실제 게이트웨이 통과
- 읽기 경로
- 필요한 경우 되돌릴 수 있는 쓰기 경로
- 응답 스키마 또는 핵심 본문 검사
- 명확한 타임아웃

```sh
curl --fail --show-error --silent \
  --max-time 10 \
  https://service.example/api/notes >/dev/null
```

고정 `/healthz`만 검사하면 애플리케이션과 데이터베이스 장애를 놓칠 수 있습니다.

쓰기 스모크 테스트는 운영 데이터를 오염시키지 않도록 전용 계정·네임스페이스·멱등성 키와 정리 절차를 사용합니다.

## 8. 릴리스 확정 지점

다음이 모두 성공하기 전에는 새 릴리스를 `current`로 기록하지 않습니다.

- 컨테이너가 기대한 다이제스트로 실행 중
- 준비 상태 검사 통과
- 외부 스모크 테스트 통과
- 오류율과 핵심 지표가 허용 범위
- 마이그레이션 상태가 기대한 버전

확정할 때 다음 정보를 원자적으로 기록합니다.

```yaml
current: 2026-08-07.1
previous: 2026-08-01.2
activated_at: 2026-08-07T11:00:00Z
manifest_digest: sha256:...
operator: ci://run/1234
```

현재 파일을 먼저 덮어쓰고 스모크 테스트가 실패하면 롤백 대상과 실제 상태가 어긋납니다.

## 9. 자동 롤백의 경계

자동 롤백이 적합한 경우:

- 새 컨테이너가 시작되지 않음
- readiness가 제한 시간 안에 통과하지 않음
- 결정적인 스모크 테스트 실패
- 마이그레이션이 상태 변경 전에 실패함
- 이전 릴리스와 스키마 호환이 확인됨

자동 롤백을 멈추고 사람이 판단해야 하는 경우:

- 파괴적 마이그레이션 일부가 적용됨
- 데이터 정합성 위반 가능성
- 현재와 이전 릴리스 모두 실패
- 외부 의존 서비스 장애
- 보안 사고 또는 자격 증명 유출
- 원인이 불명확한 반복 재배포

롤백을 “무조건 이전 이미지를 실행한다”로 정의하지 않습니다. 애플리케이션, 스키마, 설정, 비밀값의 호환성을 함께 확인합니다.

## 10. 롤백 절차

```text
새 트래픽 또는 추가 변경 중지
→ 증거 보존
→ 현재 실행 다이제스트·스키마 확인
→ 이전 매니페스트 호환성 재검사
→ 이전의 정확한 다이제스트 배포
→ 준비 상태 확인
→ 외부 스모크 테스트
→ 현재 릴리스 기록 복구
→ 사고 또는 배포 실패 기록
```

실패한 후보 컨테이너와 로그를 즉시 모두 지우지 않습니다. 원인 분석에 필요한 정보를 먼저 보존합니다. 다만 사용자 영향이 계속되면 분석보다 완화가 우선입니다.

## 11. 롤포워드

데이터 변경 때문에 롤백이 위험하면 수정 릴리스를 앞으로 배포하는 편이 안전할 수 있습니다.

선택 기준:

- 이전 코드가 현재 스키마를 읽을 수 있는가?
- 데이터 변환을 되돌릴 수 있는가?
- 문제 원인이 작고 수정이 검증됐는가?
- 현재 사용자 영향이 얼마나 큰가?
- 수정 릴리스 준비 시간과 롤백 시간이 어떻게 다른가?

런북에 자동 답을 넣기보다 판단에 필요한 증거를 정의합니다.

## 12. CI/CD 권한

워크플로는 필요한 최소 권한만 가집니다.

분리 예:

```text
검사 작업       소스 읽기
빌드 작업       패키지·이미지 push
attestation 작업 provenance 기록
배포 작업       운영 환경 접근
```

운영 배포는 환경 보호 규칙과 승인을 사용할 수 있습니다. 같은 워크플로를 실행한 사람이 자신의 배포를 승인할 수 있는지는 조직 정책에 맞게 결정합니다.

클라우드나 레지스트리가 지원하면 장기 액세스 키 대신 OIDC로 짧은 수명의 자격 증명을 발급받습니다. OIDC 신뢰 조건은 저장소 이름뿐 아니라 브랜치, 환경과 불변 식별자까지 가능한 범위에서 제한합니다.

외부 CI action이나 플러그인은 가능한 경우 검토된 버전과 변경 불가능한 리비전으로 고정하고 업데이트 절차를 둡니다.

## 13. Self-hosted runner 주의

운영 호스트를 CI 러너로 직접 사용하는 방식은 단순하지만 신뢰 경계를 합칩니다.

- Pull Request의 코드가 호스트에서 실행될 수 있는가?
- 러너 작업 공간에 운영 비밀값이 남는가?
- 이전 작업의 컨테이너·파일이 다음 작업에 영향을 주는가?
- 러너가 침해되면 Docker daemon과 운영 환경 전체를 제어할 수 있는가?

사용해야 한다면 공개되었거나 신뢰할 수 없는 워크플로와 분리하고 일회성 러너 또는 별도 배포 에이전트를 검토합니다.

## 14. 배포 후 관찰 창

스모크 테스트를 통과한 직후 모든 문제가 드러나는 것은 아닙니다.

배포 후 일정 시간 다음을 비교합니다.

- HTTP 오류율
- 지연 시간 백분위수
- 컨테이너 재시작
- 메모리와 CPU
- DB 연결·잠금
- 큐 또는 백그라운드 작업 지연
- 애플리케이션 고유 실패 지표

문제가 생겼을 때 릴리스 마커를 로그와 지표에 연결할 수 있어야 합니다.

## 15. 배포 기록

각 시도마다 성공·실패와 관계없이 기록합니다.

```text
릴리스 ID와 매니페스트 다이제스트
소스 리비전
이미지 다이제스트 목록
시작·종료 시각
승인자와 실행 주체
사전 검사 결과
마이그레이션 결과
준비 상태·스모크 테스트 결과
롤백 여부와 대상
관찰한 오류 링크
```

CI 실행 기록만 유일한 기준 원본이면 보존 기간이 끝난 뒤 증거가 사라질 수 있습니다. 필요한 운영 보존 정책을 정합니다.

## 16. 실습

[`exercises/12-deployment-rollback`](../exercises/12-deployment-rollback/)은 실제 Docker daemon 상태를 바꾸지 않는 배포 상태 머신을 구현합니다.

fixture:

- `v1`: 현재 정상 릴리스
- `v2`: 정상 후보
- `bad`: 스모크 테스트가 실패하는 후보

학습자는 다음 계약을 구현합니다.

1. 사전 검사 실패 시 현재 상태 불변
2. 동시에 하나의 배포만 허용
3. 후보를 스테이징 상태에 둠
4. 준비 상태와 스모크 테스트가 성공한 뒤에만 `current` 확정
5. 실패 시 `previous` 릴리스 복원
6. 모든 전이를 append-only 이벤트 로그에 기록
7. 스키마 비호환이면 자동 롤백 거부

이 상태 머신은 실제 배포 스크립트에서 가장 중요한 순서와 실패 후 상태를 작은 파일 시스템 모델로 검증합니다.
