# 동기·비동기 명령 계약

## 목표

서비스 전체에 하나의 통신 방식을 적용하지 않고, 명령마다 즉시 판정·대기 상태·지연 처리 계약을 선택합니다.

## 문제

“비동기가 확장성이 좋다”거나 “동기가 단순하다”는 이유만으로 통신 방식을 정하면 사용자에게 약속할 결과와 시스템이 실제로 보장하는 결과가 어긋납니다.

동기 호출은 응답을 받은 시점에 판정을 알려 줄 수 있지만 하위 서비스의 지연과 장애를 호출자에게 전파합니다. 비동기 전달은 호출 경로를 짧게 만들 수 있지만 최종 결과가 늦고, 재전달·순서·중간 상태를 계약에 포함해야 합니다.

핵심 질문은 다음입니다.

> 이 명령을 받은 시점에 어떤 결과를 반드시 확정해야 합니까?

## 계약

### 즉시 판정이 필요한 명령

다음 조건에서는 동기 판정이 자연스럽습니다.

- 현재 값이 빠르게 바뀌며 오래된 복제본으로 판단할 수 없습니다.
- 사용자가 다음 행동을 하기 전에 수락·거절을 알아야 합니다.
- 거절이면 어떤 상태도 바뀌지 않아야 합니다.
- 짧은 시간 안에 단일 소유 서비스가 결정할 수 있습니다.

동기 경로에서는 전체 deadline을 먼저 정하고 하위 호출에 남은 시간을 전달합니다. 하위 서비스가 응답하지 않을 때 보수적으로 거절할지, `PENDING`으로 소유권을 넘길지도 명시합니다.

### 지연 처리가 가능한 명령

다음 조건에서는 비동기 처리가 적합할 수 있습니다.

- 통계, 알림처럼 핵심 판정 이후 처리할 수 있습니다.
- 호출자가 대기 상태와 결과 조회를 받아들일 수 있습니다.
- 재전달과 순서 변경을 처리할 수 있습니다.
- 처리량을 흡수하기 위한 bounded queue와 지연 한도가 있습니다.

비동기 API가 `202 Accepted`를 반환한다면 “처리가 끝났다”가 아니라 “시스템이 이 작업의 진행 책임을 받아들였다”는 뜻이어야 합니다. 작업 식별자와 조회 경로가 필요합니다.

### 혼합 경로를 명령 단위로 기록합니다

하나의 사용자 요청 안에서도 경로가 나뉠 수 있습니다.

```text
수량 가능 여부 판정: 동기
예약 기록과 Outbox: 로컬 transaction
통계와 알림: 비동기 event
읽기 모델 반영: 비동기 projection
```

“reservation-service는 비동기 서비스”처럼 서비스 단위로 규정하면 명령별 실패 계약이 사라집니다. 결정 기록에는 다음을 남깁니다.

- 즉시 필요한 결과
- 허용 가능한 최대 지연
- 의존성 실패 시 상태
- 결과 조회 방법
- 재시도와 취소 방법
- 바뀌면 안 되는 상태

### 원격 호출 중 transaction을 열어 두지 않습니다

데이터베이스 잠금을 잡은 채 원격 서비스 응답을 기다리면 네트워크 지연이 로컬 잠금 시간으로 전파됩니다. 일반적으로 다음처럼 나눕니다.

```text
짧은 transaction으로 PENDING 기록
→ transaction 종료
→ 원격 명령
→ 결과에 따라 짧은 transaction으로 상태 전이
```

이 구조는 중간 상태를 만들지만, 그 상태를 명시적으로 복구할 수 있습니다.

## 실패 조건

- `202`를 반환하면서 작업 식별자와 조회 경로가 없습니다.
- 정책 서비스가 끊겼는데 먼저 수량을 변경합니다.
- 비동기 대기열이 무제한이며 최대 지연을 측정하지 않습니다.
- 동기 경로의 하위 timeout 합이 전체 deadline보다 깁니다.
- 원격 호출 동안 DB transaction과 잠금을 유지합니다.
- “메시지를 발행했다”를 최종 업무 성공으로 반환합니다.

## 검증

동기 실패 검사는 **부정 불변 조건**을 포함해야 합니다.

```text
정책 서비스 응답 없음
→ 요청은 REJECTED 또는 PENDING
→ reserved_units는 증가하지 않음
```

비동기 수락 검사는 진행 책임을 확인합니다.

```text
202 + operation_id
→ 조회 시 PENDING
→ 처리 뒤 ACCEPTED 또는 REJECTED
→ 최대 처리 시간 초과 시 재조정 대상
```

## 완료 조건

- 명령별 동기·비동기 선택 이유를 기록할 수 있습니다.
- `202 Accepted`가 약속하는 범위를 설명할 수 있습니다.
- 동기 의존성 실패 시 바뀌면 안 되는 상태를 검사합니다.
- 원격 호출과 로컬 transaction의 수명을 분리합니다.
