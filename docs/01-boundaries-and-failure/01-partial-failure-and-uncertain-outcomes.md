# 부분 실패와 확정할 수 없는 결과

## 목표

원격 호출에서 `성공`과 `실패`만으로 결과를 표현할 수 없는 이유를 이해하고, `UNKNOWN` 상태와 조회·재조정 경로를 설계합니다.

## 문제

로컬 함수가 예외를 던지면 일반적으로 호출자는 해당 함수의 결과가 만들어지지 않았다고 판단할 수 있습니다. 원격 호출은 다릅니다.

```text
클라이언트가 요청을 보냅니다.
→ 서버가 상태를 저장합니다.
→ 서버가 성공 응답을 보냅니다.
→ 네트워크가 응답을 잃습니다.
```

클라이언트는 시간 초과를 관찰하지만 서버의 상태는 이미 바뀌었습니다. 같은 요청을 새 식별자로 다시 보내면 두 번째 상태 변경이 생길 수 있습니다. 반대로 시간 초과를 최종 실패로 기록하면 실제로 성공한 결과를 사용자에게 실패라고 보여 줄 수 있습니다.

따라서 원격 호출의 관찰 결과와 업무 처리 결과를 분리해야 합니다.

```text
호출 관찰: 응답을 받음 / 연결 실패 / 시간 초과
업무 결과: ACCEPTED / REJECTED / PENDING / UNKNOWN
```

`UNKNOWN`은 오류 메시지를 부드럽게 표현한 값이 아닙니다. **이미 처리되었을 가능성과 처리되지 않았을 가능성이 모두 남아 있어 다시 확인해야 하는 상태**입니다.

## 계약

### 연산 식별자를 먼저 만듭니다

재시도할 때 같은 업무 연산이라는 사실을 서버가 알아야 합니다. 식별자는 네트워크 호출마다 새로 만들지 않고 사용자가 시작한 업무 연산의 수명 동안 유지합니다.

```text
operation_id = 사용자 또는 상위 서비스가 시작한 한 번의 업무 의도
attempt_id   = 같은 연산을 전달하기 위한 개별 호출
```

서버는 `operation_id`와 입력 지문을 함께 저장합니다.

- 같은 `operation_id`와 같은 입력이 다시 오면 이전 결과를 반환합니다.
- 같은 `operation_id`에 다른 입력이 오면 충돌로 거절합니다.
- 결과가 아직 확정되지 않았다면 현재 상태를 반환합니다.

### 명령과 조회를 분리합니다

응답을 잃은 호출자는 같은 명령을 무한히 반복하는 대신 결과 조회 경로를 사용할 수 있어야 합니다.

```text
POST /reservations
Idempotency-Key: op-123

GET /operations/op-123
```

조회 결과는 적어도 다음을 구분합니다.

- `PENDING`: 시스템이 처리를 소유하고 계속 진행합니다.
- `ACCEPTED`: 상태 변경이 적용되었습니다.
- `REJECTED`: 상태 변경이 적용되지 않았으며 이유가 확정되었습니다.
- `UNKNOWN`: 처리 주체도 결과를 확정하지 못해 재조정이 필요합니다.

### 취소와 시간 초과를 구분합니다

호출자가 기다리기를 중단했다고 서버 작업이 자동으로 취소되는 것은 아닙니다. 네트워크 클라이언트의 timeout은 관찰 기한이고, 서버 명령의 deadline과 cancellation은 별도의 계약입니다.

서버가 취소를 지원한다면 다음을 정해야 합니다.

- 취소가 가능한 상태
- 이미 적용된 변경을 되돌릴지
- 취소와 완료가 경쟁할 때 우선하는 상태
- 취소 요청 자체의 멱등성 키
- 최종 결과 조회 방법

## 실패 조건

다음 구현은 불확실한 결과를 숨깁니다.

- timeout을 곧바로 업무 실패로 저장합니다.
- 재시도마다 새 멱등성 키를 만듭니다.
- 같은 키에 다른 입력을 허용합니다.
- 응답이 없으면 상태를 조회하지 않고 다시 변경합니다.
- 호출 취소를 서버 상태 변경의 취소와 동일하게 봅니다.
- `UNKNOWN`을 영구 상태로 남기고 담당 재조정 작업을 두지 않습니다.

## 검증

검사는 응답 코드보다 상태 변경 횟수를 봐야 합니다.

```text
서버가 저장한 직후 응답을 잃습니다.
→ 클라이언트가 같은 operation_id로 결과를 조회합니다.
→ ACCEPTED를 확인합니다.
→ 같은 명령을 다시 보내도 변경 횟수는 1입니다.
```

같은 키에 다른 입력을 보내면 이전 결과를 재사용하지 않고 명시적으로 거절되어야 합니다.

## 실습

[uncertain-outcome 실습](../../exercises/01-boundaries-and-failure/01-uncertain-outcome/README.md)은 저장 직후 응답이 사라지는 상황을 만듭니다. skeleton은 timeout을 최종 실패처럼 반환하며, reference는 같은 연산 키로 결과를 조회합니다.

## 완료 조건

- 원격 호출의 관찰 실패와 업무 실패를 구분할 수 있습니다.
- `PENDING`, `REJECTED`, `ACCEPTED`, `UNKNOWN`의 책임 주체를 설명할 수 있습니다.
- 같은 연산 식별자를 재시도와 조회에 사용합니다.
- 응답 유실 뒤에도 업무 효과가 하나만 남는 검사를 작성할 수 있습니다.
