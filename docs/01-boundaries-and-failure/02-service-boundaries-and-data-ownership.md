# 서비스 경계와 데이터 소유권

## 목표

저장소 수나 배포 단위보다 먼저 정해야 하는 데이터의 정본, 변경 권한과 의존 방향을 설계합니다.

## 문제

서비스를 나누었는데 두 서비스가 같은 테이블을 직접 수정한다면 실행 파일만 분리되었을 뿐 변경 계약은 분리되지 않았습니다.

```text
reservation-service ─┐
                     ├─ shared.reservations UPDATE
admin-service ───────┘
```

이 구조에서는 다음 질문에 일관되게 답하기 어렵습니다.

- 어떤 서비스의 검증 규칙이 최종 규칙입니까?
- 두 배포 버전이 다른 동안 어느 스키마를 사용합니까?
- 한 서비스의 transaction이 다른 서비스의 잠금에 어떤 영향을 줍니까?
- 장애 뒤 어느 서비스가 잘못된 값을 복구합니까?

서비스 경계는 “이 데이터에 대한 최종 결정을 누가 내리는가”에서 시작합니다.

## 계약

### 정본과 변경 주체를 하나로 둡니다

각 업무 상태에는 다음을 기록합니다.

| 항목 | 질문 |
|---|---|
| 정본 | 최종 업무 상태를 보관하는 곳은 어디입니까? |
| 변경 주체 | 상태 전이를 승인하고 기록하는 서비스는 어디입니까? |
| 읽기 소비자 | 복제본 또는 API로 상태를 읽는 서비스는 어디입니까? |
| 지연 허용 | 복제본이 늦을 수 있는 최대 시간은 얼마입니까? |
| 복구 주체 | 불일치를 발견하고 수렴시키는 작업은 어디에 있습니까? |

다른 서비스는 소유 서비스의 명령 API나 이벤트를 통해 변경을 요청합니다. 읽기 편의를 위해 복제본을 만들 수 있지만, 복제본은 쓰기 판정의 정본이 아닙니다.

### 업무 불변 조건과 함께 경계를 정합니다

같은 transaction 안에서 항상 지켜야 하는 불변 조건을 서로 다른 서비스로 분리하면 네트워크를 건너는 조정이 필요합니다.

예를 들어 “가용 수량은 음수가 될 수 없다”는 조건을 inventory 서비스가 소유한다면 reservation 서비스는 inventory 테이블을 직접 줄이지 않습니다. reservation 서비스는 수량 예약 명령을 보내고, inventory 서비스가 수락 또는 거절을 결정합니다.

경계가 적절한지 판단할 때는 다음을 봅니다.

- 함께 바뀌어야 하는 상태
- 같은 규칙으로 보호해야 하는 불변 조건
- 독립적인 배포와 확장이 실제로 필요한지
- 장애와 지연을 감수할 만큼 조직적 소유권이 분명한지

### 조정자와 참여자를 구분합니다

조정자는 여러 명령의 순서와 전체 업무 상태를 관리합니다. 참여 서비스는 자신의 데이터와 불변 조건만 변경합니다.

조정자가 참여자의 데이터베이스를 직접 수정하면 보상과 재조정의 경계가 사라집니다. 참여자가 다른 참여자의 내부 상태를 조회해 결정하면 숨은 순환 의존이 생깁니다.

```text
오케스트레이터: 전체 진행 상태와 다음 명령
inventory: 수량 불변 조건
payment: 결제 승인과 취소
notification: 전달 시도와 결과
```

### 계약 모듈의 의존 방향을 고정합니다

공유 이벤트 타입이나 API 스키마는 서비스 구현을 참조하지 않습니다.

```text
service implementation → published contract
published contract      -X→ service implementation
```

공통 라이브러리에 업무 구현을 계속 추가하면 공유 데이터베이스와 비슷한 배포 결합이 생깁니다. 계약에는 외부에 약속한 형식과 의미만 둡니다.

## 실패 조건

- 두 서비스가 같은 테이블의 쓰기 권한을 가집니다.
- 읽기 모델을 최신 정본처럼 사용해 쓰기 판정을 합니다.
- 조정자가 참여 서비스의 DB를 직접 보정합니다.
- 이벤트 타입 모듈이 서비스 내부 entity나 repository를 참조합니다.
- 서비스 분리의 비용을 고려하지 않고 모든 모듈을 네트워크 경계로 바꿉니다.
- 복제 데이터의 지연과 재구축 경로가 없습니다.

## 검증

설계 검토에서는 구성도보다 명령과 상태 표를 사용합니다.

```text
명령: ReserveInventory
정본: inventory-service
입력: operation_id, item_id, units
가능 결과: ACCEPTED / REJECTED / PENDING
부정 불변 조건: REJECTED이면 reserved_units는 증가하지 않음
복구: operation_id로 결과 조회
```

각 상태 변경에 유일한 주체를 지정할 수 없다면 경계가 아직 완성되지 않은 것입니다.

## 실습

[service-boundary 실습](../../exercises/01-boundaries-and-failure/02-service-boundary/README.md)은 데이터 집합마다 writer가 소유자 하나인지, 등록되지 않은 서비스 참조와 동기 의존 순환이 없는지 검사합니다. 이후 [request-decision](../../exercises/01-boundaries-and-failure/03-request-decision/README.md)과 [통합 과제](../05-capstone.md)에서는 이 경계를 실제 상태 변경에 적용합니다.

## 완료 조건

- 데이터별 정본과 유일한 변경 주체를 표로 작성할 수 있습니다.
- 복제본의 지연과 재구축 책임을 명시할 수 있습니다.
- 조정자와 참여 서비스의 책임을 구분할 수 있습니다.
- 모듈 경계로 충분한 경우와 서비스 분리가 필요한 경우를 설명할 수 있습니다.
