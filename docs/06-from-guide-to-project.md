# 가이드에서 실제 프로젝트로 이동하기

가이드 완료는 시작점이다. 실제 역량은 코드베이스의 역사, 불완전한 요구사항, 운영 제약과 다른 사람의 리뷰를 반복해서 경험할 때 형성된다.

브랜치 완료는 한 학습 범위의 종료 능력을 확인한 것이고, 트랙 완료는 목표 업무의 필수 브랜치들을 연결한 것이다. 어느 쪽도 실제 프로젝트 완료를 의미하지 않는다. 프로젝트에서는 실제 사용자·유지보수자의 요구, 기존 상태, 리뷰, 배포와 후속 책임까지 다뤄야 한다.

## 이동 단계

### 1. 기준 구현을 보지 않고 누적 최종 실습 완성

- 문서와 공개 계약만 사용한다.
- 실패 메시지와 관측 결과를 먼저 읽는다.
- reference는 구현 뒤 설계 비교에만 사용한다.
- 이름이 capstone이 아니더라도 브랜치의 핵심 능력을 함께 요구하는 동등한 누적 과제를 사용한다.

### 2. 작은 독립 프로젝트

브랜치의 누적 최종 실습과 동일한 핵심 기술을 쓰되 문제와 데이터는 바꾼다.

- 기능 수를 늘리기보다 실패 조건을 구체화한다.
- 설치·실행·검증 명령을 처음 보는 사람이 재현할 수 있게 한다.
- 성능·보안·복구 주장은 측정 또는 테스트로 고정한다.

### 3. 오픈소스의 문서·테스트 변경

처음부터 핵심 기능을 노리지 않는다.

- 깨진 링크와 예제
- 재현 가능한 작은 버그
- 누락된 경계 테스트
- 오류 메시지와 진단 개선
- 문서와 실제 동작의 불일치

이 단계의 목표는 프로젝트의 기여 규칙, 빌드, 테스트와 리뷰 문화를 복원하는 것이다.

### 4. 버그 재현과 최소 수정

```text
증상 수집
→ 최소 재현
→ 마지막 정상 상태와 첫 실패 상태 분리
→ root cause 가설
→ 수정 전 실패 테스트
→ 최소 패치
→ 회귀·호환성 검사
```

수정 코드보다 재현과 실패 테스트가 먼저다.

### 5. 반복 기여

같은 하위 시스템에서 세 번 이상 변경한다.

- 첫 변경: 구조와 검증 명령을 배운다.
- 두 번째 변경: 인접 상태와 호환성을 이해한다.
- 세 번째 변경: 반복 문제와 설계 부채를 발견한다.

이 지점부터 문서에서 배운 개념이 프로젝트의 실제 책임과 연결된다.

### 6. 운영 또는 사용자 피드백

가능하면 다음 중 하나를 경험한다.

- 실제 사용자 입력과 오류
- 배포·rollback
- 장애 대응과 복구
- 성능·용량 변화
- 보안 보고와 패치
- 데이터 migration과 backfill

운영 접근이 없는 오픈소스라면 issue·release·호환성·성능 회귀를 통해 유사한 책임을 경험한다.

## 프로젝트 선택 기준

좋은 다음 프로젝트는 다음 조건을 만족한다.

- 실행과 검증 방법이 문서화돼 있다.
- issue와 Pull Request 기록을 읽을 수 있다.
- 작은 변경이 실제 사용자 또는 유지보수자에게 가치가 있다.
- 자동 검사나 반복 가능한 사람 검토처럼 결과를 다시 확인할 근거가 있다.
- 한 번의 기여 뒤 인접 문제로 확장할 여지가 있다.

피해야 할 프로젝트:

- 설치만으로 대부분의 시간이 소모되고 학습 목표와 무관하다.
- 정상 결과의 판단 기준을 기록하거나 다른 사람과 재현할 수 없다.
- 핵심 상태와 실패 조건이 외부 서비스에 완전히 숨겨져 있다.
- 사용 허가와 공격 범위가 불명확한 보안 대상이다.

## 기록해야 할 결과

프로젝트마다 다음을 남긴다.

```text
문제와 사용자 영향
초기 상태와 재현 절차
원인과 거부한 가설
변경한 상태·소유권·실패 계약
추가한 검사와 보장 범위
배포·호환성·잔여 위험
다음에 조사할 경계
```

커밋 수나 코드 줄 수보다 이 기록이 역량의 깊이를 더 잘 보여준다.

## 다음 브랜치를 추가할 시점

다음 중 하나가 반복될 때만 인접 브랜치로 이동한다.

- 같은 계층의 원인을 세 번 이상 제대로 설명하지 못한다.
- 다른 팀과의 경계에서 문제를 반복적으로 잘못 전달한다.
- 성능·보안·복구 주장을 검증할 방법이 없다.
- 현재 분야에서 맡고 싶은 역할이 실제로 다음 브랜치를 요구한다.

막연한 불안 때문에 모든 기반 브랜치를 선행하지 않는다.
