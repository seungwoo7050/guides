# 계층별 네트워크 장애 분리

네트워크 장애 조사의 목표는 익숙한 원인을 빨리 선택하는 것이 아니라 마지막으로 성공한 경계와 처음 실패한 경계 사이를 재현 가능한 증거로 좁히는 것입니다. “DNS 같습니다”, “방화벽 같습니다”, “서버가 느립니다”와 같은 문장은 가설일 뿐이며 관찰 결과와 분리해서 기록해야 합니다.

## 학습 목표

- 요청 계약과 관찰 위치를 고정한 뒤 마지막 성공·첫 실패 경계를 결정합니다.
- 관찰, 해석, 가설, 변경과 rollback 증거를 분리합니다.

## 선행 개념

앞선 링크·IP·전송·응용 경계와 각 계층에서 얻을 수 있는 대표 관찰 명령을 알고 있어야 합니다.

## 먼저 요청 계약을 고정합니다

같은 이름과 포트라도 호스트, 컨테이너, VPN, 네임스페이스와 브라우저에서 resolver와 route가 다를 수 있습니다. 실험을 시작하기 전에 다음 값을 고정합니다.

```text
클라이언트 위치와 프로세스
실행 네임스페이스 또는 컨테이너
요청한 이름·주소·포트
전송·암호화·응용 프로토콜
시작 시각과 전체 기한
기대한 응답
실제 오류와 발생 시각
재현 입력과 반복 횟수
```

한 번의 성공과 한 번의 실패가 섞이면 같은 실험인지 확인할 수 없습니다. 주소 후보, 연결 재사용, proxy, VPN과 캐시를 가능한 범위에서 고정합니다.

## 관찰과 해석을 분리합니다

조사 기록의 한 행은 다음 네 항목을 가집니다.

| 항목 | 질문 |
|---|---|
| 관찰 | 실제 출력·패킷·상태는 무엇인가요? |
| 위치 | 어느 프로세스·인터페이스·홉에서 관찰했나요? |
| 해석 | 이 관찰이 어떤 가설을 지지하거나 반증하나요? |
| 다음 검사 | 불확실성을 가장 많이 줄이는 읽기 전용 검사는 무엇인가요? |

예시는 다음과 같습니다.

| 시간 | 위치 | 관찰 | 해석 | 다음 검사 |
|---|---|---|---|---|
| 12:00:00.100 | 클라이언트 | A·AAAA 응답 수신 | 이름 해석 성공 | 실제 선택 주소 확인 |
| 12:00:00.110 | 클라이언트 | `/0` 경로와 게이트웨이 선택 | 로컬 route 존재 | 이웃 상태 확인 |
| 12:00:00.120 | 클라이언트 | SYN 세 번, 응답 없음 | 로컬 송신 확인 | 게이트웨이 이후 캡처 |
| 12:00:03.200 | 서버 경계 | SYN 미관찰 | 중간 경로·정책 후보 | 홉별 계수기 확인 |

관찰 열에는 “방화벽이 막았습니다”가 아니라 “SYN이 클라이언트에서 나갔지만 서버 경계에서 보이지 않았습니다”처럼 씁니다.

## 1. 이름 해석과 주소 후보

다음을 확인합니다.

- 어느 resolver가 질의를 받았나요?
- A, AAAA와 HTTPS 레코드 가운데 무엇을 받았나요?
- hosts 파일, 로컬 cache와 부정 cache가 개입했나요?
- NXDOMAIN, SERVFAIL, 응답 없음 가운데 무엇인가요?
- 클라이언트가 실제로 선택하고 시도한 주소는 무엇인가요?

숫자 주소 연결이 성공하고 이름만 실패하면 DNS와 주소 선택에 집중합니다. 숫자 주소도 실패하면 이름 해석을 반복하지 말고 경로와 전송 단계로 이동합니다.

## 2. 로컬 경로와 출발지 선택

다음을 기록합니다.

- 선택된 routing table과 prefix
- next hop과 출력 interface
- 실제 출발지 주소
- 정책 기반 경로, VRF, VPN과 namespace
- IPv4·IPv6 가운데 선택한 주소 체계

전체 라우팅 표에 기본 경로가 존재해도 해당 목적지와 namespace에서 실제 선택되었다는 뜻은 아닙니다. Linux에서는 `ip route get`, macOS에서는 `route -n get`과 같이 특정 목적지를 질의한 결과를 우선합니다.

## 3. 다음 홉과 링크

현재 링크에서 필요한 대상은 원격 서버의 MAC 주소가 아니라 route가 선택한 다음 홉입니다. 다음 증거를 확인합니다.

- 출력 interface의 링크 상태와 VLAN
- 다음 홉의 ARP·Neighbor Discovery 상태
- ARP Request 또는 Neighbor Solicitation 송신
- Reply 또는 Neighbor Advertisement 수신
- interface 오류와 폐기 계수기

neighbor entry가 존재한다는 사실만으로 현재 도달 가능하다고 단정하지 않습니다. 상태, 갱신 시각과 실제 프레임 송수신을 함께 봅니다.

## 4. 중간 전달과 MTU

다음을 확인합니다.

- TTL 또는 Hop Limit가 어느 위치에서 줄어드나요?
- 어느 홉까지 패킷과 계수기 증거가 있나요?
- 작은 payload와 큰 payload의 결과가 다른가요?
- ICMP Packet Too Big 또는 fragmentation needed가 돌아오나요?
- 터널 헤더를 포함한 실제 경로 MTU가 얼마인가요?

작은 요청은 성공하지만 큰 TLS 응답에서 멈추고 필요한 ICMP도 보이지 않으면 MTU black hole을 후보로 둡니다. `ping` 하나의 성공으로 모든 packet 크기와 전송 프로토콜이 정상이라고 판단하지 않습니다.

## 5. 전송 계층

TCP에서는 다음 사건을 구분합니다.

```text
SYN을 보내지 못함
SYN 전송 뒤 응답 없음
RST 수신
SYN/ACK 뒤 마지막 ACK 누락
ESTABLISHED 뒤 sequence 진행 중단
zero window
반복 재전송과 RTO
FIN·RST에 의한 종료
```

UDP에서는 다음을 확인합니다.

```text
데이터그램 송신·수신
ICMP 오류
NAT mapping과 idle timeout
응답 경로의 대칭성
애플리케이션 메시지 ID와 재시도
```

TCP timeout은 서버가 요청을 처리하지 않았다는 증거가 아닙니다. 응답이 유실되었거나 중간 장비가 상태를 버렸을 수 있습니다. 처리 결과를 확정하는 업무 계약은 애플리케이션과 분산 시스템에서 별도로 설계합니다.

## 6. TLS와 응용 프로토콜

전송 연결 뒤 다음 경계를 분리합니다.

- SNI가 의도한 이름인가요?
- 인증서 체인과 호스트 이름 검증 중 무엇이 실패했나요?
- 협상한 TLS 버전과 ALPN은 무엇인가요?
- HTTP 버전, 상태 코드와 redirect는 무엇인가요?
- 인증 실패와 권한 부족 가운데 무엇인가요?

TCP handshake 성공은 TLS 성공을 보장하지 않고, TLS 성공은 HTTP 성공을 보장하지 않으며, HTTP `200`도 업무 상태가 정확하다는 증거는 아닙니다.

## 마지막 성공과 첫 실패를 선언합니다

충분한 증거를 모으면 다음 형식으로 결론을 기록합니다.

```text
마지막 성공 계층: route
성공 증거: 192.0.2.10 목적지에 eth0, next hop 192.0.2.1 선택
첫 실패 계층: neighbor
실패 증거: ARP Request 3회 송신, Reply 없음, entry FAILED
아직 확인하지 않은 영역: 스위치 VLAN, 게이트웨이 interface 상태
다음 읽기 전용 검사: 게이트웨이 포트와 동일 시각 캡처
```

증거가 부족하면 `UNKNOWN`으로 남깁니다. 불확실한 상황에서 특정 제품이나 팀을 원인으로 확정하지 않습니다.

## 변경 전 안전 계약

설정 변경 전에 다음을 준비합니다.

1. 변경하려는 상태와 예상 효과를 적습니다.
2. 현재 출력과 패킷 증거를 보존합니다.
3. 영향받는 interface, namespace, rule과 사용자를 적습니다.
4. 되돌리기 명령과 확인 조건을 준비합니다.
5. 한 번에 한 변수만 변경합니다.
6. 변경 뒤 원래 증상뿐 아니라 인접 경로의 회귀도 검사합니다.

패킷 캡처와 방화벽 변경은 권한과 개인정보 범위를 확인한 격리 환경에서 수행합니다. [안전한 실험 범위](../../reference/network-safety.md)를 먼저 확인합니다.

## 경로 진단 exercise

[경로 진단 실습](../../exercises/path-diagnosis/README.md)은 DNS부터 HTTP까지의 증거를 JSON fixture로 제공하고 다음 결과를 구현하게 합니다.

```text
정상 경로
NXDOMAIN
route 누락
neighbor 해석 실패
MTU black hole
TCP timeout
TLS 이름 불일치
HTTP 권한 거부
```

학습자 구현은 입력 단계의 순서와 모순을 검증하고, 첫 실패 계층, 근거와 다음 검사를 구조화된 결과로 반환해야 합니다. 실제 네트워크를 변경하지 않으므로 모든 플랫폼에서 결정적으로 실행할 수 있습니다.

## 모델의 한계

fixture 하나는 실제 분산 경로의 모든 시각과 관찰 지점을 표현하지 않습니다. ECMP, 비대칭 라우팅, 중간 proxy, anycast, 연결 재사용과 캡처 누락은 동일한 증상을 다른 원인으로 만들 수 있습니다. 실습 분류를 운영 장애에 그대로 대입하지 말고 실제 위치와 시각의 증거를 추가합니다.

## 연결 실습

[계층별 경로 진단](../../exercises/path-diagnosis/README.md)에서 정상과 일곱 실패 fixture를 분류하고 모순된 trace를 거부합니다.

## 완료 기준

- 재현 입력, 실행 위치와 시각을 포함한 요청 계약을 작성합니다.
- 마지막 성공과 첫 실패를 원본 관찰값으로 뒷받침합니다.
- 변경 전에 반증 조건과 rollback 검증을 명시하고 자동 분류의 한계를 기록합니다.
