# DNS, HTTP, TLS와 QUIC

웹 요청 하나는 이름 해석, 주소 후보 선택, IP 경로, 전송 연결, 암호화 협상과 HTTP 메시지 처리 경계를 차례로 통과합니다. 이 장은 HTTP 애플리케이션을 설계하는 방법보다 네트워크 프로토콜이 서로 어떤 입력을 넘기고 어느 단계에서 어떤 실패 증거를 남기는지 설명합니다.

## 학습 목표

- DNS, 경로, 전송, TLS와 HTTP 성공을 독립된 경계로 기록합니다.
- 주소 후보, ALPN과 fallback이 최종 결과를 만드는 과정을 추적합니다.

## 선행 개념

[UDP와 TCP 계약](../03-transport/01-udp-and-tcp-service-contracts.md)과 인증서의 호스트 이름 검증 개념을 알고 있어야 합니다.

## DNS는 이름을 여러 종류의 데이터로 해석합니다

애플리케이션의 스텁 리졸버는 재귀 리졸버에 질의하고, 재귀 리졸버는 캐시가 없으면 루트, TLD와 권한 서버를 따라 답을 구할 수 있습니다. 실제 구성은 전달 리졸버, Split-Horizon DNS, hosts 파일과 프로세스별 캐시 때문에 달라질 수 있습니다.

대표 레코드의 역할은 다음과 같습니다.

| 레코드 | 네트워크 경로에서의 의미 |
|---|---|
| A | 이름에 대응하는 IPv4 주소 후보 |
| AAAA | 이름에 대응하는 IPv6 주소 후보 |
| CNAME | 다른 canonical 이름으로 이어지는 alias |
| MX | mail exchanger와 우선순위 |
| NS | 영역의 권한 네임 서버 |
| TXT | 텍스트 기반 정책과 검증 데이터 |
| HTTPS | 서비스 종단점, ALPN과 주소 힌트 등의 정보 |

TTL은 리졸버가 답을 캐시할 수 있는 시간을 안내합니다. 애플리케이션, 운영체제, 브라우저와 중간 리졸버가 서로 다른 캐시를 둘 수 있으므로 권한 레코드를 바꾼 직후 모든 클라이언트가 동시에 새 값으로 전환되지는 않습니다. 존재하지 않는 이름에 대한 부정 응답도 캐시될 수 있습니다.

DNS는 전통적으로 UDP와 TCP 53번 포트를 사용하며 응답 크기, truncation과 전송 정책에 따라 TCP를 사용할 수 있습니다. DNS over TLS와 DNS over HTTPS는 암호화된 다른 전송 경로를 사용합니다. “DNS는 항상 UDP입니다”라는 설명은 정확하지 않습니다.

## 주소 후보 선택은 DNS 응답 뒤에도 계속됩니다

A와 AAAA가 모두 있으면 클라이언트는 주소 체계, 실제 route와 연결 진행 상황을 고려해 후보를 시도할 수 있습니다. DNS 응답의 첫 주소와 실제 연결에 성공한 주소가 같다고 가정하지 않습니다.

장애 기록에는 다음을 남깁니다.

```text
질의한 이름과 resolver
반환된 A·AAAA·HTTPS 레코드
캐시 출처와 남은 TTL
실제로 선택한 주소 후보
각 후보의 시작 시각과 실패 신호
최종 선택 주소와 출력 인터페이스
```

숫자 주소 접속이 성공하고 이름만 실패하면 DNS와 주소 선택을 우선 확인합니다. 숫자 주소도 실패하면 경로, 이웃, MTU와 전송 단계로 이동합니다.

## HTTP 의미와 전송 매핑을 분리합니다

HTTP는 메서드, 대상, 필드, 상태 코드와 표현의 의미를 정의합니다. HTTP/1.1, HTTP/2와 HTTP/3은 같은 의미를 서로 다른 프레이밍과 전송 방식으로 전달할 수 있습니다.

```text
HTTP 의미
GET /items/42
Host 또는 :authority
Accept

HTTP 전송 매핑
HTTP/1.1 메시지
HTTP/2 프레임과 스트림
HTTP/3 프레임과 QUIC 스트림
```

메서드의 안전성·멱등성은 프로토콜 의미이고, 실제 서비스가 그 의미를 지키는지는 애플리케이션 검증 대상입니다. 네트워크 가이드는 재시도 뒤 중복 상태 변경을 해결하는 업무 계약까지 소유하지 않습니다. 해당 설계는 웹 애플리케이션과 분산 서비스 가이드에서 다룹니다.

## HTTP/1.1, HTTP/2와 HTTP/3의 손실 경계

HTTP/1.1은 텍스트 기반 메시지 프레이밍과 지속 연결을 사용합니다. `Content-Length`, chunked coding와 연결 종료가 메시지 경계를 결정할 수 있습니다.

HTTP/2는 하나의 TCP 연결 안에 이진 프레임과 여러 스트림을 다중화하고 HPACK으로 헤더를 압축합니다. 한 스트림의 애플리케이션 처리가 늦어도 다른 스트림 프레임을 보낼 수 있지만, TCP 바이트 하나가 손실되면 그 뒤의 모든 스트림 바이트가 전송 계층의 순서 복구를 기다릴 수 있습니다.

HTTP/3는 QUIC 스트림 위에 HTTP 의미를 매핑하고 QPACK을 사용합니다. 한 QUIC 스트림의 손실은 다른 스트림의 이미 도착한 데이터를 TCP의 전역 바이트 순서처럼 막지 않습니다. 같은 스트림 내부의 순서와 QPACK 의존성은 남으므로 Head-of-Line Blocking이 모든 위치에서 사라진다고 표현하지 않습니다.

## TLS가 제공하는 것과 제공하지 않는 것

TLS는 서버 인증과 선택적인 클라이언트 인증 수단, 기밀성, 무결성 및 협상한 키를 제공합니다. 2026년 7월에 발행된 RFC 9846은 TLS 1.3의 현재 기본 명세이며 RFC 8446을 대체합니다. 구체적인 판본과 갱신 관계는 [표준 지도](../90-standards-map.md)에서 확인합니다.

일반적인 클라이언트는 서버 인증서 체인과 요청한 호스트 이름을 검증합니다. 인증서가 유효해도 애플리케이션 권한이 허용된다는 뜻은 아니며, TLS가 성공해도 HTTP에서 `401`, `403` 또는 다른 오류가 나올 수 있습니다.

SNI는 클라이언트가 연결하려는 서버 이름을 핸드셰이크에 전달하고, ALPN은 `h2`, `http/1.1`, `h3` 같은 애플리케이션 프로토콜을 협상합니다. 같은 IP와 포트에서도 SNI와 ALPN에 따라 다른 인증서와 프로토콜이 선택될 수 있습니다.

TLS 1.3의 0-RTT 애플리케이션 데이터는 이전 세션 정보를 이용해 지연을 줄일 수 있지만 재생 가능성이 있습니다. 네트워크 계층은 0-RTT 바이트를 전달할 수 있어도 상태 변경을 받아들일지는 애플리케이션 계약이 결정해야 합니다.

## QUIC은 UDP 위의 암호화된 전송 프로토콜입니다

QUIC은 UDP 데이터그램 안에서 다음 기능을 사용자 공간에 구현합니다.

- TLS 1.3 기반 암호화 핸드셰이크
- 여러 독립 스트림
- 손실 탐지와 혼잡 제어
- Connection ID를 이용한 경로 변화 처리
- 패킷 번호 공간과 ACK
- 전송 매개변수 협상

QUIC 연결은 단순한 UDP 4-튜플만으로 식별되지 않으므로 NAT 재바인딩과 네트워크 변경 뒤 연결 이동을 지원할 수 있습니다. 그러나 새 경로 검증, 증폭 방지 제한, 서버 정책과 유효한 Connection ID가 필요하므로 주소가 바뀌면 항상 끊김 없이 이동한다고 단정하지 않습니다.

UDP를 차단하거나 지나치게 짧은 NAT 매핑 제한 시간을 사용하는 경로에서는 HTTP/3가 실패하고 HTTP/2로 대체될 수 있습니다. 페이지가 열렸다는 사실만으로 실제 전송 프로토콜을 추정하지 말고 개발자 도구, 클라이언트 기능과 서버 로그를 확인합니다.

## 계층별 관찰 순서

```text
DNS       이름, 응답 코드, A·AAAA·HTTPS, cache
주소 선택 실제 연결을 시도한 주소와 순서
IP        출발지, route, next hop, MTU, ICMP
전송      TCP SYN·ACK 또는 QUIC Initial·Handshake
TLS       SNI, certificate, version, ALPN
HTTP      version, status, redirect, framing
애플리케이션 인증·인가와 업무 상태
```

대표적인 관찰 명령은 다음과 같습니다.

```sh
dig example.com A
dig example.com AAAA
curl -v --http2 https://example.com/
openssl s_client -connect example.com:443 -servername example.com -alpn h2
```

명령 지원 옵션은 빌드와 운영체제에 따라 다릅니다. 패킷 캡처에서 TLS와 QUIC 페이로드는 암호화되어 애플리케이션 내용을 직접 읽을 수 없으므로 종단점의 키 로그와 명시적인 디버그 환경이 필요할 수 있습니다.

## 대체 경로도 증거로 남깁니다

한 프로토콜의 실패 뒤 다른 프로토콜로 성공하면 최초 실패가 사라진 것이 아닙니다. 다음과 같이 기록합니다.

```text
AAAA 주소의 TCP 연결: timeout
A 주소의 TCP 연결: 성공
ALPN h3 시도: UDP timeout
ALPN h2 재시도: 성공
최종 HTTP 상태: 200
```

이 기록은 “서비스는 열립니다”와 “모든 주소 체계와 전송 경로가 정상입니다”를 구분합니다. 다음 장에서는 이러한 증거를 이용해 마지막 성공 계층과 첫 실패 계층을 결정합니다.
