# 커머스 도메인 불변식

쇼핑몰에서 어려운 부분은 상품 목록이나 장바구니 화면 자체가 아닙니다. 가격이 바뀌고 여러 사용자가 같은 재고를 두고 경쟁하며 결제 이벤트가 늦거나 중복되는 상황에서도 **과거 주문 금액, 현재 재고, 허용된 주문 상태가 서로 모순되지 않아야 한다**는 점이 핵심입니다.

이 문서는 특정 결제대행사나 배송사를 다루지 않습니다. 단일 통화를 사용하는 작은 상점에서 지켜야 할 도메인 상태의 기준과 실패 이후의 상태를 정의합니다.

## 목표

- 금액을 최소 화폐 단위의 정수와 통화 코드가 결합된 값으로 다룹니다.
- 현재 상품 가격과 주문 당시 가격 스냅샷을 구분합니다.
- 장바구니 입력을 확정 견적이 아닌 외부 요청으로 취급하고 서버에서 다시 계산합니다.
- 재고 경쟁을 데이터베이스 잠금, 조건부 갱신, 제약 조건으로 보호합니다.
- 주문 상태를 명시적인 상태 머신으로 제한합니다.
- 결제 취소와 환불, 재고 확보와 반환을 구분합니다.
- 최종 상태 이벤트가 중복되어도 재고와 활동 기록이 한 번만 바뀌게 합니다.

## 금액은 숫자 하나가 아닙니다

금액에는 값과 통화가 함께 있어야 합니다.

```ts
type Money = {
  amountMinor: number;
  currency: "KRW" | "USD";
};
```

`amountMinor`는 해당 통화의 최소 단위를 정수로 표현한 값입니다.

```text
KRW 12,500원 → 12500
USD 12.50달러 → 1250 cents
```

JavaScript 부동소수점으로 세금, 할인, 합계를 반복 계산하면 반올림 시점에 따라 결과가 달라질 수 있습니다. 이 실습에서는 모든 금액을 안전한 정수 범위의 최소 화폐 단위로 제한하고 데이터베이스에는 `bigint`로 저장합니다. 데이터베이스 드라이버가 `bigint`를 `number`로 변환할 때도 `Number.isSafeInteger`로 범위를 확인합니다.

실제 다중 통화 시스템에서는 통화별 소수 자릿수, 환율 적용 시점, 회계 반올림, 표시 형식을 별도 모델로 관리해야 합니다. 이 과정에서는 한 주문의 모든 품목이 같은 통화를 사용한다는 불변식만 다룹니다.

## 클라이언트가 보낸 합계를 신뢰하지 않습니다

다음 요청 본문의 합계는 서버가 사용할 기준값이 아닙니다.

```json
{
  "items": [{ "productId": "p1", "quantity": 2 }],
  "totalMinor": 100
}
```

클라이언트는 상품 ID와 수량만 보냅니다. 서버는 트랜잭션 안에서 현재 판매 가능한 상품과 가격을 읽고 합계를 다시 계산합니다.

```text
line_total = unit_price_snapshot × quantity
subtotal = 모든 line_total의 합
```

각 계산 단계에서 결과가 안전한 정수인지 확인합니다. 음수, `NaN`, 무한대, 허용 범위를 벗어난 수량은 전송 스키마와 도메인 규칙 양쪽에서 거부합니다.

## 현재 상품 가격과 주문 항목 가격은 서로 다른 기준입니다

상품 가격은 변경될 수 있지만 이미 생성된 주문의 금액이 함께 바뀌어서는 안 됩니다.

```text
products.price_minor           = 현재 판매 가격
order_items.unit_price_minor   = 주문 생성 당시 가격 스냅샷
```

주문을 조회할 때 현재 상품 테이블과 조인해 가격을 다시 계산하면 과거 영수증의 금액이 바뀝니다. 주문 항목에는 최소한 다음 값을 스냅샷으로 저장합니다.

```text
product_id
sku
name
unit_price_minor
currency
quantity
line_total_minor
```

상품 이름과 SKU를 어느 수준까지 보존할지는 영수증, 감사, 개인정보 정책에 따라 달라집니다. 이 실습에서는 주문을 상품 테이블과 무관하게 읽을 수 있도록 SKU와 이름도 함께 저장합니다.

## 장바구니와 주문을 구분합니다

장바구니는 사용자가 편집할 수 있는 구매 의도입니다. 주문은 서버가 검증하고 확정한 도메인 기록입니다.

```text
장바구니 항목
→ 체크아웃 요청
→ 상품·가격·재고 재검증
→ 주문 스냅샷 생성
```

장바구니에 저장된 가격, 할인 가능 여부, 재고는 체크아웃 시점에 다시 확인합니다. 오래 열어 둔 화면의 값은 기준 상태가 아닙니다.

이 실습에서는 장바구니 테이블을 만들지 않습니다. 체크아웃 요청 본문이 장바구니 스냅샷 역할을 하며 주문 생성에 필요한 최소 입력만 받습니다. 이 단계의 목표는 장바구니 UI가 아니라 트랜잭션 경계를 구현하는 것입니다.

## 재고 모델을 먼저 선택합니다

재고를 처리하는 방식에는 여러 가지가 있습니다.

### 즉시 차감 모델

```text
products.stock_on_hand
```

체크아웃 요청이 성공하면 재고를 바로 차감하고, 결제 실패·취소·환불 시 반환합니다. 작은 실습에는 적합하지만 결제 대기 시간이 길면 판매 가능한 재고가 오랫동안 묶일 수 있습니다.

### 예약 모델

```text
on_hand
reserved
available = on_hand - reserved
```

예약 모델에는 주문 만료와 예약 해제를 수행할 스케줄러가 필요합니다. 실제 서비스에 더 가까울 수 있지만 관리해야 할 생명주기가 늘어납니다.

이 실습에서는 **체크아웃 시 재고를 즉시 차감하고 최종 실패 상태에서 한 번만 반환하는 단순 모델**을 사용합니다. 대신 `inventory_movements`를 기록해 차감과 반환이 중복되지 않았음을 검증합니다.

## 사전 조회만으로 초과 판매를 막을 수 없습니다

다음 흐름에는 경쟁 조건이 있습니다.

```text
A: stock=1 읽음
B: stock=1 읽음
A: 1 차감
B: 1 차감
```

보호하려는 불변식에 따라 다음 수단 중 하나를 선택합니다.

- 상품 행을 항상 같은 순서로 `FOR UPDATE` 잠금
- `UPDATE ... WHERE stock_on_hand >= quantity`
- 별도 예약 행과 고유 제약 조건
- 높은 격리 수준과 제한된 재시도

이 실습에서는 주문에 포함된 상품 ID를 정렬한 뒤 해당 행을 잠급니다. 여러 품목을 서로 다른 순서로 잠글 때 발생할 수 있는 교착 상태를 줄이기 위한 방식입니다. 잠금을 얻은 뒤에도 현재 재고를 다시 확인하고 차감합니다.

```text
stock_on_hand >= 0
```

이 불변식은 데이터베이스 검사 제약 조건으로도 보호합니다.

## 재고 변동 기록은 현재 수량을 대신하지 않습니다

```text
reserve  -2
release  +2
```

변동 기록을 남기면 주문별 재고 변화와 중복 반환 여부를 확인할 수 있습니다. 그러나 현재 재고를 조회할 때마다 모든 변동을 합산하는 구조는 성능과 정합성 관리 방식이 달라집니다. 이 실습에서는 다음과 같이 구분합니다.

- `products.stock_on_hand`: 현재 재고의 기준값
- `inventory_movements`: 재고 변화의 감사 기록

두 값은 하나의 트랜잭션에서 함께 변경합니다. `unique(order_id, product_id, kind)` 제약 조건으로 같은 주문의 `release`가 두 번 기록되는 것을 막습니다.

## 주문은 상태 머신으로 관리합니다

여러 불리언으로 상태를 표현하면 불가능한 조합이 생길 수 있습니다.

```text
paid=true
canceled=true
refunded=false
```

하나의 상태 값과 허용된 전이를 정의합니다.

```text
pending_payment
  ├─ payment.succeeded ──> paid
  ├─ payment.failed ─────> payment_failed
  └─ cancel.requested ───> cancel_pending

cancel_pending
  ├─ payment.canceled ───> canceled
  └─ payment.succeeded ──> paid

paid
  └─ refund.requested ───> refund_pending

refund_pending
  └─ payment.refunded ───> refunded
```

`cancel_pending` 상태에서 결제가 먼저 성공하면 주문은 `paid`가 됩니다. 취소 요청이 있었다는 이유만으로 이미 성공한 결제를 `canceled`로 표시해서는 안 됩니다. 필요하다면 결제 성공 후 별도의 환불 명령을 시작합니다.

최종 상태는 다음과 같습니다.

```text
payment_failed
canceled
refunded
```

늦게 도착한 `payment.succeeded` 이벤트가 최종 상태를 `paid`로 되돌려서는 안 됩니다. 이벤트는 기록하되 상태 전이는 거부합니다.

## 결제 취소와 환불은 다른 작업입니다

```text
cancel
= 결제가 확정되기 전에 진행 중인 작업을 중단

refund
= 이미 확정된 결제 효과를 반대 방향으로 보상
```

따라서 API와 외부 제공자 명령도 구분합니다.

```text
POST /orders/:id/cancel
POST /orders/:id/refund
```

- `pending_payment` 상태에서만 취소 요청 가능
- `paid` 상태에서만 환불 요청 가능
- 같은 명령을 다시 보내도 중복 효과가 없어야 함
- 외부 제공자의 확정 이벤트 전에는 최종 상태로 표시하지 않음

실제 서비스에서는 배송 이후 환불이 재고 반환을 의미하는지 반품 검수 정책에 따라 달라집니다. 이 실습에서는 전체 흐름을 검증하기 위해 `payment.refunded` 이벤트가 도착하면 전량을 재고로 반환하는 단순한 정책을 사용합니다. 실제 제품에서는 환불과 재입고를 분리할 수 있습니다.

## 재고 반환은 최종 상태 전이와 같은 트랜잭션에서 처리합니다

다음 순서로 따로 커밋하면 데이터가 어긋날 수 있습니다.

```text
order = canceled 커밋
→ 재고 반환 실패
```

주문은 취소되었지만 재고가 복구되지 않은 상태가 됩니다. 다음 작업은 하나의 트랜잭션에서 처리해야 합니다.

```text
주문 상태 전이
결제 상태 갱신
재고 반환
재고 변동 기록 삽입
주문 이벤트 삽입
제공자 이벤트 처리 결과 갱신
```

중복 웹훅은 제공자 이벤트 ID의 고유 제약 조건과 `inventory_released_at` 조건으로 이중 방어합니다.

## 주문 합계 불변식

주문을 만든 뒤 다음 관계가 항상 성립해야 합니다.

```text
order_item.line_total_minor
= order_item.unit_price_minor × quantity

order.subtotal_minor
= sum(order_item.line_total_minor)

order.total_minor
= subtotal_minor
```

이 실습에는 할인, 배송비, 세금이 없으므로 `total = subtotal`입니다. 실제 시스템에서는 각 구성 요소를 숨기지 말고 다음처럼 나누어 저장합니다.

```text
subtotal
discount_total
shipping_total
tax_total
grand_total
```

총액 하나만 저장한 채 계산 근거를 잃어서는 안 됩니다.

## 데이터베이스 제약 조건과 애플리케이션 정책을 구분합니다

데이터베이스가 직접 보호하기 적합한 규칙은 다음과 같습니다.

- 수량이 0보다 큼
- 금액이 0 이상
- `stock_on_hand`가 0 이상
- 허용된 주문 상태 집합
- 주문과 결제의 1:1 관계
- 제공자 이벤트 ID 고유성
- 명령 멱등성 키 고유성
- 재고 변동 기록 중복 금지

애플리케이션 서비스가 트랜잭션 안에서 판정할 규칙은 다음과 같습니다.

- 한 주문의 모든 품목이 같은 통화를 사용하는가
- 현재 상태에서 취소 또는 환불이 가능한가
- 같은 멱등성 키가 같은 요청에 사용되었는가
- 제공자 이벤트가 현재 상태에서 허용되는가
- 어떤 오류를 409와 422로 공개할 것인가

모든 상태 머신 규칙을 데이터베이스 검사 제약 조건에 넣을 필요는 없습니다. 다만 어떤 쓰기 경로도 우회해서는 안 되는 기본 범위는 제약 조건으로 남깁니다.

## 실패를 숨기는 자동 보상에 주의합니다

외부 결제는 성공했지만 내부 처리에서 오류가 발생했다고 `catch` 블록에서 즉시 자동 환불을 호출하면 새로운 외부 실패 경계가 생깁니다. 보상 명령도 식별자, 재시도, 상태, 관찰 수단이 필요합니다.

```text
원래 명령
→ 부분 성공
→ 보상 명령
→ 보상 명령 재시도
```

이 실습에서는 동기 예외 처리 안에서 보상 작업을 임의로 실행하지 않습니다. 취소와 환불도 영속 명령으로 저장합니다.

## 검증 항목

최소한 다음을 테스트합니다.

- 상품 가격 변경 후에도 기존 주문 항목 가격이 바뀌지 않는지
- 클라이언트가 보낸 총액을 무시하고 서버가 다시 계산하는지
- 서로 다른 통화의 품목을 한 주문에 섞지 못하게 하는지
- 같은 상품이 중복된 주문 항목을 합치거나 거부하는 정책이 적용되는지
- 재고가 1개일 때 두 체크아웃 요청 중 하나만 성공하는지
- 여러 상품의 잠금 순서가 항상 같은지
- 체크아웃 트랜잭션 중간 실패 시 주문과 재고 차감이 모두 롤백되는지
- 결제 실패·취소·환불 시 재고가 정확히 한 번 반환되는지
- 최종 상태 웹훅이 중복되어도 재고가 추가로 증가하지 않는지
- 늦은 이벤트가 최종 상태를 이전 상태로 되돌리지 않는지
- 주문 총액과 주문 항목 합계가 일치하는지

## 흔한 오류

- `number`가 정수이며 안전한 범위에 있는지 확인하지 않습니다.
- 클라이언트의 총액이나 상품 가격을 주문 금액의 기준으로 사용합니다.
- 주문 조회 시 현재 상품 가격으로 과거 합계를 다시 계산합니다.
- 재고 조회와 차감을 서로 다른 트랜잭션에서 처리합니다.
- 주문마다 상품 행을 잠그는 순서가 다릅니다.
- 결제 취소와 환불을 같은 상태 전이로 취급합니다.
- 제공자의 확정 응답 전에 성공·취소·환불을 최종 상태로 표시합니다.
- 중복 이벤트에서 재고를 다시 반환합니다.
- 늦은 성공 이벤트가 최종 상태를 되돌립니다.
- 주문 상태 변경, 활동 기록, 재고 변경을 각각 따로 커밋합니다.

## 연결 실습

[`커머스 체크아웃`](03-commerce-checkout.md)과 [`commerce-checkout 실습`](../../exercises/commerce-checkout/README.md)의 01–02단계와 05단계에서 금액, 가격 스냅샷, 재고 경쟁, 취소·환불 상태 전이를 구현합니다.

## 완료 기준

- 금액 값과 주문 가격 스냅샷의 기준을 설명할 수 있습니다.
- 체크아웃 요청에서 서버가 가격과 합계를 다시 계산합니다.
- 실제 PostgreSQL의 경쟁 요청에서 초과 판매를 막습니다.
- 주문 상태를 허용된 전이로만 변경합니다.
- 최종 상태 전이와 재고 반환을 같은 트랜잭션에서 한 번만 수행합니다.
