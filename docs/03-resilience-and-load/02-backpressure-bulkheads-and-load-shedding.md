# 역압, Bulkhead와 Load Shedding

## 목표

처리 속도보다 빠른 유입을 무제한 queue와 retry로 숨기지 않고, 동시 실행·대기·거절 한도를 명시해 장애 전파를 막습니다.

## 문제

서비스가 초당 100건을 처리할 수 있는데 초당 500건이 계속 들어오면 queue는 지연을 잠시 숨길 뿐입니다. queue가 무제한이면 메모리와 처리 지연이 증가하고, 사용자는 이미 deadline이 지난 작업의 결과를 늦게 받습니다.

의존성 하나가 느려졌을 때 모든 worker와 연결을 점유하면 다른 기능도 함께 멈춥니다. 이를 막으려면 “더 많이 받아 두기”보다 **받을 수 있는 양을 계약으로 제한**해야 합니다.

## 계약

### 실행과 대기 한도를 따로 정합니다

각 작업 유형에 다음 한도를 둡니다.

```text
max_running
max_queued
max_queue_time
request_deadline
```

새 작업을 받을 때 다음을 판단합니다.

1. deadline이 이미 지났으면 즉시 거절합니다.
2. 실행 자리가 있으면 시작합니다.
3. 대기 자리가 있고 예상 대기 시간이 deadline 안이면 queue에 넣습니다.
4. 그렇지 않으면 `OVERLOADED`로 거절합니다.

비동기 API라면 queue에 넣었다는 사실만 반환하지 않고 최대 지연과 작업 조회를 제공합니다.

### 역압을 위쪽으로 전달합니다

소비자가 느릴 때 생산자가 계속 보내면 내부 queue만 이동합니다. 사용할 수 있는 방법은 시스템에 따라 다릅니다.

- 브로커 소비를 일시 중지합니다.
- producer의 in-flight 수를 제한합니다.
- HTTP에서 429 또는 503과 `Retry-After`를 반환합니다.
- upstream의 concurrency limit를 줄입니다.
- batch 크기와 poll 수를 제한합니다.
- 중요도가 낮은 작업을 먼저 거절합니다.

재시도 가능한 거절이라도 모든 호출자가 동시에 다시 시도하지 않도록 지터와 최대 재시도 시간을 둡니다.

### Bulkhead로 자원을 분리합니다

기능별로 worker, connection pool 또는 queue를 분리하면 한 의존성의 지연이 전체 자원을 소비하지 못합니다.

예:

```text
inventory 호출 pool: 20
notification 호출 pool: 5
admin export pool: 2
```

분리는 무조건 많을수록 좋은 것이 아닙니다. 너무 세분화하면 유휴 자원이 늘고 운영 복잡성이 커집니다. 서로 다른 실패 도메인과 중요도를 기준으로 나눕니다.

### Load Shedding 결과를 업무 계약으로 만듭니다

과부하 거절은 시스템 오류를 숨기는 응답이 아닙니다. 호출자는 다음을 알아야 합니다.

- 요청이 전혀 시작되지 않았는지
- operation ID를 다시 사용해야 하는지
- 언제 다시 시도할 수 있는지
- 우선순위 또는 quota가 있는지
- 상태 조회가 필요한지

쓰기 작업이 queue에 들어간 뒤 timeout이 발생했다면 단순 거절이 아니라 결과가 불확실할 수 있습니다.

## 실패 조건

- queue 크기와 최대 대기 시간이 없습니다.
- 이미 deadline이 지난 작업을 계속 처리합니다.
- 한 의존성의 worker·connection pool이 전체 서비스와 공유됩니다.
- 과부하에서 retry가 요청 수를 더 증폭합니다.
- queue 길이만 보고 가장 오래된 작업의 나이를 보지 않습니다.
- 내부에서 버린 작업을 성공으로 응답합니다.
- 우선순위 작업이 낮은 중요도의 대량 작업에 막힙니다.

## 검증

burst 입력을 넣고 다음을 확인합니다.

- 동시에 실행되는 수가 `max_running`을 넘지 않습니다.
- queue가 `max_queued`를 넘지 않습니다.
- 초과 작업은 명시적으로 거절됩니다.
- 완료 뒤 queue가 정해진 순서로 줄어듭니다.
- deadline이 지난 작업은 실행되기 전에 제거됩니다.
- 한 bulkhead의 포화가 다른 bulkhead의 실행을 막지 않습니다.

성능 검사는 처리량만 보지 않고 거절 수, queue age와 최종 완료 수를 함께 기록합니다.

## 완료 조건

- 실행 수·대기 수·대기 시간 한도를 함께 정할 수 있습니다.
- upstream에 전달할 과부하 응답 계약을 설명합니다.
- 실패 도메인에 따라 bulkhead를 분리합니다.
- burst와 deadline 경계에서 queue가 제한되는지 검사합니다.
