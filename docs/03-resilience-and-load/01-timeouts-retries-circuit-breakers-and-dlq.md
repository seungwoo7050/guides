# 시간 예산, 재시도, Circuit Breaker와 DLQ

## 목표

개별 라이브러리 설정이 아니라 사용자 요청의 전체 기한에서 timeout과 retry를 배분하고, 실패 분류에 따라 Circuit Breaker와 DLQ의 역할을 정합니다.

## 문제

게이트웨이, 서비스와 HTTP 클라이언트가 각각 세 번 재시도하면 한 번의 사용자 요청이 여러 하위 호출로 증폭됩니다. 의존성이 느려진 상황에서 재시도는 복구보다 추가 부하가 될 수 있습니다.

또한 timeout은 처리 결과를 알려 주지 않습니다. 호출자는 기다리기를 멈췄지만 서버가 계속 처리할 수 있습니다. 쓰기 명령을 다시 시도하려면 멱등성 키와 결과 조회가 함께 필요합니다.

## 계약

### 전체 deadline을 먼저 정합니다

시간 제한을 계층마다 독립적으로 설정하지 않습니다.

```text
사용자 요청 전체 deadline: 800ms
게이트웨이 처리·전달:       100ms
서비스 로컬 처리:           100ms
하위 호출과 재시도:         최대 500ms
응답 직렬화·여유:           100ms
```

실제 값은 시스템마다 다르지만 합은 전체 deadline을 넘지 않아야 합니다. 하위 호출에는 고정 timeout보다 **남은 시간**을 전달하는 편이 좋습니다.

다음 시간을 구분합니다.

- 연결 timeout
- 개별 시도 timeout
- queue 대기 시간
- 전체 연산 deadline
- 비동기 작업의 최대 처리 시간

시간이 끝난 뒤 실행 중인 작업을 취소할 수 있는지, 취소가 업무 상태를 어떻게 바꾸는지도 별도 계약입니다.

### 재시도 가능한 실패를 제한합니다

일반적으로 다음 조건을 모두 만족할 때 재시도를 고려합니다.

- 실패가 일시적일 가능성이 있습니다.
- 같은 operation ID로 반복해도 단일 효과가 유지됩니다.
- 다음 시도가 전체 deadline 안에 들어옵니다.
- 재시도가 의존성 복구를 방해하지 않습니다.
- 호출 계층 중 한 곳만 재시도를 소유합니다.

업무 거절, 입력 검증 실패와 권한 실패는 재시도 대상이 아닙니다. 일시적인 네트워크 실패도 시도 횟수보다 최대 경과 시간으로 제한합니다.

Backoff에는 지터를 사용해 여러 인스턴스가 같은 시점에 다시 몰리지 않게 합니다. 테스트에서는 난수와 실제 sleep 대신 가상 시계와 결정적 지터를 사용합니다.

### Circuit Breaker의 실패 표본을 정의합니다

Circuit Breaker는 실패를 없애는 장치가 아니라 실패한 의존성으로 보내는 요청을 빠르게 줄이는 장치입니다.

기록할 실패와 제외할 결과를 구분합니다.

| 결과 | breaker 실패로 기록 |
|---|---|
| 연결 실패·timeout | 일반적으로 예 |
| 5xx 기반 시설 실패 | 정책에 따라 예 |
| 업무 규칙에 따른 409·422 | 아니오 |
| 호출자가 취소한 요청 | 원인을 구분 |
| breaker가 열려 빠르게 거절 | 원래 의존성 실패와 별도 지표 |

half-open 시험 요청이 쓰기라면 같은 멱등성 키를 사용합니다. breaker가 닫혔다고 업무 불일치가 자동으로 복구되는 것은 아니므로 재조정은 별도로 필요합니다.

### DLQ를 복구 대기열로 설계합니다

DLQ에는 실패한 payload만 넣지 않습니다.

- 원본 채널과 위치
- event ID와 operation ID
- schema version
- 실패 분류와 마지막 오류
- 시도 횟수와 최초·최종 실패 시각
- 재처리 담당자
- 수정 뒤 되돌릴 채널 또는 처리 경로
- 보존 기간과 폐기 승인

원인을 고치지 않고 원본 채널로 계속 되돌리면 poison message가 반복됩니다. 재처리는 동일한 event ID를 유지하고 소비자 멱등성을 다시 사용합니다.

## 실패 조건

- 각 계층이 독립적으로 여러 번 재시도합니다.
- 하위 timeout 합이 전체 deadline보다 깁니다.
- 재시도마다 새 operation ID를 만듭니다.
- 업무 거절을 breaker 실패로 기록합니다.
- 열린 breaker를 정상 응답처럼 숨깁니다.
- DLQ에 payload만 있고 원본 위치와 재처리 책임이 없습니다.
- 실제 sleep을 사용하는 느리고 비결정적인 검사만 있습니다.

## 검증

검사는 가상 시계로 다음을 확인합니다.

- 업무 거절은 한 번만 호출됩니다.
- transient failure는 같은 operation ID로 재시도합니다.
- 다음 backoff가 deadline을 넘으면 새 시도를 시작하지 않습니다.
- 연속 실패 뒤 breaker가 열리고 의존성을 호출하지 않습니다.
- half-open 성공 뒤 제한적으로 닫힙니다.
- DLQ 재처리도 같은 event ID로 단일 효과를 유지합니다.
