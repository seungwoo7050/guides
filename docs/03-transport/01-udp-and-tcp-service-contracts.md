# UDP와 TCP의 서비스 계약

UDP와 TCP를 “빠른 프로토콜”과 “느린 프로토콜”로 나누면 애플리케이션 계약을 놓칩니다. 먼저 데이터 경계, 순서, 중복, 손실, 연결 상태와 혼잡 반응 중 무엇을 전송 계층에 맡길지 정한 뒤 프로토콜을 선택해야 합니다.

## 학습 목표

- UDP 데이터그램과 TCP 바이트 스트림의 전달 단위를 구분합니다.
- 손실·순서·중복·혼잡 책임을 애플리케이션 요구에 연결합니다.

## 선행 개념

IP의 best-effort 전달과 주소·포트로 구성된 전송 endpoint를 알고 있어야 합니다.

## UDP는 데이터그램 경계를 보존합니다

한 번의 UDP 전송은 하나의 데이터그램을 만들고 수신은 데이터그램 단위로 일어납니다. 수신 버퍼가 작으면 데이터그램이 잘리거나 API가 오류·플래그로 이를 알릴 수 있지만, 두 데이터그램이 하나의 수신 메시지로 합쳐지는 TCP식 스트림은 아닙니다.

UDP 자체는 다음을 보장하지 않습니다.

- 전달
- 순서
- 중복 제거
- 혼잡에 따른 자동 전송률 조절
- 연결 수립과 종료 핸드셰이크

따라서 애플리케이션이 필요하면 메시지 ID, 순서 번호, ACK, 제한 시간, 재전송, 중복 억제와 전송률 제어를 설계해야 합니다. 이 기능을 일부 추가했다고 자동으로 TCP와 같은 의미가 되는 것은 아닙니다.

UDP checksum은 IPv4에서 0으로 두어 사용하지 않음을 나타낼 수 있지만 IPv6에서는 일반적으로 필수입니다. checksum이 있다고 전달·순서 보장이 생기는 것은 아니며, 전송 중 비트 오류를 검출하는 범위만 제공합니다.

## TCP는 순서 있는 양방향 바이트 스트림입니다

TCP는 애플리케이션 message 경계를 보존하지 않습니다.

```text
send 40바이트 + send 60바이트
≠ 상대 recv 40바이트 + recv 60바이트 보장
```

상대는 한 번에 100바이트를 읽거나 여러 번에 나눠 읽을 수 있습니다. 애플리케이션 프로토콜은 고정 길이, 구분자, 길이 프리픽스, 자기 서술 형식 또는 연결 종료 같은 프레이밍 규칙을 정의해야 합니다.

TCP가 제공하는 핵심 계약은 다음과 같습니다.

- 연결된 두 종단점 사이의 순서 있는 바이트 스트림
- 손실된 바이트의 재전송
- 중복 바이트 제거
- checksum을 통한 손상 검출
- 수신 흐름 제어
- 네트워크 혼잡 제어
- 양방향 독립 종료가 가능한 full-duplex 연결

“신뢰성”은 요청 전체가 업무적으로 한 번만 처리된다는 뜻이 아닙니다. 서버가 상태를 변경한 뒤 응답이 끊기면 클라이언트 retry가 같은 작업을 다시 만들 수 있으므로 idempotency는 애플리케이션에서 설계해야 합니다.

## endpoint와 연결 식별자

전송 protocol은 IP 주소만으로 프로세스를 구분하지 않습니다. UDP flow와 TCP 연결을 설명할 때는 보통 다음 값을 사용합니다.

```text
프로토콜
출발지 IP:출발지 포트
목적지 IP:목적지 포트
```

TCP 수신 소켓은 하나의 로컬 포트에서 많은 연결을 받을 수 있습니다. `accept`가 반환한 각 소켓은 원격 튜플이 달라 별도 연결 상태를 가집니다. 소켓 수명주기와 부분 I/O는 Unix 네트워크 문서에서 확인할 수 있습니다.

NAT, 로드 밸런서와 프록시가 있으면 애플리케이션이 관찰한 피어 튜플은 원래 클라이언트와 다를 수 있습니다. 전달 헤더를 신뢰할 범위와 Proxy Protocol 사용 여부를 명시합니다.

## port는 service 이름이 아니라 숫자 namespace입니다

잘 알려진 포트는 상호 운용을 위한 기본 약속이지만 해당 포트에서 반드시 예상 프로토콜이 실행된다는 보장은 없습니다. `443`이 열려 있어도 TLS가 아닌 다른 바이트 스트림을 보낼 수 있고, TLS가 성공해도 HTTP가 아닐 수 있습니다.

클라이언트의 임시 포트 범위는 운영체제 설정과 현재 사용량에 따라 달라집니다. 짧은 연결을 대량으로 만들면 로컬 포트, NAT 포트와 TIME-WAIT 상태가 자원이 될 수 있습니다.

## 실패 신호의 차이

| 상황 | UDP에서 흔한 관찰 | TCP에서 흔한 관찰 |
|---|---|---|
| 대상 프로세스 없음 | ICMP 오류 또는 제한 시간 초과 | RST 또는 연결 오류 |
| 중간 손실 | 아무 응답 없음 | 재전송 뒤 성공 또는 제한 시간 초과 |
| 상대 비정상 종료 | 다음 요청의 제한 시간 초과 가능 | RST, EOF 또는 쓰기 오류 |
| message 너무 큼 | 분할, ICMP 또는 손실 | stream이 여러 segment로 나뉨 |
| 수신자가 느림 | 커널 버퍼 폐기 가능 | `rwnd` 감소와 송신자 역압 |

정확한 API 오류와 발생 시점은 운영체제, 소켓 상태와 패킷 시점에 따라 달라집니다. “UDP는 오류가 없고 TCP는 즉시 오류를 줍니다”라고 단정하지 않습니다.

## 어떤 protocol을 선택할지

다음 질문에 답한 뒤 선택하세요.

1. message 하나의 최대 크기와 framing은 무엇인가요?
2. 늦게 도착한 데이터가 가치가 있나요, 버리는 편이 낫나요?
3. 순서가 필요한 범위는 전체 연결인가요, stream별인가요, message별인가요?
4. 중복 처리를 애플리케이션이 감당할 수 있나요?
5. congestion control과 fairness를 누가 구현하나요?
6. NAT 매핑과 방화벽 제한 시간을 어떻게 유지하고 복구하나요?
7. 연결 migration과 여러 독립 stream이 필요한가요?

실시간 media는 늦은 packet을 재전송하지 않고 다음 frame으로 넘어갈 수 있고, 파일 전송은 모든 바이트의 정확한 순서를 필요로 합니다. 같은 “낮은 지연” 요구라도 손실 처리 계약이 다릅니다.

QUIC은 UDP 위에서 사용자 공간의 신뢰성, 혼잡 제어, 암호화와 스트림을 구현합니다. UDP 자체가 신뢰성을 제공하는 것이 아니라, UDP의 데이터그램 인터페이스와 커널 배포 독립성을 바탕으로 새 전송 프로토콜을 만든 사례입니다.
