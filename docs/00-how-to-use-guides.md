# guides 사용법

## 목적

이 저장소는 특정 분야의 모든 지식을 완성하지 않는다. 다음 상태를 만드는 것이 목적이다.

```text
용어와 책임 경계를 이해한다
→ 작은 예제에서 실패를 재현한다
→ 기존 코드베이스의 구조와 검증 명령을 복원한다
→ 명확한 범위의 변경을 구현한다
→ 테스트와 관측 근거로 완료를 증명한다
→ 실제 프로젝트에서 부족한 지식을 추가한다
```

## 브랜치의 네 가지 종류

| 종류 | 역할 | 예시 |
|---|---|---|
| 공통 기반 | 여러 분야가 공유하는 원리와 관찰 능력 | `git`, `algorithms`, `computer-networks` |
| 언어 진입 | 언어와 그 언어로 만들 수 있는 첫 프로그램·도구 | `c`, `cpp`, `java`, `python` |
| 분야 진입 | 독립적인 업무 분야에 들어가는 최소 경로 | `web-app`, `game-development`, `cybersecurity`, `mobile-app`, `machine-learning`, `agentic-systems` |
| 심화 | 진입 이후 특정 책임과 내부구조를 깊게 다룸 | `database-systems`, `distributed-systems`, `platform-engineering` |

종류는 난이도 순서가 아니다. `field-entry`도 여러 기반을 필요로 할 수 있고, `common-foundation`도 깊은 내용을 포함할 수 있다.

**교차 확장**은 다섯 번째 종류가 아니라 둘 이상의 기반을 새로운 상태·실패 모델에 연결하는 직교 특성이다. 예를 들어 `data-engineering`, `agentic-systems`, `language-implementation`은 각자의 카탈로그 종류를 가지면서 교차 확장 특성을 가질 수 있다.

## 의존성과 경로 표기

- **권장 선형 경로**: 목표 직무로 처음 진입하는 독자가 순서대로 진행할 현실적인 경로다. 엄밀한 필수 관계뿐 아니라 직무 맥락에 유용한 권장 기반을 포함할 수 있다.
- **공통**: 트랙 전체에서 반복해 사용하는 변경·검증 기반이다.
- **필수**: 핵심 문서가 해당 지식을 전제로 한다.
- **택일 필수**: 나열된 브랜치 중 하나의 구현 경험이 필요하다.
- **권장**: 먼저 완료하면 좋지만 필요한 부분만 참조하며 진행할 수 있다.
- **심화**: 현재 트랙의 종료 뒤 더 넓거나 깊은 문제로 이동하는 경로다.

선형 경로와 필수 의존성은 같은 개념이 아니다. 선형 경로는 실제 학습 순서를 안내하고, 브랜치의 최소 전제는 `catalog/branches.json`의 `requires`가 정본이다.

필수라고 해서 모든 문서를 다시 정독해야 한다는 뜻은 아니다. 이미 실무 경험이 있다면 브랜치의 roadmap과 종료 검사를 이용해 결손만 확인한다.

## 학습 단위

각 브랜치의 전체 학습 경로는 다음 질문에 답해야 한다.

1. 어떤 실제 문제가 존재하는가
2. 누가 상태와 자원을 소유하는가
3. 어떤 사건이 상태를 바꾸는가
4. 실패하면 무엇이 남고 무엇이 바뀌면 안 되는가
5. 어떤 증거로 결과를 검증하는가
6. 이 브랜치가 다루지 않는 영역은 어디인가

한 문서가 모든 질문을 반복할 필요는 없다. roadmap, 개념 문서, 실습을 합친 전체 경로에서 답을 찾을 수 있어야 한다.

실습과 capstone 또는 그에 해당하는 누적 최종 실습은 문서를 대체하지 않는다. 문서의 상태·실패·검증 계약을 실제 작업으로 확인하는 수단이다. 브랜치 작성과 검토의 전체 기준은 [브랜치 품질 계약](09-branch-quality-contract.md)을 따른다.

## 완료 판단

브랜치를 완료했다는 말은 문서를 끝까지 읽었다는 뜻이 아니다. 다음을 수행할 수 있어야 한다.

- 카탈로그에 선언된 종료 능력을 설명이나 수행 결과로 보여 준다.
- 대표적인 정상·경계·실패 사례를 실습 또는 관찰로 재현한다.
- capstone 또는 동등한 누적 최종 실습에서 핵심 능력을 함께 사용한다.
- 테스트·측정·trace·사람 검토가 보장하는 것과 한계를 구분한다.
- 해당 브랜치의 범위를 넘는 문제를 올바른 인접 브랜치나 외부 영역으로 보낸다.

이 판단은 자동 검사 하나로 확정하지 않는다. 자동 검사는 일부 동작과 기계적 무결성을 확인하고, 독자와 리뷰어는 설명, 실습 결과, 누적 과제와 검사의 한계를 함께 보고 브랜치 완료를 판단한다.

트랙 완료는 `common`, `required`, 각 `required_any`에서 선택한 브랜치들의 종료 능력을 목표 업무에 연결해 다음 작업을 시도할 준비가 된 상태다. 권장 선형 경로는 그 상태까지 이동할 현실적인 순서를 제안하지만, 경로에 추가된 권장 기반까지 모두 완료해야 한다는 뜻은 아니다.

- 처음 보는 작은 저장소의 실행·데이터·검증 경계를 찾는다.
- 요구사항을 변경 단위와 실패 조건으로 나눈다.
- 작은 변경을 구현하고 기존 계약을 보존한다.
- 로그·테스트·측정 또는 검토 결과를 근거로 완료를 설명한다.

브랜치 완료와 트랙 완료 모두 실제 프로젝트에서 변경을 끝낸 경험을 대신하지 않는다.

## 진행 방법

1. 목표 직무를 하나 선택한다.
2. 해당 트랙의 권장 선형 경로 하나를 선택한다.
3. 경로에 포함된 브랜치의 엄밀한 필수 의존성을 의존성 지도에서 확인한다.
4. 이미 아는 브랜치는 전체 검증과 capstone 또는 동등한 누적 최종 실습으로 건너뛸지 판단한다.
5. 한 번에 두 개 이상의 심화 브랜치를 병렬로 시작하지 않는다.
6. 각 브랜치 뒤 실제 프로젝트에서 한 번 이상 사용한다.
7. 프로젝트에서 반복적으로 막히는 경계가 생길 때 인접 브랜치로 확장한다.

선택한 브랜치로 바로 전환하거나 `main`을 유지한 별도 worktree에서 학습할 수 있다.

```sh
git switch python

# main의 로드맵과 학습 브랜치를 동시에 열어 둘 때
git worktree add ../guides-python python
```

## 하지 말아야 할 것

- 브랜치 개수를 경력 수준으로 환산하지 않는다.
- 선형 경로에 표시된 모든 권장 기반을 엄밀한 필수 조건으로 오해하지 않는다.
- 언어와 프레임워크 이름을 많이 아는 것을 넓이라고 착각하지 않는다.
- 답안을 복사해 검사를 통과하는 것을 완료로 보지 않는다.
- 특정 도구의 명령 목록을 분야 전체로 취급하지 않는다.
- 실제 운영·보안·데이터 문제를 가이드 실습만으로 경험했다고 주장하지 않는다.
