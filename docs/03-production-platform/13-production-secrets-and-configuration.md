# 운영 비밀값과 설정

설정과 비밀값을 모두 `.env`라고 부르면 공개 가능한 동작 설정, 인증 정보, 버전 관리가 필요한 계약이 한 파일에 섞입니다. 운영에서는 값의 민감도뿐 아니라 **누가 읽고, 누가 쓰고, 언제 교체하며, 어떤 릴리스와 호환되는지**를 구분해야 합니다.

이 장의 목표는 다음 수명 주기를 구현하는 것입니다.

```text
필요한 비밀값 정의
→ 최소 권한으로 생성·전달
→ 실행 시점에만 주입
→ 사용 여부 검증
→ 겹치는 기간을 두고 회전
→ 이전 값 폐기
→ 유출 시 영향 범위 확인과 재발급
```

대응 실습은 [`exercises/13-secret-rotation`](../exercises/13-secret-rotation/)입니다.

## 1. 값을 네 종류로 나누기

### 코드에 포함되는 기본값

민감하지 않고 모든 환경에서 같은 값입니다.

```text
기본 페이지 크기
지원 프로토콜 버전
내부 기능의 안전한 기본값
```

### 공개 환경 설정

환경마다 다르지만 공개돼도 인증 권한을 주지 않는 값입니다.

```text
PUBLIC_BASE_URL
LOG_LEVEL
WORKER_COUNT
DATABASE_HOST
FEATURE_FLAG
```

Git 또는 릴리스 매니페스트에 넣을 수 있지만 변경 이력과 스키마를 관리합니다.

### 비밀값

노출되면 인증이나 권한을 제공하는 값입니다.

```text
DATABASE_PASSWORD
REGISTRY_PULL_TOKEN
DNS_API_TOKEN
BACKUP_ENCRYPTION_KEY
SESSION_SIGNING_KEY
```

### 파생·단기 자격 증명

장기 원본에서 짧은 시간 동안 발급됩니다.

```text
OIDC로 교환한 클라우드 액세스 토큰
짧은 수명의 DB 자격 증명
일회용 부트스트랩 토큰
```

가능하면 장기 고정 비밀값보다 짧은 수명의 자격 증명을 사용합니다.

## 2. 비밀값을 넣지 말아야 할 곳

- Git 커밋과 과거 이력
- Dockerfile `ARG`·`ENV`
- 컨테이너 이미지 레이어
- Compose 파일의 리터럴 값
- CI 로그와 디버그 출력
- 셸 이력
- 프로세스 인자
- 모든 사용자가 읽을 수 있는 환경변수 덤프
- 백업 매니페스트의 평문 메타데이터

환경변수는 편리하지만 다음 경로로 노출될 수 있습니다.

- 프로세스 검사 권한을 가진 주체
- 크래시 리포트
- 디버그 엔드포인트
- 잘못된 로그
- 자식 프로세스
- 지원 도구의 환경변수 덤프

모든 환경변수가 곧바로 위험하다는 뜻은 아닙니다. 민감도와 플랫폼의 노출 모델을 이해하고 파일 디스크립터, 마운트 파일, 비밀값 관리 시스템 등을 선택합니다.

## 3. Compose 비밀값의 실제 경계

Compose는 비밀값을 서비스에 선언하고 컨테이너 내부의 `/run/secrets/<name>` 같은 파일로 제공할 수 있습니다.

```yaml
services:
  app:
    secrets:
      - db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt
```

중요한 점:

- 원본 파일은 호스트에 존재합니다.
- 단독 Compose 환경에서 이 기능은 호스트 원본을 자동으로 암호화된 비밀값 저장소에 저장하는 것과 같지 않습니다.
- 호스트 파일 권한과 백업 정책이 여전히 중요합니다.
- 비밀값을 허용받은 서비스에만 마운트해야 합니다.

Docker Swarm secret의 암호화·Raft 수명 주기와 단독 Compose 환경의 파일 기반 비밀값 전달 방식을 혼동하지 않습니다.

## 4. 비밀값 원본과 전달 경로

각 비밀값에 다음을 기록합니다.

| 항목 | 질문 |
|---|---|
| 이름 | 용도를 드러내고 값은 포함하지 않는가? |
| 원본 | 비밀번호 관리자, 클라우드 비밀값 관리 시스템, 오프라인 키 중 어디인가? |
| 발급자 | 누가 만들고 회전할 수 있는가? |
| 소비자 | 어떤 서비스와 사용자만 필요한가? |
| 전달 | CI, 프로비저닝, 에이전트 중 어떤 경로인가? |
| 저장 | 호스트에서 어디에 어떤 권한 모드로 저장되는가? |
| 수명 | 만료·회전 주기는 무엇인가? |
| 폐기 | 이전 값을 언제 비활성화하는가? |
| 복구 | 원본 손실 시 다시 발급 가능한가? |

운영 호스트에 있는 파일 하나만 유일한 원본이면 호스트 손실과 함께 복구 권한도 사라질 수 있습니다.

## 5. 호스트 파일 권한

예:

```text
/etc/example/secrets/
  db_password_v2
  session_key_v3
```

확인:

```sh
stat -c '%U %G %a %n' /etc/example/secrets/*
```

일반 원칙:

- 필요한 사용자·그룹만 읽습니다.
- 디렉터리 탐색 권한도 제한합니다.
- 애플리케이션은 비밀값 원본을 수정하지 못합니다.
- 백업 도구가 읽어야 한다면 별도 권한과 감사 경계를 둡니다.
- 값 생성 시 안전한 `umask`를 사용합니다.

`chmod 600`만으로 컨테이너 안의 실제 접근 주체까지 해결되는 것은 아닙니다. bind mount와 컨테이너 UID/GID 매핑을 확인합니다.

## 6. 시작 시 검증

필수 비밀값이 없거나 형식이 잘못됐다면 애플리케이션은 부분적으로 실행된 것처럼 보이지 않고 명확히 실패해야 합니다.

검증 항목:

- 파일 존재
- 읽기 권한
- 빈 값이 아님
- 예상 인코딩과 길이
- 허용된 버전
- 줄바꿈 처리
- 의존 서비스 인증 성공

실제 값은 오류 메시지에 출력하지 않습니다.

좋은 오류:

```text
required secret db_password_v2 is unreadable
```

나쁜 오류:

```text
login failed with password SuperSecret123!
```

## 7. 이름과 버전

`DB_PASSWORD` 하나를 제자리에서 덮어쓰면 어느 소비자가 새 값을 읽었는지 판단하기 어렵습니다.

```text
db_password_v1
db_password_v2
```

또는 메타데이터에 버전을 둡니다. 릴리스 매니페스트는 필요한 비밀값의 **이름과 버전**만 기록합니다.

```yaml
required_secrets:
  database_password: db_password_v2
  session_signing_key: session_key_v3
```

값 자체는 매니페스트에 넣지 않습니다.

## 8. 안전한 회전 패턴

### 두 자격 증명을 동시에 허용할 수 있는 경우

```text
1. 새 자격 증명 생성
2. 공급자에 이전 값과 새 값을 모두 유효하게 등록
3. 호스트에 새 비밀값 배포
4. 새 릴리스 또는 리로드로 소비자 전환
5. 새 자격 증명이 실제로 사용되는지 확인
6. 모든 소비자의 전환 확인
7. 이전 자격 증명 폐기
8. 폐기 뒤 스모크 테스트
```

### 하나의 비밀번호만 허용하는 데이터베이스

중단 없는 회전을 위해 별도 사용자 또는 임시 자격 증명을 사용할 수 있습니다.

```text
app_user_v1 유지
→ app_user_v2 생성·동일 최소 권한 부여
→ 애플리케이션을 v2로 전환
→ 연결 풀 교체 확인
→ v1 로그인 거부
→ v1 사용자 삭제
```

권한을 복사할 때 불필요한 권한까지 함께 복제하지 않습니다.

### 서명 키 회전

세션·토큰 서명 키는 검증과 발급 역할을 분리할 수 있습니다.

```text
새 키로 발급
+ 일정 기간 옛 키로 검증
→ 이전 토큰의 최대 수명 경과
→ 옛 키 제거
```

즉시 이전 키를 제거하면 모든 활성 세션을 강제로 종료할 수 있습니다. 보안 사고에서는 그 결과가 의도한 조치일 수 있습니다.

## 9. 회전의 완료 증거

파일이 바뀐 것만 확인하지 않습니다.

- 새 연결 또는 토큰이 새 자격 증명을 사용하는가?
- 오래 유지된 연결 풀이 이전 자격 증명으로 남아 있는가?
- 모든 인스턴스·워커가 리로드됐는가?
- 이전 자격 증명 사용 시 실제로 거부되는가?
- 배포·회전 이벤트가 기록됐는가?
- 로그와 지표에 비밀값이 노출되지 않았는가?

회전 뒤 일정 기간 이전 자격 증명의 사용 시도를 탐지하면 누락된 소비자를 찾을 수 있습니다.

## 10. CI 비밀값과 운영 런타임 비밀값

CI가 이미지를 빌드하는 데 필요한 권한과 운영 애플리케이션이 실행되는 데 필요한 권한을 분리합니다.

```text
CI 빌드:
- 소스 읽기
- 레지스트리 push
- attestation 기록

운영 호스트:
- 레지스트리 pull
- 런타임 비밀값 읽기
- 백업 쓰기

애플리케이션:
- DB 최소 권한
- 필요한 외부 API 권한 범위
```

CI가 런타임 DB 비밀번호를 알 필요가 없다면 제공하지 않습니다.

## 11. DNS와 백업 비밀값

### DNS API 토큰

- ACME TXT 레코드에 필요한 DNS 존만 허용합니다.
- 레코드 읽기·쓰기 범위를 가능한 한 제한합니다.
- 도메인 이전·계정 결제 권한과 분리합니다.
- 사용 로그와 만료를 확인합니다.

### 백업 암호화 키

백업 파일과 같은 호스트·같은 저장소에 유일한 복호화 키를 두지 않습니다. 키 복구 절차도 별도로 시험합니다.

암호화 키를 잃으면 정상 백업도 복원할 수 없습니다. 공격자가 백업과 키를 함께 얻으면 암호화 효과가 크게 줄어듭니다.

## 12. 로그와 진단에서 민감 정보 제거

다음 패턴을 검사합니다.

- 요청 헤더 전체 출력
- `Authorization`
- 쿠키
- 쿼리 문자열 토큰
- DB DSN
- 환경변수 덤프
- 예외 메시지에 포함된 자격 증명
- 셸 `set -x`

민감 정보 제거는 값이 저장된 뒤 삭제하는 것이 아니라 기록 전에 수행합니다. 엔트로피가 낮은 비밀값의 직접 해시는 사전 대입으로 원문을 추측할 수 있게 합니다. 상관관계 식별이 꼭 필요하면 공급자가 발급한 키 ID·버전을 우선 사용하고 값에서 식별자를 만들어야 한다면 별도의 감사용 키를 사용한 HMAC처럼 로그만으로 오프라인 추측하기 어려운 방식을 사용합니다.

## 13. 유출 대응

비밀값이 Git이나 로그에 노출되면 파일을 삭제하는 것만으로 끝나지 않습니다.

```text
1. 영향받은 비밀값 식별
2. 사용 권한과 접근 가능 기간 확인
3. 즉시 폐기 또는 제한
4. 새 자격 증명 발급
5. 소비자 전환
6. 이전 자격 증명 사용 탐지
7. Git·로그·산출물의 잔존 범위 처리
8. 원인과 예방 조치 기록
```

Git 이력에서 값을 제거하기 전에 먼저 자격 증명을 폐기합니다. 이미 복제된 저장소나 캐시는 되돌릴 수 없습니다.

## 14. 비상 자격 증명

자동화와 일반 관리자 경로가 모두 실패했을 때 사용할 비상 권한이 필요할 수 있습니다.

조건:

- 평소에는 사용하지 않습니다.
- 강한 별도 보관과 접근 승인이 있습니다.
- 사용 시 즉시 알림과 감사 기록이 생깁니다.
- 사용 뒤 반드시 회전합니다.
- 정기적으로 접근 가능성과 절차를 시험합니다.

비상 자격 증명이 편리한 상시 우회 경로가 되어서는 안 됩니다.

## 15. 실습

[`exercises/13-secret-rotation`](../exercises/13-secret-rotation/)은 임시 호스트 루트에서 버전이 있는 비밀값을 회전합니다.

학습자는 다음 계약을 구현합니다.

1. 안전한 권한으로 새 버전 생성
2. 값 자체를 이벤트 로그에 기록하지 않음
3. 새 소비자를 검증하기 전 현재 포인터(`current`)를 바꾸지 않음
4. 현재 버전을 원자적으로 전환
5. 검증 실패 시 이전 버전 유지
6. 전환 확인 뒤에만 이전 버전 폐기 가능
7. 실제 비밀값 대신 지문과 메타데이터만 출력

실습은 외부 비밀값 관리 제품을 흉내 내지 않습니다. 모든 구현에 필요한 회전 순서와 실패 후 상태를 검증합니다.
