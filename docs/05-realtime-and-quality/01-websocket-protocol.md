# WebSocket 프로토콜

HTTP 요청은 한 번의 요청과 응답으로 끝나지만 WebSocket 연결은 오래 유지되며 클라이언트와 서버가 언제든 메시지를 보낼 수 있습니다. 연결이 열렸다는 사실만으로는 사용자가 어떤 보드에 참가했는지, 마지막으로 어떤 상태를 받았는지, 현재 어떤 권한을 가졌는지 알 수 없습니다. 연결, 세션, 방, 메시지의 상태를 명시적으로 관리해야 합니다.

## 목표

- HTTP 업그레이드와 WebSocket 연결의 수명을 구분합니다.
- 클라이언트와 서버 메시지를 판별 가능한 계약으로 정의합니다.
- 연결별 인증 정보, 참가 상태, 정리 책임을 관리합니다.
- ping·pong, 타임아웃, 역압, 메시지 제한을 적용합니다.
- 정상 종료, 오류, 재연결 이후의 상태 복구 흐름을 설명합니다.

## 연결 시작

브라우저는 HTTP 요청으로 WebSocket 업그레이드를 요청합니다.

```text
GET /ws HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Origin: https://app.example.com
Cookie: app_session=...
```

서버는 업그레이드 전에 다음 항목을 확인합니다.

- 허용된 `Origin`
- 세션 토큰과 만료 여부
- 계정 상태
- 사용자별 최대 연결 수와 서버 준비 상태

연결이 열린 뒤에도 사용자가 특정 보드의 구성원이라고 가정해서는 안 됩니다. 클라이언트가 `board.join` 메시지를 보내면 서버가 멤버십을 다시 확인한 뒤 해당 방에 연결을 등록합니다.

## 메시지는 판별 가능한 유니언으로 정의합니다

```ts
const ClientMessageSchema = z.discriminatedUnion("type", [
  z.object({
    type: z.literal("board.join"),
    boardId: z.string().uuid()
  }),
  z.object({
    type: z.literal("cursor.move"),
    boardId: z.string().uuid(),
    x: z.number().finite(),
    y: z.number().finite()
  }),
  z.object({
    type: z.literal("item.move"),
    boardId: z.string().uuid(),
    itemId: z.string().uuid(),
    baseVersion: z.number().int().nonnegative(),
    x: z.number().finite(),
    y: z.number().finite(),
    final: z.boolean()
  })
]);
```

수신한 문자열을 JSON으로 파싱하는 단계와 스키마로 검증하는 단계를 분리합니다. 잘못된 메시지 하나가 프로세스 전체의 예외나 다른 연결의 종료로 이어지지 않게 처리합니다.

## 메시지 봉투

프로토콜이 확장되면 도메인 데이터 외에도 메시지를 추적할 식별자가 필요할 수 있습니다.

```ts
interface Envelope<T> {
  type: string;
  messageId: string;
  sentAt: string;
  payload: T;
}
```

다음 식별자를 서로 혼동하지 않습니다.

- `messageId`: 한 번 전송한 메시지를 추적하는 식별자
- `operationId`: 한 사용자의 변경 시도를 추적하는 식별자
- `itemId`: 도메인 리소스의 식별자
- `sequence`: 보드에서 확정된 변경의 순서
- `version`: 특정 리소스의 낙관적 동시성 번호

모든 메시지에 이 값이 전부 필요한 것은 아닙니다. 복구, 중복 제거, 추적에 실제로 사용하는 항목만 계약에 포함합니다.

## 연결 상태

서버는 소켓 객체만 모아 두지 말고 연결별 문맥을 관리합니다.

```ts
interface ConnectionContext {
  socket: WebSocket;
  actorId: string;
  joinedBoardIds: Set<string>;
  alive: boolean;
  queuedBytes: number;
}
```

방 참가와 퇴장은 공통 함수로 관리하고, 소켓이 종료되면 모든 방 인덱스에서 해당 연결을 제거합니다. 연결 목록에는 남아 있지만 방 목록에는 없는 유령 연결이나 그 반대 상태가 생기지 않게 합니다.

## 참가와 초기 상태 동기화

```text
연결 성공
→ 클라이언트: board.join
→ 서버: 세션·멤버십 확인
→ 서버: board.snapshot
→ 이후 board.patch 수신
```

스냅샷을 받기 전에 패치를 적용하면 기준 상태가 없습니다. 서버는 참가 처리 도중 발생한 변경을 어떤 순서로 전달할지 정해야 합니다. 작은 구현에서는 스냅샷을 만든 시점의 시퀀스를 함께 보내고, 클라이언트가 그 이후의 패치만 적용하게 할 수 있습니다.

## 메시지 크기와 전송 빈도

WebSocket은 연결이 오래 유지되므로 한 클라이언트가 큰 JSON이나 초당 수천 개의 메시지를 보내 서버 자원을 소모할 수 있습니다.

- 최대 프레임·메시지 크기
- 초당 메시지 수
- 보드별·사용자별 최대 연결 수
- JSON 파싱 전 원시 바이트 제한
- 좌표 범위와 문자열 길이
- 압축 사용 시 메모리와 CPU 비용

`cursor.move`처럼 전송 빈도가 높은 이벤트는 마지막 값만 의미가 있을 수 있습니다. 모든 중간 메시지를 큐에 쌓기보다 합치거나 버릴 수 있는 정책을 정합니다.

## 역압

소켓의 송신 버퍼가 계속 증가하면 느린 클라이언트 하나가 서버 메모리를 과도하게 점유할 수 있습니다.

```text
bufferedAmount가 임계값 미만 → 전송
일시적으로 임계값 초과      → 임시 이벤트 삭제 또는 전송 중단
계속 임계값 초과             → 연결 종료 후 재동기화
```

확정된 `board.patch`를 조용히 버려서는 안 됩니다. 느린 클라이언트의 연결을 종료하고 재연결 시 스냅샷으로 복구하게 하는 편이 더 명확할 수 있습니다. 커서처럼 일시적인 상태는 최신 값만 유지할 수 있습니다.

## 하트비트

네트워크가 끊겨도 TCP 연결이 즉시 닫히지 않을 수 있습니다. 서버는 ping을 보내고 pong을 받은 연결만 살아 있는 것으로 표시합니다.

```text
주기 시작
→ 모든 연결의 alive=false 설정 후 ping 전송
→ pong 수신 시 alive=true
→ 다음 주기에도 false인 연결 종료
```

하트비트 타이머는 서버 종료와 테스트 정리 과정에서 반드시 해제합니다. 애플리케이션 수준의 하트비트를 별도로 사용한다면 프로토콜 메시지와 WebSocket 제어 프레임의 역할을 구분합니다.

## 오류 메시지와 연결 종료

입력 하나가 잘못되었다고 모든 경우에 연결을 닫을 필요는 없습니다.

```ts
{
  type: "operation.rejected",
  operationId: "...",
  code: "stale_item",
  message: "최신 상태를 다시 불러와 주세요."
}
```

반면 인증 만료, 허용되지 않은 출처, 반복되는 프로토콜 위반, 메시지 크기 초과는 연결 종료 사유가 될 수 있습니다. 종료 코드와 클라이언트의 재연결 가능 여부를 문서화합니다.

## 정상 종료

서버를 배포하거나 종료할 때는 다음 순서를 따릅니다.

1. 새 업그레이드 요청 수락을 중단합니다.
2. 필요하면 클라이언트에 종료 예정 또는 재연결 신호를 보냅니다.
3. 진행 중인 확정 작업을 제한된 시간 안에 마칩니다.
4. 소켓을 닫습니다.
5. 방 인덱스와 하트비트 타이머를 정리합니다.
6. 데이터베이스와 HTTP 서버를 닫습니다.

강제 종료 전에 무제한 기다리지 않도록 전체 종료 제한 시간을 둡니다.

## 재연결

클라이언트는 연결이 끊긴 이유를 분류하고 상한이 있는 지수 백오프와 무작위 지연을 사용해 재연결합니다.

```text
0.5초 → 1초 → 2초 → 4초 → 최대 간격
```

인증 실패나 명시적인 접근 거부를 네트워크 오류처럼 무한히 재시도해서는 안 됩니다. 재연결 후에는 메모리에 남은 이전 상태를 그대로 신뢰하지 않고 다시 방에 참가해 스냅샷을 받습니다.

## 흔한 오류

- 연결 성공을 보드 참가 완료와 같은 상태로 취급합니다.
- JSON 파싱이나 스키마 검증 실패를 프로세스 수준의 예외로 만듭니다.
- 소켓 종료 후 방 인덱스에서 연결을 제거하지 않습니다.
- 메시지 크기, 전송 빈도, 송신 버퍼에 제한이 없습니다.
- 테스트와 서버 종료 시 하트비트 타이머를 정리하지 않습니다.
- 재연결 후 이전 상태에 패치만 계속 적용합니다.
- 인증 실패도 무한히 재연결합니다.
