# CLI 검사기 설계

## 학습 목표

이 문서를 마치면 다음 내용을 설명하고 구현할 수 있어야 합니다.

- 명령줄 프로그램을 검사할 때 확인해야 하는 외부 동작
- 입력 명세 오류와 실행 결과 불일치의 구분
- 프로세스 실행, 결과 비교, 보고서 생성을 분리한 모듈 구조
- 제한 시간과 출력 상한을 포함한 프로세스 정리 절차
- 병렬 실행 중에도 입력 순서를 유지하는 결과 집계 방식

## 선행 개념

- 파일과 JSON 입력 검증
- `subprocess`를 사용한 외부 프로세스 실행
- 제한된 동시 실행과 자원 정리
- 단위·통합·종단 간 테스트의 역할
- 의도된 실패와 구현 오류의 구분

## 검사 범위

함수를 직접 호출하는 단위 테스트만으로는 명령줄 프로그램이 실제로 제공하는 동작을 모두 확인할 수 없습니다.

```text
명령줄 인자 경계
현재 작업 디렉터리
환경 변수
stdin
stdout
stderr
종료 상태
제한 시간
자식 프로세스 수명
보고서 저장
```

누적 실습 [`command-checker`](../../exercises/command-checker/README.md)는 이 항목을 단계별로 구현합니다.

## 최종 인터페이스

`workspace/`를 `make install-workspace`로 준비된 가상 환경에 설치한 뒤 실제 콘솔 스크립트를 실행합니다.

```text
command-checker --cases CASES [--jobs N]
                [--json-report PATH]
                [--junit-report PATH]
                -- COMMAND [ARG ...]
```

사례 파일은 다음과 같은 JSON 배열입니다.

```json
[
  {
    "name": "ascending",
    "args": [],
    "stdin": "3 1 2\n",
    "stdout": "1\n2\n3\n",
    "stderr": "",
    "returncode": 0,
    "timeout": 2.0,
    "output_limit": 1048576
  }
]
```

## 상태와 실패 유형

### 입력·실행 환경 오류

다음 문제는 검사 대상 프로그램의 결과 불일치가 아니라 검사 자체를 정상적으로 수행할 수 없는 오류입니다.

- JSON 문법 오류
- 필드 타입 오류
- 중복된 사례 이름
- 존재하지 않는 작업 디렉터리
- 잘못된 환경 변수 이름이나 값
- 실행 파일을 찾을 수 없거나 실행할 수 없음
- 보고서 경로에 결과를 저장할 수 없음

이 경우 전체 종료 상태로 2를 사용합니다.

### 실행 결과 불일치

검사 대상 프로그램을 실행하고 관찰했지만 기대와 다른 경우입니다.

- `returncode` 불일치
- `stdout` 불일치
- `stderr` 불일치
- 제한 시간 초과
- 출력 상한 초과

각 사례를 `Result(passed=False, ...)`로 기록하고 전체 종료 상태로 1을 사용합니다.

### 성공

모든 사례의 결과가 기대값과 일치하면 종료 상태 0을 사용합니다.

이 구분이 유지되어야 사용자가 사례 파일이나 실행 환경을 고쳐야 하는지, 검사 대상 프로그램을 고쳐야 하는지 판단할 수 있습니다.

## 모듈별 책임

| 모듈 | 책임 |
|---|---|
| `model.py` | 불변 `Case`, `Result`, 입력·실행 오류 예외 정의 |
| `comparison.py` | 종료 상태·표준 출력·표준 오류와 기대값의 순수 비교 |
| `specification.py` | JSON을 검증된 `Case`로 변환 |
| `process.py` | 프로세스·파이프·마감 시각·신호 처리와 정리 |
| `reports.py` | JSON·JUnit 직렬화와 원자적 파일 교체 |
| `runner.py` | 사례 실행 순서, 병렬 실행, 결과 출력, 종료 상태 결정 |
| `cli.py` | `argparse`, 사용자 오류 메시지, 전체 기능 조립 |

의존 방향은 다음과 같습니다.

```text
model ← comparison
model ← specification
model ← process
model ← reports
cli → specification, runner, reports
runner → process
```

`process.py`가 터미널 출력 문구를 결정하거나 `reports.py`가 직접 명령을 실행한다면 책임이 다시 섞인 것입니다.

## 단계별 구현

### 1단계: 패키지와 진입점

제공된 `__main__.py`와 패키징 뼈대는 모듈 실행과 설치된 `command-checker` 콘솔 스크립트를 같은 `cli.main` 함수로 연결합니다. 학습자는 `cli.py`의 파서와 `main()`을 구현합니다.

- 도움말: `stdout`, 종료 상태 0
- 사용법 오류: `stderr`, 종료 상태 2

### 2단계: 데이터 모델

여러 모듈과 워커가 공유하는 데이터를 불변 타입으로 만듭니다. 환경 변수는 가변 `dict` 대신 정렬된 튜플 쌍으로 저장합니다.

### 3단계: 결과 비교

`returncode`, `stdout`, `stderr`를 각각 정확하게 비교하는 순수 함수를 작성합니다. 공백과 줄바꿈도 결과의 일부로 취급합니다.

### 4단계: 명세 검증

JSON 문법뿐 아니라 허용 필드, 실제 타입, 숫자 범위, 경로 기준, 환경 변수 문자열 제약을 확인합니다.

### 5단계: 사례 한 건 실행

명령과 인자의 경계를 보존하고 `stdin`, `cwd`, 환경 변수를 전달합니다. 실행이 끝나면 세 결과 항목을 수집합니다.

### 6단계: 전체 사례 집계

사례 하나가 실패해도 나머지를 계속 실행합니다. 결과는 명세 파일의 입력 순서대로 표시하고 전체 종료 상태를 한곳에서 결정합니다.

### 7단계: 프로세스 수명 제한

POSIX 프로세스 그룹, 논블로킹 파이프, 절대 마감 시각, 스트림별 출력 상한을 추가합니다. 제한을 넘으면 자식 프로세스와 파이프까지 정리합니다.

### 8단계: 병렬 실행과 보고서

동시에 실행할 사례 수를 제한하고 완료 순서와 관계없이 입력 순서를 유지합니다. 같은 `Result` 목록에서 JSON과 JUnit을 생성하고, 완성된 임시 파일을 최종 경로로 원자적으로 교체합니다.

마지막으로 공개 API의 타입 어노테이션, `py.typed`, 패키지 메타데이터, 설치된 콘솔 스크립트도 검사합니다.

## 검증 방법

각 단계 검사는 이전 단계까지 포함합니다.

```sh
make stage-01 EXERCISE_IMPL=workspace
make stage-02 EXERCISE_IMPL=workspace
...
make stage-08 EXERCISE_IMPL=workspace
```

참고 구현과 저장소 전체 구성은 다음 명령으로 검증합니다.

```sh
./verify.sh
```

검증 항목은 다음과 같습니다.

- 패키지 `import`와 `-m` 모듈 실행
- 격리된 가상 환경에 설치한 `command-checker` 콘솔 스크립트
- 공개 API 타입 어노테이션과 `py.typed`
- 불변 데이터 모델
- 종료 상태·표준 출력·표준 오류의 정확한 비교
- 잘못된 JSON과 필드 검증
- `cwd`·환경 변수·인자 경계
- 사례 하나가 실패한 뒤에도 다음 사례 실행
- 제한 시간 초과 후 자식 프로세스 제거
- `stdout`·`stderr` 출력 상한
- 병렬 작업의 완료 순서 역전
- JSON·JUnit 보고서의 결과 일관성
- 기존 보고서 보존과 임시 파일 정리
- `skeleton/`이 의도된 첫 미구현 지점에서 실패하는지 여부

## 한계

- Windows 네이티브 프로세스 트리 종료는 구현하지 않습니다.
- 셸 파이프라인 문법을 해석하지 않습니다. 명령은 이미 분리된 인자 목록으로 받습니다.
- `stdout`과 `stderr`의 원본 바이트를 그대로 보존하지 않고 UTF-8 텍스트로 검사합니다. 디코딩할 수 없는 바이트는 대체 문자로 변환합니다.
- 원격 실행, 컨테이너 오케스트레이션, 분산 테스트 스케줄링은 범위에 포함하지 않습니다.

## 연결 실습

- [command-checker 전체 실습](../../exercises/command-checker/README.md)을 1단계부터 8단계까지 순서대로 구현합니다.
- `workspace/` 전체 검사를 통과하고 각 설계 선택을 설명한 뒤 처음으로 최종 `reference/` 구현과 비교합니다.
- 완성한 `workspace/` 명령을 설치한 뒤 저장소 루트의 `./verify.sh`로 전체 구성을 검증합니다.

## 완료 기준

- 입력·실행 환경 오류와 실행 결과 불일치를 구분합니다.
- 프로세스 실행과 결과 비교를 독립적으로 테스트할 수 있습니다.
- 프로세스와 모든 파이프를 누가 정리하는지 명확합니다.
- 제한 시간이나 출력 상한을 초과해도 자식 프로세스가 남지 않습니다.
- 병렬 실행이 사용자에게 표시하는 결과 순서를 바꾸지 않습니다.
- 보고서 파일은 전체 내용이 완성된 뒤에만 최종 경로로 교체됩니다.
- `./verify.sh` 하나로 저장소 전체를 확인할 수 있습니다.
