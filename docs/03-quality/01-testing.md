# 재현 가능한 테스트

## 학습 목표

좋은 테스트는 입력 개수가 많은 테스트가 아니라 어떤 동작과 실패 조건을 확인하는지 설명할 수 있는 테스트입니다. `command-checker`의 모든 단계는 이 장의 원칙을 적용합니다.

## 선행 개념

- 외부 상태에 의존하지 않는 순수 로직과 파일·프로세스 I/O를 구분할 수 있어야 합니다.
- 정상 사례, 경계 사례, 실패 사례를 나누어 생각할 수 있어야 합니다.

## 핵심 로직과 부작용 분리하기

```python
def normalize_words(text: str) -> list[str]:
    return sorted({word.lower() for word in text.split()})
```

위 함수는 파일이나 프로세스 없이 직접 테스트할 수 있습니다.

```python
import unittest


class NormalizeWordsTest(unittest.TestCase):
    def test_removes_duplicates_and_sorts(self) -> None:
        self.assertEqual(normalize_words("B a b"), ["a", "b"])
```

CLI 진입점처럼 실제 실행 환경까지 확인해야 하는 부분은 소수의 종단 간 테스트로 보완합니다.

## 테스트 수준 구분하기

| 수준 | 확인하는 범위 | 예시 |
|---|---|---|
| 단위 테스트 | 함수나 타입 하나의 동작 | 종료 상태·표준 출력·표준 오류 비교 |
| 통합 테스트 | 여러 모듈과 실제 자원의 연결 | JSON 파일 읽기와 보고서 저장 |
| 종단 간 테스트 | 사용자가 실행하는 최종 진입점 | `python -m command_checker` 또는 설치된 콘솔 스크립트 |

모든 테스트를 하위 프로세스로 실행하면 느리고 실패 원인을 찾기 어렵습니다. 반대로 단위 테스트만 작성하면 명령줄 인자, `cwd`, 환경 변수, 출력 스트림, 종료 상태 같은 실제 실행 조건이 빠집니다.

## 경곗값과 분기 겨냥하기

일반적으로 다음 사례를 확인합니다.

- 빈 입력과 최소 입력
- 중복 값
- 마지막 원소에서만 상태가 바뀌는 경우
- 정상값과 오류값이 갈리는 경계의 바로 앞·뒤 값
- 잘못된 타입과 허용하지 않은 필드
- 존재하지 않는 파일과 권한 오류
- 제한 시간 초과와 출력 상한 초과
- 일부 작업이 성공한 뒤 발생하는 정리 실패

예제 입력을 단순히 여러 개 복사하기보다 각 테스트가 어떤 분기와 불변식을 확인하는지 이름과 설명에 드러냅니다.

## 표 기반 테스트

```python
cases = [
    ("", []),
    ("a", ["a"]),
    ("B a b", ["a", "b"]),
]

for input_text, expected in cases:
    with self.subTest(input_text=input_text):
        self.assertEqual(normalize_words(input_text), expected)
```

테스트가 실패했을 때는 입력, 기대값, 실제값을 확인할 수 있어야 합니다.

## 작은 입력 공간 전수 검사하기

입력 공간이 충분히 작다면 모든 조합을 확인할 수 있습니다.

```python
from itertools import product

for values in product(range(3), repeat=4):
    self.assertEqual(optimized(values), reference(values))
```

입력 크기가 커지면 조합 수가 기하급수적으로 증가합니다. 가능한 조합 수를 계산한 뒤 전수 검사가 현실적인 범위에서만 사용합니다.

## 재현 가능한 무작위 테스트

```python
import random

rng = random.Random(4242)
for _ in range(500):
    values = [
        rng.randint(-100, 100)
        for _ in range(rng.randint(0, 30))
    ]
    self.assertEqual(optimized(values), reference(values))
```

난수 시드를 고정하고, 실패 시 실제 입력도 출력해야 합니다. 여러 테스트가 전역 난수 상태를 공유하면 실행 순서에 따라 결과가 달라질 수 있으므로 테스트 전용 난수 생성기를 사용합니다.

## 독립적인 기준 구현 사용하기

최적화한 구현과 기준 구현은 동작 명세만 공유하는 편이 좋습니다. 양쪽이 같은 내부 헬퍼를 재사용하면 동일한 버그가 두 구현에 함께 들어가 잘못된 결과가 통과할 수 있습니다.

`command-checker`에서는 프로세스 실행 코드와 결과 비교 코드를 분리합니다. 프로세스 수집 코드는 비교 규칙을 다시 구현하지 않고, 수집한 값을 순수 비교 함수에 전달합니다.

## 실패 주입하기

정상 경로만 테스트하면 자원 정리와 오류 처리 동작을 확인할 수 없습니다.

- 파일 기록 중 예외 발생
- `os.replace()` 실패
- 실행 파일을 찾을 수 없음
- 부모 프로세스는 종료됐지만 자식이 파이프를 계속 열어 둠
- `stdout`을 무한히 출력함
- 워커 하나에서 예외가 발생함

실패를 반복해서 재현할 수 있도록 모의 객체, 임시 디렉터리, 전용 `fixture`를 사용합니다.

## `skeleton/` 검증하기

`skeleton/`이 단순히 모든 테스트에서 무작위로 실패해서는 안 됩니다.

- 패키지와 모듈을 정상적으로 `import`할 수 있어야 합니다.
- 현재 단계에서 처음 구현하지 않은 책임이 명확한 `NotImplementedError`를 발생시켜야 합니다.
- 문법 오류나 누락된 `fixture` 때문에 실패해서는 안 됩니다.
- 새 단계를 구현한 뒤에도 이전 단계 테스트가 계속 통과해야 합니다.

루트 `verify.sh`는 각 단계의 스켈레톤을 직접 실행해 약속한 `NotImplementedError` 메시지에서 정확히 멈추는지 확인합니다. `stage-N` 명령은 1단계부터 N단계까지 누적 실행되므로 이전 단계의 회귀도 같은 명령에서 발견됩니다.

## 환경에 의존하는 테스트

POSIX 프로세스 그룹 테스트는 macOS와 Linux에서 실행합니다. 다른 운영체제에서는 해당 기능이 지원 범위 밖임을 명확히 표시해야 합니다. 환경 차이 때문에 실행하지 않은 테스트를 성공한 것으로 처리해서는 안 됩니다.

## 연결 실습

- [단계별 공개 테스트](../../exercises/command-checker/README.md)는 학습자가 수정하는 코드가 아니라 저장소에서 제공하는 검증 코드입니다.
- 같은 공개 동작을 `workspace/`와 `reference/`에 적용하고, 의도적으로 결함을 주입한 각 구현이 어떤 테스트에서 거부되는지 확인합니다.

## 완료 기준

- 각 테스트 이름이 확인하려는 동작을 설명합니다.
- 단위·통합·종단 간 테스트가 역할에 따라 분리되어 있습니다.
- 경곗값과 실패 경로를 반복해서 재현할 수 있습니다.
- 무작위 테스트는 시드와 실제 실패 입력을 남깁니다.
- `skeleton/`과 `reference/`를 서로 다른 기준으로 검증합니다.
