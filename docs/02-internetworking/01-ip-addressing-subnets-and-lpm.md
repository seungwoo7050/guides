# IP 주소, subnet과 라우팅 조회

IP 주소는 호스트의 영구 이름이라기보다 특정 네트워크 인터페이스와 경로에서 사용하는 논리적 위치입니다. CIDR prefix는 주소 비트 가운데 네트워크 범위를 나타내는 길이를 정하고, 라우팅 테이블은 목적지와 일치하는 후보 중 가장 구체적인 prefix를 선택합니다.

## 학습 목표

- CIDR prefix로 주소 범위와 동일 링크 여부를 계산합니다.
- 최장 프리픽스, metric과 입력 순서의 경로 선택 우선순위를 적용합니다.

## 선행 개념

2진수와 비트 AND의 기본 연산, [ARP와 Neighbor Discovery](../01-link-and-path/03-arp-and-neighbor-discovery.md)의 다음 홉 개념이 필요합니다.

## 주소와 prefix를 함께 읽기

`192.0.2.10/24`에서 `/24`는 앞 24비트가 prefix임을 뜻합니다.

```text
주소:      192.0.2.10
네트워크: 192.0.2.0
프리픽스: /24
IPv4 mask: 255.255.255.0
```

CIDR에서는 옛 Class A/B/C 분류로 범위를 추측하지 않습니다. `/20`, `/27`, `/31`처럼 필요한 프리픽스 길이를 직접 사용합니다. 두 주소가 같은 서브넷인지 판단할 때도 문자열의 앞 옥텟 수가 아니라 프리픽스 마스크를 적용한 네트워크 값을 비교합니다.

IPv4의 네트워크와 브로드캐스트 주소 사용 규칙은 프리픽스와 링크 유형에 따라 달라집니다. `/31` 지점 간 연결과 `/32` 호스트 경로를 일반 LAN의 “첫 주소와 마지막 주소는 항상 사용 불가” 규칙에 억지로 맞추지 않습니다.

## 호스트는 먼저 직접 연결 여부를 판단합니다

호스트는 목적지 주소에 대해 라우팅 테이블을 조회합니다. 일치한 경로가 직접 연결 경로이면 목적지 자체를 이웃 조회 대상으로 사용하고, 게이트웨이 경로이면 지정된 다음 홉을 사용합니다.

```text
10.20.30.0/24 dev lan0
0.0.0.0/0 via 10.20.30.1 dev lan0
```

`10.20.30.50`은 직접 연결 경로와 일치하고, `203.0.113.9`는 기본 경로를 사용합니다. 두 경우 모두 Ethernet 목적지 MAC을 찾는 대상은 경로 조회 결과로 정해집니다.

## 최장 프리픽스 일치가 메트릭보다 먼저입니다

다음 route가 있다고 가정합니다.

```text
0.0.0.0/0       via 203.0.113.1 dev wan0 metric 10
10.0.0.0/8      via 10.0.0.1    dev core0 metric 100
10.20.0.0/16    via 10.20.0.1   dev branch0 metric 50
10.20.30.0/24   dev lan0                      metric 500
```

목적지 `10.20.30.8`에는 네 경로가 모두 일치하지만 `/24`가 가장 길어 `lan0`이 선택됩니다. 더 낮은 메트릭의 기본 경로가 더 구체적인 경로를 이기지 않습니다. 메트릭과 프로토콜별 선호도는 같은 프리픽스 길이의 후보를 비교하는 다음 단계에서 사용됩니다.

라우팅 제품과 운영체제는 정책 기반 라우팅, 출발지 주소, VRF, 테이블 우선순위 같은 추가 조건을 사용할 수 있습니다. 목적지 최장 프리픽스 일치라는 기본 원리를 이해한 뒤 해당 구현의 선택 순서를 확인하세요.

## 기본 route도 `/0` prefix입니다

IPv4 `0.0.0.0/0`과 IPv6 `::/0`은 아무 경로도 없을 때 사용하는 특별한 if문이 아니라 모든 주소에 일치하는 가장 덜 구체적인 prefix입니다. 더 구체적인 경로가 있으면 그것이 우선합니다.

기본 경로가 없다는 것은 로컬 서브넷 밖으로 나갈 일반 경로가 없다는 뜻입니다. DNS가 외부 주소를 돌려줘도 경로 조회에서 실패할 수 있습니다.

## IPv6 주소에서 추가로 볼 범위

IPv6는 128비트 주소와 프리픽스를 사용합니다. 한 인터페이스는 링크 로컬, 전역 또는 고유 로컬 등 여러 주소를 가질 수 있으며 출발지 주소 선택 절차가 실제 출발지 주소를 고릅니다.

링크 로컬 주소 `fe80::/10`은 링크 범위이므로 같은 값이 여러 인터페이스에 존재할 수 있습니다. 명령과 API에서 범위 ID 또는 인터페이스를 함께 지정해야 할 수 있습니다.

IPv6에는 일반적인 서브넷 브로드캐스트가 없고 멀티캐스트를 사용합니다. 라우터는 IPv6 패킷을 단편화하지 않으며 이 차이는 다음 장의 MTU 처리와 연결됩니다.

## 코드로 LPM 검증하기

먼저 읽기 전용 경로 입력에서 결과를 손으로 예상하고, root README 순서 6에서 `workspace/protocol_inspector/routing.py`를 구현해 공개 검사로 확인합니다.

```sh
cd exercises/protocol-inspector
PYTHONPATH=workspace python3 -m unittest tests.test_routing -v
```

직접 구현할 때는 각 route가 목적지를 포함하는지 검사한 뒤 다음 순서로 비교합니다.

```text
1. 프리픽스 길이가 큰 후보
2. 프리픽스 길이가 같으면 메트릭이 작은 후보
3. 두 값도 같으면 명시한 결정 규칙
```

실습은 먼저 추가된 경로를 마지막 동률 결정 기준으로 사용합니다. 실제 운영체제가 같은 규칙을 쓴다고 일반화하지 말고 해당 플랫폼의 경로 선택 문서를 확인하세요.

## 경로 조회 결과를 운영체제에서 확인하기

Linux:

```sh
ip address show
ip route show table all
ip route get 203.0.113.9
ip -6 route get 2001:db8::10
```

macOS:

```sh
ifconfig
netstat -rn
route -n get 203.0.113.9
route -n get -inet6 2001:db8::10
```

전체 테이블을 보는 것과 특정 목적지의 실제 선택 결과를 보는 것은 다릅니다. 정책 규칙, 출발지 주소와 인터페이스 범위가 있으면 `route get` 형태의 질의가 더 직접적인 증거가 됩니다.

## 프리픽스 계산에서 자주 생기는 오류

- 호스트 주소를 네트워크 프리픽스로 저장하면서 호스트 비트를 그대로 비교하는 오류
- 문자열 접두사 비교로 서브넷 포함 관계를 판단하는 오류
- 더 낮은 metric을 더 긴 prefix보다 먼저 적용하는 오류
- 기본 gateway가 항상 같은 인터페이스에 하나만 있다고 가정하는 오류
- IPv6 링크 로컬 주소에서 인터페이스 범위를 누락하는 오류

실습의 `Route.from_strings`는 `strict=False`로 호스트 비트가 있는 입력을 네트워크 주소로 정규화합니다. 설정 검증 도구에서는 이를 자동 보정할지 오류로 거부할지 계약을 명시해야 합니다.
