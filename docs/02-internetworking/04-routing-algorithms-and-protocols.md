# 라우팅 알고리즘과 프로토콜

라우팅 테이블 조회는 이미 만들어진 경로를 데이터 평면에서 선택하는 일입니다. 동적 라우팅은 여러 라우터가 도달 가능성, 비용과 정책을 교환해 그 테이블을 만드는 제어 평면의 일입니다. 최장 프리픽스 일치와 라우팅 프로토콜의 경로 학습을 같은 단계로 취급하지 않습니다.

## 학습 목표

- 경로 학습·선택·설치와 실제 패킷 전달을 별도 단계로 기록합니다.
- distance-vector, link-state와 path-vector가 교환하는 정보를 구분합니다.

## 선행 개념

[최장 프리픽스 경로 조회](01-ip-addressing-subnets-and-lpm.md)와 그래프의 경로·비용 개념이 필요합니다.

## 데이터 평면과 제어 평면

```text
제어 평면
이웃 관계와 토폴로지 정보 수집
→ 후보 경로 계산과 정책 적용
→ 전달 테이블 설치

데이터 평면
패킷 목적지 읽기
→ 전달 테이블에서 최장 프리픽스 일치
→ next hop과 출력 interface로 전달
```

제어 평면이 잠시 불안정해도 이미 설치된 경로로 패킷이 계속 전달될 수 있고, 반대로 제어 평면이 경로를 알고 있어도 하드웨어 테이블 설치 실패로 데이터 평면이 다를 수 있습니다. 장애 조사에서는 라우팅 정보 기반과 전달 정보 기반을 구분해 확인합니다.

## 유니캐스트 라우팅의 범위

유니캐스트 패킷은 하나의 목적지 주소를 향합니다. 라우터는 그 주소에 대한 경로를 조회해 한 다음 홉 또는 ECMP 후보 가운데 하나로 패킷을 전달합니다. ECMP가 여러 경로를 보유하더라도 보통 하나의 유니캐스트 패킷을 모든 경로에 복제하지는 않습니다.

브로드캐스트는 한 링크의 여러 수신자에게 전달하는 범위이고, 멀티캐스트는 그룹 주소와 배포 트리를 사용합니다. 이 가이드는 일반적인 유니캐스트 전달과 경로 학습을 중심으로 하며 멀티캐스트 라우팅 프로토콜과 애니캐스트 운영은 별도 범위로 둡니다. 애니캐스트는 여러 위치가 같은 유니캐스트 프리픽스를 광고하고 라우팅 정책이 선택한 위치 하나에 도달하게 하는 배치 방식입니다. 그 위치는 흔히 토폴로지상 가깝지만 지리적으로 가장 가깝다고 보장되지는 않습니다.

## 정적 route의 장점과 한계

정적 route는 변화가 적고 경로가 단순한 환경에서 예측하기 쉽습니다. 그러나 링크와 장비 수가 늘면 다음 문제가 생깁니다.

- 모든 도달 범위를 수동으로 추가하고 제거해야 합니다.
- 장애 뒤 우회 경로로 자동 수렴하지 않습니다.
- 잘못된 next hop과 상호 모순되는 route가 누적될 수 있습니다.
- 여러 관리자가 같은 prefix의 의도를 다르게 해석할 수 있습니다.

동적 라우팅은 이 문제를 줄이지만 프로토콜 인접 관계, 메트릭, 타이머, 인증, 정책과 수렴 과정이라는 새 상태를 만듭니다. 규모가 작다는 이유만으로 무조건 정적 경로를 쓰거나, 자동화된다는 이유만으로 무조건 동적 프로토콜을 쓰지 않습니다.

## distance-vector의 정보 모델

Distance-vector 계열은 이웃에게 “어떤 목적지까지 내 비용이 얼마인지”를 알립니다. 각 라우터는 이웃까지의 비용과 이웃이 광고한 거리를 합쳐 더 나은 경로를 선택합니다. 이 생각은 Bellman-Ford 갱신과 연결됩니다.

```text
D_x(y) = min_v { cost(x, v) + D_v(y) }
```

전체 토폴로지를 직접 알 필요가 없다는 장점이 있지만, 장애 정보가 느리게 퍼지면 순환 경로와 Count-to-Infinity 문제가 생길 수 있습니다. Split Horizon, Poison Reverse, Hold-down과 제한된 최대 메트릭 같은 장치는 특정 실패를 줄이지만 모든 수렴 문제를 없애지는 않습니다.

## 링크 상태 라우팅의 정보 모델

링크 상태 계열은 각 라우터가 자신의 인접 링크 상태를 영역에 플러딩하고, 같은 토폴로지 데이터베이스에서 최단 경로 트리를 계산하도록 합니다. 일반적으로 Dijkstra 알고리즘으로 자신을 루트로 한 최단 경로를 구합니다.

```text
인접 관계 형성
→ 링크 상태 광고 플러딩
→ 토폴로지 데이터베이스 동기화
→ SPF 계산
→ 다음 홉 설치
```

정보가 빠르게 퍼지고 각 라우터가 전체 영역 구조를 볼 수 있지만 데이터베이스 동기화, 순서 번호, 만료 처리와 재계산 부하를 관리해야 합니다. 링크가 반복해서 활성화·비활성화되면 잦은 재계산과 경로 변동이 발생할 수 있습니다.

OSPF는 하나의 자율 시스템 안에서 사용하는 대표적인 링크 상태 프로토콜입니다. 영역을 사용해 토폴로지와 플러딩 범위를 나누고, 링크 비용을 이용해 경로를 계산합니다. OSPF가 인터넷 전체의 사업자 정책을 결정하는 프로토콜은 아닙니다.

## BGP는 정책을 포함한 경로 벡터 프로토콜입니다

서로 다른 자율 시스템 사이에서는 단순한 지연 최단 경로보다 사업 관계, 내보내기 정책, 안정성과 트래픽 엔지니어링이 중요합니다. BGP는 프리픽스와 AS_PATH를 포함한 속성을 교환하고 정책에 따라 최적 경로를 선택합니다.

BGP가 선택한 경로를 다음처럼 오해하지 마세요.

- 물리 거리나 RTT가 가장 짧은 경로라는 단정
- AS_PATH 길이 하나만 비교한다는 단정
- 모든 라우터가 같은 경로를 즉시 선택한다는 단정
- 경로가 보이므로 데이터 평면도 반드시 통한다는 단정

구현마다 Local Preference, AS_PATH, Origin, MED, eBGP/iBGP 관계, IGP 비용과 동률 결정 기준을 정해진 순서로 적용합니다. 운영 정책을 설명할 때는 “BGP가 알아서 최단 경로를 고릅니다”가 아니라 어떤 속성과 정책이 우선했는지 기록합니다.

## 수렴 중에는 일시적 불일치가 생깁니다

링크 장애가 발생하면 각 라우터가 같은 순간에 같은 정보를 갖지 않습니다. 탐지, 광고, 계산, 테이블 설치가 순차적으로 일어나므로 다음 현상이 나타날 수 있습니다.

- 일시적 전달 순환
- blackhole
- 이전 경로와 새 경로의 패킷 순서 뒤바뀜
- ECMP 구성원 변화
- 경로 변동에 따른 반복 수렴

애플리케이션의 timeout과 retry는 이 전환 구간을 고려해야 합니다. 재시도가 경로 수렴보다 훨씬 빠르면 같은 실패를 반복해 부하만 늘릴 수 있습니다.

## ECMP와 흐름별 선택

동일 비용 후보가 여러 개면 Equal-Cost Multi-Path로 트래픽을 분산할 수 있습니다. 일반적으로 각 패킷을 무작위로 보내기보다 흐름 튜플을 해시해 같은 흐름의 순서를 유지하려고 합니다.

경로 구성원이 바뀌면 해시 결과가 달라져 일부 연결이 다른 경로로 이동할 수 있습니다. 두 경로의 MTU, 지연, 방화벽 상태와 NAT 상태가 다르면 특정 흐름만 실패하는 원인이 됩니다.

## 알고리즘과 protocol을 검증하는 질문

1. 라우터가 가진 정보는 이웃의 거리인가요, 전체 topology인가요, AS 경로와 정책인가요?
2. 메트릭은 어떤 자원을 근사하며 서로 다른 프로토콜 사이에서 직접 비교할 수 있나요?
3. 장애 탐지와 경로 철회가 얼마나 걸리나요?
4. loop를 탐지하거나 제한하는 장치는 무엇인가요?
5. 계산된 경로가 전달 테이블에 실제로 설치되었나요?
6. 동일 prefix를 여러 source에서 배웠을 때 preference 순서는 무엇인가요?
7. 경로 광고를 어느 이웃에게 내보낼 수 있나요?

프로토콜 검사기의 LPM은 마지막 데이터 평면 선택만 구현합니다. 동적 프로토콜 자체를 구현하지 않는 이유는 전송 형식보다 토폴로지 동기화, 타이머, 정책과 실패 수렴을 이해하는 데 초점을 두기 위해서입니다.

## 운영 증거를 분리하기

장애 기록에는 다음 세 층을 따로 남기세요.

```text
학습: 어떤 neighbor와 protocol에서 prefix를 받았나요?
선택: 어떤 속성과 정책 때문에 최적 경로가 되었나요?
설치: 어떤 다음 홉과 인터페이스가 전달 테이블에 들어갔나요?
```

그리고 실제 패킷 캡처와 카운터로 전달 결과를 확인합니다. 제어 평면 로그만으로 데이터 평면 성공을 주장하지 않습니다.
