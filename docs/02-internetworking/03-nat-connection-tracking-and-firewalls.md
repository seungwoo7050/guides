# NAT, 연결 추적과 방화벽

Network Address Translation은 패킷의 주소 또는 포트를 바꾸고 응답 방향에서 원래 값으로 되돌리기 위한 매핑 상태를 만듭니다. 방화벽은 어떤 트래픽을 허용하거나 거부할지 결정합니다. 두 기능이 같은 장비와 연결 추적 상태를 공유할 수 있지만 목적과 계약은 다릅니다.

## 학습 목표

- NAT mapping, connection tracking과 방화벽 판정의 책임을 분리합니다.
- 요청·응답 tuple 변화를 방향별 상태로 추적합니다.

## 선행 개념

[IP 전달](02-ip-forwarding-mtu-and-icmp.md)의 다음 홉·출력 인터페이스와 UDP/TCP의 주소·포트 tuple을 알고 있어야 합니다.

## 대표적인 변환

| 형태 | 주로 바꾸는 값 | 대표 사용례 |
|---|---|---|
| SNAT | 출발지 주소·포트 | 내부 호스트가 외부로 나갈 때 |
| DNAT | 목적지 주소·포트 | 외부 요청을 내부 서비스로 전달할 때 |
| PAT/NAPT | 여러 흐름의 포트까지 변환 | 여러 내부 주소가 한 외부 주소를 공유할 때 |
| hairpin NAT | 내부에서 외부 공개 주소를 통해 내부로 재진입 | 동일한 서비스 이름 사용 |

예를 들어 내부 UDP 흐름이 다음처럼 바뀔 수 있습니다.

```text
원래: 10.202.1.2:53000 → 198.18.0.2:9000
외부: 198.18.0.1:41000 → 198.18.0.2:9000
응답: 198.18.0.2:9000 → 198.18.0.1:41000
복원: 198.18.0.2:9000 → 10.202.1.2:53000
```

장비는 외부 tuple을 원래 내부 tuple로 되돌릴 상태를 유지합니다. 같은 외부 주소를 많은 내부 흐름이 공유하려면 포트 공간, 매핑 timeout과 충돌 정책이 자원이 됩니다.

## 연결 추적은 프로토콜별 상태를 추정합니다

TCP는 SYN, ACK, FIN과 RST를 관찰해 연결 상태를 비교적 구체적으로 추적할 수 있습니다. UDP에는 연결 수립 handshake가 없으므로 최근 양방향 패킷과 timeout을 이용해 임시 상태를 관리합니다.

따라서 UDP NAT mapping은 애플리케이션이 기대하는 idle 시간보다 먼저 사라질 수 있습니다. keepalive 주기를 정할 때 NAT 장비의 정확한 timeout을 인터넷 전체에서 하나의 값으로 가정하지 말고, 실패를 허용하는 재등록·재연결 계약을 설계하세요.

ICMP 오류도 원래 패킷 일부를 이용해 관련 NAT 상태와 연결해야 할 수 있습니다. 주소 변환 장비가 header만 기계적으로 바꾸면 오류 메시지 안에 인용된 내부 주소와 checksum이 일치하지 않을 수 있습니다.

## stateful firewall과 NAT를 구분하기

상태 기반 방화벽은 먼저 허용된 외부 방향 흐름의 응답을 `ESTABLISHED` 또는 관련 상태로 허용할 수 있습니다. 이것은 주소를 바꿔서 안전해지는 것이 아니라 정책과 추적 상태가 응답 방향을 허용한 결과입니다.

다음 문장은 모두 부정확합니다.

- 사설 주소이므로 방화벽이 필요 없다는 설명
- NAT를 제거하면 외부에서 모든 내부 서비스에 자동 접근된다는 설명
- IPv6는 NAT가 없으므로 보안이 약하다는 설명
- 포트 forwarding이 애플리케이션 인증을 대신한다는 설명

IPv6에서는 주소 부족 때문에 NAPT를 사용할 필요가 줄지만, 인입 정책, 호스트 방화벽, 서비스 바인드와 인증은 여전히 필요합니다. 주소 보존은 종단 간 추적과 일부 프로토콜을 단순하게 할 수 있지만 접근 허용 정책과는 별개입니다.

## NAT가 만드는 설계 비용

NAT는 주소 공유라는 이점과 함께 다음 제약을 만듭니다.

- 외부에서 내부로 새 흐름을 시작하려면 명시적 mapping이나 traversal이 필요합니다.
- 페이로드 안에 IP·포트를 넣는 프로토콜은 별도 수정이 필요할 수 있습니다.
- 장애 조사에서 한 외부 tuple을 내부 흐름과 연결할 NAT log가 필요합니다.
- 매핑 테이블과 포트 공간이 고갈될 수 있습니다.
- 장비 재시작이나 failover에서 상태가 사라질 수 있습니다.
- 서로 다른 NAT 동작 때문에 피어 간 연결 성공률이 달라집니다.

Carrier-grade NAT는 여러 가입자가 외부 주소를 공유하므로 운영자는 주소뿐 아니라 포트와 시간까지 기록해야 내부 사용자를 식별할 수 있습니다. 애플리케이션 로그도 원격 IP 하나를 사용자 신원으로 취급하지 마세요.

## 격리된 SNAT 실험

Linux 실습은 외부 네트워크에 연결하지 않고 시험용 주소만 사용합니다.

```sh
cd exercises/linux-routing-nat
sudo ./scripts/run-nat.sh
```

클라이언트 `10.202.1.2`가 UDP 요청을 보내면 라우터가 출발지를 `198.18.0.1`로 바꿉니다. 서버가 기록한 피어 주소가 라우터 외부 주소인지 확인하고 응답이 내부 클라이언트로 돌아오는지 검사합니다.

실습은 NAT 테이블만 추가하며 Filter 테이블 규칙으로 보안을 주장하지 않습니다. 두 기능을 분리해 관찰하는 것이 목적입니다.

## 정책 설계 질문

NAT 또는 방화벽 변경 전에 다음 계약을 적어 보세요.

1. 누가 어느 방향에서 새 흐름을 시작할 수 있나요?
2. 어떤 protocol, 주소, 포트와 interface가 범위인가요?
3. 응답과 관련 오류는 어떤 상태로 허용하나요?
4. 유휴 제한 시간이 지난 뒤 애플리케이션은 어떻게 복구하나요?
5. NAT mapping과 정책 결정을 어떤 log로 추적하나요?
6. 장비 재시작과 failover에서 상태는 어떻게 처리하나요?
7. IPv4와 IPv6 정책이 같은 의도를 구현하나요?

규칙 한 줄의 문법보다 이 질문에 대한 답이 먼저입니다. 다음 장에서는 정적 route를 넘어 여러 라우터가 경로를 만드는 제어 평면을 다룹니다.
