# 운영 계약과 위협 모델

로컬에서 요청이 성공했다는 사실만으로 공개 운영 준비가 끝나지 않습니다. 운영에서는 먼저 **무엇을 지켜야 하는지, 어느 정도의 중단과 데이터 손실을 허용하는지, 누가 판단하고 복구하는지**를 정해야 합니다. 이 결정이 없으면 TLS, 백업, 경보와 고가용성 기술을 추가해도 서로 다른 목표를 향하게 됩니다.

이 장의 목표는 도구를 설치하는 것이 아니라 다음 운영 계약을 작성하는 것입니다.

```text
서비스 경계
+ 보호할 자산
+ 사용자에게 약속할 최소 동작
+ 허용 가능한 중단과 데이터 손실
+ 공개·관리 진입점
+ 소유자와 의사결정 경계
+ 단일 호스트에서 수용하는 잔여 위험
```

대응 실습은 [`exercises/08-production-contract`](../exercises/08-production-contract/)입니다.

## 1. “운영 가능”의 의미

운영 가능하다는 말은 단순히 다음을 뜻하지 않습니다.

- 컨테이너가 실행 중입니다.
- `curl` 한 번이 성공했습니다.
- 도메인이 연결됩니다.
- 백업 파일이 하나 있습니다.

최소한 다음 주기를 반복할 수 있어야 합니다.

```text
배포
→ 사용자 경로 검증
→ 상태 관찰
→ 변경
→ 실패 감지
→ 완화 또는 rollback
→ 데이터 복원
→ 원인과 후속 조치 기록
```

운영 계약은 이 주기의 성공 조건을 미리 정합니다.

## 2. 먼저 서비스 한 문장으로 정의하기

운영 문서는 기술 목록보다 사용자 기능으로 시작합니다.

나쁜 예:

> Nginx, PHP-FPM, MariaDB와 Docker Compose를 운영합니다.

좋은 예:

> 사용자는 공개 HTTPS 주소에서 메모를 조회하고 작성할 수 있으며, 작성된 메모는 호스트 재시작과 애플리케이션 재배포 뒤에도 유지됩니다.

두 번째 문장은 무엇을 검증해야 하는지 드러냅니다.

- 공개 HTTPS 접근
- 읽기와 쓰기 경로
- 영속 데이터
- 재시작
- 재배포

기술은 이 계약을 구현하는 수단입니다.

## 3. 시스템 경계와 소유권

운영 대상의 안과 밖을 그립니다.

```text
사용자 브라우저
      │
      ▼
공개 DNS ── 도메인 등록자
      │
      ▼
Linux 호스트
  ├─ gateway
  ├─ application
  ├─ database volume
  ├─ runtime secrets
  └─ local logs
      │
      ├─ image registry
      ├─ external backup storage
      ├─ monitoring destination
      └─ CI system
```

각 구성요소에 다음을 기록합니다.

| 항목 | 질문 |
|---|---|
| 소유자 | 누가 변경할 수 있는가? |
| 정본 | 잃으면 다시 만들 수 없는 상태는 무엇인가? |
| 인증 수단 | 어떤 자격 증명으로 접근하는가? |
| 변경 경로 | 수동, CI, API 중 무엇으로 바뀌는가? |
| 실패 영향 | 실패하면 어떤 사용자 기능이 깨지는가? |
| 복구 원본 | registry, Git, backup 중 어디에서 복구하는가? |

예를 들어 컨테이너는 정본이 아닙니다. 검증된 이미지와 실행 설정에서 다시 만들 수 있어야 합니다. 반면 데이터베이스 volume의 최신 내용은 일반적으로 다른 곳에서 자동으로 재생성할 수 없으므로 보호 대상입니다.

## 4. 데이터 분류

데이터를 모두 같은 방식으로 보호하지 않습니다.

### 재생성 가능한 데이터

- 이미지 layer
- 빌드 cache
- 임시 파일
- 계산 가능한 검색 색인
- registry에서 다시 받을 수 있는 image

잃어도 시간 비용만 들고 정보 손실은 없어야 합니다.

### 운영 설정

- Compose 구성
- release manifest
- gateway 설정
- 경보 규칙
- runbook

Git 또는 다른 형상 관리에서 재구성할 수 있어야 합니다. 환경별 비밀값은 포함하지 않습니다.

### 비밀값

- 데이터베이스 비밀번호
- registry 자격 증명
- DNS API token
- 백업 암호화 키
- TLS 개인키

공개 설정과 다른 저장·접근·교체 정책이 필요합니다.

### 업무 데이터

- 사용자 계정
- 작성한 콘텐츠
- 결제·주문·예약 기록
- 업로드 파일

백업 대상, 보존 기간, 복원 순서와 허용 가능한 손실량을 정해야 합니다.

### 운영 증거

- 배포 기록
- 감사 로그
- 경보 이력
- 복원 시험 결과
- 사고 timeline

장애 원인과 변경 책임을 확인하는 데 필요합니다. 업무 데이터와 보존 요구가 다를 수 있습니다.

## 5. RPO와 RTO

### RPO: 허용 가능한 데이터 손실 범위

Recovery Point Objective는 장애가 발생했을 때 어느 시점까지의 데이터를 복원해야 하는지를 나타냅니다.

예:

```text
RPO 24시간
→ 최악의 경우 마지막 성공 백업 이후 최대 24시간의 변경을 잃을 수 있음
```

백업 주기가 24시간이라고 자동으로 RPO 24시간을 달성하는 것은 아닙니다. 백업 실패를 발견하지 못하거나 외부 저장소로 복제되지 않으면 실제 손실 범위는 더 커집니다.

### RTO: 허용 가능한 복구 시간

Recovery Time Objective는 장애 판단부터 핵심 기능 복구까지 허용하는 시간입니다.

예:

```text
RTO 4시간
→ 호스트 전체 손실 뒤 4시간 안에 핵심 읽기·쓰기 경로를 복구
```

RTO는 문서의 예상 시간이 아니라 실제 복구 훈련 결과로 검증합니다.

### 목표를 기능별로 나누기

모든 기능이 같은 우선순위를 갖지 않을 수 있습니다.

| 기능 | 예시 목표 |
|---|---|
| 공개 상태 페이지 | 30분 안에 제공 |
| 읽기 경로 | 2시간 안에 복구 |
| 쓰기 경로 | 4시간 안에 복구 |
| 관리자 보고서 | 다음 영업일 안에 복구 |

초기 서비스는 단순한 하나의 RTO·RPO를 사용해도 되지만, 어떤 기능을 기준으로 했는지 적습니다.

## 6. 최소 서비스 수준과 오류 예산

정교한 SLO 체계가 없어도 사용자 관점의 최소 동작을 수치로 정의할 수 있습니다.

예:

```text
측정 경로: GET /healthz가 아니라 실제 읽기 API
측정 위치: 호스트 외부
성공 조건: TLS 검증 성공 + HTTP 2xx + 응답 본문 계약
시간 창: 최근 30일
목표: 성공률 99.5%
지연 목표: 95% 요청이 500ms 이하
```

여기서 중요한 점은 수치 자체보다 측정 경로입니다. gateway의 고정 `/healthz`가 성공해도 데이터베이스를 사용하는 기능은 실패할 수 있습니다.

작은 서비스에서 목표를 지나치게 높이면 비용과 복잡도가 급격히 증가합니다. 단일 호스트가 가진 한계를 인정하고, 목표가 그 구조로 가능한지 확인합니다.

## 7. 위협 모델

위협 모델은 모든 공격 기법을 나열하는 문서가 아닙니다. 보호할 자산, 신뢰 경계와 가능한 오용 경로를 연결합니다.

### 자산

- 사용자 데이터
- 관리자 계정
- DNS 제어권
- 배포 권한
- registry 이미지
- 백업과 암호화 키
- TLS 개인키
- 운영 로그

### 진입점

- 공개 80·443 포트
- SSH
- Docker daemon socket
- CI workflow
- image registry
- DNS provider API
- 백업 저장소
- 애플리케이션 관리자 UI

### 가능한 행위자

- 인증되지 않은 인터넷 사용자
- 탈취된 사용자 계정
- 탈취된 관리자 계정
- 악성 또는 취약한 의존성
- 실수한 운영자
- 손상된 CI 실행
- 호스트를 획득한 공격자

### 신뢰 경계

```text
인터넷 ↔ gateway
관리자 장치 ↔ SSH
CI ↔ registry
호스트 ↔ 외부 backup storage
container ↔ Docker daemon
application ↔ database
```

경계를 넘을 때 어떤 인증과 권한 검사가 필요한지 기록합니다.

## 8. 대표 오용 사례

다음 질문에 답합니다.

- 공개된 애플리케이션이 Docker socket에 접근할 수 있습니까?
- CI가 production에 장기 관리자 키로 접근합니까?
- 공격자가 임의 image tag를 덮어쓰면 production이 그 이미지를 받습니까?
- DNS API token이 전체 계정의 모든 도메인을 변경할 수 있습니까?
- 백업 저장소를 삭제할 권한과 production 데이터를 변경할 권한이 같은 계정에 있습니까?
- 애플리케이션 로그에 비밀번호나 session token이 남습니까?
- 호스트 하나가 손상되면 백업까지 함께 삭제할 수 있습니까?
- 인증서 갱신이 실패해도 만료 직전까지 알 수 없습니까?

각 사례를 `예방`, `탐지`, `복구`로 나눕니다.

| 오용 사례 | 예방 | 탐지 | 복구 |
|---|---|---|---|
| 변경 가능한 tag가 다른 image를 가리킴 | digest 배포 | release manifest 비교 | 이전 digest로 rollback |
| 호스트와 로컬 백업 동시 손실 | 외부 저장소 복제 | backup age 경보 | 새 호스트에 외부 백업 복원 |
| DNS token 탈취 | 최소 scope·별도 자격 증명 | DNS 변경 알림 | token 폐기·record 복구 |

예방만으로 모든 실패를 막을 수 없습니다. 탐지와 복구가 함께 있어야 합니다.

## 9. 단일 호스트에서 수용하는 위험

이 과정은 다음 위험을 제거하지 않습니다.

- 호스트 장애 동안 서비스가 중단됩니다.
- 호스트 지역이나 공급자 장애에 영향을 받습니다.
- 배포 중 짧은 연결 중단이 생길 수 있습니다.
- 데이터베이스가 단일 인스턴스입니다.
- 운영자가 한 명이면 판단과 대응이 지연될 수 있습니다.

대신 다음을 요구합니다.

- 호스트 밖에 복구 원본이 있습니다.
- exact image digest를 알고 있습니다.
- DNS와 비밀값에 다시 접근할 수 있습니다.
- 새 호스트에서 복원 절차를 실행해 봤습니다.
- 사용자에게 장애 상태를 알릴 경로가 있습니다.

위험을 문서화한 상태에서 수용하는 것과, 존재를 모르는 것은 다릅니다.

## 10. 변경 권한과 승인 경계

최소한 다음 역할을 구분합니다. 한 사람이 여러 역할을 맡아도 논리적 책임은 분리합니다.

| 역할 | 책임 |
|---|---|
| 코드 소유자 | 애플리케이션 변경 검토 |
| release 소유자 | 배포 후보와 manifest 승인 |
| 운영 소유자 | 호스트·DNS·backup·경보 관리 |
| 사고 지휘자 | 장애 중 우선순위와 의사결정 기록 |
| 데이터 소유자 | 보존·복원·삭제 기준 결정 |

작은 프로젝트에서는 모두 같은 사람일 수 있습니다. 그래도 “지금 코드를 수정하는 중인지, production을 완화하는 중인지”를 구분해야 합니다.

## 11. 운영 준비 완료 조건

공개 전 다음 증거를 준비합니다.

### 서비스와 데이터

- 사용자 핵심 경로가 정의되어 있습니다.
- 정본 데이터와 재생성 가능한 데이터가 분리되어 있습니다.
- RTO와 RPO가 명시되어 있습니다.
- backup과 restore의 소유자가 정해져 있습니다.

### 노출과 권한

- 공개 포트와 관리 포트가 명시되어 있습니다.
- SSH, registry, DNS와 backup 권한의 소유자가 정해져 있습니다.
- 비밀값이 Git과 이미지에 포함되지 않습니다.
- Docker daemon 접근 주체를 알고 있습니다.

### 배포와 복구

- 배포 image digest를 기록합니다.
- 이전 release로 rollback할 수 있습니다.
- migration과 애플리케이션 버전의 호환 범위를 압니다.
- 외부 backup에서 별도 디렉터리로 복원해 봤습니다.

### 관측과 대응

- 사용자 관점 상태 검사가 있습니다.
- 인증서, backup, disk와 핵심 오류에 경보가 있습니다.
- runbook이 실제 명령과 검증 기준을 포함합니다.
- 연락과 의사결정 경로가 정해져 있습니다.

## 12. 실습

[`exercises/08-production-contract`](../exercises/08-production-contract/)에서 불완전한 운영 계약을 수정합니다. 자동 검사는 다음을 확인합니다.

- 사용자 기능으로 서비스가 정의됐는가?
- 공개·관리 진입점이 분리됐는가?
- 데이터 종류별 정본과 복구 원본이 있는가?
- RTO·RPO와 측정 경로가 있는가?
- 위험마다 예방·탐지·복구가 연결됐는가?
- 단일 호스트 잔여 위험을 숨기지 않았는가?
- 각 결정에 소유자가 있는가?

검사를 통과한 YAML은 실제 조직의 완전한 정책을 대신하지 않습니다. 다만 이후 장의 기술 선택이 어떤 목표를 만족해야 하는지 고정합니다.
