# main 유지보수 계약

`main`은 전체 저장소의 라우터이자 새 브랜치의 기준점이다. 독자에게는 목표 업무까지의 경로를 제공하고, 작성자와 리뷰어에게는 기존 브랜치와 같은 구조·품질·완성도를 판단할 계약을 제공한다. 개별 브랜치의 세부 문서를 복사하지 않고, 브랜치가 어떤 문제를 소유하며 어떤 트랙에 놓이는지와 어떤 기준으로 승인되는지를 관리한다.

`main`은 제작 일정이나 현재 원격 브랜치 목록이 아니라 **모든 등재 브랜치가 완성됐을 때의 목표 상태**를 현재형으로 기록한다. 새 브랜치는 이 목표 계약을 `main`에 먼저 확정한 뒤 구현한다. 그러므로 카탈로그는 원격 브랜치 생성과 실제 완료보다 앞설 수 있으며, 구현 중이라는 이유로 최종 `owns`, 종료 능력이나 경로를 축소하지 않는다.

## 정본과 생성 산출물

사람이 직접 수정하는 정본은 다음 세 파일이다.

- `catalog/branches.json`: 브랜치 메타데이터
- `catalog/tracks.json`: 업무 트랙, 분야 그룹과 권장 선형 경로
- `docs/09-branch-quality-contract.md`: 새 브랜치의 공통 구조와 사람 검토 기준

다음 Markdown은 카탈로그에서 만드는 생성 산출물이다.

- `docs/01-branch-catalog.md`: 브랜치 카탈로그에서 생성
- `docs/03-career-tracks.md`: 트랙 카탈로그와 브랜치 의존성에서 생성
- `docs/04-dependency-map.md`: 브랜치 카탈로그에서 생성

생성 문서는 직접 수정하지 않는다. 카탈로그를 수정한 뒤 다음 명령으로 다시 만든다.

```sh
python3 scripts/render_catalog.py
```

## 브랜치 메타데이터 필수 항목

- 고유한 `id`
- 표시 제목과 종류
- 한 문단 요약
- `requires`, `recommends`, `connects`, `continues_to`
- `owns`, `excludes`
- 실제 종료 능력
- 브랜치 URL과 상태

종류는 `common-foundation`, `language-entry`, `field-entry`, `specialization` 네 가지 중 하나다. 교차 확장은 별도 종류가 아니라 여러 기반을 결합하는 직교 특성으로 다룬다.

## 트랙 메타데이터 필수 항목

- 고유한 `id`, 표시 제목과 상위 `group`
- 목표 업무와 종료 능력
- `common`, `required`, `required_any`
- `recommended`, `advanced`
- 하나 이상의 `linear_paths`

권장 선형 경로는 실제로 따라갈 순서를 제공하지만 브랜치의 엄밀한 의존성이나 트랙 완료 조건의 정본은 아니다. 각 경로는 트랙의 공통·핵심 브랜치를 모두 포함하고, 택일 필수 그룹의 선택을 적어도 하나 대표해야 한다. 경로에 포함된 브랜치의 직접 필수 의존성은 해당 브랜치보다 앞에 배치하며, 핵심 트랙 종료 뒤 진행하는 `advanced`는 선형 진입 경로에 넣지 않는다.

## 새 브랜치 추가 절차

1. [소유권과 중복 방지](07-ownership-boundaries.md)의 분리 조건을 검토한다.
2. 기존 브랜치와 소유권 충돌을 정리하고 카탈로그 밖의 영역을 내부 브랜치처럼 표현하지 않았는지 확인한다.
3. [브랜치 품질 계약](09-branch-quality-contract.md)에 따라 구조, 품질 프로필, 종료 능력과 누적 종료 근거를 설계한다.
4. 완성 상태의 `owns`, `excludes`, 종료 능력과 인접 관계를 사람이 검토하고 `catalog/branches.json`에 `stable` 목표 계약으로 추가한다.
5. 하나 이상의 업무 트랙에 브랜치를 연결하고, 처음 접하는 독자가 사용할 선형 경로에서 실제 위치를 정한다.
6. 직접 의존성 graph의 cycle과 선형 경로의 참조·순서를 확인하고 생성 문서와 `README.md`의 개수를 갱신한다.
7. 링크·카탈로그·문서의 기계적 무결성을 검사한 뒤 `main`을 먼저 커밋·게시한다.
8. 제공된 초안과 독립 브랜치 이력을 출발점으로 문서·실습·대표 실패·누적 종료 과제와 재현 절차를 구현한다. `main`의 tree를 대상 기술 브랜치의 파일 기반으로 복사하거나 병합하지 않는다.
9. 저자가 기준 학습 경로를 따라가고 사람 리뷰어가 실제 브랜치의 구조·품질·완성도를 검토한다. 중대한 공백을 해결하며, 구현 중 계약 변경이 필요하면 `main`을 먼저 보정한다.

## 브랜치 제거·이름 변경

- 대체 브랜치와 이동 경로 없이 제거하지 않는다.
- 이름 변경은 URL, 카탈로그, 트랙, 선형 경로와 모든 교차 링크를 동시에 수정한다.
- 범위를 분할할 때 기존 브랜치의 종료 능력이 어디로 이동했는지 기록한다.
- 범위를 병합할 때 고유한 실패 모델과 실습이 사라지지 않는지 확인한다.

## 검사

```sh
./prepare.sh
./verify.sh
```

검사는 다음을 확인한다.

- branch, track과 선형 경로 ID의 유일성
- 모든 참조가 카탈로그의 branch ID를 가리키는지
- 필수 의존성 graph에 cycle이 없는지
- 선형 경로가 공통·핵심·택일 필수 조건을 대표하는지
- 생성 문서가 카탈로그와 같은지
- 내부 Markdown 링크가 존재하는지
- prepare 이후 source fingerprint가 바뀌지 않았는지

이 검사는 브랜치가 실제로 완성됐는지, 설명이 정확한지, 실습이 교육적으로 충분한지를 증명하지 않는다. 검사 범위를 실제 완료 판정까지 넓히지 않는다.

## 목표 계약과 실제 완료의 사람 검토

카탈로그의 `stable`은 원격 구현 상태가 아니라 후속 브랜치가 도달해야 할 완성 목표 계약의 승인이다. `main`을 먼저 완성하려면 저자와 리뷰어가 [브랜치 품질 계약](09-branch-quality-contract.md)에 따라 최종 설계에서 다음 역할이 모두 이어질 수 있는지 검토한다.

- 대상 독자, 진입점, 범위 계약과 재현 절차의 역할이 정의돼 있다.
- 핵심 소유 범위가 개념, 실습, 대표 실패와 판단 근거로 이어질 수 있다.
- capstone 또는 동등한 누적 최종 실습이 종료 능력을 함께 요구하도록 설계돼 있다.
- 선택한 품질 프로필에 필요한 안전·측정·재현·검토 근거가 명시돼 있다.
- 비소유 범위와 인접 브랜치가 정확하고 알려진 한계가 공개돼 있다.

실제 브랜치 구현 뒤에는 같은 항목을 설계 문구가 아니라 존재하는 문서·실습·실행 결과·누적 과제의 근거로 다시 검토한다. 표준 파일 배치와 다른 형태도 같은 역할을 더 적절하게 수행하면 허용한다. 반대로 모든 파일이 존재하고 자동 검사가 통과해도 핵심 종료 근거가 비어 있으면 브랜치 완료로 승인하지 않는다. 카탈로그 상태와 실제 완료 판단을 한 값으로 섞거나 자동화하지 않는다.

## 문서 표현 원칙

- 직급을 브랜치 완료 개수로 환산하지 않는다.
- 특정 제품 버전보다 상태·책임·실패·검증을 먼저 쓴다.
- 업무 트랙은 권장 선형 경로와 엄밀한 필수·권장·심화를 구분한다.
- 카탈로그에 등재된 모든 브랜치를 완성 목표 상태의 현재형으로 설명한다.
- 카탈로그에 없는 영역은 존재하는 내부 브랜치처럼 쓰지 않고 외부 자료 또는 향후 검토 영역으로 표시한다.
- 계획·제작 순서·개인 일정은 `main`의 최종 카탈로그에 포함하지 않는다.
