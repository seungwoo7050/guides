# 연습문제: account-simulator

## 목표

여러 스레드가 두 계좌 사이에서 동시에 이체하고 조회할 때 잔액과 전체 합 불변식을 유지합니다. 반대 방향 이체가 교착하지 않도록 명시적인 잠금 순서를 사용합니다.

## 구현 위치

`skeleton/src/account.c`를 구현합니다. 공개 헤더는 변경하지 않습니다.

## 수명 계약

- `account_init`은 아직 초기화되지 않은 새 객체에 한 번 호출합니다. 초기화된 객체를 다시 초기화하지 않습니다.
- 초기화 뒤 `id`와 `initialized`를 호출자가 직접 변경하지 않습니다.
- 모든 worker와 observer가 `join`되어 더 이상 객체를 사용할 수 없을 때만 `account_destroy`를 호출합니다.
- `account_destroy` 뒤에는 다시 초기화하기 전까지 조회·이체하지 않습니다.

## 동작 계약

- 계좌 ID는 서로 다른 계좌 사이에서 유일해야 합니다.
- 초기 잔액과 이체 금액은 음수가 될 수 없습니다.
- 이체 성공은 0입니다.
- 잔액 부족, 목적지 overflow, 잘못된 객체와 같은 ID의 다른 객체는 -1이며 두 잔액을 보존합니다.
- 금액 0의 이체는 유효한 성공이며 상태를 바꾸지 않습니다.
- 같은 계좌로의 이체는 잔액이 충분하면 성공하지만 상태는 바뀌지 않습니다.
- 두 계좌는 항상 작은 ID부터 잠급니다. 같은 객체는 뮤텍스를 한 번만 잠급니다.
- balance와 total 조회도 같은 잠금 계약을 사용해 일관된 값을 반환합니다.
- 실패 시 출력 매개변수를 변경하지 않습니다.

## 완료 기준

- `make exercise-test`와 `make sanitize`가 통과하고, 지원 환경에서는 `make thread-sanitize`도 통과합니다. 지원하지 않으면 probe의 생략 이유를 기록합니다.
- 8개 이체 worker와 2개 observer가 동시에 실행되는 동안 음수 잔액이 없고 모든 관찰에서 전체 합 400000이 유지되며 교착이나 data race가 없습니다.
- 잔액 부족·목적지 overflow·잘못된 객체·같은 ID의 다른 객체가 두 잔액과 출력 매개변수를 보존하고, 금액 0·자기 이체는 계약대로 성공함을 확인합니다.

## 자기 설명

- 반대 방향 이체도 항상 작은 ID의 계좌부터 잠그면 circular wait가 사라지는 이유는 무엇인가요?
- `account_total`이 두 mutex를 같은 순서로 잠그지 않거나 개별 잔액을 따로 읽으면 존재하지 않았던 합계를 관찰할 수 있는 이유는 무엇인가요?

## 검증

```sh
make exercise-test
make sanitize
make thread-sanitize
```

기본 검사는 8개 이체 worker와 2개 observer를 동시에 시작합니다. observer는 이체 중 `account_total`과 개별 잔액을 반복해서 읽으며 전체 합 400000과 음수 잔액 부재를 검사합니다. 추가로 잘못된 객체, 같은 ID, 자기 이체, 잔액 부족과 overflow를 확인합니다. ThreadSanitizer는 지원하는 컴파일러·플랫폼에서만 사용할 수 있습니다.
