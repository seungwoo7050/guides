# 요청, 프로세스와 포트

Docker 없이 작은 HTTP 서버를 관찰합니다.

## 확인할 흐름

- 서버 프로세스의 PID와 수신 포트를 찾습니다.
- 200, 404, 연결 실패를 구분합니다.
- SIGTERM으로 서버를 종료합니다.
- 환경변수로 호스트와 포트를 바꿉니다.

## 시작

완성 예제를 먼저 검증합니다.

```sh
./verify.sh reference
```

그다음 `skeleton/server.py`를 수정해 같은 검증을 통과시킵니다.

```sh
./verify.sh skeleton
```

## 라우팅 구현

현재 시작 코드는 모든 경로에 200을 반환합니다. 다음 동작으로 바꿉니다.

| 요청 | 상태 | 본문 |
|---|---:|---|
| `GET /` | 200 | 서버 정보 JSON |
| `GET /healthz` | 200 | `ok` |
| 그 외 | 404 | `요청한 경로를 찾을 수 없습니다.` |

추가 조건:

- `APP_HOST`, `APP_PORT` 환경변수를 사용합니다.
- 요청 메서드, 경로, 클라이언트 주소를 표준 오류에 한 줄로 기록합니다.
- SIGTERM과 Ctrl-C에서 정상 종료합니다.

## 관찰 질문

1. 서버가 실행 중일 때 `curl /missing`은 연결에 성공했는가?
2. 서버 종료 뒤 같은 `curl`은 HTTP 상태 코드를 받는가?
3. `APP_HOST=127.0.0.1`과 `0.0.0.0`은 서버 관점에서 무엇이 다른가?
4. 검증 스크립트는 왜 서버가 준비될 때까지 반복하는가?

## 완료 기준

- [ ] `./verify.sh skeleton`이 통과하고 `/`, `/healthz`, 존재하지 않는 경로가 계약한 상태와 본문을 반환한다.
- [ ] 서버 실행 중의 HTTP 404와 서버 종료 뒤의 연결 실패를 서로 다른 증거로 기록한다.
- [ ] 요청 로그가 표준 오류에 남고 SIGTERM 뒤 서버 프로세스와 수신 포트가 함께 사라지는지 확인한다.

## 자기 설명

1. HTTP 404와 TCP 연결 실패는 각각 어느 계층이 정상이고 어느 계층부터 실패했다는 뜻인가?
2. `127.0.0.1` 대신 `0.0.0.0`에 bind해야 컨테이너 밖 요청을 받을 수 있는 이유는 무엇인가?
3. 준비 대기 반복에 시간 제한이 없으면 검증 실패가 어떻게 가려질 수 있는가?
