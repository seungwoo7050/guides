# 서비스 경계와 데이터 소유권 검토

## 목표

저장소나 배포 단위의 이름보다 먼저 데이터의 정본과 유일한 변경 주체를 명시하고, 서비스 사이 의존 방향이 그 소유권을 우회하지 않는지 검사합니다.

## 문제 계약

실습의 `Architecture`는 다음 정보를 가집니다.

- 서비스 이름
- 각 데이터 집합의 소유 서비스
- 해당 데이터에 쓰기를 수행하는 서비스 집합
- 서비스 사이 동기 의존 관계

검토기는 다음을 거절해야 합니다.

- 데이터 집합에 소유자가 없습니다.
- 소유자가 아닌 서비스가 같은 데이터에 직접 씁니다.
- 소유 서비스가 실제 writer 목록에서 빠져 있습니다.
- 동기 의존 관계가 순환합니다.
- 등록되지 않은 서비스가 소유자·writer·의존 대상으로 나타납니다.

복제된 읽기 모델이나 이벤트 구독은 writer가 아닙니다. 이 실습은 읽기 복제보다 **변경 권한**의 유일성을 검사합니다.

## 실패 조건

skeleton은 소유자 문자열이 비어 있는지만 확인합니다. 두 서비스가 같은 테이블을 직접 변경하거나 동기 호출이 순환해도 유효한 구조로 판정합니다.

## 구현 순서

1. 모든 참조가 등록된 서비스를 가리키는지 확인합니다.
2. 각 데이터 집합의 writer가 정확히 소유자 하나인지 확인합니다.
3. 동기 의존 그래프를 깊이 우선 탐색해 순환을 찾습니다.
4. 오류를 첫 번째 하나로 숨기지 말고 모두 수집합니다.
5. 오류 메시지에는 데이터나 서비스 이름을 포함합니다.

## 완료 기준

- 모든 데이터 집합에서 writer가 소유 서비스 하나로만 제한됩니다.
- 등록되지 않은 서비스 참조와 소유자 누락이 이름을 포함한 오류로 드러납니다.
- 동기 의존 그래프의 순환과 같은 입력의 복수 결함을 함께 보고합니다.

## 자기 설명

- 읽기 복제와 직접 쓰기 권한은 왜 같은 소유권으로 취급할 수 없습니까?
- 양방향 동기 호출이 서비스 경계를 약하게 만드는 이유는 무엇입니까?

## 검증

학습자 복사본은 다음 정본 명령으로 검사합니다.

```sh
./scripts/verify-java.sh .workspace/service-boundary
```

- 단일 writer와 단방향 의존을 가진 구조는 통과합니다.
- 공유 쓰기와 소유자 누락을 각각 찾습니다.
- 등록되지 않은 서비스 참조를 찾습니다.
- `orchestrator → inventory → orchestrator` 순환을 찾습니다.
- 한 구조에 여러 결함이 있으면 모든 결함을 반환합니다.
