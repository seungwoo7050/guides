# 저장소 Git 정책 점검 항목

Git은 같은 작업을 여러 방식으로 처리할 수 있으므로 저장소마다 선택한 규칙을 명확히 적어 두는 편이 좋습니다. 새 저장소를 시작하거나 기존 기여 안내를 손볼 때 아래 항목을 확인해 보세요.

## 저장소와 브랜치

- 중앙 저장소와 기본 브랜치를 명시합니다.
- 조직 저장소에서 직접 브랜치를 만드는지, 개인 fork를 사용하는지 구분합니다.
- 브랜치 이름에 이슈 번호나 작업 종류를 포함하는지 설명합니다.
- 기본 브랜치와 릴리스 브랜치에 직접 push할 수 있는 주체를 정합니다.

작업 브랜치의 일반적인 시작 명령도 실제 기본 브랜치 이름에 맞춰 제공합니다.

```bash
git fetch origin
git switch --no-track -c feature/123-add-timeout origin/main
```

## 작성자 정보와 인증

- 커밋에 사용할 이름과 이메일 범위를 정합니다.
- HTTPS, SSH, 조직 SSO 중 사용하는 인증 방식을 안내합니다.
- GPG 또는 SSH 서명, DCO sign-off, CLA가 필요한지 밝힙니다.
- 토큰과 개인 키를 저장하거나 공유해서는 안 되는 위치를 설명합니다.

작성자 정보와 원격 인증 계정은 서로 다른 설정입니다. 둘을 각각 확인할 수 있는 명령을 함께 제공하면 초기 설정 오류를 줄일 수 있습니다.

## 커밋

- 커밋 메시지 형식과 언어를 정합니다.
- 생성 파일과 잠금 파일을 추적하는 기준을 설명합니다.
- 하나의 커밋이 독립적으로 검토·검증·되돌리기 가능한 범위를 갖도록 안내합니다.
- 커밋 전에 실행할 형식 검사와 테스트 명령을 기록합니다.

```bash
git status --short
git diff --staged --check
git diff --staged
```

## 풀 리퀘스트

- 초안 상태를 사용하는 기준과 필요한 승인 수를 정합니다.
- 필수 CI 작업, CODEOWNERS 적용 범위와 대상 브랜치를 명시합니다.
- PR 본문에는 변경 이유, 구현 내용, 검증 결과와 리뷰가 필요한 판단을 적도록 안내합니다.
- 관련 없는 작업과 후속 작업은 현재 범위와 구분합니다.

## 기준 브랜치 동기화와 충돌

- 작업 브랜치에 기준 브랜치를 merge할지 rebase할지 정합니다.
- 공유 브랜치의 `rebase`와 강제 푸시 허용 범위를 명시합니다.
- 충돌 해결 뒤 다시 실행해야 하는 검증을 기록합니다.
- 강제 푸시가 필요하다면 일반 `--force` 대신 `--force-with-lease`를 사용하는 조건을 설명합니다.

## 병합과 정리

- 병합 커밋, 스쿼시 병합, 리베이스 병합 가운데 허용하는 방식을 정합니다.
- 병합된 브랜치의 자동 삭제 여부를 설명합니다.
- 태그와 릴리스 브랜치의 생성 권한과 이름 규칙을 명시합니다.

## 사고 대응

- 공유된 커밋을 취소할 때는 원칙적으로 `git revert`를 사용합니다.
- 잘못된 강제 push가 발생하면 추가 push를 멈추고 저장소 관리자와 복구 기준점을 확인합니다.
- 비밀값이 커밋되면 이력 정리보다 먼저 해당 자격 정보를 폐기하고 교체합니다.
- 데이터가 사라질 수 있는 명령의 승인과 백업 기준을 정합니다.

정책에는 팀이 실제로 지킬 규칙과 실행 가능한 명령만 남깁니다. 선택하지 않은 예시나 빈 항목을 그대로 두면 작업자가 현재 정책으로 오해할 수 있습니다.
